Helm Charts

Deploying one service means writing a Deployment, a Service, a ConfigMap, and applying them by hand. Deploying forty microservices across dev, staging, and prod means templating, versioning, and releasing them as one unit. Helm is Kubernetes' package manager — this guide covers what a chart physically is, every file inside it, the full render-and-release pipeline, and the tools that compete with it — grounded in the jahez-prod cluster.

Part 01 · Foundations

Definitions — what each thing physically is

Before commands and templates: what Helm's core nouns actually are on disk, in etcd, and in memory.

Helm

WHAT IT IS · a single client-side Go binary on your machine / CI runner
Official

The Helm project defines it as the package manager for Kubernetes — a tool for defining, installing, and upgrading applications packaged as charts. It is a CNCF graduated project (same maturity tier as Kubernetes itself and Prometheus).

Simple

apt / NuGet for your cluster. Instead of hand-applying YAML files, you install, upgrade, and remove whole applications by name and version.

In-depth

A client-side program that (1) fetches a chart from disk, an HTTP repo, or an OCI registry, (2) deep-merges values, (3) renders Go templates into plain manifests, (4) submits them to the kube-apiserver over the standard API using your kubeconfig identity, and (5) records the result as a versioned release. Since v3 there is no server-side agent — Helm v2's Tiller was removed because it held cluster-admin-like power that bypassed per-user RBAC.

Details

Distributed as one static binary per OS/arch. The same logic is exposed as a Go SDK, which is how Argo CD, Flux, and the Terraform helm provider embed Helm without shelling out. Extensible via a plugin system (helm plugin install … — helm-diff and helm-secrets being the two you'll actually use). Release state driver is configurable with HELM_DRIVER: secret (default), configmap, or sql (PostgreSQL) for very large release payloads.

Used for

Installing third-party platform software (ingress-nginx, Redis, Datadog agent, cert-manager) in minutes; packaging your own microservices for repeatable deploys; the deploy step of CI/CD; instant whole-app rollback during incidents.

Chart

WHAT IT IS · a directory (or its .tgz archive) with a defined layout
Official

Per the Helm docs, a chart is a collection of files that together describe a related set of Kubernetes resources — from a single memcached pod to a full web-app stack.

Simple

A folder: metadata (Chart.yaml) + default settings (values.yaml) + templated manifests (templates/). The recipe, not the meal.

In-depth

Two types exist: application (deployable) and library (only exports named templates for other charts to include — your shared jahez-service base would be one). Charts compose: the dependencies: list pulls subcharts into charts/, each configured through its own key in the parent's values (redis.*) and toggled with condition: flags.

Details

Packaged as <name>-<version>.tgz — name and SemVer version are part of the artifact identity, and a published version is treated as immutable (repos won't let you overwrite 1.4.2; you publish 1.4.3). Charts can be cryptographically signed: helm package --sign produces a .prov provenance file that helm verify / helm install --verify checks against a keyring — supply-chain protection for internal registries.

Used for

One chart per deployable service (menu-api, orders-api); an umbrella chart composing a whole environment out of subcharts; a library chart deduplicating the 95%-identical manifests across your microservices.

Release

WHAT IT IS · one named installation of a chart, stored as Secrets in the target namespace
Official

The docs define a release as an instance of a chart running in a Kubernetes cluster — one chart can be installed many times, each install creating a new independently-named release.

Simple

Chart + your values + a name = a release. menu-api-dev and menu-api-prod are two releases of one chart.

In-depth

Helm persists every revision of a release as a Kubernetes Secret named sh.helm.release.v1.<release>.v<rev> (type helm.sh/release.v1) in the release namespace: a gzipped, base64-encoded protobuf holding the chart, the merged values, the rendered manifests, and a status. A release is always in exactly one state: deployed, superseded, failed, uninstalling, or one of the transient pending-install / pending-upgrade / pending-rollback states.

Details

Those pending-* states matter operationally: if a CI job is killed mid-upgrade, the release stays pending and every later upgrade fails with "another operation is in progress" — recovered with helm rollback or, last resort, deleting the stuck revision Secret. Because state lives in the namespace, RBAC on Secrets is RBAC on release management; and helm get values/manifest works from any machine with cluster access — the ledger travels with the cluster, not with the laptop that deployed.

Used for

Running many isolated copies of one chart (per env, per tenant, per PR-preview namespace); incident forensics — proving exactly what config was live at 02:00; whole-set rollback.

Values

WHAT IT IS · a YAML tree merged into the template render context as .Values
Official

The docs describe values as the mechanism for supplying configuration to a chart's templates — the chart author ships defaults in values.yaml, and users override them at install/upgrade time.

Simple

The settings panel of the chart. Everything meant to differ per environment — replicas, tags, hostnames, resources — lives here.

In-depth

Sources deep-merge in priority order: chart values.yaml → parent-chart overrides → -f files left-to-right → --set family. Subcharts see only their slice: keys under redis: in the parent become the redis subchart's whole .Values; keys under global: are the one tree visible to every chart in the dependency graph (cluster domain, region, image registry).

Details

Setting a key to null via --set key=null deletes the default rather than overriding it. --set-string forces string typing (protects tag: "1.30" from becoming the float 1.3); --set-file cert=tls.pem loads a file's content into a value. helm get values shows only user-supplied overrides; add --all for the fully merged tree.

Used for

Per-environment sizing and endpoints; feature flags (autoscaling.enabled); toggling whole subcharts (redis.enabled=false in prod where you run managed Redis); injecting CI variables (--set image.tag=$GIT_SHA).

Template

WHAT IT IS · a YAML file containing Go text/template expressions, rendered client-side
Official

The docs describe the template files under templates/ as the heart of a chart: Helm runs them through its template engine and sends the rendered output to Kubernetes.

Simple

YAML with holes. {{ .Values.replicaCount }} gets filled in at render time; until then the file isn't valid Kubernetes YAML.

In-depth

The engine is Go's text/template extended with ~70 Sprig functions (string, math, date, crypto, dict/list manipulation) plus Helm-specific ones: include, required, tpl, toYaml, lookup (query live cluster objects during install — returns empty in helm template). Rendering is text-based, which is why whitespace control ({{- / -}}) and nindent exist — the engine has no idea it's producing YAML.

Details

All templates of a chart and its subcharts share one namespace of {{ define }} names — hence the <chartname>.helpers naming convention to avoid collisions. Files beginning with _ render to nothing (definitions only). Annotating a rendered object with helm.sh/hook turns it into a lifecycle hook (see the hooks example in Part 09) instead of a regular tracked resource.

Used for

Parameterizing manifests; conditionally emitting whole objects (HPA only when autoscaling is on); standardized labels/names via helpers; generating config checksums that roll pods on change.

Repository

WHAT IT IS · an HTTP server hosting an index.yaml + chart .tgz files (or an OCI registry)
Official

The docs define a repository as the place where charts are collected and shared — conceptually the cluster world's equivalent of a package feed.

Simple

A website serving chart archives plus one index file. nuget.org for charts.

In-depth

A classic repo is pure static hosting: index.yaml (every chart name, version, digest, URL) + the .tgz files — S3/GitHub Pages/ChartMuseum all work. Since Helm 3.8, OCI registries are first-class: charts are pushed/pulled as OCI artifacts (oci://ghcr.io/jahez/charts/menu-api) living beside your container images, reusing the registry's auth, replication, and retention.

Details

OCI references skip helm repo add/update entirely — no local index cache to go stale; you address charts directly by registry path + --version. Discovery across public repos happens on Artifact Hub. For classic repos, helm repo update re-downloads indexes; forgetting it is why "version not found" errors happen right after a release.

Used for

Consuming community charts (bitnami, prometheus-community, ingress-nginx); publishing internal charts to ECR/GHCR/Harbor next to images so chart 1.4.2 and image 2.7.1 share one registry, one auth, one retention policy.

Revision

WHAT IT IS · a monotonically increasing integer per release; one Secret per revision
Official

In Helm's model, every install starts a release at revision 1, and each upgrade or rollback increments the revision counter — the docs describe rollback targets by these revision numbers.

Simple

The release's save-game slots. Revision 5 = the fifth state this release has ever been in.

In-depth

History is append-only: helm rollback menu-api 2 doesn't rewind to revision 2 — it appends a new revision whose content equals revision 2 and marks it deployed. Exactly one revision per release is deployed at any time; earlier good ones are superseded, broken ones stay failed forever as evidence.

Details

Retention is capped by --history-max (default 10) — oldest Secrets are pruned beyond it, which also bounds how far back you can roll. Each revision Secret stores the complete rendered manifests, so upgrades compute a three-way merge (old manifest ↔ new manifest ↔ live object) — that's how Helm tolerates fields other controllers add to live objects without fighting them.

Used for

helm history as the incident timeline; helm rollback <rel> <rev> targeting; diffing what changed between two deploys (helm get manifest --revision).

What Helm is used for — the six real scenarios

Installing platform software

ingress-nginx, cert-manager, Redis, Kafka, the Datadog agent — hundreds of manifests each, consumed with two commands and a small values file. This alone is why Helm is unavoidable: the ecosystem ships as charts.

Packaging internal services

menu-api as a versioned artifact (chart 1.4.2 / app 2.7.1) in the same registry as its image — deployable to any cluster, any namespace, by anyone with the values file.

The CI/CD deploy step

One idempotent command — helm upgrade --install … --atomic --wait — replaces apply scripts, adds readiness gating, and self-rolls-back on failure.

Multi-environment fan-out

dev / staging / prod (and Tier-2 region variants) as thin values files over one chart, instead of parallel YAML trees that drift apart.

Incident response

helm history for "what changed at 02:00?", helm get values for "what's actually configured?", helm rollback for "make it yesterday again" — Deployment and ConfigMap together.

Composition

An umbrella chart declaring the whole stack as dependencies; a library chart deduplicating the shared Deployment/Service/HPA shape across every microservice.

Mental model
Chart = the recipe (versioned, parameterized). Values = the ingredients you chose. Release = the cooked meal running in a namespace. Revision = each time you re-cooked it. Helm itself is just the chef's knife — a local binary; the cluster never runs any Helm software.

Where this breaks down
It works for one service in one environment. But jahez-prod runs home, search, menu, and orders — each needing dev/staging/prod variants. That's 4 files × 4 services × 3 environments = 48 hand-maintained YAMLs that differ only in replicas, image tags, hostnames, and resource sizes. kubectl rollout undo only rolls back the Deployment — never the ConfigMap that changed with it (the exact coupling that bit you in the time-slot CMS incident: config and workload versions drifting independently).
Part 03 · The problem

Why Helm exists — the four gaps in raw kubectl

Helm answers four operational questions that kubectl apply cannot.

1 · Parametrization

The same Deployment differs across environments only in a handful of fields (replicas, tag, resources, hostnames). Raw YAML forces full-file duplication; templates extract the differences into one values-<env>.yaml each.

2 · Atomic release units

Deployment + Service + ConfigMap belong together. Helm installs, upgrades, and — critically — rolls back all of them as one unit. kubectl rollout undo covers only the Deployment.

3 · Versioned history

Each release revision (chart + values + rendered manifests) is stored in-cluster as a Secret. helm history shows exactly what was live at 02:00 during an incident; git alone can't prove what was applied.

4 · Distribution & reuse

Installing Redis, ingress-nginx, or Datadog's agent should not mean hand-writing 30 manifests. Repositories let you consume community charts with two commands — and publish your own internal jahez-service library chart.

Part 04 · The pipeline

Helm architecture — from chart to running pods

One command, six stages. Every stage below is self-contained: a plain-language explanation first, then its diagram, then the real files and real outputs — each artifact in its own block, every YAML complete.

The story in one paragraph: you run one command on your laptop or CI runner. Helm reads a folder (the chart) and your settings (values), merges the settings into one tree, fills that tree into the templates to produce normal Kubernetes YAML, sends that YAML to the cluster's API server, saves a snapshot of everything as a Secret, and then ordinary Kubernetes takes over and starts the pods. That's the whole pipeline. Now step by step.

the one command we follow end-to-endanatomy · every flag explained
helm upgrade --install menu-api ./menu-api \   # upgrade if release exists, install if not (idempotent)
  -n jahez-prod --create-namespace \           # target namespace; create it on first run
  -f values-prod.yaml \                        # environment overrides file
  --set image.tag=2.7.1 \                      # the CI variable (usually $GIT_SHA / version)
  --atomic --wait --timeout 5m                 # block until Ready; auto-rollback on failure
01

The inputs — what exists on disk before anything runs

location: workstation / CI runner · cluster contact: none

Simple version: before the command runs, everything is just files in a folder. No cluster is involved yet. Helm needs three things, all local:

  • The chart — the menu-api/ folder: metadata, default settings, and templates.
  • Your settings — values-prod.yaml from git, plus --set image.tag=2.7.1 from CI.
  • Your identity — ~/.kube/config, the same file kubectl uses. Same user, same RBAC. If kubectl can't create a Deployment in jahez-prod, neither can Helm.

ThingSource of truthWhere it is when helm runsEver in the cluster?

So git is the source of truth, the machine's disk is just a checkout, and the cluster holds only the results — applied objects plus the release-Secret snapshot. Deleting the laptop loses nothing.

Hint — "workstation / CI runner" means: wherever the helm binary runs

There is no special deploy machine. Three common approaches, identical pipeline, different trigger:

1 · Your laptop — you type the command by hand. Fine for dev, risky for prod (whatever kubeconfig context you forgot to switch is what gets deployed).

2 · A CI runner — the normal production path. A GitHub Actions / GitLab job spins up a temporary container, clones the repo (chart + values arrive via git clone), receives credentials as a masked variable, runs the exact same helm upgrade --install, and is destroyed. "Workstation" here is a disposable Linux box that lives for two minutes.

3 · A GitOps controller — Argo CD / Flux invert the direction: a pod inside the cluster watches the git repo, runs the render itself (Helm as an SDK, steps 2–3), and applies the output. Nobody runs a deploy command at all; merging to git is the deploy. Same chart, same values files — only the machine and the trigger change.

Values resolution — building the .Values tree

operation: deep merge · order: defaults → -f file → --set · lists don't merge

Simple version: Helm has three sources of settings and must turn them into one. The rule is easy: the later source wins, key by key. Defaults lose to the prod file; the prod file loses to --set. Keys the prod file never mentions (like timezone) simply keep their default — that inheritance is why values-prod.yaml is 10 lines, not 60.

The one trap: this merging is per-key for maps, but lists are replaced whole. Override one item of a list and you've replaced the entire list.

03

Rendering — templates become plain Kubernetes YAML

engine: Go text/template + Sprig · runs on your machine · zero cluster changes

Simple version: Helm takes each file in templates/, replaces every {{ … }} with real values from step 2, and writes out normal YAML. After this step there is nothing Helm-specific left in the output — you could kubectl apply it by hand. helm template runs the pipeline exactly this far and prints the result, which is how you preview a deploy safely.

In depth: the engine first loads all {{ define }} helpers from _helpers.tpl, then executes each template with four context objects: .Values (step 2), .Release (name menu-api, namespace jahez-prod, revision), .Chart (Chart.yaml), and .Capabilities (cluster version/APIs). Rendering is text substitution — the engine doesn't know it's writing YAML, which is why nindent exists and why this step is where you debug.

04

Submission — ordered apply through the kube-apiserver

the only network crossing · kind-sorted · ownership stamped · three-way merge on upgrades

Simple version: Helm now sends the three manifests to the cluster — through the same API server, with the same credentials, that kubectl would use. It doesn't send them randomly: ConfigMap goes before Deployment (so the pods' envFrom has something to read), and every object gets stamped with "Helm owns this" metadata on the way in.

In depth — three behaviors that matter:

  • Kind-aware ordering. Manifests are sorted by a fixed priority list so dependencies exist before consumers. Uninstall runs the exact reverse.
  • Ownership stamping. The meta.helm.sh/release-name annotations are how Helm finds its objects later, and how it refuses to overwrite objects owned by someone else.
  • Three-way merge on upgrade. Helm compares old manifest ↔ new manifest ↔ live object, so fields other controllers added to the live object (an injected Datadog annotation, HPA-managed replicas) survive your upgrades instead of being blindly stomped.

06

Running — controllers and the scheduler take over

standard Kubernetes from here · what --wait actually watches · pods across 3 nodes

Simple version: Helm's work is done. Kubernetes itself now turns the Deployment into running pods, in a chain of hand-offs:

  • controller-manager sees the Deployment → creates a ReplicaSet (menu-api-7d4f9c8b6).
  • ReplicaSet controller → creates 6 Pod objects (Pending, no node yet).
  • scheduler → assigns each pod to a node, spreading across node-1/2/3.
  • kubelet on each node → pulls ghcr.io/jahez/menu-api:2.7.1, starts dotnet Menu.API.dll, probes /healthz/ready.
  • Pods that pass readiness are added to the Service's EndpointSlices → traffic flows.

What --wait does: Helm polls this convergence — for the Deployment, ready replicas == 6. If that never becomes true within --timeout 5m (a bad readiness probe, a crashing container), --atomic rolls back automatically. Your readiness probe is, literally, the release gate.

Chart structure — every file and folder

menu-api/chart layout

Chart.yaml required
The chart's identity card: name, SemVer chart version, the packaged app's appVersion, dependencies, maintainers. The only file Helm refuses to work without. Full property table in the next section.
values.yaml optional
Default values for every template expression. This is the chart's API: anything a consumer should be able to change belongs here with a sane default; anything not exposed here is effectively hard-coded.
values.schema.json optional
JSON Schema applied to the final merged values on install/upgrade/lint. Rejects typos like replicaCont: 6 before anything reaches the cluster — the Helm equivalent of DTO validation attributes.
templates/ required*
Every .yaml/.tpl file here goes through the render engine. Files starting with _ produce no output — they only define reusable named templates. (*Required in practice; a chart with no templates deploys nothing.)
templates/_helpers.tpl
Convention home for {{ define }} blocks: standardized names, label sets, image strings. Called via {{ include "menu-api.labels" . }}. Keeps every manifest's metadata identical — the same role your C# base classes and extension methods play.
templates/NOTES.txt
A template whose rendered output is printed to the terminal after install/upgrade instead of being applied. Used for "your release is live at…" instructions, port-forward hints, credential retrieval commands.
templates/tests/
Pod manifests annotated helm.sh/hook: test. helm test menu-api runs them post-deploy — e.g. a curl pod asserting /healthz/ready returns 200. Smoke tests as part of the package.
charts/
Vendored subcharts pulled by helm dependency update from the dependencies: list in Chart.yaml (arrives as .tgz files). Lets menu-api ship with, say, a Redis chart it depends on.
crds/
Plain (non-templated) CustomResourceDefinitions. Helm installs these before templates render so CRs in templates/ have their types registered. Caveat: Helm never upgrades or deletes CRDs — that's deliberate data-safety behavior.
Chart.lock
Generated pin-file recording exact resolved dependency versions — the packages.lock.json of the chart world. Commit it; helm dependency build reproduces charts/ from it byte-for-byte.
.helmignore
Glob patterns (like .gitignore) excluded when packaging: .git/, *.md~, CI configs — keeps the published .tgz minimal.

Whitespace control
{{- eats whitespace (including the newline) before the expression; -}} eats it after. Forgetting them is the #1 source of broken YAML indentation. Debug with helm template --debug, which prints the rendered output even when it's invalid YAML.

Hooks — running Jobs at lifecycle points

Annotating a rendered object with helm.sh/hook removes it from the normal release and runs it at a lifecycle moment instead. The canonical use: EF Core migrations before the new pods start — solving the "new code, old schema" race that plain rolling updates have.

templates/migration-job.yamlpre-upgrade hook · EF Core
apiVersion: batch/v1
kind: Job
metadata:
  name: {{ include "menu-api.fullname" . }}-migrate-{{ .Release.Revision }}
  annotations:
    "helm.sh/hook": pre-install,pre-upgrade   # run BEFORE manifests are applied
    "helm.sh/hook-weight": "0"                 # lower weights run first
    "helm.sh/hook-delete-policy": before-hook-creation,hook-succeeded
spec:
  backoffLimit: 1
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: {{ include "menu-api.image" . | quote }}
          command: ["dotnet", "Menu.API.dll", "--migrate-only"]
          envFrom:
            - configMapRef:
                name: {{ include "menu-api.fullname" . }}-config

How it flows: helm upgrade → hook Job runs and must complete (Helm waits) → only then are the Deployment/Service/ConfigMap applied → rollout proceeds against the already-migrated schema. If the migration fails, the upgrade aborts and the old revision keeps serving — with --atomic, entirely automatically. Available hook points: pre/post-install, pre/post-upgrade, pre/post-rollback, pre/post-delete, test.

Hook caveats
Hook resources are not part of the release: rollback doesn't touch them and uninstall doesn't delete them — cleanup is the job of hook-delete-policy. before-hook-creation (delete the previous run's Job before creating the new one) plus hook-succeeded is the standard pair; keep failed Jobs around so kubectl logs job/…-migrate-7 can tell you why 02:00 went sideways.

--set syntax — the gotchas

terminalworked examples · correct vs broken

Part 12 · Discipline

Principles & best practices

What separates a chart you can trust in jahez-prod from one that pages you.

1 · values.yaml is a public API — design it like one

Flat where possible, grouped by concern (image.*, service.*, resources.*), every key with a working default, documented with comments. Ship values.schema.json so typos fail at lint time, not at 2 AM. Breaking a values key is a breaking change — bump the chart's major version.

2 · Make CI deploys idempotent and self-healing

helm upgrade --install --atomic --wait --timeout 5m as the single pipeline command. It installs on first run, upgrades after, blocks until pods are actually Ready, and rolls back automatically on failure — your probes become the release gate.

3 · Roll pods when config changes

Updating a ConfigMap does not restart consumers of envFrom. The checksum/config annotation (sha256 of the rendered ConfigMap in pod-template annotations) forces a rolling update whenever config content changes — killing the config/workload drift class of incident.

4 · Pin everything

Never tag: latest; deploy explicit tags via --set image.tag=$GIT_SHA or CI-written values. Pin dependency versions and commit Chart.lock. Pin community chart versions in install commands — an unpinned helm repo update && helm upgrade is a supply-chain surprise waiting to happen.

5 · Keep real secrets out of values files

Values end up in git, CI logs, and the release Secret. Reference secrets instead of embedding them: External Secrets Operator / Vault injection, or encrypt values with helm-secrets + SOPS. The chart should template the reference (secretKeyRef), not the Mada merchant key itself.

6 · One library chart to rule your microservices

Home, search, menu, orders share 95% of their manifests. Publish an internal type: library chart (jahez-service) holding the common Deployment/Service/HPA templates; each service's chart becomes a thin wrapper: a Chart.yaml, a values.yaml, and includes. One fix propagates everywhere — the platform-team pattern used by most large orgs.

7 · Lint, template, diff — in that order, in CI

helm lint catches structural errors, helm template | kubeconform validates against real API schemas, helm diff upgrade posts the change preview to the PR. Rendered-manifest review catches the nindent 4-vs-nindent 8 bugs that lint can't.

Part 13 · Ecosystem

Tools like Helm — and how they differ

Helm's competitors attack the same problem — "raw YAML doesn't scale" — from four different philosophies: patching, templating, real programming languages, and typed configuration languages.

Kustomize — patch, don't template

Philosophy: keep manifests as plain, valid YAML and layer overlays of patches on a common base. No template syntax, no curly braces — every file is always parseable. It's built into kubectl (kubectl apply -k), so there is nothing to install.

kustomize layout + overlaybase/overlays pattern
menu-api/
├── base/
│   ├── deployment.yaml        # complete, valid manifests (the dev shape)
│   ├── service.yaml
│   └── kustomization.yaml     # resources: [deployment.yaml, service.yaml]
└── overlays/
    ├── staging/kustomization.yaml
    └── prod/
        ├── kustomization.yaml
        └── patch-replicas.yaml

# overlays/prod/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: jahez-prod
resources: [../../base]
images:
  - name: ghcr.io/jahez/menu-api
    newTag: "2.7.1"
patches:
  - path: patch-replicas.yaml       # strategic-merge: just {spec: {replicas: 6}}
configMapGenerator:
  - name: menu-api-config
    literals: [ASPNETCORE_ENVIRONMENT=Production]
    # generated name gets a content hash suffix → pods roll on config change automatically

# deploy
kubectl apply -k overlays/prod

Strengths: zero install, always-valid YAML, content-hashed ConfigMaps solve the restart-on-change problem natively, favored by GitOps purists. Trade-offs: no packaging/versioning/distribution, no release history or rollback (git is your history), no conditionals — complex variation across many environments becomes a maze of patch files. Kustomize and Helm are often combined: Helm renders, Kustomize applies org-wide patches on top (Argo CD supports this natively).

Helmfile — orchestrating many Helm releases

Not a Helm replacement but a layer above it: one declarative helmfile.yaml describing all releases in an environment — the whole jahez-prod stack — with shared values, ordering, and diffing. helmfile apply diffs and converges everything. The answer to "we have 25 helm upgrade commands in a shell script."

helmfile.yamlstack as one file
environments:
  prod:
    values: [env/prod.yaml]

releases:
  - name: menu-api
    namespace: jahez-prod
    chart: oci://ghcr.io/jahez/charts/menu-api
    version: 1.4.2
    values: [values/menu-api/prod.yaml]
  - name: orders-api
    namespace: jahez-prod
    chart: oci://ghcr.io/jahez/charts/orders-api
    version: 2.1.0
    needs: [jahez-prod/menu-api]   # ordering between releases

cdk8s — manifests in a real programming language

Define resources in TypeScript, Python, Java, or Go with typed constructs; cdk8s synth emits plain YAML you apply with kubectl/Argo. You get compiler type-checking, IDE autocomplete, refactoring, unit tests, loops and abstraction as ordinary code — no template whitespace debugging ever. Trade-offs: output is static YAML (no release lifecycle — pair with GitOps), and it adds a toolchain + synth step; the team must treat infra as a software project.

main.tscdk8s · typed constructs
import { App, Chart } from 'cdk8s';
import { Deployment, Service, EnvValue } from 'cdk8s-plus-30';

class MenuApi extends Chart {
  constructor(scope: App, id: string, replicas: number, tag: string) {
    super(scope, id, { namespace: 'jahez-prod' });
    const deploy = new Deployment(this, 'deploy', {
      replicas,
      containers: [{
        image: `ghcr.io/jahez/menu-api:${tag}`,
        command: ['dotnet', 'Menu.API.dll'],
        portNumber: 8080,
        envVariables: { TZ: EnvValue.fromValue('Asia/Riyadh') },
      }],
    });
    deploy.exposeViaService({ ports: [{ port: 80, targetPort: 8080 }] });
  }
}
const app = new App();
new MenuApi(app, 'menu-api', 6, '2.7.1');
app.synth();   // → dist/menu-api.k8s.yaml

Carvel ytt + kapp — structure-aware templating + a real apply engine

ytt templates YAML as a data structure (annotations in comments, Starlark/Python-like logic), so it can never emit indentation-broken output the way text templating can; it also does overlays like Kustomize. kapp replaces the apply side: groups resources into an "app", shows a diff before changing anything, orders operations by dependency, and waits on actual readiness. Powerful and composable; smaller community than Helm and its own syntax to learn.

Jsonnet / Tanka & Timoni (CUE)

Jsonnet (with Grafana's Tanka) is a functional configuration language generating JSON/YAML — deep composition and inheritance, beloved for large monitoring stacks (the kube-prometheus library), with a real learning curve. Timoni uses CUE, where types and constraints are first-class: invalid config (a negative replica count, a malformed URL) fails at evaluation, not in the cluster. Timoni deliberately mirrors Helm's UX (modules ≈ charts, instances ≈ releases, OCI distribution) and is the most direct "modern Helm" candidate, but the ecosystem is young — you'll write your own modules rather than pull community ones.
