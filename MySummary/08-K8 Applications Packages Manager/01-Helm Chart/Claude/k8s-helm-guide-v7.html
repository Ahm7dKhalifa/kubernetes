Helm Charts

Deploying one service means writing a Deployment, a Service, a ConfigMap, and applying them by hand. Deploying forty microservices across dev, staging and prod means templating, versioning and releasing them as one unit. Helm is Kubernetes' package manager — this guide goes from the concepts, to every file and flag, to exam-style labs, grounded in the jahez-prod namespace on EKS in me-central-1.

1.0What is Helm

In one sentenceHelm is the package manager for Kubernetes: it packs all the YAML an app needs into one versioned chart, fills it with your settings for each environment, installs it as one unit, and remembers every deploy so you can roll back.
What it is
A single command-line program, helm, written in Go. It runs on your laptop or a CI runner and talks to the cluster through the normal Kubernetes API, using your kubeconfig. It is a graduated CNCF project, like Kubernetes itself.
The problem it solves
One service needs several YAML files (ConfigMap, Deployment, Service…). Forty services in dev, staging and prod become hundreds of near-identical files, deployed one by one, with no record of what is running and no single "undo". Helm replaces them with one chart per service plus one small values file per environment.
How it works
  1. Read the chart and your values files from disk.
  2. Render: fill every {{ }} blank in the templates → plain Kubernetes YAML.
  3. Apply that YAML to the cluster in the right order, as you — like a careful kubectl apply.
  4. Record the deploy as a numbered revision (a Secret in the namespace).
Then Helm exits. Kubernetes itself runs the Pods.
Think of it as
NuGet or apt for your cluster: a package (chart) has a name and a version, you install it with options (values), and you can upgrade or roll back it later.
At Jahez
Every service (menu-api, orders-api, home, search) has a chart. CI runs helm upgrade --install menu-api … -f environments/values-prod.yaml --set image.tag=$GIT_SHA on every merge. Ready-made software — ingress-nginx, cert-manager, Prometheus — is installed from community charts.

Three tools in one

What Helm is not

It is not…BecauseExample
a program running in the clusterHelm is client-only. Helm 2 had an in-cluster server (Tiller); Helm 3 removed it.kubectl get pods -A | grep -i tiller # nothing

a build toolIt never builds images; it only points at tags your CI already pushed.--set image.tag=$GIT_SHA
a replacement for Kubernetes YAMLTemplates still produce normal Deployments, Services, ConfigMaps.helm get manifest menu-api -n jahez-prod

Step 2 / 4

Releasing a new version

You: edit the Deployment · re-apply
  • Change the image tag by hand (2 places).
  • A rollback restores the Deployment only — the ConfigMap that changed with it stays new.
release 2.7.1 by handbash
# ① edit the tag in the Deployment (image + version label)
sed -i 's/2.7.0/2.7.1/g' 02-deployment.yaml
# ② re-apply only that file
kubectl apply -f 02-deployment.yaml
# ③ something breaks → undo
kubectl rollout undo deployment/menu-api-deployment -n jahez-prod
# ④ but the ConfigMap stays on the new settings
kubectl get cm menu-api-config-map -n jahez-prod -o yaml

Gap: no "undo everything that changed together".

Step 3 / 4

4 services × 3 environments

You: maintain 48 files
  • home, search, menu, orders — each in dev, staging, prod.
  • The files are 95% identical; only a few values differ.
deploy everything by handbash
# 4 services × 3 environments, 4 files each
for svc in home search menu orders; do
  for env in dev staging prod; do
    kubectl apply -f k8s/$svc/$env/ -n jahez-$env
  done
done
# → 12 folders, 48 files to keep in sync by hand
# → which tag runs in prod? only kubectl can tell
kubectl get deploy -n jahez-prod \
  -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image

Gap: copy-paste YAML, and no record of what is actually running.

Step 4 / 4

The same work with Helm

You: write 1 chart + 1 small values file per environment
  • One command installs or upgrades all objects together.
  • Every deploy is saved as a numbered revision you can roll back to.
the same work with Helmbash
# ① same chart, one values file per env
helm upgrade --install menu-api ./menu-api \
  -n jahez-dev -f environments/values-dev.yaml
helm upgrade --install menu-api ./menu-api \
  -n jahez-staging -f environments/values-staging.yaml
helm upgrade --install menu-api ./menu-api \
  -n jahez-prod -f environments/values-prod.yaml

# ② new version: change one value
helm upgrade menu-api ./menu-api -n jahez-prod \
  -f environments/values-prod.yaml --set image.tag=2.7.1

# ③ what runs, and every past deploy
helm list -n jahez-prod
helm history menu-api -n jahez-prod

# ④ undo all objects together
helm rollback menu-api 1 -n jahez-prod

The seven blocks, one card each

1

Helm

the tool
In one sentence
A command-line tool that installs, upgrades and removes apps on Kubernetes from packages called charts.
Think of it as
An app store (or NuGet) for your cluster.
Where it lives
A single program on your laptop or CI runner. Nothing Helm-specific runs inside the cluster.
menu-api example
helm upgrade --install menu-api ./menu-api -n jahez-prod
Watch out
Helm uses your kubeconfig, so it acts as you, on whatever cluster your current context points at.
2

Chart

the package
In one sentence
A folder that describes everything one app needs: templates for its Kubernetes objects plus default settings.
Think of it as
A recipe.
Where it lives
As a folder in git while you work on it; as a .tgz file in a registry once published.
menu-api example
menu-api/ → Chart.yaml, values.yaml, templates/ · packed: menu-api-1.5.0.tgz
Watch out
A published version cannot be overwritten — any change ships as a new version number.
3

Values

the settings
In one sentence
The settings you feed into a chart: replicas, image tag, hostnames, resources.
Think of it as
The ingredients you choose for the recipe.
Where it lives
Defaults in the chart's values.yaml; your overrides in values-prod.yaml (git) and --set flags (CI).
menu-api example
replicaCount: 6 · image.tag: 2.7.1
Watch out
helm upgrade does not remember your old --set flags unless you pass them again.
4

Template

the blueprint
In one sentence
A Kubernetes YAML file with blanks ({{ }}) that Helm fills in from the values.
Think of it as
A form letter with mail-merge fields.
Where it lives
The templates/ folder inside the chart.
menu-api example
replicas: {{ .Values.replicaCount }} → replicas: 6
Watch out
Helm fills blanks as plain text, so wrong indentation gives broken YAML. Preview with helm template.
5

Release

the installed app
In one sentence
One installed copy of a chart, in one namespace, under a name you choose.
Think of it as
The cooked meal on the table.
Where it lives
In the cluster: the Kubernetes objects it created, plus its history in the same namespace.
menu-api example
Release menu-api in jahez-prod. The same chart can also be release menu-api in jahez-dev.
Watch out
Names are unique per namespace — always pass -n, or Helm looks in the default namespace.
6

Revision

a saved version
In one sentence
A numbered snapshot of a release, saved every time you install, upgrade or roll back.
Think of it as
A save point in a game.
Where it lives
One Secret per revision in the release namespace.
menu-api example
sh.helm.release.v1.menu-api.v2 — rev 1 ran 2.7.0, rev 2 runs 2.7.1
Watch out
A rollback does not delete anything; it saves a new revision. Only the last 10 are kept by default.
7

Repository

the shop
In one sentence
A place where packaged charts are published and downloaded from.
Think of it as
A package feed, like nuget.org.
Where it lives
An OCI registry (same place as your images) or a website with an index.yaml.
menu-api example
helm push menu-api-1.5.0.tgz oci://ghcr.io/jahez/charts
Watch out
Website repos are cached locally: run helm repo update to see new versions. OCI needs no update.

3Architecture & workflow

3.1The pipeline at a glance ▶

The whole pipeline in one sentence: Helm turns a folder of templates plus your settings into normal Kubernetes YAML, sends that YAML to the cluster once, and saves a snapshot so you can always see or undo what it did.

On your machine · steps 1–3

Read the chart → merge the values → render the templates. Pure file processing; the cluster doesn't know anything is happening. helm template stops here.

Over the network · step 4

One authenticated conversation with the kube-apiserver: send the rendered YAML in dependency order, stamped with "Helm owns this".

In the cluster · steps 5–6

A snapshot Secret (the release record) and ordinary Kubernetes objects that the scheduler and kubelets turn into running pods. Helm itself is gone.

Keep one mental anchor: Helm is a preprocessor plus a careful kubectl apply plus a save-file.

10.0How a hook works

① The logic — read first

A hook is any template with a helm.sh/hook annotation. Helm pulls it out of the normal release and runs it at a lifecycle point, waiting for it (Jobs: completion; other kinds: created/ready). 15Best practices

15.1Eight rules & what to avoid

1Treat values.yaml as a public API
Why
Every consumer depends on its keys.
How
Group keys by question, give each a working default, add values.schema.json (8.2). Renaming a key = new major chart version.
2Deploy with one safe command
Why
CI must be repeatable and fail safely.
How
helm upgrade --install … --rollback-on-failure --wait --timeout 5m
3Restart Pods when config changes
Why
Pods don't reload a changed ConfigMap.
How
Add the checksum/config annotation (9.0).
4Pin every version
Why
Unpinned versions change under you.
How
No latest tags; --version on every install; commit Chart.lock.
5Keep secrets out of values
Why
Values end up in git, CI logs and the release Secret.
How
Reference an existing Secret (existingSecret, 8.0); create it with External Secrets.
6Share templates with a library chart
Why
Services are 95% the same.
How
One jahez-service library chart (11.1).
7Check before you deploy
Why
Lint can't see indentation bugs.
How
helm lint → helm template | kubeconform → helm diff upgrade in the PR.
8Name every object after its kind
Why
kubectl get all reads like an inventory.
How
{{ include "menu-api.fullname" . }}-deployment, -service, -config-map.
