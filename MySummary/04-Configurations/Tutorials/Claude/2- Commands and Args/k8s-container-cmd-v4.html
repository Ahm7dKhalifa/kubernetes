Container command & args
KUBERNETES · THE CONTAINER ENTRYPOINT

What a container actually runs
— command & args.

Every container runs exactly one foreground process, and two small fields in the Pod spec decide what it is: command and args. They override the image's built-in ENTRYPOINT and CMD — so you can change what a container does without rebuilding the image. Get them wrong and you get instant CrashLoopBackOff, broken graceful shutdown, or env vars that never expand. This guide takes both fields apart, grounded in the Jahez cluster (jahez-prod, me-central-1).

# the two fields this whole guide is about
command: ["dotnet", "Jahez.Api.dll"]  # overrides image ENTRYPOINT
args:    ["--urls", "http://0.0.0.0:8080"] # overrides image CMD
D0

Running your app — by hand vs by machine

Before Kubernetes, before even Docker, there's one question every container must answer: "what program do I run when I start?" The cleanest way to see why ENTRYPOINT/CMD exist is to watch what changes when a human stops being in the loop.

On your laptop, you run it yourself

You finish building the Jahez API. To run it, you open a terminal and type a command. During development that's usually:

▸ your terminal, during devyou type this
# build + run straight from source while developing
dotnet run

# …or, once you've published a release build:
dotnet publish -c Release -o ./publish
cd publish
dotnet Jahez.Api.dll --urls http://0.0.0.0:8080

The important part isn't the .NET syntax — it's that a person decided to run it. You knew which DLL to launch, which flags to pass, and which directory to be in. That knowledge lived in your head and your fingers.

In a container, no one is there to type it

Now you ship the app as a container image to run on the Jahez cluster. Containers don't get started by a developer at a keyboard. They get started automatically by the machine:

  • When you deploy a new version.
  • When the HPA scales jahez-api from 3 to 12 pods during an Iftar rush.
  • When a node reboots at 3am and Kubernetes reschedules its pods elsewhere.
  • When a crashed container is restarted seconds later.

In every one of those, there is no human to type dotnet Jahez.Api.dll --urls …. So the command you would have typed has to be recorded inside the image ahead of time, so the machine can run it for you, identically, every single time. That recording is exactly what ENTRYPOINT and CMD are.

Human runs it (dev laptop)

# you, deciding, at a prompt
dotnet Jahez.Api.dll --urls :8080

Knowledge lives in your head. Works because you're present to type it.

Machine runs it (container start)

# baked into the image — runs with no human
ENTRYPOINT ["dotnet", "Jahez.Api.dll"]
CMD        ["--urls", ":8080"]

Knowledge lives in the image. Works because the start command is pre-recorded.

The Dockerfile records the command you'd type

A Dockerfile builds the image. Its last instruction is where you write down that start command — turning "the thing the dev types" into "the thing the machine runs."

▸ Dockerfilebuild recipe
FROM mcr.microsoft.com/dotnet/aspnet:8.0
WORKDIR /app
COPY ./publish .                     # the built app filesystem
EXPOSE 8080

# ↓ the command the developer used to type, now recorded
ENTRYPOINT ["dotnet", "Jahez.Api.dll"]
CMD ["--urls", "http://0.0.0.0:8080"]

Now docker run ghcr.io/jahez/api — with nothing after it — runs dotnet Jahez.Api.dll --urls http://0.0.0.0:8080 on its own. The machine no longer needs you. That single shift, from a human typing the command to the image carrying it, is the entire reason ENTRYPOINT and CMD exist.

CONCEPT CHECK

A container runs one foreground process and stops the instant that process exits. ENTRYPOINT/CMD name that process. So they aren't an optional extra — without them the image has a filesystem but no answer to "what do I run?", and the container would have nothing to do.

D1

ENTRYPOINT & CMD — what each one is

The final command that runs the process inside a container is built from two parts:

ENTRYPOINT — the fixed part

  • Fixed — the command itself, the same on every run.
  • Required — something has to run; this is it.
  • Always first — it leads the final command line.
  • Always runs — arguments from docker run are added after it, they don't replace it.

CMD — the arguments

  • Arguments passed to the ENTRYPOINT.
  • Optional — an image can have none.
  • Has default values declared in the Dockerfile.
  • Overridable — values you pass to docker run replace the defaults.

The components of the final command

Read any container's start command as these two slots. The fixed slot comes from ENTRYPOINT; the argument slot comes from CMD (or from what you type on docker run):

pingENTRYPOINT — fixed · first · always runs
jahez.saCMD — arguments · optional · overridable
final command = ENTRYPOINT (fixed) + CMD (arguments)

The two parts side by side

PropertyENTRYPOINT fixed partCMD arguments
What it isThe command / executable that runsThe arguments passed to it
Required?Yes — something must runNo — optional
Position in final commandAlways firstAlways after the ENTRYPOINT
Default in the DockerfileThe executable to runDefault argument values
Args on docker runAppended after itReplace the default entirely
Changes per run?Never (fixed)Yes (overridable)
RULE

Final command = ENTRYPOINT + CMD. The ENTRYPOINT half never moves; the CMD half is whatever you didn't override (the Dockerfile default) or what you did (your docker run value).

More examples — different images, same two parts

Every image splits the same way. blank "you run" = no override, so the CMD default is used; a value in "you run" replaces the CMD half.

ENTRYPOINT fixedCMD default argsYou runFinal command
pingjahez.sadocker run imgping jahez.sa
pingjahez.sadocker run img keeta.comping keeta.com
nodeserver.jsdocker run imgnode server.js
pythonapp.pydocker run img worker.pypython worker.py
nginx-g "daemon off;"docker run imgnginx -g daemon off;
java -jar app.jar--port=8080docker run img --port=9090java -jar app.jar --port=9090
WATCH ROW 4

Overriding replaces the whole CMD: with ENTRYPOINT python and CMD app.py, running docker run img worker.py gives python worker.py — app.py is gone, not kept alongside. Your value replaces the default argument, it doesn't add to it.

ESCAPE HATCH

"Fixed" means fixed in normal use. You can replace the ENTRYPOINT for one run with the explicit --entrypoint flag: docker run --entrypoint sh img. It's deliberately awkward because overriding the fixed part is rarely what you want.

D2

How they combine — and the bridge to Kubernetes

Now the full picture. Most images use both together: ENTRYPOINT is the fixed command, and CMD is the argument — a default you can override. Below are the three cases you'll meet, all using one tiny ping image so the only thing changing is the argument. The purple part is always fixed; the blue part is the argument.

ping (purple) never changes — only the argument does: none → CMD default → your override

Case 1 — ENTRYPOINT only

No default argument is baked in. ping always runs, but you must supply the host every time.

▸ Dockerfilecase 1
FROM alpine
ENTRYPOINT ["ping"]
▸ developer terminalfinal command
docker run pinger
# final command →  ping
# (no host → ping prints a usage error)

docker run pinger jahez.sa
# final command →  ping jahez.sa

Case 2 — ENTRYPOINT + CMD (default arguments)

Now we bake a default host into CMD. Run it with no arguments and the default is used automatically.

▸ Dockerfilecase 2
FROM alpine
ENTRYPOINT ["ping"]        # fixed
CMD ["jahez.sa"]          # default argument
▸ developer terminalfinal command
docker run pinger
# final command →  ping jahez.sa
# ENTRYPOINT (ping) + CMD default (jahez.sa)

Case 3 — ENTRYPOINT + CMD (override the default)

Same image as Case 2. This time you pass your own host on docker run — it replaces the CMD default, but ping still runs.

▸ Dockerfile (unchanged from Case 2)case 3
FROM alpine
ENTRYPOINT ["ping"]        # fixed
CMD ["jahez.sa"]          # default — about to be overridden
▸ developer terminalfinal command
docker run pinger keeta.com
# final command →  ping keeta.com
# ENTRYPOINT (ping) stays · your "keeta.com" replaced the CMD default
THE TAKEAWAY

Across all three, ping (the ENTRYPOINT) is fixed and never changes. Only the argument moves: in Case 1 it comes from you, in Case 2 from the CMD default, in Case 3 your value overrides that default. That is the whole ENTRYPOINT + CMD relationship.

YOUR REAL APP

The Jahez API image is this exact shape — swap ping/host for dotnet/flags:
ENTRYPOINT ["dotnet", "Jahez.Api.dll"]  (fixed — always the API)
CMD ["--urls", "http://0.0.0.0:8080"]  (default port)
So docker run jahez/api → dotnet Jahez.Api.dll --urls http://0.0.0.0:8080 (Case 2), and docker run jahez/api --urls :9090 → dotnet Jahez.Api.dll --urls :9090 (Case 3).

The two real-world patterns

ENTRYPOINT-led

"This image is this tool." Every run goes through the same executable; users only tweak arguments. Best for apps and CLIs — like jahez-api.

CMD-only

"Here's a default, but feel free to replace it." Leaves the image easy to override with a shell for debugging: docker run -it image sh.

The bridge to everything above

This is the connection to the rest of the guide. Kubernetes uses the same two concepts — it just renames them in the Pod spec:

Where"what to run" (fixed)"default args" (overridable)
DockerfileENTRYPOINTCMD
docker run(ENTRYPOINT) + args after the image name
Kubernetes Podcommandargs
CARRY THIS FORWARD

Everything in §00 onward is just this idea in Kubernetes clothing: a Pod's command overrides the image's ENTRYPOINT, and a Pod's args overrides its CMD — same "fixed executable + overridable arguments" model, applied by the kubelet instead of by docker run.

00

What command & args actually are

A container is a single foreground process plus its namespaces. command and args together are that process and its arguments.

They live in the container block of any Pod spec:

▸ where they livePod spec
spec:
  containers:
  - name: api
    image: ghcr.io/jahez/api:1.8.2
    command: ["dotnet"]          # the executable (PID 1)
    args:    ["Jahez.Api.dll"]   # its arguments

At container start, the runtime joins them into a single argument vector and execs it. With the example above, the process that runs as PID 1 inside the container is literally:

dotnetcommand[0] — the executable
Jahez.Api.dllargs[0] — first argument
command (a list)

The executable and any arguments you consider part of the command itself. Overrides the image's ENTRYPOINT. If omitted, the image's ENTRYPOINT is used.

args (a list)

The arguments passed to the command. Overrides the image's CMD. If omitted, the image's CMD is used.

KEY

Neither field is a string — both are YAML lists of strings. command: ["dotnet", "app.dll"] is correct; command: "dotnet app.dll" is a single-element list whose one element contains a space, which the runtime tries to exec as a file literally named "dotnet app.dll" → not found.

01

Why they exist — the need they fill

Most images already ship with a sensible ENTRYPOINT/CMD, so why override? Because the same image is used in many situations, and rebuilding to change one flag is wasteful and slow. command/args let one image serve many roles:

The needHow command/args solves it
Run the same image as a one-off migration jobSame ghcr.io/jahez/api image, but command: ["dotnet","Jahez.Api.dll","migrate"]
Keep a crashing pod alive to debug itOverride with command: ["sleep","3600"] and exec in
Pass an environment-specific flagChange only args per environment, image stays identical
Run a setup step before the appAn initContainer with its own command
Use a generic base image (busybox, alpine)Supply the whole command yourself; the image has no useful default
Wrap startup in a shell one-linercommand: ["sh","-c","flyway migrate && exec dotnet app.dll"]
THE PRINCIPLE

Build the image once; configure behaviour at deploy time. command/args are part of that contract alongside env vars and ConfigMaps — they keep the image immutable and the behaviour declarative in your committed YAML.

02

The Docker mapping — the one thing to memorize

The single biggest source of confusion: the Kubernetes field names do not match the Dockerfile instruction names. They map across like this:

ENTRYPOINT → command · CMD → args
DockerfileKubernetes fieldRole
ENTRYPOINT ["dotnet"]command: ["dotnet"]The executable — what actually runs
CMD ["app.dll"]args: ["app.dll"]The default arguments to it
THE TRAP

People expect command to map to CMD because the names look alike. It does not. command ↔ ENTRYPOINT, and args ↔ CMD. Burn this in — almost every command/args bug traces back to this one mismatch.

03

The four override combinations

What runs depends on which of the two fields you set. Take an image built with ENTRYPOINT ["/app"] and CMD ["--default"]. Here is every case:

You set commandYou set argsWhat actually runsRule
— (omit)— (omit)/app --defaultBoth come from the image
— (omit)["--prod"]/app --prodImage ENTRYPOINT + your args
["/other"]— (omit)/otherYour command, image CMD is dropped
["/other"]["--x"]/other --xBoth come from you; image ignored
CRITICAL ROW 3

The moment you set command but leave args unset, the image's CMD is discarded entirely — it is not appended. If your app needed that CMD argument to run, it now starts with none and may crash. If you override command, you usually must also supply args.

The mental shortcut

  • Set neither → trust the image (the common case).
  • Set only args → keep the image's entrypoint, change its arguments (the safe override).
  • Set command → you're replacing the entrypoint; assume the image's CMD is gone and provide your own args.

Safe: override args only

# image ENTRYPOINT ["dotnet","Jahez.Api.dll"]
args: ["--urls", "http://0.0.0.0:8080"]
# runs: dotnet Jahez.Api.dll --urls http://0.0.0.0:8080

Full replace: command + args

command: ["dotnet", "Jahez.Api.dll"]
args:    ["migrate", "--latest"]
# runs: dotnet Jahez.Api.dll migrate --latest
04

Exec form vs shell form

There are two ways to write a command, and the choice has real consequences for signals, env vars, and what PID 1 ends up being.

Exec form (preferred)

A list where element 0 is the executable. The runtime execs it directly — no shell involved.

command: ["dotnet", "Jahez.Api.dll"]
# OR equivalently:
command:
  - dotnet
  - Jahez.Api.dll
  • Your process is PID 1 → receives SIGTERM directly.
  • Graceful shutdown works.
  • No shell features (no &&, |, $VAR, globbing).

Shell form

You explicitly invoke a shell with -c and pass a command string. The shell interprets it.

command: ["sh", "-c"]
args: ["flyway migrate && dotnet Jahez.Api.dll"]
  • Shell features work: &&, pipes, $VAR, redirects.
  • sh becomes PID 1, not your app.
  • Signals may not reach your app → broken shutdown (see §08).
RULE OF THUMB

Use exec form by default. Reach for shell form only when you genuinely need shell features — chaining commands, expanding a shell variable, or a pipe. When you do use shell form for the main process, prefix the real app with exec so it replaces the shell and reclaims PID 1: sh -c "setup && exec dotnet app.dll".

CONVENTION

With shell form you'll see two styles: command: ["sh","-c","..."] (whole thing in command) or command: ["sh","-c"] + args: ["..."]. Both work. Putting the script in args reads more cleanly and keeps command as just the interpreter.

05

Exec vs shell — when to use which, and why

§04 showed what each form is. This is the decision: which one to reach for, and the reason behind it. The short version — default to exec form; use shell form only when you actually need a shell.

Side by side

DimensionExec form defaultShell form sh -c
Who is PID 1Your appsh (app is a child)
Receives SIGTERM directlyYes ✓No — sh must forward it ✗
Graceful shutdownWorks out of the boxBreaks unless you use exec
&& ; | redirectsNot availableAvailable ✓
Shell $VAR expansionNo (only K8s $(VAR))Yes ✓
Globbing (*.log)NoYes ✓
Needs a shell in the imageNo — works on distrolessYes — fails if none ✗
Extra process / overheadNoneAn extra sh process
Best forRunning your actual app/binaryMulti-step or shell-feature startup

Use exec form when… (almost always)

You're just starting one program. There are no pipes, no chaining, no shell variables. This is the default and what you want for jahez-api.

▸ start the app — nothing fancy neededexec ✓
command: ["dotnet", "Jahez.Api.dll"]
args:    ["--urls", "http://0.0.0.0:8080"]
# PID 1 = dotnet → SIGTERM lands on the app → clean drain on rollout
DISTROLESS

Many production images (incl. hardened .NET/Go bases) ship no shell at all. Shell form there fails instantly with exec: "sh": not found. Exec form is the only option — another reason to make it your default.

Use shell form when… (you need a shell feature)

Reach for sh -c only when the startup genuinely requires something a shell provides. The three real cases:

1. Chaining steps — run a setup command, then the app:

▸ needs &&shell ✓
command: ["sh", "-c"]
args: ["flyway migrate && exec dotnet Jahez.Api.dll"]
#                            ↑ exec hands PID 1 to dotnet (keeps shutdown working)

2. A shell variable or pipe — value only the shell can resolve, or a pipe:

▸ needs $VAR / a pipeshell ✓
command: ["sh", "-c"]
args: ["echo starting on $HOSTNAME | tee /proc/1/fd/1; exec dotnet Jahez.Api.dll"]

3. Globbing — let the shell expand a wildcard:

▸ needs * expansionshell ✓
command: ["sh", "-c", "cat /config/*.json > /app/merged.json && exec dotnet Jahez.Api.dll"]
ALWAYS exec THE REAL APP

Whenever shell form launches your long-running process, prefix it with exec. Without it, sh stays PID 1, swallows SIGTERM, and the app gets SIGKILLed after the grace period — dropping in-flight orders on every rollout. exec replaces the shell with your app so it reclaims PID 1. Full detail in §08.

The decision in one flow

when in doubt, it's exec form
06

The executable part + the arguments

Let's settle this with one equation, then zoom all the way down to the very first word.

The equation

final command = entry point (executable part) + arguments (optional parameters)

Same idea, three vocabularies for each half — they all mean the same thing:

  • Entry point = command = the executable part = the program that runs. Required.
  • Arguments = args = the optional parameters = what you hand to that program. Optional.

What is the executable part?

It's the program the operating system actually runs — a real file that exists inside the container. In YAML it's command, written as a list. The important nuance:

KEY

The executable part can have several items, but only the first item is the real program (the file the OS runs). Every item after it is just a fixed argument that travels with the command.

item 0 is the program; the rest are arguments to it

So "file to run or what?" — yes: the first item names a file the OS executes. dotnet is a real binary that lives in the image (at /usr/bin/dotnet). Jahez.Api.dll is not a program — it's data the dotnet program reads. The OS can only run real executables, so the executable is dotnet, and the .dll is one of its arguments.

The first item: the rules

The first item must be exactly one word — the program, with nothing tacked on. It can be a bare name or a path:

First itemWhat it meansOK?
dotnetBare name → searched for in PATH → /usr/bin/dotnet✓
/app/serverAbsolute path → that exact file is run✓
./start.shRelative path (to workingDir) → that script is run✓
dotnet Jahez.Api.dllTwo words in one item → OS seeks a file named exactly that✗
Jahez.Api.dllNot an executable — it needs dotnet to run it✗

The rules, in order:

  1. One token only — no spaces, no arguments mixed in.
  2. It must be a real executable present in the image, with execute permission (a binary, or a script starting with #!).
  3. A bare name (dotnet) is looked up in the PATH directories; a name with a / (/app/server) is used as that exact path.
  4. Everything after the first item is an argument, never part of the program name.

Each argument = one item

The same rule continues past item 0: one terminal word → one list item. The OS never splits on spaces; only a shell does. So convert any command by splitting it on spaces:

▸ terminal command → exec listconvert
# terminal:
dotnet Jahez.Api.dll --urls http://0.0.0.0:8080
# list (one word = one item):
["dotnet", "Jahez.Api.dll", "--urls", "http://0.0.0.0:8080"]

# terminal:
ping -c 4 jahez.sa
# list:
["ping", "-c", "4", "jahez.sa"]
A SPACE INSIDE AN ITEM IS LITERAL

Sometimes one argument genuinely contains a space — then keep it as one item on purpose: ["nginx", "-g", "daemon off;"]. Likewise ["echo", "Hello from Jahez"] passes one argument, while ["echo", "Hello", "from", "Jahez"] passes three. The space isn't a separator inside an item — it's just text.

Flag styles: value vs =value

▸ two valid styles, one trapflags
["--urls", "http://0.0.0.0:8080"]     # ✓ two items  (space style)
["--urls=http://0.0.0.0:8080"]      # ✓ one item   (equals style)
["--urls http://0.0.0.0:8080"]      # ✗ one item with a space — broken

The first two are both fine — pick whichever style the program expects. The third jams a flag and its value into one token, which the program reads as a single odd argument.

Mandatory vs optional

FieldMandatory?If omitted
namerequiredPod rejected
imagerequiredPod rejected
commandoptionalImage ENTRYPOINT is used
argsoptionalImage CMD is used (empty if you set command — see §03)
OPTIONAL ≠ FREE

command/args are optional in the spec, but the resolved command can't be empty — something must run. If the image has no ENTRYPOINT/CMD and you set neither, the container fails with no command specified.

One string? Use sh -c

If you really want the whole command as a single string with spaces, bring back a shell to split it:

▸ the shell does the splittingshell form
command: ["sh", "-c", "dotnet Jahez.Api.dll --urls http://0.0.0.0:8080"]
#          item0  item1   item2 = one big string → sh splits it

This works because the executable is now sh, and sh does the space-splitting a shell normally does. In pure exec form there is no shell, so you must split it into separate items yourself.

THE WHOLE RULE

• final command = entry point (executable) + arguments.
• Item 0 = one word, a real program file (bare name via PATH, or a path).
• Every other terminal word = its own item; a space inside an item is literal.
• Want one big string? Hand it to sh -c.

07

command vs args — which token goes where?

Real question: in command: ["dotnet", "Menu.API.dll"], why is the DLL the second item of command instead of the first item of args? The answer is mostly about intent, not mechanics — but the difference bites hard the moment someone overrides args.

Mechanically, both are identical

The runtime concatenates command + args into one list, then runs it. So these two produce the exact same running process:

Option A — dll in command
command: ["dotnet", "Menu.API.dll"]
Option B — dll in args
command: ["dotnet"]
args:    ["Menu.API.dll"]
when nobody overrides, A and B run identically

So if the question is "will they run differently?" — when untouched, no. The kernel concatenates and runs the same argv either way.

So why put the DLL in command?

Because command/args aren't just two halves of a list — they map to ENTRYPOINT and CMD, and those carry intent:

  • command (ENTRYPOINT) = "the identity of the container — it always runs this way."
  • args (CMD) = "swappable parameters someone might override later."

Menu.API.dll is not a swappable parameter — it is the app. You'd never keep this image but swap the DLL for a different one; that would be a different application. It belongs with the fixed identity, so it goes in command. What belongs in args is something genuinely tunable, like the port:

▸ the right splitintent
command: ["dotnet", "Menu.API.dll"]            # fixed: this IS the app
args:    ["--urls", "http://0.0.0.0:8080"]    # swappable: the port

The difference appears the moment args is overridden

This is the whole reason the choice matters. Recall §03: overriding args (on docker run, or by setting args in another manifest) replaces the entire args/CMD — but never touches command/ENTRYPOINT. Watch both options under the same override.

✓ Option A — DLL in command (safe)
▸ DLL sits in the protected halfcase A
command: ["dotnet", "Menu.API.dll"]
args:    ["--urls", "http://0.0.0.0:8080"]

# someone overrides args to change ONLY the port:
docker run jahez/menu --urls http://0.0.0.0:9090
# → dotnet Menu.API.dll --urls http://0.0.0.0:9090    ✓ Menu still runs, new port

What happens: the override replaces only the args half (--urls :8080 → --urls :9090). Menu.API.dll lives in command, so it is untouched — the new args are appended after it. You changed exactly what you meant to (the port) and nothing else. The service identity is protected.

✗ Option B — DLL in args (fragile)
▸ DLL sits in the half that gets replacedcase B
command: ["dotnet"]
args:    ["Menu.API.dll", "--urls", "http://0.0.0.0:8080"]

# you ALSO only want to change the port — but args holds the DLL,
# so you must restate it... and a wrong DLL slips in:
docker run jahez/menu Order.API.dll --urls http://0.0.0.0:9090
# EXPECTED:  dotnet Menu.API.dll --urls http://0.0.0.0:9090
# ACTUAL:    dotnet Order.API.dll --urls http://0.0.0.0:9090   ✗ Menu.API.dll is GONE

What happens: you only meant to change the port, but because Menu.API.dll sits inside args, any args override must restate the whole list — and here Order.API.dll got passed instead. Since args replaces (never merges), the entire old list (Menu.API.dll --urls :8080) is thrown away and swapped for the new one (Order.API.dll --urls :9090). The container now silently runs the Order service instead of Menu — a completely different app — with no error. Had Menu.API.dll been in command, it could never have been replaced this way. (And if you'd passed only --urls :9090, you'd get dotnet --urls :9090 — no DLL at all → CrashLoopBackOff.)

override replaces args entirely; command is protected — so keep essentials in command

The rule that falls out of this

Put in command everything required for the container to be itself — the executable and any argument the app can't run without (like the DLL). Put in args only what's genuinely meant to vary.

Goes in command fixedGoes in args swappable
dotnet — the executable--urls http://0.0.0.0:8080 — the port
Menu.API.dll — the app, can't run without it--environment Production
-jar app.jar for Javalog level, feature flags, tunables
IN ONE LINE

The DLL goes in command not because it mechanically must, but because it's part of what makes this container this app — and keeping it there means an override of args can never accidentally delete it.

Summary — the whole structure in one picture

final command = entry command (Item 0 executable + fixed Items 1…N) + overridable arguments
08

PID 1 & signal handling — why the form matters

When Kubernetes wants to stop a pod (rollout, scale-down, node drain), the kubelet sends SIGTERM to PID 1 of each container, waits terminationGracePeriodSeconds (default 30s), then sends SIGKILL. Whether your app shuts down gracefully depends entirely on what PID 1 is.

A naive sh -c wrapper swallows SIGTERM; the app is killed hard 30s later

In the bad case, requests in flight are dropped, connections aren't drained, and you get 502s during every rollout. Three fixes, best first:

  1. Use exec form — your app is PID 1, done.
  2. exec in the shell string — sh -c "migrate && exec dotnet app.dll" replaces sh with your app so it becomes PID 1.
  3. Run an init process — set shareProcessNamespace or use a tiny init like tini to reap and forward signals (mostly handled by modern runtimes, but relevant for multi-process containers).
JAHEZ IMPACT

For jahez-api, broken SIGTERM handling means every deploy and every autoscale-down drops live order requests. The Deployment's maxUnavailable: 0 only helps if old pods drain cleanly — which requires PID 1 to actually receive SIGTERM.

09

Environment variable expansion — $(VAR)

This trips up almost everyone, because there are really two different expansion systems and people mix them up.

In exec-form command/args (no shell), only $(VAR) is expanded, and Kubernetes itself (the kubelet) does it — before the process starts, looking VAR up in this container's own env/envFrom. By contrast $VAR and ${VAR} are shell syntax; there is no shell in exec form, so Kubernetes leaves them as literal text. The whole topic comes down to one question:

THE QUESTION

Who is doing the expanding? If it's Kubernetes → use $(VAR). If it's a shell → use $VAR, and you must actually be running one (sh -c).

pick the syntax that matches who's expanding — Kubernetes ($(VAR)) or the shell ($VAR)

✅ Correct — $(VAR) in exec form

▸ Kubernetes expands before execcorrect
env:
- name: HOST
  value: "0.0.0.0"
- name: PORT
  value: "8080"
command: ["dotnet", "Jahez.Api.dll"]
args:    ["--urls", "http://$(HOST):$(PORT)"]

What happens: the kubelet substitutes before exec, so the process runs as dotnet Jahez.Api.dll --urls http://0.0.0.0:8080. Why: $(VAR) is Kubernetes' own syntax, resolved against the container's env.

❌ Wrong #1 — $VAR in exec form

▸ shell syntax with no shellwrong
args: ["--urls", "http://$HOST:$PORT"]

What happens: the app receives the literal string http://$HOST:$PORT and tries to bind to a host literally named $HOST — it fails or binds to garbage. Why: $HOST is shell expansion. No shell is running in exec form, and Kubernetes only does $(VAR), never $VAR.

❌ Wrong #2 — referencing a variable that isn't defined

▸ typo: PROT, not PORTwrong
args: ["--urls", "http://0.0.0.0:$(PROT)"]

What happens: the process runs with the literal text --urls http://0.0.0.0:$(PROT) — the broken reference is left as-is. Why: this is the surprising part — an undefined $(VAR) is not replaced with an empty string; Kubernetes leaves the original text unchanged. (A shell does the opposite: undefined $VAR becomes empty.) A typo'd variable silently leaks $(...) into your arguments.

#1 BUG

The two failures you'll actually hit: using $VAR where you needed $(VAR) (Wrong #1), and a typo'd $(VAR) leaking through as literal text instead of erroring (Wrong #2). Both pass YAML validation and only show up at runtime — check the resolved Args: in kubectl describe pod.

The escape — when you want a literal $(...)

▸ double-dollar escapes expansionescape
args: ["--pattern", "$$(date)"]   # app receives literal: $(date)

What happens: $$ collapses to a single $, so the app receives the literal $(date). Why: $$(VAR) tells Kubernetes "don't expand this" — needed when your own program uses $(...) syntax.

✅ When you genuinely need $VAR → use shell form

$(VAR) only reads this container's env. If you need a real shell variable, shell features, or the shell's undefined-→-empty behaviour, run a shell explicitly:

▸ shell form does $VARshell form
command: ["sh", "-c"]
args: ["exec dotnet Jahez.Api.dll --urls http://0.0.0.0:$PORT"]

Now a shell expands $PORT. Note the exec — it hands PID 1 back to dotnet so SIGTERM still works (the §08 issue).

Variables can chain

$(VAR) in an env value can reference an earlier env var (not a later one):

▸ build values from earlier oneschaining
env:
- name: HOST
  value: "0.0.0.0"
- name: PORT
  value: "8080"
- name: ADDRESS
  value: "$(HOST):$(PORT)"       # references the two above
args: ["--urls", "http://$(ADDRESS)"]   # → http://0.0.0.0:8080

Summary

You writeWho expands itIn exec form (command/args)
$(VAR)Kubernetes✓ expands from container env
$(UNDEFINED)Kubernetes⚠ left literal (not emptied)
$VAR / ${VAR}a shell✗ literal passthrough — no shell present
$$(VAR)Kubernetes (escape)✓ becomes literal $(VAR)
$VAR inside sh -c "…"the shell✓ shell expands it
SCOPE

$(VAR) only sees variables declared in this container's env/envFrom before the one referencing them. It cannot see arbitrary node or shell variables — for those you need shell form.

Where else exec commands appear

command/args aren't the only place you supply commands to a container. The same exec-list pattern shows up in three other spots — and the same rules apply.

initContainers — run a command, then exit

An init container runs to completion before the app container starts. Its whole purpose is its command — a setup step like waiting for a dependency or running a migration.

▸ initContainerinit
initContainers:
- name: wait-for-postgres
  image: busybox:1.36
  command: ["sh", "-c"]
  args:
  - until nc -z postgres-rw.jahez-prod.svc 5432; do echo waiting; sleep 2; done

Probes with exec — health by running a command

A liveness/readiness probe can run a command inside the container; exit code 0 = healthy. Same exec-list shape under exec.command.

▸ exec probeprobe
livenessProbe:
  exec:
    command: ["sh", "-c", "curl -fsS localhost:8080/healthz/live"]
  periodSeconds: 20

Lifecycle hooks — preStop for graceful drain

A preStop hook runs before SIGTERM. The classic use: a small sleep so the load balancer stops routing before the app exits — directly relevant to the shutdown story in §08.

▸ preStop hooklifecycle
lifecycle:
  preStop:
    exec:
      command: ["sh", "-c", "sleep 5"]   # let endpoints drain first
ONE PATTERN

Learn the exec-list shape once and it transfers everywhere: container command, initContainers[].command, livenessProbe.exec.command, and lifecycle.preStop.exec.command are all the same []string with the same exec-vs-shell rules.

Where each command lives in the Pod spec

All four sit in the same Pod spec, but at different paths. The structure tells you the role:

▸ the command fields of a Podstructure
spec:
  initContainers:
  - command + args            # ① setup — own container, runs first, to completion
  containers:
  - command + args            # ② the main app — this container's PID 1, runs for life
    startupProbe:   { exec: { command } }   # ③ health checks — run INSIDE
    readinessProbe: { exec: { command } }   #    the already-running
    livenessProbe:  { exec: { command } }   #    container, repeatedly
    lifecycle:
      postStart: { exec: { command } }  # ④ once, right after start
      preStop:   { exec: { command } }  # ④ once, just before SIGTERM
THE BIG STRUCTURAL SPLIT

Notice it: container & initContainer have TWO fields — command + args (they override the image's ENTRYPOINT/CMD and start a new container). Probes & lifecycle hooks have ONE field — exec.command (no separate args, no ENTRYPOINT/CMD concept; you write the whole command in the list, and it runs inside the container that's already running).

Full comparison

initContainer initContainers[].command + args yes Setup before the app: wait for deps, migrate, fetch config A new container (own image) kubelet → runtime Once each, in order, before app containers Retried until success — blocks the whole pod

When each one runs — a pod's lifetime

init → app (PID 1) + postStart → probes repeat → preStop → SIGTERM
SO, THE DIFFERENCE IN ONE LINE

A container/initContainer command is a process the container exists to run (with command + args, overriding the image). A probe/hook command is an extra command (just exec.command) that the kubelet runs inside that container at health-check time or a lifecycle moment — it doesn't define the container, it observes or nudges it.

Startup walkthrough — command to PID 1

Press Next (or ← → arrow keys) to follow exactly how command and args turn into the running process inside a jahez-api container.

▸ image → PID 1 → SIGTERM 1 / 7
STEP 1 · scheduled
The pod lands on a node

The scheduler assigns the pod to worker-2. Its kubelet now owns starting the container. Nothing has run yet — the kubelet first needs the image.

STEP 2 · image pulled
kubelet pulls the image & reads its defaults

The runtime pulls ghcr.io/jahez/api:1.8.2 and inspects its config: the baked-in ENTRYPOINT and CMD. These are the fallbacks if your spec omits command/args.

# image ships with:
ENTRYPOINT ["dotnet"]
CMD        ["Jahez.Api.dll"]
STEP 3 · merge
Spec overrides are merged with image defaults

The kubelet applies the override rules from §03. Our spec sets both command and args, so the image's ENTRYPOINT and CMD are fully replaced.

# from the Pod spec:
command: ["dotnet", "Jahez.Api.dll"]
args:    ["--urls", "http://0.0.0.0:$(PORT)"]
STEP 4 · env expansion
Kubernetes expands $(VAR) references

Before exec, the kubelet substitutes $(PORT) using the container's env (PORT=8080). This is Kubernetes' own expansion — no shell is involved because we used exec form.

# final argument vector after expansion:
["dotnet", "Jahez.Api.dll", "--urls", "http://0.0.0.0:8080"]
STEP 5 · exec → PID 1
The runtime exec()s the vector

The container runtime calls execve() with that vector in the container's namespaces, starting in workingDir: /app. Because we used exec form, dotnet is PID 1 — there is no shell wrapper between it and the kernel.

STEP 6 · ready → serving
App listens, readiness passes, traffic flows

The app binds 0.0.0.0:8080 (from our args). Its readiness probe on /healthz/ready succeeds, its IP joins the Service's endpoints, and kube-proxy starts routing order traffic to it.

STEP 7 · graceful stop
On stop, SIGTERM reaches PID 1 directly

When the pod is told to terminate, the preStop hook sleeps 5s (so the LB stops routing), then the kubelet sends SIGTERM to PID 1 — which is dotnet. The app drains in-flight orders and exits cleanly, all within the 30s grace period. This only works because of the exec-form choice in step 3.

17

Best practices

✓ Prefer exec form

Use the list form so your app is PID 1 and receives signals. Reach for sh -c only when you need real shell features.

✓ Override args, not command

When you only need to change flags, set args alone and keep the image's trusted ENTRYPOINT.

✓ If you set command, set args too

Remember the image's CMD is dropped. Supply your own args so the process starts correctly.

✓ Use $(VAR) for K8s env

Inside exec-form command/args, only $(VAR) expands. Save $VAR for inside sh -c.

✓ exec in shell wrappers

sh -c "setup && exec app" hands PID 1 to your app so shutdown works.

✓ Keep behaviour in YAML, not images

One image, many roles. Configure command/args at deploy time and commit it to git.

✗ Never use string form

command: "dotnet app.dll" is a single filename with a space. Always a list.

✗ Don't put secrets in args

Args are visible in describe, events, and process listings. Use env from a Secret instead.
