Part I · Foundations

Why configuration is hard in distributed systems

Before we dive into primitives, let's frame the problem. These two sections establish why Kubernetes gives you three separate tools — env vars, ConfigMaps, and Secrets — instead of one.

01The Configuration Problem

Every non-trivial application needs configuration — values that change between environments (dev, staging, prod) or between runs, without changing the code or rebuilding the image. Database URLs, feature flags, API endpoints, credentials, tuning knobs. A container image should be environment-agnostic; only configuration should differ between a dev pod and a production pod.

Kubernetes solves this with three complementary primitives:

env

Environment Variables

Key/value pairs injected directly into the container process. Simplest mechanism. Ideal for a handful of small, non-sensitive values.

configMap

ConfigMaps

A cluster-stored object holding non-sensitive key/value or file data. Decouples config from pods; one source, many consumers.

secret

Secrets

Like ConfigMaps but for sensitive data: passwords, tokens, TLS certs, SSH keys. Stored base64-encoded, optionally encrypted at rest.

The twelve-factor principle

Configuration that varies between deploys must live outside the code. In Kubernetes, that "outside" is a ConfigMap or Secret, surfaced to the container via env vars or mounted files. Treat your image as a pure function of code; configuration is the argument.

02The Three Primitives at a Glance

Before diving into each, here is how they relate inside a cluster. ConfigMaps and Secrets are cluster objects stored in etcd. Env vars are a projection mechanism — a way to inject those values (or literal values) into a container's process environment. Files-on-disk is the other projection mechanism, via volumeMounts.

Part II · Environment Variables

The process-level contract between Kubernetes and your app

Environment variables are the oldest, simplest, and most universal way to pass configuration to a process. Every language can read them. Here's how Kubernetes injects them, what sources you can pull from, and when to use them vs. alternatives.

03Environment Variables — Deep Dive

Definition — what env vars actually are

An environment variable is not a Kubernetes object and not stored in etcd. At the Linux level, env vars live in a contiguous block of memory at the top of the process's stack — specifically in the envp array passed to execve(2) when a process is started. After that, they're copied into the process's own address space and exposed via /proc/<pid>/environ (a null-separated blob). That's it — no file on disk, no inode, no K8s resource.

What this means in practice

You cannot ls env vars, you cannot kubectl get envvars, and you cannot change them while the container runs. They exist only for the lifetime of the process. When the container restarts, the kubelet rebuilds the envp array from the Pod spec again — re-reading any referenced ConfigMap/Secret fresh from the API server.

Where the values come from

The env field in a Pod spec is a delivery mechanism, not a source. Each entry tells the kubelet: "at container-start time, assemble this name=value pair from somewhere." The somewhere can be:

  • A literal string written inline in the Pod spec (stored in etcd as part of the Pod object)
  • A ConfigMap key — kubelet fetches the CM, reads the key, copies the value
  • A Secret key — kubelet fetches the Secret, base64-decodes the value, copies it
  • A Pod field via the Downward API (fieldRef) — e.g., the pod's name, namespace, labels, or IP
  • A container resource via resourceFieldRef — e.g., the CPU limit in millicores, memory limit in bytes

Each of those follows a slightly different physical path from somewhere in the cluster to the bytes inside /proc/<pid>/environ. The five diagrams below show exactly what kubelet does in each case — what it fetches, what it computes, what it copies.

Figure 3.1 — Source 1: Literal value (inline in Pod spec)

The value is already in the Pod object in etcd. When the kubelet starts the container, it reads spec.containers[0].env[i].value straight from the Pod it's watching, copies that string into the envp array passed to execve(), and the bytes land in the process's /proc/<pid>/environ. Zero extra API calls. Zero decoding. The fastest path.

Figure 3.2 — Source 2: ConfigMap key (configMapKeyRef)

The Pod spec only carries a reference: "go fetch ConfigMap order-config, take key db.host." The kubelet makes an extra GET to the apiserver, pulls the ConfigMap from etcd, plucks the requested key, and copies that value into envp. The CM stays in etcd; only the resolved value lives in the process. If the CM changes later, the running process sees nothing — env-var snapshots are taken once, at start.

Figure 3.3 — Source 3: Secret key (secretKeyRef) — adds base64 decode

Same shape as ConfigMap, with two extra realities: (1) the Secret may be encrypted in etcd — the apiserver decrypts it on read; (2) Secret values are base64-encoded on the wire, so the kubelet must decode before injecting. The plaintext then lives unprotected in the process's environ memory, readable by any process with the same UID — which is the core reason Secrets-as-files (tmpfs, mode 0400) are preferred over Secrets-as-env-vars for very sensitive values.

Figure 3.4 — Source 4: Pod field via Downward API (fieldRef)

The Downward API exposes the pod's own metadata back into the container. The kubelet already has the full Pod object — no extra apiserver call is needed. It just walks the JSON path you specified (e.g. status.podIP, metadata.labels['app']) and writes the result to envp. Useful when an app needs to know its own IP, namespace, or pod name without hitting the API — common in observability sidecars and service-mesh init containers.

Figure 3.5 — Source 5: Container resource via resourceFieldRef (computed)

The unique step here is conversion. The kubelet reads limits.memory: "1Gi" from the container spec, converts the human-readable quantity into raw bytes (1073741824), and writes that number into envp. The classic real-world use is JVM tuning — your Java process can compute its heap as a percentage of the container's memory limit (-XX:MaxRAMPercentage=70) instead of hard-coding -Xmx and risking OOMKill if you ever resize the pod.

All five paths converge in the same place

No matter the source — literal, ConfigMap, Secret, Downward API, or resource — the destination is identical: a contiguous block of null-separated bytes in the process's /proc/<pid>/environ. The kubelet is the resolver; execve() is the loader; the process never knows where the value originally came from. That's the whole point — your application code reads os.getenv("DB_PASSWORD") and doesn't care whether it came from a Secret in etcd or a literal string in the Pod manifest.

Common misconception

People say "I put my config in env vars." That's imprecise. What you actually put in etcd is the Pod spec (with literals) and the ConfigMap/Secret (with referenced values). Env vars are the runtime view the process sees — reconstructed every time the container starts, never persisted as env vars anywhere.

The full lifecycle — from kubectl apply to process.env

When you create a Pod, here's the exact chain of custody:

  1. kubectl apply → sends Pod manifest (YAML) to kube-apiserver
  2. apiserver → validates, persists Pod object in etcd (encrypted at rest if configured)
  3. scheduler → binds the Pod to a node
  4. kubelet on that node → watches the Pod, pulls image, then resolves every env entry: literals straight from the spec, configMapKeyRef/secretKeyRef via additional API calls, fieldRef from pod metadata it already has
  5. kubelet → CRI (containerd/CRI-O) → passes the fully resolved env map to the runtime
  6. runc → calls execve() with the envp array as the third argument
  7. your process → sees the values in process.env / os.environ / getenv()
Security implication

Because env vars are stored in /proc/<pid>/environ with file mode 0444 (world-readable to the same UID), any process running as the same user — including sidecars, kubectl exec sessions, and crash-dump collectors — can read them. This is why Secrets-as-files are preferred over Secrets-as-env-vars for highly sensitive values. More in §12.

Anatomy of an env block

pod-env.yaml
apiVersion: v1
kind: Pod
metadata:
  name: order-api
spec:
  containers:
  - name: api
    image: ghcr.io/jahez/order-api:1.8.2
    env:
    # 1. Literal value
    - name: LOG_LEVEL
      value: "info"

    # 2. From a ConfigMap key
    - name: DB_HOST
      valueFrom:
        configMapKeyRef:
          name: order-config
          key: db.host

    # 3. From a Secret key
    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: order-secrets
          key: db.password

    # 4. From pod metadata (Downward API)
    - name: POD_NAME
      valueFrom:
        fieldRef:
          fieldPath: metadata.name

    # 5. From container resource limits
    - name: MEM_LIMIT
      valueFrom:
        resourceFieldRef:
          containerName: api
          resource: limits.memory

What happens at pod start — step by step

  1. Scheduler assigns the Pod to a node.
  2. Kubelet on that node pulls the Pod spec from the API server.
  3. For each valueFrom, the kubelet resolves the reference by fetching the ConfigMap or Secret from the API server (or its watch cache).
  4. If any referenced key is missing and optional: false (the default), the container will fail to start with CreateContainerConfigError.
  5. Kubelet builds the final env list, passes it to the container runtime (containerd/CRI-O), which launches the process with that environment.
Failure mode to know

If you reference a ConfigMap/Secret that doesn't exist yet, the pod stays in CreateContainerConfigError forever until you create it. Use optional: true if the variable is genuinely optional.

Variable expansion ($(VAR))

You can reference an earlier env var inside a later one using $(VAR_NAME). Order matters — the referenced variable must be declared before the one that uses it.

env-expansion.yaml
env:
- name: DB_HOST
  value: "postgres.data.svc.cluster.local"
- name: DB_PORT
  value: "5432"
- name: DATABASE_URL
  value: "postgres://app@$(DB_HOST):$(DB_PORT)/orders"

04Env Var Types & Sources

There are five sources a container env var can pull from. Swipe through each below.

The 5 sources of env vars
1 / 5
Type 01 · Literal

Static value inline in the Pod spec

The simplest form. Hard-coded into the manifest. Good for non-sensitive, per-deployment constants that rarely change.

literal.yaml
apiVersion: v1
kind: Pod
metadata:
  name: order-api
  namespace: orders
spec:
  containers:
  - name: api
    image: ghcr.io/jahez/order-api:1.8.2
    env:
    - name: LOG_LEVEL
      value: "info"
    - name: MAX_CONNECTIONS
      value: "100"             # must be a string!
    - name: TZ
      value: "Asia/Riyadh"

Gotcha: all env-var values must be strings. Quote numbers and booleans.

Type 02 · configMapKeyRef

Pull one key out of a ConfigMap

Use when you want a small number of specific keys, possibly renamed, rather than dumping the whole ConfigMap.

configmap-ref.yaml
apiVersion: v1
kind: Pod
metadata:
  name: cache-client
  namespace: orders
spec:
  containers:
  - name: api
    image: ghcr.io/jahez/cache-client:2.1.0
    env:
    - name: REDIS_HOST
      valueFrom:
        configMapKeyRef:
          name: cache-config
          key: redis.host
          optional: false          # default; fail if missing
    - name: REDIS_PORT
      valueFrom:
        configMapKeyRef:
          name: cache-config
          key: redis.port
    - name: REDIS_DB
      valueFrom:
        configMapKeyRef:
          name: cache-config
          key: redis.db
          optional: true           # skip if key missing
Type 03 · secretKeyRef

Pull one key out of a Secret

Identical shape to configMapKeyRef but reads from a Secret. The value is base64-decoded by the kubelet before injection.

secret-ref.yaml
apiVersion: v1
kind: Pod
metadata:
  name: payment-service
  namespace: orders
spec:
  containers:
  - name: payment
    image: ghcr.io/jahez/payment-service:3.4.1
    env:
    - name: STRIPE_API_KEY
      valueFrom:
        secretKeyRef:
          name: payment-secrets
          key: stripe.api_key
    - name: MADA_MERCHANT_SECRET
      valueFrom:
        secretKeyRef:
          name: payment-secrets
          key: mada.merchant_secret
    - name: JWT_SIGNING_KEY
      valueFrom:
        secretKeyRef:
          name: payment-secrets
          key: jwt.signing.key

Trade-off: a Secret consumed as env var appears in /proc/<pid>/environ and can leak via crash dumps or child processes. For ultra-sensitive values, prefer a file mount.

Type 04 · fieldRef (Downward API)

Inject pod/container metadata

Useful for observability: sidecars that need to know their own pod name, namespace, service account, or node.

downward.yaml
apiVersion: v1
kind: Pod
metadata:
  name: observability-agent
  namespace: orders
  labels:
    app: order-api
    tier: backend
spec:
  containers:
  - name: agent
    image: datadog/agent:7.54
    env:
    - name: POD_NAME
      valueFrom: { fieldRef: { fieldPath: metadata.name } }
    - name: POD_NAMESPACE
      valueFrom: { fieldRef: { fieldPath: metadata.namespace } }
    - name: POD_UID
      valueFrom: { fieldRef: { fieldPath: metadata.uid } }
    - name: POD_IP
      valueFrom: { fieldRef: { fieldPath: status.podIP } }
    - name: HOST_IP
      valueFrom: { fieldRef: { fieldPath: status.hostIP } }
    - name: NODE_NAME
      valueFrom: { fieldRef: { fieldPath: spec.nodeName } }
    - name: SERVICE_ACCOUNT
      valueFrom: { fieldRef: { fieldPath: spec.serviceAccountName } }
    - name: APP_LABEL
      valueFrom: { fieldRef: { fieldPath: metadata.labels['app'] } }

Supported paths: metadata.name, metadata.namespace, metadata.uid, metadata.labels['x'], metadata.annotations['x'], spec.nodeName, spec.serviceAccountName, status.hostIP, status.podIP, status.podIPs.

Type 05 · resourceFieldRef

Inject container resource requests/limits

Lets the app right-size itself — e.g. setting a JVM heap based on the container's memory limit. This is exactly the pattern used to fix the OOM issue in the jahez-gateway (JVM didn't know the container limit).

resource-downward.yaml
apiVersion: v1
kind: Pod
metadata:
  name: jvm-app
  namespace: orders
spec:
  containers:
  - name: api
    image: ghcr.io/jahez/order-api:1.8.2
    # JVM picks up the container's actual limit, avoids OOMKill
    command: ["java"]
    args:
    - -XX:MaxRAMPercentage=70.0
    - -Xss512k
    - -jar
    - /app/order-api.jar
    resources:
      requests: { cpu: 500m, memory: 512Mi }
      limits:   { cpu: "2",  memory: 1Gi }
    env:
    - name: MEM_LIMIT_BYTES
      valueFrom:
        resourceFieldRef:
          containerName: api
          resource: limits.memory
          divisor: "1"           # bytes. Use 1Mi for MB
    - name: MEM_REQUEST_MB
      valueFrom:
        resourceFieldRef:
          containerName: api
          resource: requests.memory
          divisor: "1Mi"
    - name: CPU_LIMIT_MILLI
      valueFrom:
        resourceFieldRef:
          containerName: api
          resource: limits.cpu
          divisor: "1m"          # millicores

Supported: limits.cpu, limits.memory, limits.ephemeral-storage, and the matching requests.* forms.

Bulk injection — envFrom

When you want every key from a ConfigMap or Secret to become an env var, use envFrom. Optionally prefix the names to avoid collisions.

envfrom.yaml
envFrom:
- configMapRef:
    name: order-config      # every key becomes an env var
- configMapRef:
    name: feature-flags
    optional: true
- secretRef:
    name: order-secrets
  prefix: SEC_              # db.password → SEC_db.password
envFrom quirks

Keys that aren't valid env-var names (e.g. contain dots or hyphens) are silently skipped and logged as events. Keep ConfigMap keys in UPPER_SNAKE_CASE if you plan to use envFrom.

Part III · ConfigMaps

Non-sensitive configuration as a first-class object

ConfigMaps decouple configuration from container images. One object can be consumed by many pods, many ways — as env vars, as files, or as command-line arguments. Let's unpack the anatomy, the creation methods, and the four consumption patterns.

05ConfigMaps — Deep Dive

Definition — what a ConfigMap actually is

A ConfigMap is a namespaced Kubernetes API object (kind: ConfigMap, apiVersion: v1, resource name: configmaps, short name: cm) whose sole purpose is to store non-confidential configuration data as key/value pairs. Unlike env vars, a ConfigMap is a real object — it has a name, a UID, a resourceVersion, a creationTimestamp, labels, annotations, and it participates in the full Kubernetes API surface: you can get, list, watch, patch, delete it, RBAC it, version it, GitOps it.

Where is it stored?

A ConfigMap lives in etcd, the cluster's distributed key-value store, alongside every other API object (Pods, Services, Deployments, Nodes, etc.). The etcd key looks roughly like /registry/configmaps/<namespace>/<name>. When you run kubectl get cm order-config -o yaml, the apiserver fetches that etcd key, deserializes the protobuf/JSON, and returns it to you. ConfigMap data is not encrypted at rest by default — it's stored as plain strings in etcd, same as the rest of your cluster state.

What it is not

  • Not a file on the node. ConfigMaps exist only in etcd until the kubelet projects them into a pod (as env vars or as tmpfs-mounted files). There is no /etc/k8s/configmaps/ directory on your worker nodes.
  • Not meant for large data. The total size of a single ConfigMap is capped at 1 MiB (etcd value-size limit minus overhead). For bigger blobs, use a real object store (S3, GCS) and pass its URL via a ConfigMap.
  • Not for secrets. ConfigMap values are visible to anyone with get configmaps RBAC, and they're stored unencrypted. Sensitive data belongs in a Secret (§7).
  • Not type-safe. All values are strings. "true" is a string, not a boolean. Numbers are strings. Your application parses them.

Lifecycle — from kubectl create to a running pod

  1. You create the CM via YAML, --from-literal, or --from-file. kubectl sends a POST to the apiserver.
  2. apiserver validates and writes the object to etcd. The CM now exists cluster-wide within its namespace.
  3. A Pod references the CM in its spec — either via envFrom/configMapKeyRef (env-var path) or as a volume with configMap: (file path).
  4. kubelet resolves the reference when starting the pod. For env vars: fetch-once, inject into envp, done. For volume mounts: the kubelet creates a tmpfs (RAM-backed filesystem) and writes each key as a file inside it, then bind-mounts it into the container.
  5. The kubelet keeps watching the CM if it's mounted as a volume. When the CM changes in etcd, the kubelet updates the tmpfs files — usually within a minute (the kubelet's sync period, configurable via --configMapAndSecretChangeDetectionStrategy).
Env-var consumption is a point-in-time snapshot

If you consume a CM via env or envFrom, the values are captured at pod start. Updating the CM afterwards does not update the running process — you must restart the pod. Only volume mounts of a CM propagate updates automatically. This is one of the most common Kubernetes gotchas.

Structure

configmap-structure.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-config
  namespace: orders
# simple key/value pairs — used by env vars OR as files
data:
  LOG_LEVEL: "info"
  FEATURE_DARK_MODE: "true"
  db.host: "postgres.data.svc.cluster.local"

  # multi-line content — behaves as a whole file
  application.yaml: |
    server:
      port: 8080
      shutdown: graceful
    logging:
      level:
        root: INFO
        com.jahez: DEBUG
    jahez:
      region: KSA
      checkout:
        max-retries: 3

# binary data — base64-encoded; only mountable as files
binaryData:
  logo.png: iVBORw0KGgoAAAANSUhEUg...

data

UTF-8 strings. Each key can be used individually (via configMapKeyRef), all at once (envFrom), or mounted as a file whose content is the value.

binaryData

Base64-encoded bytes. Cannot be consumed as env vars; only projected as files. Use for certificates, small icons, compiled templates.

Three ways to create a ConfigMap

yaml-approach.yaml
# Best for GitOps. Check into source control.
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-config
data:
  LOG_LEVEL: "info"
  TIMEOUT_MS: "5000"

kubectl apply -f order-config.yaml

kubectl
# Best for quick experiments. Not GitOps-friendly.
kubectl create configmap order-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=TIMEOUT_MS=5000 \
  --from-literal=FEATURE_X=true
kubectl
# Load each file as a key (filename=key, contents=value)
kubectl create configmap nginx-config --from-file=./nginx.conf
# Yields: data.nginx.conf = <file contents>

# Load a whole directory (every file becomes a key)
kubectl create configmap app-config --from-file=./config/

# Parse a dotenv-style file: each KEY=VALUE line → individual key
kubectl create configmap env-config --from-env-file=.env

# Rename key on import
kubectl create configmap app --from-file=settings=./prod.yaml

06ConfigMap Consumption Patterns

Same ConfigMap, three ways to reach your container. Pick based on what the app expects.

Consumption patterns
1 / 4
Pattern 01

Pick specific keys as env vars

Use when only a few keys are needed and you want them renamed in-pod.

pattern-pick.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  namespace: orders
spec:
  replicas: 3
  selector:
    matchLabels: { app: order-api }
  template:
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: api
        image: ghcr.io/jahez/order-api:1.8.2
        ports:
        - { name: http, containerPort: 8080 }
        env:
        # pick individual keys from the ConfigMap, rename freely
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: order-config
              key: LOG_LEVEL
        - name: DB_HOST               # renamed: CM has "db.host"
          valueFrom:
            configMapKeyRef:
              name: order-config
              key: db.host
        - name: FEATURE_DARK_MODE
          valueFrom:
            configMapKeyRef:
              name: order-config
              key: FEATURE_DARK_MODE
              optional: true    # don't fail if key missing
        resources:
          requests: { cpu: 100m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }

When: 2-5 vars, strict naming, want renames.

Downside: pod restart required when ConfigMap changes.

Pattern 02

Bulk-import all keys (envFrom)

Use when the ConfigMap was designed as an "env file" with UPPER_SNAKE_CASE keys.

pattern-envfrom.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  namespace: orders
spec:
  replicas: 3
  selector:
    matchLabels: { app: order-api }
  template:
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: api
        image: ghcr.io/jahez/order-api:1.8.2
        ports:
        - { name: http, containerPort: 8080 }
        envFrom:
        # every key in order-config becomes an env var, prefixed with ORDER_
        - configMapRef:
            name: order-config
          prefix: ORDER_     # optional: namespaces the vars
        # can combine with another CM or a Secret at the same time
        - configMapRef:
            name: feature-flags
            optional: true       # skip if CM missing
        - secretRef:
            name: order-secrets
        resources:
          requests: { cpu: 100m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }

When: many flags, naming already fits.

Downside: no selective import, no renames, pod restart on change.

Pattern 03

Mount as files (volume)

Use when the app reads a config file (application.yaml, nginx.conf, …). Files are auto-updated in place — no pod restart needed.

pattern-volume.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  namespace: orders
spec:
  replicas: 3
  selector:
    matchLabels: { app: order-api }
  template:
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: api
        image: ghcr.io/jahez/order-api:1.8.2
        ports:
        - { name: http, containerPort: 8080 }
        args: ["--spring.config.location=/etc/app/"]
        volumeMounts:
        - name: cfg
          mountPath: /etc/app       # every CM key becomes a file here
          readOnly: true
        resources:
          requests: { cpu: 100m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }
      volumes:
      - name: cfg
        configMap:
          name: order-config
          defaultMode: 0444       # read-only for everyone
          # optional: false means pod won't start if CM missing
          optional: false

Result: /etc/app/LOG_LEVEL, /etc/app/application.yaml, … each as a separate file.

Pattern 04

Mount specific keys with paths (items)

Pick only some keys, rename their file paths, and set per-file permissions.

pattern-items.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  namespace: orders
spec:
  replicas: 3
  selector:
    matchLabels: { app: order-api }
  template:
    metadata:
      labels: { app: order-api }
    spec:
      containers:
      - name: api
        image: ghcr.io/jahez/order-api:1.8.2
        ports:
        - { name: http, containerPort: 8080 }
        volumeMounts:
        - name: cfg
          mountPath: /etc/app
          readOnly: true
        resources:
          requests: { cpu: 100m, memory: 256Mi }
          limits:   { cpu: 500m, memory: 512Mi }
      volumes:
      - name: cfg
        configMap:
          name: order-config
          # only project these keys, at these paths, with these modes
          items:
          - key: application.yaml
            path: config/app.yaml    # relative to mountPath
            mode: 0440
          - key: logback.xml
            path: config/logback.xml
          # unlisted CM keys are NOT projected

When: the ConfigMap holds many keys but this container only needs a subset, at specific paths.

The auto-update mechanic (the subtle one)

When a ConfigMap or Secret is mounted as a volume, the kubelet watches the API server and replaces the files on disk when the object changes. Propagation takes on the order of 60 seconds (dependent on kubelet-sync-frequency and cache TTL).

But: env vars do NOT auto-update. The process started with whatever was in environ at launch. Updating the ConfigMap has no effect until the pod restarts.

Figure 6.1 — Propagation: file vs. env
Trick

To force a rolling restart when a ConfigMap changes (to pick up new env vars), add a hash annotation to the pod template: checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }} in Helm, or use kubectl rollout restart deployment.

Part IV · Secrets

Sensitive data — with all the caveats you need to know

Secrets look almost identical to ConfigMaps on the surface, but they behave very differently under the hood: eight distinct types, base64 encoding (not encryption!), tmpfs-backed volume mounts, and a completely different security story. Here's what you must know.

07Secrets — Deep Dive

Definition — what a Secret actually is

A Secret is a namespaced Kubernetes API object (kind: Secret, apiVersion: v1, resource name: secrets) designed to hold sensitive data: passwords, OAuth tokens, TLS private keys, SSH keys, image-pull credentials. Structurally it's almost identical to a ConfigMap — same key/value shape, same creation patterns, same namespace scoping — but with four critical differences in behavior and storage.

Where is it stored?

Just like ConfigMaps, Secrets live in etcd under /registry/secrets/<namespace>/<name>. The difference: when you configure EncryptionConfiguration on the apiserver (with a provider like aescbc, kms, or aesgcm), the values of Secrets are encrypted before being written to etcd — so even someone with raw etcd access sees ciphertext, not plaintext. ConfigMaps can also be encrypted this way, but Secrets are the canonical target. See §12 for the full setup.

The four key differences from ConfigMaps:

  1. Values are base64-encoded in data (not encryption — encoding only). This exists so binary data can travel cleanly through JSON/YAML. You can use stringData to write plain strings and let Kubernetes base64 them for you.
  2. Can be encrypted at rest in etcd via EncryptionConfiguration — Secrets are the primary object this feature is designed for.
  3. Mounted as tmpfs (RAM), not disk. When a Secret is projected into a pod as a volume, the kubelet mounts it on a RAM-backed tmpfs filesystem — so the plaintext never touches the node's disk. ConfigMaps are also mounted as tmpfs in practice, but for Secrets this is a hard guarantee.
  4. Typed. The type field (e.g. Opaque, kubernetes.io/tls, kubernetes.io/dockerconfigjson) dictates required keys and how other components (kubelet, ingress controllers, the container runtime) interpret the data. See §8 for all 8 types.
Base64 ≠ encryption

echo 'cGFzc3dvcmQ=' | base64 -d → password. Anyone with get secrets RBAC, or anyone reading raw etcd without encryption-at-rest enabled, sees plaintext. Security comes from the combination of: RBAC (who can read), encryption-at-rest (how etcd stores it), network policy (who can call the apiserver), audit logging (who actually read it), and tmpfs mounts (plaintext never on node disk). Encoding is just for transport.

Memory footprint and node impact

Because Secrets mount as tmpfs, every Secret projected into a pod consumes RAM on the node. The kubelet charges this against the node's total memory, not the container's memory limit. For a pod that mounts 10 Secret volumes of 1 MiB each, that's 10 MiB of node RAM held for the pod's lifetime. On small nodes running many pods, this adds up — a good reason not to project Secrets you don't actually use.

Every pod's ServiceAccount token is a Secret (sort of)

Before Kubernetes 1.24, every pod had a Secret of type kubernetes.io/service-account-token auto-mounted at /var/run/secrets/kubernetes.io/serviceaccount/. Since 1.24, this is generated via the TokenRequest API as a short-lived projected token and is not persisted as a Secret object anymore — a security win. Your older clusters may still have legacy SA-token Secrets lying around; kubectl get secrets --all-namespaces | grep service-account.

Anatomy

secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: order-secrets
  namespace: orders
type: Opaque   # default — arbitrary user data
data:
  # base64-encoded values
  db.password: c3VwZXJTZWNyZXQxMjM=       # "superSecret123"
  stripe.api_key: c2tfdGVzdF9YWFhYWA==

# OR use stringData: plain strings, k8s will base64 them for you
stringData:
  jwt.secret: "change-me-in-prod"

When both data and stringData are present, stringData wins on conflicting keys. stringData is write-only: when you kubectl get secret -o yaml, it always comes back as data.

Creating secrets — avoid secrets in git

secret-create.sh
# Preferred for manual ops (never committed to git):
kubectl create secret generic order-secrets \
  --from-literal=db.password='$uper$ecret123' \
  --from-literal=stripe.api_key='sk_live_abc'

# From files (useful for certs, SSH keys):
kubectl create secret generic tls-certs \
  --from-file=tls.crt=./server.crt \
  --from-file=tls.key=./server.key

# TLS shorthand (validates types + paths):
kubectl create secret tls ingress-tls \
  --cert=./tls.crt --key=./tls.key

# Docker registry auth:
kubectl create secret docker-registry ghcr-creds \
  --docker-server=ghcr.io --docker-username=jahez-ci \
  --docker-password='ghp_xxx' --docker-email=ci@jahez.sa
GitOps with secrets

Never commit raw Secret YAML. Use one of: Sealed Secrets (bitnami), SOPS + age/KMS, External Secrets Operator (pulls from AWS/GCP/Vault), or HashiCorp Vault Agent Injector. The manifest in git should be the encrypted or reference form; the plaintext never leaves the secret store.

09Immutable ConfigMaps & Secrets

Since Kubernetes 1.21 (GA), you can mark ConfigMaps and Secrets as immutable. Once created, their data / binaryData can never change — only the whole object can be deleted.

immutable.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: order-config-v23
immutable: true     # ← after this, data is frozen
data:
  LOG_LEVEL: "info"

Why you want it

  • Performance: kubelet stops watching for changes → fewer API server RPCs, cheaper at scale (thousands of pods on one ConfigMap).
  • Safety: no accidental mutation in production.
  • Versioned config pattern: name your ConfigMap order-config-v23; when config changes, create order-config-v24, update the Deployment to reference it, get a clean rolling update. Old pods keep their old config; rollback is trivial.
Trade-off

You lose hot-reload. Any change = new object = rolling restart. In practice this is usually what you want for production config: explicit, versioned, reviewable.

Putting it all together — how and when

Now that you know the three primitives individually, let's see how they flow through the cluster, how to choose between them, what the anti-patterns look like, and how a real service uses every one of them.

10Cluster Architecture & Data Flow

How ConfigMaps and Secrets actually move from kubectl apply to bytes in your container.

Figure 10.1 — End-to-end data path

Kubelet's two delivery paths

Path A: env var injection

  1. Kubelet reads Pod spec
  2. Resolves all valueFrom against API server cache
  3. Builds final env list
  4. Passes to CRI via CreateContainer RPC
  5. Container starts with env set

Updates require container restart.

Path B: volume mount

  1. Kubelet creates an in-memory tmpfs
  2. Writes ConfigMap/Secret data as files
  3. Bind-mounts into container at mountPath
  4. Kubelet watches for changes, rewrites atomically via symlink swap

Updates propagate in ~60s without restart.

11Decision Matrix — When to Use What

① Is the value sensitive (password, token, key, cert)?
→ Yes → Secret
Is it enormous or binary?
→ File mount (volume).
Is it a short token the app reads from env?
→ secretKeyRef env var (accept the leak-risk trade-off).
→ No → ConfigMap (or literal env)
② Does the app read a file (YAML, properties, conf) or env vars?
→ file → mount ConfigMap / Secret as volume
→ env vars → env.valueFrom or envFrom
③ Must the config update without restart?
→ Yes → volume mount (+ app file-watcher)
→ No / prefer restart → env vars (+ checksum annotation to trigger rollout)
④ Does the value vary per environment (dev/stg/prod)?
→ Yes → ConfigMap or Secret — one per environment
→ No (same everywhere) → literal env in the Deployment still fine

12Security Hardening for Secrets

Default behavior is not secure enough for production. Here are the layered protections.

1. Encryption at rest in etcd

encryption-config.yaml
# Passed to kube-apiserver via --encryption-provider-config
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  providers:
  - kms:                # prefer a KMS-backed key (AWS/GCP/Vault)
      name: kms-provider
      endpoint: unix:///var/run/kmsplugin/socket.sock
      cachesize: 1000
      timeout: 3s
  - identity: {}        # fallback for reads; never for writes

Without this, Secrets sit in etcd in plaintext (base64 ≠ encrypted). A compromised etcd backup = every Secret exposed.

2. RBAC — principle of least privilege

rbac.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: orders
  name: order-secret-reader
rules:
- apiGroups: [""]
  resources: ["secrets"]
  resourceNames: ["order-secrets"]   # only THIS secret
  verbs: ["get"]                      # read, not list

Avoid cluster-wide secrets/list. A pod with list access can enumerate every Secret in its namespace.

3. Restrict mounting via ServiceAccount scope

A pod can only consume Secrets in its own namespace. Keep blast-radius small: one namespace per team / service boundary.

4. Use file mounts over env for ultra-sensitive values

❌ Risky

Secret as env var. Appears in /proc/<pid>/environ, inheritable by any exec'd child process, sometimes printed by crash handlers.

✅ Safer

Secret as file on tmpfs. Access-controlled by mode: 0400 and pod user. App reads once on startup. Not exposed to child processes by default.

5. External secret stores

For rotating secrets, audit trails, and separation of duty, use a dedicated secret manager. Two canonical integrations:

External Secrets Operator

You declare an ExternalSecret CRD; the operator fetches from AWS Secrets Manager / GCP Secret Manager / Vault / Azure Key Vault and materializes a native k8s Secret. Refreshes on a schedule.

Vault Agent Injector

A mutating webhook injects a Vault sidecar that authenticates with the pod's SA token, fetches secrets, and writes them to a shared volume. Secrets never become k8s Secrets at all.

6. Audit every secret access

audit-policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
# Log every read on secrets at Metadata level (who, when, which)
- level: Metadata
  resources:
  - group: ""
    resources: ["secrets"]
  verbs: ["get", "list", "watch"]

13Best Practices & Anti-Patterns

Do

  • One ConfigMap per logical concern. Don't dump feature flags, DB config, and logging into one blob.
  • Use versioned names (order-config-v7) + immutable: true for production config. Changes = new object + Deployment update.
  • Put checksums in the pod template annotations so a config change triggers a rolling update automatically.
  • Validate config at startup — fail fast if required keys are missing, rather than crashing three requests later.
  • Enable encryption at rest with a KMS provider, not just AES-CBC with a static key.
  • Scope RBAC with resourceNames so a pod can only read its own Secret, not every Secret in the namespace.
  • Use namespaces as security boundaries — one per team/service means Secret exposure is contained.
  • Rotate secrets. Build the rotation pathway from day one. External Secrets Operator or Vault Agent Injector makes it routine.
  • Prefer stringData for Secret authoring; you avoid human base64 errors.

Don't

  • Don't commit plaintext Secrets to git. Ever. Use Sealed Secrets, SOPS, or an external store.
  • Don't treat base64 as encryption. It is encoding only.
  • Don't pack huge blobs into a ConfigMap. The 1 MiB limit applies to the whole object and large ConfigMaps destabilize the API server watch cache.
  • Don't rely on env-var auto-update. It doesn't exist. Restart the pod.
  • Don't share a single "god" Secret across every service. Blast radius = everything.
  • Don't log Secrets. Scrub application logs; reject PRs that print env.
  • Don't grant secrets/list cluster-wide to CI or to service accounts. Enumeration is the first step in lateral movement.

Anti-pattern gallery

❌ The "env-var kitchen sink"

30+ value entries inlined in the Deployment. Any change requires editing the Deployment, which owns workload identity. Mixes "what runs" with "how it's configured."

Fix: extract to a ConfigMap, reference via envFrom or valueFrom.

❌ Storing a Base64-encoded password in a ConfigMap "for obfuscation"

This provides zero protection and misleads reviewers. ConfigMaps aren't encrypted at rest by default; Secrets are (when you configure it). Use the right type.

❌ Secret-as-env-var for something read once

The app reads STRIPE_KEY from env on startup, then never again. Now it lives in /proc/<pid>/environ for the container's whole lifetime, visible to every kubectl exec.

Fix: file mount with mode: 0400 and a specific UID.

❌ Not triggering restarts when env-backed ConfigMap changes

Change propagates to the cluster, but running pods still run with the old values. Operator assumes "it's updated" and forgets. Cue an incident 4 hours later.

Fix: checksum annotation on pod template, or kubectl rollout restart as part of the config-update pipeline.

❌ Using the default ServiceAccount for everything

Every pod in the namespace gets the same identity; any Secret any of them can read, all of them can read. Minimizes nothing.

Fix: one ServiceAccount per workload; RBAC pinned to resourceNames.

07 — Deployment (the centerpiece)

Every primitive in use: literal env, downward API, envFrom (both ConfigMaps), secretKeyRef, volume-mounted ConfigMap, volume-mounted Secret, image-pull Secret, checksum annotation for auto-restart-on-change.

07-deployment-order-api.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api
  namespace: orders
  labels:
    app.kubernetes.io/name: order-api
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }
  selector:
    matchLabels: { app.kubernetes.io/name: order-api }
  template:
    metadata:
      labels: { app.kubernetes.io/name: order-api }
      annotations:
        # Change the checksum → pod template changes → rolling restart
        checksum/config: "REPLACE_WITH_SHA256_OF_CONFIGMAPS"
        checksum/secret: "REPLACE_WITH_SHA256_OF_SECRETS"
    spec:
      serviceAccountName: order-api
      imagePullSecrets:
      - name: ghcr-creds
      securityContext:
        runAsNonRoot: true
        runAsUser: 10001
        fsGroup: 10001
        seccompProfile: { type: RuntimeDefault }
      containers:
      - name: api
        image: ghcr.io/jahez/order-api:1.8.2
        ports:
        - { name: http, containerPort: 8080 }
        securityContext:
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities: { drop: ["ALL"] }
        resources:
          requests: { cpu: "250m", memory: "512Mi" }
          limits:   { cpu: "1",    memory: "1Gi"   }

        # ── 1. Literal + Downward API env ────────────────
        env:
        - { name: SPRING_PROFILES_ACTIVE, value: "prod" }
        - { name: TZ,                     value: "Asia/Riyadh" }
        - name: POD_NAME
          valueFrom: { fieldRef: { fieldPath: metadata.name } }
        - name: POD_NAMESPACE
          valueFrom: { fieldRef: { fieldPath: metadata.namespace } }
        - name: POD_IP
          valueFrom: { fieldRef: { fieldPath: status.podIP } }
        - name: MEM_LIMIT_MB
          valueFrom:
            resourceFieldRef:
              containerName: api
              resource: limits.memory
              divisor: "1Mi"
        # JVM heap sized from container limit — fixes the gateway OOM pattern
        - name: JAVA_TOOL_OPTIONS
          value: "-XX:MaxRAMPercentage=70.0 -XX:+UseG1GC -XX:+ExitOnOutOfMemoryError"

        # Single sensitive value consumed as env (convenience; small blast radius)
        - name: JWT_SIGNING_KEY
          valueFrom:
            secretKeyRef:
              name: order-secrets
              key: jwt.signing.key

        # ── 2. Bulk import of non-sensitive config ───────
        envFrom:
        - configMapRef: { name: order-config }
        - configMapRef: { name: feature-flags, optional: true }

        # ── 3. File mounts ───────────────────────────────
        volumeMounts:
        - { name: app-config,  mountPath: /etc/app,     readOnly: true }
        - { name: app-secrets, mountPath: /etc/secrets, readOnly: true }
        - { name: tmp,         mountPath: /tmp }

        livenessProbe:
          httpGet:  { path: /actuator/health/liveness,  port: http }
          initialDelaySeconds: 30
          periodSeconds: 10
        readinessProbe:
          httpGet:  { path: /actuator/health/readiness, port: http }
          periodSeconds: 5

      volumes:
      # ConfigMap projected — only application.yaml file
      - name: app-config
        configMap:
          name: order-config
          items:
          - { key: application.yaml, path: application.yaml, mode: 0440 }
          defaultMode: 0440
      # Secret projected — just db.password file, not env
      - name: app-secrets
        secret:
          secretName: order-secrets
          items:
          - { key: db.password,    path: db.password,    mode: 0400 }
          - { key: stripe.api_key, path: stripe.api_key, mode: 0400 }
          defaultMode: 0400
      - name: tmp
        emptyDir: { medium: Memory, sizeLimit: 64Mi }

Deploy it

deploy.sh
# Apply in order (manifests are numbered on purpose)
kubectl apply -f order-service/

# Watch the rollout
kubectl -n orders rollout status deploy/order-api

# Confirm env landed correctly
kubectl -n orders exec deploy/order-api -- env | grep -E 'LOG_LEVEL|DB_HOST|POD_NAME|MEM_LIMIT'

# Confirm mounted config
kubectl -n orders exec deploy/order-api -- ls -la /etc/app /etc/secrets

# Inspect rendered config (secrets are NOT printed; file mode 0400)
kubectl -n orders exec deploy/order-api -- cat /etc/app/application.yaml

# Trigger restart after config change (if not using checksum automation)
kubectl -n orders rollout restart deploy/order-api

# Debug: view a secret (requires RBAC)
kubectl -n orders get secret order-secrets -o json \
  | jq '.data | map_values(@base64d)'

Update flow — changing a feature flag safely

  1. Edit 02-configmap-feature-flags.yaml (FF_EXPRESS_DELIVERY: "true").
  2. kubectl apply -f 02-configmap-feature-flags.yaml.
  3. Since it's consumed via envFrom (not a volume), running pods keep the old value.
  4. Recompute checksum/config annotation OR run kubectl rollout restart deploy/order-api.
  5. Rolling update replaces pods with maxUnavailable: 0 → no downtime.
  6. Rollback is trivial: re-apply the previous ConfigMap or kubectl rollout undo.
Production upgrade path

For real production: make the ConfigMap immutable + versioned (feature-flags-2026-04-18), bump the Deployment's envFrom.configMapRef.name, and let standard Deployment rollout + rollback handle safety. You get config history in git and in kubectl rollout history simultaneously.
