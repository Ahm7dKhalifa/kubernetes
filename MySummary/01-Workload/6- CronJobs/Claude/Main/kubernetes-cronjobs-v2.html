Kubernetes CronJobs

The complete guide — cron syntax, concurrency policies, missed schedules, history limits, and SRE operations. Interactive step-by-step workflows.

01 What Is a CronJob & Why?

Definition — CronJobA CronJob creates Jobs on a time-based schedule. It's like a cron daemon in Linux but for Kubernetes. At each scheduled time, the CronJob controller creates a new Job object, which creates Pods that run to completion. The CronJob is the scheduler; the Job is the execution; the Pod does the work.
Definition — Three-Level ChainCronJob → Job → Pod. CronJob creates Jobs on schedule. Each Job creates one or more Pods. Pods run the actual command and exit. After completion, Jobs and Pods are kept (for logs) until cleanup.
Use CaseScheduleExample
Database backupDaily 2 AM0 2 * * *
Log rotationHourly0 * * * *
Report generationMonday 9 AM0 9 * * 1
Cache cleanupEvery 15 min*/15 * * * *
SSL cert renewalMonthly 1st0 0 1 * *
Health check pingEvery 5 min*/5 * * * *
ETL data syncNightly midnight0 0 * * *
Invoice generationLast day of month0 0 28-31 * *
Analogy

A CronJob is an alarm clock. At the set time, it rings (creates a Job). The Job does the task (Pod runs). When done, the alarm resets and waits for the next scheduled time. If the alarm is snoozed (suspended), it doesn't ring until un-snoozed.

04 Cron Schedule Syntax ▶

Common Mistake

* * * * * runs every minute (60 Jobs/hour, 1440 Jobs/day!). Make sure you actually need that frequency. For testing, use */5 * * * * (every 5 min) instead.

06 Timezone

Definition — timeZone(v1.27+ stable) By default, CronJobs use the kube-controller-manager's timezone (usually UTC). You can specify a timezone using the timeZone field with an IANA timezone name.
spec:
  schedule: "0 9 * * 1-5"
  timeZone: "America/New_York"   # Runs at 9 AM Eastern
SRE Principle

Always specify timeZone explicitly. Without it, your CronJob uses the cluster's timezone (usually UTC), which may not match your business hours. A "daily 9 AM" report could run at 9 AM UTC = 4 AM Eastern if you forget.

07 Full CronJob YAML — Every Field Explained

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
  namespace: production
spec:
  schedule: "30 2 * * *"              # When — daily at 2:30 AM
  timeZone: "UTC"                     # Timezone (default: controller's TZ)
  concurrencyPolicy: Forbid           # What if previous still running?
  startingDeadlineSeconds: 200        # Max seconds late to still start
  suspend: false                      # true = pause scheduling
  successfulJobsHistoryLimit: 3       # Keep last 3 successful Jobs
  failedJobsHistoryLimit: 1           # Keep last 1 failed Job

  jobTemplate:                          # Job spec — same as a regular Job
    spec:
      backoffLimit: 3                  # Retries per Job run
      activeDeadlineSeconds: 1800      # Max 30 min per Job run
      ttlSecondsAfterFinished: 86400  # Auto-delete Job 24h after finish
      template:                        # Pod spec — same as always
        spec:
          restartPolicy: Never        # Never or OnFailure (not Always!)
          containers:
          - name: backup
            image: postgres:16
            command: ["sh","-c","pg_dump mydb > /backup/dump.sql"]
            resources:
              requests: { cpu: "200m", memory: "256Mi" }
              limits: { cpu: "500m", memory: "512Mi" }
Key StructureCronJob has a jobTemplate (not template). Inside jobTemplate.spec you put all Job fields (backoffLimit, completions, parallelism, etc.). Inside jobTemplate.spec.template you put the Pod spec. It's three levels deep: CronJob → jobTemplate → template.

09 concurrencyPolicy ▶

Definition — concurrencyPolicyControls what happens when a new schedule fires but the previous Job is still running. Three options: Allow, Forbid, Replace.
Allow
Forbid
Replace
Comparison
Allow (default) — Run concurrently
concurrencyPolicy: Allow
02:00 → Job-1 starts (takes 90 min)
03:00 → Job-2 starts (Job-1 still running!)
03:30 → Job-1 finishes
04:00 → Job-3 starts (Job-2 may still be running)

⚠ Multiple Jobs can run simultaneously. Can overload cluster or cause data conflicts.
Forbid — Skip new run if previous is active
concurrencyPolicy: Forbid
02:00 → Job-1 starts (takes 90 min)
03:00 → SKIPPED! Job-1 still running → new run is skipped
03:30 → Job-1 finishes
04:00 → Job-2 starts (Job-1 done now)

✓ Safe. Never more than 1 Job running. Skipped runs are lost — they don't queue up.
Replace — Kill running Job, start new one
concurrencyPolicy: Replace
02:00 → Job-1 starts (takes 90 min)
03:00 → Job-1 KILLED! → Job-2 starts
04:00 → Job-2 KILLED! (if still running) → Job-3 starts

⚠ Aggressive. Running Job is terminated mid-execution. Data may be lost. Use only when latest run is always more important than completing the previous one.
PolicyPrevious still running?RiskUse when
AllowBoth run simultaneouslyResource overload, conflictsIndependent tasks, stateless
ForbidNew run is skippedSafestDB backup, any task that shouldn't overlap
ReplaceOld Job killed, new startsData lossLatest data always more important

11 startingDeadlineSeconds ▶

Definition — startingDeadlineSecondsThe maximum number of seconds past the scheduled time that the CronJob controller will still create a Job. If the controller can't create the Job within this window (e.g., controller was down), the run is considered missed.
How it works
Without deadline
With deadline
startingDeadlineSeconds: 200
Scheduled time: 02:00:00
Acceptable start window: 02:00:00 to 02:03:20 (200 seconds)

If Job is created at 02:01:30 → OK ✓ (within 200s)
If Job is created at 02:05:00 → TOO LATE ✗ (300s > 200s limit) → run skipped
Without startingDeadlineSeconds (default)
If the controller was down from 02:00 to 04:00:

Controller checks: "How many runs did I miss?"
Missed: 02:00, 03:00 = 2 missed runs.

If missed < 100 → create Job now for the last missed schedule
If missed ≥ 100 → do NOT create Job. Log error. CronJob is stuck.
The 100 Missed Schedules Rule

If the CronJob misses 100 or more consecutive schedules, the controller stops trying and logs: "Cannot determine if job needs to be started. Too many missed start time". You must fix the issue manually. This prevents a flood of catch-up Jobs.

With startingDeadlineSeconds: 200
Controller was down from 02:00 to 04:00:

Controller wakes up at 04:00. Checks missed runs within the 200s window:
02:00 → 04:00 - 02:00 = 7200s > 200s → missed, too late
03:00 → 04:00 - 03:00 = 3600s > 200s → missed, too late

No Jobs created. Waits for next scheduled time (05:00).

With startingDeadlineSeconds, the "100 missed" rule is less likely to trigger because the controller only counts misses within the deadline window.

12 Missed Schedules ▶

Why they happen
What K8s does
100-miss limit
Why schedules can be missed
CauseExample

What Kubernetes does about missed schedules
Missed < 100 runs:
→ Controller creates ONE Job immediately for the latest missed schedule
→ Only the LAST missed run is executed (not all of them)

Missed ≥ 100 runs:
→ Controller gives up. Logs error. No Jobs created.
→ Must manually fix: delete CronJob, recreate, or unsuspend.
The 100-Miss Rule in Detail
CronJob: every minute (* * * * *)

Controller down for 2 hours = 120 missed schedules

120 ≥ 100 → "Too many missed start times"
CronJob STOPS creating Jobs entirely!

Fix: Set startingDeadlineSeconds (e.g., 300). This limits the miss count to the deadline window, making 100 misses much harder to reach.
SRE Principle

Always set startingDeadlineSeconds on production CronJobs. Without it, a controller outage can permanently stall your CronJob with the 100-miss limit. A value of 200-600 is reasonable for most schedules.

13 Job Failure Inside a CronJob

Key RuleWhen a Job created by a CronJob fails (backoffLimit exceeded or activeDeadlineSeconds reached), the Job is marked Failed. The CronJob does NOT retry it — it waits for the next scheduled time and creates a fresh Job. The failed Job is kept (up to failedJobsHistoryLimit).
CronJob (schedule: 0 * * * *)

01:00 → Job-1 → FAILED (backoffLimit exceeded)
CronJob does NOT retry Job-1. It's done.

02:00 → Job-2 → Complete ✓ (fresh start, new Job)
03:00 → Job-3 → Complete ✓ 
# Configure retry behavior INSIDE the Job template:
jobTemplate:
  spec:
    backoffLimit: 3                # Retry failed Pod 3 times within this Job run
    activeDeadlineSeconds: 1800  # Kill Job if not done in 30 min

14 History Limits ▶

DefinitionsuccessfulJobsHistoryLimit and failedJobsHistoryLimit control how many completed/failed Jobs are kept. Default: successful=3, failed=1. Set to 0 to keep none (auto-delete immediately).
Defaults
Without limits
YAML examples
Default: Keep 3 successful, 1 failed
CronJob runs hourly for 10 hours → 10 Jobs created

Job-08 ✓ Job-09 ✓ Job-10 ✓ ← 3 kept
Job-01 through Job-07 ← auto-deleted by controller

If Job-05 failed:
Job-05 ✗ ← 1 failed kept (failedJobsHistoryLimit: 1)
Without limits (not set or very high) — Problem!
CronJob: every minute for 1 week
= 7 × 24 × 60 = 10,080 Jobs + 10,080 Pods accumulated!

etcd storage bloat. kubectl output unusable. Controller slows down.
# Keep more history (for debugging)
successfulJobsHistoryLimit: 10
failedJobsHistoryLimit: 5

# Keep none (auto-delete immediately — saves resources)
successfulJobsHistoryLimit: 0
failedJobsHistoryLimit: 0

# Production recommendation:
successfulJobsHistoryLimit: 3   # enough to check last 3 runs
failedJobsHistoryLimit: 3      # enough to diagnose failures

15 TTL & Cleanup

Two cleanup mechanisms(1) History limits (CronJob-level) — keeps N latest Jobs, deletes older ones. (2) ttlSecondsAfterFinished (Job-level) — auto-deletes each Job N seconds after it finishes. Use both together for thorough cleanup.
spec:
  successfulJobsHistoryLimit: 3       # CronJob-level: keep 3 latest
  failedJobsHistoryLimit: 1           # CronJob-level: keep 1 failed
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 3600  # Job-level: delete 1h after finish
SRE Rule

For CronJobs that run frequently (every minute/5 min), set successfulJobsHistoryLimit: 1 and ttlSecondsAfterFinished: 300. Without this, you'll have thousands of completed Jobs and Pods in a week.

16 Suspend & Resume ▶

Definition — suspendWhen set to true, the CronJob controller stops creating new Jobs on schedule. Already-running Jobs are NOT affected — they continue to completion. When set back to false, scheduling resumes from the next schedule time (missed runs during suspension are lost).
Suspend
Resume
Commands
YAML
Suspend — Stop scheduling
CronJob (schedule: 0 * * * *)

01:00 → Job-1 created ✓
01:30 → kubectl patch cronjob X -p '{"spec":{"suspend":true}}'
02:00 → SKIPPED (suspended)
03:00 → SKIPPED (suspended)

Job-1 (if still running) continues normally. Only NEW Jobs are suppressed.
Resume — Restart scheduling
04:30 → kubectl patch cronjob X -p '{"spec":{"suspend":false}}'
05:00 → Job-2 created ✓ (scheduling resumed!)

02:00 and 03:00 runs are lost — NOT retroactively created.
# Suspend
kubectl patch cronjob my-cron -p '{"spec":{"suspend":true}}'

# Resume
kubectl patch cronjob my-cron -p '{"spec":{"suspend":false}}'

# Check status
kubectl get cronjob my-cron
# SUSPEND column shows True or False
spec:
  suspend: true    # Paused — no new Jobs created
  # Change to false to resume

17 Manual Trigger — Run CronJob Now

DefinitionCreate a one-time Job FROM a CronJob's template. Doesn't wait for the schedule. The Job uses the exact same spec as the CronJob would produce. The CronJob's schedule is unaffected.
# Create a Job immediately using the CronJob's template
kubectl create job manual-backup --from=cronjob/nightly-backup

# Check it
kubectl get jobs
kubectl logs job/manual-backup
Use Cases

(1) Test a new CronJob without waiting. (2) Re-run a failed schedule. (3) Emergency manual execution of a nightly task during an incident. (4) Verify the CronJob template produces working Pods before the first schedule fires.

19 Monitoring & Best Practices

Metric / CheckAlert When
kube_cronjob_status_activeactive > 0 for > expected Job duration
kube_cronjob_next_schedule_timenext schedule is in the past (stuck)
kube_job_status_failed (child Jobs)Any child Job failed
lastScheduleTimeNo schedule fired in expected window
Always set concurrencyPolicy: Forbid

Unless you explicitly need concurrent runs. Forbid prevents resource overload and data conflicts from overlapping Jobs.

Always set startingDeadlineSeconds

Prevents the 100-missed-schedules stall. Set to 2× your schedule interval (e.g., schedule every hour → deadline 7200s).

Always set history limits

Default 3/1 is fine for hourly. For every-minute CronJobs, use 1/1 or 0/1 to prevent thousands of accumulated Jobs.

Always set activeDeadlineSeconds on the Job template

A stuck Job without a deadline runs forever, blocking Forbid policy from starting the next run. The deadline is your safety net.

Test with manual trigger before relying on schedule

kubectl create job test --from=cronjob/NAME verifies the template works before the first real schedule fires.

SRE Wisdom

CronJobs are the most common source of "silent failures" in production. A CronJob can fail every night for a week and nobody notices unless you have alerts on kube_job_status_failed. Monitor them like you monitor your main services.
