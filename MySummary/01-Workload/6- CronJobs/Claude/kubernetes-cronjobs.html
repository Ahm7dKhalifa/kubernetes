Kubernetes CronJobs

A deep-dive guide to scheduling, managing, and mastering time-based batch workloads in Kubernetes.

01 What is a CronJob?

A CronJob is a Kubernetes resource that creates Job objects on a repeating schedule. It's the Kubernetes equivalent of Linux's crontab — but instead of running shell commands on a single server, it launches full Kubernetes Jobs across your cluster.

Think of it this way

A Job is a one-time delivery truck. A CronJob is the delivery company that dispatches a new truck every day at 8 AM.

CronJob → Job → Pod — Three-Level Hierarchy

The CronJob Controller (running inside kube-controller-manager) checks approximately every 10 seconds whether any CronJob is due. When a schedule triggers, it creates a new Job object — which in turn creates Pod(s) to do the actual work. Each trigger is independent; a new Job name is auto-generated each time.

06 Time Zones

By default, CronJob schedules are evaluated against the kube-controller-manager's time zone (usually UTC). Since Kubernetes v1.27 (stable), you can set a specific time zone using the timeZone field.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "30 2 * * *"
  timeZone: "America/New_York"   # ← Runs at 2:30 AM Eastern
How It Works

The timeZone field accepts any valid IANA time zone (e.g., Europe/London, Asia/Tokyo, UTC). It correctly handles daylight saving time transitions — so "2:30 AM New York" always means local 2:30 AM, whether EDT or EST.

Watch Out

If you don't set timeZone, the schedule runs in the controller-manager's timezone. In most cloud providers this is UTC, which can cause confusion when you expect "midnight" to mean your local midnight.

07 CronJob YAML File

Here is a complete, annotated CronJob manifest covering all important fields:

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-db-backup
  labels:
    app: backup-system
spec:

  # ── Schedule ──
  schedule: "30 2 * * *"            # Every day at 2:30 AM
  timeZone: "America/New_York"      # In Eastern time

  # ── Concurrency ──
  concurrencyPolicy: Forbid         # Don't start a new Job if previous is running

  # ── Deadline ──
  startingDeadlineSeconds: 200      # If missed by 200s, skip this trigger

  # ── History ──
  successfulJobsHistoryLimit: 3    # Keep last 3 successful Jobs
  failedJobsHistoryLimit: 5        # Keep last 5 failed Jobs

  # ── Suspend ──
  suspend: false                   # Set true to pause all future triggers

  # ── Job Template (what the CronJob creates) ──
  jobTemplate:
    spec:
      backoffLimit: 3
      activeDeadlineSeconds: 1800   # Each Job must finish in 30 minutes
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: backup
            image: myapp/db-backup:v3
            command: ["/bin/sh", "-c", "pg_dump ... | gzip > /backups/db.gz"]
            resources:
              requests:
                cpu: "250m"
                memory: "256Mi"
            volumeMounts:
            - name: backup-vol
              mountPath: /backups
          volumes:
          - name: backup-vol
            persistentVolumeClaim:
              claimName: backup-pvc
Structure

A CronJob is essentially a wrapper around a Job. The outer spec defines scheduling behavior (schedule, concurrency, history). The inner jobTemplate.spec is a normal Job spec with all its usual fields (backoffLimit, parallelism, template, etc.).

08 Concurrency Policy

What happens when a new trigger fires but the previous Job is still running? The concurrencyPolicy field controls this.

Allow
Default

Multiple Jobs can run simultaneously. No limits on overlap.

Forbid
Skip if busy

If a Job is still running, the new trigger is skipped. The missed run is not rescheduled.

Replace
Kill & restart

The old running Job is terminated and a new one starts in its place.

Concurrency Policy — Visual Comparison
PolicyWhen to Use
AllowJobs are idempotent and independent — safe to run in parallel (e.g., stateless reports).
ForbidJobs must NOT overlap — running two at once causes conflicts (e.g., database backup, data sync).
ReplaceOnly the latest run matters — kill the old one and start fresh (e.g., cache rebuild, latest snapshot).

09 Job History Limits

Every time a CronJob triggers, it creates a new Job object. Over time, these pile up. History limits control how many old Jobs are kept for inspection and how many are automatically deleted.

spec:
  successfulJobsHistoryLimit: 3    # Keep 3 most recent successful Jobs (default: 3)
  failedJobsHistoryLimit: 5        # Keep 5 most recent failed Jobs (default: 1)
History Limit = 3 — Auto-Cleanup Visualization
Pro Tip

Set failedJobsHistoryLimit to at least 3-5 so you can debug recent failures. Setting it to 0 means failed Jobs are deleted immediately — you'll lose their logs before you can inspect them.

10 Starting Deadline

The startingDeadlineSeconds field defines a grace period: if the controller misses a scheduled trigger (due to downtime, high load, etc.), how many seconds late can it still start the Job?

spec:
  startingDeadlineSeconds: 300  # 5 minutes grace period
Starting Deadline — Missed Trigger Behavior
Key Behavior

If startingDeadlineSeconds is not set, the CronJob controller counts how many triggers were missed. If it counts 100+ missed triggers, it stops trying and logs an error: "Cannot determine if job needs to be started. Too many missed start times."

11 Suspend & Resume

You can pause a CronJob without deleting it by setting suspend: true. No new Jobs will be created while suspended. Already-running Jobs continue to completion.

# Suspend (stop future triggers)
kubectl patch cronjob/nightly-db-backup -p '{"spec":{"suspend":true}}'

# Resume (re-enable triggers)
kubectl patch cronjob/nightly-db-backup -p '{"spec":{"suspend":false}}'
Suspend Timeline
Missed Triggers During Suspension

Any triggers that fire during suspension are counted as missed. When you resume, the controller checks if any should still be started (subject to startingDeadlineSeconds). If too many were missed (100+), it won't catch up.

12 Failure Handling

CronJobs have two layers of failure handling: the CronJob level (schedule-related) and the Job level (execution-related).

CronJob-Level Failures

These are about the schedule itself:

Missed triggers — Controller was down or overloaded. Controlled by startingDeadlineSeconds.

Concurrent conflict — Previous Job still running. Controlled by concurrencyPolicy.

100+ missed — Controller gives up and logs an error.

Job-Level Failures

These are about Pod execution (inherited from Job spec):

Pod crashes — Controlled by backoffLimit and restartPolicy.

Timeout — Controlled by activeDeadlineSeconds.

Specific exit codes — Controlled by podFailurePolicy.

13 Patterns & Best Practices

Common CronJob Patterns

PatternScheduleKey Settings
Nightly Backup 30 2 * * * concurrencyPolicy: Forbid, activeDeadlineSeconds: 3600
Hourly Report 0 * * * * concurrencyPolicy: Allow, ttlSecondsAfterFinished: 7200
Cache Rebuild */10 * * * * concurrencyPolicy: Replace (only latest matters)
Monthly Cleanup 0 0 1 * * startingDeadlineSeconds: 43200 (12h window)
Business Hours Sync */15 9-17 * * 1-5 concurrencyPolicy: Forbid, timeZone set

Best Practices

Do

Always set timeZone — Don't rely on the controller's default timezone. Be explicit.

Set startingDeadlineSeconds — Without it, 100+ missed triggers = permanent failure.

Use concurrencyPolicy: Forbid for any Job that touches shared state (databases, files).

Set activeDeadlineSeconds on the Job template — prevent runaway Jobs from blocking the next trigger.

Make Jobs idempotent — since missed or double-triggered runs can happen, your task should be safe to run multiple times.

Keep failedJobsHistoryLimit ≥ 3 — so you can always debug recent failures.

Avoid

Don't schedule at exact popular times — e.g., 0 0 * * * (midnight) creates a thundering herd. Offset: 17 3 * * *.

Don't use sub-minute schedules — CronJobs have a minimum granularity of 1 minute. For sub-minute needs, use a Deployment with a sleep loop.

Don't forget resource limits — CronJob Pods without limits can starve other workloads during trigger storms.

Quick Commands Reference

# Create a CronJob
kubectl apply -f cronjob.yaml

# List CronJobs
kubectl get cronjobs

# See CronJob details (last trigger time, active Jobs)
kubectl describe cronjob/nightly-db-backup

# List Jobs created by a CronJob
kubectl get jobs --selector=job-name -l app=backup-system

# Manually trigger a CronJob right now
kubectl create job --from=cronjob/nightly-db-backup manual-run-001

# Suspend a CronJob
kubectl patch cronjob/nightly-db-backup -p '{"spec":{"suspend":true}}'

# Resume a CronJob
kubectl patch cronjob/nightly-db-backup -p '{"spec":{"suspend":false}}'

# Delete a CronJob (deletes all child Jobs and Pods too)
kubectl delete cronjob nightly-db-backup

# View logs of the most recent CronJob run
kubectl logs job/$(kubectl get jobs --sort-by=.metadata.creationTimestamp \
  -o jsonpath='{.items[-1].metadata.name}')
Summary

Kubernetes CronJobs are the foundation for all scheduled batch work in your cluster. Master the cron syntax, choose the right concurrencyPolicy, set proper deadlines and history limits, and always make your Jobs idempotent. With these pieces in place, you get reliable, self-managing, production-grade scheduled workloads.
