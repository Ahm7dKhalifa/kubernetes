Kubernetes Jobs

A deep-dive guide to running, managing, and mastering batch workloads in Kubernetes.

01 What is a Job?

A Job is a Kubernetes resource that creates one or more Pods and ensures they run to successful completion. Unlike a Deployment (which keeps Pods running forever), a Job's mission is to finish a task and stop.

Think of it this way

A Deployment is like a 24/7 store — always open. A Job is like a delivery truck — it arrives, drops off the package, and leaves.

The Job Controller (running inside the kube-controller-manager) watches for Job objects. When it finds one, it creates the required Pod(s). If a Pod fails, the controller can create a replacement — up to a configurable retry limit.

04 Job YAML File

Here is a complete, annotated Job manifest covering all important fields:

apiVersion: batch/v1
kind: Job
metadata:
  name: data-processing-job
  labels:
    app: batch-processor
spec:

  # ── Completion Settings ──
  completions: 5           # Total successful completions needed
  parallelism: 2           # Max Pods running at the same time
  completionMode: Indexed  # Each Pod gets a unique index (0..N-1)

  # ── Failure Handling ──
  backoffLimit: 4           # Max retries before marking Job as Failed
  activeDeadlineSeconds: 600 # Timeout: kill Job after 10 minutes

  # ── Cleanup ──
  ttlSecondsAfterFinished: 3600 # Auto-delete Job 1 hour after done
  suspend: false            # Set to true to pause the Job

  # ── Pod Template ──
  template:
    metadata:
      labels:
        app: batch-processor
    spec:
      restartPolicy: Never   # Must be Never or OnFailure (not Always!)
      containers:
      - name: worker
        image: myapp/processor:v2
        command: ["python", "process.py"]
        resources:
          requests:
            cpu: "500m"
            memory: "256Mi"
          limits:
            cpu: "1"
            memory: "512Mi"
Important Rule

restartPolicy in a Job must be Never or OnFailure. You cannot use Always because the Pod is supposed to terminate after completing its work.

05 Job Completions

The completions field tells Kubernetes: "This Job is done only when N Pods have exited successfully (exit code 0)."

Completion Modes

NonIndexed (default)

Each successful Pod is counted equally. Pods are interchangeable — no identity. The Job is complete when the total count of succeeded Pods ≥ completions.

Indexed

Each Pod gets a unique index from 0 to completions - 1 via the JOB_COMPLETION_INDEX env variable. The Job is done when every index has one success. Great for sharded processing.

Completions = 4, Parallelism = 2 — Timeline

06 Job Parallelism

The parallelism field controls the maximum number of Pods running at the same time. Kubernetes will never schedule more than this many Pods concurrently for the Job.

parallelismBehavior
1 (default)One Pod at a time — sequential execution.
NUp to N Pods run concurrently. New Pods launch as others complete.
0Job is paused — no Pods are scheduled.
How They Work Together

If completions: 10 and parallelism: 3, Kubernetes runs up to 3 Pods at a time. As each succeeds, a new one is launched — until 10 total have succeeded. Think of it like a pool with a max capacity of 3 workers.

Parallelism Pool — completions: 6, parallelism: 3

07 Fixed Completion vs Work Queue Jobs

These are the two main patterns for parallel Jobs. The difference is who decides when the work is done.

Fixed Completion Count

Kubernetes decides. You set completions: N. The Job Controller tracks successes and stops when N Pods have exited successfully.

Best for: Processing a known, fixed number of items (100 images, 50 reports).

completions: 100
parallelism: 10

Work Queue

Your Pods decide. Leave completions unset. Each Pod pulls from an external queue (Redis, RabbitMQ, SQS). When a Pod finds the queue empty, it exits successfully.

Best for: Unknown or dynamic workloads, event-driven processing.

# completions is NOT set
parallelism: 5

09 Pod Backoff Failure Policy

When a Pod fails, the Job Controller doesn't immediately retry — it uses exponential backoff. Each retry waits longer: 10s → 20s → 40s → … up to a cap of 6 minutes.

spec:
  backoffLimit: 6   # Default. After 6 failures → Job is Failed
Exponential Backoff Timeline (backoffLimit: 6)
Watch Out

With restartPolicy: OnFailure, in-Pod container restarts also count toward backoffLimit. If a container crash-loops 6 times inside one Pod, the entire Job is marked Failed.

10 Pod Failure Policy

Introduced in Kubernetes v1.26 (stable in v1.31), podFailurePolicy gives you fine-grained control over what happens when a Pod fails — based on exit codes or Pod conditions.

Why Do We Need This?

Without it, every failure counts the same — a bug crash and a transient OOM both eat a retry. With podFailurePolicy you can say: "If exit code = 42, don't retry — fail immediately" or "If it's an eviction, ignore it."

spec:
  backoffLimit: 6
  podFailurePolicy:
    rules:

    # Rule 1: Exit code 42 = permanent bug → FailJob immediately
    - action: FailJob
      onExitCodes:
        containerName: worker
        operator: In
        values: [42]

    # Rule 2: Eviction → Ignore, don't count as failure
    - action: Ignore
      onPodConditions:
      - type: DisruptionTarget

    # Rule 3: Everything else → Count and retry normally
    - action: Count
      onExitCodes:
        operator: NotIn
        values: [0]
ActionMeaning
FailJobImmediately mark the entire Job as Failed. No more retries.
IgnoreDon't count this failure — Pod is replaced without consuming backoffLimit.
CountNormal behavior — counts toward backoffLimit.
FailIndex(Indexed Jobs only) Mark the specific index as failed without failing the whole Job.

11 Job Termination & Cleanup

When a Job finishes, the Pods remain in the cluster (in Completed or Failed state) so you can inspect logs. But they take up resources. Here's how to control cleanup:

FieldWhat It Does
activeDeadlineSecondsSets a maximum runtime for the entire Job. Once exceeded, all Pods are terminated and the Job fails. Counts from the first Pod start.
backoffLimitMaximum total failures allowed before the Job is marked Failed.
ttlSecondsAfterFinishedAutomatically deletes the Job (and its Pods) N seconds after completion. Set to 0 for immediate cleanup.
suspendSet to true to pause. Running Pods are deleted. Set back to false to resume.
Job Lifecycle — From Create to Cleanup
Pro Tip

Always set ttlSecondsAfterFinished in production. Without it, completed Jobs (and their Pods) pile up forever and clutter your cluster.

Quick Commands Reference

# Create a Job
kubectl apply -f job.yaml

# Watch Job progress
kubectl get jobs --watch

# See Pods created by a Job
kubectl get pods --selector=job-name=data-processing-job

# View logs from a Job Pod
kubectl logs job/data-processing-job

# Delete a Job (and its Pods)
kubectl delete job data-processing-job

# Suspend a running Job
kubectl patch job/data-processing-job --type=strategic \
  -p '{"spec":{"suspend":true}}'

# Resume a suspended Job
kubectl patch job/data-processing-job --type=strategic \
  -p '{"spec":{"suspend":false}}'
Summary

Kubernetes Jobs are your go-to for any task that should run to completion. Combine completions, parallelism, backoffLimit, and podFailurePolicy to build resilient, efficient batch workloads — from simple one-shot scripts to massive parallel processing pipelines.
