Scheduling & Pod Placement

How the kube-scheduler decides where every pod runs — and every lever you have to control it. nodeSelector, node & pod affinity, taints & tolerations, topology spread, priority & preemption — built on a real multi-node Jahez cluster across me-central-1.

01

What "scheduling" actually means

Scheduling is the single decision: which node does this Pod run on? Nothing more. The kube-scheduler watches for Pods that have no nodeName set yet, picks the best node for each one, and writes that choice back. The kubelet on the chosen node is what actually starts the containers.

When you kubectl apply a Deployment, no container starts immediately. The flow is: the Deployment controller creates a ReplicaSet, the ReplicaSet creates Pod objects, and those Pods land in etcd with an empty spec.nodeName. They sit in Pending. The scheduler's whole job is to fill in that one field. Once nodeName is set, the kubelet on that node notices "a Pod is assigned to me" and pulls images, mounts volumes, and runs containers.

Key mental model. The scheduler does not run your Pods. It only assigns them. Assignment = setting pod.spec.nodeName. Everything in this guide — nodeSelector, affinity, taints, topology spread — is just a way of constraining or biasing that one assignment decision.

The two questions every mechanism answers

Every placement feature in Kubernetes is answering one of two questions, from one of two directions:

DirectionQuestionMechanisms
Pod → Node
(pod is attracted)		"Which nodes am I willing to / want to run on?"nodeSelector, nodeName, node affinity, pod affinity/anti-affinity, topology spread, resource requests
Node → Pod
(node repels)		"Which pods am I willing to accept?"taints (the node pushes pods away) — pods need a matching toleration to be allowed

This is the cleanest way to keep them straight: affinity / selectors pull a pod toward nodes; taints push pods away from nodes. They are designed to be used together — §9 shows the classic GPU-node pattern that needs both.

02

The scheduling lifecycle

For each Pending pod the scheduler runs a pipeline of plugins. At a high level it is three phases: Filter (which nodes are even possible), Score (rank the survivors), and Bind (write the winner). Every feature in this guide plugs into one of these phases.

Modern Kubernetes implements this as the Scheduling Framework — a set of extension points (PreFilter, Filter, PostFilter, PreScore, Score, Reserve, Permit, Bind) each backed by plugins. You rarely touch the plugins directly; you influence them through pod spec fields.

How one pod gets scheduled1/4
Step 1 · Queue

A Pending pod enters the scheduling queue

The pod api-7f9 exists in etcd with nodeName: "". The scheduler's informer sees it and pushes it into the active queue. Higher-priority pods sort to the front.

Step 2 · Filter (Predicates)

Eliminate nodes that cannot run the pod

Filter plugins remove every node that fails a hard rule: not enough allocatable CPU/memory, a NoSchedule taint with no matching toleration, a failed nodeSelector / required node affinity, or no free ports. Here node 4 is filtered out — it carries an ml:NoSchedule taint and our pod has no toleration. Three feasible nodes remain.

Step 3 · Score (Priorities)

Rank the feasible nodes 0–100

Score plugins give each surviving node points: NodeResourcesFit (prefer least-loaded or most-packed depending on strategy), InterPodAffinity, PodTopologySpread (prefer the least-skewed zone), TaintToleration, image-locality, etc. Scores are weighted and summed.

Step 4 · Bind

Write nodeName on the winner

node 2 wins with the highest combined score. The scheduler issues a Bind, setting pod.spec.nodeName = node 2. The kubelet on node 2 sees the assignment and starts the containers. The decision is final — the scheduler never moves a running pod (that is the job of the separate descheduler).

egress / origin (blue dot) bind target (green arrow) scheduler's pick
Filter is a hard gate, Score is a soft preference. If zero nodes survive Filter, the pod stays Pending forever (you'll see 0/11 nodes are available in kubectl describe pod). If many survive, Score just picks the nicest one. This filter-vs-score split maps directly onto required vs preferred rules you'll meet in affinity (§6).

The cluster we'll use everywhere: Jahez on me-central-1

Every example in this guide schedules onto one realistic cluster: the Jahez food-delivery platform running on a managed Kubernetes cluster in the me-central-1 (Saudi Arabia) region, spread across three availability zones 1a, 1b, 1c. It has five distinct node pools, each with different labels and taints — which is exactly what makes scheduling interesting.

Why this shape? Three things drive almost every real placement rule: (1) hardware — GPUs and big-memory boxes are scarce and expensive, so only the workloads that need them should land there; (2) compliance/isolation — payments must be physically separated for PCI scope; (3) availability — we want replicas spread across 1a/1b/1c so one zone failure can't take a service down. Each maps to a different mechanism in this guide.

How the labels & taints got there

Labels and taints live on the Node object, not on pods. In a managed cluster you usually set them per node-pool at creation; you can also apply them imperatively. These commands set up the cluster above:

04

nodeName — manual binding (the scheduler bypass)

nodeName is the lowest-level placement tool: you write the node yourself and the scheduler is skipped entirely. No filtering, no scoring, no checks. It is rarely the right answer for apps, but understanding it makes everything else click — every other mechanism is just a smarter way of letting the scheduler choose this value for you.

If you set spec.nodeName directly on a pod, the pod is born already "scheduled". The kubelet on that node picks it up immediately. Because no Filter ran, this ignores taints, resource fit, and affinity — if the node is full, the kubelet will admit it anyway and may evict other pods, or the pod will fail with OutOfcpu.

nodeName skips the whole pipeline1/2
Step 1 · You name the node

The pod spec already contains the answer

With nodeName: wkr-a1 set, the pod never enters the scheduler queue. There is no Pending phase to speak of — the kubelet on wkr-a1 is the only actor.

Step 2 · Direct bind

kubelet on wkr-a1 runs it — no filter, no score

Note what is skipped: the gpu-a1 / pay-a1 / spot-c1 taints are never even consulted, because Filter never ran. If you had named a tainted node here, the pod would still land there. That is the danger of nodeName.

debug-pod-pinned.yaml
apiVersion: v1
kind: Pod
metadata:
  name: netshoot-debug
  namespace: jahez-ops
spec:
  nodeName: wkr-a1            # <-- bypasses the scheduler entirely
  containers:
    - name: netshoot
      image: ghcr.io/jahez/netshoot:1.4
      command: ["sleep", "3600"]
FieldTypeMeaning & gotchas
spec.nodeNamestringExact node name (matches kubernetes.io/hostname). When set, the scheduler ignores the pod. Cannot be combined meaningfully with affinity/selectors — they're simply not evaluated. If the node doesn't exist, the pod stays Pending with no event.
Don't use nodeName for apps. It defeats HA (the pod can't reschedule if the node dies — a Deployment will just recreate a new pod that's also pinned to the dead node), and it bypasses resource fit and taints. Legitimate uses: a one-off debug/diagnostic pod on a specific node, or the kubelet writing it for static pods. For everything else, use a selector or affinity and let the scheduler choose.

05

nodeSelector — the simplest real constraint

nodeSelector is a map of label key–value pairs a node must have for the pod to schedule there. It is a pure Filter-phase rule: any node missing even one of the listed labels is dropped. It's the 80% tool — if all you need is "run on the SSD nodes" or "run on the highmem pool", reach for this before affinity.

Our Elasticsearch data pods need lots of RAM, so they must land on the highmem pool (mem-a1, mem-b1) which carries the label jahez.sa/pool=highmem. A one-line selector expresses that.

nodeSelector pins ES to the highmem pool1/3
Step 1 · Pending

es-data pod needs a node with pool=highmem

All five pools are candidates before any rule is applied. The selector will turn this into a hard filter.

Step 2 · Filter on labels

Drop every node missing pool=highmem

general, gpu, pci and spot nodes all lack the label → filtered out. Only mem-a1 (and its sibling mem-b1, off-screen) survive. Note the gpu/pci/spot taints would have dropped them anyway — but here it's the missing label that does it.

Step 3 · Score & bind

Pick the least-loaded highmem node

Among the survivors the scheduler scores by resource fit and binds. A second ES replica is added to mem-a1. If no highmem node had capacity, the pod would stay Pending — nodeSelector gives you no fallback.

es-data-nodeselector.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: es-data
  namespace: jahez-search
spec:
  serviceName: es-data
  replicas: 2
  selector:
    matchLabels: { app: es-data }
  template:
    metadata:
      labels: { app: es-data }
    spec:
      nodeSelector:                      # ALL pairs must match (logical AND)
        jahez.sa/pool: highmem           # only the highmem pool
        kubernetes.io/os: linux          # belt-and-suspenders
      containers:
        - name: elasticsearch
          image: ghcr.io/jahez/elasticsearch:8.13
          resources:
            requests: { memory: 32Gi, cpu: "4" }
            limits:   { memory: 48Gi }
          ports:
            - { name: http, containerPort: 9200 }
FieldTypeBehaviour
spec.nodeSelectormap[string]stringFilter-phase. A node qualifies only if it carries every listed label with the exact value (logical AND). No operators, no OR, no preference — it's all-or-nothing.
nodeSelector vs node affinity. nodeSelector can only do equality AND across labels. The moment you need any of these values (In [a,b]), not this value (NotIn), label just exists (Exists), numeric comparison (Gt/Lt), or a soft preference instead of a hard rule — you've outgrown nodeSelector and want node affinity (§6). They can coexist; both must be satisfied.

Best practice. Use stable, intentional pool labels like jahez.sa/pool=highmem rather than incidental ones. Prefix custom labels with a domain you own (jahez.sa/) so they never collide with Kubernetes' own kubernetes.io/ labels.

06

Node affinity — expressive node selection

Node affinity is nodeSelector with a grammar. It adds operators (In, NotIn, Exists, DoesNotExist, Gt, Lt), OR logic, and crucially the required vs preferred split — hard rules that filter, plus soft rules that merely score. The two long field names encode exactly that.

Reading the two field names

Node affinity lives under spec.affinity.nodeAffinity with two children whose verbose names tell you precisely what they do:

FieldPhase"...IgnoredDuringExecution" means
requiredDuringSchedulingIgnoredDuringExecutionFilter (hard)Must match to schedule. Ignored during execution: if the node's labels change later, an already-running pod is not evicted.
preferredDuringSchedulingIgnoredDuringExecutionScore (soft)Adds weight (1–100) to matching nodes; if none match, the pod still schedules somewhere. Also not re-evaluated after the pod runs.
Why "IgnoredDuringExecution"? The name leaves room for a future RequiredDuringExecution that would evict running pods when labels change. That variant doesn't exist yet for node affinity, so today both are "ignored during execution". (Taints, by contrast, do have a during-execution effect — NoExecute, see §8.)

Structure: required is OR-of-AND, preferred is a weighted list

required contains nodeSelectorTerms — a list where terms are OR'd, and inside each term matchExpressions are AND'd. preferred is a flat list of {weight, preference} entries, each adding its weight to nodes matching that preference.

Scenario: the recommendation service ideally runs on a GPU node, but can fall back to a general node if GPUs are full. It must never run on highmem/pci/spot. That's a preferred GPU rule plus a required pool-membership rule.

reco service: required pool + preferred GPU1/4
Step 1 · Pending

reco pod with required + preferred affinity

Required: pool In [gpu, general]. Preferred: pool=gpu weight 80. (GPU node also needs a toleration — we add it; ignore the taint for this scoring story.)

Step 2 · Required = Filter

Drop nodes outside [gpu, general]

highmem, pci and spot all fail the required term → eliminated. Only wkr-a1 (general) and gpu-a1 (gpu) survive. If both required and nodeSelector were set, a node would need to satisfy both.

Step 3 · Preferred = Score

Add weight 80 to the GPU node

Both survivors are feasible, so now scoring decides. The preferred rule matches gpu-a1 only, adding 80 to its score. wkr-a1 gets 0 from this rule (but still has base resource-fit score).

Step 4 · Bind

GPU node wins on the weighted score

gpu-a1 ends up highest and is chosen. If gpu-a1 had been full (failed resource Filter), the pod would have happily landed on wkr-a1 instead — that's the whole point of preferred: a bias, not a requirement.

reco-node-affinity.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: reco
  namespace: jahez-reco
spec:
  replicas: 2
  selector: { matchLabels: { app: reco } }
  template:
    metadata: { labels: { app: reco } }
    spec:
      tolerations:                          # needed to land on gpu-a1 (see §8)
        - key: dedicated
          operator: Equal
          value: ml
          effect: NoSchedule
      affinity:
        nodeAffinity:
          # ---- HARD: must be gpu OR general pool, on linux ----
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:           # expressions within a term = AND
                  - key: jahez.sa/pool
                    operator: In
                    values: ["gpu", "general"]
                  - key: kubernetes.io/os
                    operator: In
                    values: ["linux"]
          # ---- SOFT: strongly prefer an actual GPU node ----
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 80                    # 1..100, higher = stronger pull
              preference:
                matchExpressions:
                  - key: nvidia.com/gpu
                    operator: Exists        # node merely has the label
            - weight: 20
              preference:
                matchExpressions:
                  - key: topology.kubernetes.io/zone
                    operator: In
                    values: ["me-central-1a"]   # mild zone preference
      containers:
        - name: reco
          image: ghcr.io/jahez/reco-ranker:2.7
          resources:
            requests: { cpu: "2", memory: 4Gi }
            limits:   { nvidia.com/gpu: 1 }

The operators

Operatorvalues?Matches when the node...
Inrequiredhas the label and its value is one of values (this is the OR you don't get in nodeSelector)
NotInrequiredhas the label and value is not in values (also excludes nodes where the operator is used as anti-affinity)
Existsomithas the label key at all, any value
DoesNotExistomitdoes not have the label key

Common trap. matchExpressions (key/operator/values) is for node affinity; matchLabels (plain map) is for selectors. Also: an empty nodeSelectorTerms: [] matches nothing (pod never schedules), whereas omitting required entirely matches everything. And NotIn on a label the node lacks does not match — use DoesNotExist if you want "label absent" to qualify.

07

Pod affinity & anti-affinity — placement by neighbours

Node affinity looks at node labels. Pod affinity looks at which other pods are already running in a topology domain. "Put me near pods like X" (affinity, for latency/locality) or "keep me away from pods like X" (anti-affinity, for high availability). The pivot is one field: topologyKey.

topologyKey: what counts as "together"

topologyKey is a node label key that defines the domain over which the rule is evaluated. The scheduler groups nodes by their value of that key and treats each group as one "place". The three you'll use 99% of the time:

topologyKey"Together" meansUse for
kubernetes.io/hostnamesame node"never two replicas on one node" (node-failure HA)
topology.kubernetes.io/zonesame zone"spread replicas across zones" (zone-failure HA)
topology.kubernetes.io/regionsame regionmulti-region spreading

Anti-affinity: spread Redis so no node holds two

Jahez runs a 3-replica Redis cache. If two replicas share a node and that node dies, we lose 2/3 of the cache at once. Required pod anti-affinity with topologyKey: hostname forces one-per-node.

Required anti-affinity: one Redis per node1/4
Step 1 · Start

Three general nodes, no Redis yet

The anti-affinity rule says: don't schedule onto a node (hostname domain) that already runs a pod with app=redis.

Step 2 · redis-0

First replica lands freely

No app=redis pod exists anywhere yet, so the rule is trivially satisfied. redis-0 goes to wkr-a1.

Step 3 · redis-1

wkr-a1 is now forbidden

wkr-a1 already has a app=redis pod, so the hostname domain "wkr-a1" is filtered out for the second replica. redis-1 must pick a different node → wkr-b1.

Step 4 · redis-2

Perfectly spread, one per node

Both wkr-a1 and wkr-b1 are now blocked; redis-2 lands on wkr-c1. A 4th replica would stay Pending — there's no 4th general node, and required anti-affinity has no fallback. (Use preferred if you'd rather double-up than go Pending.)

redis-anti-affinity.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: redis
  namespace: jahez-cache
spec:
  serviceName: redis
  replicas: 3
  selector: { matchLabels: { app: redis } }
  template:
    metadata:
      labels: { app: redis }            # <- the label the rule matches on
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels: { app: redis }   # "pods like me"
              topologyKey: kubernetes.io/hostname   # one per NODE
      containers:
        - name: redis
          image: ghcr.io/jahez/redis:7.2
          ports: [ { containerPort: 6379 } ]

Affinity: co-locate api-gateway with the session cache

The reverse: keep the api-gateway in the same zone as a Redis session replica to cut cross-zone latency. This is preferred (a nudge, not a mandate) so the gateway still schedules if a zone has no Redis.

gateway-pod-affinity.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api-gateway, namespace: jahez-edge }
spec:
  replicas: 6
  selector: { matchLabels: { app: api-gateway } }
  template:
    metadata: { labels: { app: api-gateway } }
    spec:
      affinity:
        podAffinity:                      # ATTRACT toward redis
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 60
              podAffinityTerm:
                labelSelector:
                  matchLabels: { app: redis }
                topologyKey: topology.kubernetes.io/zone   # same ZONE
        podAntiAffinity:                  # REPEL own replicas off same node
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels: { app: api-gateway }
                topologyKey: kubernetes.io/hostname
      containers:
        - name: gateway
          image: ghcr.io/jahez/api-gateway:5.1
          ports: [ { containerPort: 8080 } ]

Field reference

FieldWhereMeaning
podAffinity / podAntiAffinityspec.affinityAttract toward / repel away from matching pods
required...under eachHard (Filter). List of terms, AND'd. No fallback if unsatisfiable.
preferred...under eachSoft (Score). List of {weight, podAffinityTerm}.
labelSelectorin the termWhich pods to look for (supports matchLabels + matchExpressions)
topologyKeyin the term (required field)Node-label key defining the domain. Empty/missing is rejected by the API.
namespaces / namespaceSelectorin the termWhich namespaces to match pods in (default: the pod's own namespace)
Performance & pitfalls. Pod affinity is O(pods × nodes) to evaluate — required pod affinity on large clusters can noticeably slow scheduling; prefer topology spread constraints for pure "spread evenly" goals (they're cheaper and more precise). Also: required anti-affinity caps your replica count at the number of domains (3 nodes → max 3 replicas here). And the very first pod always schedules — anti-affinity only constrains pods relative to ones already placed.

Rule of thumb. Want even spread across zones/nodes? Use topology spread constraints (§10). Want hard "these two services must / must never coexist"? Use pod (anti-)affinity. They compose — many production specs use spread for balance plus a preferred anti-affinity for extra resilience.

08

Taints & tolerations — nodes that push back

Taints invert the direction of control. Instead of a pod choosing nodes, a node repels pods — "don't put anything here unless it explicitly says it can handle me." A pod overrides that repulsion with a matching toleration. This is how you reserve nodes for special workloads (GPU, payments, spot) so random pods never wander in.

Anatomy of a taint

A taint is three parts: key=value:effect. The Jahez payment nodes carry dedicated=payments:NoSchedule. A toleration must match the key (and value, if the operator is Equal) and the effect.

A tainted node accepts only tolerating pods1/3
Step 1 · The taint

pay-a1 is tainted dedicated=payments:NoSchedule

During Filter, any pod without a matching toleration is dropped from this node. The node still runs the payment pods that do tolerate it.

Step 2 · Untolerated pods bounce

cart-svc and orders try & get filtered out

Ordinary stateless pods have no toleration for dedicated=payments, so pay-a1 is removed from their candidate set. They schedule elsewhere on the general pool. The payment node stays clean.

Step 3 · A tolerating pod is admitted

payments-v2 carries the matching toleration

The new payments deployment tolerates dedicated=payments:NoSchedule, so the taint no longer filters this node out — it becomes a feasible candidate and the pod can bind here.

The three effects

EffectPhaseWhat it does to an untolerated pod
NoScheduleFilter (hard)Won't be scheduled here. Already-running pods stay (taint added later doesn't evict them).
PreferNoScheduleScore (soft)Scheduler tries to avoid the node, but will use it if nothing else fits. A "soft" taint.
NoExecuteFilter + evictionWon't be scheduled here and any already-running untolerated pod is evicted. This is the one taint with a during-execution effect.

Toleration operators & tolerationSeconds

payments-tolerations.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: payments, namespace: jahez-pay }
spec:
  replicas: 4
  selector: { matchLabels: { app: payments } }
  template:
    metadata: { labels: { app: payments } }
    spec:
      tolerations:
        # (a) Equal: match key AND value AND effect exactly
        - key: dedicated
          operator: Equal
          value: payments
          effect: NoSchedule

        # (b) Exists: match the key regardless of value
        #     (omit 'value'); here for the node-pressure taints
        - key: node.kubernetes.io/disk-pressure
          operator: Exists
          effect: NoSchedule

        # (c) tolerationSeconds: tolerate a NoExecute taint, but only
        #     for 300s, then evict (used for node-not-ready handling)
        - key: node.kubernetes.io/unreachable
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 300
      # IMPORTANT: tolerating the taint only REMOVES the repulsion.
      # To force payments ONTO pci nodes (not just allow), add affinity:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - { key: jahez.sa/pool, operator: In, values: [pci] }
      containers:
        - name: payments
          image: ghcr.io/jahez/payments-mada:4.2
          ports: [ { containerPort: 8443 } ]
Toleration fieldMeaning
keyTaint key to tolerate. Empty key + operator: Exists = tolerate all taints (use with care).
operatorEqual (default) needs matching value; Exists ignores value.
valueRequired only with Equal. Omit for Exists.
effectWhich effect to tolerate (NoSchedule/PreferNoSchedule/NoExecute). Empty = tolerate all effects for that key.
tolerationSecondsOnly for NoExecute: how long to stay after the taint appears, then evict. Omit = tolerate forever.

Built-in taints Kubernetes adds for you

The node controller automatically taints unhealthy nodes with NoExecute; this is what drives pod eviction when a node goes bad. Every pod gets default 300s tolerations for the not-ready/unreachable ones (that's the "5-minute grace" before pods move off a dead node).

Taints vs affinity — why you usually need both

This is the single most common point of confusion, so it gets its own section. Taints and node affinity feel similar but solve opposite halves of the same problem. For dedicated nodes (GPU, payments) you almost always need both.

Taint (on the node)

Repels pods that don't tolerate it. Keeps strangers out — but does nothing to pull your special pod in. A tolerating pod is merely allowed, not directed.

Affinity (on the pod)

Attracts the pod to matching nodes. Directs your pod onto the right nodes — but does nothing to keep other pods off those nodes.

The classic failure mode

You configure...Result
Only a toleration on the GPU podGPU pod may land on GPU nodes — but the scheduler might also place it on a cheaper general node (scoring picks whatever fits best). Your GPU pod ends up GPU-less.
Only node affinity (pull to GPU pool), no taintGPU pod lands on GPU nodes — but so do random cart/orders pods, because nothing repels them. Your expensive GPUs fill with junk.
Taint + toleration + affinity together✓ Taint keeps everyone else off the GPU nodes; affinity guarantees the GPU pod actually goes there. The intended outcome.

This is exactly why the reco spec (§6) had a toleration for dedicated=ml and a node-affinity preference for nvidia.com/gpu, and why payments (§8) had a toleration for dedicated=payments and required affinity for pool=pci.

Memorise this. Toleration = permission to enter. Affinity = desire to enter. Taint = wall around the node. Dedicated hardware needs the wall (taint) so others stay out, the permission (toleration) so your pod isn't blocked, and the desire (affinity/selector) so your pod actually chooses it.

Topology spread constraints — even distribution

Topology spread is the purpose-built tool for "balance my replicas evenly across zones / nodes". It's cheaper and far more precise than pod anti-affinity for this job, because you state the allowed imbalance directly with one number: maxSkew.

maxSkew: the allowed imbalance

Skew = (pods in the most-populated domain) − (pods in the least-populated eligible domain). maxSkew: 1 means no domain may have more than one extra pod versus the emptiest. The scheduler will only place a new pod in a domain if doing so keeps skew within the limit.

Spread api-gateway evenly across zones, maxSkew=11/3
Step 1 · Current state

5 gateway pods: 2 / 2 / 1 across 1a / 1b / 1c

Most-loaded domain has 2, least has 1, so current skew = 1 — exactly at the limit. Now a 6th pod arrives.

Step 2 · Evaluate domains

Adding to 1a or 1b would push skew to 2

If the new pod went to 1a, that zone becomes 3 while 1c stays 1 → skew 2 > maxSkew. With whenUnsatisfiable: DoNotSchedule those zones are filtered out. Only 1c keeps skew within 1.

Step 3 · Bind to the emptiest zone

Pod lands in 1c → 2 / 2 / 2, skew 0

Perfectly balanced. If every domain would breach maxSkew and the policy is DoNotSchedule, the pod stays Pending; switch to ScheduleAnyway to make it a soft preference that always places.

gateway-topology-spread.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: api-gateway, namespace: jahez-edge }
spec:
  replicas: 6
  selector: { matchLabels: { app: api-gateway } }
  template:
    metadata: { labels: { app: api-gateway } }
    spec:
      topologySpreadConstraints:
        # 1) spread evenly across ZONES, hard
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule        # hard: filter
          labelSelector:
            matchLabels: { app: api-gateway }
          minDomains: 3                            # expect >=3 zones
          # how to treat tainted / affinity-excluded nodes when counting:
          nodeAffinityPolicy: Honor                # respect nodeAffinity/Selector
          nodeTaintsPolicy: Honor                  # ignore nodes we can't tolerate
        # 2) also spread across NODES within a zone, soft
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway        # soft: score only
          labelSelector:
            matchLabels: { app: api-gateway }
      containers:
        - name: gateway
          image: ghcr.io/jahez/api-gateway:5.1
          resources:
            requests: { cpu: 500m, memory: 512Mi }
          ports: [ { containerPort: 8080 } ]

Every field

FieldMeaning
maxSkewMax allowed difference in pod count between the busiest and emptiest eligible domain. Smaller = stricter balance.
topologyKeyNode label defining a domain (zone, hostname, region...). Each distinct value is one domain.
whenUnsatisfiableDoNotSchedule (Filter / hard) or ScheduleAnyway (Score / soft).
labelSelectorWhich pods to count when measuring skew (normally the workload's own label).
minDomains (1.27+)Treat the spread as if at least this many domains exist; forces spreading out even when few domains currently have pods. Only with DoNotSchedule.
matchLabelKeys (1.27+)Extra pod-label keys (e.g. pod-template-hash) to scope counting per rollout, so a new ReplicaSet spreads independently of the old one.
nodeAffinityPolicyHonor (default): only count domains the pod's nodeAffinity/Selector allows. Ignore: count all.
nodeTaintsPolicyHonor: ignore domains the pod can't tolerate. Ignore (default): count them anyway.
Cluster-wide defaults. The scheduler ships with default constraints (spread by hostname and zone, maxSkew 3, ScheduleAnyway) applied to all pods unless you set spec.topologySpreadConstraints yourself. You can tune these in the scheduler's defaultConstraints config. Two constraints on one pod are AND'd — a node must satisfy both.

spread vs anti-affinity. Required anti-affinity is binary (0 or 1 per domain) and caps replicas at the domain count. Topology spread lets you say "balanced to within 1" while still allowing many pods per domain — it scales. Prefer spread for balance; keep anti-affinity for strict "never coexist" rules.

Resource requests & how they drive scheduling

Before any affinity or taint logic, the scheduler asks the most basic question: does this pod even fit? That check is based entirely on requests — not limits, not actual usage. Getting requests right is the highest-leverage scheduling decision you make.

requests = the scheduler's currency; limits = the kubelet's cap

Used by scheduler?Enforced at runtime?
requestsYes — sum of requests on a node must fit its AllocatableGuarantees a floor (cgroup shares / reservation)
limitsNo — ignored for fitYes — CPU is throttled, memory over-limit is OOM-killed
Fig 11.1 — Filter compares the pod's requests against each node's remaining Allocatable. wkr-b1 has only 1 core free, so a 2-core request is filtered out there.

A node's Allocatable is its capacity minus what the kubelet/system reserves. The scheduler tracks the sum of requests of all pods already assigned and subtracts from Allocatable. Real usage is irrelevant for this — a node can be 90% idle but "full" because requests are booked.

orders-resources.yaml
containers:
  - name: orders
    image: ghcr.io/jahez/orders:6.0
    resources:
      requests:                 # <- scheduler books these
        cpu: 500m               #    0.5 core reserved
        memory: 512Mi
      limits:                   # <- kubelet enforces these
        cpu: "2"                #    burst up to 2 cores, then throttle
        memory: 1Gi             #    exceed -> OOMKilled

QoS classes (affect eviction order, not initial placement)

QoS classConditionEvicted under node pressure...
Guaranteedrequests == limits for every resourcelast
Burstablehas requests but requests < limitsmiddle
BestEffortno requests or limits at allfirst
The #1 scheduling bug. Pods with no requests (BestEffort) tell the scheduler they need nothing, so it crams them everywhere — then they fight over real CPU/RAM and get OOM-killed first. Always set requests. Conversely, requests set far above real need silently waste capacity and cause false Pending ("Insufficient cpu") even on empty-looking nodes. Use a LimitRange to set namespace defaults and a ResourceQuota to cap totals.

Extended resources. GPUs are scheduled the same way via a request like nvidia.com/gpu: 1 — the device plugin advertises them as a countable resource, and Filter ensures the node has a free one. That's why the reco pod (§6) requested a GPU as a limit.

PriorityClass & preemption

Priority controls two things: the order pending pods are scheduled in, and whether a pod is important enough to preempt (evict) lower-priority pods to make room for itself when the cluster is full. This is how you guarantee that payments always schedules even if batch jobs have eaten the cluster.

Define priority levels once, reference them everywhere

priorityclasses.yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: jahez-critical }
value: 1000000           # higher = more important
globalDefault: false
preemptionPolicy: PreemptLowerPriority   # may evict lower-pri pods
description: "Payments, checkout, auth - never starve these."
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: jahez-standard }
value: 100000
globalDefault: true      # pods with no priorityClassName get this
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: { name: jahez-batch }
value: 1000              # ETL / reports - first to be preempted
preemptionPolicy: Never  # this class never preempts others
payments-priority.yaml
spec:
  template:
    spec:
      priorityClassName: jahez-critical   # <- attach the class
      containers:
        - name: payments
          image: ghcr.io/jahez/payments-mada:4.2
Preemption: critical payments evicts batch1/3
Step 1 · Cluster full

Low-priority batch pods occupy every slot

Both general nodes are packed with jahez-batch ETL/report pods. There is no free capacity.

Step 2 · Critical pod can't fit

payments (jahez-critical) goes Pending → PostFilter preemption

Normal Filter fails (no room). Because payments out-ranks the batch pods, the scheduler's preemption logic looks for the fewest, lowest-priority victims whose removal would let payments fit. It marks a batch pod on wkr-a1 for eviction.

Step 3 · Evict & bind

Victim is deleted; payments takes the freed slot

The batch pod gets a graceful termination (respecting its terminationGracePeriodSeconds), then payments binds to wkr-a1. The evicted batch pod returns to Pending and reschedules when capacity frees up. A PodDisruptionBudget can limit how aggressively victims are removed.

FieldMeaning
valueInteger priority. Higher wins. Avoid the reserved >1e9 system range.
globalDefaultIf true, pods without a priorityClassName inherit this. Only one class should set it.
preemptionPolicyPreemptLowerPriority (default) may evict others; Never means high-priority for queue order but it will wait rather than evict.
pod.spec.priorityClassNameReferences the class by name; admission sets the numeric spec.priority.
Preemption respects affinity & PDBs but not perfectly. The scheduler won't preempt if doing so still wouldn't let the pod fit (e.g. the pending pod has anti-affinity against the only freeable nodes). Victims honour graceful termination. Set preemptionPolicy: Never on batch tiers so they queue politely, and use PriorityClasses sparingly — three or four tiers is plenty.

Multiple schedulers & schedulerName

A cluster can run more than one scheduler at once. Each pod names the scheduler it wants in spec.schedulerName; if you omit it, the pod is handled by default-scheduler (kube-scheduler). This lets a specialized scheduler own a slice of your workloads — e.g. a bin-packing scheduler for batch jobs — while everything else keeps the stock behaviour.

How a pod picks its scheduler

Each scheduler process is told its own name (via its KubeSchedulerConfiguration profiles[].schedulerName). A scheduler only acts on pods whose schedulerName matches one of its profiles and that are still unbound. If you set a schedulerName that no running scheduler owns, the pod stays Pending forever — nothing claims it.

Routing a batch pod to a custom scheduler1/2
Step 1 · Default path

No schedulerName → default-scheduler owns the pod

A normal pod (no schedulerName) is watched and bound by default-scheduler using all the rules in this guide. The custom scheduler ignores it.

Step 2 · Custom path

schedulerName: jahez-bin-packer → custom scheduler binds it

The batch ETL pod asks for jahez-bin-packer. The default scheduler skips it; our bin-packer claims it and packs it tightly onto spot-c1 to maximise spot utilisation before binding.

batch-etl-custom-scheduler.yaml
apiVersion: batch/v1
kind: Job
metadata: { name: nightly-sales-rollup, namespace: jahez-ops }
spec:
  template:
    spec:
      schedulerName: jahez-bin-packer      # route to our custom scheduler
      tolerations:
        - key: lifecycle                   # allow landing on spot nodes
          operator: Equal
          value: spot
          effect: NoSchedule
      containers:
        - name: rollup
          image: ghcr.io/jahez/sales-rollup:2.3
          resources:
            requests: { cpu: "1", memory: 1Gi }
      restartPolicy: Never

Running a second scheduler

The simplest custom scheduler is just another copy of kube-scheduler with a different profile name and (optionally) different plugin weights — deployed as a Deployment in kube-system with its own RBAC. The profile below makes the default scheduler favour packing pods onto fewer nodes (good for draining spot capacity).

bin-packer-config.yaml
apiVersion: kubescheduler.config.k8s.io/v1
kind: KubeSchedulerConfiguration
profiles:
  - schedulerName: jahez-bin-packer
    pluginConfig:
      - name: NodeResourcesFit
        args:
          scoringStrategy:
            type: MostAllocated        # pack tightly (default is LeastAllocated = spread)
    plugins:
      score:
        enabled:
          - { name: NodeResourcesFit, weight: 5 }

Fields

FieldMeaning
spec.schedulerNameName of the scheduler that should handle this pod. Default: default-scheduler. Must match a running scheduler's profile or the pod hangs Pending.
profiles[].schedulerNameIn KubeSchedulerConfiguration: the name this scheduler answers to. One process can serve multiple profiles.
scoringStrategy.typeLeastAllocated (spread, default) vs MostAllocated (bin-pack) vs RequestedToCapacityRatio.
plugin weightRelative influence of a scoring plugin. Raising NodeResourcesFit makes fit dominate placement.
Scheduler profiles vs separate binaries. Modern kube-scheduler supports multiple profiles in one process — you usually do not need a second binary. Add another entry under profiles: with its own schedulerName and plugin config. Use a fully separate scheduler deployment only when you need custom plugin code.

Jahez use. Keep payments, search and edge on the stock default-scheduler (predictable spreading). Route only cost-sensitive batch/ETL to a MostAllocated profile so spot nodes fill up and scale down cleanly.

DaemonSet & static pod scheduling

Not every pod goes through the normal "find the best node" flow. DaemonSets place exactly one pod on every matching node, and static pods are placed by the kubelet on one specific node with no scheduler involved at all. Both are core to running node-level agents (logging, metrics, CNI) at Jahez.

DaemonSet: one pod per node

A DaemonSet controller creates a pod for each node that matches its nodeSelector/affinity. Since Kubernetes 1.17 these pods go through the normal scheduler (via nodeAffinity the controller injects), so they respect resources and can be preempted — but the intent is still "blanket every node". To cover tainted nodes (payments, gpu, spot), the DaemonSet must carry matching tolerations, otherwise those nodes are skipped.

Rolling node-exporter + fluent-bit onto every node1/2
Step 1 · Fan out

One agent pod is created per node

The DaemonSet controller sees N nodes and creates N pods, each pinned (by injected nodeAffinity) to its own node. No bin-packing — placement is "one each".

Step 2 · Cover tainted nodes

Tolerations let the agent reach payments / gpu / spot

Without tolerations, pay-a1 (NoSchedule taint) would have no node-exporter and you'd lose metrics there. The DaemonSet tolerates everything so observability is truly cluster-wide.

node-exporter-daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata: { name: node-exporter, namespace: jahez-ops }
spec:
  selector: { matchLabels: { app: node-exporter } }
  template:
    metadata: { labels: { app: node-exporter } }
    spec:
      tolerations:
        # run on EVERY node, including all tainted pools
        - operator: Exists                       # tolerate any taint, any effect
      containers:
        - name: node-exporter
          image: ghcr.io/jahez/node-exporter:1.8
          resources:
            requests: { cpu: 50m, memory: 64Mi }
            limits:   { cpu: 100m, memory: 128Mi }
          ports: [ { containerPort: 9100, hostPort: 9100 } ]
      # optional: restrict to a subset of nodes instead of all
      # nodeSelector: { jahez.sa/observability: "true" }
operator: Exists with no key. A single toleration with just operator: Exists (no key, no effect) tolerates every taint — the standard pattern for cluster agents that must run everywhere. Narrow it (per-key tolerations) if some pools should stay agent-free.

Static pods

A static pod is defined by a manifest file in the kubelet's --pod-manifest-path (typically /etc/kubernetes/manifests) on a specific node. The kubelet on that node starts it directly — the API server never schedules it and the scheduler never sees it. The control-plane components (kube-apiserver, etcd, kube-scheduler itself) run as static pods. The API server only gets a read-only mirror pod so you can see it with kubectl, but you cannot delete it via the API.

kubelet static pod (on the node)
# placed at /etc/kubernetes/manifests/edge-cache.yaml on node wkr-a1
# kubelet watches this dir and runs the pod locally — no scheduler, no Deployment
apiVersion: v1
kind: Pod
metadata: { name: edge-cache, namespace: jahez-edge }
spec:
  nodeName: wkr-a1            # implied: it only ever runs on this node's kubelet
  containers:
    - name: cache
      image: ghcr.io/jahez/edge-cache:3.0
      ports: [ { containerPort: 6379 } ]

Best practices

Hard-won rules for keeping scheduling predictable as a cluster grows. Most production incidents trace back to violating one of these.

DoWhy
Always set resource requests on every container.Requests are what the scheduler reserves. No request = the scheduler assumes ~0 and overcommits the node, causing OOM/CPU starvation later.
Use nodeAffinity, not nodeName.nodeName bypasses the scheduler entirely — no resource check, no rescheduling if the node dies.
Pair every isolating taint with required nodeAffinity on the same workload.Toleration only grants permission; without affinity the pod can still drift to general nodes. Both layers = true isolation.
Prefer topology spread over required anti-affinity for balance.Required anti-affinity caps replicas at the domain count and is brittle; spread scales and states the allowed imbalance directly.
Use preferred rules unless a violation is genuinely unacceptable.required rules that can't be met leave pods Pending forever. Start soft, harden only proven invariants (PCI, GPU).
Define explicit PriorityClasses; never rely on default 0 for critical pods.Without priority, a flood of batch pods can starve a customer-facing service. Critical workloads must outrank batch.
Keep DaemonSet agents on operator: Exists tolerations.Otherwise tainted nodes silently lose logging/metrics — you discover the gap during an incident.
Set requests == limits for latency-critical pods (Guaranteed QoS).Guaranteed pods are evicted last under node pressure and get exclusive CPU with the static policy.
Label nodes with stable, well-known keys (topology.kubernetes.io/zone).Built-in keys are set by the cloud provider and survive node replacement; custom ad-hoc labels drift.
Anti-patterns. Hard-coding nodeName in Deployments; required affinity with no fallback pool; mixing many strict anti-affinity rules so nothing schedules; giving everything the same priority; forgetting tolerations on system DaemonSets; setting CPU limits on latency-sensitive services (throttling) — set requests, leave CPU limits off unless you must cap noisy neighbours.

Decision guide — which mechanism, when

Start from the constraint you actually have, not the feature you know. This maps the real requirement to the smallest mechanism that satisfies it.

"This pod needs an SSD / GPU / 64Gi node."nodeSelector or required nodeAffinitynodeName (too rigid), taints (that reserves the node, a different goal)

Layering order. Filtering mechanisms compose as AND: a node must pass nodeSelector AND required nodeAffinity AND tolerate all its taints AND satisfy required pod (anti-)affinity AND keep topology spread within maxSkew. Scoring mechanisms (preferred rules, spread ScheduleAnyway, fit strategy) then rank whatever survived. If a pod is stuck Pending, one of the AND filters is the culprit — see §18.

Troubleshooting placement

A pod is Pending, or landed somewhere wrong. The fastest path is kubectl describe pod — the Events section reports exactly which predicate failed on how many nodes.

triage commands
# 1) why is it Pending? read the scheduler's own explanation:
kubectl describe pod <pod> -n <ns> | sed -n '/Events/,$p'
#   e.g. "0/11 nodes are available: 3 node(s) had untolerated taint,
#          5 Insufficient memory, 3 node(s) didn't match nodeAffinity."

# 2) what labels/taints do nodes actually have?
kubectl get nodes -L jahez.sa/pool,topology.kubernetes.io/zone
kubectl describe node <node> | grep -A3 Taints

# 3) where did pods actually land?
kubectl get pods -A -o wide --field-selector status.phase=Running

# 4) priority / preemption activity
kubectl get events -A --field-selector reason=Preempted

The descheduler. kube-scheduler is one-shot: once a pod is bound it never reconsiders, so a cluster can drift (nodes added after placement stay empty, anti-affinity violated by later events). The descheduler is a separate component that periodically evicts pods matching policies (LowNodeUtilization, RemoveDuplicates, PodLifeTime) so the scheduler can place them better. It's the missing "rebalance" half of scheduling.
