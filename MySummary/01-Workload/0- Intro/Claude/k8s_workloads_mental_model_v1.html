K8s Workloads Mental Model
Kubernetes reference · Workloads

Six questions that organize every workload decision

Every field you set on a workload answers one of six questions. Read them in order and you follow the operating lifecycle: What → How to deploy → How much → Where → How important → What happens when it's interrupted. This guide expands each layer with the primitives, the decision rules, and apply-ready YAML from the jahez-prod cluster.

The lifecycle snake. Each layer narrows the space the next one operates in: the workload type decides which release strategies are even possible; resource requests are the input the scheduler uses for placement; priority decides who loses when placement fails; disruption rules decide how gracefully anything leaves.
How to use this modelWhen reviewing any manifest (yours or a teammate's), walk the six questions top to bottom. A missing answer is usually a production incident waiting for a trigger: no requests → noisy-neighbor; no spread → zone outage takes the service; no PDB → a node upgrade drains every replica at once; no preStop → 502s on every deploy.

PrimitiveWhat it guaranteesIdentityJahez example

1.2Decision rule

  • Does it finish? Yes → Job (once) or CronJob (repeating). No → keep going.
  • Must it run on every node? Yes → DaemonSet.
  • Does each replica own data or need a stable network identity? Yes → StatefulSet. No → Deployment.

2.2Rolling update tuning

Rolling update tuning for an API on the order pathmaxUnavailable: 0 + maxSurge: 25% means capacity never drops during a rollout. Pair it with a real readinessProbe and minReadySeconds — otherwise "ready" just means "process started", and a broken build rolls through the fleet in seconds.

2.6Model review

Model reviewOnly Recreate and RollingUpdate are Kubernetes-native. Blue/Green, Canary and A/B are traffic-routing patterns you assemble from Services, Ingress annotations, a service mesh (Istio VirtualService weights), or a progressive-delivery controller (Argo Rollouts, Flagger) that automates promotion based on metrics. Also: Canary answers "is the new version safe?", A/B answers "is the new version better?" — same plumbing, different question.

3.1Planning & Design

3.1.1Requests, limits & namespace policy

PrimitiveScopeWhat it really does
requestsContainerWhat the scheduler reserves on a node. Also sets CPU weight under contention. Not a usage floor — just a reservation.
limitsContainerCPU over limit → throttled. Memory over limit → OOMKilled.
QoS ClassPod (derived)Computed from requests/limits — you never set it. Decides eviction order under node pressure.
ResourceQuotaNamespaceCaps the total requests/limits/object counts in a namespace.
LimitRangeNamespaceInjects default requests/limits and enforces per-container min/max.

3.1.2QoS classes

QoS classConditionEvictedFits
GuaranteedEvery container: requests = limits for CPU and memoryLastRedis, Elasticsearch, Postgres
BurstableAt least one request or limit set, not GuaranteedMiddle (those over requests first)Most .NET APIs (memory limit, no CPU limit)
BestEffortNo requests or limits at allFirstNothing in jahez-prod — block it with LimitRange

3.1.3.NET sizing note

.NET sizing noteThe .NET GC reads the container memory limit and sizes its heap from it, so the memory limit is load-bearing for ASP.NET Core services. Leave ~25% headroom above steady-state working set. For CPU, many teams set a request but no limit on latency-sensitive APIs to avoid CFS throttling during GC pauses and burst traffic — that keeps them Burstable, which is acceptable as long as the memory request reflects reality.

3.2.4KEDA — Ramadan iftar pre-scale + live order-rate triggerapply-ready · needs KEDA
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: order-api
  namespace: jahez-prod
spec:
  scaleTargetRef:
    name: order-api
  minReplicaCount: 6
  maxReplicaCount: 40
  cooldownPeriod: 300
  triggers:
    # Pre-warm before the lunch peak, every day
    - type: cron
      metadata:
        timezone: Asia/Riyadh
        start: "0 12 * * *"
        end: "0 15 * * *"
        desiredReplicas: "18"
    # Pre-warm ahead of iftar (adjust window during Ramadan)
    - type: cron
      metadata:
        timezone: Asia/Riyadh
        start: "15 17 * * *"
        end: "30 20 * * *"
        desiredReplicas: "28"
    # React to real demand on top of the floor
    - type: prometheus
      metadata:
        serverAddress: http://prometheus.observability.svc:9090
        query: sum(rate(http_requests_total{service="order-api",route="/orders",method="POST"}[1m]))
        threshold: "40"           # target ~40 order POSTs/sec per replica

KEDA takes the highest desired count across triggers, so cron sets a floor before the rush arrives and Prometheus handles anything above it.

3.2.5Don't stack scalers

Don't stack scalers on the same signalKEDA creates and manages an HPA for its target — delete your hand-written HPA for order-api before applying the ScaledObject. Likewise, never run VPA in Auto mode and HPA on CPU/memory against the same Deployment: they fight (VPA raises requests → utilization % drops → HPA scales in).

3.3Model review

Model review"Requests = minimum guaranteed" is close but slightly off. Requests are a scheduling reservation plus a CPU-share weight. A Pod can use less than its request (wasting reserved capacity) and, for memory, can be killed anywhere above its request if the node is under pressure. QoS is an output of requests/limits, not an input — worth drawing it as derived in your mental model.

4.3The attract / repel pairing

The attract / repel pairingTaints repel everything except tolerating Pods; affinity / nodeSelector attract specific Pods. A dedicated node pool needs both: a taint so nothing else lands there, and a nodeSelector so the dedicated workload doesn't land elsewhere. A toleration alone only permits — it doesn't attract.
4.4Elasticsearch on a dedicated, tainted pool with hard anti-affinitysnippet in context
# One-time node setup (or via node-group config):
#   kubectl taint nodes -l jahez.io/nodepool=search dedicated=search:NoSchedule
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: elasticsearch-data
  namespace: jahez-prod
spec:
  serviceName: elasticsearch-data
  replicas: 3
  selector:
    matchLabels:
      app: elasticsearch-data
  template:
    metadata:
      labels:
        app: elasticsearch-data
    spec:
      nodeSelector:
        jahez.io/nodepool: search          # attract
      tolerations:
        - key: dedicated                   # permit
          operator: Equal
          value: search
          effect: NoSchedule
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchLabels:
                  app: elasticsearch-data
              topologyKey: kubernetes.io/hostname
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app: elasticsearch-data
      containers:
        - name: elasticsearch
          image: docker.elastic.co/elasticsearch/elasticsearch:8.15.0
          resources:
            requests: { cpu: "2", memory: "8Gi" }
            limits:   { cpu: "2", memory: "8Gi" }
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 200Gi

4.5Model review

Model reviewAll the …IgnoredDuringExecution rules are evaluated only at scheduling time. If node labels change or the zones drift out of balance after scale-down, nothing moves Pods back. Rebalancing needs a rollout or the Descheduler — a useful addition to the Placement layer.

5.3Iftar scenario

Iftar scenarioAt 18:05 KEDA asks for 28 order-api replicas, but the nodes are full and Cluster Autoscaler needs ~2 minutes for new nodes. Without priority, new order-api Pods sit Pending behind a reindex job. With jahez-critical, the scheduler preempts jahez-batch Pods immediately; the batch work resumes once the new nodes arrive. That two-minute window is exactly when orders peak.

5.4Model review

Model reviewPrioritization isn't only an "insufficient resources" layer. Priority also (1) orders the scheduling queue for every Pod, and (2) is a tiebreaker in node-pressure eviction among Pods exceeding requests. And preemption honours PDBs only on a best-effort basis — it may violate one if there's no other way to fit a higher-priority Pod.

6.2Graceful termination timeline

Endpoint removal and preStop start in parallel. The preStop sleep exists purely to let load balancers stop sending traffic before the app receives SIGTERM — without it, rollouts produce a burst of 502s.

  --delete-emptydir-data \
  --timeout=10m

# 4. After maintenance
kubectl uncordon ip-10-20-3-41.me-central-1.compute.internal

6.5Node pressure eviction order

  • Kubelet watches signals like memory.available, nodefs.available, pid.available against thresholds (default hard: memory.available<100Mi).
  • Ranks Pods by: usage above requests first → then priority → then usage relative to requests. BestEffort Pods (no requests) are therefore always first.
  • Guaranteed Pods within their requests are only evicted when system components need the memory.

6.6Model review

Model review"Eviction" in the list mixes two different mechanisms: API-initiated eviction (drain, autoscaler — PDB-aware) and node-pressure eviction (kubelet — not PDB-aware). Splitting them in your model clarifies which protections apply. Also, Graceful Termination depends on readiness: a Pod should start failing readiness on SIGTERM so it leaves every load balancer, not just the Service.

7.2Why replicas: 6 with three zones

Why replicas: 6 with 3 zonesTwo per zone. Lose a whole AZ and 4 remain (67% capacity) — HPA scales the survivors while Cluster Autoscaler adds nodes in the two healthy zones. With DoNotSchedule zone spread, though, a dead zone can block new Pods once skew exceeds 1; if that bites you during an AZ outage, switch the zone constraint to ScheduleAnyway and rely on the hostname spread.

8Model review: what's solid, what to refine

The six-question framing is strong — it maps cleanly onto how manifests are actually reviewed. These refinements make it more precise.

8In this section3 topics
8.1What's solid! Review 8.2Refinements! Review 8.3Gaps & scope! Review

8.1What's solid

✓ Solid

Question-first structure; the What → Deployment & Release → Resources → Where → Importance → Interruption order mirrors how you author and then operate a service.

8.2Refinements

Refine: native vs. assembled

Mark Blue/Green, Canary, A/B as patterns built on Ingress/mesh/Argo Rollouts — only Recreate and RollingUpdate are built in.

Refine: derived things

QoS class is computed from requests/limits; KEDA drives an HPA rather than replacing it. Draw them as outputs, not knobs.

Refine: the order is conceptual

At run-time, layers 3, 4 and 5 fire in the same scheduling cycle: requests filter nodes, priority orders the queue and triggers preemption.

Refine: split eviction

API-initiated eviction (PDB-aware) vs. node-pressure eviction (not PDB-aware) are different mechanisms with different defenses.

8.3Gaps & scope

Gap: Health

Startup / readiness / liveness probes aren't in any layer, yet they gate rollouts (L2), HPA readiness (L3) and graceful drains (L6). Consider a 7th question: "How does Kubernetes know it's working?"

Gap: Rebalancing

Placement is decided once. Descheduler (or periodic rollouts) is the missing "re-place" step after scale-down or node changes.

Scope note

Networking, configuration and security are separate pillars that wrap workloads — this model deliberately covers only the workload itself.
