01 Stateless vs Stateful Applications ▶

Stateless Applications
Definition — Stateless AppAn application that does not need to store persistent data, configuration, or state between requests or restarts. Every request is processed independently. Any Pod can handle any request. Pods are interchangeable — if one dies, any replacement works fine.
Key characteristics:

① Request independence: Every request is processed independently in any Pod
② No persistent identity: Pod name, IP, hostname don't matter
③ No persistent storage: Pod can use ephemeral storage (emptyDir) or no storage at all
④ Interchangeable: All Pods are identical clones — any can be replaced by any other

Use: Deployments (with ReplicaSets)
Stateful Applications
Definition — Stateful AppAn application that needs to store persistent data, configuration, or state across requests and restarts. Each Pod may have a unique role. Losing a Pod's identity or storage would break the application. Pods need a unique identity at the networking + storage level.
Key characteristics:

① Role-based requests: Specific Pods handle specific operations (primary for writes, replicas for reads)
② Persistent identity: Pod needs a stable name, hostname, and DNS address
③ Persistent storage: Each Pod has its own dedicated volume that survives restarts
④ Not interchangeable: Pod-0 ≠ Pod-1 ≠ Pod-2 — each has a unique role and data

Use: StatefulSets (with Headless Service)
Request Handling — The Critical Difference
Stateless (web server):
Request 1 → any Pod ← doesn't matter which
Request 2 → any Pod ← independent of request 1
Request 3 → any Pod ← all Pods are identical

Stateful (database cluster — PostgreSQL):
WRITE query → MUST go to pod-0 (primary) ← only primary can write
READ query → any pod (pod-0, pod-1, pod-2) ← replicas can read

Stateful (sticky session — ZooKeeper):
Client A → always connects to zk-1 ← session tied to specific node
Client B → always connects to zk-0 ← different node, different session

Stateful apps need to know WHO they are (identity) and WHICH Pod handles WHAT (role). This is impossible with random Pod names from Deployments.
Restart/Reschedule Behavior — What Happens When a Pod Dies?
Stateless Pod dies and is replaced:
web-6d4f-abc12 dies → web-6d4f-xyz99 created
New name ✗ | New IP ✗ | New volume ✗ | New hostname ✗
Doesn't matter! The new Pod is identical. Service load-balances to it. No state to restore.

Stateful Pod dies and is replaced:
mysql-1 dies → mysql-1 recreated
Same name: mysql-1 ✓
Same hostname: mysql-1 ✓
Same DNS: mysql-1.mysql-svc ✓
Same PVC: data-mysql-1 ✓ (all data intact)
New IP: may change (use DNS, not IP!)

If a stateful Pod got a random new name, the cluster would break — other nodes wouldn't recognize it, data would be on the wrong volume, replication would fail.
Why Stateful Pods Need Unique Identity
Definition — Unique IdentityA stateful Pod needs a unique identity at TWO levels:
① Networking level: Stable name + hostname + DNS so other Pods and clients can always find it at the same address, even after restart. Example: the primary must always be reachable at mysql-0.mysql-svc.
② Storage level: Dedicated persistent volume that survives restart. When the Pod restarts, it must reconnect to the SAME volume with all its data. Example: mysql-1 must always mount data-mysql-1.
mysql-0 = unique identity:
├── Network: mysql-0.mysql-svc (always reachable here)
├── Storage: data-mysql-0 (always mounts this volume)
├── Role: PRIMARY (handles writes)
└── Data: all tables, indexes, WAL logs on data-mysql-0

mysql-1 = different unique identity:
├── Network: mysql-1.mysql-svc
├── Storage: data-mysql-1
├── Role: REPLICA (handles reads, replicates from mysql-0)
└── Data: replicated copy on data-mysql-1

If mysql-1 died and came back as mysql-1 with a DIFFERENT volume, it would lose all replicated data and need a full re-sync.
Real-World Examples

02 What Is a StatefulSet?

Definition — StatefulSetA Kubernetes controller that manages stateful applications by providing: stable unique Pod identities (name + hostname + DNS), persistent storage (dedicated PVC per Pod that survives restarts), and ordered operations (Pods created/deleted/updated in predictable sequence). It solves the problem: "How do I run a database cluster in Kubernetes where each node needs to know who it is and keep its data?"
Analogy — Cattle vs Pets

Deployment = cattle ranch. Animals are numbered by random tags (web-6d4f-abc12). One dies? Get another. They're all the same.
StatefulSet = pet household. Each pet has a name (mysql-0, mysql-1), its own bed (PVC), and a fixed address (DNS). If a pet dies, the replacement gets the same name, same bed, same address.

Pod Names — Random vs Ordered
Deployment:
web-6d4f5b-abc12 web-6d4f5b-def34 web-6d4f5b-ghi56
Pod dies → replacement gets NEW random name. No identity persistence.

StatefulSet:
mysql-0 mysql-1 mysql-2
mysql-1 dies → replacement is ALSO named mysql-1. Identity preserved.
Storage — Shared vs Dedicated
Deployment (shared/ephemeral):
Pod A Pod B Pod C → all mount → PVC-shared (or emptyDir — lost on restart)

StatefulSet (dedicated per Pod):
mysql-0 → data-mysql-0 (its OWN 10Gi volume)
mysql-1 → data-mysql-1 (its OWN 10Gi volume)
mysql-2 → data-mysql-2 (its OWN 10Gi volume)

mysql-1 restarts → re-mounts data-mysql-1. All database data intact.
Ordering — Parallel vs Sequential
Deployment (parallel):
Pod A Pod B Pod C ← all created simultaneously

StatefulSet (ordered, each waits for Ready):
mysql-0 created → must be Running + Ready ✓
then → mysql-1 created → must be Ready ✓
then → mysql-2 created → must be Ready ✓

Why? The PRIMARY (mysql-0) must be up before replicas (mysql-1, mysql-2) join. Replicas need to discover the primary and start replicating from it.
Network — Load Balanced VIP vs Per-Pod DNS
Deployment + ClusterIP Service:
nslookup web-svc → 10.96.0.15 (single VIP)
Requests load-balanced randomly to any Pod. Can't target a specific Pod.

StatefulSet + Headless Service:
nslookup mysql-svc → 10.244.1.5, 10.244.2.8, 10.244.3.2 (all Pod IPs!)
nslookup mysql-0.mysql-svc → 10.244.1.5 (specific Pod!)

Apps can connect to a SPECIFIC Pod by name. Writes → mysql-0. Reads → mysql-1 or mysql-2.

04 The 3 Guarantees ▶

① Stable Identity
② Stable Storage
③ Ordered Ops
① Stable, Unique Network Identity
mysql-0 → hostname: mysql-0 → DNS: mysql-0.mysql-svc.default.svc.cluster.local
mysql-1 → hostname: mysql-1 → DNS: mysql-1.mysql-svc.default.svc.cluster.local

After mysql-1 crashes and restarts:
Same name ✓ Same hostname ✓ Same DNS ✓ Same PVC ✓
IP may change — always use DNS, not IP!
② Stable, Persistent Storage
mysql-0 → data-mysql-0 (auto-created, 10Gi)
mysql-1 → data-mysql-1

mysql-1 deleted + recreated:
New mysql-1 → re-mounts data-mysql-1 ← all data intact!

Scale down then up:
PVCs are NEVER auto-deleted. Scale back up → Pods remount old PVCs.
③ Ordered, Graceful Operations
Create: 0 → Ready → 1 → Ready → 2 (sequential forward)
Delete: 2 → gone → 1 → gone → 0 (sequential reverse)
Update: 2 → ready → 1 → ready → 0 (reverse — primary last)

Index 0 = usually the primary/leader. Created first, deleted last, updated last.

05 Stable Network ID ▶

Pod naming
Before/after crash
Format: {statefulset-name}-{ordinal}

mysql-0 (ordinal 0 — primary)
mysql-1 (ordinal 1 — replica)
mysql-2 (ordinal 2 — replica)

Hostname: $(hostname) inside mysql-0 returns mysql-0
Predictable and stable. Apps use ordinal to determine their role.
After crash — identity preserved, IP may change
Before: mysql-1 (IP: 10.244.2.8)
After crash + recreate: mysql-1 (IP: 10.244.2.12)

IP changed: 10.244.2.8 → 10.244.2.12 — this is why you use DNS, NOT IP!

Other Pods connecting via mysql-1.mysql-svc automatically get the new IP. No config change needed.

06 Headless Service ▶

DefinitionA Service with clusterIP: None. DNS returns individual Pod IPs instead of a single VIP. Each Pod gets its own DNS A record. Required for StatefulSets.
Normal vs Headless
YAML
Normal Service:
nslookup web-svc → 10.96.0.15 (one VIP, load balanced)

Headless Service:
nslookup mysql-svc → 10.244.1.5, 10.244.2.8, 10.244.3.2 (all Pod IPs!)
nslookup mysql-0.mysql-svc → 10.244.1.5 (specific Pod!)
apiVersion: v1
kind: Service
metadata:
  name: mysql-svc              # Must match StatefulSet's serviceName
spec:
  clusterIP: None              # ← THIS makes it headless
  selector:
    app: mysql
  ports:
  - port: 3306
    name: mysql
Critical Rules

① Headless Service MUST be created BEFORE StatefulSet. ② Service name must match spec.serviceName in the StatefulSet. ③ Without it, Pods don't get per-Pod DNS records.

SRE Rule

Always use DNS names, never Pod IPs. Pod IPs change on restart. DNS names are stable and auto-point to the new IP.

08 VolumeClaimTemplates ▶

DefinitionAuto-creates a PVC per Pod. Name: {template.name}-{sts}-{ordinal}. PVCs are NOT deleted when Pods die — data survives.
How it works
YAML
StatefulSet: mysql (replicas: 3), volumeClaimTemplate name=data

Auto-creates:
data-mysql-0 (10Gi) → mounted in mysql-0 at /var/lib/mysql
data-mysql-1 (10Gi) → mounted in mysql-1
data-mysql-2 (10Gi) → mounted in mysql-2
volumeClaimTemplates:
- metadata:
    name: data
  spec:
    accessModes: ["ReadWriteOnce"]
    storageClassName: standard
    resources:
      requests:
        storage: 10Gi

09 PVC Lifecycle ▶

Pod dies
Scale down + up
mysql-1 deleted → data-mysql-1 STILL EXISTS
mysql-1 recreated → re-mounts data-mysql-1 → all data intact ✓
Scale 3→1:
mysql-2 del → data-mysql-2 kept
mysql-1 del → data-mysql-1 kept

Scale 1→3:
mysql-1 → remounts data-mysql-1 (old data!)
mysql-2 → remounts data-mysql-2 (old data!)
Cleanup

PVCs are NEVER auto-deleted (by default). Must clean up manually: kubectl delete pvc data-mysql-0 data-mysql-1 data-mysql-2

10 Full StatefulSet YAML

# ═══ Headless Service (create FIRST) ═══
apiVersion: v1
kind: Service
metadata:
  name: mysql-svc
spec:
  clusterIP: None
  selector: { app: mysql }
  ports:
  - { port: 3306, name: mysql }
---
# ═══ StatefulSet ═══
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-svc            # MUST match Service name
  replicas: 3
  podManagementPolicy: OrderedReady  # or Parallel
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0
  selector:
    matchLabels: { app: mysql }
  template:
    metadata:
      labels: { app: mysql }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - { containerPort: 3306, name: mysql }
        env:
        - { name: MYSQL_ROOT_PASSWORD, value: "rootpass" }
        volumeMounts:
        - { name: data, mountPath: /var/lib/mysql }
        resources:
          requests: { cpu: "500m", memory: "512Mi" }
          limits: { cpu: "1", memory: "1Gi" }
        readinessProbe:
          exec:
            command: ["mysqladmin", "ping"]
          periodSeconds: 10
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi

12 Ordered Scaling ▶

Scale Up
Scale Down
Parallel mode
kubectl scale statefulset mysql --replicas=5
mysql-3 + data-mysql-3 → Ready ✓ → then mysql-4 + data-mysql-4
mysql-4 del → mysql-3 del → mysql-2 del (reverse order)
PVCs kept! Scale back up → old data remounted.
podManagementPolicy: Parallel   # All at once (skip ordering)
Use only when startup order doesn't matter (e.g., Cassandra where all nodes are peers).

13 Update Strategies ▶

RollingUpdate
OnDelete
Comparison
RollingUpdate — Reverse order, automatic
Update mysql:8.0 → 8.1:
mysql-2 → mysql-2 (8.1) → Ready ✓
→ mysql-1 → mysql-1 (8.1) → Ready ✓
→ mysql-0 → mysql-0 (8.1) → Ready ✓

Primary (0) updated LAST — replicas updated first to minimize risk.
OnDelete — Manual control
Template updated → Pods NOT replaced → you manually delete each Pod
kubectl delete pod mysql-2 → recreated with new template

Use for critical databases where you verify each node after update.

14 Partitioned Rolling Update ▶

DefinitionOnly Pods with ordinal ≥ partition are updated. Pods below partition keep old template. Enables canary updates.
Canary (partition=2)
Promote (partition=0)
kubectl patch sts mysql -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
kubectl set image sts/mysql mysql=mysql:8.1
mysql-0 (8.0) mysql-1 (8.0) mysql-2 (8.1) ← only this updated
kubectl patch sts mysql -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'
→ mysql-1 updated → mysql-0 updated → All on 8.1 ✓

16 PVC Retention Policy ▶

Definition (v1.27+)persistentVolumeClaimRetentionPolicy controls auto-deletion of PVCs. Default: Retain (keep forever).
spec:
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain     # When STS deleted: Retain or Delete
    whenScaled: Retain      # When scaled down: Retain or Delete

17 Monitoring & Best Practices

Create Headless Service first

Without it, Pods don't get DNS records.

Use DNS names, never Pod IPs

IPs change on restart. DNS is stable.

Set readiness probes

Ordered creation waits for Ready. Without probes, next Pod starts before app is actually serving — can break cluster formation.

Plan PVC cleanup

PVCs never auto-deleted by default. After decommissioning, delete PVCs manually.

Use partition for canary updates

Update one replica first, verify, then update rest. Critical for DB version upgrades.

SRE Wisdom

StatefulSets are pets — treat them carefully. Every operation should be planned and verified. A StatefulSet mistake can mean data loss. Use OnDelete for production databases, partition for canary updates, always backup before upgrades.

18 Command Reference

# ══ CREATE ══
kubectl apply -f headless-svc.yaml   # Service FIRST
kubectl apply -f statefulset.yaml    # StatefulSet SECOND (no imperative create)

# ══ INSPECT ══
kubectl get sts mysql
kubectl get pods -l app=mysql -o wide
kubectl get pvc
kubectl describe sts mysql

# ══ SCALE ══
kubectl scale sts mysql --replicas=5

# ══ UPDATE ══
kubectl set image sts/mysql mysql=mysql:8.1
kubectl rollout status sts/mysql
kubectl rollout undo sts/mysql

# ══ PARTITIONED CANARY ══
kubectl patch sts mysql -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'

# ══ DELETE ══
kubectl delete sts mysql                    # Pods deleted, PVCs kept
kubectl delete sts mysql --cascade=orphan   # Keep Pods too
kubectl delete pvc data-mysql-0 data-mysql-1 data-mysql-2   # Manual cleanup

# ══ DNS TEST ══
kubectl run -it --rm dns-test --image=busybox -- nslookup mysql-0.mysql-svc
