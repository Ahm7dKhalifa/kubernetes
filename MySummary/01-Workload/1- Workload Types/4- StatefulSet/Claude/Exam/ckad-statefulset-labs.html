Create & Basics

LAB 01
Create a Headless Service
Easy

Create a Headless Service named web-svc for Pods with label app=web, port 80. A Headless Service has clusterIP: None.

Verify: kubectl get svc web-svc → CLUSTER-IP shows None
YAML
Imperative + patch
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  clusterIP: None          # ← THIS makes it headless
  selector:
    app: web
  ports:
  - port: 80
    name: http
# No direct imperative for headless. Create normal then it won't work.
# Best: generate YAML, add clusterIP: None
kubectl create service clusterip web-svc --tcp=80:80 --dry-run=client -o yaml > svc.yaml
# Edit: add clusterIP: None under spec, change selector to app: web
kubectl apply -f svc.yaml
Exam trapThere's no --clusterip=None flag in imperative commands. You MUST use YAML for headless services. Generate a skeleton and add clusterIP: None.
LAB 02
Create a StatefulSet with Headless Service
Medium

Create StatefulSet web with 3 replicas, image nginx, using Headless Service web-svc from Lab 01. Each Pod gets a 1Gi PVC at /usr/share/nginx/html.

Verify: kubectl get sts web → READY 3/3. kubectl get pvc → 3 PVCs.
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  serviceName: web-svc             # MUST match Headless Service name
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80
          name: http
        volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi
kubectl apply -f sts.yaml
Key rules① No imperative kubectl create statefulset — YAML only. ② serviceName MUST match the Headless Service. ③ Headless Service must exist BEFORE applying the StatefulSet.

Delete StatefulSet web (keep PVCs), recreate it, and watch Pods created in order: web-0 → web-1 → web-2. Prove each waits for the previous to be Ready.

LAB 06
Verify Stable Hostname After Restart
Medium

Check the hostname of web-1. Delete it. Wait for recreation. Check hostname again — prove it's the same.

# Before: check hostname
kubectl exec web-1 -- hostname
# web-1

# Delete the Pod
kubectl delete pod web-1

# Wait for recreation
kubectl get pods -l app=web -w
# web-1 goes Terminating → new web-1 Created → Running

# After: check hostname again
kubectl exec web-1 -- hostname
# web-1 ← SAME hostname! Identity preserved.
Before: web-1 (hostname: web-1, IP: 10.244.2.8)
After restart: web-1 (hostname: web-1, IP: 10.244.2.12)

Name ✓ Hostname ✓ DNS ✓ PVC ✓ | IP may change — use DNS!
LAB 07
Connect Pod-to-Pod Using DNS
Medium

From inside web-0, connect to web-2 using its stable DNS name (not IP).

# Exec into web-0
kubectl exec -it web-0 -- sh

# Connect to web-2 using DNS (short form)
wget -qO- http://web-2.web-svc:80

# Or full FQDN
wget -qO- http://web-2.web-svc.default.svc.cluster.local:80
Why DNS, not IP?If web-2 restarts, its IP changes. But web-2.web-svc always resolves to the current IP automatically. Apps should ALWAYS use DNS names for StatefulSet Pods.

LAB 09
Prove Data Survives Pod Restart
Medium

Write data to web-1's volume. Delete the Pod. After recreation, verify data is still there.

# Step 1: Write data to web-1's persistent volume
kubectl exec web-1 -- sh -c 'echo "IMPORTANT DATA" > /usr/share/nginx/html/test.txt'

# Step 2: Verify it exists
kubectl exec web-1 -- cat /usr/share/nginx/html/test.txt
# IMPORTANT DATA

# Step 3: Delete the Pod (simulating crash)
kubectl delete pod web-1

# Step 4: Wait for recreation
kubectl get pods -l app=web -w
# web-1 recreated with same name

# Step 5: Verify data SURVIVED the restart!
kubectl exec web-1 -- cat /usr/share/nginx/html/test.txt
# IMPORTANT DATA  ← STILL THERE! PVC preserved the data.
web-1 deleted → data-web-1 KEPT → web-1 recreated → re-mounts data-web-1 → data intact ✓
LAB 10
Scale Down + Up — PVC Preserved
Medium

Write data to web-2. Scale down to 1 (web-2 deleted). Scale back to 3. Verify web-2 remounts its old PVC with data intact.

# Write data to web-2
kubectl exec web-2 -- sh -c 'echo "SCALE TEST" > /usr/share/nginx/html/scale.txt'

# Scale down to 1 (web-2 and web-1 deleted)
kubectl scale sts web --replicas=1

# Verify PVCs still exist!
kubectl get pvc
# data-web-0   Bound
# data-web-1   Bound   ← STILL EXISTS (no Pod using it)
# data-web-2   Bound   ← STILL EXISTS

# Scale back to 3
kubectl scale sts web --replicas=3

# Verify data survived!
kubectl exec web-2 -- cat /usr/share/nginx/html/scale.txt
# SCALE TEST  ← data preserved through scale down + up!
KeyPVCs are NEVER auto-deleted when scaling down. Scale back up → old PVCs remounted with all data. This is critical for databases — you never lose data just because you temporarily scaled down.

Scale web from 3 to 5. Watch: web-3 created first, must be Ready, then web-4.

LAB 12
Scale Down — Observe Reverse Order
Easy

Scale web from 5 to 2. Watch: web-4 deleted first, then web-3, then web-2.

kubectl scale sts web --replicas=2

kubectl get pods -l app=web -w
# web-4 Terminating → gone
# web-3 Terminating → gone
# web-2 Terminating → gone
# Only web-0 and web-1 remain
Scale down is REVERSE order: highest ordinal first.
web-4 → web-3 → web-2
Index 0 (primary) is ALWAYS the last to be deleted. This protects the leader.
LAB 13
Parallel Pod Management
Medium

Create a StatefulSet with podManagementPolicy: Parallel. Observe: all Pods created simultaneously (no ordering).

spec:
  podManagementPolicy: Parallel    # All at once, skip ordering
  replicas: 3
  serviceName: web-svc
kubectl get pods -l app=web -w
# web-0, web-1, web-2 all appear simultaneously!
# No waiting for Ready between them.
When to use ParallelWhen startup order doesn't matter — e.g., Cassandra or other peer-to-peer databases where all nodes are equal. For MySQL/PostgreSQL (primary + replicas), always use OrderedReady (default).

Updates

LAB 14
RollingUpdate — Reverse Order
Medium

Update web StatefulSet image from nginx to nginx:1.25. Watch: Pods updated in reverse order (web-2 → web-1 → web-0).

# Trigger update
kubectl set image sts/web nginx=nginx:1.25

# Watch (another terminal)
kubectl get pods -l app=web -w
# web-2 Terminating → web-2 ContainerCreating → web-2 Running (1.25)
# web-1 Terminating → web-1 Running (1.25)
# web-0 Terminating → web-0 Running (1.25)

# Watch rollout
kubectl rollout status sts/web
Update order is REVERSE: highest ordinal first
web-2 updated → Ready ✓ → web-1 updated → Ready ✓ → web-0 updated → Ready ✓
Primary (web-0) updated LAST — replicas updated first to minimize risk.
LAB 15
OnDelete Update Strategy
Medium

Set StatefulSet web to updateStrategy: OnDelete. Update the image. Observe: Pods are NOT replaced until you manually delete them.

# Set OnDelete strategy
kubectl patch sts web -p '{"spec":{"updateStrategy":{"type":"OnDelete"}}}'

# Update image (template changes, but nothing happens!)
kubectl set image sts/web nginx=nginx:1.26

# Check — all Pods still running old image!
kubectl get pods -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\n"}{end}'
# web-0  nginx:1.25
# web-1  nginx:1.25
# web-2  nginx:1.25

# Manually delete web-2 → recreated with new image
kubectl delete pod web-2
# web-2 now runs nginx:1.26. Others still on 1.25.

# Delete web-1 when ready
kubectl delete pod web-1

# Delete web-0 last (primary)
kubectl delete pod web-0
Use caseCritical databases where you want to verify each node after update before proceeding. You control exactly when each Pod is replaced — full manual control.
LAB 16
Partitioned Rolling Update (Canary)
Hard

Update only web-2 first (canary). Verify it works. Then update all remaining Pods.

# Step 1: Set partition=2 (only ordinal ≥ 2 updated)
kubectl patch sts web -p '{"spec":{"updateStrategy":{"type":"RollingUpdate","rollingUpdate":{"partition":2}}}}'

# Step 2: Update image
kubectl set image sts/web nginx=nginx:1.27

# Step 3: Only web-2 is updated!
kubectl get pods -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\n"}{end}'
# web-0  nginx:1.26  ← old
# web-1  nginx:1.26  ← old
# web-2  nginx:1.27  ← UPDATED (canary)

# Step 4: Verify web-2 works correctly... then promote

# Step 5: Set partition=0 → update ALL remaining
kubectl patch sts web -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'
# web-1 updated → web-0 updated → all on 1.27 ✓
Partition=2: web-0 (old) web-1 (old) web-2 (NEW) ← canary
Partition=0: web-0 (new) web-1 (new) web-2 (new) ← all updated ✓

LAB 18
Delete StatefulSet — Keep Pods (Orphan)
Medium

Delete STS web without deleting its Pods. Verify Pods are still running. Recreate STS to re-adopt them.

# Delete STS, keep Pods
kubectl delete sts web --cascade=orphan

# Pods still running!
kubectl get pods -l app=web
# web-0 Running, web-1 Running, web-2 Running

# Recreate STS with same name + selector → adopts orphan Pods
kubectl apply -f sts.yaml
# Pods adopted, no restart needed
Use caseUpdating the StatefulSet spec (e.g., changing strategy or adding fields) without restarting any Pods. Orphan → edit spec → recreate → adopt.
LAB 19
Clean Up PVCs After Deleting StatefulSet
Easy

Delete StatefulSet web. Verify PVCs still exist. Delete them manually.

# Delete StatefulSet (Pods deleted, PVCs kept!)
kubectl delete sts web

# PVCs still exist
kubectl get pvc
# data-web-0   Bound
# data-web-1   Bound
# data-web-2   Bound

# Manual cleanup
kubectl delete pvc data-web-0 data-web-1 data-web-2

# Also delete the Headless Service if decommissioning
kubectl delete svc web-svc
KeyDeleting a StatefulSet does NOT delete PVCs. This is a safety feature — prevents accidental data loss. You must always clean up PVCs manually (or use persistentVolumeClaimRetentionPolicy).

Troubleshooting

LAB 20
Fix — No Headless Service (Pods Have No DNS)
Medium

StatefulSet web is running but nslookup web-0.web-svc fails. Diagnose and fix.

# Step 1: Check if Headless Service exists
kubectl get svc web-svc
# Either: not found, OR ClusterIP is NOT "None"

# Step 2: If missing — create it
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  clusterIP: None
  selector:
    app: web
  ports:
  - { port: 80, name: http }
# Step 3: If exists but NOT headless (has a ClusterIP)
kubectl delete svc web-svc
# Recreate with clusterIP: None

# Step 4: Verify DNS now works
kubectl run -it --rm test --image=busybox -- nslookup web-0.web-svc
3 common DNS failures① Service doesn't exist. ② Service exists but is NOT headless (has ClusterIP). ③ Service name doesn't match spec.serviceName in the StatefulSet.
LAB 21
Fix — serviceName Mismatch
Medium

StatefulSet has serviceName: mysql-svc but the Service is named db-svc. Pods exist but have no DNS records. Fix it.

# Diagnose
kubectl get sts web -o jsonpath='{.spec.serviceName}'
# mysql-svc

kubectl get svc
# db-svc   ClusterIP   None   ← wrong name!

# Fix: serviceName is IMMUTABLE — must delete and recreate STS
# Option A: Rename the Service
kubectl delete svc db-svc
# Create new Service with name mysql-svc

# Option B: Recreate STS with correct serviceName
kubectl delete sts web --cascade=orphan   # keep Pods
# Edit YAML: serviceName: db-svc (match existing Service)
kubectl apply -f sts-fixed.yaml          # adopts orphan Pods
Key ruleserviceName is immutable. You cannot change it on a running StatefulSet. You must delete (orphan) and recreate. The Service name and serviceName MUST match exactly.
LAB 22
Fix — Pod Stuck Pending (Blocks Ordered Creation)
Hard

StatefulSet has replicas=3 but only web-0 is Running. web-1 is stuck Pending. web-2 is never created. Diagnose and fix.

# Step 1: Check Pod status
kubectl get pods -l app=web
# web-0   1/1   Running
# web-1   0/1   Pending   ← stuck!
# web-2 doesn't exist (blocked by web-1)

# Step 2: Why is web-1 Pending?
kubectl describe pod web-1 | tail -10
# Events: FailedScheduling — insufficient cpu/memory
# OR: no PV available for PVC data-web-1

# Step 3: Fix based on cause
# Cause A: Not enough resources → add node or reduce requests
# Cause B: No PV for PVC → create a PV or fix StorageClass
kubectl get pvc data-web-1
# If Pending → StorageClass can't provision volume

# Cause C: PVC exists but wrong size → delete PVC, let STS recreate
kubectl delete pvc data-web-1
# STS controller will create a new PVC and retry scheduling
Why web-2 doesn't exist:
OrderedReady policy requires web-1 to be Ready before web-2 is created.
web-1 is stuck Pending → web-2 is blocked forever.

One stuck Pod blocks ALL subsequent Pods in ordered creation. Fix the stuck Pod to unblock the chain.

Real-World Scenarios

LAB 23
MySQL Primary/Replica Cluster
Hard

Create a StatefulSet simulating a MySQL cluster: 3 replicas, each with 5Gi storage, Headless Service. Pod-0 is the "primary" (writes), Pod-1 and Pod-2 are "replicas" (reads).

# Headless Service
apiVersion: v1
kind: Service
metadata:
  name: mysql-svc
spec:
  clusterIP: None
  selector: { app: mysql }
  ports:
  - { port: 3306, name: mysql }
---
# StatefulSet
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-svc
  replicas: 3
  selector:
    matchLabels: { app: mysql }
  template:
    metadata:
      labels: { app: mysql }
    spec:
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - { containerPort: 3306 }
        env:
        - { name: MYSQL_ROOT_PASSWORD, value: "rootpass" }
        volumeMounts:
        - { name: data, mountPath: /var/lib/mysql }
        resources:
          requests: { cpu: "250m", memory: "256Mi" }
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 5Gi
# Usage from app Pods:
# Writes → mysql-0.mysql-svc:3306 (primary)
# Reads  → mysql-1.mysql-svc:3306 or mysql-2.mysql-svc:3306 (replicas)

LAB 25
Full Production StatefulSet
Hard

Create a production StatefulSet in namespace production:

  • Headless Service db-svc, port 5432
  • StatefulSet postgres: 3 replicas, image postgres:16
  • Resources: cpu 500m/1, memory 512Mi/1Gi
  • Env: POSTGRES_PASSWORD=secret
  • volumeClaimTemplate: name pgdata, 10Gi at /var/lib/postgresql/data
  • Readiness probe: exec pg_isready
  • RollingUpdate strategy with partition=0
kubectl create namespace production
apiVersion: v1
kind: Service
metadata:
  name: db-svc
  namespace: production
spec:
  clusterIP: None
  selector: { app: postgres }
  ports:
  - { port: 5432, name: postgres }
---
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: postgres
  namespace: production
spec:
  serviceName: db-svc
  replicas: 3
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 0
  selector:
    matchLabels: { app: postgres }
  template:
    metadata:
      labels: { app: postgres }
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: postgres
        image: postgres:16
        ports:
        - { containerPort: 5432 }
        env:
        - { name: POSTGRES_PASSWORD, value: "secret" }
        resources:
          requests: { cpu: "500m", memory: "512Mi" }
          limits: { cpu: "1", memory: "1Gi" }
        readinessProbe:
          exec:
            command: ["pg_isready", "-U", "postgres"]
          periodSeconds: 10
        volumeMounts:
        - { name: pgdata, mountPath: /var/lib/postgresql/data }
  volumeClaimTemplates:
  - metadata:
      name: pgdata
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi
kubectl apply -f production-postgres.yaml

# Verify
kubectl -n production get sts,pods,pvc,svc

# Test DNS
kubectl run -n production -it --rm test --image=busybox -- nslookup postgres-0.db-svc.production.svc.cluster.local
Key Takeaways

1. No imperative create — YAML only. 2. Headless Service (clusterIP: None) MUST exist BEFORE StatefulSet. 3. serviceName must match Service name (immutable). 4. Pod names are ordered: web-0, web-1, web-2. 5. Each Pod gets its own PVC ({template}-{sts}-{ordinal}). 6. PVCs are NEVER auto-deleted. 7. Create order: 0→1→2. Delete/update order: 2→1→0 (primary last). 8. Use partition for canary updates. 9. Use DNS names (pod.svc), not IPs. 10. One stuck Pod blocks all subsequent Pods in ordered mode.
