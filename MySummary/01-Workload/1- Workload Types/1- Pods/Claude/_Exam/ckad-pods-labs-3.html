LAB 01
Create a Pod
Easy⏱ 1 min
Namespace: default

Create a Pod: name web-pod, image nginx:1.25, port 80.

Verify: kubectl get pod web-pod → STATUS: Running, READY: 1/1
Method A: Imperative
Method B: YAML
Method C: Hybrid

Method A — One imperative command (fastest)

kubectl run web-pod --image=nginx:1.25 --port=80
Best for examFastest for simple Pods. One command, done.

Method B — Write YAML from scratch

apiVersion: v1
kind: Pod
metadata:
  name: web-pod
spec:
  containers:
  - name: nginx
    image: nginx:1.25
    ports:
    - containerPort: 80
kubectl apply -f pod.yaml
When to useWhen you need to add fields that imperative commands don't support (probes, volumes, securityContext, etc.).

Method C — Generate YAML then apply (recommended workflow)

# Step 1: Generate YAML skeleton
kubectl run web-pod --image=nginx:1.25 --port=80 --dry-run=client -o yaml > pod.yaml

# Step 2: Edit if needed (add probes, resources, etc.)
vi pod.yaml

# Step 3: Apply
kubectl apply -f pod.yaml
Best for complex tasksGenerate the boilerplate, then add the complex fields. Saves typing and avoids YAML indentation mistakes.

Pod with Labels & Annotations
Easy⏱ 2 min
Namespace: default

Create Pod labeled-pod, image httpd:2.4. Labels: app=frontend, tier=web. Annotation: description=CKAD lab pod.

Verify: kubectl get pod labeled-pod --show-labels and kubectl get pod labeled-pod -o jsonpath='{.metadata.annotations.description}'
Method A: All imperative
Method B: All in YAML
Method C: Create then add

Method A — Imperative with post-creation annotation

# Create Pod with labels in one command
kubectl run labeled-pod --image=httpd:2.4 --labels="app=frontend,tier=web"

# Add annotation (can't do this in kubectl run)
kubectl annotate pod labeled-pod description="CKAD lab pod"
Notekubectl run supports --labels but NOT --annotations. You must add annotations as a separate step or use YAML.

Method B — Full YAML (labels + annotations together)

apiVersion: v1
kind: Pod
metadata:
  name: labeled-pod
  labels:
    app: frontend
    tier: web
  annotations:
    description: CKAD lab pod
spec:
  containers:
  - name: httpd
    image: httpd:2.4
kubectl apply -f labeled-pod.yaml

Method C — Generate YAML, edit, apply

# Generate skeleton with labels
kubectl run labeled-pod --image=httpd:2.4 --labels="app=frontend,tier=web" --dry-run=client -o yaml > lab02.yaml

# Edit: add annotations section under metadata
# annotations:
#   description: CKAD lab pod

kubectl apply -f lab02.yaml

LAB 04
Pod with Command and Args
Medium⏱ 2 min
Namespace: default

Create Pod cmd-pod, image busybox:1.36, that prints "Hello CKAD" then sleeps 3600 seconds. Pod must stay running.

Verify: kubectl logs cmd-pod → "Hello CKAD" and kubectl get pod cmd-pod → Running
Method A: Imperative
Method B: YAML command
Method C: YAML command+args

Method A — Imperative (everything after -- is the command)

kubectl run cmd-pod --image=busybox:1.36 --restart=Never \
  -- /bin/sh -c "echo Hello CKAD && sleep 3600"

Method B — YAML with command only (overrides ENTRYPOINT + CMD)

apiVersion: v1
kind: Pod
metadata:
  name: cmd-pod
spec:
  restartPolicy: Never
  containers:
  - name: cmd
    image: busybox:1.36
    command: ["/bin/sh","-c","echo Hello CKAD && sleep 3600"]

Method C — YAML with separate command + args

apiVersion: v1
kind: Pod
metadata:
  name: cmd-pod
spec:
  restartPolicy: Never
  containers:
  - name: cmd
    image: busybox:1.36
    command: ["/bin/sh", "-c"]      # = Docker ENTRYPOINT
    args: ["echo Hello CKAD && sleep 3600"]  # = Docker CMD
command vs argscommand overrides Docker ENTRYPOINT. args overrides Docker CMD. If you set only args, the image's default ENTRYPOINT is used with your new args.

LAB 08
ConfigMap → Environment Variables
Medium⏱ 5 min
Namespace: default

Create a ConfigMap named app-config with keys DB_HOST=mysql and DB_PORT=3306. Then create Pod config-pod (image nginx) that uses these values as environment variables.

Verify: kubectl exec config-pod -- env | grep DB_ → DB_HOST=mysql, DB_PORT=3306

Step 1 — Create the ConfigMap (3 methods)

Imperative literal
Imperative from file
YAML file

Create ConfigMap — imperative from literals

kubectl create configmap app-config \
  --from-literal=DB_HOST=mysql \
  --from-literal=DB_PORT=3306
FastestOne command. Use for simple key-value pairs.

Create ConfigMap — imperative from file

# Create a properties file first
cat > app.properties <<EOF
DB_HOST=mysql
DB_PORT=3306
EOF

# Create ConfigMap from file (each line becomes a key-value pair)
kubectl create configmap app-config --from-env-file=app.properties
When to useWhen you have many config values in an existing file. --from-env-file splits lines as key=value pairs. --from-file stores the entire file as a single key.

Create ConfigMap — YAML file

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: mysql
  DB_PORT: "3306"
kubectl apply -f configmap.yaml
TrapConfigMap values are always strings. Numeric values like 3306 must be quoted: "3306". Without quotes, YAML parses it as an integer and Kubernetes rejects it.

Step 2 — Create Pod using the ConfigMap (3 methods)

envFrom (all keys)
env valueFrom (pick keys)
All-in-one YAML

Method A — envFrom: load ALL keys from ConfigMap as env vars

apiVersion: v1
kind: Pod
metadata:
  name: config-pod
spec:
  containers:
  - name: app
    image: nginx
    envFrom:
    - configMapRef:
        name: app-config
Best whenYou want ALL keys from the ConfigMap as env vars with their original names. Shortest YAML.

Method B — env.valueFrom: pick individual keys (can rename)

apiVersion: v1
kind: Pod
metadata:
  name: config-pod
spec:
  containers:
  - name: app
    image: nginx
    env:
    - name: DB_HOST            # env var name in container
      valueFrom:
        configMapKeyRef:
          name: app-config     # ConfigMap name
          key: DB_HOST          # key inside ConfigMap
    - name: DATABASE_PORT      # ← can rename the env var!
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: DB_PORT
When to useWhen you need only specific keys, or want to rename them (e.g., ConfigMap key DB_PORT → env var DATABASE_PORT).

Method C — Define ConfigMap + Pod in a single YAML file

# Both resources in one file, separated by ---
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  DB_HOST: mysql
  DB_PORT: "3306"
---
apiVersion: v1
kind: Pod
metadata:
  name: config-pod
spec:
  containers:
  - name: app
    image: nginx
    envFrom:
    - configMapRef:
        name: app-config
kubectl apply -f all-in-one.yaml
When to useWhen both resources are tightly coupled. Use --- to separate multiple resources in one file. kubectl apply -f creates them all in order.
LAB 09
Secret → Mounted as Volume
Medium⏱ 5 min
Namespace: default

Create Secret db-creds with username=admin, password=s3cret. Create Pod secret-pod (image nginx) that mounts the Secret as a read-only volume at /etc/db-credentials.

Verify: kubectl exec secret-pod -- cat /etc/db-credentials/password → s3cret

Step 1 — Create the Secret (3 methods)

Imperative
YAML (base64)
YAML (stringData)
kubectl create secret generic db-creds \
  --from-literal=username=admin \
  --from-literal=password=s3cret
Fastestkubectl handles base64 encoding automatically.

YAML with base64-encoded data

# First encode values:
# echo -n "admin" | base64  → YWRtaW4=
# echo -n "s3cret" | base64 → czNjcmV0

apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
data:
  username: YWRtaW4=        # base64 of "admin"
  password: czNjcmV0       # base64 of "s3cret"
TrapUse echo -n (no newline!) when encoding. echo "admin" | base64 includes a newline character, giving wrong output.

YAML with stringData (plain text, auto-encoded)

apiVersion: v1
kind: Secret
metadata:
  name: db-creds
type: Opaque
stringData:                  # ← plain text, K8s encodes it for you
  username: admin
  password: s3cret
Best for YAMLstringData accepts plain text — no manual base64 encoding needed. Kubernetes converts it to data (base64) when stored.

Step 2 — Pod mounting the Secret as a volume

apiVersion: v1
kind: Pod
metadata:
  name: secret-pod
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: creds
      mountPath: /etc/db-credentials
      readOnly: true
  volumes:
  - name: creds
    secret:
      secretName: db-creds
Volume vs EnvWhen mounted as a volume, each Secret key becomes a file. /etc/db-credentials/username contains "admin", /etc/db-credentials/password contains "s3cret". Volumes auto-update when the Secret changes (env vars don't).
LAB 10
ConfigMap → Mounted as File
Medium⏱ 4 min
Namespace: default

Create ConfigMap nginx-conf containing a custom nginx config. Mount it into Pod custom-nginx at /etc/nginx/conf.d.

Verify: kubectl exec custom-nginx -- cat /etc/nginx/conf.d/default.conf
Method A: From file
Method B: All YAML

Method A — Create ConfigMap from an actual file

# Step 1: Create the config file
cat > default.conf <<'EOF'
server {
    listen 80;
    server_name localhost;
    location / {
        return 200 "Hello from CKAD!\n";
    }
}
EOF

# Step 2: Create ConfigMap from file
kubectl create configmap nginx-conf --from-file=default.conf
Key--from-file=default.conf stores the entire file as a single key. The key name = filename (default.conf). The value = file contents.

Method B — ConfigMap YAML with embedded file content

apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-conf
data:
  default.conf: |             # ← key becomes filename
    server {
        listen 80;
        server_name localhost;
        location / {
            return 200 "Hello from CKAD!\n";
        }
    }
Pipe symbol |The YAML | preserves newlines in multi-line strings. Without it, the config would be on one line.

Pod YAML (same for both methods)

apiVersion: v1
kind: Pod
metadata:
  name: custom-nginx
spec:
  containers:
  - name: nginx
    image: nginx
    volumeMounts:
    - name: config
      mountPath: /etc/nginx/conf.d
  volumes:
  - name: config
    configMap:
      name: nginx-conf

LAB 11
Liveness Probe
Medium⏱ 3 min

Create Pod liveness-pod, image nginx. Add liveness probe: HTTP GET / port 80, period 10s, failure threshold 3.

Verify: kubectl describe pod liveness-pod | grep Liveness
YAML (httpGet)
YAML (exec)
YAML (tcpSocket)

httpGet probe (most common for web apps)

apiVersion: v1
kind: Pod
metadata:
  name: liveness-pod
spec:
  containers:
  - name: nginx
    image: nginx
    ports:
    - containerPort: 80
    livenessProbe:
      httpGet:
        path: /
        port: 80
      periodSeconds: 10
      failureThreshold: 3

exec probe (custom command, exit 0 = healthy)

    livenessProbe:
      exec:
        command:
        - cat
        - /tmp/healthy
      periodSeconds: 10
      failureThreshold: 3
Use whenApp doesn't have HTTP endpoints. The command must return exit 0 for healthy.

tcpSocket probe (connection opens = healthy)

    livenessProbe:
      tcpSocket:
        port: 80
      periodSeconds: 10
      failureThreshold: 3
Use whenNon-HTTP services like databases, message queues. Just checks if the port is open.

LAB 21
Fix Wrong Image
Medium⏱ 3 min

Setup: kubectl run broken-pod --image=ngnix:latest (typo: ngnix → nginx)

Fix the Pod so it runs.

Verify: kubectl get pod broken-pod → Running

Step 1 — Diagnose

kubectl describe pod broken-pod | tail -5
# Events: Failed to pull image "ngnix:latest" → ImagePullBackOff
Method A: Delete + recreate
Method B: Export + edit + replace
Method C: kubectl edit (won't work)

Method A — Delete and recreate (fastest)

kubectl delete pod broken-pod
kubectl run broken-pod --image=nginx:latest
Fastest for examImage is immutable. Fastest fix is delete + create with correct image.

Method B — Export, edit, replace

# Export current spec
kubectl get pod broken-pod -o yaml > fix.yaml

# Edit: change "ngnix" to "nginx"
sed -i 's/ngnix/nginx/g' fix.yaml

# Replace (deletes + creates in one step)
kubectl replace --force -f fix.yaml
kubectl replace --forceDeletes and recreates in one command. Cleaner than separate delete + apply. Also removes runtime fields automatically.

Method C — kubectl edit (DOES NOT WORK for image!)

kubectl edit pod broken-pod
# You CAN open the editor, but saving a changed image FAILS:
# "spec.containers[0].image: Forbidden: pod updates may not change fields"
Exam Trapkubectl edit can change labels, annotations, and some other fields. But image, command, env, ports, and most spec fields are immutable. Don't waste time trying — delete and recreate.

kubectl create configmap missing-config --from-literal=host=mysql.default.svc

kubectl get pod config-err-pod -o yaml > fix24.yaml

#     name: missing-config
#     key: host

kubectl replace --force -f fix24.yaml

Update a Pod's Image
Medium⏱ 3 min

Pod web-pod runs nginx:1.25. Update to nginx:1.26.

Verify: kubectl get pod web-pod -o jsonpath='{.spec.containers[0].image}' → nginx:1.26
Method A: replace --force
Method B: delete + create
Method C: kubectl edit (won't work)

Method A — Export, edit, replace --force (cleanest)

kubectl get pod web-pod -o yaml > update.yaml

# Edit: change nginx:1.25 → nginx:1.26
sed -i 's/nginx:1.25/nginx:1.26/g' update.yaml

# Replace force = delete + create in one step
kubectl replace --force -f update.yaml
Best for examreplace --force handles immutable field changes by deleting and recreating. One command instead of two.

Method B — Manual delete + create

kubectl get pod web-pod -o yaml > update.yaml
# Edit the image
kubectl delete pod web-pod
kubectl apply -f update.yaml

Method C — kubectl edit (FAILS for image change)

kubectl edit pod web-pod
# Change the image in the editor...
# ERROR: "Forbidden: pod updates may not change fields"
This does NOT workImage is immutable on a Pod. kubectl edit will reject the change. You MUST delete + recreate. (Note: this DOES work on Deployments — only naked Pods are immutable.)
LAB 30
Full Production Pod
Hard⏱ 10 min

Create namespace production. Create Pod with:

  • Name: prod-app, namespace: production, image: nginx:1.25, port: 80
  • Labels: app=web, env=production
  • Env: APP_ENV=production
  • CPU: request 100m, limit 200m. Memory: request 64Mi, limit 128Mi
  • Liveness: HTTP / port 80, period 10s
  • Readiness: HTTP / port 80, period 5s
  • Run as user 1000, read-only root filesystem
  • Grace period: 45s, preStop: sleep 5
  • Mount emptyDir at /tmp and /var/cache/nginx
Verify: kubectl -n production get pod prod-app → Running

Step 1 — Create namespace

kubectl create namespace production

Step 2 — Generate skeleton, then add everything

# Generate base YAML
kubectl run prod-app --image=nginx:1.25 --port=80 \
  --labels="app=web,env=production" \
  --env="APP_ENV=production" \
  -n production \
  --dry-run=client -o yaml > prod.yaml

Step 3 — Final YAML (add resources, probes, security, lifecycle, volumes)

apiVersion: v1
kind: Pod
metadata:
  name: prod-app
  namespace: production
  labels:
    app: web
    env: production
spec:
  terminationGracePeriodSeconds: 45
  securityContext:
    runAsUser: 1000
  containers:
  - name: nginx
    image: nginx:1.25
    ports:
    - containerPort: 80
    env:
    - name: APP_ENV
      value: "production"
    resources:
      requests:
        cpu: "100m"
        memory: "64Mi"
      limits:
        cpu: "200m"
        memory: "128Mi"
    livenessProbe:
      httpGet:
        path: /
        port: 80
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /
        port: 80
      periodSeconds: 5
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh","-c","sleep 5"]
    securityContext:
      readOnlyRootFilesystem: true
    volumeMounts:
    - name: tmp
      mountPath: /tmp
    - name: cache
      mountPath: /var/cache/nginx
  volumes:
  - name: tmp
    emptyDir: {}
  - name: cache
    emptyDir: {}
kubectl apply -f prod.yaml
Why emptyDir for /tmp and /var/cache/nginxWith readOnlyRootFilesystem: true, nginx can't write anywhere. It needs writable paths for temp files and cache. Without these emptyDirs, nginx fails to start.
Exam Strategy

Always use the hybrid approach: (1) kubectl run ... --dry-run=client -o yaml > pod.yaml to generate skeleton, (2) edit the YAML to add complex fields, (3) kubectl apply -f pod.yaml. This is faster than writing YAML from scratch and avoids indentation mistakes. Master kubectl explain for field names you forget.
