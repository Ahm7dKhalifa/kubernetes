01 What is a Pod?

A Pod is the smallest deployable unit in Kubernetes — a wrapper around one or more containers that share network, storage, and lifecycle. Kubernetes never runs a bare container; every container lives inside a Pod.

Analogy

A Pod is a shared apartment. Containers are roommates sharing the same address (IP), living space (volumes), and lease (lifecycle).

Shared ResourceWhat It MeansPractical Impact
NetworkSame IP + port spaceContainers talk via localhost
StorageVolumes mountable by all containersSidecar reads app log files
IPCShared IPC namespaceShared memory between processes
PID (opt-in)shareProcessNamespace: trueDebug container can see app PID
LifecycleCo-scheduled on same nodeAll containers start/stop together
HostnameSame hostname = Pod namehostname returns Pod name in all containers

02 Pod Internals — The Pause Container

Every Pod has a hidden pause container created first. It holds the network namespace alive. If your app crashes and restarts, the IP stays the same because the pause container is still running.

08 Creating Pods — YAML File (Declarative)

# pod.yaml — Complete example with all important fields
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  namespace: production
  labels:
    app: web
    env: prod
    version: v2.1
  annotations:
    prometheus.io/scrape: "true"
spec:
  terminationGracePeriodSeconds: 60
  restartPolicy: Always
  containers:
  - name: web
    image: myapp/web:v2.1
    ports:
    - containerPort: 8080
      name: http
    env:
    - name: DB_HOST
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: db-host
    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 15
      failureThreshold: 3
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 5
# Apply the YAML
kubectl apply -f pod.yaml
$ kubectl apply -f pod.yaml pod/my-app created $ kubectl get pod my-app NAME READY STATUS RESTARTS AGE my-app 1/1 Running 0 8s

09 Creating Pods — CLI Commands (Imperative)

# ── Basic: run a pod ──
kubectl run my-app --image=nginx:1.25

# ── With port ──
kubectl run my-app --image=nginx:1.25 --port=80

# ── With environment variables ──
kubectl run my-app --image=myapp:v2 --env="DB_HOST=postgres" --env="LOG_LEVEL=info"

# ── With labels ──
kubectl run my-app --image=nginx --labels="app=web,env=dev"

# ── With resource requests ──
kubectl run my-app --image=nginx --requests="cpu=250m,memory=128Mi"

# ── Dry-run: generate YAML without creating ──
kubectl run my-app --image=nginx:1.25 --port=80 --dry-run=client -o yaml > pod.yaml

# ── One-shot command (run and delete after) ──
kubectl run tmp-debug --image=busybox --rm -it --restart=Never -- /bin/sh

# ── Run a specific command ──
kubectl run batch-job --image=myapp/worker --restart=Never -- python process.py
$ kubectl run my-app --image=nginx:1.25 --port=80 pod/my-app created $ kubectl run my-app --image=nginx --dry-run=client -o yaml apiVersion: v1 kind: Pod metadata: labels: run: my-app name: my-app spec: containers: - image: nginx name: my-app
SRE Principle — Declarative > Imperative

Imperative commands are great for testing and quick debugging. For production, always use YAML files stored in Git. This gives you version history, code review, rollback capability, and reproducibility. kubectl run is for throwaway debugging; kubectl apply -f is for production.

10 Creating Pods — Via Controllers (Production)

In production, you never create Pods directly. You create a controller, and it creates Pods for you:

# Deployment (most common — stateless services)
kubectl create deployment my-app --image=nginx:1.25 --replicas=3

# Generate Deployment YAML
kubectl create deployment my-app --image=nginx --replicas=3 --dry-run=client -o yaml > deploy.yaml

# Job (batch task)
kubectl create job my-job --image=myapp/worker -- python process.py

# CronJob (scheduled)
kubectl create cronjob my-cron --image=myapp/backup --schedule="0 2 * * *" -- /backup.sh

11 Updating Manual (Naked) Pods

If you created a Pod directly (not via controller), your update options are very limited:

What You Want to ChangeCan You?How
Labels, annotationsYeskubectl label pod my-app version=v2
ImageNoMust delete and recreate the Pod
Command, argsNoMust delete and recreate
Environment variablesNoMust delete and recreate
Resource requests/limitsPartialIn-place resize (v1.27+ with InPlacePodVerticalScaling feature gate)
TolerationsAdd onlyCan add new tolerations, cannot remove
activeDeadlineSecondsReduce onlyCan reduce, cannot increase
# The manual update workflow for naked Pods:

# Step 1: Export current Pod to YAML
kubectl get pod my-app -o yaml > pod-backup.yaml

# Step 2: Edit the YAML (change image, env, etc.)
vi pod-backup.yaml

# Step 3: Delete the old Pod
kubectl delete pod my-app

# Step 4: Create the new Pod
kubectl apply -f pod-backup.yaml

# ⚠ DOWNTIME between step 3 and 4!
Why This Is Bad

Updating a naked Pod requires deleting it first, causing downtime. There's no rolling update, no rollback, no version history. This is why naked Pods should never be used in production.

12 Updating Controller-Managed Pods

When Pods are managed by a Deployment, you update the Deployment spec and it handles the rest — zero downtime, automatic rollback capability.

Method 1 — Edit YAML and Apply

# Edit the Deployment YAML file (change image tag)
# image: myapp:v2.0 → image: myapp:v2.1
kubectl apply -f deployment.yaml

Method 2 — Set Image Directly

kubectl set image deployment/my-app web=myapp:v2.1

Method 3 — Edit Live Object

kubectl edit deployment my-app   # Opens in editor

Method 4 — Patch

kubectl patch deployment my-app -p '{"spec":{"template":{"spec":{"containers":[{"name":"web","image":"myapp:v2.1"}]}}}}'
$ kubectl set image deployment/my-app web=myapp:v2.1 deployment.apps/my-app image updated $ kubectl rollout status deployment/my-app Waiting for deployment "my-app" rollout to finish: 1 out of 3 new replicas have been updated... Waiting for deployment "my-app" rollout to finish: 2 out of 3 new replicas have been updated... deployment "my-app" successfully rolled out $ kubectl rollout history deployment/my-app REVISION CHANGE-CAUSE 1 kubectl apply --filename=deployment.yaml 2 kubectl set image deployment/my-app web=myapp:v2.1

Rolling Update Strategies

StrategyHowDowntime?Use When
RollingUpdate DefaultReplace Pods graduallyZero ✓Almost always
RecreateKill all old, then create all newYes ✗Can't run 2 versions at once
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1           # Allow 1 extra Pod during update
      maxUnavailable: 0     # Never go below desired count

Rollback

# Rollback to previous version
kubectl rollout undo deployment/my-app

# Rollback to specific revision
kubectl rollout undo deployment/my-app --to-revision=3

14 Deleting Pods

# Graceful (default 30s grace period)
kubectl delete pod my-app

# Custom grace period
kubectl delete pod my-app --grace-period=60

# Force delete (DANGEROUS — skip graceful shutdown)
kubectl delete pod my-app --grace-period=0 --force

# Delete by label
kubectl delete pods -l app=web

# Delete all in namespace
kubectl delete pods --all -n staging
$ kubectl delete pod my-app pod "my-app" deleted # Waits for graceful shutdown (up to 30s) $ kubectl delete pod my-app --grace-period=0 --force warning: Immediate deletion does not wait for confirmation that the running resource has been terminated. pod "my-app" force deleted

19 Lifecycle Hooks

  postStart:           # Runs AFTER container starts (parallel with entrypoint)

32 Requests vs Limits

resources:
  requests:           # GUARANTEED minimum — used for scheduling
    cpu: "250m"      # 250 millicores = 0.25 CPU
    memory: "128Mi"  # 128 Mebibytes
  limits:             # HARD CEILING — cannot exceed
    cpu: "500m"      # CPU over limit → throttled (slowed)
    memory: "256Mi"  # Memory over limit → OOM KILLED
$ kubectl top pods NAME CPU(cores) MEMORY(bytes) web-abc 45m 98Mi # Healthy — well within limits web-def 490m 241Mi # Warning — near limits! web-ghi 500m 256Mi # At limit — CPU throttled, OOM risk
ResourceWhat Happens at Limit?Symptom
CPUThrottled (slowed down) — NOT killedHigher latency, slower responses
MemoryOOM Killed (exit 137) — container diesContainer restarts, OOMKilled reason

33 Resource Calculation for Multi-Container Pods

# Example Pod with mixed container types:
# Init 1:   CPU 500m, Mem 512Mi
# Init 2:   CPU 200m, Mem 256Mi
# Sidecar:  CPU 100m, Mem 128Mi
# App:      CPU 300m, Mem 256Mi

# Formula:
# MAX(init) = 500m CPU, 512Mi mem   ← largest init
# SUM(app+sidecar) = 400m CPU, 384Mi mem
# Pod effective = MAX(500m, 400m) = 500m CPU
#                 MAX(512Mi, 384Mi) = 512Mi mem

✅ Startup + Liveness + Readiness probes · ✅ Separate /healthz vs /ready endpoints · ✅ Liveness never checks external deps

✅ Controller-managed (never naked Pods) · ✅ ≥ 2 replicas · ✅ Pod anti-affinity · ✅ PDB configured · ✅ Graceful shutdown handles SIGTERM

Final SRE Wisdom

The goal isn't zero failures — it's fast, automated, observable recovery. Design Pods to crash safely (exit codes, graceful shutdown), detect failures quickly (probes, metrics), recover automatically (controllers, restart policies), and provide full visibility (logs, traces, events). A well-instrumented Pod that restarts cleanly in 5 seconds is worth more than a fragile Pod that silently corrupts data when it eventually fails.
