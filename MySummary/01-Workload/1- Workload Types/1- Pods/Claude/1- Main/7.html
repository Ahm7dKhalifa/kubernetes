1Foundations

1.1Introduction

A Pod is the smallest thing Kubernetes runs: one or more containers that share one IP address, the same volumes and one lifecycle, always placed together on one node.

Definition. Pod is a built-in object of the core v1 API (kind Pod), maintained by the Kubernetes project. You describe the containers you want; the kube-scheduler picks a node; the kubelet on that node asks the container runtime (containerd on EKS) to create a sandbox with one network namespace, then starts your containers inside it. Every container in Kubernetes runs inside a Pod — even the ones a Deployment, StatefulSet, DaemonSet or Job creates. Those controllers only write Pods; the Pod is what actually runs.

API groupv1 (core) · kind Pod
Short namepo
ScopeNamespaced — jahez-prod
Lives onExactly one node, from bind to delete
Created byDeployment · StatefulSet · DaemonSet · Job · you
NetworkOne IP per Pod from the VPC CNI (10.20.x.x)
✓ It is
  • The unit of scheduling: all its containers land on the same node or none do
  • A shared network and storage scope: containers talk over localhost and share mounted volumes
  • Disposable: a replaced Pod gets a new name, a new UID and a new IP
  • Self-healing inside one node: the kubelet restarts crashed containers according to restartPolicy
✕ It is not
  • Not a container — it is a wrapper around one or more containers plus a sandbox
  • Not a VM — containers share the node’s kernel; only namespaces and cgroups separate them
  • Not rescheduled when its node dies — a bare Pod is simply gone; only a controller makes a new one
  • Not editable in place for most fields — image, some tolerations and activeDeadlineSeconds can change; everything else needs a new Pod

Definitions

Pod

A group of containers with one IP, shared volumes and one lifecycle, running on one node.
🎯 Why it existsSome processes must live side by side — an API and its log shipper, a proxy and its app. The Pod makes them one unit that is scheduled, started and deleted together.
📄 What it looks like
kind: Pod
metadata:
  name: order-service-pod
spec:
  containers:
  - name: order-service
    image: ghcr.io/jahez/order-service:2.14.0
⚙ What Kubernetes does with itThe scheduler binds it to a node, the kubelet starts its containers and reports status back.
Before
order-service-pod  Pending  <none>
After
order-service-pod  Running  ip-10-20-1-14  10.20.1.37
📍 Where it livesetcd (the object) · one node (the running containers)
⚠ Watch outTwo containers that do not need localhost or shared files belong in two Pods — otherwise they scale and fail together.

Pod sandbox (pause container)

A tiny hidden container (pause) that holds the Pod’s network namespace and IP.
🎯 Why it existsIf the app container crashes and restarts, the Pod must keep its IP and its sidecar must keep working. The sandbox outlives every container restart.
📄 What it looks like
# not in your YAML — containerd creates it
# image: registry.k8s.io/pause:3.10
⚙ What Kubernetes does with itThe kubelet asks containerd for a sandbox first, the CNI gives it an IP, then every container joins its namespaces.
Before
no sandbox · no IP
After
sandbox 7c1e… · eth0 10.20.1.37
📍 Where it livesThe node: crictl pods lists sandboxes
⚠ Watch outA Pod’s IP changes only when the sandbox is recreated (new Pod, or node restart) — never on a container restart.

App container

An entry in spec.containers[] — your program, e.g. the order-service API.
🎯 Why it existsThis is what the Pod is for. Every app container starts after all init containers finish, and they start in parallel.
📄 What it looks like
containers:
- name: order-service
  image: ghcr.io/jahez/order-service:2.14.0
  ports:
  - containerPort: 8080
⚙ What Kubernetes does with itThe kubelet pulls the image, starts the process, runs its probes and restarts it per restartPolicy.
Before
Init:2/3
After
Running · READY 2/2
📍 Where it livesspec.containers
⚠ Watch outIts main process is PID 1 of the container: if PID 1 ignores SIGTERM, shutdown ends in SIGKILL.

Init container

An entry in spec.initContainers[] that runs to completion before the app starts, one at a time, in order.
🎯 Why it existsSetup belongs before the app: wait for orders-db, run EF Core migrations, render a config file.
📄 What it looks like
initContainers:
- name: wait-for-orders-db
  image: busybox:1.36.1
  command: ["sh", "-c", "until nc -z orders-db-service 5432; do sleep 2; done"]
⚙ What Kubernetes does with itRuns #1 until exit 0, then #2… If one fails, the kubelet retries it (with back-off) and the app never starts.
Before
STATUS Init:0/2
After
STATUS Init:1/2 → PodInitializing
📍 Where it livesspec.initContainers
⚠ Watch outNo liveness/readiness probes on plain init containers — a hung init container blocks the Pod forever.

Native sidecar

An init container with restartPolicy: Always: it starts before the app and keeps running beside it.
🎯 Why it existsHelpers like Fluent Bit or an Envoy proxy must be up before the app and must stop after it. Old-style sidecars in containers[] had no order.
📄 What it looks like
initContainers:
- name: fluent-bit
  image: cr.fluentbit.io/fluent/fluent-bit:3.2.4
  restartPolicy: Always
⚙ What Kubernetes does with itStarted in order with init containers, but the kubelet moves on as soon as it is started (or its startupProbe passes). Stopped last on shutdown.
Before
fluent-bit in containers[] — races the app
After
fluent-bit up first · stops last
📍 Where it livesspec.initContainers (stable since 1.33)
⚠ Watch outIts resources add to every later init container and to the app phase — see 6.3.

Ephemeral container

A temporary debug container added to a running Pod with kubectl debug.
🎯 Why it existsProduction images are distroless (.NET chiseled): no shell, no curl. You need tools without restarting the Pod that shows the bug.
📄 What it looks like
ephemeralContainers:
- name: debugger-x7k2
  image: nicolaka/netshoot:v0.13
  targetContainerName: order-service
⚙ What Kubernetes does with itThe API server adds it through the ephemeralcontainers subresource; the kubelet starts it in the same sandbox.
Before
no shell in order-service
After
shell in netshoot, sees order-service processes
📍 Where it livesspec.ephemeralContainers (never in your YAML)
⚠ Watch outCannot be removed or restarted — it stays in the Pod spec until the Pod is deleted.

kubelet

The node agent that turns Pod objects bound to its node into running containers.
🎯 Why it existsSomeone on each node must start containers, run probes, mount volumes and report status. That is the kubelet.
📄 What it looks like

evictionHard:
  memory.available: "100Mi"
maxPods: 58
⚙ What Kubernetes does with itWatches Pods with spec.nodeName = its node, calls containerd through CRI, writes status.

After

⚠ Watch outIf the kubelet stops reporting, the node becomes NotReady and its Pods show Unknown later.

Owner controller

The object that created the Pod and replaces it — usually a ReplicaSet owned by a Deployment.
🎯 Why it existsPods are disposable; something must keep N of them alive and replace lost ones on other nodes.
📄 What it looks like

  ownerReferences:
  - kind: ReplicaSet
    name: order-service-deployment-7d9f8c6b5
    controller: true

After

Phase and conditions

status.phase is the coarse stage (Pending, Running, Succeeded, Failed, Unknown); conditions are the yes/no checkpoints.
🎯 Why it existsYou need to know at a glance where a Pod is, and exactly which gate it is stuck at.
📄 What it looks like

  phase: Running
  conditions:
  - type: Ready
    status: "True"
⚙ What Kubernetes does with itThe kubelet and scheduler set them; Services use the Ready condition.

After

Probe

A health check the kubelet runs against a container: startup, liveness or readiness.
🎯 Why it existsA running process is not a healthy one. Probes let Kubernetes restart hung apps and keep traffic away from apps that cannot serve.
📄 What it looks like
readinessProbe:
  httpGet:
    path: /healthz/ready
    port: 8080
  periodSeconds: 5
⚙ What Kubernetes does with itStartup gates the other two; liveness failure restarts the container; readiness failure removes the Pod from EndpointSlices.
Before
Running · READY 0/1
After
Running · READY 1/1 · in EndpointSlice
📍 Where it livescontainers[].startupProbe / livenessProbe / readinessProbe
⚠ Watch outNever check orders-db in liveness: one DB blip would restart every Pod at once.

QoS class

A label Kubernetes derives from requests and limits: Guaranteed, Burstable or BestEffort.
🎯 Why it existsWhen a node runs out of memory something must die first; the QoS class sets the kernel OOM score.
📄 What it looks like
resources:
  requests: {cpu: 250m, memory: 384Mi}
  limits: {memory: 512Mi}
# → Burstable
⚙ What Kubernetes does with itWritten to status.qosClass at creation; immutable.
Before
no resources → BestEffort
After
requests set → Burstable
📍 Where it livesstatus.qosClass
⚠ Watch outBestEffort Pods are killed first under memory pressure — every Jahez container sets requests.

PodDisruptionBudget

A separate object (policy/v1) that says how many Pods of an app may be down at once during voluntary disruptions.
🎯 Why it existsNode drains and Karpenter consolidation evict Pods. Without a limit, all order-service Pods on a node could go at once.
📄 What it looks like
kind: PodDisruptionBudget
spec:
  maxUnavailable: 1
  selector:
    matchLabels: {app: order-service}
⚙ What Kubernetes does with itThe Eviction API refuses an eviction that would break the budget (HTTP 429); kubectl drain retries.
Before
drain evicts 3 Pods at once
After
drain evicts 1, waits for a replacement
📍 Where it livesIts own object in jahez-prod
⚠ Watch outIt does not protect against node crashes or kubectl delete pod.

1.3Solution

Kubernetes wraps the API and its helpers in one Pod: they share a sandbox, the scheduler places it by declared needs, the kubelet keeps it healthy, and readiness and budgets keep traffic safe.

The solution in numbered steps

  1. Group what must live together. order-service and Fluent Bit go into one Pod: one sandbox, one IP, shared emptyDir volume for logs.
  2. Declare, don’t run. You write the Pod (inside a Deployment) as YAML; kubectl apply stores it; controllers create the Pods.
  3. Place by declared needs. resources.requests tell the scheduler how much room a Pod needs; the scheduler reserves it on a node and spreads copies across zones.
  4. Order and restart automatically. Init containers run first in order, the native sidecar starts before the app, and the kubelet restarts crashed containers.
  5. Gate traffic on health. Probes decide: startup protects warm-up, liveness restarts a hung process, readiness adds or removes the Pod from the Service’s EndpointSlice.
  6. Bound every app. Memory limits keep a leak inside its own cgroup; QoS decides who dies first under pressure.
  7. Stop gracefully, disrupt carefully. preStop + SIGTERM + grace period drain requests; a PodDisruptionBudget limits how many Pods a drain can take at once.

SRE principle — cattle, not pets

Pods are disposable: new name, new IP on replacement. Never store state in a Pod without a PersistentVolume, never depend on a Pod IP — use the Service. If a Pod is sick, replace it, don’t repair it.

When to choose something else

  • Stateless API (order-service) → Deployment.
  • Stable identity or own disk (orders-db) → StatefulSet.
  • One per node (log/metric agents) → DaemonSet.

A Pod answers eight questions you write — identity, permissions, containers, size, health, placement, start/stop, storage — and one Kubernetes writes: where it is and how it is doing.

4.3Native sidecars

A native sidecar is an init container that never finishes: up before the app, restarted if it dies, and shut down after the app.
Step 1 · The logic, read first

A native sidecar is an init container with restartPolicy: Always. It starts in init order, but the kubelet moves on as soon as it is started (or its startupProbe passes); it keeps running, is restarted if it dies, and is stopped after the app containers. Stable since Kubernetes 1.33 (on by default since 1.29).

Problem with old sidecars in containers[]Native sidecar
No start order: the app could start before the proxy/log shipperStarted before every container after it
No stop order: the log shipper could die first and lose the app’s last linesStopped after the app containers
A Job never completes: the sidecar keeps running after the job container exitsIgnored for Pod completion — Job Pods finish
Sidecar restart policy tied to the Pod (Never/OnFailure Jobs)Always restarts, whatever the Pod policy

6.2Limits

Limits are what the kernel enforces: too much CPU and the container is slowed down; too much memory and it is killed.

6.3Effective Pod resources

A Pod’s size for scheduling is the larger of its init phase and its running phase — and native sidecars count in both.

The rule

for each init container i: initᵢ = request(i) + sum(requests of sidecars started before i) init peak = max(initᵢ, sum of all sidecars) app phase = sum(app containers) + sum(all sidecars) Pod size = max(init peak, app phase) + Pod overhead (RuntimeClass, usually 0)
Fix from v6

v6 used max(init) vs sum(app + sidecar). That ignores sidecars that are already running while later init containers execute, so it under-books the init phase.

6.5Node-pressure eviction

When a node runs low on memory or disk, the kubelet evicts Pods — first those using more than they requested, lowest priority first, biggest overuse first.

The ranking (fixes v6)

  1. Is usage above requests? Pods using more than they asked for go first.
  2. Pod priority (priorityClassName) — lower first.
  3. Usage relative to requests — the biggest overuse first.

9.0How a PodDisruptionBudget works

A PodDisruptionBudget says how many Pods of an app may be voluntarily evicted at the same time; the Eviction API refuses anything that would break it.
Step 1 · The logic, read first

A PodDisruptionBudget limits voluntary disruptions — evictions through the Eviction API by kubectl drain, Karpenter consolidation, EKS managed node group upgrades. It cannot stop a node crash, a kernel OOM kill or a plain kubectl delete pod.

Latency (p50/p95/p99), traffic (orders/s), errors (5xx rate), saturation (CPU/memory vs requests and limits) — per Pod and per Service.

11.8Production checklist

Every Jahez Pod passes this list before it reaches jahez-prod.

Health

  • ✅ Startup + liveness + readiness probes
  • ✅ /healthz/live has no dependencies; /healthz/ready checks orders-db/Redis
  • ✅ Thresholds tuned from load tests

Resources

  • ✅ CPU + memory requests on every container incl. sidecars
  • ✅ Memory limits; no CPU limits on latency-sensitive APIs
  • ✅ QoS ≥ Burstable; values from p95 usage

Resilience

  • ✅ Managed by a controller — never a bare Pod
  • ✅ ≥ 2 replicas (6 for order-service) spread across 3 zones
  • ✅ PDB with maxUnavailable: 1 and AlwaysAllow
  • ✅ Exec-form ENTRYPOINT, SIGTERM handled, preStop sleep 5, grace ≥ preStop + shutdown

Observability

  • ✅ JSON logs to stdout (and files only if shipped)
  • ✅ /metrics scraped
  • ✅ Alerts: restarts, OOM, pending, latency
  • ✅ Traces with the Pod name attribute

Security

  • ✅ runAsNonRoot, readOnlyRootFilesystem, drop ALL capabilities, seccomp RuntimeDefault
  • ✅ No privileged, no hostPath
  • ✅ automountServiceAccountToken: false unless needed
  • ✅ Secrets from External Secrets, never in Git; NetworkPolicies in place
Final SRE wisdom

The goal isn’t zero failures — it’s fast, automatic, observable recovery. A Pod that restarts cleanly in five seconds beats a fragile one that silently corrupts data when it finally fails.
