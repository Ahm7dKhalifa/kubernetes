1Foundations

1.1Introduction

A DaemonSet is a Kubernetes workload object that keeps exactly one copy of a Pod on every eligible node — when a node joins it gets the Pod, when a node leaves the Pod goes with it.

Definition. DaemonSet is a built-in object of the apps/v1 API group (stable since Kubernetes 1.9). It is maintained by the Kubernetes project itself: its logic is the DaemonSet controller, one of the control loops inside kube-controller-manager. You write one DaemonSet; the controller compares the list of nodes with the list of Pods it owns and creates or deletes Pods until every eligible node has one Pod. Since Kubernetes 1.12 the controller does not place Pods itself — it pins each Pod to one node with node affinity and lets the normal kube-scheduler bind it, so DaemonSet Pods follow the same rules as every other Pod: resources, taints, priority.

API groupapps/v1 · kind DaemonSet
Short nameds
ScopeNamespaced (its Pods land on cluster-wide nodes)
Pod countNumber of eligible nodes — no replicas
ControllerDaemonSet controller in kube-controller-manager
Typical useLogs · metrics · CNI · CSI · security agents
✓ It is
  • A workload controller like Deployment and StatefulSet, but counted per node, not per replica
  • The standard way to run node-level infrastructure: Fluent Bit, node-exporter, aws-node (VPC CNI), kube-proxy, ebs-csi-node
  • Self-healing: a deleted Pod is recreated on the same node
  • Rolled out node by node with RollingUpdate or by hand with OnDelete
✕ It is not
  • Not a way to scale an app — you never set a Pod count; kubectl scale ds does not work
  • Not a guarantee that the Pod runs — it still needs CPU/memory on the node and admission (PSA) to pass
  • Not the same as a static Pod (a file in /etc/kubernetes/manifests that the kubelet runs without the API server)
  • Not available on EKS Fargate — there is no node you own, so use a sidecar there instead

Definitions

DaemonSet

The object that says “run this Pod template once on every node that matches”.
🎯 Why it existsNode agents must exist on each node, including nodes that appear later. Counting replicas by hand cannot keep up with Karpenter adding and removing nodes.
📄 What it looks like
kind: DaemonSet
spec:
  selector:
    matchLabels: {app: fluent-bit}
  template: {...}   # no replicas
⚙ What Kubernetes does with itThe controller lists nodes, keeps one Pod per eligible node and writes the counts into status.

⚠ Watch outIts selector cannot change after creation. Change it = delete and recreate the DaemonSet.

Eligible node

A node the Pod is allowed to run on: it matches nodeSelector and node affinity, and every NoSchedule/NoExecute taint is tolerated.
🎯 Why it existsNot every agent belongs everywhere: a GPU driver only on GPU nodes, a log agent everywhere except Fargate.
📄 What it looks like

  kubernetes.io/os: linux
tolerations:
- key: workload
  value: elasticsearch
  effect: NoSchedule
⚙ What Kubernetes does with itThe controller re-checks eligibility whenever a node or its labels/taints change, and adds or removes the Pod.

Node-pinned Pod

Each Pod the controller creates carries a required node affinity on metadata.name — it can only ever land on its one node.
🎯 Why it existsSince v1.12 the scheduler (not the controller) binds Pods, so resources, priority and preemption work normally. The pin keeps it on the right node.
📄 What it looks like

  nodeAffinity:
    requiredDuring...:
      nodeSelectorTerms:
      - matchFields:
        - key: metadata.name
          operator: In
          values: [ip-10-20-1-14...]
⚙ What Kubernetes does with itController writes the pin → scheduler checks it fits → kubelet starts it.

After

📍 Where it livesOnly on the live Pod (kubectl get pod -o yaml) — never in your file.
⚠ Watch outIf that node lacks CPU/memory the Pod stays Pending forever — it cannot move to another node. Give agents a high PriorityClass.

Automatic tolerations

The controller adds tolerations to every DaemonSet Pod so agents keep running when a node is sick, cordoned or under pressure.
🎯 Why it existsThe log and metrics agents are exactly what you need while a node is in trouble — evicting them would blind you.
📄 What it looks like
- key: node.kubernetes.io/not-ready
  operator: Exists
  effect: NoExecute
- key: node.kubernetes.io/unschedulable
  operator: Exists
  effect: NoSchedule
⚙ What Kubernetes does with itAdded to the Pod at creation: not-ready, unreachable, disk/memory/pid-pressure, unschedulable (+ network-unavailable with hostNetwork).

⚠ Watch outThey do not cover your own taints (e.g. workload=elasticsearch) or the control-plane taint — add those yourself.

Analogy kept from v1

A Deployment is a delivery fleet: you order 30 riders and dispatch places them wherever demand is. A DaemonSet is the fire alarm in every branch kitchen: one per kitchen, a new branch opens → it gets an alarm, a branch closes → the alarm leaves with it.

1.2Problems or needs

Jahez needs one log agent on every node of a cluster whose node count changes all day — and without a DaemonSet, every way to do that is manual and breaks.

The jahez-prod EKS cluster in me-central-1 runs ~12 nodes off-peak and up to 30 at iftar and dinner rush, because Karpenter adds spot nodes when order-service and dispatch-service scale out. Every node writes container logs to /var/log/containers/. If no agent reads them, a rider-assignment bug at 9 pm leaves no trace in Elasticsearch. 1.3Solution

Write one DaemonSet with the agent’s Pod template and the rule for which nodes qualify; the controller then keeps exactly one Pod on each of those nodes, forever, and rolls changes out node by node.

The solution in 6 steps

StepWhat you doWhat Kubernetes does
① TemplateWrite the Pod template once (Fluent Bit container, hostPath /var/log)Validates it like any Pod template
② EligibilitynodeSelector / node affinity / tolerations say which nodes qualifyRe-checks every node on every change
③ Applykubectl apply -f platform/namespaces/ -f platform/priority-classes/ once, then kubectl apply -k platform/daemonsets/fluent-bit (Argo CD does both)Stores the DaemonSet in etcd
④ One per nodeNothingController creates one node-pinned Pod per eligible node → 12 Pods
⑤ Nodes changeNothingKarpenter adds a node → Pod created; node removed → Pod garbage-collected
⑥ UpdateChange the image tag and applyNew ControllerRevision → RollingUpdate replaces 2 nodes at a time

When to choose something else

  • App replicas spread across nodes (e.g. 3 menu-api Pods, one per zone) → a Deployment with topologySpreadConstraints, not a DaemonSet.
  • A one-off task on every node (clean a disk once) → a DaemonSet whose Pod finishes is wrong: the container exits and restarts forever (restartPolicy must be Always). Use a Job per node or an initContainer + pause pattern.
  • Fargate Pods → sidecar container or the Fargate log router; DaemonSets never run there.
  • Control-plane components before the API exists (kubeadm’s kube-apiserver, etcd) → static Pods.
  • An agent only for some apps → a sidecar inside those Pods is cheaper than an agent on all 30 nodes.

Before v1.12 vs now

3.0How a DaemonSet works

A DaemonSet answers three questions you write — which Pods it owns, which nodes get one, how Pods are replaced on change — and one Kubernetes writes: how far along it is.
Step 1 · The logic, read first

A DaemonSet is a Pod template plus a node filter. It lives as long as you keep it; its Pods live as long as their node stays eligible. The fields group by question — the YAML below uses the same ①–④ headers in the same order.

📄 daemonset-skeleton.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: NAME-daemon-set
  namespace: jahez-platform
spec:
  # ① Which Pods does it own?
  selector:
    matchLabels:
      app: NAME
  template:
    metadata:
      labels:
        app: NAME
    spec:
      # ② Which nodes may run it?
      nodeSelector:
        kubernetes.io/os: linux
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: NAME
        image: busybox:1.36
        command: ["sh", "-c", "sleep infinity"]
  # ③ How are Pods replaced when the template changes?
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
Rules
  • No replicas; count = eligible nodes.
  • Selector immutable; must match template labels.
  • restartPolicy only Always.
  • Preferred node affinity has no effect.
  • Automatic tolerations: not-ready, unreachable, *-pressure, unschedulable (+ network-unavailable w/ hostNetwork). Not control-plane, not your taints.
  • maxUnavailable/maxSurge % round up; both 0 is invalid; maxSurge GA 1.25; no surge with hostPort.
  • ConfigMap change ≠ rollout → rollout restart.
  • No rollout pause; use OnDelete.
  • Drain needs --ignore-daemonsets.
  • containerd socket: /run/containerd/containerd.sock.
  • Agents need PSA privileged namespace.
