Create & Basics

LAB 01
Create a DaemonSet (YAML)
Medium

Create DaemonSet log-agent with image fluentd:v1.16 in namespace default.

Verify: kubectl get ds log-agent → DESIRED = number of nodes, READY = same
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-agent
spec:
  selector:
    matchLabels:
      app: log-agent
  template:
    metadata:
      labels:
        app: log-agent
    spec:
      containers:
      - name: fluentd
        image: fluentd:v1.16
kubectl apply -f ds.yaml
No imperative createThere is NO kubectl create daemonset command. You MUST use YAML. But see Lab 02 for the fast exam trick.
LAB 02
Exam Trick — Create DS from Deployment Skeleton
Easy

Create DaemonSet monitor with image prom/node-exporter using the fastest exam method.

# Step 1: Generate Deployment YAML skeleton
kubectl create deployment monitor --image=prom/node-exporter --dry-run=client -o yaml > ds.yaml

# Step 2: Edit ds.yaml — change 3 things:
# ① kind: Deployment → kind: DaemonSet
# ② Remove spec.replicas line
# ③ Remove spec.strategy section (DaemonSets use updateStrategy)

# Step 3: Apply
kubectl apply -f ds.yaml
30-second methodGenerate → change kind → remove replicas → remove strategy → apply. This is the fastest way to create DaemonSets on the CKAD exam. Memorize it.

LAB 04
Verify One Pod Per Node
Easy

Prove DaemonSet log-agent has exactly one Pod on each worker node. No node has 0 or 2 Pods.

Node Selection

LAB 05
nodeSelector — Run Only on Labeled Nodes
Medium

Label node01 with disk=ssd. Create DaemonSet ssd-monitor that only runs on nodes with disk=ssd.

Verify: Pod only exists on node01, not on other nodes
# Label the node
kubectl label node node01 disk=ssd
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: ssd-monitor
spec:
  selector:
    matchLabels:
      app: ssd-monitor
  template:
    metadata:
      labels:
        app: ssd-monitor
    spec:
      nodeSelector:
        disk: ssd               # Only nodes with this label
      containers:
      - name: monitor
        image: busybox
        command: ["sh","-c","while true; do echo SSD check; sleep 60; done"]
# Verify: Pod only on node01
kubectl get pods -l app=ssd-monitor -o wide
# ssd-monitor-xxx   Running   node01   ← only on labeled node

kubectl get ds ssd-monitor
# DESIRED=1 (only 1 node matches)
LAB 06
Dynamic — Add/Remove Labels
Medium

DaemonSet ssd-monitor uses nodeSelector: disk=ssd. Add the label to another node. Observe: Pod auto-appears. Remove the label. Observe: Pod auto-disappears.

# Add label to node02 → Pod should auto-appear
kubectl label node node02 disk=ssd

kubectl get pods -l app=ssd-monitor -o wide
# ssd-monitor-xxx   Running   node01
# ssd-monitor-yyy   Running   node02   ← new Pod appeared!

kubectl get ds ssd-monitor
# DESIRED=2 (now 2 nodes match)

# Remove label from node02 → Pod should auto-disappear
kubectl label node node02 disk-

kubectl get pods -l app=ssd-monitor -o wide
# ssd-monitor-xxx   Running   node01   ← only 1 Pod again

kubectl get ds ssd-monitor
# DESIRED=1
KeyDaemonSet controller constantly reconciles. Add matching label → Pod created. Remove label → Pod deleted. No manual intervention needed. This is how you dynamically control which nodes run the DaemonSet.
LAB 07
Node Affinity — Advanced Selection
Hard

Create DaemonSet zone-agent that runs ONLY on nodes where label topology.kubernetes.io/zone is either us-east-1a or us-east-1b.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: zone-agent
spec:
  selector:
    matchLabels:
      app: zone-agent
  template:
    metadata:
      labels:
        app: zone-agent
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values:
                - us-east-1a
                - us-east-1b
      containers:
      - name: agent
        image: busybox
        command: ["sh","-c","while true; do echo zone check; sleep 60; done"]
nodeSelector vs nodeAffinitynodeSelector is simple key=value. nodeAffinity supports operators: In, NotIn, Exists, DoesNotExist, Gt, Lt. Use affinity when you need "OR" logic (multiple values) or "NOT" logic.

Tolerations

LAB 08
Tolerate Control-Plane — Run on Master Nodes
Medium

Create DaemonSet all-nodes-agent that runs on ALL nodes including the control-plane.

Verify: kubectl get pods -l app=all-nodes-agent -o wide shows Pods on control-plane too
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: all-nodes-agent
spec:
  selector:
    matchLabels:
      app: all-nodes-agent
  template:
    metadata:
      labels:
        app: all-nodes-agent
    spec:
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        operator: Exists
        effect: NoSchedule
      containers:
      - name: agent
        image: busybox
        command: ["sh","-c","while true; do echo running on $(hostname); sleep 60; done"]
kubectl get pods -l app=all-nodes-agent -o wide
# Pod on controlplane ✓
# Pod on node01 ✓
# Pod on node02 ✓
Why neededControl-plane nodes have taint node-role.kubernetes.io/control-plane:NoSchedule. Without this toleration, DaemonSet Pods skip the control-plane.
LAB 09
Tolerate ALL Taints — Run Everywhere
Medium

Create DaemonSet infra-agent that tolerates ALL taints — runs on every node regardless of any taint.

      tolerations:
      - operator: Exists          # No key/value/effect = match EVERYTHING
This single toleration matches ANY taint on any node:
control-plane (tainted) → Pod ✓
gpu-node (tainted) → Pod ✓
unhealthy (tainted) → Pod ✓
worker (no taint) → Pod ✓
Use forCritical infrastructure like CNI plugins (Calico, Cilium), kube-proxy, and log agents that MUST run on every single node to function.
LAB 10
Custom Taint + Toleration
Medium

Taint node01 with dedicated=gpu:NoSchedule. Create DaemonSet gpu-driver that tolerates this taint AND uses nodeSelector dedicated=gpu.

# Apply taint
kubectl taint node node01 dedicated=gpu:NoSchedule
spec:
  template:
    spec:
      nodeSelector:
        dedicated: gpu
      tolerations:
      - key: dedicated
        operator: Equal
        value: gpu
        effect: NoSchedule
      containers:
      - name: gpu-driver
        image: nvidia/driver:latest
Both needednodeSelector = which nodes to target. toleration = permission to run on tainted nodes. You need BOTH: the selector says "go to GPU nodes" and the toleration says "I'm allowed on tainted GPU nodes."

LAB 12
OnDelete Update Strategy
Medium

Set log-agent to OnDelete strategy. Update the image. Verify: Pods NOT replaced until you manually delete them.

# Change strategy to OnDelete
kubectl patch ds log-agent -p '{"spec":{"updateStrategy":{"type":"OnDelete"}}}'

# Update image
kubectl set image ds/log-agent fluentd=fluentd:v1.18

# Check — ALL Pods still on old image!
kubectl get pods -l app=log-agent -o jsonpath='{range .items[*]}{.spec.nodeName}{"\t"}{.spec.containers[0].image}{"\n"}{end}'
# node01   fluentd:v1.17   ← still old!
# node02   fluentd:v1.17

# Manually delete Pod on node01 → recreated with new image
kubectl delete pod $(kubectl get pods -l app=log-agent --field-selector spec.nodeName=node01 -o name)

# Verify node01 updated
kubectl get pods -l app=log-agent -o wide
# node01 now running fluentd:v1.18 ✓
LAB 13
Rollback a DaemonSet Update
Easy

DaemonSet log-agent was updated to a bad image. Rollback to the previous version.

# View history
kubectl rollout history ds/log-agent

# Rollback to previous
kubectl rollout undo ds/log-agent

# Rollback to specific revision
kubectl rollout undo ds/log-agent --to-revision=1

# Watch
kubectl rollout status ds/log-agent
Same as DeploymentsDaemonSets support rollout status, rollout history, rollout undo, and rollout undo --to-revision=N — identical commands to Deployments.

LAB 15
Node Drain — DaemonSet Pod Stays
Medium

Drain node01 for maintenance. Prove DaemonSet Pods are NOT evicted (they stay on the node).

# Drain the node (must ignore DaemonSets!)
kubectl drain node01 --ignore-daemonsets --delete-emptydir-data

# Check: DaemonSet Pod STILL on node01
kubectl get pods -l app=log-agent -o wide
# log-agent-xxx   Running   node01   ← still there!

# Deployment Pods were evicted to other nodes

# Uncordon after maintenance
kubectl uncordon node01
--ignore-daemonsets is requiredWithout this flag, kubectl drain fails because it can't evict DaemonSet Pods. DaemonSet Pods are infrastructure — they should keep running during maintenance.

Host Access

LAB 16
hostPath — Mount Node's /var/log
Medium

Create DaemonSet log-reader that mounts the node's /var/log directory (read-only) and lists its contents.

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-reader
spec:
  selector:
    matchLabels:
      app: log-reader
  template:
    metadata:
      labels:
        app: log-reader
    spec:
      containers:
      - name: reader
        image: busybox
        command: ["sh","-c","ls /host-logs && sleep 3600"]
        volumeMounts:
        - name: varlog
          mountPath: /host-logs
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
# Verify: see the node's log files from inside the Pod
kubectl exec log-reader-xxx -- ls /host-logs

hostNetwork — Use Node's Network Stack
Hard

Create DaemonSet net-agent that uses the host's network namespace. Verify: Pod sees node's IP, not Pod IP.

      spec:
        hostNetwork: true            # Use node's network
        containers:
        - name: net
          image: busybox
          command: ["sh","-c","hostname -i && sleep 3600"]
# Verify: Pod IP = Node IP (not 10.244.x.x Pod network)
kubectl exec net-agent-xxx -- hostname -i

Troubleshooting

LAB 18
Fix — DS Not Running on a Specific Node
Medium

DaemonSet log-agent runs on node01 and node02 but NOT on node03. Diagnose and fix.

# Step 1: Check if node03 has a taint
kubectl describe node node03 | grep Taints
# Taints: dedicated=special:NoSchedule

# Step 2: Check if DS has matching toleration
kubectl get ds log-agent -o jsonpath='{.spec.template.spec.tolerations}'
# [] — no tolerations!

# Step 3: Fix — add toleration
kubectl patch ds log-agent --type=json -p='[{"op":"add","path":"/spec/template/spec/tolerations","value":[{"key":"dedicated","operator":"Equal","value":"special","effect":"NoSchedule"}]}]'

# OR: could also be a nodeSelector/affinity issue
# Step 1b: Check if DS has nodeSelector that excludes node03
kubectl get ds log-agent -o jsonpath='{.spec.template.spec.nodeSelector}'

# Step 2b: Check node03 labels
kubectl get node node03 --show-labels
3 reasons a DS Pod is missing from a node:
① Node has a taint that DS doesn't tolerate → add toleration
② DS has nodeSelector and node doesn't have matching label → add label
③ Node is cordoned (kubectl cordon) → uncordon it

Medium

Create DaemonSet filebeat that mounts /var/log and /var/lib/docker/containers from each node (read-only).

apiVersion: apps/v1
kind: DaemonSet
metadata:

        - { name: containers, mountPath: /var/lib/docker/containers, readOnly: true }
        resources:
          requests: { cpu: "100m", memory: "128Mi" }
          limits: { cpu: "200m", memory: "256Mi" }
      volumes:
      - name: varlog
        hostPath: { path: /var/log }
      - name: containers
        hostPath: { path: /var/lib/docker/containers }
LAB 22
Monitoring Agent with Priority
Medium

Create DaemonSet node-exporter with priorityClassName: system-node-critical so it's never evicted under resource pressure.

      spec:
        priorityClassName: system-node-critical   # Never evicted
        tolerations:
        - operator: Exists                        # Run everywhere
        containers:
        - name: exporter
          image: prom/node-exporter:v1.7.0
          ports:
          - { containerPort: 9100 }
          resources:
            requests: { cpu: "50m", memory: "64Mi" }
Why priority?If a node runs out of resources, the kubelet evicts low-priority Pods first. system-node-critical (priority 2000001000) ensures your monitoring agent is the LAST thing evicted — you never want to lose visibility into a node that's under resource pressure.

LAB 25
Full Production DaemonSet
Hard

Create production DaemonSet in namespace monitoring:

  • Name: node-monitor, image: prom/node-exporter:v1.7.0, port 9100
  • Runs on ALL nodes including control-plane
  • Priority: system-node-critical
  • Resources: cpu 50m/100m, memory 64Mi/128Mi
  • Mount /proc (read-only) and /sys (read-only) from node
  • RollingUpdate with maxUnavailable=1
kubectl create namespace monitoring
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-monitor
  namespace: monitoring
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
  selector:
    matchLabels:
      app: node-monitor
  template:
    metadata:
      labels:
        app: node-monitor
    spec:
      priorityClassName: system-node-critical
      tolerations:
      - operator: Exists          # Run on ALL nodes (including tainted)
      containers:
      - name: exporter
        image: prom/node-exporter:v1.7.0
        ports:
        - containerPort: 9100
          name: metrics
        resources:
          requests: { cpu: "50m", memory: "64Mi" }
          limits: { cpu: "100m", memory: "128Mi" }
        volumeMounts:
        - { name: proc, mountPath: /host/proc, readOnly: true }
        - { name: sys, mountPath: /host/sys, readOnly: true }
      volumes:
      - name: proc
        hostPath: { path: /proc }
      - name: sys
        hostPath: { path: /sys }
kubectl apply -f node-monitor.yaml

# Verify — Pods on ALL nodes including control-plane
kubectl -n monitoring get pods -l app=node-monitor -o wide
Key Takeaways

1. No imperative create — use the Deployment trick (change kind, remove replicas + strategy). 2. No replicas field — Pod count = number of matching nodes. 3. nodeSelector limits which nodes get Pods. Add/remove labels dynamically controls Pod placement. 4. tolerations allow Pods on tainted nodes. operator: Exists (no key) tolerates ALL taints. 5. Control-plane needs explicit toleration for node-role.kubernetes.io/control-plane:NoSchedule. 6. updateStrategy (not strategy!): RollingUpdate (default, node by node) or OnDelete (manual). 7. kubectl drain requires --ignore-daemonsets. 8. hostPath mounts node's filesystem into Pod. 9. priorityClassName: system-node-critical prevents eviction. 10. Explore kubectl get ds -n kube-system to learn from real system DaemonSets.
