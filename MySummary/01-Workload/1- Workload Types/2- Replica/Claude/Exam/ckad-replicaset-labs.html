Create & Basics

LAB 01
Create a ReplicaSet
Medium

Create a ReplicaSet named web-rs with 3 replicas, image nginx:1.25, label app=web, port 80.

Verify: kubectl get rs web-rs → DESIRED=3 CURRENT=3 READY=3
ImportantThere is NO kubectl create replicaset command. You must write YAML. Tip: generate a Deployment YAML and modify it to kind: ReplicaSet.
Full YAML
Quick trick
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
kubectl apply -f rs.yaml

Exam trick — generate from Deployment, change kind

# Step 1: Generate Deployment YAML
kubectl create deployment web-rs --image=nginx:1.25 --replicas=3 --dry-run=client -o yaml > rs.yaml

# Step 2: Edit rs.yaml:
# - Change kind: Deployment → kind: ReplicaSet
# - Remove spec.strategy section
# - Keep everything else

# Step 3: Apply
kubectl apply -f rs.yaml
Exam speedThis is faster than writing RS YAML from scratch. The Deployment template is almost identical — just change kind and remove the strategy.

LAB 03
Inspect a ReplicaSet — Extract Information
Easy

Given RS web-rs from Lab 01, extract: desired count, current count, ready count, selector, image, and the Pods it owns.

# Overview
kubectl get rs web-rs

# Desired count
kubectl get rs web-rs -o jsonpath='{.spec.replicas}'

# Current count
kubectl get rs web-rs -o jsonpath='{.status.replicas}'

# Ready count
kubectl get rs web-rs -o jsonpath='{.status.readyReplicas}'

# Selector
kubectl get rs web-rs -o jsonpath='{.spec.selector.matchLabels}'

# Image in template
kubectl get rs web-rs -o jsonpath='{.spec.template.spec.containers[0].image}'

# Pods owned by this RS
kubectl get pods -l app=web --show-labels

# Full details + events
kubectl describe rs web-rs

Scaling

LAB 04
Scale Up a ReplicaSet (3 → 5)
Easy

Scale web-rs from 3 to 5 replicas. Use 3 different methods.

Verify: kubectl get rs web-rs → DESIRED=5 READY=5
kubectl scale
Edit YAML + apply
kubectl patch
kubectl scale rs web-rs --replicas=5
WarningThis is in-memory only. Your YAML file still says replicas: 3. Next kubectl apply resets it back to 3!
# Edit rs.yaml: replicas: 3 → replicas: 5
kubectl apply -f rs.yaml
Best practiceUpdates file AND cluster. Git stays in sync. No drift.
kubectl patch rs web-rs -p '{"spec":{"replicas":5}}'
What happens internally:
RS: desired=5, actual=3 → 3 < 5 → create 2 new Pods

Pod 1 ✓ Pod 2 ✓ Pod 3 ✓ Pod 4 creating Pod 5 creating
New Pods use the current template. All 5 running within seconds.
LAB 05
Scale Down a ReplicaSet (5 → 2)
Medium

Scale web-rs from 5 to 2 replicas. Observe which Pods get deleted and why.

Verify: kubectl get pods -l app=web → only 2 Pods running
kubectl scale rs web-rs --replicas=2

# Watch the deletion happen
kubectl get pods -l app=web -w
Scale-down algorithm picks which 3 to delete:
① Pending Pods deleted first
② Lowest deletion-cost annotation next
③ Pods on nodes with most replicas
④ Newest Pods (created most recently)
⑤ Random tie-breaker
ObserveThe newest Pods (Pod 4 and Pod 5 from Lab 04) are deleted first because they're the youngest. Older, proven Pods are kept.
LAB 06
Scale to Zero — Pause Without Deleting RS
Easy

Scale web-rs to 0 replicas. Verify all Pods are gone but RS still exists. Then scale back to 3.

Verify: kubectl get rs web-rs → DESIRED=0 CURRENT=0, then DESIRED=3 READY=3
# Scale to zero — all Pods deleted, RS remains
kubectl scale rs web-rs --replicas=0

kubectl get rs web-rs
# DESIRED=0  CURRENT=0  READY=0

kubectl get pods -l app=web
# No resources found (all gone)

# Scale back — 3 new Pods created instantly
kubectl scale rs web-rs --replicas=3
Use caseTemporary maintenance, cost saving during off-hours, or testing. The RS template is preserved — scale back up anytime.
LAB 07
Conditional Scale (Safety Check)
Medium

Scale web-rs to 5 replicas ONLY IF it currently has exactly 3. If someone already changed it, the command should fail.

# Only scales if current replicas is exactly 3
kubectl scale rs web-rs --replicas=5 --current-replicas=3
Why this mattersPrevents race conditions. If another admin just scaled to 10 and you run a blind scale --replicas=5, you'd accidentally scale DOWN. The --current-replicas flag acts as a safety check.

Updates

LAB 08
Update Image in RS Template — Observe What Happens
Hard

RS web-rs runs nginx:1.25. Change the template image to nginx:1.26. Observe: do existing Pods update?

Verify: kubectl get pods -l app=web -o jsonpath='{range .items[*]}{.spec.containers[0].image}{"\n"}{end}'

Step 1 — Update the template

kubectl edit
kubectl patch
Edit YAML + apply
kubectl edit rs web-rs
# Find image: nginx:1.25 → change to nginx:1.26 → save
kubectl patch rs web-rs --type='json' \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/image","value":"nginx:1.26"}]'
# Edit rs.yaml: image: nginx:1.25 → image: nginx:1.26
kubectl apply -f rs.yaml

Step 2 — Check existing Pods

kubectl get pods -l app=web -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.containers[0].image}{"\n"}{end}'
# web-rs-x7k2j    nginx:1.25   ← STILL OLD!
# web-rs-m9p4r    nginx:1.25   ← STILL OLD!
# web-rs-a3b8n    nginx:1.25   ← STILL OLD!
⚠ KEY INSIGHT: Existing Pods are NOT updated.

RS template: nginx:1.26 ← updated ✓
Pod 1 (nginx:1.25) Pod 2 (nginx:1.25) Pod 3 (nginx:1.25) ← still old ✗

RS only checks count not template content. It sees 3 Pods → desired 3 → do nothing.
Only new Pods (from scale-up or crash replacement) will use nginx:1.26.
Exam trapIf the question says "update the image of a ReplicaSet" — changing the template does NOT update running Pods. You must also delete old Pods (Lab 09) or use a Deployment.
LAB 09
Force All Pods to Use New Image
Hard

After Lab 08, all 3 Pods still run nginx:1.25 but template says nginx:1.26. Force ALL Pods to use the new image.

Verify: All Pods show nginx:1.26
Method A: Delete all (downtime)
Method B: Delete one-by-one
Method C: Use Deployment

Delete all Pods at once — RS recreates with new template

kubectl delete pods -l app=web
Pod 1 DEL Pod 2 DEL Pod 3 DEL ← ALL dead simultaneously! DOWNTIME!

Pod 4 (1.26) creating Pod 5 (1.26) creating Pod 6 (1.26) creating
All new Pods use the updated template ✓ but there was downtime ✗
Downtime warningAll Pods die at the same time. Zero capacity until new Pods are ready.

Delete Pods one at a time — manual rolling update

# Delete Pod 1 — RS creates replacement with new image
kubectl delete pod web-rs-x7k2j
# Wait until new Pod is Ready
kubectl get pods -l app=web -w

# Delete Pod 2
kubectl delete pod web-rs-m9p4r
# Wait until Ready

# Delete Pod 3
kubectl delete pod web-rs-a3b8n
Manual rolling update:
1 (1.25) 2 (1.25) 3 (1.25) ← delete 1
4 (1.26) 2 (1.25) 3 (1.25) ← delete 2
4 (1.26) 5 (1.26) 3 (1.25) ← delete 3
4 (1.26) 5 (1.26) 6 (1.26) ← all updated! ✓
Reduced downtimeAt least 2 Pods always serving. But it's slow and manual.

The RIGHT way — use a Deployment (zero downtime, automatic)

# If this was a Deployment instead of RS:
kubectl set image deployment/web-deploy nginx=nginx:1.26
# → Deployment creates new RS, does rolling replacement
# → Zero downtime, automatic, with rollback capability
SRE Principle

This is exactly why you should never manage RS directly in production. Deployments automate the entire image update process with zero downtime.

LAB 11
Set Pod Deletion Cost
Medium

RS web-rs has 3 Pods. Make Pod 1 protected (cost=1000) and Pod 3 preferred for deletion (cost=-100). Scale down to 1 and verify Pod 1 survives.

Verify: After scale-down to 1, only the protected Pod remains
Imperative
YAML annotation
# Get Pod names
kubectl get pods -l app=web
# web-rs-abc12   web-rs-def34   web-rs-ghi56

# Protect Pod 1 (high cost = deleted LAST)
kubectl annotate pod web-rs-abc12 controller.kubernetes.io/pod-deletion-cost="1000"

# Mark Pod 3 for preferred deletion (low cost = deleted FIRST)
kubectl annotate pod web-rs-ghi56 controller.kubernetes.io/pod-deletion-cost="-100"

# Scale down to 1
kubectl scale rs web-rs --replicas=1

# Check who survived
kubectl get pods -l app=web
# web-rs-abc12 — the protected Pod! ✓

YAML — Pod with deletion cost in annotations

apiVersion: v1
kind: Pod
metadata:
  name: protected-pod
  labels:
    app: web
  annotations:
    controller.kubernetes.io/pod-deletion-cost: "1000"
spec:
  containers:
  - name: nginx
    image: nginx:1.25

YAML — RS template with deletion cost built-in

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
      annotations:
        controller.kubernetes.io/pod-deletion-cost: "500"
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
Scale-down order (5→1):
cost=-100: DELETE 1st → cost=0: DELETE 2nd → cost=0: DELETE 3rd → cost=0: DELETE 4th → cost=1000: SURVIVES ✓
LAB 12
Delete RS but Keep Pods Running (Orphan)
Medium

Delete web-rs but keep all its Pods running. Verify Pods are alive but have no controller.

Verify: kubectl get rs web-rs → not found. kubectl get pods -l app=web → still running
# Delete RS with --cascade=orphan
kubectl delete rs web-rs --cascade=orphan

# RS is gone
kubectl get rs web-rs
# Error: replicasets.apps "web-rs" not found

# Pods still alive!
kubectl get pods -l app=web
# web-rs-abc12   Running
# web-rs-def34   Running
# web-rs-ghi56   Running

# But they have NO owner now
kubectl get pod web-rs-abc12 -o jsonpath='{.metadata.ownerReferences}'
# empty — these are orphan Pods
RS deleted → Pods become orphans
Pod 1 (alive, unmanaged) Pod 2 (alive, unmanaged) Pod 3 (alive, unmanaged)
⚠ If any Pod dies now, nobody recreates it!
LAB 13
Isolate a Pod from ReplicaSet for Debugging
Medium

RS web-rs has 3 Pods. Isolate one Pod for debugging without affecting service capacity (RS should create a replacement).

Verify: RS shows 3/3 + 1 isolated Pod exists outside RS
# Get Pod names
kubectl get pods -l app=web
# web-rs-abc12   web-rs-def34   web-rs-ghi56

# Remove the matching label from one Pod (trailing '-' removes it)
kubectl label pod web-rs-def34 app-

# RS detects only 2 matching Pods → creates a replacement
kubectl get rs web-rs
# DESIRED=3  CURRENT=3  READY=3  ← back to full capacity

# The isolated Pod is still running, outside RS control
kubectl get pods --show-labels | grep web-rs-def34
# web-rs-def34   Running   (no app label)

# Debug it freely
kubectl exec -it web-rs-def34 -- sh
kubectl logs web-rs-def34

# Clean up when done
kubectl delete pod web-rs-def34
Before:
RS: 3/3 → Pod 1 (app=web) Pod 2 (app=web) Pod 3 (app=web)

After removing label from Pod 2:
RS: 3/3 → Pod 1 Pod 3 Pod 4 (new!)
+ Pod 2 (isolated, alive, debug freely)

LAB 15
Extra Pod Created After RS — Gets Killed
Medium

RS web-rs has 3/3 Pods. Create an extra Pod with matching label app=web. Observe: does RS kill it?

# RS has 3 Pods, all healthy
kubectl get rs web-rs
# DESIRED=3  CURRENT=3  READY=3

# Create extra Pod with matching label
kubectl run extra-pod --image=nginx --labels="app=web"

# RS detects 4 Pods but wants 3 → deletes 1
kubectl get pods -l app=web -w
# You'll see one Pod go to Terminating within seconds

kubectl get rs web-rs
# DESIRED=3  CURRENT=3  READY=3  ← back to 3
RS: desired=3, actual=4! → 4 > 3 → DELETE 1 Pod → back to 3 ✓
RS doesn't care who created the extra Pod — if labels match, it's counted. Excess = deleted.

LAB 16
Fix RS — Selector Doesn't Match Template Labels
Medium

Setup: Try to create this broken RS. It will fail. Fix it.

cat <
# Error message:
# The ReplicaSet "broken-rs" is invalid:
# spec.template.metadata.labels: Invalid value: "app":"api":
# selector does not match template labels
ProblemSelector says app: web but template labels say app: api. They MUST match.
# Fix: change template label to match selector
# template.metadata.labels.app: api → app: web
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: broken-rs
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web       # ← FIXED: now matches selector
    spec:
      containers:
      - name: nginx
        image: nginx
LAB 17
Fix RS — Wrong Image, Pods in ImagePullBackOff
Medium

Setup:

cat <

Fix the Pods so they run successfully.

# Step 1: Diagnose
kubectl get pods -l app=img-test
# All 3 Pods in ImagePullBackOff — typo "ngnix" should be "nginx"

# Step 2: Fix the RS template
kubectl patch rs img-rs --type='json' \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/image","value":"nginx:latest"}]'

# Step 3: Template is fixed, but old Pods STILL have wrong image!
# Must delete them so RS recreates with correct template
kubectl delete pods -l app=img-test

# Step 4: Verify new Pods are running
kubectl get pods -l app=img-test
# All 3 Running ✓
Key lessonFixing the template alone is NOT enough — you must also delete the broken Pods. The RS won't restart them just because the template changed.
LAB 18
Fix RS — Desired ≠ Ready for 10 Minutes
Hard

RS shows DESIRED=3, CURRENT=3, but READY=1. Diagnose and fix.

Setup:

cat <
# Step 1: Check RS
kubectl get rs stuck-rs
# DESIRED=3  CURRENT=3  READY=0  ← Pods exist but not ready!

# Step 2: Check Pod events
kubectl describe pod -l app=stuck | grep -A3 "Readiness"
# Readiness probe failed: HTTP probe failed with statuscode: 404
# The probe checks /nonexistent which returns 404

# Step 3: Fix — change readiness probe to valid path
kubectl patch rs stuck-rs --type='json' \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/readinessProbe/httpGet/path","value":"/"}]'

# Step 4: Delete old Pods (template change doesn't affect running Pods!)
kubectl delete pods -l app=stuck

# Step 5: Verify
kubectl get rs stuck-rs
# DESIRED=3  CURRENT=3  READY=3  ✓

LAB 19
Full Production Setup — RS + Service + PDB
Hard

Create a complete production setup in namespace production:

  • RS web-rs: 3 replicas, nginx:1.25, port 80, resources (cpu: 100m/200m, mem: 64Mi/128Mi), readiness probe on /
  • Service web-svc: ClusterIP, port 80 → target 80, selector app=web
  • PDB web-pdb: minAvailable=2, selector app=web
Verify: kubectl -n production get rs,svc,pdb
kubectl create namespace production
# All-in-one YAML
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
  namespace: production
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "64Mi"
          limits:
            cpu: "200m"
            memory: "128Mi"
        readinessProbe:
          httpGet:
            path: /
            port: 80
          periodSeconds: 5
---
apiVersion: v1
kind: Service
metadata:
  name: web-svc
  namespace: production
spec:
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
---
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
  namespace: production
spec:
  minAvailable: 2
  selector:
    matchLabels:
      app: web
kubectl apply -f production.yaml
LAB 20
Migrate RS to Deployment — Zero Downtime
Hard

RS web-rs has 3 running Pods. Migrate to a Deployment without any downtime — Pods should NOT restart.

Verify: Deployment manages 3 Pods, none were restarted (check AGE — should be old)
# Step 1: Delete the RS but KEEP the Pods
kubectl delete rs web-rs --cascade=orphan

# Step 2: Create a Deployment with the SAME selector and template
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web           # SAME selector as the old RS
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: nginx
        image: nginx:1.25   # SAME image
        ports:
        - containerPort: 80
kubectl apply -f deploy.yaml

# Step 3: Verify — Deployment adopted existing Pods (check AGE)
kubectl get pods -l app=web
# All Pods have OLD age — they were adopted, not recreated!

kubectl get rs
# Shows RS created by Deployment, which adopted the orphan Pods
Zero-downtime migration:
① RS deleted (--cascade=orphan) → Pods become orphans, still running
② Deployment created → creates new RS → RS finds matching orphan Pods
③ RS adopts orphan Pods → no restart needed
④ Deployment now manages Pods with rolling updates + rollback ✓
SRE Best Practice

This is the correct way to migrate from RS to Deployment in production. The orphan cascade preserves running Pods. The new Deployment's RS adopts them via label matching. Zero downtime, zero restarts.

After All 20 Labs

Key takeaways: (1) RS has no imperative create command — use YAML or generate from Deployment. (2) Image template changes do NOT affect running Pods — must delete them manually. (3) Replica changes take effect immediately. (4) Selector is immutable. (5) --cascade=orphan keeps Pods when deleting RS. (6) Always use Deployments in production — they automate everything RS can't do.
