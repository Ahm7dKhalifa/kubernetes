01 What Is a Deployment & Why?

Definition — DeploymentA controller that manages ReplicaSets, which manage Pods. Provides declarative updates: you describe desired state, the Deployment controller changes actual state at a controlled rate. Adds rolling updates, rollback, revision history, pause/resume on top of ReplicaSets.
Definition — Why It ExistsA ReplicaSet can maintain Pod count but cannot update Pod images without downtime. A Deployment solves this by creating a NEW RS with the new template, gradually shifting Pods from old RS to new RS — zero downtime.
FeatureWhat It Does
Rolling UpdateReplace Pods gradually — zero downtime
RollbackRevert to any previous version instantly via old RS
Revision HistoryTrack every change with revision numbers
Pause/ResumeBatch multiple changes into one rollout
Status TrackingReports progress, deadline, conditions
Self-HealingDead Pods automatically replaced (via RS)

04 Full Deployment YAML

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
  namespace: production
  annotations:
    kubernetes.io/change-cause: "Initial v1.25"    # Shows in rollout history
spec:
  replicas: 3                          # Desired Pod count
  revisionHistoryLimit: 10             # Old RS kept for rollback
  progressDeadlineSeconds: 600        # Max 10min for rollout progress
  minReadySeconds: 5                  # Pod ready 5s before "available"

  strategy:
    type: RollingUpdate                # or Recreate
    rollingUpdate:
      maxSurge: 1                      # Extra Pods allowed during update
      maxUnavailable: 0               # Pods that can be down (0 = safest)

  selector:                             # IMMUTABLE — cannot change after creation
    matchLabels:
      app: web

  template:                             # Changes here trigger NEW rollout
    metadata:
      labels:
        app: web                      # MUST match selector
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        env:
        - name: APP_ENV
          value: "production"
        resources:
          requests: { cpu: "100m", memory: "64Mi" }
          limits: { cpu: "200m", memory: "128Mi" }
        readinessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 5
        livenessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 10

07 Scenario: Update Image + Replicas Together ▶

Same time
Separate commands
YAML approach
Change image AND replicas in one apply
Before: image=1.25, replicas=3
You change in YAML: image=1.26, replicas=5
kubectl apply -f deploy.yaml

Result: ONE rollout. New RS created with image 1.26 AND scales to 5.
RS-old(3→0) scaling down
RS-new(0→5) scaling up to NEW count

Final: 5 Pods all running nginx:1.26 ✓
When you change both image and replicas simultaneously (single kubectl apply), Kubernetes creates a new RS and targets the new replica count. The old RS scales down. One rollout, not two.
Two separate commands — what happens?
# Command 1: change image → triggers rollout
kubectl set image deployment/web-deploy nginx=nginx:1.26

# Command 2: change replicas → NO rollout
kubectl scale deployment/web-deploy --replicas=5
Command 1: New RS created (1.26). Rolling update starts: RS-old 3→0, RS-new 0→3.
Command 2 (during or after): Adjusts the CURRENT active RS to 5. No new RS.

If command 2 fires DURING rollout: the in-progress rollout adjusts its target to 5.
Final: 5 Pods running 1.26 ✓ (same result, but 2 operations).
YAML approach (cleanest)
# Edit deploy.yaml:
# replicas: 3 → replicas: 5
# image: nginx:1.25 → image: nginx:1.26

kubectl apply -f deploy.yaml
# One apply = one rollout = both changes applied atomically
Best practiceMake all changes in your YAML file and apply once. This creates a single rollout with both changes. Git stays in sync. No drift.

09 Scenario: Multiple Template Changes ▶

Without Pause (BAD)
With Pause (GOOD)
Full YAML (BEST)
3 separate commands = 3 rollouts = 3 RS (wasteful!)
kubectl set image deploy/web nginx=nginx:1.26 → RS-2 created, rollout starts

kubectl set resources deploy/web -c nginx --limits=mem=256Mi → RS-4 created, RS-3 ABANDONED!

kubectl rollout pause deployment/web-deploy

kubectl set resources deployment/web-deploy -c nginx --limits=memory=256Mi

kubectl rollout resume deployment/web-deploy
Result: 1 new RS containing all 3 changes. 1 rollout. Clean.

# Then single apply:

10 RollingUpdate Strategy ▶

DefinitionGradually replaces old Pods with new Pods. Creates new RS, scales it up while scaling old RS down. Each new Pod must pass readiness before an old Pod is killed. At no point fewer than replicas - maxUnavailable healthy Pods.
YAML
Flow Diagram
With Readiness
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1              # 1 extra Pod allowed (total = desired+1)
    maxUnavailable: 0       # 0 Pods can be down (always ≥ desired ready)
Rolling Update Flow (replicas=3, maxSurge=1, maxUnavail=0)
T=0: Old-1Old-2Old-3 | total=3 | ready=3 ✓

T=1: Old-1Old-2Old-3New-1⏳ | total=4 | ready=3 (new starting)

T=2: Old-1Old-2Old-3↓New-1✓ | total=3 | ready=3 (new ready → kill old)

T=3: Old-1Old-2New-1New-2⏳ | total=4 | ready=3

T=4: Old-1Old-2↓New-1New-2✓ | total=3 | ready=3

T=5: Old-1New-1New-2New-3⏳ | total=4 | ready=3

T=6: Old-1↓New-1New-2New-3✓ | total=3 | ready=3 DONE ✓
Why Readiness Probes Are Critical
WITHOUT readiness probe:
Pod is "ready" the moment container starts → old Pod killed immediately → new Pod crashes 2s later → lost capacity!

WITH readiness probe:
Pod starts → readiness check every 5s → passes after 15s → THEN old Pod killed → safe!
SRE Rule

Never deploy without readiness probes. Without them, rolling updates can't verify new Pods are actually serving before killing old ones.

11 Recreate Strategy ▶

DefinitionTerminates ALL old Pods first, then creates ALL new Pods. Causes guaranteed downtime. Use only when two versions cannot coexist (shared DB lock, incompatible schema, license conflict).
YAML
Flow Diagram
When to Use
strategy:
  type: Recreate     # No rollingUpdate section needed
T=0: Old-1Old-2Old-3 running
T=1: Old-1↓Old-2↓Old-3↓ ALL terminated
T=2: ⚠ DOWNTIME — zero Pods serving!
T=3: New-1⏳New-2⏳New-3⏳ creating
T=4: New-1✓New-2✓New-3✓ ready
When Recreate is the right choice
ScenarioWhy Recreate?

13 Blue/Green Deployment — Full Workflow ▶

DefinitionRun two complete, identical environments: Blue (current, serving traffic) and Green (new, ready to go). Test Green. Switch ALL traffic instantly by changing Service selector. Rollback = switch back. Not built into Deployments — uses Service selector manipulation.
① Blue Live
② Deploy Green
③ Test Green
④ Switch Traffic
⑤ Verify
⑥ Rollback
Full YAML
① Blue is live — serving all traffic
Service: web-svc (selector: version=blue)
└──→ Deployment: blue (nginx:1.25, replicas:3)
     PodPodPod ← all traffic goes here
② Deploy Green — runs in parallel, receives NO traffic
Service: web-svc (selector: version=blue)
└──→ Blue (nginx:1.25, 3 Pods) ← still serving

Green (nginx:1.26, 3 Pods) ← running but NO traffic
PodPodPod
③ Test Green in isolation
# Port-forward to a green Pod to test
kubectl port-forward deployment/green 8080:80
# curl localhost:8080 → verify new version works

# Or create a temporary test Service
kubectl expose deployment green --name=green-test --port=80 --type=ClusterIP
④ Switch ALL traffic to Green — instant
kubectl patch svc web-svc -p '{"spec":{"selector":{"version":"green"}}}'
Service: web-svc (selector: version=green)
└──→ Green (nginx:1.26) ← NOW serving all traffic

Blue (nginx:1.25) ← still running, no traffic (standby for rollback)
⑤ Verify — monitor errors
# Check endpoints switched
kubectl describe svc web-svc | grep Selector

# Monitor green Pod logs for errors
kubectl logs -l version=green -f

# If everything looks good after 30min → delete blue
kubectl delete deployment blue
⑥ Rollback — switch back to Blue (instant!)
kubectl patch svc web-svc -p '{"spec":{"selector":{"version":"blue"}}}'
# ALL traffic instantly goes back to blue (still running!)

14 Canary Deployment — Full Workflow ▶

DefinitionSend a small % of traffic to the new version. Monitor for errors. If healthy → gradually increase. If bad → kill canary, all traffic stays on stable. Named after canaries in coal mines — detects danger before it affects everyone.
① Stable Running
② Deploy Canary
③ Traffic Split
④ Monitor
⑤ Promote
⑤b Rollback
Full YAML
① Stable version running
Service: web-svc (selector: app=web)
└──→ Stable (nginx:1.25, replicas:3)
     PodPodPod ← all traffic (100%)
② Deploy canary (1 replica)
Service: web-svc (selector: app=web)
├──→ Stable (1.25, 3 Pods) PPP
└──→ Canary (1.26, 1 Pod) P

Both Deployments have label app=web. Service routes to ALL 4 Pods.
③ Traffic split: ~75% stable, ~25% canary
4 Pods total behind Service. Load balanced round-robin:

Request 1 → Stable Pod (1.25)
Request 2 → Stable Pod (1.25)
Request 3 → Stable Pod (1.25)
Request 4 → Canary Pod (1.26) ← ~25% of traffic

Exact split depends on number of Pods: 3 stable + 1 canary = 75%/25%
④ Monitor canary health
# Watch canary logs
kubectl logs -l app=web,version=canary -f

# Compare error rates (if Prometheus):
# rate(http_errors{version="canary"}[5m]) vs rate(http_errors{version="stable"}[5m])

# Check canary Pod restarts
kubectl get pods -l version=canary
⑤a Promote — canary is healthy
# Gradually increase canary
kubectl scale deployment web-canary --replicas=2   # 3+2 = 40% canary
kubectl scale deployment web-canary --replicas=3   # 3+3 = 50% canary

# Full promote: canary takes over
kubectl scale deployment web-stable --replicas=0
kubectl scale deployment web-canary --replicas=3

# Clean up
kubectl delete deployment web-stable
⑤b Rollback — canary has errors
# Kill canary immediately — all traffic goes to stable
kubectl delete deployment web-canary

# 100% traffic back on stable. Instant recovery.

15 Rollback ▶

Undo previous
Undo to revision
Internal mechanism
kubectl rollout undo deployment/web-deploy
kubectl rollout history deployment/web-deploy              # see all revisions
kubectl rollout history deployment/web-deploy --revision=2 # inspect one
kubectl rollout undo deployment/web-deploy --to-revision=1 # rollback to it
What happens internally
Current state (revision 3, nginx:1.27):
RS-1(0, 1.25) RS-2(0, 1.26) RS-3(3, 1.27) ← active

After rollout undo --to-revision=1:
RS-1(3, 1.25) ← scaled UP (rolling update)
RS-2(0) RS-3(0) ← scaled DOWN

Same rolling update process — zero downtime.
Revision 1 becomes revision 4 (number always increases).

17 Monitoring & Best Practices

Always set readiness probes

Without them, rolling updates can't verify Pods are serving before killing old ones.

Set maxSurge=1, maxUnavailable=0

Safest strategy. Never fewer than desired Pods serving.

Use pause/resume for multi-field changes

Prevents unnecessary intermediate RS and partial rollouts.

Annotate every change

kubernetes.io/change-cause makes rollout history meaningful.

Stuck rollouts do NOT auto-rollback

Progressing=False is informational only. You must rollout undo manually.

SRE Wisdom

Every SRE should be able to: trigger a rollout, watch progress, diagnose a stuck rollout, and rollback — all in under 60 seconds. Practice until these commands are muscle memory.
