⬡ Kubernetes Deployments

One stateless service — order-service in jahez-prod on EKS (me-central-1) — followed from the first apply through every rollout, strategy, release pattern and rollback. Part I explains the idea, Part II every field and command, Part III practises it.

Part I

High Level

1.Foundations

1.1Introduction

A Deployment keeps a set number of identical Pods running and changes them to a new version step by step, without downtime — with history so you can go back.

Definition. Deployment is a built-in object of the apps/v1 API group, maintained by the Kubernetes project. Its logic is the Deployment controller, one of the control loops inside kube-controller-manager. A Deployment does not create Pods itself: it creates a ReplicaSet for each version of the Pod template, and each ReplicaSet keeps its count of Pods alive. When you change the template, the controller creates a new ReplicaSet and moves Pods from the old one to the new one at the pace your strategy allows. Old ReplicaSets stay behind at 0 Pods as revisions, so a rollback is just “scale the old one back up”.

API groupapps/v1 · kind Deployment
Short namedeploy
ScopeNamespaced — jahez-prod
Pod countspec.replicas (or an HPA)
ControllerDeployment controller in kube-controller-manager
Typical useStateless APIs and workers: order-service, menu-api, dispatch-service
✓ It is
  • The standard way to run a stateless app: any Pod can serve any request, Pods are interchangeable
  • A manager of ReplicaSets: one ReplicaSet per template version, Pods owned by the ReplicaSet
  • A rollout engine: RollingUpdate or Recreate, with readiness gates, a progress deadline and pause/resume
  • A history: up to revisionHistoryLimit old ReplicaSets kept for kubectl rollout undo
✕ It is not
  • Not for apps that need a stable name or their own disk per Pod — that is a StatefulSet (orders-db, Elasticsearch)
  • Not one Pod per node — that is a DaemonSet (fluent-bit, node-exporter)
  • Not run-to-completion work — that is a Job / CronJob (settlement export)
  • Not a traffic router: it does not split traffic by percent; blue/green and canary use Services or a mesh on top
  • Not an automatic rollback: a failed rollout is only marked failed; you run rollout undo

Definitions

Deployment

The object that says “keep N Pods of this template, and change them safely”.
🎯 Why it existsPods die and versions change every day. Somebody must keep the count and replace old Pods without dropping orders.
📄 What it looks like
kind: Deployment
spec:
  replicas: 6
  selector: {matchLabels: {app: order-service}}
  template: {...}
  strategy: {type: RollingUpdate}
⚙ What Kubernetes does with itThe controller finds or creates the ReplicaSet whose hash matches the template and scales it to replicas.
Before
deploy/order-service-deployment
(no ReplicaSet, 0 Pods)
After
rs/…-7d9f8c6b5   6/6
6 Pods Running
📍 Where it livesGit: apps/order-service/base/order-service-deployment.yaml · cluster: etcd, namespace jahez-prod
⚠ Watch outspec.selector is immutable. Changing app: order-service later means delete and re-create.

ReplicaSet

Keeps exactly N Pods of one template alive. The Deployment creates and scales it; you never edit it.
🎯 Why it existsSomething must notice a missing Pod and create a new one within seconds. That loop is the ReplicaSet controller.
📄 What it looks like
kind: ReplicaSet
metadata:
  name: order-service-deployment-7d9f8c6b5
  ownerReferences: [{kind: Deployment}]
spec:
  replicas: 6
⚙ What Kubernetes does with itA Pod is deleted → the ReplicaSet controller creates a replacement from the same template.
Before
6/6 Pods
Pod …-x2kqp deleted
After
6/6 Pods
new Pod …-r4vbn created
📍 Where it livesReplicaSets in jahez-prod, owned by the Deployment
⚠ Watch outEditing a ReplicaSet by hand is undone by the Deployment controller at the next sync.

Pod template

spec.template — the blueprint every Pod is made from: labels, containers, image, env, probes, resources.
🎯 Why it existsOne blueprint, many copies. A change to the blueprint is exactly what “a new version” means.
📄 What it looks like
template:
  metadata:
    labels: {app: order-service}
  spec:
    containers:
    - name: order-service
      image: ghcr.io/jahez/order-service:2.14.0
⚙ What Kubernetes does with itAny change inside the template gives it a new hash → new ReplicaSet → rollout.
Before
image: …:2.14.0
hash 7d9f8c6b5
After
image: …:2.15.0
hash 5c8b7d9f4 (new RS)
📍 Where it livesInside the Deployment; copied into each ReplicaSet
⚠ Watch outLabels in the template must match spec.selector or the API rejects the Deployment.

pod-template-hash

A short hash of the template that the controller adds as a label to the ReplicaSet and its Pods.
🎯 Why it existsTwo ReplicaSets of the same Deployment must not fight over the same Pods. The hash label keeps their selectors apart.
📄 What it looks like
labels:
  app: order-service
  pod-template-hash: 7d9f8c6b5
⚙ What Kubernetes does with itAdded to the ReplicaSet name, its selector and every Pod. You never write it yourself.
Before
selector: app=order-service
After
RS selector: app=order-service,
  pod-template-hash=7d9f8c6b5
📍 Where it livesLabels on ReplicaSets and Pods; the RS name suffix
⚠ Watch outNever put the hash into a Service selector — the Service would lose every Pod after the next rollout.

Revision

A numbered version of the template. Each ReplicaSet carries its number in deployment.kubernetes.io/revision.
🎯 Why it existsTo go back, you need to know which template ran before and when it changed.
📄 What it looks like
metadata:
  annotations:
    deployment.kubernetes.io/revision: "2"
    kubernetes.io/change-cause: Release 2.15.0
⚙ What Kubernetes does with itEvery new template → next number. A rollback re-uses the old ReplicaSet but gives it the next number.
Before
rev 1 (2.14.0) · rev 2 (2.15.0)
After
undo → rev 3 (= 2.14.0 again)
📍 Where it livesAnnotations on the Deployment and on each ReplicaSet
⚠ Watch outOnly revisionHistoryLimit old ReplicaSets are kept. Set it to 0 and rollback is impossible.

Rollout

The process of moving all Pods from the old ReplicaSet to the new one.
🎯 Why it existsReplacing six Pods at once drops traffic; replacing them one by one by hand is slow and error-prone.
📄 What it looks like
kubectl rollout status deployment/order-service-deployment -n jahez-prod
⚙ What Kubernetes does with itScales the new ReplicaSet up and the old one down, waiting for readiness each time.
Before
old RS 6 · new RS 0
After
old RS 0 · new RS 6
📍 Where it livesDeployment status.conditions
⚠ Watch outA stuck rollout is not rolled back by Kubernetes; after progressDeadlineSeconds it is only marked ProgressDeadlineExceeded.

Strategy

spec.strategy — how the rollout replaces Pods: RollingUpdate (default) or Recreate.
🎯 Why it existsSome apps can run two versions at once, some cannot. The strategy says which.
📄 What it looks like
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 25%
    maxUnavailable: 0
⚙ What Kubernetes does with itDecides how many extra Pods may exist and how many may be missing during the rollout.
Before
replicas 6 · surge 25% · unavail 0
After
max 8 Pods · never below 6 ready
📍 Where it livesspec.strategy of the Deployment
⚠ Watch outmaxSurge and maxUnavailable cannot both be 0 — the rollout could never move.

Rollback

Going back to an older revision with kubectl rollout undo.
🎯 Why it existsA bad release must be reverted in seconds during the iftar peak, without rebuilding images.
📄 What it looks like
kubectl rollout undo deployment/order-service-deployment --to-revision=1 -n jahez-prod
⚙ What Kubernetes does with itCopies the old ReplicaSet’s template into the Deployment, then rolls out normally.
Before
rev 2 active (2.15.0)
After
rev 3 active (= 2.14.0)
📍 Where it livesA kubectl command; visible in rollout history
⚠ Watch outOnly the template goes back. ConfigMaps, Secrets and DB migrations are not rolled back.

1.3Solution

You write one Deployment. Its controller creates a ReplicaSet per template version, keeps the count, and rolls Pods from the old ReplicaSet to the new one at a safe pace — keeping the old one for rollback.

The solution in 6 steps

  1. Declare the desired state in one file: selector, replicas, template, strategy.
  2. Apply it. The API server stores it in etcd.
  3. The Deployment controller hashes the template (7d9f8c6b5), finds no ReplicaSet with that hash and creates order-service-deployment-7d9f8c6b5 with 6 replicas.
  4. The ReplicaSet controller creates 6 Pods; the scheduler spreads them over 3 zones; readiness puts them behind order-service-service.
  5. You change the template (new image). New hash 5c8b7d9f4 → new ReplicaSet. The controller scales it up and the old one down, never below 6 ready Pods.
  6. The old ReplicaSet stays at 0 Pods as revision 1. rollout undo scales it back up.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service-deployment
  namespace: jahez-prod
  labels:
    app: order-service
    team: orders
  annotations:
    kubernetes.io/change-cause: "Release 2.14.0 — order batching"
spec:
  # ① Which Pods, and how many?
  selector:
    matchLabels:
      app: order-service          # immutable after create
  replicas: 6                     # how many Pods
  # ② What does each Pod run?
  template:
    metadata:
      labels:
        app: order-service        # must satisfy the selector
        version: "2.14.0"
    spec:
      serviceAccountName: order-service-service-account
      terminationGracePeriodSeconds: 45
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: ScheduleAnyway
        labelSelector:
          matchLabels:
            app: order-service
      containers:
      - name: order-service
        image: ghcr.io/jahez/order-service:2.14.0
        ports:
        - name: http
          containerPort: 8080
        envFrom:
        - configMapRef:
            name: order-service-config-map
        env:
        - name: ConnectionStrings__OrdersDb
          valueFrom:
            secretKeyRef:
              name: order-service-db-secret
              key: connection-string
        resources:
          requests:
            cpu: 250m
            memory: 512Mi
          limits:
            memory: 1Gi
        readinessProbe:           # gates every rollout step
          httpGet:
            path: /health/ready
            port: http
          periodSeconds: 5
          failureThreshold: 3
        livenessProbe:
          httpGet:
            path: /health/live
            port: http
          initialDelaySeconds: 20
          periodSeconds: 10
        lifecycle:
          preStop:                # let the load balancer drain first
            sleep:
              seconds: 10
  # ③ How are changes rolled out?
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%               # extra Pods allowed above replicas
      maxUnavailable: 0           # Pods allowed below replicas
  minReadySeconds: 10             # ready for 10 s before it counts as available
  # ④ How long, and how much history?
  progressDeadlineSeconds: 600    # mark the rollout failed after 10 min without progress
  revisionHistoryLimit: 10        # old ReplicaSets kept for rollback
  paused: false

3.The Deployment object

3.0How a Deployment works

A Deployment answers four questions — which Pods and how many, what they run, how changes roll out, how long and how much history — and Kubernetes writes the answers it observes back into status.

Think of it as a shift manager for identical workers. You give the headcount, the uniform (template) and the rules for changing uniforms. The manager never does the work: it tells the ReplicaSet (team lead) how many workers to keep, and hires a new team when the uniform changes. It lives as long as you keep it.

Why readiness probes are critical

The Pod is “ready” the moment the process starts → an old Pod is killed → the new one crashes 2 s later on a missing config key → lost capacity, and the rollout keeps going.

The Pod starts → /health/ready checks DB + Redis every 5 s → passes after 15 s → stays ready 10 s (minReadySeconds) → only then an old Pod goes.

SRE rule

Never ship a Deployment without a readiness probe. Without it the rollout cannot tell a serving Pod from a starting one.

10.Best practices & cheat sheet

10.1Best practices

Always set readiness probes

Rollouts move only on available Pods.

maxUnavailable: 0 in prod

Never fewer than desired Pods serving; pay with maxSurge capacity.

One change → one apply

Use Git; pause/resume only for imperative batches.

Set change-cause with every release

History is useless without it.

Failed rollouts are not rolled back

Gate CI on rollout status; undo or revert the commit.

Remove replicas when an HPA owns it

Otherwise each apply cuts capacity.

preStop sleep + grace period

No 502s while Pods leave the load balancer.

Backward-compatible releases

Both versions serve together for minutes — DB changes in expand/contract steps.

Keep revisionHistoryLimit ≥ 5

Enough to roll back a few releases.

Never edit ReplicaSets

The Deployment owns them.
