LAB 01
Create a Deployment
Easy

Create Deployment web-deploy, image nginx:1.25, 3 replicas, port 80.

Verify: kubectl get deploy web-deploy → READY 3/3
Imperative
YAML
Hybrid (exam)
kubectl create deployment web-deploy --image=nginx:1.25 --replicas=3 --port=80
FastestOne command. Use for simple Deployments in the exam.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-deploy
  template:
    metadata:
      labels:
        app: web-deploy
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
kubectl create deployment web-deploy --image=nginx:1.25 --replicas=3 --port=80 --dry-run=client -o yaml > deploy.yaml
# Edit: add strategy, resources, probes, etc.
kubectl apply -f deploy.yaml
Best for complex specsGenerate skeleton, add what you need, apply.
LAB 02
Create Deployment with Rolling Update Strategy
Medium

Create Deployment safe-deploy, image nginx:1.25, 4 replicas, with: maxSurge=1, maxUnavailable=0 (safest rolling update).

Verify: kubectl get deploy safe-deploy -o jsonpath='{.spec.strategy}'
# Generate then edit
kubectl create deployment safe-deploy --image=nginx:1.25 --replicas=4 --dry-run=client -o yaml > safe.yaml

Add strategy section under spec:

spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1             # Max 5 Pods during update (4+1)
      maxUnavailable: 0      # Always ≥ 4 Pods ready
kubectl apply -f safe.yaml
maxSurge=1, maxUnavailable=0The safest strategy. One extra Pod is created, must pass readiness, THEN one old Pod is killed. At no point are there fewer than 4 healthy Pods. Slow but safe.

Rolling Updates

LAB 04
Update Image — Trigger a Rolling Update
Medium

Update web-deploy from nginx:1.25 to nginx:1.26. Watch the rollout happen. Verify all Pods run the new image.

Verify: All Pods show nginx:1.26 and rollout is complete
set image
kubectl edit
Apply YAML
Patch
kubectl set image deployment/web-deploy nginx=nginx:1.26
Fastest for examOne command. nginx= refers to the container name, not the image.
kubectl edit deployment web-deploy
# Change image: nginx:1.25 → nginx:1.26 in editor, save
# Edit deploy.yaml: image: nginx:1.25 → nginx:1.26
kubectl apply -f deploy.yaml
Best for GitOpsFile and cluster stay in sync.
kubectl patch deployment web-deploy -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","image":"nginx:1.26"}]}}}}'

Watch + verify:

# Watch rollout progress
kubectl rollout status deployment/web-deploy

# Verify all Pods run new image
kubectl get pods -l app=web-deploy -o jsonpath='{range .items[*]}{.spec.containers[0].image}{"\n"}{end}'

# Check RS — old RS has 0, new RS has 3
kubectl get rs -l app=web-deploy
What happened internally:
RS-v1 (1.25): 3→2→1→0 scaling down
RS-v2 (1.26): 0→1→2→3 scaling up

Each new Pod passes readiness before an old Pod is killed. Zero downtime.

Rollback

LAB 08
Rollback to Previous Version
Easy

You deployed a broken image. Rollback web-deploy to the previous working version.

Setup:

kubectl set image deployment/web-deploy nginx=nginx:9.99-broken
Verify: kubectl rollout status deployment/web-deploy → successfully rolled out
# Step 1: Check current status — rollout stuck
kubectl rollout status deployment/web-deploy --timeout=30s
# error: timed out

# Step 2: Check Pods — new Pods in ImagePullBackOff
kubectl get pods -l app=web-deploy

# Step 3: Rollback to previous
kubectl rollout undo deployment/web-deploy

# Step 4: Verify
kubectl rollout status deployment/web-deploy
# deployment "web-deploy" successfully rolled out
What happened:
RS-bad (nginx:9.99): scaled DOWN to 0
RS-prev (nginx:1.27): scaled UP to 3 ← same RS that existed before

Rollback is a rolling update in reverse. Old RS is kept specifically for this.
LAB 09
Rollback to a Specific Revision
Medium

You've done multiple updates. Rollback web-deploy to revision 1 (the original image).

Setup (creates 3 revisions):

kubectl create deployment rev-test --image=nginx:1.24 --replicas=2
kubectl set image deployment/rev-test nginx=nginx:1.25
kubectl set image deployment/rev-test nginx=nginx:1.26
Verify: Image is nginx:1.24 (revision 1)
# View all revisions
kubectl rollout history deployment/rev-test

# Inspect specific revision (see the image)
kubectl rollout history deployment/rev-test --revision=1

# Rollback to revision 1
kubectl rollout undo deployment/rev-test --to-revision=1

# Verify
kubectl get deployment rev-test -o jsonpath='{.spec.template.spec.containers[0].image}'
# nginx:1.24 ✓
NoteAfter rollback to revision 1, the revision number INCREASES (becomes revision 4, not 1 again). The revision 1 entry disappears from history because it's now the current state.

Scaling

LAB 11
Manual Scale — Up and Down
Easy

Scale web-deploy to 5, then to 1. Verify no new RS is created (scaling ≠ rollout).

# Scale up
kubectl scale deployment/web-deploy --replicas=5

# Scale down
kubectl scale deployment/web-deploy --replicas=1

# Check: NO new RS created
kubectl get rs -l app=web-deploy
# Same RS as before — only replicas changed
Key pointScaling does NOT trigger a rollout. No new RS. Existing RS adjusts its replica count. Only spec.template changes create new RS.
LAB 12
HorizontalPodAutoscaler (HPA)
Medium

Create an HPA for web-deploy: min 2, max 10, target CPU 80%. (Requires metrics-server.)

Imperative
YAML
kubectl autoscale deployment web-deploy --min=2 --max=10 --cpu-percent=80

kubectl get hpa
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: web-deploy
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80
PrerequisiteHPA requires metrics-server running in the cluster and containers MUST have resources.requests.cpu set. Without it, HPA can't calculate utilization.

Strategies

LAB 13
Recreate Strategy (Kill All, Then Create)
Medium

Create Deployment db-deploy with strategy: Recreate. Update its image and observe: all Pods die before new ones start.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: db-deploy
spec:
  replicas: 3
  strategy:
    type: Recreate           # Kill all → create all. DOWNTIME!
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
      - name: postgres
        image: postgres:15
kubectl apply -f db.yaml

# Watch in another terminal
kubectl get pods -l app=db -w

# Trigger update
kubectl set image deployment/db-deploy postgres=postgres:16
# You'll see ALL Pods terminate, THEN all new Pods created
Pod 1Pod 2Pod 3 → ALL killed → DOWNTIME → Pod 4Pod 5Pod 6
When to use RecreateOnly when two versions CANNOT run simultaneously: database schema migrations, shared storage locks, license restrictions.
LAB 14
Tune maxSurge and maxUnavailable
Hard

Create 4 Deployments with different strategy tuning. Update each and observe the behavior difference.

# A: Safest — always ≥ desired Pods running
maxSurge: 1
maxUnavailable: 0
# replicas=3: during update → always 3 ready, max 4 total

# B: Fast — replace 25% at a time (DEFAULT)
maxSurge: 25%
maxUnavailable: 25%
# replicas=4: max 5 total, min 3 ready

# C: Fastest — create ALL new Pods first (double resources)
maxSurge: 100%
maxUnavailable: 0
# replicas=3: creates 3 new first (6 total!), then kills 3 old

# D: Constrained — no extra Pods (must kill before create)
maxSurge: 0
maxUnavailable: 1
# replicas=3: kills 1 old, creates 1 new, repeat. Max 3 total.

maxSurge=1, maxUnavail=043SlowHighest

LAB 15
Pause & Resume — Batch Multiple Changes
Medium

Make 3 changes to web-deploy (image + env + resources) as ONE single rollout instead of 3.

# Step 1: Pause — freeze rollouts
kubectl rollout pause deployment/web-deploy

# Step 2: Make all changes (none trigger rollout while paused)
kubectl set image deployment/web-deploy nginx=nginx:1.28
kubectl set env deployment/web-deploy LOG_LEVEL=info
kubectl set resources deployment/web-deploy -c nginx --limits=memory=256Mi

# Step 3: Resume — all changes applied as ONE rollout
kubectl rollout resume deployment/web-deploy

# Watch
kubectl rollout status deployment/web-deploy
Without pause: 3 changes = 3 RS created, 3 rollouts (wasteful, messy)
With pause: 3 changes = 1 RS created, 1 rollout (clean, efficient)

Deployment Patterns

LAB 16
Blue/Green Deployment
Hard

Implement blue/green: Deploy v1 (blue) behind a Service. Deploy v2 (green). Test green. Switch traffic instantly.

# Step 1: Blue (current) — receives all traffic
kubectl create deployment blue --image=nginx:1.25 --replicas=3

# Step 2: Label blue Pods
kubectl patch deployment blue -p '{"spec":{"template":{"metadata":{"labels":{"version":"blue"}}}}}'

# Step 3: Service points to blue
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    version: blue
  ports:
  - port: 80
# Step 4: Green (new) — test in isolation
kubectl create deployment green --image=nginx:1.26 --replicas=3
kubectl patch deployment green -p '{"spec":{"template":{"metadata":{"labels":{"version":"green"}}}}}'

# Step 5: Test green (port-forward to a green Pod, verify)
kubectl port-forward deployment/green 8080:80

# Step 6: Switch ALL traffic to green
kubectl patch svc web-svc -p '{"spec":{"selector":{"version":"green"}}}'

# Step 7: Rollback if needed — switch back to blue
kubectl patch svc web-svc -p '{"spec":{"selector":{"version":"blue"}}}'
Blue/Green: two full deployments, instant traffic switch via Service selector.
LAB 17
Canary Deployment
Hard

Send 25% of traffic to a canary (new version). Monitor. Then promote or rollback.

# Step 1: Stable deployment (3 replicas)
kubectl create deployment web-stable --image=nginx:1.25 --replicas=3

# Step 2: Service selects shared label 'app=web'
kubectl label deployment web-stable app=web --overwrite
kubectl expose deployment web-stable --name=web-svc --port=80 --selector=app=web

# Step 3: Canary deployment (1 replica = ~25% traffic)
kubectl create deployment web-canary --image=nginx:1.26 --replicas=1
kubectl label deployment web-canary app=web --overwrite

# Step 4: Verify traffic split (4 Pods total, 1 canary)
kubectl get pods -l app=web

# Step 5a: Canary looks good → promote
kubectl scale deployment web-canary --replicas=3
kubectl delete deployment web-stable

# Step 5b: Canary is bad → rollback
kubectl delete deployment web-canary

Troubleshooting

LAB 18
Fix Failed Rollout — Bad Image
Medium

Setup:

kubectl create deployment fix-img --image=nginx:1.25 --replicas=3
kubectl set image deployment/fix-img nginx=nginx:9.99-nonexistent

Rollout is stuck. Diagnose and fix.

Fix A: Rollback
Fix B: Fix forward
# Diagnose
kubectl rollout status deployment/fix-img --timeout=30s
# Waiting for rollout... (stuck)

kubectl get pods -l app=fix-img
# New Pod in ImagePullBackOff

# Fix — rollback to previous working version
kubectl rollout undo deployment/fix-img
kubectl rollout status deployment/fix-img
# Fix forward — set the correct image
kubectl set image deployment/fix-img nginx=nginx:1.26
kubectl rollout status deployment/fix-img
Fix forward vs rollbackRollback is safer (known good state). Fix forward is faster if you know the correct image. Both trigger a new rolling update.
LAB 19
Fix Stuck Rollout — Pods CrashLooping
Hard

Setup:

kubectl create deployment fix-crash --image=nginx:1.25 --replicas=3
kubectl set image deployment/fix-crash nginx=busybox
kubectl set env deployment/fix-crash COMMAND="exit 1"

New Pods keep crashing. Old Pods still running. Diagnose and fix.

# Step 1: Diagnose
kubectl rollout status deployment/fix-crash --timeout=30s
# Stuck — new Pods crashing

kubectl get pods -l app=fix-crash
# Old Pods Running, new Pods CrashLoopBackOff

kubectl logs -l app=fix-crash --sort-by=.metadata.creationTimestamp | tail -5

# Step 2: Check RS — old RS still has Pods (maxUnavailable protects them)
kubectl get rs -l app=fix-crash

# Step 3: Rollback
kubectl rollout undo deployment/fix-crash
kubectl rollout status deployment/fix-crash
Safety netDuring a rolling update, old Pods are NOT deleted until new Pods are ready. If new Pods crash, old Pods keep serving. The rollout is stuck but the service is still up. This is why readiness probes and rolling updates are critical.
LAB 20
Fix — progressDeadlineSeconds Exceeded
Medium

Deployment shows Progressing=False. Understand what this means and fix it.

# Check conditions
kubectl get deployment fix-crash -o jsonpath='{range .status.conditions[*]}{.type}={.status} ({.reason}){"\n"}{end}'
# Progressing=False (ProgressDeadlineExceeded)

# This means: no progress was made for progressDeadlineSeconds (default 600s)
# It does NOT auto-rollback! You must fix it manually.

# Fix: rollback
kubectl rollout undo deployment/fix-crash
Exam trapProgressing=False does NOT mean Kubernetes automatically rolls back. The bad rollout stays stuck forever. You must manually undo or fix forward. This is by design — Kubernetes doesn't assume what the correct action is.

LAB 22
Rollout Restart — Restart All Pods Without Changing Template
Medium

Restart all Pods of web-deploy without changing the image or config (e.g., to pick up a new ConfigMap or clear cache).

kubectl rollout restart deployment/web-deploy

# Watch: creates new RS, does rolling replacement
kubectl rollout status deployment/web-deploy
How it worksrollout restart adds a restartedAt annotation to the Pod template, which counts as a template change and triggers a new RS + rolling update. All Pods are gradually replaced with fresh ones. Zero downtime.
Use casesPick up updated ConfigMap/Secret (mounted as volume), clear application cache, apply new log rotation, refresh connections after a downstream service restart.
LAB 23
Set minReadySeconds
Medium

Configure web-deploy so each new Pod must be ready for 10 seconds before being considered "available".

kubectl patch deployment web-deploy -p '{"spec":{"minReadySeconds":10}}'

# OR in YAML:
spec:
  minReadySeconds: 10
Why use thisPrevents the rollout from going too fast. A Pod might pass readiness immediately but crash 5 seconds later. minReadySeconds: 10 waits 10 extra seconds after readiness before considering the Pod stable and moving on to the next one. Catches fast-failure scenarios.
NoteChanging minReadySeconds does NOT trigger a rollout (it's not part of spec.template).
LAB 24
Set revisionHistoryLimit
Easy

Configure web-deploy to keep only 5 old ReplicaSets (instead of default 10).

kubectl patch deployment web-deploy -p '{"spec":{"revisionHistoryLimit":5}}'

# OR in YAML:
spec:
  revisionHistoryLimit: 5    # Keep 5 old RS for rollback (default 10)
What it controlsHow many old (empty, replicas=0) ReplicaSets are kept. Each old RS is a rollback target. More = more rollback options but more clutter. Less = cleaner but fewer rollback targets.
WarningSetting to 0 means you can NEVER rollback. Old RS are immediately garbage collected.
LAB 25
Full Production Deployment
Hard

Create a complete production-ready Deployment in namespace production:

  • Name: prod-deploy, image: nginx:1.25, replicas: 3, port: 80
  • Strategy: RollingUpdate, maxSurge=1, maxUnavailable=0
  • Resources: cpu 100m/200m, memory 64Mi/128Mi
  • Liveness probe: HTTP / port 80, period 10s
  • Readiness probe: HTTP / port 80, period 5s
  • Env: APP_ENV=production
  • Grace period: 45s, minReadySeconds: 5
  • revisionHistoryLimit: 5, progressDeadlineSeconds: 300
  • Annotation: kubernetes.io/change-cause: "Initial release v1.25"
Verify: kubectl -n production get deploy prod-deploy → 3/3
kubectl create namespace production
apiVersion: apps/v1
kind: Deployment
metadata:
  name: prod-deploy
  namespace: production
  annotations:
    kubernetes.io/change-cause: "Initial release v1.25"
spec:
  replicas: 3
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 300
  minReadySeconds: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: prod
  template:
    metadata:
      labels:
        app: prod
    spec:
      terminationGracePeriodSeconds: 45
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        env:
        - name: APP_ENV
          value: "production"
        resources:
          requests:
            cpu: "100m"
            memory: "64Mi"
          limits:
            cpu: "200m"
            memory: "128Mi"
        livenessProbe:
          httpGet:
            path: /
            port: 80
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /
            port: 80
          periodSeconds: 5
kubectl apply -f prod-deploy.yaml
Key Takeaways

1. kubectl set image is the fastest way to trigger rollouts. 2. kubectl rollout undo is instant rollback. 3. Only spec.template changes create new RS. 4. maxSurge=1,maxUnavailable=0 is safest. 5. rollout restart replaces all Pods without changing template. 6. rollout pause/resume batches multiple changes. 7. Stuck rollouts do NOT auto-rollback — you must fix them manually. 8. Always set readiness probes — without them, rolling updates can't wait for Pods to be ready.
