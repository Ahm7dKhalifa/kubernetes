Create & Basics

LAB 01
Create a Simple Job
Easy

Create a Job named hello-job using image busybox that prints "Hello CKAD" and exits.

Verify: kubectl get job hello-job → COMPLETIONS 1/1
Imperative
YAML
Hybrid
kubectl create job hello-job --image=busybox -- /bin/sh -c "echo Hello CKAD"
FastestOne command. Everything after -- is the container command.
apiVersion: batch/v1
kind: Job
metadata:
  name: hello-job
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: hello
        image: busybox
        command: ["sh","-c","echo Hello CKAD"]
Exam traprestartPolicy MUST be Never or OnFailure. If you use Always (or forget it — default is Always), the API server rejects the Job.
kubectl create job hello-job --image=busybox --dry-run=client -o yaml -- /bin/sh -c "echo Hello CKAD" > job.yaml
kubectl apply -f job.yaml
# Check result
kubectl get job hello-job
kubectl logs job/hello-job
# Hello CKAD

Completions & Parallelism

LAB 05
Sequential Job — 5 Completions, 1 at a Time
Medium

Create Job seq-job that runs 5 Pods sequentially (one at a time). Each Pod prints its hostname and exits.

Verify: kubectl get job seq-job → COMPLETIONS 5/5
apiVersion: batch/v1
kind: Job
metadata:
  name: seq-job
spec:
  completions: 5        # 5 Pods must succeed
  parallelism: 1        # 1 at a time (sequential)
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: busybox
        command: ["sh","-c","echo Processing on $(hostname) && sleep 5"]
P1→✓ then P2→✓ then P3→✓ then P4→✓ then P5→✓
Total time ≈ 5 × 5s = 25s
# Watch Pods being created one after another
kubectl get pods -l job-name=seq-job -w
LAB 06
Parallel Job — 6 Completions, 3 at a Time
Medium

Create Job par-job that needs 6 completions but runs 3 Pods at a time (parallel).

Verify: kubectl get job par-job → COMPLETIONS 6/6. Watch with -w to see 3 Pods at a time.
apiVersion: batch/v1
kind: Job
metadata:
  name: par-job
spec:
  completions: 6        # 6 Pods must succeed total
  parallelism: 3        # 3 Pods running simultaneously
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: busybox
        command: ["sh","-c","echo Worker $(hostname) && sleep 10"]
Batch 1: P1P2P3 (3 running)
Batch 2: P4P5P6 (3 more)
Total time ≈ 2 × 10s = 20s (3× faster than sequential)

LAB 08
Indexed Job — Each Pod Gets Unique Index
Hard

Create an Indexed Job indexed-job with 4 completions, parallelism 2. Each Pod should print its JOB_COMPLETION_INDEX.

Verify: Logs show indices 0, 1, 2, 3
apiVersion: batch/v1
kind: Job
metadata:
  name: indexed-job
spec:
  completions: 4
  parallelism: 2
  completionMode: Indexed       # Each Pod gets unique index 0-3
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: busybox
        command: ["sh","-c","echo Processing shard $JOB_COMPLETION_INDEX && sleep 3"]
# View logs from all Pods
kubectl logs -l job-name=indexed-job
# Processing shard 0
# Processing shard 1
# Processing shard 2
# Processing shard 3
Use caseShard processing. Pod 0 handles rows 0-999, Pod 1 handles 1000-1999, etc. Each Pod knows its index via the JOB_COMPLETION_INDEX environment variable (auto-injected by Kubernetes).

apiVersion: batch/v1
kind: Job
metadata:

Pod 1: exit 1 → wait 10s → Pod 2: exit 1 → wait 20s → Pod 3: exit 1 → wait 40s → Pod 4: exit 1
backoffLimit=3 reached → Job FAILED

4 Pods total created (original + 3 retries). All kept with restartPolicy:Never — check their logs.
# Verify Job failed
kubectl get job fail-job -o jsonpath='{.status.conditions[0].type}'

LAB 10
restartPolicy: Never vs OnFailure
Medium

Create two Jobs that fail: one with restartPolicy: Never, one with OnFailure. Observe the difference in Pod behavior.

Never (new Pod per failure)
OnFailure (restart in same Pod)
kubectl create job never-job --image=busybox -- /bin/sh -c "exit 1"
# restartPolicy defaults to Never for imperative create

kubectl get pods -l job-name=never-job -w
# You'll see MULTIPLE Pods created: never-job-abc, never-job-def, never-job-ghi...
# Each failure = NEW Pod. Old failed Pods kept (Status: Error).
Pod 1 (Error) Pod 2 (Error) Pod 3 (Error) ... ← each failure creates NEW Pod
apiVersion: batch/v1
kind: Job
metadata:
  name: onfail-job
spec:
  backoffLimit: 3
  template:
    spec:
      restartPolicy: OnFailure    # Restart CONTAINER inside same Pod
      containers:
      - name: worker
        image: busybox
        command: ["sh","-c","exit 1"]
kubectl get pods -l job-name=onfail-job -w
# Only 1 Pod, but RESTARTS column increases: 0 → 1 → 2 → 3
Pod 1 (Restarts: 3, CrashLoopBackOff) ← SAME Pod, container restarted inside it
NeverOnFailure
Failed PodsMultiple Pods created1 Pod, container restarts
Crash logsKept (each failed Pod stays)Lost on each restart
ResourcesMore (each Pod = new scheduling)Less (reuses same Pod)
Best forDebugging failuresResource efficiency
LAB 11
activeDeadlineSeconds — Job Timeout
Medium

Create a Job that sleeps for 300s but set activeDeadlineSeconds=30. Observe: Job is killed after 30s even though the Pod is still running.

apiVersion: batch/v1
kind: Job
metadata:
  name: timeout-job
spec:
  activeDeadlineSeconds: 30        # Kill everything after 30s
  backoffLimit: 3
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: sleeper
        image: busybox
        command: ["sleep", "300"]
# Wait 30s, then check
kubectl get job timeout-job -o jsonpath='{.status.conditions[0]}'
# type:Failed, reason:DeadlineExceeded
Pod running ... 30s passes ... KILLED by deadline
Job status: Failed (DeadlineExceeded)
KeyactiveDeadlineSeconds overrides backoffLimit. Even if retries are left, the deadline kills everything.
LAB 12
backoffLimit=0 — No Retries At All
Easy

Create a Job with backoffLimit: 0 that runs a command that fails. Observe: Job fails immediately with no retries.

apiVersion: batch/v1
kind: Job
metadata:
  name: noretry-job
spec:
  backoffLimit: 0                # Zero retries — fail immediately
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: busybox
        command: ["sh","-c","exit 1"]
kubectl get pods -l job-name=noretry-job
# Only 1 Pod ever created. Job immediately Failed.
Use caseWhen you know the task is non-retryable (bad input, wrong config). Don't waste time retrying something that will always fail.

apiVersion: batch/v1

CronJobs

LAB 15
Create a CronJob — Runs Every 5 Minutes
Medium

Create CronJob backup-cron that runs every 5 minutes, image busybox, command: echo backup at $(date).

Verify: kubectl get cronjob backup-cron → shows SCHEDULE and LAST SCHEDULE
Imperative
YAML
kubectl create cronjob backup-cron --image=busybox --schedule="*/5 * * * *" -- /bin/sh -c "echo backup at $(date)"
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-cron
spec:
  schedule: "*/5 * * * *"          # Every 5 minutes
  successfulJobsHistoryLimit: 3    # Keep last 3 successful Jobs
  failedJobsHistoryLimit: 1        # Keep last 1 failed Job
  concurrencyPolicy: Forbid       # Don't start new if old still running
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: backup
            image: busybox
            command: ["sh","-c","echo backup at $(date)"]
Schedule syntax* * * * * = minute hour day-of-month month day-of-week. */5 * * * * = every 5 minutes. 0 2 * * * = daily at 2 AM. 0 0 * * 0 = weekly Sunday midnight.

# Check it

LAB 17
CronJob concurrencyPolicy & History Limits
Medium

Create CronJob report-cron every minute. Set: concurrencyPolicy=Forbid, successfulJobsHistoryLimit=2, failedJobsHistoryLimit=1.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: report-cron
spec:
  schedule: "* * * * *"               # Every minute
  concurrencyPolicy: Forbid          # Skip if previous still running
  successfulJobsHistoryLimit: 2       # Keep 2 successful Jobs
  failedJobsHistoryLimit: 1           # Keep 1 failed Job
  startingDeadlineSeconds: 60        # Skip run if >60s late
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: report
            image: busybox
            command: ["sh","-c","echo Report $(date) && sleep 5"]
concurrencyPolicyBehavior
Allow (default)Multiple Jobs can run simultaneously
ForbidSkip new run if previous is still active
ReplaceKill running Job, start new one

Troubleshooting

LAB 18
Fix Failed Job — Wrong Command
Medium

Setup:

kubectl create job broken-job --image=busybox -- /bin/sh -c "cat /nonexistent-file"

Job keeps failing. Diagnose and create a working version.

# Step 1: Check Job status
kubectl get job broken-job
# COMPLETIONS 0/1 — not completing

# Step 2: Check Pod logs
kubectl logs -l job-name=broken-job
# cat: can't open '/nonexistent-file': No such file or directory

# Step 3: Jobs are IMMUTABLE — cannot fix. Delete and recreate.
kubectl delete job broken-job
kubectl create job broken-job --image=busybox -- /bin/sh -c "echo fixed"
Key ruleUnlike Deployments, you CANNOT edit a Job's template after creation. Jobs are immutable. You must delete and recreate with the correct spec.
LAB 19
Fix Stuck Job — Pods in ImagePullBackOff
Medium

Setup:

kubectl create job pull-job --image=busybox:nonexistent-tag -- echo hello

Job never completes. Diagnose and fix.

# Diagnose
kubectl get pods -l job-name=pull-job
# ImagePullBackOff

kubectl describe pod -l job-name=pull-job | tail -5
# Failed to pull image "busybox:nonexistent-tag"

# Fix — Jobs are immutable, must delete and recreate
kubectl delete job pull-job
kubectl create job pull-job --image=busybox:1.36 -- echo hello
LAB 20
Fix Wrong restartPolicy
Medium

Try to create a Job with restartPolicy: Always. Observe the error. Fix it.

# This YAML will be rejected by the API server:
apiVersion: batch/v1
kind: Job
metadata:
  name: bad-policy
spec:
  template:
    spec:
      restartPolicy: Always      # ← INVALID for Jobs!
      containers:
      - name: worker
        image: busybox
        command: ["echo","hi"]
kubectl apply -f bad-policy.yaml
# Error: spec.template.spec.restartPolicy: Unsupported value: "Always":
# supported values: "OnFailure", "Never"
FixChange restartPolicy: Always to Never or OnFailure. Always is for Deployments only — Jobs must terminate, so "always restart" makes no sense.

LAB 24
Suspend and Resume a Job
Medium

Create a parallel Job (completions=10, parallelism=3). While it's running, suspend it, then resume.

# Create long-running parallel Job
kubectl create job suspend-test --image=busybox -- /bin/sh -c "sleep 30"
# (or use YAML with completions=10, parallelism=3, sleep 30)

# Suspend — stops all Pods, pauses Job
kubectl patch job suspend-test -p '{"spec":{"suspend":true}}'
# Active Pods are terminated. No new Pods created.

# Verify suspended
kubectl get job suspend-test
# ACTIVE=0, COMPLETIONS less than total

# Resume — restarts from where it left off
kubectl patch job suspend-test -p '{"spec":{"suspend":false}}'
# New Pods created to continue the work
Use casePause a Job during maintenance. Suspend a resource-heavy Job during peak hours, resume at night.
LAB 25
Full Production Job + CronJob
Hard

Create a production CronJob in namespace production:

  • Name: nightly-report, Schedule: daily at 2 AM (0 2 * * *)
  • Job: completions=1, backoffLimit=3, activeDeadlineSeconds=1800 (30 min)
  • ttlSecondsAfterFinished=86400 (24h), concurrencyPolicy=Forbid
  • Container: image busybox, command: echo "Report generated at $(date)"
  • Resources: cpu 200m/500m, memory 128Mi/256Mi
  • successfulJobsHistoryLimit=3, failedJobsHistoryLimit=2
kubectl create namespace production
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
  namespace: production
spec:
  schedule: "0 2 * * *"
  concurrencyPolicy: Forbid
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 2
  jobTemplate:
    spec:
      backoffLimit: 3
      activeDeadlineSeconds: 1800
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: reporter
            image: busybox
            command: ["sh","-c","echo Report generated at $(date)"]
            resources:
              requests:
                cpu: "200m"
                memory: "128Mi"
              limits:
                cpu: "500m"
                memory: "256Mi"
kubectl apply -f nightly-report.yaml

# Test immediately without waiting
kubectl create job test-report -n production --from=cronjob/nightly-report
Key Takeaways

1. restartPolicy must be Never or OnFailure (never Always). 2. completions = how many must succeed. parallelism = how many run at once. 3. backoffLimit defaults to 6 with exponential backoff (10s→20s→40s...). 4. Always set activeDeadlineSeconds (safety net) and ttlSecondsAfterFinished (cleanup). 5. Jobs are immutable — can't fix, must delete and recreate. 6. --from=cronjob/NAME triggers a CronJob manually. 7. Indexed completion mode gives each Pod a unique index for shard processing.
