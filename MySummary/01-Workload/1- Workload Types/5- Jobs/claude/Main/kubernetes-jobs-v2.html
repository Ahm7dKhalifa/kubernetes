Kubernetes Jobs

The complete guide — completions, parallelism, failure policies, backoff behavior, TTL cleanup, and job patterns. Interactive step-by-step workflows.

01 What Is a Job & Why?

Definition — JobA Job creates one or more Pods and ensures that a specified number of them successfully complete (exit code 0). Unlike Deployments (which run forever), Jobs are run-to-completion — they start, do work, and stop. The Job controller tracks successful completions and stops when enough Pods have succeeded.
Definition — Run-to-CompletionA workload pattern where the process starts, performs a finite task, and exits with code 0 (success). Opposite of long-running services (Deployments) that run indefinitely.
Use CaseExample
Batch processingProcess 10,000 images, then stop
Data migrationMove data from MySQL to PostgreSQL
Report generationGenerate monthly PDF report
Database backupDump database to S3, then exit
ETL pipelineExtract, transform, load data
ML trainingTrain model on dataset, save weights
Email sendingSend 5000 notification emails
Cleanup tasksDelete old logs, expired sessions
Analogy

A Deployment is a restaurant — open all day, continuously serving. A Job is a catering order — prepare 100 meals, deliver them, done. You don't keep the kitchen running after the order is fulfilled.

Type 1 — Single Pod Job (simplest)
Job → Pod 1 runs → exit 0 ✓ → Job Complete
completions: 1    # default — 1 Pod must succeed
parallelism: 1    # default — 1 Pod at a time
One Pod runs. If it succeeds (exit 0) → Job complete. If it fails → Job retries up to backoffLimit times. Most common for simple tasks: backup, migration, one-off script.
Type 2 — Fixed Completion Count (sequential)
Job (completions:5, parallelism:1)

Pod 1 → ✓ → Pod 2 → ✓ → Pod 3 → ✓ → Pod 4 → ✓ → Pod 5 → ✓
5/5 succeeded → Job Complete
completions: 5    # 5 Pods must succeed
parallelism: 1    # one at a time
Runs 5 Pods one after another. Each must exit 0. Job is complete when 5 Pods have succeeded. If one fails, it retries that task, then continues.
Type 3 — Parallel with Fixed Completions
Job (completions:6, parallelism:3)

Batch 1: Pod 1 Pod 2 Pod 3 (3 running in parallel)
→ all complete → Batch 2: Pod 4 Pod 5 Pod 6
→ all complete → 6/6 succeeded → Job Complete
completions: 6    # 6 Pods must succeed
parallelism: 3    # 3 at a time
Runs up to 3 Pods simultaneously. As one finishes, a new one starts (until 6 total have succeeded). Much faster than sequential. Each Pod gets a unique completion index (0-5) via JOB_COMPLETION_INDEX env var.
Type 4 — Work Queue (parallel, no fixed completions)
Job (completions: unset, parallelism:3)

Pod 1 Pod 2 Pod 3 (all pull from queue)
Each Pod pulls work items from a shared queue (Redis, RabbitMQ)
When queue is empty → Pod exits 0 → eventually all Pods done
→ Any Pod exits 0 → Job stops creating new Pods
# Do NOT set completions (leave unset)
parallelism: 3    # 3 workers pulling from queue
Pods are workers that pull tasks from an external queue. No fixed count — the Job runs until a Pod signals "queue is empty" by exiting 0. Once one Pod succeeds, no new Pods are created (existing ones finish their current work).

04 Full Job YAML — Every Field Explained

apiVersion: batch/v1                 # Jobs are in batch API group
kind: Job
metadata:
  name: data-migration
spec:
  completions: 5                     # Total successful Pods needed (default 1)
  parallelism: 2                     # Max concurrent Pods (default 1)
  backoffLimit: 6                    # Max retries before Job fails (default 6)
  activeDeadlineSeconds: 3600        # Max total runtime — 1 hour, then Job killed
  ttlSecondsAfterFinished: 86400     # Auto-delete Job 24h after completion
  completionMode: Indexed            # Indexed or NonIndexed (default)
  suspend: false                     # true = Job is paused

  template:                            # Pod template — same as in Deployments
    spec:
      restartPolicy: Never            # MUST be Never or OnFailure (not Always!)
      containers:
      - name: worker
        image: python:3.11
        command: ["python", "migrate.py"]
        resources:
          requests: { cpu: "500m", memory: "256Mi" }
          limits: { cpu: "1", memory: "512Mi" }
        env:
        - name: DB_HOST
          value: "mysql.default.svc"
restartPolicy Rules for JobsAlways is forbidden for Jobs (that's for Deployments). You must use:
Never — failed Pod stays dead, Job controller creates a NEW Pod. Best for debugging (you can inspect the failed Pod's logs).
OnFailure — kubelet restarts the failed CONTAINER inside the same Pod. Pod stays, container retries. Uses less resources but you lose crash logs.

06 Completions — How Many Pods Must Succeed ▶

Definition — completionsThe total number of Pods that must successfully complete (exit 0) for the Job to be considered done. Default: 1. The Job tracks succeeded count and stops when it reaches completions.
completions=1
completions=5
With failure
Indexed mode
completions: 1 (default)
Pod 1 runs → exit 0 ✓ → Job Complete (1/1)
spec:
  completions: 1
completions: 5 (parallelism: 1 — sequential)
P1→✓ P2→✓ P3→✓ P4→✓ P5→✓
5/5 → Job Complete. One at a time.
What if Pod 3 fails?
P1 ✓ P2 ✓ P3 ✗ (exit 1) → P3-retry → P3 ✓ P4 ✓ P5 ✓
Job retries P3 (up to backoffLimit). Then continues to P4, P5. 5/5 Complete.
A failed Pod doesn't count toward completions. The Job creates a replacement. The failure counter increments. If total failures reach backoffLimit (default 6), the Job stops and is marked Failed.
Indexed Completion Mode (v1.24+)
spec:
  completions: 5
  completionMode: Indexed    # Each Pod gets a unique index 0-4
Pod 0 (index=0) Pod 1 (index=1) Pod 2 (index=2) ...

Each Pod has env JOB_COMPLETION_INDEX = 0, 1, 2, 3, 4
Pod hostname: jobname-{index}

Use when each Pod processes a different chunk: "Pod 0 handles rows 0-999, Pod 1 handles 1000-1999, etc."

07 Parallelism — How Many Pods Run Simultaneously ▶

Definition — parallelismThe maximum number of Pods that can run at the same time. Default: 1 (sequential). The Job controller ensures no more than this many Pods are active simultaneously.
parallelism=1
parallelism=3
Dynamic behavior
YAML examples
parallelism: 1 (sequential — default)
completions=5, parallelism=1

T=0: P1 running
T=1: P1 ✓ → P2 running
T=2: P2 ✓ → P3 running
...
T=5: P5 ✓ → Job Complete (5/5)

Total time = 5 × single Pod time. Slowest but simplest.
parallelism: 3 (3 Pods at once)
completions=6, parallelism=3

T=0: P1 P2 P3 (3 running simultaneously)
T=1: P1 ✓ → P4 starts | P2 P3 still running
T=2: P2 ✓ → P5 starts | P3 ✓ → P6 starts
T=3: P4 ✓ P5 ✓ P6 ✓ → Job Complete (6/6)

Total time ≈ 2× single Pod time (3× faster than sequential)
Dynamic behavior — as Pods finish, new ones fill their slot
completions=10, parallelism=4

Active slots: [1] [2] [3] [4]
P1 finishes: [5] [2] [3] [4] ← P5 immediately fills the slot
P3 finishes: [5] [2] [6] [4] ← P6 fills
...
Near end (8 done): [9] [10] [ ] [ ] ← only 2 remaining, 2 slots empty
The Job controller maintains up to parallelism active Pods. When one completes, a new one starts immediately (if needed). Near the end, fewer than parallelism Pods may be running because there's not enough work left.
YAML Examples
# Sequential: 1 at a time, 5 total
completions: 5
parallelism: 1

# Parallel: 3 at a time, 10 total
completions: 10
parallelism: 3

# Max parallel: all 5 at once
completions: 5
parallelism: 5

# Work queue: no fixed count, 4 workers
# (do NOT set completions)
parallelism: 4

09 Backoff Failure Policy ▶

Definition — backoffLimitMaximum number of Pod failures before the Job is considered Failed. Default: 6. The Job controller uses exponential backoff to retry: 10s, 20s, 40s, 80s, 160s, capped at 6 minutes. After backoffLimit failures, the Job stops creating Pods and its condition becomes Failed.
Backoff sequence
restartPolicy effect
YAML examples
Counting rules
Exponential backoff timing
Fail 1 → wait 10s → retry
Fail 2 → wait 20s → retry
Fail 3 → wait 40s → retry
Fail 4 → wait 80s → retry
Fail 5 → wait 160s → retry
Fail 6 → backoffLimit reached! Job FAILED.

Formula: min(10s × 2^(n-1), 360s). Capped at 6 minutes.
How restartPolicy affects counting
restartPolicyOn failureWhat counts as 1 failure
NeverPod stays dead. Job creates NEW Pod.Each failed Pod = 1 failure. Old Pod kept (check logs).
OnFailureKubelet restarts CONTAINER in same Pod.Each container restart = 1 failure. Pod reused.
When to use whichNever = best for debugging (failed Pods kept, logs accessible). OnFailure = best for resource efficiency (reuses Pod, but loses crash logs after restart).
YAML examples
# Default: 6 retries
backoffLimit: 6

# No retries: fail immediately
backoffLimit: 0

# Many retries: 20 attempts
backoffLimit: 20

# With activeDeadlineSeconds as safety net:
backoffLimit: 100
activeDeadlineSeconds: 3600   # Even with 100 retries, kill after 1 hour
What counts toward backoffLimit
EventCounts?
Container exits non-zero (exit 1)Yes
Container OOMKilled (exit 137)Yes
Pod evicted by nodeYes
Container exits 0 (success)No — counts as completion
Image pull errorYes (Pod fails to start)

10 Pod Failure Policy (v1.26+) ▶

Definition — podFailurePolicyAdvanced rules that let you customize how the Job reacts to specific failure types. Instead of blindly retrying all failures, you can say: "If exit code 42, don't retry (FailJob). If exit code 137 (OOM), retry. If disruption, ignore and don't count against backoffLimit."
Why it exists
Actions
Full YAML
Problem with basic backoffLimit
Without podFailurePolicy:
Pod fails with "invalid input" (exit 42) → Job retries 6 times → all fail with same error → wasted 6 Pods

With podFailurePolicy:
Pod fails with exit 42 → rule says FailJob → Job immediately marked Failed — no wasted retries
Three possible actions
ActionMeaningUse when
FailJobImmediately fail entire Job, stop all PodsNon-retryable error (bad input, config error)
IgnoreDon't count this failure against backoffLimitTransient error (node eviction, preemption)
CountNormal behavior — count toward backoffLimitDefault for everything else
Full YAML example
apiVersion: batch/v1
kind: Job
metadata:
  name: smart-job
spec:
  backoffLimit: 6
  podFailurePolicy:
    rules:
    # Rule 1: Exit code 42 = bad input → fail immediately, don't retry
    - action: FailJob
      onExitCodes:
        containerName: worker
        operator: In
        values: [42]
    # Rule 2: Node disruption → ignore, don't count against limit
    - action: Ignore
      onPodConditions:
      - type: DisruptionTarget
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: myapp:v1

11 activeDeadlineSeconds — Job Timeout

DefinitionMaximum time (in seconds) the Job can be active. After this deadline, ALL running Pods are terminated and the Job is marked Failed. Counts from Job creation. Overrides backoffLimit — even if you have retries left, the deadline kills everything.
spec:
  activeDeadlineSeconds: 3600   # Job MUST finish within 1 hour
  backoffLimit: 10             # Can retry 10 times, but deadline wins
Pod running... at 59min → 60min reached → ALL Pods killed!
Job status: Failed (reason: DeadlineExceeded)
SRE Principle

Always set activeDeadlineSeconds on Jobs. Without it, a stuck Job retries forever, wasting cluster resources. The deadline is your safety net.

13 Termination & Cleanup

Key ProblemCompleted/Failed Jobs and their Pods are NOT auto-deleted. They stay forever, cluttering your cluster. You must clean them up manually or use TTL.
# Manual cleanup
kubectl delete job math-job                  # Deletes Job + all its Pods
kubectl delete jobs --field-selector status.successful=1   # Delete all completed Jobs

# See completed Pods (still consuming etcd)
kubectl get pods --field-selector=status.phase=Succeeded
Why Pods are kept

Completed Pods stay so you can check their logs and exit codes. But they consume etcd storage and make kubectl get pods output noisy. Always plan for cleanup.

14 TTL Controller — Automatic Cleanup

Definition — ttlSecondsAfterFinishedAutomatically deletes the Job (and its Pods) a specified number of seconds after the Job finishes (succeeds or fails). Set to 0 to delete immediately after completion.
spec:
  ttlSecondsAfterFinished: 3600   # Delete 1 hour after Job finishes

# Delete immediately after completion:
  ttlSecondsAfterFinished: 0

# Keep forever (default — no auto-cleanup):
# Don't set ttlSecondsAfterFinished
SRE Best Practice

Always set ttlSecondsAfterFinished. Common values: 3600 (1h — enough to check logs) or 86400 (24h). For CronJobs that run frequently, use 0 or 3600 to prevent accumulation of thousands of completed Pods.

Pattern 1 — One-shot Task
completions: 1
parallelism: 1
1 Pod → done ✓
Use for: database backup, migration script, send one email, generate one report.
Pattern 2 — Parallel Batch (fixed count)
completions: 100
parallelism: 10
10 Pods running simultaneously → as one finishes, next starts → until 100 done
Use for: process 100 files, resize 100 images, run 100 test suites.
Pattern 3 — Indexed Job (each Pod gets unique index)
completions: 5
parallelism: 5
completionMode: Indexed
Pod 0 (rows 0-999) Pod 1 (rows 1000-1999) ... Pod 4 (rows 4000-4999)
Use for: shard processing. Each Pod knows its index via JOB_COMPLETION_INDEX env var and processes a unique slice of data.
Pattern 4 — Work Queue
# completions: NOT SET
parallelism: 5
5 Pods all pull from Redis queue → queue empty → one exits 0 → Job stops
Use for: dynamic work: email queue, event processing, message consumption. Requires external queue (Redis, RabbitMQ, SQS).
Pattern 5 — Fan-out / Fan-in
Fan-out: Job 1 (completions:10, parallelism:10) → 10 workers process data

Fan-in: Job 2 (completions:1) → waits for Job 1, aggregates results

Requires external orchestration (Argo Workflows, Tekton) for Job dependencies.

16 Monitoring & Best Practices

MetricAlert When
kube_job_status_failedfailed > 0 (any failure)
kube_job_status_activeactive > 0 for > expectedDuration
kube_job_completeJob didn't complete within SLA
Always set activeDeadlineSeconds

Without it, a stuck Job retries forever. The deadline is your safety net against runaway Jobs.

Always set ttlSecondsAfterFinished

Without it, completed Jobs and Pods accumulate forever, cluttering etcd and kubectl output.

Use restartPolicy: Never for debugging

Failed Pods are kept — you can check their logs. With OnFailure, crash logs are lost on restart.

Set resource requests on Job Pods

Jobs often run batch work that's CPU/memory intensive. Without requests, they may be scheduled on overloaded nodes and OOMKilled.

Use podFailurePolicy for smart retries

Don't waste retries on non-retryable errors. FailJob on bad-input errors. Ignore transient disruptions.
