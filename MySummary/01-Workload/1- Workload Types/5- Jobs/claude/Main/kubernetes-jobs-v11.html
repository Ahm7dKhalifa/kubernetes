1Definitions

1.1 What Is a Job & Why?

Definition — JobA Job creates one or more Pods and ensures that a specified number of them successfully complete (exit code 0). Unlike Deployments (which run forever), Jobs are run-to-completion — they start, do work, and stop. The Job controller tracks successful completions and stops when enough Pods have succeeded.
Definition — Run-to-CompletionA workload pattern where the process starts, performs a finite task, and exits with code 0 (success). Opposite of long-running services (Deployments) that run indefinitely.
Use CaseExample
Batch processingProcess 10,000 images, then stop
Data migrationMove data from MySQL to PostgreSQL
Report generationGenerate monthly PDF report
Database backupDump database to S3, then exit
ETL pipelineExtract, transform, load data
ML trainingTrain model on dataset, save weights
Email sendingSend 5000 notification emails
Cleanup tasksDelete old logs, expired sessions
Analogy

A Deployment is a restaurant — open all day, continuously serving. A Job is a catering order — prepare 100 meals, deliver them, done. You don't keep the kitchen running after the order is fulfilled.

4Architecture & Workflow

4.1 The question behind every pattern: who tells a Pod what to work on?

The one fact that clears up the confusionIn the default NonIndexed mode every Pod of a Job is an identical clone: same image, same command, same env. Nothing in Kubernetes tells Pod 7 that it is "Pod 7". completions: 100 is a counter of exit-0s, not a list of work. So the only ways for a Pod to know its work are A (ask Kubernetes for an index, which needs Indexed mode), B (ask a shared coordinator), or C (bake the work into the spec).

4.2 "I need to process 100 files": how does each Pod know its files?

Your question

You guessed right. With completions: 100, parallelism: 10 in NonIndexed mode, Kubernetes gives each Pod nothing. Which file a Pod processes depends entirely on your code and on the source it pulls from. The usual source is a database table where each Pod atomically marks one pending row as processing (FOR UPDATE SKIP LOCKED), so no two Pods ever get the same file. That's Pattern ③.

That pattern is really a work queue with an extra constraint, though: the number of successful exits must equal the number of rows. In real projects, 100 known files is usually better served by Indexed, and an unknown or growing set by a work queue:

Usually the best fit

Indexed: Kubernetes hands out numbers

completions: 10 · parallelism: 5 · Indexed
# Pod with JOB_COMPLETION_INDEX=3
start=$((JOB_COMPLETION_INDEX*10+1))   # 31
sed -n "${start},$((start+9))p" files.txt
# → menu-0031.jpg … menu-0040.jpg
Use when the list is known and frozen at creation. No coordinator is needed, a retried Pod redoes the same 10 files, and failedIndexes tells you which slice broke. → Pattern ④
Dynamic

Work queue: the queue hands out files

completions: unset · parallelism: 10
# every Pod loops
f=$(redis-cli LMOVE files:queue \
      files:processing:$POD LEFT RIGHT)
# empty AND nothing in flight → exit 0
Use when files keep arriving or their cost varies a lot (5 KB vs 50 MB). Fast Pods simply take more files. → Pattern ⑤
Your idea

Claim: the DB hands out files

completions: 100 · parallelism: 10 · NonIndexed
UPDATE files SET status='processing',
  claimed_by=:pod, lease_until=now()+'45s'
WHERE id = (SELECT id FROM files
  WHERE status='pending' ORDER BY id
  LIMIT 1 FOR UPDATE SKIP LOCKED)
RETURNING id, path;
Use when you want one Pod per file and you already track files in a table. You need a lease, a fencing check, and completions = rows. → Pattern ③
Freeze the list
Never run aws s3 ls inside each Pod to work out its slice. The bucket can change between Pod 0 starting and Pod 9 starting, which shifts every slice, so files get skipped or done twice. Write a manifest (a ConfigMap, or an S3 object named with the run id) when you create the Job, and have every Pod and every retry read that same snapshot.

5.1 Full Job YAML — Every Field Explained

apiVersion: batch/v1                 # Jobs are in batch API group
kind: Job
metadata:
  name: data-migration
spec:
  completions: 5                     # Total successful Pods needed (default 1)
  parallelism: 2                     # Max concurrent Pods (default 1)
  backoffLimit: 6                    # Retries allowed; Job fails on failure #7 (default 6)
  activeDeadlineSeconds: 3600        # Max total runtime — 1 hour, then Job killed
  ttlSecondsAfterFinished: 86400     # Auto-delete Job 24h after completion
  completionMode: Indexed            # Indexed or NonIndexed (default)
  suspend: false                     # true = Job is paused (deadline timer also paused)
  podReplacementPolicy: Failed       # Wait for terminating Pods before replacing (default TerminatingOrFailed)

  template:                            # Pod template — same as in Deployments
    spec:
      restartPolicy: Never            # MUST be Never or OnFailure (not Always!)
      containers:
      - name: worker
        image: python:3.11
        command: ["python", "migrate.py"]
        resources:
          requests: { cpu: "500m", memory: "256Mi" }
          limits: { cpu: "1", memory: "512Mi" }
        env:
        - name: DB_HOST
          value: "mysql.default.svc"
restartPolicy Rules for JobsAlways is forbidden for Jobs (that's for Deployments). You must use:
Never — failed Pod stays dead, Job controller creates a NEW Pod. Best for debugging (you can inspect the failed Pod's logs).
OnFailure — kubelet restarts the failed CONTAINER inside the same Pod. Pod stays, container retries. Fewer Pod objects; the previous crash is still readable with kubectl logs <pod> --previous, but once backoffLimit is hit the Pod is deleted and those logs go with it. podFailurePolicy and backoffLimitPerIndex require Never.

6.1 Completions — How Many Pods Must Succeed ▶

Definition — completionsThe total number of Pods that must successfully complete (exit 0) for the Job to be considered done. Default: 1. The Job tracks succeeded count and stops when it reaches completions.
What · completions

How many Pods must exit 0 before the Job is Complete. Default 1. It is a counter of successes, not a list of work. Kubernetes never tells a Pod which unit of work it represents (unless you add completionMode: Indexed).

Why · needs
  • A clear definition of "done" for finite work, which Deployments don't have
  • Saying "this work needs N successful units" declaratively, without a babysitting script
  • Keep going through failures until the required successes are reached
Why · problems without it
  • A bare Pod that fails is simply gone, and nobody retries it
  • A Deployment restarts finished work forever: a nightly settlement would re-run in a loop
  • Without a counter you write external scripts to count successes and decide when to stop
◎Why · goals & principles
Goals
  • A clear, machine-checkable definition of "done" for finite work
  • Reach the required amount of successful work despite individual Pod failures
  • Stop automatically once enough work has succeeded, with no babysitting
Principles
  1. Kubernetes counts exits; your code decides what each exit means
  2. Keep "1 exit = 1 unit of work" true. Otherwise the count lies: the Job finishes with work left, or never finishes
  3. Make every unit idempotent, because retries and lease expiry can run a unit twice
  4. If you can't know the count up front, don't invent one: leave it unset (work queue)
How · values as solutions

What · completionMode

Whether a Job's Pods are interchangeable (NonIndexed, default) or each owns a fixed index 0 … completions-1 (Indexed), injected as JOB_COMPLETION_INDEX, an annotation, and the hostname <job>-<index>.

Why · needs
  • Split known work deterministically with no coordinator
  • A retry should redo the same slice, not "whatever is next"
  • Know exactly which slice failed
  • Peers sometimes need to find each other (leader/worker, MPI-style)
Why · problems without it
  • NonIndexed Pods can't tell themselves apart, so you need a DB claim or a queue just to split work
  • Retries pick a different item, so a failure is hard to attribute
  • Status only says "3 failed", not "shard 7 failed"
◎Why · goals & principles
Goals
  • Deterministic split of known work, with no coordinator
  • Retries that redo the same slice
  • Failures you can name: "index 7 failed"
Principles
  1. The index is the assignment
  2. The index → work mapping must be pure and stable: same index, same input, every attempt (freeze the manifest)
  3. Count-dependent config (SHARDS, CITIES) must equal completions. Guard it and fail fast with a dedicated exit code
  4. Use more small shards than parallelism to absorb skew

6.2 Parallelism — How Many Pods Run Simultaneously ▶

Definition — parallelismThe maximum number of Pods that can run at the same time. Default: 1 (sequential). The Job controller ensures no more than this many Pods are active simultaneously.
What · parallelism

The maximum number of Pods running at the same time. Default 1. The controller keeps up to this many slots busy and refills a slot as soon as a Pod ends. It is mutable on a running Job.

Why · needs
  • Finish big batches faster
  • …while protecting dependencies: PostgreSQL connection limits, Elasticsearch bulk queues, rate-limited APIs (ZATCA)
  • Fit inside the namespace's quota and the nodes' free capacity
Why · problems without it
  • Too low: 20 PDFs × 8 s run strictly one after another and miss the finance cut-off
  • Too high: a thundering herd. max_connections is exhausted, ES returns 429s, Pending Pods eat quota, and the Orders API on the same nodes gets noisy neighbours
◎Why · goals & principles
Goals
  • Finish within the time budget
  • Never overload shared dependencies (PostgreSQL, Elasticsearch, partner APIs)
  • Stay inside quota and node capacity
Principles
  1. A throttle, not a work splitter: it decides how many run, never who does what
  2. Size it from the weakest dependency, e.g. DB max_connections ÷ connections per Pod, not from cluster size
  3. Change it live (patch) instead of recreating the Job
  4. Pending Pods are a signal: lower parallelism or raise quota

6.3 Backoff Failure Policy ▶

Definition — backoffLimitNumber of retries allowed before the Job is considered Failed. Default: 6. The Job fails when the failure count exceeds the limit — so backoffLimit: 6 allows 7 attempts and fails on the 7th failure; backoffLimit: 0 fails on the first. Retries use exponential backoff: 10s, 20s, 40s… capped at 6 minutes. The Job then stops creating Pods, terminates running ones, and gets condition Failed (reason BackoffLimitExceeded).
What · backoffLimit

How many retries a Job gets before it is marked Failed (default 6, so it fails on the 7th failure). Retries are spaced with exponential backoff: 10 s, 20 s, 40 s … capped at 6 min.

Why · needs
  • Survive transient failures: a PostgreSQL failover, a DNS blip, a lost node
  • But stop eventually and surface the error to alerting
  • Don't hammer a dependency that is trying to recover
Why · problems without it
  • No retry: a 2-second DB failover at 02:00 fails the nightly settlement
  • Unlimited retry: a real bug loops forever, burns CPU, floods logs and hides the incident
  • Immediate retry: a retry storm against a database that is still restarting
◎Why · goals & principles
Goals
  • Recover automatically from transient failures
  • Surface permanent failures quickly to on-call
  • Protect dependencies that are recovering
Principles
  1. Retry transient failures, fail permanent ones, and always keep it bounded
  2. Retries are only safe when the work is idempotent
  3. Match the budget to the cost of a failure: fail fast for migrations, tolerate more for flaky I/O
  4. It doesn't stop hangs, so bound time too with activeDeadlineSeconds

6.4 Pod Failure Policy GA v1.31 ▶

Definition — podFailurePolicyAdvanced rules that let you customize how the Job reacts to specific failure types. Instead of blindly retrying all failures, you can say: "If exit code 42, don't retry (FailJob). If exit code 137 (OOM), retry. If disruption, ignore and don't count against backoffLimit."
What · podFailurePolicy

An ordered list of rules that classifies a Pod failure by exit code or Pod condition and picks an action: FailJob, Ignore, Count or FailIndex. The first matching rule wins.

Why · needs
  • React to why a Pod failed, not just that it failed
  • Tell a bug or bad input apart from an infrastructure disruption
  • Keep cluster maintenance (node rotation, preemption) from failing healthy Jobs
Why · problems without it
  • backoffLimit treats every failure the same: bad input is retried 7 times and the alert arrives ~10 min late
  • EKS node rotation during an upgrade drains nodes, and those evictions burn the retry budget until a healthy Job fails
  • Configuration errors (wrong SHARDS) retry pointlessly
◎Why · goals & principles
Goals
  • Spend retries only on failures retries can fix
  • Don't let cluster maintenance fail healthy Jobs
  • Fail immediately and loudly on non-retryable errors
Principles
  1. Classify the failure, then decide
  2. Exit codes are an API: define and document them in the worker (e.g. 2 = config, 42 = bad data)
  3. Order matters: specific rules first, because the first match wins
  4. Ignore disruptions, never application errors

        operator: In

    - action: Ignore
      onPodConditions:
      - type: DisruptionTarget

      restartPolicy: Never
      containers:
      - name: worker
        image: myapp:v1

Three newer Job fields that matter for Indexed Jobs at scale. All are stable in current Kubernetes releases (check your cluster with kubectl version).

What · backoffLimitPerIndex · maxFailedIndexes

A separate retry budget for every index of an Indexed Job, plus maxFailedIndexes as a ceiling on how many indexes may fail before the whole Job stops.

Why · needs
  • One bad shard must not kill 99 good ones
  • Know exactly which slices to re-run
  • Still stop early when the data is broken everywhere
Why · problems without it
  • With a shared backoffLimit, shard 7's corrupt row consumes every retry. The whole reindex fails, healthy shards are stopped mid-way, and you re-run everything
◎Why · goals & principles
Goals
  • Contain a bad shard
  • Finish every healthy shard
  • An exact list of what to re-run
Principles
  1. Isolate failure per shard, and make it visible
  2. Give up early when failures are systemic (maxFailedIndexes)
  3. Re-run only failedIndexes, from the same frozen manifest

6.6 activeDeadlineSeconds — Job Timeout

DefinitionMaximum time (in seconds) the Job can be active. After this deadline, ALL running Pods are terminated and the Job is marked Failed. Counts from when the Job starts (status.startTime) and is reset if you suspend/resume it. Takes precedence over backoffLimit — even if you have retries left, the deadline kills everything.
What · activeDeadlineSeconds

A wall-clock budget for the whole Job, counted from status.startTime (reset by suspend and resume). When it expires, every Pod is terminated and the Job fails with DeadlineExceeded, even if retries remain.

Why · needs
  • Business deadlines: settlement must finish before the 06:00 finance cut-off
  • Free cluster resources held by stuck work
  • Turn "silently stuck" into a visible, alertable failure
Why · problems without it
  • backoffLimit only bounds failures. A Pod waiting on a DB lock, an HTTP call with no timeout, or an image stuck in ImagePullBackOff never fails, so the Job runs forever
  • A stuck Job can block the next CronJob run (concurrencyPolicy: Forbid) and hold locks
◎Why · goals & principles
Goals
  • Bound wall-clock time
  • Turn hangs into visible failures
  • Release resources and locks
Principles
  1. Every Job needs a wall-clock budget
  2. Derive it from the SLA and p95 runtime (a common rule: 2–3× p95)
  3. Job-level bounds the whole run; Pod-level bounds each attempt. Use both for calls that sometimes hang
  4. A deadline failure should page: alert on reason DeadlineExceeded
How · values as solutions
ValueBehaviourSolvesJahez example
unsetNo time boundNothing; avoid in production—
activeDeadlineSeconds: 60010 min for the whole JobMigrations that might wait on locksOrders API pre-upgrade hook

spec:
  activeDeadlineSeconds: 3600   # Job MUST finish within 1 hour
  backoffLimit: 10             # Can retry 10 times, but deadline wins
Pod running... at 59min → 60min reached → ALL Pods killed!
Job status: Failed (reason: DeadlineExceeded)
SRE Principle

Always set activeDeadlineSeconds on Jobs. backoffLimit only bounds failures; it does nothing for a Pod that hangs, runs forever, or sits Pending on a bad image. The deadline is the only bound on wall-clock time.

Don't confuse the two
spec.activeDeadlineSeconds (Job) kills the whole Job. spec.template.spec.activeDeadlineSeconds (Pod) limits each individual Pod — a timed-out Pod then counts as one failure and gets retried.

6.7 TTL Controller — Automatic Cleanup

Definition — ttlSecondsAfterFinishedAutomatically deletes the Job (and its Pods) a specified number of seconds after the Job finishes (succeeds or fails). Set to 0 to delete immediately after completion.
What · ttlSecondsAfterFinished

The TTL controller deletes a finished Job (Complete or Failed) and, by cascade, its Pods, N seconds after it finishes.

Why · needs
  • Keep the evidence (Pods, logs, status) long enough to debug
  • Then clean up automatically, with no manual kubectl delete
Why · problems without it
  • Never cleaned: Jobs created directly (one per file, per deploy, per tenant) pile up by the thousand. etcd grows and kubectl get pods drowns in Completed Pods
  • Deleted too early: the failed Pod's logs are gone before on-call looks at them
◎Why · goals & principles
Goals
  • Keep evidence long enough to debug
  • Keep the cluster clean automatically
Principles
  1. Ship the logs out, then let the cluster forget
  2. Pick the TTL from how long an investigation takes: 24 h in prod, 1 h in dev
  3. Never use Pods as your log store
  4. For CronJob children, the history limits are the count-based equivalent

Always set ttlSecondsAfterFinished. Common values: 3600 (1h — enough to check logs) or 86400 (24h). For CronJobs that run frequently, use 0 or 3600 to prevent accumulation of thousands of completed Pods.

①

One-shot: one Pod, one unit of work

The Pod does everything, and ordering lives inside your code. At Jahez: EF Core migrations for the Orders API, run as a Helm pre-upgrade hook.

  • Schema migrations before a rollout (Helm pre-upgrade hook / Argo CD PreSync)
  • Elasticsearch alias swap after a reindex (restaurants → restaurants-v2)

Avoid when

  • The work is big and splittable. One Pod failing at 90% restarts at 0 unless you checkpoint, so go to ④

②

Sequential: fixed count, one Pod at a time

Kubernetes guarantees at most one running Pod, and nothing about which item it handles. Each Pod claims the next row. At Jahez: submitting e-invoices to ZATCA under a strict rate limit.

completions: 6parallelism: 1NonIndexedwork source: row claim (FIFO by id)
YAML & code → §9.2
What you're watchingOnly one slot exists. The 3rd Pod crashes while holding INV-00003, and the row stays processing with a lease countdown. After backoff the replacement Pod starts, finds nothing claimable, and polls until the lease expires. Then it re-claims the same invoice. 6 exits = 6 invoices.
Honest takeThis pattern is less common than it looks. If all you need is "one at a time", a one-shot Pod that loops over the rows is simpler and faster, because you skip 2–5 s of Pod start-up per item. Choose ② when you want each item in a fresh Pod: per-item logs, per-item retry and backoff, and a clean process every time.

Use it for

  • A downstream that allows only one concurrent caller: ZATCA submission, a payment gateway's settlement-file upload, a partner SFTP that allows one session
  • Work that leaks memory or needs clean state per item, e.g. headless Chrome PDF rendering
  • Running the same test N times (soak / flakiness checks): completions: 50, parallelism: 1

Avoid when

  • You need a strict order with gaps handled. Use one-shot, or Indexed + parallelism: 1 (the controller fills the lowest pending index first in practice, but strict ordering isn't a documented guarantee)
  • Items are tiny. Pod overhead dominates

Beat the straggler

⑤

Work queue: completions unset, workers drain a queue

A "free delivery tonight" push campaign across 60 user segments, 4 workers. Nobody knows the total in advance, and each worker loops until the queue is drained and nothing is in flight.

YAML & code → §9.2
What you're watchingItems have uneven sizes, so fast workers simply take more. Pod #2 crashes holding an item, which stays orphaned in its processing list until its heartbeat key expires. Because no Pod has succeeded yet, the controller replaces the crashed Pod. When the queue runs dry, workers wait instead of exiting, and one of them reaps the orphan. The first exit 0 means no new Pods. The Job completes once every Pod has ended.
The exit rule (Kubernetes docs, paraphrased)Once any Pod exits 0, no new Pods are created, and the Job is Complete when every Pod has ended. So a worker must exit 0 only when the whole job is done (queue empty and nothing in flight), not when it happens to see an empty queue. Otherwise the last crash goes unrecovered.

    #!/bin/sh
    # NonIndexed worker: ONE Pod = ONE row.
    # Kubernetes gives every Pod the same command and env and only counts exit codes.
    # THIS script decides which row a Pod gets, using an atomic claim in PostgreSQL.
    #   exit 0 -> processed exactly one row, OR nothing is left (keeps successes == rows)
    #   exit 1 -> crashed or lost its lease (must NOT be counted as a completion)
    set -u
    POD="${POD_NAME:-$(hostname)}"

    claim() {
    psql -v ON_ERROR_STOP=1 -tAq -v tbl="$WORK_TABLE" -v pod="$POD" -v lease="$LEASE_SECONDS" <<'SQL'
    WITH next AS (
      SELECT id FROM :"tbl"
      WHERE status = 'pending'
         OR (status = 'processing' AND lease_until < now())   -- re-claim rows of dead Pods
      ORDER BY id
      LIMIT 1
      FOR UPDATE SKIP LOCKED                                   -- concurrent Pods never get the same row
    )
    UPDATE :"tbl" AS t
    SET status      = 'processing',
        claimed_by  = :'pod',
        lease_until = now() + make_interval(secs => :lease),
        attempts    = t.attempts + 1
    FROM next
    WHERE t.id = next.id
    RETURNING t.id, t.payload;
    SQL
    }

    remaining() {
    psql -v ON_ERROR_STOP=1 -tAq -v tbl="$WORK_TABLE" <<'SQL'
    SELECT count(*) FROM :"tbl" WHERE status <> 'done';
    SQL
    }

    mark_done() {
    psql -v ON_ERROR_STOP=1 -tAq -v tbl="$WORK_TABLE" -v pod="$POD" -v id="$1" <<'SQL'
    UPDATE :"tbl"
    SET status = 'done', done_at = now(), lease_until = NULL
    WHERE id = :id AND claimed_by = :'pod' AND status = 'processing'   -- fencing: only the current owner
    RETURNING id;
    SQL
    }

    while :; do
      row="$(claim)" || { echo "$POD: database error while claiming"; exit 1; }
      [ -n "$row" ] && break
      left="$(remaining)" || exit 1
      if [ "$left" = "0" ]; then
        echo "$POD: nothing left to claim, exit 0 (still counts as one completion)"
        exit 0
      fi
      echo "$POD: $left row(s) not done but all leased by other Pods, polling"
      sleep 5
    done

    id="${row%%|*}"
    payload="${row#*|}"
    echo "$POD: claimed #$id ($payload)"

    # ---- the real work goes here: render the PDF, call ZATCA, upload to S3 ----
    sleep "$WORK_SECONDS"

    roll=$(( $(od -An -N1 -tu1 /dev/urandom) * 100 / 256 ))
    if [ "$roll" -lt "${CRASH_PERCENT:-0}" ]; then
      echo "$POD: DEMO crash while holding #$id, row stays 'processing' until its lease expires"
      exit 1

      echo "$POD: lost the lease on #$id (another Pod re-claimed it), exit 1 so it is not counted twice"

    echo "$POD: #$id done, exit 0"

// Jahez.Lab.ClaimWorker — NonIndexed Job worker: ONE Pod = ONE claimed row.
// Kubernetes gives every Pod the same image, command and env, and only counts exit codes.
// Which row a Pod gets is decided HERE, by an atomic claim in PostgreSQL.
//   exit 0   -> processed exactly one row, or nothing is left (keeps successes == rows)
//   exit 1   -> lost the lease: must NOT count as a completion
//   exit 143 -> SIGTERM (deadline / Job deleted): row handed back immediately
using System.Runtime.InteropServices;
using System.Text.RegularExpressions;
using Npgsql;

var table = Env("WORK_TABLE");
if (!Regex.IsMatch(table, "^[a-z_][a-z0-9_]*$"))
    throw new ArgumentException($"Unsafe table name: {table}");
var pod = Environment.GetEnvironmentVariable("POD_NAME") ?? Environment.MachineName;
var lease = TimeSpan.FromSeconds(int.Parse(Environment.GetEnvironmentVariable("LEASE_SECONDS") ?? "60"));
var workTime = TimeSpan.FromSeconds(int.Parse(Environment.GetEnvironmentVariable("WORK_SECONDS") ?? "8"));

using var cts = new CancellationTokenSource();
using var sigterm = PosixSignalRegistration.Create(PosixSignal.SIGTERM, ctx => { ctx.Cancel = true; cts.Cancel(); });
var ct = cts.Token;

await using var db = NpgsqlDataSource.Create(Env("ConnectionStrings__Lab"));

try
{
    while (true)
    {
        var item = await TryClaimAsync();
        if (item is { } claimed)
        {
            Console.WriteLine($"{pod}: claimed #{claimed.Id} ({claimed.Payload})");
            try
            {
                await ProcessAsync(claimed.Payload, ct);
            }
            catch (OperationCanceledException)
            {
                await ReleaseAsync(claimed.Id);
                Console.WriteLine($"{pod}: SIGTERM, released #{claimed.Id} back to 'pending'");
                return 143;
            }

            if (!await MarkDoneAsync(claimed.Id))
            {
                Console.Error.WriteLine($"{pod}: lost the lease on #{claimed.Id}, exit 1 so it is not counted twice");
                return 1;
            }
            Console.WriteLine($"{pod}: #{claimed.Id} done, exit 0");
            return 0;
        }

        var left = await RemainingAsync();
        if (left == 0)
        {
            Console.WriteLine($"{pod}: nothing left to claim, exit 0 (still counts as one completion)");
            return 0;
        }
        Console.WriteLine($"{pod}: {left} row(s) not done but all leased by other Pods, polling");
        await Task.Delay(TimeSpan.FromSeconds(5), ct);
    }
}
catch (OperationCanceledException)
{
    Console.WriteLine($"{pod}: SIGTERM while idle");
    return 143;
}

async Task<(long Id, string Payload)?> TryClaimAsync()
{
    await using var cmd = db.CreateCommand($"""
        WITH next AS (
          SELECT id FROM {table}
          WHERE status = 'pending'
             OR (status = 'processing' AND lease_until < now())
          ORDER BY id
          LIMIT 1
          FOR UPDATE SKIP LOCKED
        )
        UPDATE {table} AS t
        SET status = 'processing', claimed_by = @pod,
            lease_until = now() + @lease, attempts = t.attempts + 1
        FROM next
        WHERE t.id = next.id
        RETURNING t.id, t.payload
        """);
    cmd.Parameters.AddWithValue("pod", pod);
    cmd.Parameters.AddWithValue("lease", lease);
    await using var reader = await cmd.ExecuteReaderAsync(ct);
    if (!await reader.ReadAsync(ct)) return null;
    return (reader.GetInt64(0), reader.GetString(1));
}

async Task<long> RemainingAsync()
{
    await using var cmd = db.CreateCommand($"SELECT count(*) FROM {table} WHERE status <> 'done'");
    return (long)(await cmd.ExecuteScalarAsync(ct))!;
}

async Task<bool> MarkDoneAsync(long id)
{
    // Fencing: only the Pod that still owns the row may complete it.
    await using var cmd = db.CreateCommand($"""
        UPDATE {table}
        SET status = 'done', done_at = now(), lease_until = NULL
        WHERE id = @id AND claimed_by = @pod AND status = 'processing'
        """);
    cmd.Parameters.AddWithValue("id", id);
    cmd.Parameters.AddWithValue("pod", pod);
    return await cmd.ExecuteNonQueryAsync(CancellationToken.None) == 1;
}

async Task ReleaseAsync(long id)
{
    await using var cmd = db.CreateCommand($"""
        UPDATE {table}
        SET status = 'pending', claimed_by = NULL, lease_until = NULL
        WHERE id = @id AND claimed_by = @pod AND status = 'processing'
        """);
    cmd.Parameters.AddWithValue("id", id);
    cmd.Parameters.AddWithValue("pod", pod);
    await cmd.ExecuteNonQueryAsync(CancellationToken.None);
}

async Task ProcessAsync(string payload, CancellationToken token)
{
    // Real work goes here: render the settlement PDF, upload it to S3, email the vendor.
    // Keep it idempotent (same payload -> same object key), because a lease can expire and a
    // second Pod can redo the same row.
    await Task.Delay(workTime, token);
}

// Jahez.Lab.QueueWorker — work-queue Job worker (spec.completions UNSET).
// Loops: LMOVE the next item into notif:processing:<pod>, send it, LREM it.
// Exits 0 only when the queue is drained AND no peer still holds an item, because once
// any Pod exits 0 Kubernetes creates no new Pods for this Job.
using System.Runtime.InteropServices;
using StackExchange.Redis;

const string Queue = "notif:queue";
const string ProcessingPattern = "notif:processing:*";
var pod = Environment.GetEnvironmentVariable("POD_NAME") ?? Environment.MachineName;
var aliveTtl = TimeSpan.FromSeconds(int.Parse(Environment.GetEnvironmentVariable("ALIVE_TTL") ?? "20"));
var workTime = TimeSpan.FromSeconds(double.Parse(Environment.GetEnvironmentVariable("WORK_SECONDS") ?? "2"));
RedisKey mine = $"notif:processing:{pod}";
RedisKey alive = $"notif:alive:{pod}";

using var sigterm = PosixSignalRegistration.Create(PosixSignal.SIGTERM, ctx => { ctx.Cancel = true; cts.Cancel(); });
var ct = cts.Token;

var server = redis.GetServer(redis.GetEndPoints()[0]);
var sent = 0;
var waitingLogged = false;

try
{
    while (true)
    {
        await db.StringSetAsync(alive, "1", aliveTtl);           // heartbeat
        var item = await db.ListMoveAsync(Queue, mine, ListSide.Left, ListSide.Right);
        if (item.IsNull)
        {
            await ReapAsync();
            if (await db.ListLengthAsync(Queue) > 0) continue;
            if (await OthersBusyAsync())
            {
                if (!waitingLogged) Console.WriteLine($"{pod}: queue empty, peers still working, waiting");
                waitingLogged = true;
                await Task.Delay(TimeSpan.FromSeconds(3), ct);
                continue;
            }
            Console.WriteLine($"{pod}: queue drained and nothing in flight, sent {sent}, exit 0");
            return 0;
        }

        waitingLogged = false;
        Console.WriteLine($"{pod}: sending {item}");
        await SendPushAsync(item.ToString(), ct);
        await db.ListRemoveAsync(mine, item, 1);
        await db.StringIncrementAsync("notif:sent");
        sent++;
    }
}

    while (!(await db.ListMoveAsync(mine, Queue, ListSide.Right, ListSide.Left)).IsNull) { }
    await db.KeyDeleteAsync(alive);
    Console.WriteLine($"{pod}: SIGTERM, in-flight item requeued, sent {sent}");
    return 143;
}

async Task ReapAsync()
{
    // Requeue items held by workers whose heartbeat key has expired (dead Pods).
    await foreach (var key in server.KeysAsync(pattern: ProcessingPattern))
    {
        var owner = key.ToString()["notif:processing:".Length..];
        if (owner == pod) continue;
        if (await db.KeyExistsAsync($"notif:alive:{owner}")) continue;
        var moved = 0;
        while (!(await db.ListMoveAsync(key, Queue, ListSide.Right, ListSide.Left)).IsNull) moved++;
        if (moved > 0) Console.WriteLine($"{pod}: requeued {moved} orphaned item(s) from dead worker {owner}");
    }
}

async Task<bool> OthersBusyAsync()
{
    await foreach (var key in server.KeysAsync(pattern: ProcessingPattern))
        if (key != mine) return true;
    return false;
}

    // Real work: call FCM / APNs for this user segment. Delivery is at-least-once
    // (a crash after sending but before LREM re-sends), so use a collapse key /

#

#   kubectl apply -f 06-fan-out-fan-in.yaml -l lab-step=seed

#   kubectl -n jobs-lab exec deploy/postgres -- psql -U lab -d jahez_lab -c "TABLE city_stats_partial"
#   kubectl -n jobs-lab logs job/city-stats-reduce -c reduce
# Re-run:
#   kubectl -n jobs-lab delete job city-stats-map city-stats-reduce city-stats-seed --ignore-not-found

    # Fan-out: index i -> i-th city in CITIES. Writes ONE partial row per city.
    set -eu
    IDX="$JOB_COMPLETION_INDEX"
    CITY="$(echo "$CITIES" | cut -d' ' -f"$((IDX + 1))")"

      echo "no city for index $IDX: CITIES has fewer entries than spec.completions"
      exit 2
    fi

    psql -v ON_ERROR_STOP=1 -tAq -v run="$RUN_ID" -v city="$CITY" -v pod="$POD_NAME" <<'SQL'
    INSERT INTO city_stats_partial (run_id, city, orders, gmv, avg_basket, computed_by, computed_at)
    SELECT :'run', :'city', count(*), coalesce(sum(amount), 0), coalesce(round(avg(amount), 2), 0), :'pod', now()
    FROM orders
    WHERE city = :'city' AND created_at >= current_date AND created_at < current_date + 1
    ON CONFLICT (run_id, city) DO UPDATE
      SET orders = EXCLUDED.orders, gmv = EXCLUDED.gmv, avg_basket = EXCLUDED.avg_basket,
          computed_by = EXCLUDED.computed_by, computed_at = EXCLUDED.computed_at;
    SELECT city || ': ' || orders || ' orders, GMV ' || gmv || ' SAR, avg basket ' || avg_basket
    FROM city_stats_partial WHERE run_id = :'run' AND city = :'city';
    SQL
  wait-partials.sh: |
    #!/bin/sh
    # Fan-in barrier (initContainer): block until every map index has written its partial.
    set -u
    count() {
    psql -tAq -v run="$RUN_ID" <<'SQL'
    SELECT count(*) FROM city_stats_partial WHERE run_id = :'run';
    SQL
    }
    while :; do
      n="$(count 2>/dev/null || echo 0)"
      if [ "$n" = "$EXPECTED_PARTIALS" ]; then
        echo "barrier open: $n/$EXPECTED_PARTIALS partials present for $RUN_ID"
        exit 0
      fi
      echo "fan-in barrier: $n/$EXPECTED_PARTIALS partials for $RUN_ID, waiting"
      sleep 5
    done
  reduce.sh: |
    #!/bin/sh
    # Fan-in: combine the per-city partials into one daily row.
    set -eu
    psql -v ON_ERROR_STOP=1 -tAq -v run="$RUN_ID" <<'SQL'
    INSERT INTO daily_stats (run_id, stat_date, orders, gmv, top_city, cities)
    SELECT :'run', current_date, sum(orders), sum(gmv),
           (array_agg(city ORDER BY gmv DESC))[1], count(*)
    FROM city_stats_partial
    WHERE run_id = :'run'
    ON CONFLICT (run_id) DO UPDATE
      SET orders = EXCLUDED.orders, gmv = EXCLUDED.gmv,
          top_city = EXCLUDED.top_city, cities = EXCLUDED.cities;
    SELECT 'run ' || run_id || ' | ' || stat_date || ' | ' || orders || ' orders | GMV ' || gmv
           || ' SAR | top city ' || top_city || ' | ' || cities || ' cities'
    FROM daily_stats WHERE run_id = :'run';
    SQL

#!/usr/bin/env bash
# run-city-stats.sh — orchestrate Pattern 6 from CI (GitLab/GitHub Actions/Jenkins) instead of
# relying only on the initContainer barrier: map first, check it really Completed, then reduce.
# Usage: ./run-city-stats.sh [path/to/06-fan-out-fan-in.yaml]
set -euo pipefail
NS=jobs-lab
FILE="${1:-06-fan-out-fan-in.yaml}"
RUN_ID="run-$(date -u +%Y%m%d-%H%M%S)"
render() { sed "s/demo-run-1/${RUN_ID}/g" "$FILE"; }

job_state() {   # prints Complete / Failed / "" for a Job
  kubectl -n "$NS" get job "$1" -o jsonpath='{.status.conditions[?(@.status=="True")].type}' 2>/dev/null \
    | tr ' ' '\n' | grep -E '^(Complete|Failed)$' | head -1 || true
}

wait_job() {    # wait_job <name> <timeout-seconds>
  local name="$1" deadline=$((SECONDS + $2)) state=""
  while [ $SECONDS -lt $deadline ]; do
    state="$(job_state "$name")"
    if [ -n "$state" ]; then echo "$name: $state"; [ "$state" = "Complete" ]; return; fi
    sleep 5
  done
  echo "$name: timed out after $2s"; return 1
}
