1.1 Definitions

What Is a CronJob & Why?

Definition — CronJobA CronJob creates Jobs on a time-based schedule. It's like a cron daemon in Linux but for Kubernetes. At each scheduled time, the CronJob controller creates a new Job object, which creates Pods that run to completion. The CronJob is the scheduler; the Job is the execution; the Pod does the work.
Definition — Three-Level ChainCronJob → Job → Pod. CronJob creates Jobs on schedule. Each Job creates one or more Pods. Pods run the actual command and exit. After completion, Jobs and Pods are kept (for logs) until cleanup.
Use CaseScheduleExample
Database backupDaily 2 AM0 2 * * *
Log rotationHourly0 * * * *
Report generationMonday 9 AM0 9 * * 1
Cache cleanupEvery 15 min*/15 * * * *
SSL cert renewalMonthly 1st0 0 1 * *
Health check pingEvery 5 min*/5 * * * *
ETL data syncNightly midnight0 0 * * *
Invoice generationLast day of month0 0 28-31 * *
Analogy

A CronJob is an alarm clock. At the set time, it rings (creates a Job). The Job does the task (Pod runs). When done, the alarm resets and waits for the next scheduled time. If the alarm is snoozed (suspended), it doesn't ring until un-snoozed.

2.1 The Full YAML

Full CronJob YAML — Every Field Explained

apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
  namespace: production
spec:
  schedule: "30 2 * * *"              # When — daily at 2:30 AM
  timeZone: "UTC"                     # Timezone (default: controller's TZ)
  concurrencyPolicy: Forbid           # What if previous still running?
  startingDeadlineSeconds: 200        # Max seconds late to still start
  suspend: false                      # true = pause scheduling
  successfulJobsHistoryLimit: 3       # Keep last 3 successful Jobs
  failedJobsHistoryLimit: 1           # Keep last 1 failed Job

  jobTemplate:                          # Job spec — same as a regular Job
    spec:
      backoffLimit: 3                  # Retries per Job run
      activeDeadlineSeconds: 1800      # Max 30 min per Job run
      ttlSecondsAfterFinished: 86400  # Auto-delete Job 24h after finish
      template:                        # Pod spec — same as always
        spec:
          restartPolicy: Never        # Never or OnFailure (not Always!)
          containers:
          - name: backup
            image: postgres:16
            command: ["sh","-c","pg_dump mydb > /backup/dump.sql"]
            resources:
              requests: { cpu: "200m", memory: "256Mi" }
              limits: { cpu: "500m", memory: "512Mi" }
Key StructureCronJob has a jobTemplate (not template). Inside jobTemplate.spec you put all Job fields (backoffLimit, completions, parallelism, etc.). Inside jobTemplate.spec.template you put the Pod spec. It's three levels deep: CronJob → jobTemplate → template.
2.2 Property by Property
1 schedule

1.1 Cron Schedule Syntax ▶

Definition — Cron ExpressionA string with 5 fields separated by spaces: minute hour day-of-month month day-of-week. Each field can be a number, * (any), */N (every N), N-M (range), or N,M (list). Uses the same syntax as Linux crontab.
What
The cron expression that tells the CronJob controller when to create a Job. It is the only scheduling input — every other field decides what happens around that moment.
Why
Needs
  • Recurring work that must run without a human or an always-on process
  • Timing that follows the business rhythm — after the dinner peak, before the working day, at month-end
  • A declarative, reviewable schedule that lives in Git with the rest of the manifest
Problems it prevents
  • A Deployment running while true; sleep burns CPU/RAM 24/7 and fails silently when the loop dies
  • A too-frequent schedule floods the cluster with Jobs and Pods (every minute = 1,440 Jobs/day)
  • Heavy jobs firing during peak traffic compete with customer-facing services
  • "Thundering herd" — many CronJobs all set to minute 0 start at the same second
◆ Goals & Principles
🎯 Goals
  • Run work exactly as often as the business needs — no more, no less
  • Keep batch load away from customer-facing peak hours
  • Make timing obvious to anyone reading the manifest
⚖ Principles
  1. Choose the slowest schedule that still meets the freshness need
  2. Run heavy work off-peak, after traffic has cleared
  3. Stagger minutes (7, 23, 41) instead of stacking every job on :00
  4. Use explicit expressions when the exact time matters — @daily always means midnight
  5. Read the expression back in plain words before applying it
How
ValueBehaviorUse when
"*/5 * * * *"Every 5 minutesNear-real-time sync, cache refresh
"0 * * * *" / @hourlyTop of every hourAggregations, log roll-ups
"15 3 * * *"Daily at a fixed timeBackups, settlements — off-peak
"0 9 * * 0-4"9 AM Sunday–ThursdayBusiness-day reports (KSA work week)
"0 0 1 * *" / @monthly1st of every monthBilling, invoices, archives
Jahez scenarioA restaurant settlement report runs at "15 3 * * *" — after the late-night order peak has cleared and before restaurants open — rather than at midnight when delivery traffic is still high.

2 timeZone — Timezone

Definition — timeZone(v1.27+ stable) By default, CronJobs use the kube-controller-manager's timezone (usually UTC). You can specify a timezone using the timeZone field with an IANA timezone name.
What
The IANA time-zone name the schedule is read in. Without it the schedule follows the kube-controller-manager's local zone, which is almost always UTC.
Why
Needs
  • Business schedules are written in local wall-clock time, not UTC
  • Teams across regions need the manifest itself to state the intended zone
  • Readers of the YAML should not have to do time-zone arithmetic
Problems it prevents
  • A "9 AM" report runs at 12:00 noon in Riyadh when the cluster is on UTC
  • Moving to a cluster with a different controller time zone silently shifts every schedule
  • In zones with daylight saving, runs in the switch-over hour can be skipped or run twice
  • Putting CRON_TZ= / TZ= inside schedule is not supported — use the field
◆ Goals & Principles
🎯 Goals
  • A schedule means the same thing to every reader and on every cluster
  • Business-hour jobs land at local business time
⚖ Principles
  1. Interval schedules don't need a zone; wall-clock schedules always do
  2. Use IANA names (Asia/Riyadh), never offsets or abbreviations
  3. Never put CRON_TZ= / TZ= inside schedule — use the field
  4. In daylight-saving zones, avoid scheduling in the switch-over hour
  5. When you mean UTC, write "Etc/UTC" so it is explicit
How
ValueBehaviorUse when
(not set)Controller's zone (usually UTC)Interval jobs (*/5) where wall-clock time is irrelevant
"Etc/UTC"Explicit UTCSystem jobs where you still want the zone visible in the YAML
"Asia/Riyadh"Saudi local time, UTC+3, no daylight savingAnything tied to KSA business hours
"Europe/London"Local time with daylight savingOnly if needed — avoid scheduling in the switch-over hour
Jahez scenarioA daily ops summary for KSA city managers uses schedule: "0 8 * * 0-4" with timeZone: "Asia/Riyadh", so it lands at 8 AM local time no matter where the cluster runs.
spec:
  schedule: "0 9 * * 1-5"
  timeZone: "America/New_York"   # Runs at 9 AM Eastern
SRE Principle

Always specify timeZone explicitly. Without it, your CronJob uses the cluster's timezone (usually UTC), which may not match your business hours. A "daily 9 AM" report could run at 9 AM UTC = 4 AM Eastern if you forget.

3 concurrencyPolicy

3.1 Allow / Forbid / Replace ▶

Definition — concurrencyPolicyControls what happens when a new schedule fires but the previous Job is still running. Three options: Allow, Forbid, Replace.
What
The rule the controller applies when a new schedule fires while the previous Job from this CronJob is still running.
Why
Needs
  • Run time is not constant — it grows with data volume (e.g., Ramadan nights, big promo days)
  • Some jobs must have a single writer at any moment
  • Some jobs only care about the most recent result
Problems it prevents
  • Overlapping runs double CPU, memory and database load
  • Two runs process the same records — duplicate notifications, double payouts, double exports
  • Lock contention or deadlocks between two copies of the same job
  • A backlog of overlapping runs that never catches up
◆ Goals & Principles
🎯 Goals
  • Two runs never fight over the same data
  • Cluster load stays predictable when runs slow down
  • Each job's overlap behavior matches what a late result is worth
⚖ Principles
  1. Keep Allow only when runs are independent and idempotent
  2. Use Forbid for anything that writes money, messages or shared state
  3. Use Replace only when the newest result fully supersedes the old one and the job is safe to kill mid-way
  4. The policy prevents overlap, not duplication — retries and manual runs can still repeat work, so make jobs idempotent
  5. Pair Forbid with activeDeadlineSeconds so a hung run can't block every future run
How
ValueBehaviorUse when
Allow (default)New Job starts alongside the old oneIndependent, idempotent, cheap runs
ForbidNew run is not started while the old one is activeSingle-writer work: backups, settlements, payouts
ReplaceOld Job is deleted, new one startsOnly the newest result matters: rankings, cache rebuilds
Jahez scenarioRestaurant payout settlement → Forbid (two copies could pay twice). "Top restaurants near you" ranking refresh → Replace (a stale ranking is worthless). Per-city metrics export → Allow (cities are independent).

4 startingDeadlineSeconds

4.1 How the Deadline Works ▶

Definition — startingDeadlineSecondsThe maximum number of seconds past the scheduled time that the CronJob controller will still create a Job. If the controller can't create the Job within this window (e.g., controller was down), the run is considered missed.
What
How many seconds after its scheduled time a run may still be started. Past that window the run counts as missed and is not started.
Why
Needs
  • Runs do get delayed: controller restarts, cluster upgrades, a Forbid block, a suspension
  • Some jobs are worthless if late; others are better late than never
  • The controller needs a bound on how far back it looks for missed runs
Problems it prevents
  • A time-sensitive job fires hours late — a lunch promo push at 3 PM
  • Without a bound the controller counts every missed time since the last run and reports "too many missed start times"
  • Catch-up runs land in peak hours instead of their off-peak slot
◆ Goals & Principles
🎯 Goals
  • A late run starts only while it is still useful
  • Catch-up work after an outage is bounded and predictable
⚖ Principles
  1. Ask: "If this run starts X seconds late, is it still useful?" — the largest X you would accept is your deadline
  2. Never set it below 10 seconds
  3. Time-sensitive jobs → minutes; jobs worth catching up → about one schedule interval
  4. With Forbid, a blocked run can still start after the previous one ends — but only inside this window
  5. Set it explicitly on every production CronJob
How

(not set)No limit — a late run still starts however lateLate is always better than never (e.g., backups)
60 – 300Only start close to the intended timeTime-sensitive: notifications, promo pushes
≈ schedule interval (e.g. 3600 for hourly)Tolerate a long delay, but never more than one intervalHourly/daily jobs that should catch up once

5 suspend — Suspend & Resume ▶

Definition — suspendWhen set to true, the CronJob controller stops creating new Jobs on schedule. Already-running Jobs are NOT affected — they continue to completion. When set back to false, scheduling resumes from the next schedule time (missed runs during suspension are lost).
What
A boolean switch that pauses scheduling while keeping the CronJob, its spec and its history intact.
Why
Needs
  • Maintenance windows — a database migration the job depends on
  • Incidents — the job itself is causing load or bad data
  • Downstream outages — e.g., a payment or SMS provider is down
  • Peak freezes — high-traffic periods where batch work should wait
Problems it prevents
  • Deleting the CronJob to stop it loses its config and history and causes drift from Git
  • Editing the schedule to a fake date as a "pause" is error-prone and easy to forget
  • There is no replicas count to scale a CronJob to zero
◆ Goals & Principles
🎯 Goals
  • Pause safely without losing config or history
  • Keep the paused state visible and easy to reverse
⚖ Principles
  1. Suspend, don't delete
  2. Suspend stops new Jobs only — delete the active Job to stop the current run
  3. Change it where the source of truth lives — in Git when the CronJob is managed by GitOps
  4. Resume deliberately: without startingDeadlineSeconds the last missed run may start immediately

6 successfulJobsHistoryLimit / failedJobsHistoryLimit — History Limits ▶

DefinitionsuccessfulJobsHistoryLimit and failedJobsHistoryLimit control how many completed/failed Jobs are kept. Default: successful=3, failed=1. Set to 0 to keep none (auto-delete immediately).
What
How many finished Jobs (with their Pods) the CronJob keeps — counted separately for successful and failed runs. Older ones are deleted by the controller.
Why
Needs
  • Logs and status of recent runs for debugging and post-mortems
  • Visibility in kubectl get jobs and dashboards
  • Failure signals that monitoring (kube-state-metrics) can still see
Problems it prevents
  • Too many kept → thousands of Job and Pod objects, etcd and API-server bloat, slow kubectl
  • Too few kept → the evidence of a failure is gone before anyone looks
  • Keeping 0 failed Jobs hides failures from Job-based alerts
◆ Goals & Principles
🎯 Goals
  • Enough recent evidence to debug any run
  • A bounded, predictable number of Job and Pod objects
⚖ Principles
  1. Always keep at least one failed Job
  2. Lower the limits as the schedule gets more frequent
  3. History is a short-term buffer — long-term logs belong in central logging
  4. Raise limits temporarily while debugging, then lower them again

7 backoffLimit / activeDeadlineSeconds — Job Failure Inside a CronJob

Key RuleWhen a Job created by a CronJob fails (backoffLimit exceeded or activeDeadlineSeconds reached), the Job is marked Failed. The CronJob does NOT retry it — it waits for the next scheduled time and creates a fresh Job. The failed Job is kept (up to failedJobsHistoryLimit).
What
backoffLimit = how many times a failed Pod is retried within one run (default 6). activeDeadlineSeconds = the maximum wall-clock time for that run (no default). They live in jobTemplate.spec.
Why
Needs
  • Transient failures (DB failover, network blip, rate limit) deserve a retry
  • A hung run needs a hard stop
  • A run must finish before the next schedule fires
Problems it prevents
  • No time cap → a hung run lives forever, and with Forbid it blocks every future run
  • Too many retries → exponential back-off (10 s, 20 s, 40 s … up to 6 min) delays the failure signal
  • Retrying non-idempotent work repeats its side effects
  • With restartPolicy: OnFailure, failed attempts restart in place and their logs are lost
◆ Goals & Principles
🎯 Goals
  • Recover from transient failures automatically
  • Guarantee that every run ends
  • Surface real failures quickly instead of hiding them behind retries
⚖ Principles
  1. Retry only idempotent work — use backoffLimit: 0 for side effects
  2. Keep retries small (2–3); the default 6 is usually too many
  3. Always set activeDeadlineSeconds below the schedule interval
  4. activeDeadlineSeconds wins over backoffLimit — once it passes, the Job fails regardless of retries left
  5. Prefer restartPolicy: Never when you need the logs of every attempt
How
ValueBehaviorUse when
backoffLimit: 0Fail on the first errorNon-idempotent work (sending messages, payments)
backoffLimit: 2 – 3A few retries with back-offMost production jobs
(not set) = 6Up to 6 retriesRarely ideal — usually too many
activeDeadlineSeconds < intervalRun is killed before the next scheduleAny job using Forbid
restartPolicy: NeverNew Pod per retry — old Pods kept for logsWhen you need each attempt's logs
Jahez scenarioThe hourly order-aggregation job uses backoffLimit: 3 and activeDeadlineSeconds: 3000 (50 min), so a stuck run is killed before the next hour's run is due.

8 ttlSecondsAfterFinished — TTL & Cleanup

Two cleanup mechanisms(1) History limits (CronJob-level) — keeps N latest Jobs, deletes older ones. (2) ttlSecondsAfterFinished (Job-level) — auto-deletes each Job N seconds after it finishes. Use both together for thorough cleanup.
What
The TTL controller deletes a Job — and its Pods — N seconds after it finishes, whether it completed or failed. It sits in jobTemplate.spec.
Why
Needs
  • A time-based cleanup guarantee, independent of how many runs happened
  • Short-lived evidence for frequent jobs without manual cleanup
  • Predictable object counts in busy namespaces
Problems it prevents
  • No cleanup → completed Jobs and Pods accumulate
  • Too short → the Job vanishes before anyone reads its logs
  • Too short → a failed Job is deleted before the failure alert evaluates, so the alert never fires
◆ Goals & Principles
🎯 Goals
  • Finished Jobs clean themselves up on a time basis
  • Failed Jobs live long enough to be noticed, alerted on and inspected
⚖ Principles
  1. History limits keep the last N; TTL keeps the last N seconds — whichever removes a Job first wins
  2. Set TTL longer than your alert window plus the time it takes a human to look
  3. Use a short TTL only when logs are shipped to central logging
  4. Use it mainly for frequent jobs; daily jobs are usually fine with history limits alone
How
ValueBehaviorUse when
(not set)Only history limits clean upDefault; fine for most daily/hourly jobs
0Deleted as soon as it finishesLogs shipped elsewhere and no Job-based alerts
300Deleted after 5 minutesEvery-minute / every-5-minute jobs
3600 – 86400Kept 1 – 24 hoursDaily jobs someone checks the next morning
Jahez scenarioThe nightly settlement job keeps ttlSecondsAfterFinished: 86400, so the on-call engineer can inspect the 03:15 run during the next working morning.
spec:
  successfulJobsHistoryLimit: 3       # CronJob-level: keep 3 latest
  failedJobsHistoryLimit: 1           # CronJob-level: keep 1 failed
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 3600  # Job-level: delete 1h after finish
SRE Rule

For CronJobs that run frequently (every minute/5 min), set successfulJobsHistoryLimit: 1 and ttlSecondsAfterFinished: 300. Without this, you'll have thousands of completed Jobs and Pods in a week.

2.3 Operations & Reference

Manual Trigger — Run CronJob Now

DefinitionCreate a one-time Job FROM a CronJob's template. Doesn't wait for the schedule. The Job uses the exact same spec as the CronJob would produce. The CronJob's schedule is unaffected.
# Create a Job immediately using the CronJob's template
kubectl create job manual-backup --from=cronjob/nightly-backup

# Check it
kubectl get jobs
kubectl logs job/manual-backup
Use Cases

(1) Test a new CronJob without waiting. (2) Re-run a failed schedule. (3) Emergency manual execution of a nightly task during an incident. (4) Verify the CronJob template produces working Pods before the first schedule fires.

Monitoring & Best Practices

Metric / CheckAlert When

Always set concurrencyPolicy: Forbid

Unless you explicitly need concurrent runs. Forbid prevents resource overload and data conflicts from overlapping Jobs.

Always set startingDeadlineSeconds

Prevents the 100-missed-schedules stall. Set to 2× your schedule interval (e.g., schedule every hour → deadline 7200s).

Always set history limits

Default 3/1 is fine for hourly. For every-minute CronJobs, use 1/1 or 0/1 to prevent thousands of accumulated Jobs.

Always set activeDeadlineSeconds on the Job template

A stuck Job without a deadline runs forever, blocking Forbid policy from starting the next run. The deadline is your safety net.

Test with manual trigger before relying on schedule

kubectl create job test --from=cronjob/NAME verifies the template works before the first real schedule fires.

SRE Wisdom

CronJobs are the most common source of "silent failures" in production. A CronJob can fail every night for a week and nobody notices unless you have alerts on kube_job_status_failed. Monitor them like you monitor your main services.
