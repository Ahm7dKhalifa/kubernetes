Create & Basics

LAB 01
Create a CronJob
Easy

Create CronJob hello-cron that runs every minute, image busybox, prints "Hello from CronJob" and exits.

Verify: kubectl get cronjob hello-cron → SCHEDULE * * * * *. Wait 1 min, then kubectl get jobs.
Imperative
YAML
Hybrid
kubectl create cronjob hello-cron --image=busybox --schedule="* * * * *" -- /bin/sh -c "echo Hello from CronJob"
FastestOne command. Note: schedule MUST be in quotes.
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello-cron
spec:
  schedule: "* * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: hello
            image: busybox
            command: ["sh","-c","echo Hello from CronJob"]
NestingCronJob YAML is 3 levels deep: spec.jobTemplate.spec.template.spec. This is the #1 YAML indentation mistake on the exam.
kubectl create cronjob hello-cron --image=busybox --schedule="* * * * *" \
  --dry-run=client -o yaml -- /bin/sh -c "echo Hello from CronJob" > cron.yaml
# Edit: add concurrencyPolicy, history limits, etc.
kubectl apply -f cron.yaml
LAB 02
Create CronJob with All Fields
Medium

Create CronJob backup-cron running every 6 hours with: concurrencyPolicy=Forbid, startingDeadlineSeconds=300, successfulJobsHistoryLimit=3, failedJobsHistoryLimit=1, Job backoffLimit=2, activeDeadlineSeconds=600.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-cron
spec:
  schedule: "0 */6 * * *"              # Every 6 hours
  concurrencyPolicy: Forbid            # Skip if previous still running
  startingDeadlineSeconds: 300         # Must start within 5 min of schedule
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 2                  # Job-level: max 2 retries per run
      activeDeadlineSeconds: 600       # Job-level: kill if >10 min
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: backup
            image: busybox
            command: ["sh","-c","echo Backup started && sleep 30 && echo Backup done"]
Field placementconcurrencyPolicy, schedule, historyLimits, startingDeadlineSeconds go under spec (CronJob level). backoffLimit, activeDeadlineSeconds go under spec.jobTemplate.spec (Job level). restartPolicy goes under spec.jobTemplate.spec.template.spec (Pod level).

Write the cron expression for each scenario. Don't look at a reference — practice from memory.

LAB 06
Set Timezone on CronJob
Medium

Create CronJob tz-cron that runs daily at 9 AM Eastern (America/New_York), not UTC.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: tz-cron
spec:
  schedule: "0 9 * * *"
  timeZone: "America/New_York"    # v1.27+ (stable)
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: report
            image: busybox
            command: ["sh","-c","echo Report at $(date)"]
Without timeZoneThe CronJob uses the kube-controller-manager's timezone (usually UTC). "9 AM" would be 9 AM UTC = 4 AM Eastern. Always specify timezone for business-hour schedules.

Concurrency

LAB 07
concurrencyPolicy: Forbid — Skip Overlapping Runs
Medium

Create CronJob slow-cron that runs every minute but takes 90 seconds to complete. Set concurrencyPolicy=Forbid. Observe that the next run is skipped when previous is still active.

Verify: After 3 minutes, you should see only 2 Jobs (not 3) — one was skipped.
apiVersion: batch/v1
kind: CronJob
metadata:
  name: slow-cron
spec:
  schedule: "* * * * *"                # Every minute
  concurrencyPolicy: Forbid            # Skip if previous active
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: slow
            image: busybox
            command: ["sh","-c","echo Started && sleep 90 && echo Done"]
# Watch Jobs being created
kubectl get jobs -w

# After 3 min: Job-1 (Complete), Job-2 (Running or Complete)
# One minute was SKIPPED because Forbid + previous still active
Timeline:
T=0:00 → Job-1 starts (takes 90s)
T=1:00 → SKIPPED (Forbid — Job-1 still running)
T=1:30 → Job-1 done
T=2:00 → Job-2 starts (Job-1 finished, slot open)
LAB 08
concurrencyPolicy: Replace — Kill Old, Start New
Hard

Create CronJob replace-cron every minute, takes 90s. Set concurrencyPolicy=Replace. Observe: old Job is killed when new schedule fires.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: replace-cron
spec:
  schedule: "* * * * *"
  concurrencyPolicy: Replace           # Kill running, start new
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: worker
            image: busybox
            command: ["sh","-c","echo Started $(date) && sleep 90"]
kubectl get jobs -w
# T=0: Job-1 starts
# T=1: Job-1 KILLED → Job-2 starts
# T=2: Job-2 KILLED → Job-3 starts
# No Job ever completes because each is killed after 60s!
DangerWith Replace, if your Job takes longer than the schedule interval, it will NEVER complete. Each run kills the previous. Use only when you explicitly want "latest run wins."

LAB 10
Suspend and Resume a CronJob
Medium

CronJob hello-cron runs every minute. Suspend it. Wait 2 minutes (verify no new Jobs). Resume it.

Imperative
YAML
# Suspend — no new Jobs will be created
kubectl patch cronjob hello-cron -p '{"spec":{"suspend":true}}'

# Verify
kubectl get cronjob hello-cron
# SUSPEND = True

# Wait 2 min — no new Jobs appear
kubectl get jobs

# Resume — scheduling restarts
kubectl patch cronjob hello-cron -p '{"spec":{"suspend":false}}'

# Verify — SUSPEND = False, new Jobs start appearing
kubectl get cronjob hello-cron
# In cronjob YAML:
spec:
  suspend: true     # Paused
  # Change to false to resume
Key behaviorSuspend does NOT kill already-running Jobs. It only stops creating NEW Jobs. Runs missed during suspension are permanently lost — they are NOT retroactively created when you resume.

LAB 11
Set History Limits
Medium

Create CronJob hist-cron every minute with: successfulJobsHistoryLimit=2, failedJobsHistoryLimit=1. Wait 5 minutes. Verify only 2 successful Jobs are kept.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: hist-cron
spec:
  schedule: "* * * * *"
  successfulJobsHistoryLimit: 2     # Keep only 2 latest successful Jobs
  failedJobsHistoryLimit: 1        # Keep only 1 failed Job
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: worker
            image: busybox
            command: ["echo","tick"]
# Wait 5 minutes, then check
kubectl get jobs --sort-by=.metadata.creationTimestamp
# Only 2 Jobs exist! Older ones were auto-deleted by the controller.
Without limits (default 3/1)A CronJob running every minute creates 1,440 Jobs/day. After a week: 10,080 Jobs + Pods cluttering etcd. Always set limits for frequent CronJobs.
LAB 12
TTL — Auto-Delete Jobs After Completion
Easy

Create CronJob ttl-cron every minute. Each Job should auto-delete 60 seconds after completing.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: ttl-cron
spec:
  schedule: "* * * * *"
  jobTemplate:
    spec:
      ttlSecondsAfterFinished: 60     # Auto-delete Job 60s after finish
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: worker
            image: busybox
            command: ["echo","done"]
TTL vs History LimitsBoth clean up Jobs. historyLimit keeps N latest (CronJob-level). ttlSecondsAfterFinished deletes each Job after N seconds (Job-level). Use both for thorough cleanup.

Failure Handling

LAB 13
Job Failure Inside CronJob — Observe Behavior
Medium

Create CronJob fail-cron every minute where the Job always fails (exit 1, backoffLimit=1). Observe: CronJob does NOT retry the failed Job — it creates a fresh Job next minute.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: fail-cron
spec:
  schedule: "* * * * *"
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 1               # 1 retry per Job, then Job fails
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: fail
            image: busybox
            command: ["sh","-c","exit 1"]
# Wait 3 minutes
kubectl get jobs
# COMPLETIONS show 0/1 for each Job — all failed
# But a NEW Job is created each minute (not a retry of the old one)
Key insight:
T=0 → Job-1 → Failed (backoffLimit exhausted)
T=1 → Job-2 → Failed (fresh Job, NOT a retry of Job-1)
T=2 → Job-3 → Failed (again fresh)

CronJob creates new Jobs on schedule. It does NOT retry failed Jobs.
LAB 14
startingDeadlineSeconds
Medium

Create CronJob deadline-cron every minute with startingDeadlineSeconds: 30. Explain what this means and when it matters.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: deadline-cron
spec:
  schedule: "* * * * *"
  startingDeadlineSeconds: 30       # Must start within 30s of schedule
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: worker
            image: busybox
            command: ["echo","tick"]
What it means:
Schedule fires at T=0:00. Controller has until T=0:30 to create the Job.
If controller is busy/down and can't create it by T=0:30 → run is SKIPPED.

Why it matters:
Without this: if controller is down for hours, it counts ALL missed schedules. If ≥100 missed → CronJob permanently stalls.
With this: controller only counts misses within the 30s window. Much harder to hit the 100-miss stall.
SRE Rule

Always set startingDeadlineSeconds. A good value is 2× your interval. Every-minute CronJob → 120s. Hourly → 7200s.

LAB 15
activeDeadlineSeconds on CronJob's Job
Medium

Create CronJob timeout-cron every 5 min. Each Job must finish within 60s or be killed.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: timeout-cron
spec:
  schedule: "*/5 * * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      activeDeadlineSeconds: 60       # Kill Job after 60s
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: worker
            image: busybox
            command: ["sh","-c","echo Working && sleep 30 && echo Done"]
Critical with ForbidWithout activeDeadlineSeconds, a stuck Job runs forever. With concurrencyPolicy: Forbid, this blocks ALL future runs permanently. The deadline is your safety net — it kills stuck Jobs so the next schedule can fire.

Troubleshooting

LAB 16
Fix CronJob — Wrong Schedule Syntax
Easy

This CronJob was supposed to run daily at 3 AM but it runs every minute. Fix it.

kubectl create cronjob fix-sched --image=busybox --schedule="3 * * * *" -- echo "Daily task"
# The bug: "3 * * * *" = at minute 3 of EVERY hour (24 times/day)
# Fix: "0 3 * * *" = at hour 3, minute 0 (once daily at 3 AM)

kubectl delete cronjob fix-sched
kubectl create cronjob fix-sched --image=busybox --schedule="0 3 * * *" -- echo "Daily task"
Common mistakes3 * * * * = minute 3 of every hour. * 3 * * * = every minute of hour 3 (60 runs!). 0 3 * * * = once at 3:00 AM. Always read it back: "At minute 0, of hour 3, every day."
LAB 17
Fix CronJob — restartPolicy: Always
Easy

This CronJob YAML is rejected. Why? Fix it.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: bad-cron
spec:
  schedule: "*/5 * * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: worker
            image: busybox
            command: ["echo","hi"]
# Error: spec.jobTemplate.spec.template.spec.restartPolicy:
# Unsupported value: "Always" (default when not specified for CronJobs)
# Supported: "OnFailure", "Never"

# Fix: add restartPolicy explicitly
        spec:
          restartPolicy: Never        # ← ADD THIS LINE
          containers:
          - name: worker
Exam trapIf you omit restartPolicy in a CronJob/Job, it defaults to Always, which is INVALID for Jobs. The API server rejects it. Always explicitly set restartPolicy: Never or OnFailure.

LAB 19
Fix Stuck CronJob — Not Creating Jobs
Hard

CronJob stuck-cron exists but hasn't created any Jobs in hours. Diagnose and fix.

# Step 1: Check if suspended
kubectl get cronjob stuck-cron -o jsonpath='{.spec.suspend}'
# If true → fix: kubectl patch cronjob stuck-cron -p '{"spec":{"suspend":false}}'

# Step 2: Check if Forbid + stuck Job blocking
kubectl get cronjob stuck-cron -o jsonpath='{.spec.concurrencyPolicy}'
kubectl get cronjob stuck-cron -o jsonpath='{.status.active}'
# If concurrencyPolicy=Forbid AND active > 0 → a Job is stuck running
# Fix: delete the stuck Job
kubectl delete job $(kubectl get jobs -o name | grep stuck-cron | head -1)

# Step 3: Check if 100-missed-schedules stall
kubectl describe cronjob stuck-cron | grep -i "cannot determine"
# If you see "Too many missed start times" → CronJob is stalled
# Fix: delete and recreate, or set startingDeadlineSeconds
kubectl delete cronjob stuck-cron
# Recreate with startingDeadlineSeconds: 300

# Step 4: Check schedule syntax
kubectl get cronjob stuck-cron -o jsonpath='{.spec.schedule}'
# Make sure it's valid (e.g., not "60 * * * *" which is invalid minute)
4 reasons a CronJob stops creating Jobs:
① suspend: true → unsuspend it
② Forbid + stuck Job → delete the stuck Job
③ 100 missed schedules → delete & recreate with startingDeadlineSeconds
④ Invalid schedule syntax → fix the expression

Nightly Database Backup CronJob
Medium

Create CronJob db-backup: daily at 2 AM UTC, Forbid overlap, 30-min deadline per Job, 2 retries, TTL 24h, keep 7 successful / 3 failed.

apiVersion: batch/v1

      backoffLimit: 2
      activeDeadlineSeconds: 1800
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: backup
            image: busybox
            command: ["sh","-c","echo DB backup started && sleep 60 && echo DB backup complete"]
            resources:
              requests: { cpu: "200m", memory: "256Mi" }

LAB 24
CronJob with Parallel Completions
Hard

Create CronJob batch-cron every hour. Each run should process 6 items with parallelism=3.

apiVersion: batch/v1
kind: CronJob
metadata:
  name: batch-cron
spec:
  schedule: "0 * * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      completions: 6              # 6 Pods must succeed per run
      parallelism: 3              # 3 at a time
      backoffLimit: 4
      activeDeadlineSeconds: 600
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: processor
            image: busybox
            command: ["sh","-c","echo Processing item on $(hostname) && sleep 10"]
CronJobs can have completions + parallelismEach scheduled run creates a Job with 6 completions and 3 parallel workers. This is how you do "hourly batch processing of N items."
LAB 25
Full Production CronJob
Hard

Create production CronJob in namespace production:

  • Name: nightly-report, Schedule: daily 3:30 AM UTC
  • concurrencyPolicy: Forbid, startingDeadlineSeconds: 600
  • successfulJobsHistoryLimit: 7, failedJobsHistoryLimit: 3
  • Job: backoffLimit=3, activeDeadlineSeconds=3600, ttlSecondsAfterFinished=172800 (48h)
  • Container: image busybox, resources (cpu 200m/500m, memory 128Mi/256Mi)
  • ConfigMap report-config with REPORT_TYPE=monthly as env
kubectl create namespace production
kubectl create configmap report-config -n production --from-literal=REPORT_TYPE=monthly
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-report
  namespace: production
spec:
  schedule: "30 3 * * *"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 600
  successfulJobsHistoryLimit: 7
  failedJobsHistoryLimit: 3
  jobTemplate:
    spec:
      backoffLimit: 3
      activeDeadlineSeconds: 3600
      ttlSecondsAfterFinished: 172800
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: reporter
            image: busybox
            command: ["sh","-c","echo Generating $REPORT_TYPE report && sleep 30 && echo Done"]
            envFrom:
            - configMapRef:
                name: report-config
            resources:
              requests:
                cpu: "200m"
                memory: "128Mi"
              limits:
                cpu: "500m"
                memory: "256Mi"
kubectl apply -f nightly-report.yaml

# Test immediately
kubectl create job test-report -n production --from=cronjob/nightly-report
kubectl logs -n production job/test-report
Key Takeaways

1. Schedule syntax: minute hour day month weekday. 2. YAML is 3 levels deep: spec.jobTemplate.spec.template.spec. 3. restartPolicy must be Never or OnFailure (never Always). 4. concurrencyPolicy: Forbid prevents overlapping runs. 5. startingDeadlineSeconds prevents the 100-missed-schedules stall. 6. --from=cronjob/NAME triggers a CronJob manually. 7. Always set history limits + TTL for cleanup. 8. activeDeadlineSeconds on the Job prevents stuck Jobs from blocking Forbid policy.
