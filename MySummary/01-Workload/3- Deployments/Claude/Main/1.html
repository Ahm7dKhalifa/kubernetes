The complete guide — rolling updates, rollbacks, strategies, patterns, and SRE operations. Interactive step-by-step workflows for every concept.

01 What is a Deployment?

Definition — DeploymentA Deployment is a Kubernetes controller that manages ReplicaSets, which in turn manage Pods. It provides declarative updates: you describe the desired state (image, replicas, strategy), and the Deployment controller changes the actual state at a controlled rate. It adds rolling updates, rollback, revision history, and pause/resume on top of what ReplicaSets offer.
Definition — Why Deployments ExistReplicaSets can maintain Pod count but cannot update Pod images without downtime. Deployments solve this by creating a NEW ReplicaSet with the new template, then gradually shifting Pods from the old RS to the new RS — zero downtime.
Analogy

A Deployment is a fleet manager. ReplicaSets are the vehicle pools. Pods are the vehicles. When you need to upgrade the fleet (new image), the manager doesn't scrap all vehicles at once — it gradually replaces old with new, keeping the fleet operational the entire time.

FeatureWhat It DoesWithout Deployment
Rolling UpdateReplace Pods gradually, zero downtimeMust delete all Pods manually → downtime
RollbackRevert to any previous version instantlyMust remember and reapply old YAML manually
Revision HistoryTrack every change with revision numbersNo history — changes are lost
Pause/ResumeMake multiple changes then apply all at onceEvery change triggers a rollout immediately
Status TrackingReports progress, deadline, conditionsMust watch Pods manually

04 Full Deployment YAML — Every Field Explained

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-deploy
  namespace: production
  labels:
    app: web
  annotations:
    kubernetes.io/change-cause: "Initial deployment v1.25"  # Shows in rollout history
spec:
  replicas: 3                          # Desired Pod count
  revisionHistoryLimit: 10             # Keep 10 old RS for rollback (default 10)
  progressDeadlineSeconds: 600        # Rollout must progress within 10 min
  minReadySeconds: 5                  # Pod must be ready 5s before considered available

  strategy:                             # How to replace Pods
    type: RollingUpdate                # RollingUpdate (default) or Recreate
    rollingUpdate:
      maxSurge: 1                      # Max extra Pods during update (25% or int)
      maxUnavailable: 0               # Max Pods that can be down (25% or int)

  selector:                             # Which Pods belong to this Deployment (IMMUTABLE)
    matchLabels:
      app: web

  template:                             # Pod blueprint — changes trigger rollout
    metadata:
      labels:
        app: web                      # MUST match selector
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests: { cpu: "100m", memory: "64Mi" }
          limits: { cpu: "200m", memory: "128Mi" }
        readinessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 5
        livenessProbe:
          httpGet: { path: /, port: 80 }
          periodSeconds: 10
Definition — What Triggers a Rollout?Only changes to spec.template trigger a new rollout (new RS). Changes to replicas, strategy, metadata, or revisionHistoryLimit do NOT trigger a rollout — they apply in-place.

06 Rolling Update — Step by Step ▶

Definition — Rolling UpdateA strategy that replaces old Pods with new Pods gradually. The Deployment creates a new ReplicaSet, scales it up while scaling the old RS down. Each new Pod must pass readiness before an old Pod is killed. At no point are there zero healthy Pods.
① Trigger
② New RS
③ First Pod
④ Ready → Kill
⑤ Repeat
⑥ Complete
⑦ After
① You trigger the update
kubectl set image deployment/web-deploy nginx=nginx:1.26
Deployment detects template change
Current: RS-v1 (3 Pods, nginx:1.25)
Pod 1 (1.25) Pod 2 (1.25) Pod 3 (1.25)
Any change to spec.template triggers a rollout. The Deployment controller detects the template hash changed and begins the rolling update process.
② Deployment creates a NEW ReplicaSet
Deployment
RS-v1 (replicas: 3, nginx:1.25) Pod 1 Pod 2 Pod 3
RS-v2 (replicas: 0, nginx:1.26) ← NEW, empty
A brand new RS is created with the updated template. It starts with 0 replicas. The old RS still has all 3 Pods running. Both RS exist simultaneously.
③ RS-v2 scales to 1 — first new Pod created
RS-v1 (3): Pod 1 Pod 2 Pod 3
RS-v2 (1): Pod 4 (1.26) ⏳ starting...

maxSurge=1 allows 4 total Pods temporarily (3 desired + 1 extra)
RS-v2 scales from 0→1. Pod 4 is created with nginx:1.26. It goes through: schedule → image pull → start → probes. It must pass readiness before the next step.
④ Pod 4 passes readiness → Pod 1 is terminated
RS-v1 (2): Pod 1 terminating Pod 2 Pod 3
RS-v2 (1): Pod 4 (1.26) READY ✓

3 healthy Pods serving traffic: Pod 2 + Pod 3 + Pod 4. Zero downtime.
Pod 4 passes readiness → it's added to Service endpoints → receives traffic. Now the Deployment can safely terminate Pod 1. RS-v1 scales 3→2. At no point are there fewer than 3 healthy Pods (because maxUnavailable=0).
⑤ Process repeats for remaining Pods
RS-v1 (1): Pod 3
RS-v2 (2): Pod 4 ✓ Pod 5 ✓

Next: Pod 6 created → passes readiness → Pod 3 terminated
$ kubectl rollout status deployment/web-deploy Waiting for rollout to finish: 2 out of 3 new replicas have been updated...
⑥ Rollout complete — all Pods on v2
RS-v1 (0): empty — kept for rollback
RS-v2 (3): Pod 4 ✓ Pod 5 ✓ Pod 6 ✓
$ kubectl rollout status deployment/web-deploy deployment "web-deploy" successfully rolled out
⑦ After — Old RS kept for rollback
Deployment (revision 2)

RS-v1 (replicas: 0, revision 1) ← kept! kubectl rollout undo scales this back up
RS-v2 (replicas: 3, revision 2) ← active
The old RS is NOT deleted. It's scaled to 0 and kept as a rollback target. The number of old RS kept is controlled by revisionHistoryLimit (default: 10). Running kubectl rollout undo simply swaps which RS is active.

07 Update Strategies ▶

RollingUpdate
Recreate
maxSurge/maxUnavail
Tuning Examples
RollingUpdate (Default) — Zero Downtime
DefinitionGradually replaces old Pods with new Pods. Controlled by maxSurge (how many extra Pods allowed) and maxUnavailable (how many can be down). New Pod must pass readiness before old Pod is killed.
strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1
    maxUnavailable: 0
Recreate — Kill All, Then Create All (Downtime!)
DefinitionTerminates ALL old Pods first, then creates ALL new Pods. Causes downtime. Use only when your app can't run two versions simultaneously (e.g., database schema incompatibility).
strategy:
  type: Recreate
Pod 1 Pod 2 Pod 3 → ALL killed → DOWNTIME → Pod 4 Pod 5 Pod 6
maxSurge & maxUnavailable Explained
maxSurgeMaximum number of Pods that can exist ABOVE the desired count during update. Can be an integer (1) or percentage (25%). With replicas=4 and maxSurge=1, up to 5 Pods can exist during rollout.
maxUnavailableMaximum number of Pods that can be UNAVAILABLE during update. Can be integer or percentage. With replicas=4 and maxUnavailable=1, at least 3 Pods must always be ready.
SettingBehaviorSpeedSafety
maxSurge=1, maxUnavail=0Always ≥ desired Pods running. Safest.SlowHighest
maxSurge=0, maxUnavail=1Never more than desired. Kills before creates.MediumMedium
maxSurge=25%, maxUnavail=25%Default. Balanced speed and safety.FastGood
maxSurge=100%, maxUnavail=0Creates ALL new Pods first (double resources), then kills old.FastestHigh (needs 2x resources)
Tuning Examples
# Safest — zero downtime, one Pod at a time
maxSurge: 1
maxUnavailable: 0

# Fast — replace 25% at a time (default)
maxSurge: 25%
maxUnavailable: 25%

# Fastest — create all new Pods first, then kill old
maxSurge: 100%
maxUnavailable: 0

# Resource-constrained — no extra Pods, kill first
maxSurge: 0
maxUnavailable: 1

08 All Ways to Trigger an Update

# Method 1: Set image directly (most common)
kubectl set image deployment/web-deploy nginx=nginx:1.26

# Method 2: Edit live object
kubectl edit deployment web-deploy

# Method 3: Apply updated YAML file (GitOps way)
kubectl apply -f deployment.yaml

# Method 4: Patch
kubectl patch deployment web-deploy -p '{"spec":{"template":{"spec":{"containers":[{"name":"nginx","image":"nginx:1.26"}]}}}}'

# Method 5: Set env var (also triggers rollout — template changed)
kubectl set env deployment/web-deploy LOG_LEVEL=debug

# Method 6: Set resources
kubectl set resources deployment/web-deploy -c nginx --limits=memory=256Mi
What does NOT trigger a rollout

Changing replicas, strategy, revisionHistoryLimit, metadata.labels, or metadata.annotations does NOT create a new RS. Only spec.template changes trigger rollouts.

09 Rollback ▶

Definition — RollbackReverting a Deployment to a previous revision. Internally, the Deployment scales up the old ReplicaSet and scales down the current one — the same rolling update process in reverse. Old RS objects are kept specifically for this purpose.
Undo (previous)
Undo to specific
What happens
Full workflow
Rollback to previous version
kubectl rollout undo deployment/web-deploy
$ kubectl rollout undo deployment/web-deploy deployment.apps/web-deploy rolled back
Rollback to a specific revision
# View revision history
kubectl rollout history deployment/web-deploy

# See details of a specific revision
kubectl rollout history deployment/web-deploy --revision=2

# Rollback to revision 1
kubectl rollout undo deployment/web-deploy --to-revision=1
$ kubectl rollout history deployment/web-deploy REVISION CHANGE-CAUSE 1 Initial deployment v1.25 2 kubectl set image deployment/web-deploy nginx=nginx:1.26 3 kubectl set image deployment/web-deploy nginx=nginx:1.27
What happens internally during rollback
Before rollback (on revision 3, nginx:1.27):
RS-v1 (0, nginx:1.25) RS-v2 (0, nginx:1.26) RS-v3 (3, nginx:1.27) ← active

After kubectl rollout undo --to-revision=1:
RS-v1 (3, nginx:1.25) ← scaled UP RS-v2 (0) RS-v3 (0) ← scaled DOWN

Same rolling update process — RS-v1 scales up gradually, RS-v3 scales down. Zero downtime.
Full workflow — deploy, break, rollback
# Deploy v1
kubectl create deployment web --image=nginx:1.25 --replicas=3

# Update to v2 (works)
kubectl set image deployment/web nginx=nginx:1.26
kubectl rollout status deployment/web

# Update to v3 (broken image!)
kubectl set image deployment/web nginx=nginx:9.99
# Pods stuck in ImagePullBackOff

# Rollback to v2 instantly
kubectl rollout undo deployment/web
kubectl rollout status deployment/web
# deployment "web" successfully rolled out ✓

10 Revision History

Definition — revisionHistoryLimitControls how many old ReplicaSets are kept for rollback. Default: 10. Setting to 0 means you can't rollback at all. Each old RS uses minimal resources (just the RS object, no Pods).
# View all revisions
kubectl rollout history deployment/web-deploy

# View specific revision details (shows the Pod template)
kubectl rollout history deployment/web-deploy --revision=2

# Record the reason for each change
kubectl set image deployment/web-deploy nginx=nginx:1.26 --record    # deprecated but still works
# OR annotate
kubectl annotate deployment/web-deploy kubernetes.io/change-cause="Upgrade to 1.26 for CVE fix"
spec:
  revisionHistoryLimit: 10   # Keep 10 old RS (default)

11 Scaling

# Manual scale
kubectl scale deployment web-deploy --replicas=5

# HPA — auto-scale based on CPU
kubectl autoscale deployment web-deploy --min=2 --max=10 --cpu-percent=80
Key Point

Scaling does NOT trigger a rollout. It does NOT create a new RS. The existing RS simply adjusts its replica count. No new Pods are created with a different template — they use the current RS template.

12 Pause & Resume ▶

Definition — PauseStops the Deployment from rolling out changes. You can make multiple template changes (image + env + resources) while paused, then resume to apply them all as ONE single rollout instead of 3 separate ones.
Why Pause
Workflow
Commands
Without pause — 3 changes = 3 rollouts
set image → rollout #1 starts
set env → rollout #2 starts (interrupts #1!)
set resources → rollout #3 starts (interrupts #2!)

3 unnecessary RS created. Messy. Wastes resources.
With pause — 3 changes = 1 rollout
kubectl rollout pause
set image → queued
set env → queued
set resources → queued
kubectl rollout resume → ONE rollout with ALL changes ✓
# Pause — freeze rollouts
kubectl rollout pause deployment/web-deploy

# Make multiple changes (no rollout triggered)
kubectl set image deployment/web-deploy nginx=nginx:1.26
kubectl set env deployment/web-deploy LOG_LEVEL=debug
kubectl set resources deployment/web-deploy -c nginx --limits=memory=256Mi

# Resume — all changes applied as ONE rollout
kubectl rollout resume deployment/web-deploy
kubectl rollout status deployment/web-deploy

15 Blue/Green Deployment ▶

Definition — Blue/GreenRun two complete environments (blue=current, green=new). Test green, then switch ALL traffic instantly by changing the Service selector. Rollback = switch selector back. Not built into Deployments — requires manual Service manipulation.
Setup
Switch
Rollback
Setup — Two Deployments + One Service
# Blue (current — receiving traffic)
kubectl create deployment blue --image=nginx:1.25 --replicas=3
kubectl label deployment blue version=blue

# Service points to blue
kubectl expose deployment blue --name=web-svc --port=80 --selector=version=blue

# Green (new — test before switching)
kubectl create deployment green --image=nginx:1.26 --replicas=3
kubectl label deployment green version=green
Switch traffic to green
kubectl patch svc web-svc -p '{"spec":{"selector":{"version":"green"}}}'
# ALL traffic instantly goes to green ✓
Rollback — switch back to blue
kubectl patch svc web-svc -p '{"spec":{"selector":{"version":"blue"}}}'
# Instant rollback — blue is still running!

16 Canary Deployment ▶

Definition — CanarySend a small percentage of traffic to the new version first. If it works, gradually increase. If it fails, route everything back to the old version. Named after canaries in coal mines — the canary detects problems before they affect everyone.
Setup
Test
Promote
Setup — Main (3 replicas) + Canary (1 replica)
# Main deployment (stable)
kubectl create deployment web-stable --image=nginx:1.25 --replicas=3

# Canary deployment (1 replica = ~25% traffic)
kubectl create deployment web-canary --image=nginx:1.26 --replicas=1

# BOTH share the same 'app=web' label → Service routes to both
kubectl label pods -l app=web-stable app=web --overwrite
kubectl label pods -l app=web-canary app=web --overwrite

# Service selects app=web → traffic split: 75% stable, 25% canary
kubectl expose deployment web-stable --name=web-svc --port=80 --selector=app=web
Monitor canary — check errors
# Watch canary Pod logs for errors
kubectl logs -l app=web-canary -f

# Check metrics (if Prometheus is running)
# Compare error rate: canary vs stable

# If canary is bad → delete it
kubectl delete deployment web-canary
Promote canary — scale up, remove old
# Canary looks good → promote it
kubectl scale deployment web-canary --replicas=3
kubectl delete deployment web-stable

17 Monitoring & Best Practices

MetricAlert When
kube_deployment_status_replicas_availableavailable < desired > 5 min
kube_deployment_status_replicas_updatedupdated < desired > 10 min (stuck rollout)
kube_deployment_spec_replicasUnexpected change
Always Set Strategy

Explicitly set maxSurge and maxUnavailable. Don't rely on defaults. maxSurge: 1, maxUnavailable: 0 is safest.

Always Set progressDeadlineSeconds

Default 600s (10 min). Set lower for fast-starting apps. This catches stuck rollouts automatically.

Use Readiness Probes

Without readiness probes, Kubernetes considers a Pod "ready" as soon as it starts — the rolling update won't wait for your app to actually be serving. This can send traffic to Pods that aren't ready.

Record Change Cause

Annotate every deployment change: kubernetes.io/change-cause: "CVE-2024-1234 fix". This shows in rollout history and helps during incident review.

Set revisionHistoryLimit

Default 10 is usually fine. Don't set to 0 unless you never need rollback. Each old RS is just a metadata object — almost no resource cost.

SRE Wisdom

Deployments are the primary workload resource for stateless applications in production. Every SRE should be able to: trigger a rollout, watch its progress, diagnose a stuck rollout, and rollback — all in under 60 seconds. Practice until these commands are muscle memory.
