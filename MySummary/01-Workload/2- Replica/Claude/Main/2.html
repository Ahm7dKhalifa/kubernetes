Kubernetes ReplicaSets

The complete guide — reconciliation loop, scaling algorithms, label matching edge cases, and SRE operations. Interactive step-by-step workflows for every concept.

01 What is a ReplicaSet?

Definition — ReplicaSet (RS)A Kubernetes controller that ensures a specified number of identical Pod replicas are running at all times. If a Pod dies, the RS creates a new one. If there are too many, it deletes extras. It constantly watches actual state and reconciles it to match desired state.
Definition — ControllerA control loop that watches cluster state, then makes changes to move current state toward desired state. ReplicaSet is one controller type. Others: Deployment, StatefulSet, DaemonSet, Job.
Definition — Level-TriggeredThe RS checks actual state ("I need 3, I have 2"), not events ("a Pod was deleted"). This means it handles missed events gracefully — it always recounts. This is why Kubernetes is reliable.
Analogy

A ReplicaSet is a thermostat. You set it to 72°F (desired: 3 Pods). It constantly measures the room temperature (actual Pod count). Too cold? Turn on heat (create Pod). Too hot? Turn on AC (delete Pod). At 72°? Do nothing. It never stops checking.

02 Why Do We Need ReplicaSets? ▶

High Availability
Load Balancing
Scaling
Self-Healing
High Availability — Survive Failures
Without RS (1 Pod):
Pod dies → SERVICE DOWN ✗ nobody recreates it

With RS (3 Pods):
Pod 1 ✓ Pod 2 dies Pod 3 ✓ → Pod 4 created ✓
Service still available. Users notice nothing.
Definition: Multiple replicas means your app survives Pod failures, node crashes, and evictions. Even if one Pod dies, others keep serving while RS creates a replacement.
Load Balancing — Distribute Traffic
Service (Load Balancer)
├→ Pod 1 (33%)
├→ Pod 2 (33%)
└→ Pod 3 (33%)
Multiple replicas behind a Service distribute requests. No single Pod is overwhelmed. The Service automatically load-balances across all healthy Pods.
Scaling — Adjust to Demand
Low traffic: Pod 1 Pod 2 (replicas: 2)

High traffic: 1 2 3 4 5 (replicas: 5)

kubectl scale rs web-rs --replicas=5
Scale up to handle traffic spikes, scale down to save costs. Can be manual or automatic (HorizontalPodAutoscaler).
Self-Healing — Automatic Recovery
1 ✓ 2 ✓ 3 ✓ ← Normal
1 ✓ 2 OOMKilled 3 ✓ ← Pod 2 dies
1 ✓ 4 creating 3 ✓ ← RS replaces
1 ✓ 4 ✓ 3 ✓ ← Healed!
RS doesn't care why a Pod disappeared. Crash, OOM, eviction, node death — the response is always: "I need 3, I see 2, create 1."

03 The Three Pillars ▶

Definition — Three PillarsEvery ReplicaSet has three key fields: replicas (how many), selector (which Pods are mine), template (Pod blueprint for creating new ones).
① Replicas
② Selector
③ Template
How They Connect
① Replicas — "How many Pods do I need?"
Definition: The desired number of Pod replicas. The RS controller constantly ensures exactly this many Pods matching the selector are running. Default is 1.
spec:
  replicas: 3   # I want exactly 3 identical Pods at all times
② Selector — "Which Pods belong to me?"
Definition: A label query that identifies which Pods this RS owns. The RS counts Pods matching this selector to determine actual count. Selector is immutable after creation — you cannot change it.
spec:
  selector:
    matchLabels:           # Simple key=value match
      app: web
    matchExpressions:      # Advanced set-based (optional)
    - key: tier
      operator: In         # In, NotIn, Exists, DoesNotExist
      values: [frontend]
Critical Rule

The selector is immutable. You cannot change it after creation. If you need a different selector, delete the RS and create a new one.

③ Template — "What does each Pod look like?"
Definition: The Pod specification used as a blueprint when creating new Pods. Contains image, ports, resources, probes, volumes. Template labels must match the selector.
spec:
  template:
    metadata:
      labels:
        app: web        # ← MUST match selector
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
How the Three Pillars Connect
ReplicaSet: web-rs

① replicas: 3 → "I need 3 Pods"
② selector: app=web → counts Pods with app=web → actual=2
③ template: nginx:1.25 → creates 1 Pod from template

Now: desired=3, actual=3 ✓
The selector finds existing Pods. The replicas count says how many. The template creates new ones. If selector labels don't match template labels, the API server rejects the RS.

05 The Reconciliation Loop ▶

Definition — Reconciliation LoopThe continuous process where the RS controller compares desired state (replicas: 3) with actual state (matching Pods count), then takes action to make them equal. Runs every ~5 seconds and reacts to watch events for faster response.
① Count
② Compare
③ Too Few
④ Too Many
⑤ Just Right
⑥ Repeat
① Count — How many matching Pods exist?
RS controller → API: "List Pods where app=web" → actual = 2
The RS uses its selector to find all matching Pods. It counts them. This is the "actual" count. Doesn't matter who created them — if labels match, they're counted.
② Compare — actual vs desired
actual = 2 vs desired = 3 → MISMATCH!
Three outcomes: actual < desired (create), actual > desired (delete), actual = desired (nothing).
③ actual < desired → CREATE Pods
Need 3, have 2 → create 1

Pod 1 ✓ Pod 3 ✓ Pod 4 CREATING

RS sets ownerReferences on new Pod → Pod is "owned" by this RS
New Pods are created from the template. Each gets ownerReferences pointing to the RS. Pod gets a random suffix name like web-rs-x7k2j.
④ actual > desired → DELETE Pods
Need 3, have 5 → delete 2

1 ✓ 2 ✓ 3 ✓ 4 DEL 5 DEL

Uses Scale Down Algorithm to choose WHICH Pods (section 10)
When too many Pods exist, RS uses the scale-down algorithm (5-step priority) to decide which to delete. Not random.
⑤ actual = desired → Do nothing ✓
desired = 3 = actual = 3 → ✓ Balanced
⑥ Repeat — Every ~5 seconds, forever
Loop → count → compare → act → wait ~5s → count → compare → ∞
Also reacts to watch events for faster response. Even if an event is missed, the periodic recount catches it.

06 Full ReplicaSet YAML — Every Field

apiVersion: apps/v1               # MUST be apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
  namespace: production
  labels:                          # Labels on the RS itself
    app: web
spec:
  replicas: 3                      # ① How many Pods
  selector:                        # ② Which Pods (IMMUTABLE)
    matchLabels:
      app: web
  template:                        # ③ Pod blueprint
    metadata:
      labels:
        app: web                # MUST match selector
    spec:
      containers:
      - name: nginx
        image: nginx:1.25
        ports:
        - containerPort: 80
        resources:
          requests:
            cpu: "100m"
            memory: "64Mi"
          limits:
            cpu: "200m"
            memory: "128Mi"
        readinessProbe:
          httpGet:
            path: /
            port: 80
$ kubectl apply -f replicaset.yaml replicaset.apps/web-rs created $ kubectl get rs web-rs NAME DESIRED CURRENT READY AGE web-rs 3 3 3 12s

08 Update & Replace

# Method 1: Edit file then apply
kubectl apply -f replicaset.yaml

# Method 2: Edit live object
kubectl edit rs web-rs

# Method 3: Replace (delete + create)
kubectl replace -f replicaset.yaml
Template Changes Don't Affect Running Pods

If you change the image in the template (nginx:1.25 → nginx:1.26), existing Pods are NOT updated. Only NEW Pods (from scale-up or replacement) use the new template. This is why Deployments exist — they do rolling updates by creating a new RS.

Method A — kubectl scale (in-memory, instant)
kubectl scale rs web-rs --replicas=5   # Scale up
kubectl scale rs web-rs --replicas=2   # Scale down

Changes replica count in-memory on API server. Does NOT update your YAML file on disk.
Method B — Edit YAML file then apply

kubectl apply -f replicaset.yaml
Updates both the file AND the live object. Best practice — Git stays in sync.
Method C — kubectl patch
kubectl patch rs web-rs -p '{"spec":{"replicas":5}}'
Method D — HorizontalPodAutoscaler
kubectl autoscale rs web-rs --min=2 --max=10 --cpu-percent=80
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: web-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: ReplicaSet
    name: web-rs
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 80
⚠ In-Memory Drift Warning
Danger — YAML Drift

If you kubectl scale to 5 but your YAML says replicas: 3, the next kubectl apply resets it to 3. Always update the file when scaling, or use GitOps tools that detect drift.

10 Scale-Down Algorithm ▶

Definition — Scale-Down AlgorithmWhen RS deletes Pods (scale down), it follows a 5-step priority system. It's not random — it minimizes disruption.
① Pending first
② Deletion cost
③ Node spread
④ Newer first
⑤ Random
Full example
Priority 1 — Delete Pending (unscheduled) Pods first
Pod A: Pending → DELETE FIRST
Pod B: Running → kept
Pod C: Running → kept
Unscheduled Pods aren't doing work. Removing them is instant — no graceful shutdown.
Priority 2 — Check Pod Deletion Cost annotation
Pod A: cost=-100 → DELETE (low cost)
Pod B: cost=0 → maybe
Pod C: cost=1000 → KEEP (high cost)
Annotation controller.kubernetes.io/pod-deletion-cost. Lower cost = deleted first. Default 0. Negative = prefer deletion.
Priority 3 — Delete from nodes with MORE Pods
node-a: 3 Pods, node-b: 1 Pod
Delete from node-a first → spreads evenly across nodes
Kubernetes prefers even distribution. It removes from nodes with the most replicas.
Priority 4 — Delete NEWER Pods first
Pod A: 5 days old → kept
Pod C: 3 min old → DELETE (newest)
Older Pods are proven stable. Newer Pods are less tested and cheaper to lose.
Priority 5 — Random (if all else equal)
If Pods score equally on all criteria, one is picked randomly.
Full Example — Scale 5 → 3
Pod A: Pending → ① DELETE #1
Pod B: cost=-50 → ② DELETE #2
Pod C: cost=0, node-a, 1d → kept
Pod D: cost=0, node-b, 5d → kept
Pod E: cost=500, node-b, 3d → kept (protected)

11 Pod Deletion Cost

DefinitionAn annotation that tells the RS how "expensive" it is to delete a Pod. Lower cost = deleted first. Any integer (negative to positive). Default: 0.
# Protect a Pod from scale-down
kubectl annotate pod web-rs-x7k2j controller.kubernetes.io/pod-deletion-cost=1000

# Prefer this Pod for deletion
kubectl annotate pod web-rs-m9p4r controller.kubernetes.io/pod-deletion-cost=-100
SRE Use Case

Set high cost on Pods with warm caches (Redis data, ML models in memory). Set negative cost on Pods you know are unhealthy.

12 Deleting a ReplicaSet ▶

Normal (cascade)
Orphan (keep Pods)
Internal flow
Normal — RS + all Pods deleted
kubectl delete rs web-rs   # Deletes RS AND all its Pods
Orphan — RS deleted, Pods survive
kubectl delete rs web-rs --cascade=orphan   # Pods keep running!
RS deleted
Pod 1 (orphan, still running)
Pod 2 (orphan, still running)
Pod 3 (orphan, still running)
⚠ No controller. If one dies, nobody recreates it.
Internal flow
① kubectl delete rs web-rs
② API server marks RS for deletion
③ Garbage collector finds Pods with ownerReferences → web-rs
④ Garbage collector deletes those Pods
⑤ RS removed from etcd

13 Orphaning Pods

# Step 1: Delete RS but keep Pods
kubectl delete rs web-rs --cascade=orphan

# Step 2: Pods still running
kubectl get pods -l app=web   # All 3 alive

# Step 3: Create new RS (or Deployment) with same selector → adopts Pods
kubectl apply -f new-replicaset.yaml
SRE Use Case — Zero-Downtime Migration

Orphan RS, then create a Deployment with the same selector — it adopts existing Pods without restarting them.

15 Label Matching Edge Cases ▶

Case 1: Pods After RS
Case 2: Pods Before RS
Adoption Rules
Case 1 — Pods created AFTER RS with matching labels
RS: web-rs (desired: 3, actual: 3) ← balanced

Someone runs: kubectl run extra --image=nginx --labels="app=web"

RS counts: actual = 4! 4 > 3 → DELETES 1 Pod
RS detects too many matching Pods and deletes excess. You can't sneak extra Pods past a RS.
Case 2 — Pods with matching labels exist BEFORE RS
2 Pods already exist with app=web:
Pod A Pod B

You create RS (selector: app=web, replicas: 3):
RS adopts Pod A + Pod B (sets ownerReferences)
Creates 1 more → Pod C

A (adopted) ✓ B (adopted) ✓ C (new) ✓
RS adopts orphan Pods matching its selector, then creates extras to reach desired count.
Adoption Rules
ScenarioResult
Orphan Pod (no owner) matches selectorAdopted
Pod owned by ANOTHER RS matchesNOT adopted
More orphans than desired replicasAdopt all, then delete excess
Warning — Accidental Adoption

Creating a RS with selector app=web when 10 naked Pods have app=web: RS adopts all 10, then deletes 7 (if desired=3). Check for existing Pods before creating RS!

If DESIRED ≠ CURRENT or CURRENT ≠ READY for > 5 min, something is wrong. Alert immediately.

17 Best Practices

Always Use Deployments

Never create RS directly in production. Use Deployments — they add rolling updates, rollback, revision history.

Label Hygiene

Use specific label combos: app=web, version=v2, component=frontend. Prevents accidental adoption.

Monitor the Gap

Alert when desired ≠ ready for > 5 min. Earliest signal of scheduling/image/health issues.

No In-Memory Scale in GitOps

If using GitOps (ArgoCD, Flux), never kubectl scale. Always update YAML and commit.

Set PDBs

For RS with ≥2 replicas, create PodDisruptionBudgets to protect during drains/upgrades.

Final SRE Wisdom

ReplicaSets are the engine of Kubernetes self-healing. Deployments are the steering wheel. Understand the engine (reconciliation loop, label matching, scale-down algorithm) so you can diagnose issues. But always drive with the steering wheel (Deployments).
