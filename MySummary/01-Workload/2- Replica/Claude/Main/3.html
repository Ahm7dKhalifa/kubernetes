01 What Is a ReplicaSet & Why?

Definition — ReplicaSetA controller that ensures a specified number of identical Pod replicas are always running. If a Pod dies → creates one. Too many → deletes extras. Runs a reconciliation loop every ~5 seconds.
BenefitWhat It Means
High Availability3 replicas → if 1 dies, 2 still serve traffic while RS creates replacement
Load BalancingMultiple Pods behind a Service distribute traffic evenly
ScalingChange replicas: 3→10 instantly. Manual or automatic (HPA)
Self-HealingPod crash, OOM, node death → RS detects and replaces automatically

04 Reconciliation Loop ▶

① Count
② Compare
③ Too Few
④ Too Many
⑤ Equal
⑥ Repeat
① Count matching Pods
RS → API: "List Pods where app=web" → actual = 2
② Compare actual vs desired
actual=2 vs desired=3 → MISMATCH
③ actual < desired → CREATE
Pod 1 Pod 3 Pod 4 CREATING
RS creates Pod from template, sets ownerReferences
④ actual > desired → DELETE
1 2 3 4 DEL 5 DEL
Uses scale-down algorithm (section 12)
⑤ actual = desired → Do nothing ✓
desired=3 = actual=3 → balanced ✓
⑥ Repeat every ~5 seconds, forever
Loop → count → compare → act → wait → count → ∞
Also reacts to watch events for faster response.

  name: web-rs

    app: web

  selector:                          # ② Which Pods (IMMUTABLE after creation)

          name: http

06 Pod with Deletion Cost — Full YAML

Definition — Pod Deletion CostAnnotation controller.kubernetes.io/pod-deletion-cost tells the RS which Pods to delete first during scale-down. Lower cost → deleted first. Default: 0. Range: any integer.

YAML — Pod with High Deletion Cost (protected from scale-down)

apiVersion: v1
kind: Pod
metadata:
  name: cache-warm-pod
  labels:
    app: web
    tier: frontend
  annotations:
    controller.kubernetes.io/pod-deletion-cost: "1000"  # HIGH cost = delete LAST
spec:
  containers:
  - name: nginx
    image: nginx:1.25

YAML — Pod with Negative Cost (preferred for deletion)

apiVersion: v1
kind: Pod
metadata:
  name: unhealthy-pod
  labels:
    app: web
    tier: frontend
  annotations:
    controller.kubernetes.io/pod-deletion-cost: "-100"  # LOW cost = delete FIRST
spec:
  containers:
  - name: nginx
    image: nginx:1.25

Set Deletion Cost Imperatively

# Protect a Pod
kubectl annotate pod web-rs-x7k2j controller.kubernetes.io/pod-deletion-cost="1000"

# Mark for preferred deletion
kubectl annotate pod web-rs-m9p4r controller.kubernetes.io/pod-deletion-cost="-100"

# Remove annotation (back to default 0)
kubectl annotate pod web-rs-x7k2j controller.kubernetes.io/pod-deletion-cost-

ReplicaSet Template with Deletion Cost Built-In

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
      annotations:
        controller.kubernetes.io/pod-deletion-cost: "500"  # Every Pod created by this RS gets cost=500
    spec:
      containers:
      - name: nginx
        image: nginx:1.25

08 Update Image — What Happens? ▶

Critical RuleWhen you change the image in a RS template, existing running Pods are NOT updated. Only newly created Pods (from scale-up or crash replacement) will use the new image. This is the fundamental limitation of RS compared to Deployments.
① Before
② Change Template
③ What Happens
④ The Problem
⑤ Fix A: Manual
⑥ Fix B: Deployment
① Before — All 3 Pods running nginx:1.25
RS: web-rs (template: nginx:1.25)
Pod 1 (nginx:1.25) Pod 2 (nginx:1.25) Pod 3 (nginx:1.25)
All running v1.25 ✓
② You change the template image to nginx:1.26
# Method 1: Edit YAML file, change image, apply
# image: nginx:1.25 → image: nginx:1.26
kubectl apply -f replicaset.yaml

# Method 2: Edit live object
kubectl edit rs web-rs
# Change image in editor, save

# Method 3: Patch
kubectl patch rs web-rs --type='json' \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/image","value":"nginx:1.26"}]'
③ What happens — NOTHING to existing Pods!
RS: web-rs (template: nginx:1.26) ← template updated ✓

Pod 1 (nginx:1.25) Pod 2 (nginx:1.25) Pod 3 (nginx:1.25)
⚠ ALL 3 Pods STILL running the OLD image 1.25!
The template changed but RS does NOT restart or replace running Pods.
The RS only checks count — "do I have 3 matching Pods?" Yes → do nothing. It doesn't check whether Pod images match the template. The reconciliation loop only compares desired count vs actual count, not template content.
④ The Problem — Mixed Versions
When a Pod crashes or is deleted, the RS creates a replacement using the NEW template:

Pod 1 (nginx:1.25) Pod 4 (nginx:1.26) NEW! Pod 3 (nginx:1.25)
⚠ MIXED VERSIONS! Pod 1 and 3 run 1.25, Pod 4 runs 1.26
This is inconsistent and unpredictable. Some users hit v1.25, some hit v1.26.
⑤ Fix A — Manually delete all old Pods (causes downtime)
# Step 1: Update the template image
kubectl patch rs web-rs --type='json' \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/image","value":"nginx:1.26"}]'

# Step 2: Delete ALL Pods — RS recreates them with new image
kubectl delete pods -l app=web
Pod 1 DEL Pod 2 DEL Pod 3 DEL
⚠ DOWNTIME — all Pods dead simultaneously!

Pod 4 (1.26) creating Pod 5 (1.26) creating Pod 6 (1.26) creating
All new Pods use 1.26 ✓ but there was downtime ✗
Problem

Deleting all Pods at once causes downtime. No traffic can be served until new Pods are ready. This is why RS alone is not suitable for production image updates.

⑥ Fix B — Use a Deployment instead (zero downtime)
# Deployments handle image updates with ZERO downtime:
kubectl set image deployment/web-deploy nginx=nginx:1.26

# What happens internally:
# 1. Deployment creates NEW ReplicaSet (template: 1.26)
# 2. New RS scales up: 0→1→2→3
# 3. Old RS scales down: 3→2→1→0
# 4. Each new Pod must pass readiness before old Pod is killed
# 5. At NO point is there zero healthy Pods
Deployment Rolling Update (zero downtime):

RS-v1 (1.25): 3 → RS-v1: 2 + RS-v2 (1.26): 1 → RS-v1: 1 + RS-v2: 2 → RS-v1: 0 + RS-v2: 3 ✓
SRE Principle

Never update images via ReplicaSet in production. Always use Deployments. The Deployment creates a new RS with the new template and does a rolling replacement — zero downtime, with rollback capability.

09 Update Replicas — What Happens? ▶

Key DifferenceUnlike image changes, replica count changes take effect immediately. The RS acts on the new count within seconds.
Scale Up 3→5
Scale Down 5→2
Scale to 0
All Methods
⚠ Drift Warning
Scale Up: replicas 3 → 5
RS: desired=5, actual=3 → 3 < 5 → create 2 Pods

Pod 1 ✓ Pod 2 ✓ Pod 3 ✓ Pod 4 creating Pod 5 creating
Within seconds: all 5 Pods running ✓
New Pods are created from the current template. They go through normal scheduling → image pull → start → readiness. The RS creates all needed Pods immediately (not one-by-one).
$ kubectl scale rs web-rs --replicas=5 replicaset.apps/web-rs scaled $ kubectl get rs web-rs NAME DESIRED CURRENT READY AGE web-rs 5 5 3 2m # 2 still starting $ kubectl get rs web-rs # 30s later NAME DESIRED CURRENT READY AGE web-rs 5 5 5 2m30s # All ready ✓
Scale Down: replicas 5 → 2
RS: desired=2, actual=5 → 5 > 2 → delete 3 Pods

Pod 1 ✓ Pod 2 ✓ Pod 3 DEL Pod 4 DEL Pod 5 DEL
RS uses the scale-down algorithm to choose WHICH 3 to delete (section 12)
Deletion order follows the 5-step priority: ① Pending first → ② lowest deletion cost → ③ nodes with most Pods → ④ newest Pods → ⑤ random. Deleted Pods go through normal graceful shutdown (SIGTERM → grace period → SIGKILL).
$ kubectl scale rs web-rs --replicas=2 replicaset.apps/web-rs scaled $ kubectl get pods -l app=web NAME READY STATUS AGE web-rs-a3b8n 1/1 Running 5m web-rs-x7k2j 1/1 Running 5m web-rs-m9p4r 1/1 Terminating 5m # Being deleted web-rs-k2j7n 1/1 Terminating 2m # Being deleted web-rs-p4r5t 1/1 Terminating 2m # Being deleted
Scale to 0 — Delete all Pods, keep RS
kubectl scale rs web-rs --replicas=0
RS: desired=0, actual=3 → delete ALL 3 Pods

RS still exists (with template), but 0 Pods running
Useful for: maintenance, cost saving, temporary shutdown. Scale back up anytime.
# Bring back later:
kubectl scale rs web-rs --replicas=3   # 3 new Pods created instantly
All Methods to Change Replica Count
# Method 1: kubectl scale (in-memory, instant)
kubectl scale rs web-rs --replicas=5

# Method 2: Edit YAML file, then apply (best for GitOps)
# Change replicas: 3 → replicas: 5 in file
kubectl apply -f replicaset.yaml

# Method 3: kubectl edit (live edit)
kubectl edit rs web-rs
# Change replicas in editor, save

# Method 4: kubectl patch
kubectl patch rs web-rs -p '{"spec":{"replicas":5}}'

# Method 5: Conditional scale (safety check)
kubectl scale rs web-rs --replicas=5 --current-replicas=3
# Only scales if current is exactly 3 — prevents race conditions

# Method 6: HPA (automatic based on metrics)
kubectl autoscale rs web-rs --min=2 --max=10 --cpu-percent=80
⚠ In-Memory Drift Warning
Your YAML file says: replicas: 3
You run: kubectl scale rs web-rs --replicas=5
Live cluster: 5 Pods running ✓

Later, teammate runs: kubectl apply -f replicaset.yaml
YAML says 3 → cluster scales BACK DOWN to 3! Your scale is lost.
Fix

Always update the YAML file when scaling: change replicas: 5 in the file, commit to Git, then kubectl apply. This keeps your file and cluster in sync.

10 What Can You Change on a Running RS?

FieldChangeable?Takes Effect?How
spec.replicasYesImmediatelykubectl scale / edit / patch
spec.template.spec.containers[*].imageYes (template)Only new PodsEdit / patch — existing Pods unchanged
spec.template.spec.containers[*].envYes (template)Only new PodsSame — existing Pods keep old env
spec.template.spec.containers[*].resourcesYes (template)Only new PodsSame
spec.template.metadata.labelsYes (template)Only new PodsMust still match selector
spec.selectorNo — IMMUTABLE—Must delete and recreate RS
metadata.labelsYesImmediatelyLabels on the RS itself (not Pods)
Key Insight

replicas change = instant effect. template change = only affects future Pods. selector change = impossible. This is the core behavior you must understand for CKAD and SRE work.

12 Scale-Down Algorithm ▶

① Pending
② Cost
③ Node Spread
④ Newest
⑤ Random
Full Example
Priority 1 — Delete Pending Pods first
Pod A: Pending → DELETE FIRST (not doing work, instant removal)
Priority 2 — Lower deletion cost = delete first
cost=-100 → DELETE
cost=0 → maybe
cost=1000 → KEEP
Priority 3 — Delete from nodes with MORE Pods
node-a: 3 Pods, node-b: 1 Pod
Delete from node-a → even distribution
Priority 4 — Delete NEWER Pods first
Pod: 5 days old → kept
Pod: 3 min old → DELETE (newer = less proven)
Priority 5 — Random tie-breaker
If all criteria equal → random selection.
Full Example — Scale 5→3 (delete 2)
Pod A: Pending → ① DELETE #1
Pod B: cost=-50 → ② DELETE #2
Pod C: cost=0, node-a, 1d → kept
Pod D: cost=0, node-b, 5d → kept
Pod E: cost=500 → kept (protected)

17 Monitoring & Best Practices

MetricAlert When
kube_replicaset_status_replicasactual ≠ desired > 5 min
kube_replicaset_status_ready_replicasready < desired > 5 min
Use Deployments

Never create RS directly in production. Deployments manage RS and add rolling updates + rollback.

Label Hygiene

Use specific labels: app=web,version=v2,component=frontend. Prevents accidental adoption.

No In-Memory Scale in GitOps

kubectl scale creates drift. Always update the YAML file.

Set PDBs

For ≥2 replicas, create PodDisruptionBudgets to protect during node drains.

SRE Wisdom

ReplicaSets are the engine of self-healing. Deployments are the steering wheel. Understand the engine to diagnose. Drive with the wheel in production.
