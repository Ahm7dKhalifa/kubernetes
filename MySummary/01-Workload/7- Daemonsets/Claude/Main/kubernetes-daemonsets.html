Kubernetes DaemonSets

The complete guide — one Pod per node, node selection, tolerations, rolling updates, and SRE operations. Interactive step-by-step workflows.

01 What Is a DaemonSet & Why?

Definition — DaemonSetA DaemonSet ensures that exactly one copy of a Pod runs on every node (or a subset of nodes) in the cluster. When a new node is added, the DaemonSet automatically places a Pod on it. When a node is removed, the Pod is garbage collected. It's the workload controller for node-level infrastructure.
Definition — One Pod Per NodeUnlike Deployments (which run N Pods wherever the scheduler decides), a DaemonSet ties Pods to nodes: 1 node = 1 Pod. You don't set replicas — the number of Pods equals the number of matching nodes.
Use CaseExampleWhy DaemonSet?
Log collectionFluentd, Filebeat, Fluent BitMust collect logs from every node
Monitoring agentPrometheus Node Exporter, DatadogMust scrape metrics from every node
Network pluginCalico, Cilium, Flannel, WeaveCNI must run on every node for networking
Storage pluginCeph, GlusterFS, LonghornCSI must run on every node for volumes
Security agentFalco, Sysdig, AquaMust audit every node
Node maintenancekured (reboot daemon)Must be present on every node to handle reboots
GPU driverNVIDIA device pluginMust install driver on every GPU node
Analogy

A Deployment is a pizza delivery service — you order 3 pizzas, they go wherever. A DaemonSet is a fire alarm system — exactly one alarm on every floor (node). Add a new floor? It automatically gets an alarm. Remove a floor? The alarm goes with it.

02 How It Works ▶

Architecture
Scheduling
No replicas field
One Pod per node — automatic
DaemonSet: log-agent

Node-1 → log-agent-abc12
Node-2 → log-agent-def34
Node-3 → log-agent-ghi56
Node-4 (new) → log-agent-jkl78 ← auto-placed!

4 nodes = 4 Pods. Always. Automatically.
How Pods are scheduled on nodes
Before v1.12: DaemonSet controller placed Pods directly (bypassed scheduler).

v1.12+ (current): DaemonSet controller creates Pods with nodeAffinity targeting each node. The default scheduler schedules them. This means DaemonSet Pods respect taints, tolerations, node affinity, and priority — just like any other Pod.
The DaemonSet controller watches nodes. For each eligible node, it ensures exactly one Pod exists. If a Pod is missing, it creates one. If an extra Pod exists, it deletes it.
No replicas field — nodes determine Pod count
Deployment: replicas: 3 → always 3 Pods
DaemonSet: No replicas field → Pods = number of matching nodes

3 nodes → 3 Pods
Add 2 nodes → 5 Pods
Remove 1 node → 4 Pods

You never set a Pod count. It's always "one per node" (or "one per matching node" if using nodeSelector/affinity).

04 Full DaemonSet YAML — Every Field Explained

apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-agent
  namespace: kube-system            # Infra DaemonSets often go here
  labels:
    app: log-agent
spec:
  # NO replicas field! Pod count = number of matching nodes

  updateStrategy:
    type: RollingUpdate              # RollingUpdate (default) or OnDelete
    rollingUpdate:
      maxUnavailable: 1             # Max Pods that can be down during update
      maxSurge: 0                   # Extra Pods allowed (v1.22+)

  selector:
    matchLabels:
      app: log-agent

  template:
    metadata:
      labels:
        app: log-agent
    spec:
      tolerations:                    # Tolerate master/control-plane taints
      - key: node-role.kubernetes.io/control-plane
        effect: NoSchedule
      containers:
      - name: fluentd
        image: fluentd:v1.16
        resources:
          requests: { cpu: "100m", memory: "200Mi" }
          limits: { cpu: "200m", memory: "400Mi" }
        volumeMounts:
        - name: varlog
          mountPath: /var/log
          readOnly: true
      volumes:
      - name: varlog
        hostPath:                     # Mount node's /var/log into Pod
          path: /var/log
Key Differences from Deployment YAML① No replicas field. ② updateStrategy instead of strategy. ③ Usually includes tolerations (to run on tainted nodes like control-plane). ④ Often uses hostPath volumes (to access node-level files like /var/log).

06 Default: Runs on All Nodes ▶

All worker nodes
Why not control-plane?
Include control-plane
Default — Pods on all worker nodes
control-plane ✗ no Pod (tainted)
worker-1 → log-agent Pod
worker-2 → log-agent Pod
worker-3 → log-agent Pod
By default, DaemonSet Pods run on all nodes EXCEPT those with taints that the Pod doesn't tolerate. Control-plane nodes typically have node-role.kubernetes.io/control-plane:NoSchedule taint, so DaemonSet Pods don't run there unless you add a matching toleration.
Why not on control-plane?
Control-plane node has taint:
node-role.kubernetes.io/control-plane:NoSchedule

This taint prevents ALL Pods from being scheduled there (unless they tolerate it). This protects the control-plane from workload interference.

Some DaemonSets SHOULD run on control-plane (logging, monitoring, CNI). You must add a toleration.
Add toleration to run on control-plane too
spec:
  template:
    spec:
      tolerations:
      - key: node-role.kubernetes.io/control-plane
        effect: NoSchedule
      # OR tolerate ALL taints (run EVERYWHERE):
      - operator: Exists
With toleration:
control-plane → log-agent Pod ← now runs here too!
worker-1 → log-agent Pod
worker-2 → log-agent Pod

07 nodeSelector — Run on Specific Nodes ▶

Definition — nodeSelectorThe simplest way to restrict a DaemonSet to specific nodes. The DaemonSet only creates Pods on nodes that have ALL the specified labels. Simple key-value matching — no operators or complex logic.
Example
YAML
Label nodes
DaemonSet: gpu-driver (nodeSelector: gpu=true)

node-1 (gpu=true) → gpu-driver Pod ✓
node-2 (no gpu label) ✗ no Pod
node-3 (gpu=true) → gpu-driver Pod ✓
node-4 (no gpu label) ✗ no Pod

Only 2 Pods (on GPU nodes). Not all nodes.
spec:
  template:
    spec:
      nodeSelector:
        gpu: "true"          # Only nodes with this label
      containers:
      - name: gpu-driver
        image: nvidia/driver:latest
# Label a node
kubectl label node node-1 gpu=true

# Verify
kubectl get nodes --show-labels | grep gpu

# Remove label (DaemonSet Pod will be removed from this node)
kubectl label node node-1 gpu-
DynamicIf you add the gpu=true label to a new node, the DaemonSet automatically creates a Pod on it. If you remove the label, the Pod is removed. The DaemonSet controller constantly reconciles.

08 Node Affinity — Advanced Node Selection ▶

DefinitionMore powerful than nodeSelector. Supports operators (In, NotIn, Exists, DoesNotExist, Gt, Lt) and soft preferences (preferred vs required). Use when nodeSelector isn't flexible enough.
Required (hard)
Preferred (soft)
requiredDuringSchedulingIgnoredDuringExecution
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: disk-type
                operator: In
                values: ["ssd", "nvme"]
Pod only runs on nodes where disk-type is ssd OR nvme. Hard requirement — no match, no Pod.
preferredDuringSchedulingIgnoredDuringExecution
          preferredDuringSchedulingIgnoredDuringExecution:
          - weight: 1
            preference:
              matchExpressions:
              - key: zone
                operator: In
                values: ["us-east-1a"]
Prefer nodes in us-east-1a, but run elsewhere if needed. Soft preference — best effort.

09 Tolerations — Run on Tainted Nodes ▶

Definition — Taints & TolerationsNodes can have taints that repel Pods. Pods need tolerations to be scheduled on tainted nodes. DaemonSets often need tolerations because infrastructure Pods must run everywhere — even on tainted nodes like control-plane or dedicated GPU nodes.
Common taints
Tolerate specific
Tolerate ALL
Common taints you'll encounter
TaintOnMeaning
node-role.kubernetes.io/control-plane:NoScheduleControl-planeNo workloads on master
node.kubernetes.io/not-ready:NoExecuteUnhealthy nodesEvict Pods from failing node
node.kubernetes.io/unreachable:NoExecuteUnreachable nodesEvict when node can't be contacted
node.kubernetes.io/disk-pressure:NoScheduleLow disk nodesDon't schedule new Pods
dedicated=gpu:NoScheduleGPU nodesOnly GPU workloads allowed
Tolerate a specific taint
tolerations:
# Tolerate control-plane
- key: node-role.kubernetes.io/control-plane
  operator: Exists
  effect: NoSchedule

# Tolerate GPU dedicated nodes
- key: dedicated
  operator: Equal
  value: "gpu"
  effect: NoSchedule
Tolerate ALL taints — run absolutely everywhere
tolerations:
- operator: Exists             # Match ANY taint key
  # No key, no value, no effect = tolerate everything
control-plane (tainted) → Pod ✓
gpu-node (tainted) → Pod ✓
worker-1 → Pod ✓
unhealthy-node (tainted) → Pod ✓

Use for critical infrastructure: CNI plugins, kube-proxy, log agents that MUST run on every node regardless of taints.

10 RollingUpdate Strategy ▶

DefinitionDefault update strategy. Updates Pods one node at a time. On each node: old Pod is killed, new Pod is created. Controlled by maxUnavailable (how many nodes can have their Pod down simultaneously) and maxSurge (extra Pods allowed during update, v1.22+).
Flow
maxUnavailable
maxSurge
YAML
Rolling Update — node by node
Update fluentd:v1.16 → v1.17 (3 nodes, maxUnavail=1):

T=0: N1:v1.16 | N2:v1.16 | N3:v1.16
T=1: N1:kill→v1.17✓ | N2:v1.16 | N3:v1.16
T=2: N1:v1.17 | N2:kill→v1.17✓ | N3:v1.16
T=3: N1:v1.17 | N2:v1.17 | N3:kill→v1.17✓

Done. All nodes on v1.17.
maxUnavailable — how many nodes can be down
maxUnavailableBehavior (10 nodes)Speed
1 (default)1 node updated at a timeSlowest, safest
33 nodes updated simultaneouslyFaster
25%25% of nodes (= 2-3 nodes)Scaled
100%ALL nodes at once (like Recreate)Fastest, risky
maxSurge (v1.22+) — create new BEFORE killing old
maxSurge: 1          # Create new Pod first, then kill old
maxUnavailable: 0    # Zero downtime on each node
Without maxSurge: kill old → gap (no Pod) → create new
With maxSurge=1: create new → new ready → kill old → no gap!

Temporarily 2 DaemonSet Pods on one node. Requires node to have capacity.
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1    # 1 node at a time
      maxSurge: 0           # No extra Pods (default)

11 OnDelete Strategy ▶

DefinitionTemplate is updated but Pods are NOT automatically replaced. You must manually delete each Pod. When deleted, the DaemonSet controller recreates it with the new template. Full manual control over update timing — one node at a time, at your pace.
Flow
YAML
Update template (fluentd v1.16 → v1.17) with OnDelete:

N1:v1.16 | N2:v1.16 | N3:v1.16 ← nothing happens!

kubectl delete pod <pod-on-N1> → N1:v1.17 ← updated
...verify N1 is healthy...
kubectl delete pod <pod-on-N2> → N2:v1.17
kubectl delete pod <pod-on-N3> → N3:v1.17
updateStrategy:
  type: OnDelete
SRE Use Case

Use OnDelete for critical node-level infrastructure (CNI, kube-proxy) where you want to verify each node after update before proceeding. A bad CNI update can take down all networking on a node.

13 Pod Eviction & Node Drain ▶

Definition — kubectl drainSafely evicts all Pods from a node (for maintenance). DaemonSet Pods are NOT evicted by default because they're infrastructure — you must add --ignore-daemonsets flag. Even then, the DaemonSet Pod is only removed when the node is actually deleted.
Drain behavior
Commands
kubectl drain node-2 --ignore-daemonsets

Deployment Pods: evicted → rescheduled to other nodes
DaemonSet Pods: STAY on the node (ignored by drain)

DaemonSet Pods are infrastructure. They should keep running even during maintenance — they're collecting the node's final logs, monitoring its health, etc.
# Drain node (ignoring DaemonSet Pods)
kubectl drain node-2 --ignore-daemonsets --delete-emptydir-data

# Uncordon node (allow scheduling again)
kubectl uncordon node-2

14 hostNetwork, hostPID, hostPath

Why DaemonSets often need host-level accessDaemonSet Pods are infrastructure agents that need to interact with the node directly. They often need: hostNetwork (use node's network stack), hostPID (see node's processes), hostPath (read node's files like /var/log).
spec:
  template:
    spec:
      hostNetwork: true       # Use node's network (for network plugins)
      hostPID: true           # See node's processes (for security agents)
      volumes:
      - name: varlog
        hostPath:             # Mount node's filesystem (for log collectors)
          path: /var/log
      - name: dockersock
        hostPath:             # Access container runtime (for monitoring)
          path: /var/run/docker.sock
Security Warning

hostNetwork, hostPID, and hostPath are powerful — they break Pod isolation. Only use for trusted infrastructure Pods. In production, restrict these via PodSecurityAdmission or OPA/Gatekeeper policies.

16 Monitoring & Best Practices

Set resource requests and limits

DaemonSet Pods run on EVERY node. A memory leak multiplied across 100 nodes can consume enormous cluster resources. Always set limits.

Use the exam trick: Deployment → DaemonSet

Generate Deployment YAML → change kind to DaemonSet → remove replicas → remove strategy → apply. Fastest way to create DaemonSets on the exam.

Add tolerations for control-plane if needed

Logging and monitoring agents should run on ALL nodes including control-plane. Add the toleration explicitly.

Use priorityClassName for critical DaemonSets

system-node-critical prevents eviction under resource pressure. Your CNI and logging should never be evicted.

Use OnDelete for CNI/kube-proxy updates

A bad CNI update can take down networking on the entire node. Update one node manually, verify, then continue.

SRE Wisdom

DaemonSets are your eyes and ears on every node. If your logging DaemonSet goes down, you're flying blind. If your CNI DaemonSet breaks, the node loses networking. Treat DaemonSet updates with the same care as control-plane upgrades — one node at a time, verify after each.
