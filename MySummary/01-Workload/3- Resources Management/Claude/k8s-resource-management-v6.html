I.1 Foundations · What this guide is

Why resource management is the operational core of Kubernetes

Definition Principles Diagram
Resource management (in Kubernetes)

The set of mechanisms by which a cluster decides how much CPU, memory, storage, and specialized hardware each container may request, consume, and be denied — and how the scheduler, kubelet, and node-level kernel features cooperate to enforce those decisions.

Three things break in production: cost (you're paying for capacity nobody uses), reliability (one workload steals from another), and capacity planning (you can't say with confidence how much headroom you have). All three are downstream of resource management. Get this layer right and most other things become tractable.

Five Operating Principles
  1. Declare everything. A container with no resource declarations is BestEffort — first to be evicted, last to be sized correctly. Never ship blank.
  2. Requests are for scheduling, limits are for enforcement. They answer different questions and should be tuned independently.
  3. Measure before you size. p75 of historical usage is a better request than your intuition. VPA in advisor mode is free measurement.
  4. Compose the controls. LimitRange + ResourceQuota + PriorityClass + PDB + HPA work together. Each closes a hole the others can't.
  5. Treat sizing as a loop. Measure → recommend → apply → re-measure. Workloads drift; sizing reviews are quarterly, not one-shot.
The Resource Management Stack

This guide walks the stack top-down. Pod-level controls come first because they're the unit of declaration; namespace-level controls next because they're how platform teams enforce policy; autoscaling because it operationalizes the declarations; node-level last because it's where the kernel actually does the work; and the SRE playbook closes the loop with patterns, troubleshooting, and a pre-flight checklist.

I.2 Foundations · The mental model

From kubectl apply to a running container: the five gates

Definition Principles Diagram Pitfalls
The five gates

Every pod's resource declaration is read and re-interpreted by five distinct components before the workload runs. Understanding which component owns which decision is the single most useful debugging skill in Kubernetes operations — because failure messages always tell you which gate the request died at.

Why this matters
  1. Errors are layer-specific. "Forbidden: exceeded quota" is gate 2. "FailedScheduling: insufficient cpu" is gate 3. "OOMKilled" is gate 5. Knowing the gate halves your debugging time.
  2. Each gate has its own config surface. Admission policies, scheduler profiles, kubelet flags — they live in different files maintained by different teams.
  3. Caching and timing matter. The scheduler caches node allocatable; the kubelet caches cgroup state. Stale caches cause "impossible" placement decisions.
The Five-Gate Pipeline
Common confusions
  • "My pod is stuck Pending" — that's gate 3 (scheduler), not gate 4 (kubelet). kubectl describe pod shows the gate 3 verdict in Events.
  • "My quota didn't catch it" — quota runs at gate 2 against requests, not actual usage. A pod that requests 100m but uses 800m is invisible to quota.
  • "The OOM killer disagreed with my limit" — gate 5 (kernel) enforces against working-set bytes, not the friendly numbers in your YAML. Page cache counts differently than RSS.
I.3 Foundations · Units & quantities

The quantity type: what 500m, 2Gi, and 1e3 actually mean

Definition Principles YAML Pitfalls
Quantity

A Kubernetes-specific numeric type that combines a number with a suffix indicating its scale and base. Both CPU and memory use the same type, but with completely different conventions. The single most common cause of "my pod has the wrong size" is misreading a quantity.

Three rules for reading quantities
  1. CPU is a rate. 1 means one full CPU core / vCPU / hyperthread per second. 500m means 0.5 of a core (500 milli-cores). Decimal — base 10.
  2. Memory is a capacity. 1Gi means 1 gibibyte = 2³⁰ bytes ≈ 1.074 GB. 1G means 1 gigabyte = 10⁹ bytes. The i matters.
  3. No floating point. 0.5 works but is risky in YAML. Prefer 500m for CPU and binary suffixes for memory — they're unambiguous.

Quantity traps
  • 1G ≠ 1Gi. The first is 1,000,000,000 bytes; the second is 1,073,741,824. A 1Gi limit gives you ~7.4% more memory than a 1G limit.
  • 0.5 is valid but treacherous. YAML parsers can quietly convert it to a string or a float. Use 500m.
  • No suffix means raw bytes for memory. memory: 500 means 500 bytes — your pod will crash on startup.
  • CPU caps at integer cores at the kernel level. cpu: 1.5 ≠ 1500m? Actually they're the same — but YAML stringification can make them look different in kubectl get.
II.1 Per-pod controls · Requests & limits

Requests are a promise to the scheduler. Limits are a ceiling enforced by the kernel.

Definition Principles Diagram YAML Pitfalls Checklist
Request

The amount of CPU or memory a container asks the scheduler to reserve on a node. Used at gate 3 (scheduling) to filter and score nodes. The scheduler subtracts the sum of all pod requests from a node's allocatable to decide what fits.

Limit

The maximum amount of CPU or memory the container is allowed to use at runtime. Enforced at gate 4–5 (kubelet + kernel). CPU limits throttle via CFS quota; memory limits trigger OOM-kill when exceeded.

Decision Principles
  1. Always set both. Missing requests = BestEffort QoS = first to evict. Missing limits = unbounded blast radius for a single bad pod.
  2. Request = your typical usage. Aim for p75 of historical usage. Too high wastes capacity; too low causes scheduling failures.
  3. Memory limit ≈ request × 1.3. Leaves headroom for GC, cache warmup, transient allocations without OOM-killing the pod.
  4. CPU limit is contextual. On dedicated nodes for latency-critical services, consider omitting CPU limits. On shared nodes, always set them.
  5. Wire the limit into your runtime. GOMEMLIMIT, -XX:MaxRAMPercentage, --max-old-space-size. The runtime needs to know about the ceiling.

Common mistakes
  • Setting requests = limits without reason. Looks disciplined; in practice means no GC headroom and OOMs on the first usage spike. Only do this for genuinely flat-memory workloads.
  • Forgetting GOMEMLIMIT / JVM flags. A 2 Gi container without runtime awareness will OOM at ~1.9 Gi because the GC didn't know to be aggressive.
  • Using the same request for sidecar and main container. Envoy sidecar at 500m CPU request is 5× what it needs. Multiply by every pod in your cluster.
  • Setting memory limit without measuring. 256Mi looks reasonable until your app warms up its connection pool and OOMs. Measure first.
Quick checklist before kubectl apply
  • Every container has explicit requests.cpu, requests.memory, limits.cpu, limits.memory.
  • Ephemeral-storage request set (default 100Mi is often too low).
  • Runtime memory flag wired via Downward API — not hardcoded.
  • Memory limit ≥ request × 1.2 for GC'd languages, ≥ × 1.3 for JVM.
  • Sidecar containers sized smaller than main containers (typically 50–100m CPU, 64–128 Mi).
II.1· Daily operations · Real-world cases

From YAML to what actually happens at 9 PM on a Friday

The syntax above is the easy part. The four scenarios below are what requests-and-limits decisions actually feel like in production — handling predictable spikes, surviving overcommit, containing blast radius, and diagnosing the failures that show up when these don't compose well.

Case 1 · Handling predictable spikes (9 PM dinner rush)

The scenario

Your checkout service uses ~1 GiB of memory and ~300m CPU for 22 hours of the day. From 9 PM to 10 PM — Riyadh dinner rush — it consumes 4 GiB and 1.5 cores per pod. If you size for the average, you OOM at 9 PM every night. If you size for the peak, you waste 75% of your memory budget the rest of the day.

Four strategies (use more than one)
  1. Set requests at typical, limits at peak. requests=1Gi memory, limits=4Gi. Pod is Burstable QoS — can grow into spare node capacity during the spike without being throttled or killed.
  2. Scale out horizontally via HPA, not vertically. Instead of one pod growing from 1→4 GiB, run 4 pods at 1 GiB each during the rush. Spreads load across nodes and avoids relying on single-node headroom.
  3. Pre-scale before the spike, don't react to it. HPA reacts after metrics cross a threshold — by then your p99 latency is already bad. Use a scheduled HPA (KEDA cron trigger or minReplicas bump via CronJob) to scale at 8:45 PM.
  4. Reserve burst capacity at the node level. If 30% of node memory is reserved beyond pod requests, every Burstable pod has somewhere to grow. Without this headroom, "Burstable" is a lie — there's nothing to burst into.

🌙 Why pre-scale, not just rely on HPA?

HPA's default behavior reacts to metrics with a 15-second sync + a 60-second stabilization window. By the time it sees CPU climbing at 9:00 PM, you've already had 90 seconds of degraded p99 latency. Pre-scaling at 8:45 means the new pods are warm, connection pools are filled, and JIT caches are hot before the first dinner order lands.

Case 2 · When Σ(limits) > node capacity at runtime

The scenario (a.k.a. "the overcommit gamble")

A node has 32 GiB of memory. The scheduler placed 20 pods on it, each requesting 1 GiB (Σ requests = 20 GiB, well under 32). But each pod's limit is 3 GiB — Σ limits = 60 GiB, almost 2× the node's actual memory. This is legal. The scheduler only checks requests. Kubernetes deliberately allows limits to oversubscribe the node.

What actually happens — three regimes
  1. Happy path (most of the time). Not every pod hits its limit at once. The 20 pods collectively use ~22 GiB, well under 32. Everyone is happy. This is why overcommit exists — it's how clouds are profitable.
  2. Pressure regime. Several pods spike toward their limits simultaneously. Memory usage climbs past 28 GiB. Kubelet's memory.available signal trips the soft eviction threshold.
  3. Crash regime. Allocation continues past kernel memory.high. The Linux OOM killer fires — not Kubernetes' eviction logic — picking processes by OOM score. Usually the biggest Burstable pod dies. Sometimes the kubelet itself does, taking the whole node offline.

⚠️ The 2:00 AM scenario

You ship a config change. The new version uses 30% more memory at startup (warmup cache). All 20 pods restart in a rolling update. During the rollout, both old and new versions are running for ~60 seconds each — node memory spikes past the eviction threshold, kubelet starts evicting your own pods, the deployment stalls, and your on-call gets paged. Overcommit isn't the bug; the bug is not leaving enough headroom for a rolling update of an oversubscribed node.

Case 3 · How one unlimited pod can crash the whole node

The scenario

A new microservice ships without resource limits. The dev tested locally; it "worked." In production it has a memory leak — slow, ~50 MiB per minute. After 6 hours it's holding 18 GiB on a 32 GiB node. Other pods on that node start failing health checks, getting OOM-killed, evicted, or stuck Pending after restart. The whole node degrades, then goes NotReady. Other nodes in the cluster get the rescheduled load and the failure cascades.

The chain of consequences
  1. No limit = unbounded growth. The cgroup has no memory.max ceiling. The kernel will hand out memory until the node runs out.
  2. No request = BestEffort QoS = first to evict — but only after the kubelet detects pressure. The leaking pod kept growing without anyone noticing.
  3. Kernel cache gets squeezed. Other pods' page caches get evicted to make room. Their disk I/O latency jumps. Database connection pools start timing out.
  4. OOM killer fires on the wrong pod. Linux's OOM score considers memory usage but also priority. Sometimes the leaking pod wins (gets killed). Often a "victim" Burstable pod loses — restarted, throttled, evicted.
  5. Kubelet starves. When system memory is critically low, kubelet itself can't allocate. It stops sending heartbeats. The node goes NotReady. The scheduler reschedules everything to other nodes — which may then experience the same cascade.
Cascade: one unlimited pod → node NotReady

Resource limits aren't just about your pod's reliability — they're about being a good neighbor. A pod with no memory limit can take down every other pod on the node. Production should physically reject pods without limits via admission policy. Code review alone is not enough; humans miss things. Policy never does.

Case 4 · Daily-operations playbook (the cases you'll see most)

These are the situations that turn up week-after-week. Each one has a quick diagnosis and a quick fix — and a longer-term fix that prevents repeats.

📞 Case 4.1 · "Service is slow but CPU is only at 40%"

Diagnose: check container_cpu_cfs_throttled_seconds_total — if > 5% of CFS periods, you're being throttled. Average CPU lies because the kernel pauses between bursts.
Quick fix: raise the CPU limit by 50% and observe.
Long-term: on dedicated nodes for latency-critical services, consider dropping CPU limits entirely (keep requests). On shared nodes, size limits at 2–3× request to give burst room.

📞 Case 4.2 · "Pod restarts every 2 hours, no obvious crash"

Diagnose: kubectl describe pod → look at Last State: Terminated, Reason: OOMKilled, Exit Code: 137. Slow memory leak that takes hours to hit the limit.
Quick fix: raise memory limit by 30% to buy time.
Long-term: fix the leak. Restart-as-treatment is a smell, not a solution. Use heap profiling (pprof, JFR, Node's --inspect) to find what's growing.

📞 Case 4.3 · "Deployment rollout is stuck — new pods Pending"

Diagnose: kubectl describe pod <new-pod> → Events section. Either FailedScheduling: 0/N nodes available, insufficient cpu/memory (cluster is full) or exceeded quota (namespace quota maxed). Quotas count rolling deployments twice — old + new replicas — during the transition.
Quick fix: set maxSurge: 0, maxUnavailable: 1 on the deployment so it never has more than the target replica count.
Long-term: leave ~20% headroom in the quota for rolling updates. Audit quota usage monthly.

📞 Case 4.4 · "Memory usage looks high but the app idle"

Diagnose: for JVM, Go, .NET — runtimes hold onto memory after GC because returning it to the OS is expensive. container_memory_working_set_bytes looks scary but the workload is healthy. Look at allocation rate, not working-set.
Quick fix: none needed if working-set is stable below the limit.
Long-term: set GOMEMLIMIT / -XX:MaxRAMPercentage so the GC knows the ceiling. The runtime will GC more aggressively as it approaches the limit instead of getting killed.

📞 Case 4.5 · "Pod evicted on a node that looks fine"

Diagnose: kubectl describe node → check Conditions section. DiskPressure: True is common — container logs and emptyDir volumes fill nodefs faster than people expect.
Quick fix: log rotation on the affected pod. Bump ephemeral-storage request.
Long-term: centralize logging (Fluent Bit / Loki) so pods don't keep huge local log files. Set requests.ephemeral-storage explicitly — default 100Mi is far too low for anything that writes logs.

📞 Case 4.6 · "kubectl apply rejected: exceeded quota"

Diagnose: kubectl describe resourcequota -n <ns> shows which dimension is full. Usually requests.cpu or limits.memory.
Quick fix: ask the platform team to raise the quota — but only after verifying that current usage is justified.
Long-term: run VPA in advisor mode across the namespace and right-size the top 5 offenders. Usually recovers 15–25% of the quota without touching infrastructure.

📞 Case 4.7 · "Node went NotReady at 03:00 with no deploy"

Diagnose: kubectl describe node → likely MemoryPressure: True or KubeletNotReady. Some pod's working-set climbed enough that kubelet itself couldn't allocate. Check node memory metric just before the event.
Quick fix: cordon and drain the node; reschedule.
Long-term: raise kubeReserved.memory and systemReserved.memory. If kubelet has its own guaranteed budget, the node stays Ready even under pod pressure — eviction takes over and Kubernetes recovers gracefully.

📞 Case 4.8 · "HPA scaled to maxReplicas but latency still bad"

Diagnose: HPA is doing its job; the bottleneck is downstream. Check the database, the cache, the upstream API. Adding more pods just turns one bottleneck into a thundering herd.
Quick fix: identify the bottleneck (slow query, connection pool exhaustion, rate limit) and fix that.
Long-term: HPA's maxReplicas should be capped at what the downstream can handle. More replicas hammering a saturated database makes things worse, not better.

Daily operations · what to check first
  • "Slow service" → check throttle ratio before raising CPU limit.
  • "Periodic restart" → check Last State.Reason for OOMKilled, then size memory limit.
  • "Pending pods" → describe shows scheduler verdict (insufficient resources vs quota).
  • "Memory looks high" → for GC'd runtimes, working-set ≠ pressure. Wire GOMEMLIMIT & trust the runtime.
  • "Node NotReady" → check kubeReserved + systemReserved; the kubelet needs its own budget.
  • "Quota exceeded" → right-size before asking for more.
II.2 Per-pod controls · QoS classes

QoS classes: how Kubernetes decides who lives and who dies under node pressure

Definition Principles Diagram Pitfalls
Quality of Service class

An implicit classification Kubernetes assigns to every pod, derived purely from how its requests and limits relate. You don't set QoS directly — you set requests and limits, and the QoS class falls out automatically. It determines eviction order under node pressure and influences OOM-kill ranking.

How QoS is computed
  1. Guaranteed — every container has requests == limits for both CPU and memory. The strongest reliability tier.
  2. Burstable — at least one container has a request set, but it doesn't qualify as Guaranteed. The most common class for stateless services.
  3. BestEffort — no requests or limits set anywhere. First to be evicted, last to be scheduled fairly. Never use in production.

Guaranteed

requests == limits (both CPU & memory, on every container)

Strict: every container must have both requests.cpu == limits.cpu AND requests.memory == limits.memory. Last to be evicted. Eligible for CPU pinning via static manager. Use for: databases, payment services, stateful caches.

Burstable

at least one request/limit set, but not Guaranteed

The catch-all class. Covers requests < limits, requests but no limits, partial declarations (e.g. CPU only). Evicted only if exceeding their request, ranked by usage-over-request. Use for: most stateless services, HPA workloads.

BestEffort

no requests AND no limits — anywhere, any resource

First to be killed under node pressure. Scheduler has no information to reserve capacity. Use for: never in production. Acceptable for dev sandboxes only.

The class is computed from the requests/limits combination across all containers in the pod. One non-conforming container drags the whole pod into a weaker class.

🧩 The "limits-only" trick

If you set limits but omit requests, Kubernetes silently copies the limit into requests during admission. This means limits: {cpu: 1, memory: 1Gi} with no requests becomes requests == limits → Guaranteed. Useful shorthand, but be deliberate: you're now reserving peak capacity for the daily average. Most workloads should be Burstable on purpose.

⚠ "Requests-only" is Burstable with unbounded burst

Setting requests but omitting limits is legal and lands you in Burstable. The pod can grow until the node runs out of memory. Sometimes intentional (latency-critical services on dedicated nodes), but on shared multi-tenant nodes it's the "noisy neighbor" pattern from Case 3 in II.1. Pair with a LimitRange that injects a default limit to prevent accidents.

💡 What about CPU pressure?

CPU pressure doesn't cause eviction — it causes throttling. A pod that exceeds its CPU limit gets paused at the next CFS period boundary; it doesn't get killed. Memory is the only resource whose exhaustion triggers eviction in Kubernetes' default eviction policy.

QoS pitfalls
  • Accidental BestEffort. Forgetting requests on one container in a multi-container pod still drops the whole pod into BestEffort.
  • Guaranteed isn't free. It forces requests == limits, which means you're paying for peak capacity all the time. Use for genuinely critical workloads only.
  • Burstable masks oversubscription. If everyone bursts above their request at once, the node runs out of memory and pods start dying. Headroom planning matters.
II.3 Per-pod controls · OOM & throttling

How exceeding limits actually hurts: OOM-kill and CFS throttling

Definition Principles Diagram Pitfalls
Memory OOM-kill

When a container's memory cgroup hits memory.max, the kernel synchronously kills the process. There's no grace period. Exit code 137 (128 + SIGKILL=9). The kubelet observes it and reports Reason: OOMKilled in the pod status.

CPU throttling

When a container exceeds its CPU limit within a CFS period (default 100ms), the kernel pauses it until the next period starts. The process isn't killed — it's just stopped. Surfaces as latency spikes, not crashes.

Mechanical reality
  1. OOM is synchronous and brutal. The kernel doesn't ask the application to clean up. Connections drop, partial writes happen, in-flight requests fail.
  2. Throttling is invisible to kubectl top. Average CPU looks fine; p99 latency suffers. You need container_cpu_cfs_throttled_seconds_total to see it.
  3. GC'd languages amplify both. A JVM under memory pressure GCs more aggressively, burning CPU — which can hit throttling, slowing GC further, accelerating OOM.
  4. Memory pressure ≠ memory usage. The kernel tracks working-set bytes, which excludes page cache that can be evicted. Your dashboard's "memory usage" number may not match the OOM trigger.

OOM & throttling traps
  • Restart loop after OOM. The pod restarts, warms up its cache, hits OOM again. Cycle repeats. Fix the limit, don't just restart.

II.3· Deep dive · CPU units & throttling

CPU, from physical silicon to throttled containers

To understand throttling you first have to understand what a "CPU" actually is in Kubernetes — and that answer has three layers: physical cores, hyperthreads, and the time-slice budget the kernel gives your container. This section builds up from the silicon and lands at why your pod gets frozen.

Part A · What does cpu: 1 actually mean?

CPU unit (Kubernetes definition)

In Kubernetes, one CPU = one second of CPU time per second of wall-clock. That's it. It's a rate, not a count of hardware. cpu: 1 means "your container is allowed to execute for up to 1,000 milliseconds of CPU time every 1,000 milliseconds of real time." cpu: 2 means 2,000ms per 1,000ms — which requires at least 2 cores to actually achieve. cpu: 500m means 500ms per 1,000ms — half a core's worth.

The three CPU vocabularies that get mixed up
  1. Physical core. An actual chunk of silicon on the CPU die. A modern Intel Xeon or AWS Graviton chip has 8–64 of these per socket. This is the hardware truth.
  2. Logical CPU / vCPU / hyperthread. What the OS sees. Most x86 CPUs have 2 hyperthreads per physical core (Intel Hyper-Threading, AMD SMT). So a 16-core CPU shows up to Linux as 32 logical CPUs. On AWS, "1 vCPU" usually means one hyperthread, not one physical core. Graviton (ARM) gives you full cores — no hyperthreading — so 1 vCPU = 1 physical core there.
  3. Kubernetes CPU. One unit of CPU time per second. Maps 1:1 to whatever Linux calls a "logical CPU." On a node with 32 vCPUs, you have 32 CPU-seconds of capacity per second to distribute across pods.
Diagram 1 — A real node: 1 socket → 8 physical cores → 16 vCPUs
🧩 Two ways to say the same thing — both are correct

You may have read two definitions of cpu: 1 and gotten confused:

View A · time-based — "1,000ms of CPU time per second of wall-clock"

View B · capacity-based — "the right to consume 1 full logical CPU's worth of execution"

These describe the same thing. View A is the kernel's mechanism (CFS quota = 100ms per 100ms period); View B is the result you observe. Both are right.

You do NOT own a specific vCPU. cpu: 1 doesn't pin you to "vCPU number 7." You get a budget of CPU-time, and your threads can spend that budget on whatever vCPUs are available at the moment. The kernel scheduler picks. So cpu: 2 can mean: two threads at 100% on vCPU 3 and vCPU 11 right now, then vCPU 5 and vCPU 12 next millisecond — total budget consumed = 2 CPU-seconds per second. (The only exception is the CPU Manager static policy with integer-CPU Guaranteed pods — that's the one case where you do get specific vCPU pinning.)

📌 The one exception: static CPU Manager policy

There is exactly one case where cpu: N means "you own specific physical CPUs": when the kubelet runs with cpuManagerPolicy: static AND your pod is Guaranteed QoS AND you request an integer number of CPUs (cpu: 2, not cpu: 2.5 or cpu: 500m). Only then does kubelet pin your container to a specific set of physical cores — exclusive, no other pod runs there. Used for ultra-latency-sensitive workloads (ML inference, real-time trading). For everything else — which is 99% of clusters — CPU is a shared time-budget, not a hardware lease.

Virtual or physical? — answering the cloud question

On every major cloud, when you read "8 vCPU instance," that's 8 logical CPUs, which is typically 4 physical cores with hyperthreading (on Intel/AMD) or 8 physical cores (on AWS Graviton ARM, which doesn't use SMT). Kubernetes sees and exposes only the logical CPU count — it doesn't care or know whether two of "your" CPUs share a physical core.

⚠ The hyperthreading honesty problem

Two hyperthreads on the same physical core share execution units — the actual silicon. They're not independent. Two CPU-heavy workloads pinned to the same physical core's two hyperthreads will only get ~1.2–1.4× the throughput of a single thread, not 2×. So "8 vCPUs" on an SMT-enabled chip will perform worse for compute-bound work than "8 vCPUs" on Graviton. If you benchmark a workload on Graviton and it's faster per vCPU than on Intel, this is usually why. Kubernetes treats all vCPUs as identical, but they're not.

Threads per core — the question Kubernetes refuses to answer

There is no Kubernetes setting that controls how many threads your container creates. That's entirely up to your application code and runtime. Kubernetes only controls how much CPU time all your threads collectively get. A container with cpu: 1 can spawn 1,000 threads — but those threads collectively share 1,000ms of CPU time per second. They'll all run slowly rather than one running fast.

🔑 The single most common CPU mistake in Kubernetes

Setting cpu: 500m on a Java app without setting -XX:ActiveProcessorCount. Java 17+ is container-aware by default and reads the cgroup limit. Older JVMs need explicit configuration.

Part B · Now — what throttling really is

CPU throttling

The Linux kernel enforces your CPU limit by chopping time into 100ms periods and giving your container a quota of CPU-milliseconds per period. When your container uses up its quota, the kernel pauses (freezes) all of its threads until the next period starts. The threads aren't sleeping — they're forcibly removed from the run queue. That forced pause is throttling.

From CPU limit to quota — the math
  1. The CFS period is 100ms by default. The kernel re-evaluates every container every 100ms. (CFS = Completely Fair Scheduler, Linux's main scheduler.)
  2. Your quota per period = limit × period. cpu: 1 × 100ms = 100ms quota. cpu: 500m × 100ms = 50ms quota. cpu: 2 × 100ms = 200ms quota (spread across at least 2 vCPUs).
  3. "CPU-time" sums across all your threads. If you have 4 threads each running on a different vCPU at the same time for 50ms, that's 4 × 50 = 200ms of CPU time used. A cpu: 1 container would be 100ms over and get throttled for the rest of the period.
  4. When quota runs out, all your threads freeze at the same time. Not just one — all of them. The cgroup is throttled as a whole.
  5. Next period starts → quota replenished → threads unfrozen. Work resumes mid-instruction. The application has no idea it was paused.
cpu: 1 with one thread vs four threads — same limit, very different behaviour

The "wait, my CPU usage is 50% — why am I throttled?" scenario

This is the question that confuses everyone. Imagine your service has cpu: 1 (100ms quota / 100ms period) and processes requests in bursts. Every 100ms-period, two requests arrive simultaneously, each takes 40ms of CPU on its own thread, running in parallel on two vCPUs.

Wall-clock CPU usage: 40ms out of 100ms ≈ 40%. The dashboard shows you at "40% CPU." Looks healthy.
Actual CPU-time consumed: 2 threads × 40ms = 80ms. That's 80% of your quota in one shot. Add one more concurrent request → 120ms needed but only 100ms allowed → throttled.
Real-world numbers from jahez-checkout with cpu: 1: average CPU shows 60%, but during the dinner rush 6 concurrent requests run in parallel. 6 × 20ms = 120ms of CPU time wanted. You get throttled for 20ms every period. P99 latency triples. Dashboards look healthy. Nobody knows why.

🔥 The "throttled at low CPU" insight

Average CPU on a dashboard is computed over wall-clock seconds. Throttling happens over 100ms periods. A service averaging 40% CPU over a minute might be hitting 100% of quota in 30 individual periods and getting throttled in each of them. The metric that catches this is the throttle ratio: container_cpu_cfs_throttled_periods_total / container_cpu_cfs_periods_total. Anything above 0.05 (5% of periods throttled) is hurting your tail latency.

How to fix throttling (in order of preference)

FixWhen it's the right choice
Raise the CPU limitDefault move. If you have many threads doing parallel work, your CPU limit needs to cover their combined CPU-time, not just one thread's.

CPU sizing checklist
  • Know your platform's vCPU semantics — Intel/AMD = hyperthread, Graviton = full core.
  • Set CPU requests at p75 of historical usage; CPU limits at 2–3× requests for burst.
  • Match runtime parallelism to limit (GOMAXPROCS, JVM ActiveProcessorCount, gunicorn workers).
  • Wire CPU limit via Downward API — don't hardcode it.
  • Alert on throttle ratio > 5% per pod, not on average CPU.
  • For latency-critical services on dedicated nodes, consider keeping requests but dropping limits.
II.3·· Beyond OOM · Other crash modes

Other ways pods and nodes actually fail

OOM gets all the attention because it's the most visible failure. But pods and nodes break for many other reasons — and the diagnostic paths are completely different. Here are the failure modes you'll actually see in production, grouped by where they happen.

Failures at the pod level

💥 Crash 1 · CrashLoopBackOff

What it is: The container starts, exits with non-zero, kubelet restarts it, it exits again. After a few cycles kubelet starts backing off (10s, 20s, 40s, …, capped at 5 min). Pod status: CrashLoopBackOff.
Causes: bad config (missing env var, wrong DB URL), failed migration on startup, dependency unreachable (other service / DB / cache), panic in initialization code, port already in use.
Diagnose: kubectl logs <pod> --previous shows logs from the last failed run. kubectl describe pod shows the exit code (1 = generic error, 139 = segfault, 143 = SIGTERM).
Fix: read the previous logs. The answer is almost always there.

💥 Crash 2 · Liveness probe failure

What it is: Your app is running, but the liveness probe (HTTP/TCP/exec) failed too many times in a row. Kubelet kills the container and restarts it. Status: Restarting then back to Running, restart count climbs.
Causes: probe endpoint is slow under load and times out, probe path doesn't exist, app is deadlocked (technically running but not responsive), probe checks something fragile (DB connectivity → DB blip → pod restart).
Diagnose: kubectl describe pod shows Liveness probe failed: HTTP probe failed with statuscode: 503 or similar.
Fix: probes should be cheap and self-contained. Don't probe downstream dependencies in liveness — use readiness for that. Increase timeoutSeconds and failureThreshold if the probe is fine but the app is slow under burst.

💥 Crash 3 · ImagePullBackOff / ErrImagePull

What it is: Kubelet can't pull the container image. Pod stuck in ImagePullBackOff.
Causes: typo in image name/tag, image doesn't exist in the registry, registry credentials missing or expired (imagePullSecrets), private registry network unreachable from the node, rate-limited by Docker Hub.
Diagnose: kubectl describe pod shows the exact error from the runtime: manifest unknown, unauthorized, denied.
Fix: verify image exists (docker pull from your laptop with the same tag), check pull secrets, check registry connectivity from the node.

💥 Crash 4 · Init container failure

What it is: Pod has init containers that run before the main container. One of them exits non-zero. Pod stuck in Init:CrashLoopBackOff or Init:Error.
Causes: migration script fails, waiting for a dependency that never becomes ready, mounting a secret/configmap that doesn't exist, network policy blocking the init container's outbound call.
Diagnose: kubectl logs <pod> -c <init-container-name>. The main container's logs are empty because it never started.
Fix: read the init container's logs, fix the precondition.

💥 Crash 5 · Volume mount failure

What it is: Pod is scheduled, but stuck in ContainerCreating with events showing volume errors.
Causes: PVC is Pending (no PV bound), PV is on a different zone than the node, secret/configmap referenced but doesn't exist, CSI driver error, NFS server unreachable.
Diagnose: kubectl describe pod events section: FailedMount, FailedAttachVolume, or MountVolume.SetUp failed for volume "secret-X": secret "X" not found.
Fix: check that referenced secrets/configmaps exist in the same namespace; check PVC binding; for cross-zone PVCs, ensure pod affinity matches the volume's zone.

Failures at the node level

🖥️ Crash 6 · DiskPressure (your point about disk full)

What it is: Node condition DiskPressure: True. Kubelet starts evicting pods to free space. Pods get Evicted status with reason "The node was low on resource: ephemeral-storage."
Causes: container logs filled the disk (kubelet rotates at 10Mi by default but apps can write fast), an emptyDir volume filled up, container image layers accumulated, journald logs, runaway core dumps.
Diagnose: SSH to the node, df -h. Check /var/lib/docker or /var/lib/containerd, /var/log, and the pod's emptyDir paths.
Fix: set requests.ephemeral-storage and limits.ephemeral-storage per container. Centralize logs (Fluent Bit → Loki / S3) so they don't sit on the node. Tune kubelet's imageGCHighThresholdPercent.

🖥️ Crash 7 · PIDPressure

What it is: Node ran out of process IDs. Kubelet condition PIDPressure: True. Existing pods can't fork new processes; new pods can't start.
Causes: fork bomb in a pod, app spawning processes without reaping zombies, large thread counts in JVMs, runaway shell scripts. Linux default is ~32k PIDs cluster-wide; pods don't have their own PID limits unless you set podPidsLimit on kubelet.
Diagnose: on the node, ps -eLf | wc -l. kubectl describe node shows the PIDPressure condition.
Fix: set podPidsLimit: 4096 in kubelet config. Find the offending pod with ps -eo pid,ppid,cmd --forest on the node.

🖥️ Crash 8 · NetworkUnavailable / pod-to-pod failures

What it is: Pods can't reach other pods, services, or external endpoints. Manifests as connection timeouts, DNS failures, or readiness probes failing in batches.
Causes: CNI plugin crashed or misconfigured (Calico/Cilium agent down), iptables/eBPF rules corrupted, conntrack table full (nf_conntrack: table full, dropping packet in dmesg), MTU mismatch between overlay and underlay, CoreDNS unhealthy or rate-limited.
Diagnose: kubectl get pods -n kube-system — is CoreDNS running? CNI pods? Try kubectl exec into a pod and nslookup kubernetes.default. Check dmesg on the node for conntrack errors.
Fix: raise net.netfilter.nf_conntrack_max sysctl on nodes; scale CoreDNS replicas; restart CNI agents (last resort).

🖥️ Crash 9 · Kubelet/runtime hang

What it is: Kubelet stops sending heartbeats. Node goes NotReady after 40 seconds. After 5 minutes, the node controller starts evicting pods to other nodes.
Causes: kubelet itself OOM'd (insufficient kubeReserved), containerd/cri-o deadlocked, kernel hung in I/O wait, disk fully exhausted (kubelet can't write its own state), kubelet upgrade went wrong.
Diagnose: SSH to node. systemctl status kubelet, journalctl -u kubelet -n 200. systemctl status containerd. Check dmesg for kernel errors.
Fix: restart kubelet (systemctl restart kubelet); if that fails, restart the runtime; last resort, cordon and reboot the node.

🖥️ Crash 10 · Hardware / cloud-provider issues

What it is: EC2/GCE instance retirement, hardware failure, AZ outage, spot instance preemption. The node disappears without warning.
Causes: spot/preemptible instances reclaimed (2-min warning at best), AWS sends a scheduled maintenance event, EBS volume detaches, hypervisor crashes.
Diagnose: cloud provider's instance event log. kubectl get nodes shows NotReady for the lost node.
Fix: ensure topology spread across AZs, run minReplicas ≥ 2 for every Deployment, use PDBs, use a node-termination-handler for spot preemption signals.

Failures at the cluster level (the rare but lethal ones)

🌍 Crash 11 · etcd slow / disk-bound

What it is: Kubernetes' control plane database is etcd. When etcd's disk is slow or its leader changes too often, everything in the cluster slows down: kubectl apply takes 30 seconds, pods take minutes to schedule, controllers fall behind.
Causes: etcd disk too slow (must be SSD with low p99 latency), too much watch traffic from controllers, oversized objects (huge ConfigMaps, secret bloat), too many CRDs / leader election thrashing.
Diagnose: etcd metrics — etcd_disk_wal_fsync_duration_seconds p99 should be < 25ms. etcd_server_leader_changes_seen_total should be ~0.
Fix: dedicated NVMe disks for etcd; alert on fsync p99; cap object sizes (avoid 1Mi ConfigMaps); reduce CRD bloat.

🌍 Crash 12 · Very high traffic — cascading failure

What it is: Sudden 10× traffic surge (sale event, viral campaign, friendly fire from another team's load test). HPA scales up but downstream (DB, cache, payment gateway) is the real bottleneck. Pods stack up, connection pools exhaust, requests queue, latency rises, timeouts increase, retries amplify load → death spiral.
Causes: the bottleneck is rarely Kubernetes itself — it's a database, an external API, a single Redis instance, or DNS (which has its own throttling at AWS).
Diagnose: look downstream. DB connection count, slow query log, cache hit rate, p99 latency on each dependency.
Fix: set HPA maxReplicas to what the downstream can handle (more pods don't help if the DB is the bottleneck). Implement circuit breakers and request hedging. Add rate-limiting at the ingress. Use a load-shedding pattern (return 503 fast instead of queuing).

🌍 Crash 13 · API server overload

What it is: kube-apiserver itself can't keep up with watches, lists, and writes. Symptom: kubectl times out, controllers can't reconcile, webhooks time out causing apply failures.
Causes: too many controllers doing wide list-watches, a runaway operator doing list pods every second across all namespaces, oversized resources, slow admission webhooks blocking the write path.
Diagnose: apiserver metrics — apiserver_request_duration_seconds, apiserver_current_inflight_requests. Logs show Timeout: too many requests.
Fix: set --max-requests-inflight appropriately; identify the offending controller via audit logs; add admission webhook timeouts (≤ 10s) and failure policies.

Quick diagnostic flow

🔬 First questions when something breaks

1. Is the pod Pending? → scheduler issue (resources, taints, affinity, quota).
2. Is the pod ContainerCreating? → volume mount, image pull, secret/configmap missing.
3. Is the pod CrashLoopBackOff? → app-level error; check logs --previous and exit code.
4. Is the pod OOMKilled? → memory limit too tight or leak.
5. Is the pod Evicted? → node pressure (memory or disk); check node conditions.
6. Is the node NotReady? → kubelet, runtime, or kernel issue; SSH and check.
7. Is everything slow but nothing broken? → CPU throttling, etcd slow, or downstream bottleneck.
8. Does kubectl itself time out? → API server overload.

III.1 Namespace controls · LimitRange

LimitRange: the namespace-level safety net for forgotten declarations

Definition Principles YAML Pitfalls
LimitRange

A namespace-scoped policy object that (a) injects default requests/limits into pods that don't declare them, and (b) enforces min/max bounds, rejecting pods outside the allowed range. Acts as a mutating + validating admission policy at gate 2.

Why every namespace needs one
  1. Defaults catch laziness. Developers will forget to set resources. LimitRange ensures the resulting pod is at least Burstable, not BestEffort.
  2. Min bounds prevent absurd requests. Stops cpu: 1m requests that schedule everywhere but throttle on first packet.
  3. Max bounds prevent capacity hoarding. Stops one team from requesting 64 vCPU per pod and consuming the whole node.
  4. maxLimitRequestRatio caps oversubscription. Limits the gap between request and limit, preventing wildly aspirational limits that pods can never actually use.

Production LimitRange — Jahez prod namespace

limitrange-jahez-prod.yaml 
apiVersion: v1
kind: LimitRange
metadata:
  name: jahez-prod-limits
  namespace: jahez-prod
spec:
  limits:
  # ---- Per Container ----
  - type: Container
    default:                  # injected if limits not set
      cpu: "500m"
      memory: "512Mi"
    defaultRequest:           # injected if requests not set
      cpu: "100m"
      memory: "128Mi"
    min:                       # reject if below
      cpu: "50m"
      memory: "64Mi"
    max:                       # reject if above
      cpu: "4"
      memory: "8Gi"
    maxLimitRequestRatio:      # reject limit/request > this
      cpu: "4"                # burst factor cap
      memory: "2"             # tighter for memory

  # ---- Per Pod (sum of all containers) ----
  - type: Pod
    max:
      cpu: "8"
      memory: "16Gi"

  # ---- Per PVC ----
  - type: PersistentVolumeClaim
    min:
      storage: "1Gi"
    max:
      storage: "100Gi"

What each field does

FieldBehavior
defaultIf a container doesn't set limits, these values are injected. Mutating admission.
defaultRequestIf a container doesn't set requests, these values are injected. Together with default, prevents BestEffort.
minReject pods where any container requests less than this. Stops absurd low values.
maxReject pods where any container requests more than this. Caps individual pod size.
maxLimitRequestRatioFor each resource, reject if limits/requests > ratio. Cap on burst factor.
typeContainer | Pod | PersistentVolumeClaim. The scope of the rule.
LimitRange gotchas
  • Defaults don't apply retroactively. Pods that existed before the LimitRange was created keep their original (or missing) values until they restart.
  • Defaults silence developers. A developer never sees they forgot to set resources — the pod just runs with cluster defaults. Pair with a Kyverno warning policy.
  • maxLimitRequestRatio for memory should be tight (≤ 2). Huge ratios make Burstable QoS unsafe at scale.
  • Multiple LimitRanges in a namespace are intersected — the most restrictive wins. Confusing in practice; prefer one per namespace.
III.2 Namespace controls · ResourceQuota

ResourceQuota: hard caps on a namespace's total appetite

Definition Principles YAML Pitfalls
ResourceQuota

A namespace-scoped policy that caps the aggregate requests, limits, and object counts of all workloads in that namespace. Where LimitRange constrains individual pods, ResourceQuota constrains the total. Enforced at gate 2 — pods that would push the namespace over quota are rejected at kubectl apply time.

Operating principles
  1. Quota acts on requests, not usage. A pod requesting 100m but using 800m is invisible to quota. This is why right-sizing matters even with quotas in place.
  2. Quota requires LimitRange to be useful. Without LimitRange defaults, every pod must explicitly declare resources or the apply fails. Together they're a complete policy; alone they're a half-measure.
  3. Use scopeSelector to separate workload classes. Production pods (long-running) vs batch jobs (one-shot) should consume from different quota buckets.
  4. Object-count quotas catch runaway controllers. A misconfigured Job can spawn thousands of pods. count/pods caps the damage.

III.3 Namespace controls · PriorityClass & PDB

PriorityClass & PodDisruptionBudget: who gets preempted, who stays alive

Definition Principles YAML
PriorityClass

A cluster-wide object that assigns a numeric priority to pods. When a high-priority pod can't fit anywhere, the scheduler will preempt (evict) lower-priority pods to make room. Also determines eviction order under node pressure beyond QoS ranking.

PodDisruptionBudget (PDB)

A namespace-scoped policy that protects a Deployment from voluntary disruptions (node drains, cluster upgrades, eviction-by-tooling) by guaranteeing a minimum number of pods stay running. Does not protect against involuntary disruption (node crash, OOM-kill).

How they work together
  1. PriorityClass decides who survives scarcity. If two pods compete for a slot, the higher-priority one wins.
  2. PDB decides what "disruption" means for graceful operations. kubectl drain respects PDB; node crashes don't.
  3. Three classes is the right number. Critical (payments, checkout), standard (most services), batch (preemptible, low priority). More than three is over-engineering.
  4. Every production Deployment needs a PDB. Without one, kubectl drain can take all replicas down simultaneously.

III.3· Disambiguation · QoS vs Priority vs PDB

QoS class, PriorityClass, PodDisruptionBudget — three different things

These three mechanisms all sound like "who matters more," and they all answer that question — but in different scenarios, at different times, controlled by different objects. Knowing which one fires in which situation is the difference between architecting reliability and just hoping.

The one-sentence distinction

QoS class = "who gets killed when the node runs out of memory." PriorityClass = "who gets to schedule when there's no room in the cluster." PodDisruptionBudget = "how many of my pods can be voluntarily taken down at once."

PriorityClass mechanism — preemption in action

QoS chose who dies under node memory pressure. PriorityClass chooses who gets kicked out of a node so a more important pod can take its slot when the cluster has no room. This happens at scheduling time, not eviction time — and it's the scheduler doing it, not the kubelet.

PriorityClass — scheduler preempts a lower-priority pod to make room

Two important details about how the scheduler picks the victim:

Preemption logic, step by step
  1. Scheduler tries to find a feasible node normally. Only if there's no feasible node does it consider preemption.
  2. Candidates are pods with lower priority than the pending pod. Higher-priority pods are off-limits — the scheduler will never preempt a Guaranteed-critical for another Guaranteed-critical.
  3. Among candidates, scheduler picks the fewest disruptions. It prefers preempting one pod over many. Across ties, it prefers preempting on a node where the victim has the lowest priority gap.
  4. Preempted pods get their terminationGracePeriodSeconds to shut down cleanly. Default is 30s. Long-running jobs should keep this short to allow fast preemption.
  5. Preempted pods go back to the scheduler queue and get re-scheduled wherever they fit later. They aren't deleted — they're just moved off this node.
⚠ Preemption can cascade

When pod X preempts pod Y, pod Y goes back to the queue and tries to schedule somewhere else. If pod Y is mid-priority, it may itself preempt a lower-priority pod Z on a different node. One scheduling decision can cause a chain of evictions. This is why PriorityClass values should be spaced widely (1000 / 5000 / 10000) instead of contiguously (1 / 2 / 3) — leaves room for new tiers without re-tuning everything.

PodDisruptionBudget mechanism — staggered drain

QoS protected pods from kernel kills. PriorityClass got pods onto nodes. PDB controls how many of your replicas can be voluntarily evicted at the same time — when an operator drains a node, when an autoscaler consolidates, when a tool calls the eviction API. It does not protect against involuntary disruption (crashes, OOM, AZ failure).

PDB — drain sequence with maxUnavailable: 2 on 6 replicas
How PDB enforces the limit
  1. The Eviction API checks the PDB first. Tools like kubectl drain and Cluster Autoscaler don't kill pods — they call /api/v1/namespaces/.../pods/.../eviction. If granting the eviction would violate the budget, the API server returns 429 Too Many Requests.
  2. The tool retries with backoff. Drain doesn't give up — it waits until enough new pods become ready elsewhere, then tries the next eviction. This is the "pacing" behavior in the diagram.
  3. Two budget styles, pick one. minAvailable: 4 (always keep at least 4 running) or maxUnavailable: 2 (never let more than 2 be down). Logically equivalent for fixed replica counts, but maxUnavailable auto-scales with replica count when you change it.
  4. Percentages are allowed. maxUnavailable: "25%" for a 12-replica Deployment = 3 unavailable. Rounded down — so 25% of 5 replicas = 1, not 1.25.
  5. The PDB selector must match the Deployment's pods. Same labels. If labels don't match, the PDB silently protects nothing — and kubectl drain will happily kill everything.
✕ When PDB does NOT help you

PDB only intercepts the Eviction API. It does not stop:

• A node crashing (no API call happened) · • An OOM-kill (kubelet bypasses the eviction API) · • A direct kubectl delete pod (deletion ≠ eviction) · • An AZ-wide outage · • You scaling the Deployment to zero.

PDB protects against tools doing the right thing wrong — drains, autoscaler consolidations, controlled rollouts. It does nothing against the kernel, the cloud provider, or a tired human.

Now read this story together:

  • Cluster runs low on capacity at 9 PM, a new payment pod can't schedule. PriorityClass jahez-critical (value 10000) outranks jahez-batch (1000) — scheduler preempts a batch job to make room. PriorityClass fired.
  • That batch job's node was the one running checkout pods, and after preemption the node briefly has memory pressure as the new payment pod warms up. Kubelet has to evict. Checkout pods are Guaranteed (last tier); batch pods left running are Burstable. QoS fired — kubelet kills Burstable first, checkout survives.
  • An SRE drains the node at midnight for a kernel upgrade. kubectl drain would normally take all 6 checkout pods at once. PDB maxUnavailable: 2 blocks that — drain pauses, evicts 2, waits for replacements on other nodes, then evicts 2 more, etc. PDB fired.
✓ The mental shortcut

QoS class: "How urgent is my pod's survival when the node is in trouble?"
PriorityClass: "How urgent is my pod's existence when the cluster is full?"
PodDisruptionBudget: "How many of my replicas can be asked to leave at once?"

Three different problems → three different mechanisms. Every production Deployment needs all three set deliberately, not by accident.

⚠ What none of these protect against

Hardware failure. A node disappears, the underlying VM crashes, a region has an outage. QoS doesn't apply (no eviction logic ran). PriorityClass doesn't apply (no preemption decision). PDB doesn't apply (the disruption was involuntary, not initiated by a tool). Your protection here is topology spread + replicas — multiple pods across multiple zones, with PDBs that survive the loss of any one. None of the three mechanisms in this chapter helps you when the hardware itself fails.

IV.0 Autoscaling · Basics

What is scaling, really? And what does "auto" add?

Definition Principles Diagram

Before HPA, VPA, and Cluster Autoscaler — what problem are they all solving? "Scaling" is the act of adjusting your system's capacity to match demand. It can be done by a human, by a schedule, or by a controller reacting to metrics. Each approach has a place. Choosing wrong is one of the most common reasons production feels expensive and slow at the same time.

What is scaling?

Scaling

Changing the amount of compute capacity allocated to a workload so that capacity matches demand. Two fundamental directions: horizontal (more or fewer copies of the same thing) and vertical (each copy gets bigger or smaller). Two fundamental triggers: a human decides, or a controller decides automatically.

The four dimensions of "scaling"
  1. What changes? Replica count (horizontal), pod size (vertical), or node count (cluster).
  2. Who decides? A human (manual), a schedule (predictive), or a controller (reactive).
  3. What's the trigger? A metric crossing a threshold, a calendar event, a queue depth, or just gut feeling.
  4. How fast? Seconds (for replica adjustments) to minutes (for new nodes) to hours (for new clusters / regions).
Scaling — the full taxonomy

What is autoscaling, specifically?

Autoscaling

A control loop that watches a metric (CPU, memory, RPS, queue depth, ...) and automatically adjusts capacity to keep that metric near a target value. The "auto" means a controller — not a human or a schedule — owns the decision. Autoscaling can target replicas (HPA), pod size (VPA), or node count (Cluster Autoscaler / Karpenter).

The types of scaling — when to use which

There are six distinct scaling approaches in production. Each one is the right answer for a specific situation. Most teams use 2–3 of them together.

1 · Manual scaling

Manual scaling

A human directly changes replicas or resource requests, usually via kubectl scale, a Git PR + apply, or a Helm value update. No automation.

Use when
✓ BenefitsTotal control · easy to reason about · no surprise costs · works from day 1 · trivial to debug.
✕ DrawbacksDoesn't react to load · requires constant attention · slow (humans are slow) · doesn't work for off-hours spikes · doesn't right-size individual pods.
→ Use forLower environments (dev / staging) · small fleets · workloads where load is stable · workloads where the team isn't ready to automate yet.

2 · Scheduled / predictive scaling

Scheduled scaling

A CronJob, KEDA cron trigger, or external scheduler that changes minReplicas (or replica count directly) at known times. Sometimes called "pre-scaling" — you scale before demand arrives, based on calendar knowledge.

Use when
✓ BenefitsCapacity is ready before demand arrives — zero lag · users never feel a slow scale-up · combines well with HPA as a floor · cheap to operate.
✕ DrawbacksRequires knowing your traffic pattern · can't react to unexpected spikes · wastes capacity if the predicted load doesn't show up.
→ Use forDinner rush (Jahez 9 PM) · ad campaigns with known start time · Black Friday / Ramadan / Hajj surges · end-of-month batch processing · workdays vs weekends.

3 · Horizontal autoscaling (HPA)

Horizontal Pod Autoscaler

A Kubernetes controller that adjusts the replica count of a Deployment based on a metric (CPU, memory, custom metric like RPS). Reactive — acts after the metric crosses the threshold.

Use when
✓ BenefitsBuilt into Kubernetes · works for any stateless workload · cost-efficient at scale · scales with traffic shape · can use any metric via Prometheus adapter.
✕ Drawbacks~60–180s reaction time · doesn't help with sharp spikes (use pre-scaling) · doesn't right-size individual pods · can flap without proper tuning · wrong metric = wrong scaling.
→ Use forStateless web services · API gateways · workers behind a queue · anything that can run with N independent identical pods.

4 · Vertical autoscaling (VPA)

Vertical Pod Autoscaler

Adjusts per-pod resource requests/limits over time based on historical usage. Either applies changes automatically or just recommends them (most teams use it in advisor mode).

Cluster Autoscaler / Karpenter

Provisions new nodes from the cloud when pods can't fit on existing ones, and removes underutilized nodes to save cost. Works alongside HPA — HPA decides how many pods, CA decides whether new nodes are needed to hold them.

Use when
✓ BenefitsCluster expands automatically when load grows · contracts to save cost when load drops · enables true pay-as-you-go infrastructure · pairs with HPA naturally.
✕ DrawbacksSlow (~90s for classic CA, ~45s for Karpenter) · adds to the HPA reaction-time chain · charges for at-least-one-minute of node uptime · cold-start cost on cache-warming services.

How they combine in production

Most production Kubernetes workloads end up using multiple scaling approaches together. Here are the common stacks:

Stateless service

HPA + Cluster Autoscaler + VPA-Off

HPA scales replicas on CPU/RPS. CA provisions nodes when needed. VPA in Off mode generates sizing recommendations passively.

Predictable spike workload

HPA + CronJob pre-scale + CA

CronJob bumps minReplicas before the known spike. HPA handles surprises. CA backs the whole thing with nodes.

Queue worker

KEDA + CA

KEDA scales workers based on queue depth, can drop to zero replicas when queue is empty. CA scales nodes underneath.

Stateful service (database, cache)

VPA-Off + manual

VPA recommends sizing. Humans apply changes via PR for control. No HPA on stateful workloads — replica count rarely changes.

Batch / cron job

No autoscaling needed

Jobs / CronJobs spawn pods on demand. PriorityClass keeps them preemptible. They're "scaling" by being created/deleted.

Cost-optimized non-prod

KEDA cron + scale-to-zero

Dev / staging environments scale to zero overnight, scale back up at 8 AM via KEDA cron triggers. Massive cost savings.

🎯 The progression most teams follow

Phase 1: Manual — get the workload running, observe load patterns. Phase 2: HPA + CA — automate the common case. Phase 3: add VPA-Off as a passive advisor; review recommendations quarterly. Phase 4: add scheduled / KEDA for known patterns and queue workloads. Skipping ahead causes more problems than it solves — start simple, layer complexity only when you have evidence you need it.

⚠ The "one of everything" anti-pattern

Don't enable HPA, VPA, Cluster Autoscaler, AND KEDA on the same workload without thinking carefully. HPA + VPA on the same resource (CPU) actively fight. Multiple KEDA triggers can cancel each other out. The default rule: one source of truth per axis. HPA owns replicas, VPA owns pod size, CA owns nodes. Don't double up.

Definition Principles YAML Pitfalls
Horizontal Pod Autoscaler

A controller that periodically (default every 15 seconds) compares actual metric values against a target, and adjusts a workload's replica count to bring the ratio toward 1.0. Supports CPU, memory, custom metrics (per-pod), and external metrics (queue depth, RPS).

The HPA formula
  1. desiredReplicas = ceil(currentReplicas × (currentMetric / targetMetric))
  2. Scale up is aggressive by default — can double pods in 60s if metrics warrant it.
  3. Scale down is conservative — 5 minute stabilization window prevents thrashing.
  4. Per-pod metrics → ratio. CPU at 80% with target 50% → multiply replicas by 1.6.
  5. External metrics → absolute value. SQS queue depth of 1000 with target 100 → 10 replicas, regardless of current count.

IV.2· Deep dive · HPA timing

How long until HPA actually scales?

Three questions every engineer asks the first time they configure HPA: (1) how many pods does it scale to, (2) how long does it take, (3) how many pods need to be above 70% for it to trigger? The visualizers above answered the first two. This section answers all three rigorously, with a special focus on the third — the one most people get wrong.

Question 1 · How many pods does HPA scale to?

Answered in detail above. The formula is desiredReplicas = ceil(currentReplicas × currentMetric / targetMetric), clamped between minReplicas and maxReplicas, with velocity policies controlling per-tick growth. See the interactive visualizers earlier in this chapter.

Question 2 · How long does HPA take to react?

Five sequential delays between "CPU spike" and "new pods serving traffic." Detailed below with an interactive timeline.

Question 3 · How many pods need to exceed 70% for HPA to scale?

Short answer

None, individually. All of them, collectively. HPA never looks at a single pod's CPU. It computes the average across every Ready pod targeted by the HPA, then compares that single number against the target. A pod can be at 200% or at 5% — HPA only cares about the average.

The exact math
  1. HPA fetches per-pod metrics from metrics-server (or Prometheus adapter for custom metrics) — one value per Ready pod.
  2. It computes arithmetic mean of those per-pod values. Not median, not p99, not "max." Just the average.
  3. For type: Utilization, the per-pod value is (actual_usage / pod_request) × 100. So a pod requesting 500m using 350m reads as 70%.
  4. The mean is compared to the target. ratio = mean / target. If ratio > 1.1 (or < 0.9), HPA recommends a new replica count via ceil(currentReplicas × ratio).
  5. The ±10% tolerance band (default --horizontal-pod-autoscaler-tolerance=0.1) prevents thrashing — HPA only acts when the ratio is outside [0.9, 1.1].

⚠ Why the load-balancing assumption matters

HPA assumes your load balancer distributes traffic roughly evenly. If your service has session affinity, a sticky-routing bug, or skewed key-distribution (e.g., one user generates 90% of the load), some pods melt while others idle — and HPA's average looks fine. Adding more pods does not fix this because the new pods may receive zero traffic too. Fix the routing first.

💡 When you actually want "any pod above X"

If you genuinely need "scale up when even one pod is hot," use a custom metric from Prometheus that computes max() across pods instead of relying on the built-in averaging. Something like max(rate(http_requests_total[1m])) by (deployment) — wired into HPA as an External metric type. The built-in CPU/memory metrics will never give you this behavior.

Question 4 · What happens when CPU and memory disagree?

The single rule that resolves every conflict

When an HPA declares multiple metrics (CPU + memory, CPU + RPS, all three, etc.), it computes a desired replica count for each metric independently, then takes the highest number. The most aggressive scale-up wins. There is no averaging across metrics, no voting, no priority order. Just max().

The full multi-metric arbitration logic
  1. Each metric → its own desired replica count. CPU computes one number via ceil(replicas × cpu/cpuTarget). Memory computes another via ceil(replicas × mem/memTarget). RPS computes a third via ceil(totalRps / target).
  2. HPA picks the maximum of all per-metric recommendations. If CPU says 7 and memory says 3, the answer is 7. Always the higher number.
  3. This applies in both directions. Even on scale-down, HPA only reduces to the max of all recommendations. You can never scale below what any single metric demands.
  4. Each metric's recommendation goes through its own tolerance band (±10%) before being included. A metric inside its tolerance contributes "current replicas", not its raw recommendation.
  5. The winning recommendation then goes through the stabilization window as usual — same lookback rules as single-metric HPA.
  6. Failed/unavailable metrics block scale-down. If one metric can't be read, HPA can still scale up, but won't scale down (safety first).
Your two scenarios — answered explicitly

🧭 How to read the trace

Walk left-to-right per tick. First compute cpu-rec and mem-rec independently using the current pod count. Pick the max — that's the "winning number" and the metric that produced it is the "winner metric." Add the winning number to the window. Compute window-min (or just the current tick if window=0). If window-min > current pods → scale up to window-min. Otherwise hold. The winner metric is only there for human understanding — HPA discards that information immediately.

⚠ Common confusion — "max" doesn't mean "max metric"

HPA takes the max of recommendations, not the max of metric values. A metric at 200% utilization doesn't automatically win — what matters is the desired replica count it produces. CPU at 200% with current=4 → wants 12. Memory at 120% with current=4 → wants 6. CPU wins because 12 > 6, not because 200% > 120%.

🎯 Practical implications

1. Adding a metric to HPA can only scale you UP, never DOWN. Because each new metric can drive the max higher, but never overrides another metric's higher recommendation.

2. The "leading" metric tends to dominate. Whichever metric tends to spike fastest will be the active driver most of the time. The other metrics act as safety floors.

3. Don't mix HPA metrics with VPA on the same resource. If CPU drives HPA scale-up, VPA-Auto on CPU will fight it (VPA shrinks request → CPU utilization% rises → HPA scales up more → VPA shrinks again). Pick one tool per resource.

The HPA sync loop

The HPA controller does not watch metrics in real-time. It runs on a fixed schedule — every 15 seconds by default (controlled by the --horizontal-pod-autoscaler-sync-period flag on the controller-manager). On each tick it: (1) fetches the latest metric values, (2) computes the desired replica count, (3) consults the stabilization window, (4) applies scale-up/scale-down velocity policies, and (5) writes the new replica count if it changed.

The instantaneous vs. average problem

HPA doesn't see what your dashboard sees. The values it acts on are averages over a window, not instantaneous readings. This matters enormously:

Instantaneous CPU vs what HPA actually sees
📊 The math that bites you

metrics-server reports CPU as average usage over the last ~15 seconds. A pod running at 200% for 5 seconds and 25% for 10 seconds shows up as roughly (200×5 + 25×10) / 15 ≈ 83%. The user-facing pain of those 5 seconds at 200% (throttling, latency spikes) is real — but HPA reacts to the smoothed average. If the burst is too short to push the average above your target, HPA never scales. This is why long stabilization windows can be dangerous on bursty workloads: the averaging is already happening at the metric layer, and stabilization adds more averaging on top.

Stabilization windows — the most misunderstood field

Most people read stabilizationWindowSeconds: 60 as "wait 60 seconds before scaling." That's wrong. The correct reading is: "every time I decide a new desired replica count, look at every recommendation I've made over the past 60 seconds, and pick the most conservative one."

Direction"Most conservative" meansEffect on behavior
scaleUpThe lowest recommendation in the windowHPA only scales up when CPU has been high for the full window. Short spikes can't trigger scale-up.
scaleDownThe highest recommendation in the windowHPA only scales down when CPU has been low for the full window. Brief dips can't trigger scale-down.

Defaults (if you don't set behavior):

  • scaleUp.stabilizationWindowSeconds: 0 — react immediately to any single recommendation above current.
  • scaleDown.stabilizationWindowSeconds: 300 — wait 5 minutes of consistently-low recommendations before removing pods.
  • scaleUp.policies: double per 15s OR add 4 pods per 60s (whichever is more).
  • scaleDown.policies: remove 100% of pods over 15s (effectively no velocity limit — only the stabilization window protects you).

Stabilization is a trade-off, not a free improvement. The same 60-second window that perfectly absorbs noise on a chatty service can be the reason your sale event has 90 seconds of degraded latency. Here's the honest breakdown for both directions.

Before we can talk about which patterns stabilization helps with, we need shared names for them. These terms come up in postmortems, capacity-planning docs, and SRE literature. The names matter because the right scaling approach depends entirely on which pattern you have.

One-shot spike Transient spike · also "micro-burst", "blip" A single high-amplitude reading lasting 5–15 seconds, then back to baseline. Flapping Thrashing · or "bistable oscillation" Regular high-low cycling, often caused by the autoscaler itself: add pods → load drops below target → remove pods → load rises above target → add pods again. This is a control-system instability called oscillation, and stabilization is the dampening mechanism that prevents it.
Sustained spike Level shift · or "step change" Load rises and stays at the new level. This is real demand. You actually need more capacity. Stabilization delays your response to this, which is the cost you pay for the protection from patterns 1–3.
Gradual ramp Trend · or "diurnal pattern" when daily Slow, predictable climb over many minutes or hours. Dinner rush, morning login wave, end-of-month batch run. HPA handles ramps gracefully with short stabilization; long windows compound with the slow ramp to create real lag.
Burst train Bursty arrivals · or "Poisson burst" for the statistical model Repeated multi-second high-load bursts separated by quiet periods. Common in queue consumers (Kafka batch, SQS visibility timeout cycles), webhook receivers, scheduled job triggers. CPU/memory HPA gives you flapping; queue-depth metrics give you stability.
The control-theory name for what stabilization is doing

The technical term for "ignore short-duration deviations to prevent over-reacting" is hysteresis or control-loop dampening. It's the same concept your home thermostat uses — once heat turns on, it stays on until the room is comfortably above the target, not just at the target, to avoid switching the heater on and off every minute. Stabilization windows are HPA's hysteresis: once you've decided to act, commit; once you've decided to hold, commit to that too.

Other names you'll encounter in literature and postmortems for the same phenomenon stabilization fights:

  • Autoscaler oscillation — the formal control-theory term for flapping caused by the scaler reacting to its own actions.
  • Limit cycle — when a system gets stuck in repeating high-low pattern around a setpoint (control-systems textbook term).
  • Bang-bang control — controllers that only have two states (scale or don't scale) and tend to oscillate; HPA is bang-bang without hysteresis.
  • Phantom load — short bursts that look like real load to a metric collector but don't represent sustained user demand. Many one-shot spikes are phantom load.
  • Metric tornado — informal term for a brief metric anomaly that disappears before you can investigate, common in microservice meshes.

🎯 The rule of thumb

Default to scaleUp window = 30–60s and scaleDown window = 300–600s. Only deviate when you've measured a specific problem: shorter scaleUp if you've seen real latency from delayed scaling; longer scaleUp if you've seen yo-yo from noise. The asymmetric defaults (fast up, slow down) exist because the cost of over-reacting is asymmetric — wasted capacity is cheaper than degraded latency.

⚠ When stabilization is the wrong tool entirely

If your workload has a known traffic pattern (dinner rush, ad campaign, end-of-month batch run), no stabilization window will reach the right answer in time. Even window=0 only saves you ~60s of delay vs. window=60s — meanwhile your spike is already underway. The right tool is pre-scaling (CronJob bumping minReplicas before the spike, KEDA cron triggers, or scheduled HPA via tools like Keda). HPA reacts; pre-scaling anticipates. For known patterns, anticipation always wins.

⏱ The honest summary

From "real load arrives" to "new pods serving traffic" is realistically 60–180 seconds on warm nodes, 2–4 minutes if a new node has to be provisioned. HPA pitfalls
  • HPA on memory for GC'd languages. JVM and Go hold memory after GC — usage looks flat/rising even when load drops. Use CPU or RPS.
  • minReplicas: 1. Single replica means zero redundancy during rollouts and drains. Use ≥ 2 for any user-facing service.
  • No maxReplicas ceiling. A bad metric (or a real DoS) burns thousands of dollars before anyone notices.
  • Aggressive scale-down. Default 5-min stabilization is the floor, not a target. Bursty traffic needs longer windows or HPA will yo-yo.
IV.3 Autoscaling · Vertical Pod Autoscaler

VPA: right-size requests automatically (or just recommend them)

Definition Principles Diagrams YAML Pitfalls

HPA changes how many pods are running. VPA changes how big each pod is. Same goal (match capacity to demand), different axis. This chapter walks through the same five questions you've now seen for HPA — what, why, how, when, with what trade-offs — so VPA feels familiar instead of mysterious.

Question 1 · Why do we need VPA when we already set requests & limits?

The honest answer

Because the requests and limits you wrote in your YAML are guesses — based on a load test from six months ago, or copy-pasted from a sibling service, or simply numbers that "felt right" at the time. Real production usage drifts: traffic grows, code changes, new features add memory pressure, dependencies get heavier. Without something watching, your pods are always either over- or under-provisioned. VPA is the system that watches.

The four problems VPA solves that static requests/limits cannot
  1. Static requests get stale. The 500m CPU you set a year ago might be too much (50% utilization, wasted money) or too little (constantly throttled, slow). You won't notice unless you actively look. VPA looks for you.
  2. You can't right-size 200 services manually. A platform team running dozens of microservices can't review every Deployment quarterly. VPA generates recommendations continuously, for free, across the whole cluster.
  3. Memory profiles change without warning. A library upgrade, a cache size increase, a new feature — any of these can quietly raise your memory floor. You find out via OOMKill at 3 AM. VPA spots the trend earlier.
  4. OOMKill data is the worst feedback loop. Setting memory limits by "wait for OOMKill, then increase" means production outages teach you sizing. VPA learns from histograms of normal usage, not crashes.
Why static requests/limits aren't enough — three failure modes

Question 2 · How does VPA actually work?

The three components

VPA is not a single controller — it's three cooperating processes. Together they form a closed loop: observe usage, compute recommendations, apply them if you allow. You can run any subset; advisor mode (Off) uses only the recommender.

VPA's three-component pipeline · observe → recommend → apply

What the recommender actually computes

The recommender doesn't just average usage. It builds weighted histograms of CPU and memory consumption over a sliding window (default 8 days), with newer samples weighted more heavily than older ones. From those histograms it derives four values per container:

ValueHow it's computedWhat it means
TargetThe peak observed usage with a safety margin (default +15% for CPU, +15% for memory). Updated continuously."This is what I would set the request to if I were doing it manually." The value VPA will inject when it acts.
Lower boundTarget ÷ ~1.5 (configurable). Represents the smallest size still considered safe."Below this, the pod is undersized." If your current request < lowerBound, VPA wants to scale UP.
Upper boundTarget × ~1.5 (configurable). Represents the largest size still considered well-fitted."Above this, the pod is oversized — wasting capacity." If your current request > upperBound, VPA wants to scale DOWN.
Uncapped targetWhat Target would be if your maxAllowed policy didn't exist.Diagnostic value. If it differs from Target, your maxAllowed is constraining VPA — could indicate a leak or a genuinely big workload.
📊 The asymmetry in VPA's math

The recommender's safety margin is asymmetric: memory uses peak observed usage (because OOMKill is catastrophic — you must size for the worst case), while CPU uses a percentile (typically p95) since brief CPU throttling is recoverable. This is why VPA's memory recommendations tend to climb after spikes and stay there, while CPU recommendations recover faster.

Question 3 · When does VPA actually act? At runtime, or only on pod restart?

The short answer (today)

Today, VPA does not change a running pod's resources. It always acts by killing the pod and recreating it with the new sizes. The Kubernetes API does support in-place pod resize (graduated to beta in 1.27+, stable in newer versions), but most VPA distributions still default to the eviction-based model. Treat "Auto" mode as "kill and recreate" for planning purposes.

VPA's action mechanism — eviction-based resize

Why this is disruptive (and how to control it)

Because VPA's mechanism is "kill the pod and let the ReplicaSet make a new one," every resize event causes the same disruption as a manual kubectl delete pod:

  • In-flight requests must be drained via the preStop hook + terminationGracePeriodSeconds. If your service handles this well, the disruption is minimal.
  • Local state is lost. In-memory caches, JIT-compiled hot code paths, in-flight streaming connections — all gone. Cold-start cost applies.
  • The pod gets a new IP (in most CNI setups), so any direct pod IP references break. Services using ClusterIP / DNS are fine; anything bypassing the Service abstraction may not be.
  • The eviction respects PDB. If your PodDisruptionBudget says "max 1 unavailable," VPA only evicts one pod at a time and waits for the replacement to be Ready.
⏳ What about in-place resize?

Kubernetes 1.27 introduced in-place pod vertical scaling as alpha, graduated to beta in 1.32, and is stabilizing through the 1.33+ releases. When enabled, the kubelet can change a running container's cgroup limits without killing the pod — meaning VPA can resize without disruption. But: (1) the VPA project itself is still being adapted to use this, (2) most production clusters haven't enabled the feature gate, (3) some changes (memory shrink, CPU shrink with throttling) still require restart even with in-place. For 2026 production planning: assume "Auto" means eviction. Revisit in 12–18 months.

Question 4 · What are the four update modes — and which should you use?

VPA's updateMode is the dial that controls how aggressively VPA acts. The modes go from "completely passive observer" to "kill pods to resize them" — pick the one that matches how much disruption your workload tolerates. For most production workloads, start with Off and let VPA generate recommendations passively for a few weeks before considering anything more active.

Most teams find that running VPA in Off mode and applying recommendations through normal PR review gives 90% of the value with 0% of the disruption. Question 5 · Can VPA and HPA coexist? When do they conflict?

The one rule

VPA and HPA must not use the same resource as their target. If HPA scales replicas based on CPU, VPA must not adjust CPU. If they target the same resource, they enter a feedback loop and oscillate forever.

The VPA + HPA oscillation — why same-resource is a death loop

🎯 Recommended starting point for any team

VPA + HPA conflicts

  • Recreate mode disrupts pods. For stateful workloads, only Off mode is safe until in-place resize is GA-stable in your cluster.
  • VPA recommendations need enough history. First 24 hours of recommendations are unreliable. Let it bake.
IV.4 Autoscaling · Cluster Autoscaler & Karpenter

Cluster Autoscaler: add nodes when pods can't fit

Definition Principles YAML
Cluster Autoscaler (CA)

A controller that watches for unschedulable pods and provisions new nodes from pre-defined node groups. Inversely, it observes underutilized nodes and drains them to reduce cost. Triggered by pod pressure, not metrics.

Karpenter

A newer alternative to CA, originally from AWS. Skips the "node group" abstraction and provisions instances directly from EC2 (or other cloud APIs). Picks instance types based on actual pod requirements — faster, more efficient, less config.

CA vs Karpenter
  1. CA needs pre-defined node groups. You decide instance types up front; CA scales them up/down.
  2. Karpenter picks instances dynamically. Given pod requirements, it selects the optimal instance type from a NodePool spec.
  3. CA is simpler operationally. Karpenter is more efficient but requires more setup and trust.
  4. Both depend on pod requests being accurate. Bad requests → bad scaling decisions. Right-sizing matters even with autoscaling.

Karpenter NodePool — Jahez default pool

karpenter-nodepool.yaml 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: jahez-default
spec:
  template:
    spec:
      requirements:
      - key: karpenter.k8s.aws/instance-category
        operator: In
        values: [c, m, r]
      - key: karpenter.k8s.aws/instance-cpu
        operator: In
        values: ["4", "8", "16"]
      - key: karpenter.k8s.aws/instance-generation
        operator: Gt
        values: ["4"]
      - key: topology.kubernetes.io/zone
        operator: In
        values: [me-south-1a, me-south-1b, me-south-1c]
      - key: karpenter.sh/capacity-type
        operator: In
        values: [on-demand, spot]

      nodeClassRef:
        name: default
        group: karpenter.k8s.aws
        kind: EC2NodeClass

  limits:
    cpu: "1000"           # cluster-wide CPU cap from this pool
    memory: "2000Gi"

  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 5m     # wait 5min before consolidating
💡 The HPA + CA / Karpenter dance

HPA increases replicas → some are unschedulable → CA / Karpenter notices → provisions a node → pods bind. Latency from "load arrives" to "new pod serves traffic" is typically 90–180 seconds. Plan headroom accordingly — keep enough buffer in HPA minReplicas that you don't need a new node for every traffic spike.

V.1 Node-level · Resource Managers

The kubelet's three managers: CPU, Memory, Topology

Definition Principles Diagram YAML
Resource managers

Kubelet subsystems that coordinate which specific CPUs, memory regions, and NUMA nodes a container's processes are pinned to. By default, the kernel scheduler decides — workloads can land on any CPU and bounce between NUMA nodes. For latency-sensitive or NUMA-aware workloads, this default is wrong.

When to enable them
  1. Default kubelet (no managers) works for the vast majority of stateless services. Don't enable the managers unless you have evidence you need them.
  2. CPU Manager (static policy) for Guaranteed pods that need exclusive CPU cores — latency-critical services, ML inference, real-time workloads.
  3. Memory Manager when running large-page workloads or memory-bandwidth-sensitive applications.
  4. Topology Manager coordinates the above + device plugins (GPUs, NICs) to ensure all resources for a pod come from the same NUMA node.
NUMA-aware placement vs default

Topology Manager policies

PolicyBehavior
noneDefault. No NUMA-aware placement. Kubelet ignores topology hints.
best-effortTry to align on a NUMA node; admit pod even if can't.
restrictedReject pod if NUMA alignment can't be achieved. Recommended for production NUMA-sensitive workloads.
single-numa-nodeStrictest: all resources must come from a single NUMA node, or reject.

Enabling on a kubelet

/var/lib/kubelet/config.yaml 
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration

cpuManagerPolicy: static
memoryManagerPolicy: Static
topologyManagerPolicy: restricted
topologyManagerScope: pod            # or container

reservedSystemCPUs: "0,1"           # reserve cores 0-1 for OS/kubelet
V.2 Node-level · Node-pressure eviction

Node-pressure eviction: how kubelet protects itself

Definition Principles YAML
Node-pressure eviction

A kubelet mechanism that proactively kills pods before the kernel runs out of memory or disk space. Different from OOM-kill — eviction is a Kubernetes-aware operation that respects QoS, priority, and grace periods. The kubelet's last line of defense against node-wide failure.

Soft vs hard thresholds
  1. Hard threshold — when crossed, kubelet kills pods immediately, no grace period. Use for catastrophic conditions.
  2. Soft threshold — when crossed for longer than evictionSoftGracePeriod, kubelet starts evicting gracefully (sends SIGTERM, waits up to evictionMaxPodGracePeriod).
  3. Soft + hard pair — soft at 15% free memory, hard at 5%. Soft gives apps time to exit cleanly; hard prevents kubelet itself from dying.
  4. Eviction order respects QoS and priority. BestEffort first, then Burstable exceeding requests, then by priority.

Eviction signals

SignalDescription
memory.availableNode memory available. Most common eviction trigger.
nodefs.availableFree space on node filesystem (where logs, container layers live).
nodefs.inodesFreeFree inodes on node filesystem. Often the actual culprit when "disk full" makes no sense.
imagefs.availableFree space on image filesystem if separate from nodefs.
pid.availableAvailable process IDs. Catches fork bombs.

Production eviction config

/var/lib/kubelet/config.yaml 
evictionHard:
  memory.available: "200Mi"
  nodefs.available: "10%"
  nodefs.inodesFree: "5%"
  imagefs.available: "15%"

evictionSoft:
  memory.available: "500Mi"
  nodefs.available: "15%"

evictionSoftGracePeriod:
  memory.available: "1m30s"
  nodefs.available: "2m"

evictionMaxPodGracePeriod: 60      # cap on pod's terminationGracePeriod during eviction
evictionPressureTransitionPeriod: "5m"  # debounce flapping
V.3 Node-level · system-reserved

System-reserved: keeping the kubelet alive

Definition Principles YAML
Node allocatable

The portion of a node's total capacity that Kubernetes can schedule pods into. Computed as: allocatable = capacity − kube-reserved − system-reserved − eviction-hard. Everything else is held back for the kubelet, the container runtime, and the OS.

Why this matters
  1. Without reservations, the kubelet competes with pods for CPU. Under load, kubelet itself becomes slow → pod status updates lag → eviction loops fail.
  2. System daemons need RAM too. systemd-journald, ssh, monitoring agents, the runtime — easily 1–2 Gi.
  3. Eviction threshold is part of the formula. evictionHard.memory.available reserves a buffer kubelet keeps untouched.
  4. Cloud defaults are often wrong. Verify what EKS/GKE/AKS reserves on your node sizes — small nodes (4 Gi) are especially prone to under-reservation.

VI.1 SRE playbook · Right-sizing

Right-sizing as a closed loop, not a one-shot

Definition Principles Diagram Checklist
Right-sizing

The continuous process of adjusting pod requests and limits so they match observed usage with appropriate headroom. Not a one-time exercise — workloads drift as features ship, traffic grows, and dependencies change. Treat it as a quarterly engineering ritual.

The right-sizing loop
  1. Measure historical usage over a representative window (2–4 weeks, including peak days).
  2. Recommend new requests at p75–p90 of observed usage; limits with appropriate headroom.
  3. Apply via PR review — sizing changes are code changes, not console tweaks.
  4. Verify after rollout that latency, error rate, and resource consumption look right. Watch for one full traffic cycle.
01

Measure

Pull 2–4 weeks of container_memory_working_set_bytes and container_cpu_usage_seconds_total. Include weekly peaks.

02

Recommend

requests = p75 of usage. Limits = p99 × 1.3 for memory, p99 × 2 for CPU. Cross-check with VPA advisor.

03

Apply

Update Deployment via Git PR. Roll out one workload at a time. Don't batch ten sizing changes into one PR.

04

Verify

Watch p99 latency, OOM count, CFS throttle ratio for one full traffic cycle (24h minimum). Roll back if anything regresses.

Four metrics that actually matter

MetricWhat it tells you
container_memory_working_set_bytesTrue memory usage as the OOM killer sees it. The one to use for memory sizing.
container_cpu_cfs_throttled_seconds_totalTime the container was throttled. Anything > 5% of CFS periods means CPU limits are too tight.
container_cpu_usage_seconds_total (rate)Average CPU usage. Use p75 for requests, p99 for limit sizing.
kube_pod_container_status_restarts_totalRestart count. OOM-kills increment this — a leading indicator that memory is undersized.

Headroom guidance per workload type

WorkloadRequestLimit headroom
Stateless HTTP (Go, Node)p75 usageMemory: +30%. CPU: 2–4× for burst.
JVM servicep75 usageMemory: +50% (GC headroom). CPU: 2× minimum.

At Jahez scale, a quarterly review across the top 20 deployments by request-cost typically recovers 15–25% of namespace quota. Pair it with a VPA-Off rollout so the advisor's recommendations are always fresh.

  • VPA in Off mode deployed for every production workload (free advisor).
  • Dashboards for working-set, throttle ratio, restart count exist per service.
  • Sizing changes go through PR review, not kubectl edit.
  • Rollouts are one workload at a time, with verification.

VI.2 SRE playbook · Patterns & anti-patterns

What good looks like — and what to never ship

Definition Principles

Patterns are reusable combinations of the primitives this guide has covered. Anti-patterns are configurations that look reasonable but bite you in production. Both are listed below as concrete setups, not vague advice.

Patterns to adopt

✓ LimitRange + ResourceQuota as a pair

LimitRange supplies defaults so developers don't have to declare resources for every container. ResourceQuota caps the namespace total. Neither works well alone — quota without defaults causes apply failures; defaults without quota causes runaway namespaces.

✓ Runtime-aware environment variables

Inject GOMEMLIMIT, -XX:MaxRAMPercentage, or --max-old-space-size via Downward API referencing limits.memory. The runtime now respects the same ceiling the kernel will enforce.

✓ CPU requests yes, CPU limits maybe

Always set CPU requests (scheduler needs them). CPU limits are optional: on dedicated nodes for latency-critical services, omit them. On shared multi-tenant nodes, set them to control noisy neighbors.

✓ HPA + PDB + PriorityClass trio

HPA scales replicas to load. PDB protects against voluntary disruption (drains, upgrades). PriorityClass decides who wins under scarcity. Every production Deployment should have all three.

✓ VPA-Off as a passive advisor

Deploy VPA in updateMode: Off for every workload. It costs nothing, generates real recommendations, and surfaces sizing problems before users complain.

Anti-patterns to avoid

✕ BestEffort QoS in production

Pods without any requests or limits are first to evict under node pressure. A traffic spike kills your most popular service first. Always set at least requests; LimitRange should backstop missing values.

✕ Memory limit == request with no headroom

Looks disciplined, OOMs at 02:00. Garbage-collected runtimes need at least 20% headroom between request and limit to GC effectively before the kernel kills them.

✕ minReplicas: 1 on user-facing services

One replica means zero redundancy during rollouts, drains, and node failures. minReplicas: 2 is the absolute floor; 3 for anything user-facing in a multi-zone cluster.

⚠ HPA on memory for garbage-collected languages

JVM and Go runtimes hold onto memory after GC. The HPA sees "memory at 80%" and scales up, but actual demand has dropped. Use CPU or RPS-based custom metrics instead.

✕ VPA Auto + HPA on the same axis

VPA shrinks the request → HPA sees higher utilization ratio → adds pods → VPA shrinks further. Thrashing loop. Either VPA on memory + HPA on CPU, or VPA Off-mode + HPA on anything.

⚠ ResourceQuota without LimitRange

Every developer's first apply fails with "must specify requests.cpu". They'll either give up or copy-paste arbitrary values from Stack Overflow. Pair the two.

VI.3 SRE playbook · Troubleshooting

Diagnosing resource failures: a field manual

Definition Pitfalls

Five symptoms cover ~90% of resource-related production incidents. For each, the diagnostic path is straightforward once you know which gate produced the failure.

Symptom 1: OOMKilled

$ kubectl describe pod <name> 
Last State:     Terminated
  Reason:       OOMKilled
  Exit Code:    137
  Started:      Mon, 22 May 2026 04:15:00
  Finished:     Mon, 22 May 2026 04:38:21

Three possibilities: (1) memory limit too low — check working-set vs limit; (2) memory leak — restart interval shrinks over time; (3) sudden allocation spike — correlate with traffic. Fix the right one; don't just bump the limit.

Symptom 2: high latency, low average CPU

PromQL — throttle ratio 
sum by (pod) (rate(container_cpu_cfs_throttled_seconds_total[5m]))
/
sum by (pod) (rate(container_cpu_cfs_periods_total[5m]))

If the ratio is > 0.05, you're being throttled. Average CPU looks fine because the kernel pauses you between bursts. Raise CPU limit, or on dedicated nodes consider omitting it.

Symptom 3: pod stuck Pending

$ kubectl describe pod <name> — Events section 
Events:
  Warning  FailedScheduling  31s  default-scheduler
    0/8 nodes are available:
    3 Insufficient cpu, 5 Insufficient memory.

Gate 3 (scheduler) verdict. Either request is too large for any node, or all nodes are saturated. Cluster Autoscaler should kick in within 60–90s; if not, check the autoscaler logs.

Symptom 4: pod Evicted

$ kubectl get pod <name> -o yaml 
status:
  phase: Failed
  reason: Evicted
  message: 'The node was low on resource: memory.'

Node-pressure eviction (gate 4/5). Node hit a soft or hard threshold. Check node memory/disk usage at the eviction time; check if QoS class was BestEffort or Burstable-over-request.

Symptom 5: kubectl apply rejected

error from quota 
Error from server (Forbidden): error when creating "deploy.yaml":
  pods "checkout-7d9c-xxxx" is forbidden:
  exceeded quota: jahez-prod-services,
  requested: requests.cpu=2, used: requests.cpu=39, limited: requests.cpu=40

Gate 2 (admission). Quota check failed at apply time. Either raise the quota (with capacity team approval) or right-size existing workloads to free room.

VI.4 SRE playbook · Production checklist

The pre-flight: before this hits prod

Checklist

A single page to walk through before promoting a new service — or auditing an existing one. Each item maps to a chapter in this guide.

Namespace level

Namespace pre-flight
  • LimitRange defines defaults, min/max, and maxLimitRequestRatio for both CPU and memory.
  • ResourceQuota caps requests.*, limits.*, and count/*.
  • Batch and long-running workloads have separate quota buckets via scopeSelector.
  • NetworkPolicy default-deny in place (out of scope here, but pair with resource policy).

Per-workload

Workload pre-flight
  • Explicit requests.cpu, requests.memory, limits.cpu, limits.memory on every container.
  • requests.ephemeral-storage set (default 100Mi is usually too low).
  • Runtime memory flag wired via Downward API — GOMEMLIMIT / -XX:MaxRAMPercentage / --max-old-space-size.
  • Liveness + readiness probes defined (out of scope here, but resource sizing without probes is incomplete).
  • PriorityClass assigned — critical / standard / batch.
  • PodDisruptionBudget covers the Deployment with maxUnavailable: 1 (not minAvailable: 100%).
  • HPA with minReplicas ≥ 2 and a hard maxReplicas ceiling.
  • topologySpreadConstraints across zones for redundancy.
  • VPA in Off mode deployed as advisor.

Cluster level

Cluster pre-flight
  • kubeReserved and systemReserved set explicitly on every node — not relying on cloud defaults.
  • evictionHard and evictionSoft thresholds configured, with grace periods.
  • Cluster Autoscaler / Karpenter limits set to cap runaway scale-out cost.
  • Topology Manager policy chosen consciously (none is fine for most clusters; restricted for NUMA-sensitive workloads).
  • Cost dashboard showing $/namespace and $/workload — sizing improvements need a feedback loop.
🛡 Policy, not vibe

The checklist above should be enforced by policy engines (Kyverno, OPA Gatekeeper), not by code review alone. Resource hygiene drifts the moment review attention shifts. A policy that blocks apply on missing requests is worth more than a hundred Slack reminders.
