02 Two Retry Systems

Definition — Kubelet Retry (Container Level)The kubelet on each node is responsible for starting containers and restarting them when they fail. It handles: image pull retries, config check retries, container restart after crash/OOM/probe failure. The kubelet retries on the same Pod, same node, same IP. Controlled by restartPolicy (for runtime failures) or unconditionally (for pre-run failures).
Definition — Controller Retry (Pod Level)A controller (Deployment, ReplicaSet, Job) watches for missing/failed Pods and creates brand new Pods (new name, new IP, possibly different node). This handles: eviction, node death, Job retries. The original Pod is gone — the controller creates a replacement. Controlled by spec.replicas (Deployments) or backoffLimit (Jobs).
Q: What's the difference between kubelet restart and controller recreation? Kubelet restart = same Pod object, same name, same IP, same node. The container process is restarted inside the existing Pod. Fast (seconds).
Controller recreation = brand new Pod object, new name, new IP, possibly different node. The old Pod is deleted. Slower (10s-5min depending on scheduling + image pull).

03 Backoff Deep Dive — Every Second Explained

Definition — Exponential BackoffWhen a container keeps failing, Kubernetes increases the wait time between retries. The formula is: delay = min(10s × 2^(restart_count - 1), 300s). The delay caps at 300 seconds (5 minutes) and stays at 300s forever — it does NOT stop retrying.

Q: What happens after backoff reaches 300 seconds? Does it stop? NO. It keeps retrying every 300 seconds (5 minutes) forever. There is no maximum retry count. There is no timeout. The kubelet will keep restarting the container every 5 minutes for weeks, months, years — until you either fix the problem, delete the Pod, or the node dies. The backoff caps at 300s but never stops.
Q: Does the backoff timer ever reset? YES. If the container runs successfully for 10 consecutive minutes (600 seconds) without crashing, the backoff timer resets to 10 seconds. So if the container crashes after running for 15 minutes, the next wait is only 10s, not 300s.

Exact rule: lastRestartTime - lastCrashTime > 10 minutes → reset backoff to 10s.
Q: Is there jitter in the backoff? YES. Kubernetes adds a small random jitter (up to ±10%) to prevent all containers from retrying at exactly the same time. So a "20 second" backoff might actually be 18-22 seconds. The exact values in the table above are approximate.

04 Scheduling Failures ▶

Behavior
Timing details
Edge cases
Fix
RETRIES FOREVER — event-driven, no backoff
The scheduler uses a watch mechanism, not polling. It watches for events: new node added, pod deleted, node resources freed, labels changed. Every time a relevant event occurs, it re-evaluates all pending Pods instantly. There is no fixed retry interval — it reacts in real-time.
Exact Timing Details
How often does it check? The scheduler does NOT poll on a timer. It uses Kubernetes informers (watch API) to get instant notifications of cluster changes. When anything changes (node added, pod deleted, resource freed), the scheduler processes the queue of unscheduled Pods within ~100ms.

Is there a maximum pending time? No. A Pod can stay in Pending forever — days, weeks, months. There is no timeout.

What triggers a re-evaluation? Any change to: nodes (add/remove/label/taint), pods (create/delete), PVs/PVCs (create/bind), or resource quotas.

Scheduler throughput: The default scheduler can process ~100-200 pods/second on a standard cluster.
Edge Cases
Q: What if I have a Pod requesting 128 CPU cores and no node has that? The Pod stays in Pending forever. The scheduler never gives up. It just keeps waiting for a node with 128 cores to appear. You must either delete the Pod or add a node with enough resources.
Q: What if the Pod has a nodeSelector for a label that no node has? Same: Pending forever. The scheduler watches for nodes being labeled. The moment you run kubectl label node X my-label=value, the scheduler instantly schedules the Pod (within ~100ms).
How to fix
# See WHY it's pending
kubectl describe pod stuck-pod | grep -A5 "Events"

# Insufficient resources → add nodes or reduce requests
minikube node add
# Or reduce Pod requests

# Taint not tolerated → add toleration or remove taint
kubectl taint nodes node-1 dedicated=gpu:NoSchedule-   # Remove taint

# Node selector mismatch → label the node
kubectl label node node-1 disktype=ssd

Behavior
Exact timing
After max backoff

Fix
RETRIES FOREVER with exponential backoff, cap at 5 min
The kubelet tries to pull the image. On failure, it enters ImagePullBackOff — waiting before retrying. The wait doubles each time: 10s, 20s, 40s, 80s, 160s, 300s (5 min cap). After reaching 300s, it keeps retrying every 5 minutes forever.

restartPolicy has ZERO effect here. The container hasn't started yet, so there's nothing to "restart." The kubelet simply keeps trying to download the image regardless of restartPolicy.

Q: Does it stop retrying after reaching 300 seconds? Absolutely not. The 300 seconds (5 minutes) is the maximum wait between retries, not a timeout. After reaching the cap, the kubelet retries pulling the image every 5 minutes forever. It will keep doing this for hours, days, weeks — there is no limit.
Q: Does the backoff ever reset for image pulls? YES. If you fix the issue (e.g., push the correct image tag to the registry, create the imagePullSecrets), the next pull attempt will succeed. The container starts, and the backoff resets. If the image is later needed again (Pod restart), it starts from 10s again.
Q: What if the registry is temporarily down? The kubelet keeps retrying. When the registry comes back up, the next pull attempt succeeds automatically. You don't need to do anything — just wait. The Pod will start on its own.
Edge Cases
Q: What about imagePullPolicy: IfNotPresent? If set to IfNotPresent and the image is already cached on the node, the kubelet skips the pull entirely — no failure possible. The pull only happens if the image isn't cached locally. If the pull fails, same backoff behavior.
Q: What about imagePullPolicy: Always? Kubelet always contacts the registry to check for updates (even if cached locally). If the registry is unreachable, it fails with ErrImagePull and enters backoff — even if the image IS cached locally.
Q: What if I push the correct tag while the Pod is in ImagePullBackOff? You don't need to delete the Pod. The kubelet will pull the correct image on its next retry (within 5 minutes max). The Pod will start automatically.
How to fix
# Check the exact error
kubectl describe pod X | grep -A5 "Events"

# Wrong tag → fix the image (delete + recreate, or edit deployment)
kubectl set image deployment/my-app web=myapp:v2   # correct tag

# Auth needed → create pull secret
kubectl create secret docker-registry my-reg \
  --docker-server=registry.example.com \
  --docker-username=user --docker-password=pass

# Speed up retry → delete and recreate the Pod
kubectl delete pod bad-image
# (if controller-managed, it auto-creates a new one that tries immediately)

06 Config Missing ▶

Behavior
Timing details
Fix
RETRIES FOREVER — kubelet sync loop re-checks periodically
When a container references a ConfigMap, Secret, or PVC that doesn't exist, the kubelet can't create the container. It enters CreateContainerConfigError and waits. The kubelet's sync loop periodically re-checks whether the missing resource has been created.
Exact Timing Details
Q: How often does kubelet check for missing ConfigMap/Secret? The kubelet has a main sync loop that runs every --sync-frequency (default: 1 minute). On each sync, it re-evaluates all Pods assigned to the node. If a ConfigMap/Secret that was missing now exists, the kubelet detects it and creates the container.

In practice, the check happens every 60 seconds by default. Some kubelet implementations also have a watch mechanism that can detect changes faster (~1-5 seconds).
Q: Does it use exponential backoff? Not exactly. The kubelet re-evaluates at its sync frequency (every ~60s). It doesn't use the same 10s→20s→300s backoff as container restarts. It's a fixed interval check.
Q: Is there a maximum number of retries? No. It checks forever. The Pod stays in CreateContainerConfigError indefinitely until the resource appears or the Pod is deleted.
Q: Does restartPolicy affect this? No. The container has never started, so restartPolicy is irrelevant. This is a pre-start failure handled entirely by the kubelet's sync loop.
How to fix
# Create the missing resource — Pod starts automatically on next sync (~60s)
kubectl create configmap app-config --from-literal=db-host=postgres
kubectl create secret generic db-secret --from-literal=password=mypass

# OR make it optional (container starts even if resource is missing)
env:
- name: MY_VAR
  valueFrom:
    configMapKeyRef:
      name: might-not-exist
      key: value
      optional: true   # ← Container starts without this value

07 Application Crash ▶

Always
OnFailure
Never
Timing Q&A
restartPolicy: Always → Retries FOREVER, every exit code
The kubelet restarts the container regardless of exit code (even exit 0). Backoff: 10s → 20s → 40s → 80s → 160s → 300s cap. After reaching 300s, it retries every 5 minutes forever. Never gives up. Used by Deployments, StatefulSets, DaemonSets.
restartPolicy: OnFailure → Retries on non-zero exit
Same as Always, but only for non-zero exit codes. Exit 0 (success) → container stays stopped, Pod status: Succeeded. Exit 1, 137, etc. → restart with same backoff. Perfect for Jobs: retry failures, stop on success.
restartPolicy: Never → DEAD FOREVER. No retry.
The container is never restarted regardless of exit code. Pod status becomes Failed (non-zero) or Succeeded (zero) and stays there permanently. For Jobs, the Job controller creates a brand new Pod instead (up to backoffLimit, default 6).
Detailed Timing Q&A
Q: How fast does the kubelet detect a crash? Instantly. The kubelet watches container events from the runtime (containerd). When a container exits, the kubelet is notified within ~1-2 seconds. It then starts the backoff timer.
Q: If my container crashes after running for 5 minutes, what's the backoff? It depends on the restart count and whether the backoff was reset. If the container ran for less than 10 minutes, the backoff continues from where it was (doesn't reset). If it ran for more than 10 minutes, the backoff resets to 10s.
Q: My container runs for 15 minutes, crashes, runs 15 minutes, crashes. What's the backoff? Each time it runs for >10 minutes, the backoff resets. So each crash wait is only 10 seconds. You'll see: crash → 10s wait → run 15min → crash → 10s wait → run 15min → crash → 10s wait. The RESTARTS count still goes up, but the backoff stays at 10s.
Q: My container crashes immediately (<1 second) every time. When does it first reach 300s? Restart #6 reaches 300s max. Timeline: t=0 crash, t=10s retry, t=10s crash, t=30s retry, t=30s crash, t=70s retry, t=70s crash, t=150s retry, t=150s crash, t=310s retry (300s wait). First 300s wait is at approximately 5 minutes 10 seconds.
Q: Is there a maximum restart count? No. The RESTARTS counter goes up forever: 10, 50, 100, 1000+. There is no limit. Kubernetes never stops trying (with Always or OnFailure).

08 OOM Kill ▶

Behavior
Timing Q&A
Same retry behavior as app crash (exit 137)
OOM Kill produces exit code 137 (128 + SIGKILL signal 9). To the kubelet, this is just a non-zero exit. It follows the same restartPolicy logic and same backoff timing as any other crash. Always → restart forever. OnFailure → restart forever (137 ≠ 0). Never → dead.
OOM-Specific Timing Q&A
Q: How fast does the OOM kill happen? Instantly. The Linux kernel's OOM killer acts within milliseconds. There is no warning, no grace period. The process receives SIGKILL (cannot be caught or handled) and dies immediately. The kubelet detects the death within ~1-2 seconds.
Q: If my container keeps OOM-ing, will it restart forever? Yes (with Always or OnFailure). It follows the same backoff: 10s, 20s, 40s... 300s cap. Each restart, the container starts, allocates memory, hits the limit, gets OOM-killed, waits, and repeats. This cycle continues forever until you increase the memory limit or fix the memory leak.
Q: Does Kubernetes differentiate between OOM kill and app crash? Yes, for observability — the reason field shows OOMKilled instead of Error. But for retry behavior, there is no difference. Both follow the same restartPolicy and backoff logic.

09 Probe Failures ▶

Startup
Liveness

Timing Q&A
Startup Probe — LIMITED retries, then KILL
Check interval: Every periodSeconds (default: 10s).
Timeout per check: timeoutSeconds (default: 1s). If no response within this time → failure.
Max failures before kill: failureThreshold (e.g., 30).
Total startup window: failureThreshold × periodSeconds (e.g., 30 × 10 = 300s = 5 min).
After max failures: Container is KILLED. Then restartPolicy applies.
With restartPolicy: Always: Container restarts → startup probe starts over from 0 → same cycle repeats forever (CrashLoopBackOff with backoff between restarts).
Liveness Probe — KILL + restart on failure
Check interval: Every periodSeconds (default: 10s). Runs forever while container is alive.
Timeout per check: timeoutSeconds (default: 1s).
Failures to kill: failureThreshold (default: 3). So 3 consecutive failures → kill.
Time from healthy to killed: failureThreshold × periodSeconds (default: 3 × 10 = 30s).
After kill: restartPolicy applies. With Always: restart immediately (with backoff if it keeps failing). The liveness probe starts checking again after the container starts.
Resets on success: A single success resets the failure counter to 0.
Readiness Probe — NEVER kills, just removes traffic
Check interval: Every periodSeconds (default: 10s). Runs forever.
Timeout per check: timeoutSeconds (default: 1s).
Failures to remove traffic: failureThreshold (default: 3).
Successes to add back: successThreshold (default: 1).
The container is NEVER killed. Readiness only controls Service endpoints. Failed → removed from traffic. Passed → added back. This cycle continues forever at the fixed interval.
No backoff: Readiness checks at a constant interval — no exponential backoff.
Probe Timing Q&A
Q: When does the liveness probe start checking? After initialDelaySeconds (default: 0) from container start. If a startup probe is defined, liveness is completely disabled until startup passes. First liveness check happens initialDelaySeconds after startup probe passes.
Q: If liveness kills my container, what's the restart timing? The container is killed immediately upon reaching failureThreshold. Then the kubelet applies restartPolicy with the same exponential backoff (10s, 20s... 300s). If the container starts and passes liveness, the backoff timer resets after 10 minutes of healthy running.
Q: If readiness fails, how quickly is traffic removed? After failureThreshold × periodSeconds of consecutive failures. With defaults (3 × 10s), traffic is removed after ~30 seconds of readiness failure. Then kube-proxy needs 1-5 seconds to propagate the endpoint change to all nodes. Total: ~35 seconds from first failure to zero traffic.
Q: If readiness passes again, how fast does traffic come back? After successThreshold consecutive successes (default: 1). So with a 5-second periodSeconds, traffic can return within ~5-10 seconds of the Pod becoming healthy again, plus 1-5 seconds for endpoint propagation.
Q: Can a probe have a timeout longer than its period? Yes but don't. If timeoutSeconds > periodSeconds, the next probe check starts even while the previous one is still waiting. This can cause overlapping checks and unpredictable behavior. Always ensure timeoutSeconds < periodSeconds.

11 Init Container Failure ▶

Behavior
Timing Q&A
RETRIES FOREVER — ignores restartPolicy
Init containers always retry with exponential backoff regardless of the Pod's restartPolicy. Same backoff: 10s → 20s → 300s cap. The Pod stays in Init:N/M or Init:CrashLoopBackOff forever. App containers never start until all init containers succeed.
Init Container Timing Q&A
Q: restartPolicy is Never, but init container keeps retrying. Why? Init containers have special behavior. They ignore the Pod's restartPolicy because the Pod hasn't "run" yet — it's still initializing. The kubelet considers init failures as "not yet started" rather than "runtime failure." So it retries regardless. The one exception: if the Pod's restartPolicy is Never, and the init container fails, the kubelet retries the init container but the Pod will eventually be marked Failed and no new Pods are created (unless a Job controller handles it).
Q: If init container 2 of 3 fails, does init container 1 run again? No. Only the failed init container is retried. Init 1 already succeeded and won't re-run. Init 3 never starts until Init 2 succeeds. Sidecar containers (init with restartPolicy: Always) that already started keep running during init retries.
Q: Same backoff as container restart? Yes. Same formula: 10s, 20s, 40s, 80s, 160s, 300s cap. Same 10-minute success reset. Same behavior after reaching cap (retries every 5 min forever).

12 Eviction ▶

Behavior
Timing Q&A
NO RETRY — Pod is dead. Controller creates a new one.
Evicted Pods are never restarted by the kubelet. The Pod status becomes Failed with reason Evicted. It stays there until garbage collected. Only a controller (Deployment/ReplicaSet) detects the missing replica and creates a brand new Pod. Naked Pods are gone forever.
Eviction Timing Q&A
Q: How fast does eviction happen? The kubelet checks node resources every 10 seconds (housekeeping interval). When it detects pressure (memory < eviction threshold, disk < 15%), it begins evicting Pods immediately — fastest Pods (BestEffort) first. The entire eviction can happen within seconds.
Q: How long until the controller creates a replacement Pod? The ReplicaSet controller has a sync period of ~5 seconds. So within ~5-10 seconds of the Pod being evicted, the controller detects the missing replica and creates a new Pod. The new Pod then goes through the normal scheduling → image pull → startup cycle.
Q: Do evicted Pods auto-delete? Not immediately. Evicted Pods stay in Failed status until the garbage collector cleans them. You can clean them manually: kubectl get pods --field-selector status.phase=Failed -o name | xargs kubectl delete

Behavior

NO RETRY — Pod lost with the node. Controller recreates.
When a node dies (hardware failure, kernel panic, power loss), all Pods on it become unreachable. Kubernetes waits for confirmation before declaring them dead. Naked Pods are gone forever. Controller-managed Pods are recreated on healthy nodes.

Node Death Timing Q&A
Q: Why does Kubernetes wait 5 minutes? Can I speed this up? The 5-minute wait (--pod-eviction-timeout) prevents false positives — a temporary network blip shouldn't trigger Pod recreation. You can reduce it (e.g., to 30s) but risk unnecessary Pod replacement during brief network issues. In cloud environments, some setups use node-lifecycle-controller with taints for faster response.
Q: What if the node comes back after 3 minutes? If the node recovers before the eviction timeout (5 min), the kubelet reconnects, sends a heartbeat, node goes back to Ready, and Pods continue running normally. No Pods are lost.
Q: What about StatefulSets? Are their Pods recreated too? Yes, but with a catch. StatefulSet Pods are recreated with the same name and attached to the same PersistentVolume. But the controller waits longer to ensure the old Pod is truly gone (to prevent two Pods with the same identity running simultaneously). You may need to manually delete the stuck Pod: kubectl delete pod my-sts-0 --force --grace-period=0

15 FAQ — Edge Cases

Q: If I fix the bug while the Pod is in CrashLoopBackOff at 300s backoff, do I have to wait 5 minutes? Yes, unless you speed it up. The kubelet won't check until the backoff timer expires. To skip the wait: delete the Pod (kubectl delete pod X). If it's controller-managed, a new Pod is created immediately and starts fresh with no backoff.
Q: Can I change the maximum backoff from 300 seconds? No. The 300-second cap is hardcoded in the kubelet source code. There is no configuration option to change it. You can only work around it by deleting and recreating the Pod.
Q: What about the kubelet's --sync-frequency flag? This controls how often the kubelet reconciles its internal state with the desired state. Default: 1 minute. This affects how fast it detects changes to ConfigMaps/Secrets/Pod specs. It does NOT affect the container restart backoff (which is a separate timer).
Q: If a container exits 0 with restartPolicy: Always, is there backoff? Yes. Even successful exits (code 0) trigger backoff with Always. If a container exits 0 immediately every time, it enters CrashLoopBackOff just like a crash. This prevents infinite rapid restart loops for containers that succeed instantly.
Q: My Pod has 2 containers. One crashes, one is fine. What happens? Only the crashed container restarts. The healthy container keeps running. The backoff applies only to the failed container. The Pod stays Running but shows READY 1/2. Both containers share the same restartPolicy (it's Pod-level).
Q: What if my container takes 30 seconds to start, but crashes at second 25? The container ran for 25 seconds, which is less than 10 minutes, so the backoff does NOT reset. The next wait is the next backoff step. If this was restart #3, the wait would be 40 seconds.
Q: Does force-deleting a Pod (--grace-period=0 --force) affect retry? Force delete removes the Pod object from the API server immediately. If the Pod was controller-managed, the controller creates a new Pod within ~5 seconds. The new Pod starts fresh — no backoff history.
Q: What happens to readiness during CrashLoopBackOff? When the container is down (waiting for backoff), readiness is automatically false. The Pod is removed from Service endpoints. When the container restarts and passes readiness, it's added back. So during CrashLoopBackOff, the Pod gets no traffic during the "dead" periods.
Q: Job backoffLimit vs container restart — what's the difference? restartPolicy controls container-level restart (same Pod). backoffLimit (Job spec, default: 6) controls how many new Pods the Job creates. With restartPolicy: Never and backoffLimit: 6, the Job creates up to 6 separate Pods, each attempting once. With restartPolicy: OnFailure and backoffLimit: 6, each Pod's container restarts indefinitely, but the Job still counts 6 Pod failures before giving up.
