01 What is a Pod?

Definition: A Pod is the smallest deployable unit in Kubernetes — a logical host for one or more containers that share network (same IP), storage (shared volumes), and lifecycle (co-scheduled, start/stop together).

Analogy

A Pod is a shared apartment. Containers are roommates — same address (IP), same fridge (volumes), same lease (lifecycle).

Shared ResourceDefinitionPractical Impact
NetworkAll containers share one IP address and port space via a Linux network namespaceContainer A reaches Container B via localhost:PORT. No service discovery needed within a Pod.
StorageVolumes declared in the Pod spec are mountable by any containerApp writes logs to /var/log, sidecar reads from the same path and ships them.
LifecycleAll containers are co-scheduled to the same node and managed as a unitPod deleted → ALL containers get SIGTERM. Node fails → ALL containers fail.
Pause ContainerHidden infrastructure container that holds the network namespace aliveWhen your app crashes and kubelet restarts it, the Pod's IP stays the same because the pause container is still running.
SRE Principle — Cattle, Not Pets

Pods are disposable. They get new names/IPs when replaced. Never store data without a PersistentVolume. Never depend on a specific Pod's IP. If a Pod is sick, replace it — don't repair it.

02 Pod Creation Flow — Step by Step

Definition: When you run kubectl apply -f pod.yaml, the Pod doesn't appear instantly. It goes through a multi-step orchestration involving the API server, etcd, scheduler, and kubelet.

① Submit
② Store
③ Schedule
④ Pull Image
⑤ Init Containers
⑥ Start App
⑦ Probes
⑧ Ready!
① You submit the Pod YAML to the API Server
You (kubectl) → API Server → validates YAML, authenticates, authorizes
What happens: kubectl apply -f pod.yaml sends the Pod spec to the Kubernetes API server via HTTPS. The API server validates the YAML schema, checks your RBAC permissions, runs admission controllers (mutating and validating webhooks), and then accepts the Pod object.
Pod status at this point: Pending — the Pod exists in the system but has no node assigned yet.
$ kubectl apply -f pod.yaml
pod/my-app created
② API Server writes Pod to etcd
API Server → etcd (cluster database)
What happens: The API server persists the Pod object to etcd — the distributed key-value store that is the single source of truth for all Kubernetes state. The Pod is now durably stored, but still has no node assigned (spec.nodeName is empty).
Definition — etcd: A strongly consistent, distributed key-value store used by Kubernetes to store all cluster data: Pods, Services, ConfigMaps, Secrets, and more. If etcd goes down, the cluster loses its brain.
③ Scheduler assigns the Pod to a node
Scheduler watches for unscheduled Pods → evaluates nodes → picks best fit

worker-01: 90% CPU worker-02: 40% CPU ✓ worker-03: tainted
What happens: The kube-scheduler watches for Pods with empty spec.nodeName. It runs a scoring algorithm considering: resource availability, node affinity/anti-affinity, taints/tolerations, pod topology spread, and inter-pod affinity. It picks the best node and writes spec.nodeName: worker-02 to the API server.
If no node is suitable: The Pod stays in Pending with event FailedScheduling: 0/3 nodes are available.
④ Kubelet pulls the container image
kubelet (worker-02) → Container Registry (Docker Hub / ECR / GCR) → downloads image layers
What happens: The kubelet on worker-02 receives the Pod spec. It instructs the container runtime (containerd/CRI-O) to pull the image. The runtime downloads each layer, unpacks them, and creates a container filesystem. This can take seconds (cached) to minutes (large image, slow network).
If image pull fails: Status shows ImagePullBackOff. Causes: wrong image name/tag, auth required, registry down, rate limited. Kubelet retries with exponential backoff.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 ContainerCreating 3s
⑤ Init containers run (sequentially)
Init 1: wait-for-db → Init 2: migrate → Init 3: download-certs

Each runs one at a time. Each must exit 0 before the next starts.
What happens: If the Pod has initContainers, they execute sequentially. Init 1 runs first; when it exits 0, Init 2 starts; and so on. If any fails, the kubelet retries it. The Pod stays in Init:1/3 status until all succeed. Sidecar containers (init containers with restartPolicy: Always) start and keep running.
If an init container fails: Pod stays in Init:N/M and keeps retrying. App containers never start until all inits pass.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 Init:1/3 8s
⑥ App containers start (in parallel)
Container: web (PID 1: nginx)   Container: metrics (PID 1: exporter)

All app containers start simultaneously. postStart hooks run (if defined).
What happens: The kubelet creates a pause container first (holds network namespace), then starts all app containers in parallel. Each container gets its own PID namespace but shares the Pod's network. If a postStart hook is defined, it runs immediately after the container starts (in parallel with the entrypoint). Pod status: Running.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 PodInitializing 14s
⑦ Probes begin — startup → liveness → readiness
Startup probe: checking /healthz... → pass ✓ → Liveness + Readiness probes activate
What happens: If a startup probe is defined, it runs first. During this time, liveness and readiness probes are disabled. Once the startup probe passes, liveness and readiness probes begin running on their configured intervals. The readiness probe determines when the Pod can receive traffic from Services.
If startup probe keeps failing: After failureThreshold × periodSeconds (e.g., 30×10 = 300s), the container is killed and restarted.
⑧ Pod is Ready — receives traffic! ✓
Users → Service (LB) → Pod: my-app (READY 1/1) ✓ → Database
What happens: Once the readiness probe passes, the Pod's IP is added to the Service's Endpoints list. kube-proxy on every node updates its iptables/IPVS rules to include this Pod. Traffic starts flowing. The Pod is fully operational.
Condition Ready: True means the Pod is serving traffic via Service.
$ kubectl get pod my-app
NAME READY STATUS RESTARTS AGE
my-app 1/1 Running 0 21s

04 Creating Pods — All Methods

Method 1 — YAML File (Declarative)

apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels: { app: web, version: v2.1 }
spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: web
    image: myapp:v2.1
    ports: [{ containerPort: 8080 }]
    resources:
      requests: { cpu: "250m", memory: "128Mi" }
      limits: { cpu: "500m", memory: "256Mi" }
    livenessProbe:
      httpGet: { path: /healthz, port: 8080 }
    readinessProbe:
      httpGet: { path: /ready, port: 8080 }

Method 2 — CLI (Imperative)

kubectl run my-app --image=nginx:1.25 --port=80
kubectl run tmp --image=busybox --rm -it --restart=Never -- sh   # one-shot debug
kubectl run my-app --image=nginx --dry-run=client -o yaml > pod.yaml  # generate YAML

Method 3 — Via Controller (Production)

kubectl create deployment my-app --image=myapp:v2.1 --replicas=3
SRE Principle — Never Run Naked Pods in Production

Naked Pods won't be rescheduled if a node dies. Always use Deployments/StatefulSets — they recreate Pods automatically. The difference: "auto-healed in seconds" vs "pager goes off at 3 AM."

05 Updating Pods

Definition: Pods are mostly immutable. You can't change the image, command, or environment of a running Pod. Updates require Pod replacement.

Manual Pods — Delete + Recreate (Causes Downtime)

kubectl get pod my-app -o yaml > backup.yaml   # Export
# Edit backup.yaml (change image, env, etc.)
kubectl delete pod my-app                      # ⚠ DOWNTIME STARTS
kubectl apply -f backup.yaml                   # ⚠ DOWNTIME ENDS

Controller Pods — Rolling Update (Zero Downtime)

kubectl set image deployment/my-app web=myapp:v2.2   # Change image
kubectl rollout status deployment/my-app              # Watch progress
kubectl rollout undo deployment/my-app                # Rollback

06 Rolling Update — Step by Step

Definition: A rolling update gradually replaces old Pods with new ones, ensuring zero downtime. The Deployment creates a new ReplicaSet, scales it up while scaling the old one down.

① Before
② New RS
③ Scale Up
④ Replace
⑤ Continue
⑥ Complete
① All 3 Pods running v1
ReplicaSet-v1 (replicas: 3):
Pod 1 (v1) ✓ Pod 2 (v1) ✓ Pod 3 (v1) ✓
Everything is stable. All 3 Pods are running version 1 of your app, managed by ReplicaSet-v1. The Service load-balances across all 3.
② You trigger the update — new ReplicaSet created
ReplicaSet-v1 (replicas: 3):
Pod 1 (v1) Pod 2 (v1) Pod 3 (v1)

ReplicaSet-v2 (replicas: 0): ← NEW, empty
kubectl set image deployment/my-app web=myapp:v2 — the Deployment controller detects the template change and creates a new ReplicaSet (RS-v2) with 0 replicas. The old RS-v1 still has 3.
$ kubectl set image deployment/my-app web=myapp:v2
deployment.apps/my-app image updated
③ RS-v2 scales up to 1 — first new Pod created
ReplicaSet-v1 (replicas: 3):
Pod 1 (v1) Pod 2 (v1) Pod 3 (v1)

ReplicaSet-v2 (replicas: 1):
Pod 4 (v2) ⏳ starting...
RS-v2 scales to 1. A new Pod with the v2 image is created. maxSurge: 1 allows one extra Pod (4 total temporarily). The new Pod goes through image pull → init → startup. It must pass its readiness probe before the old Pod can be terminated.
$ kubectl rollout status deploy/my-app
Waiting for deployment rollout: 1 out of 3 new replicas have been updated...
④ New Pod ready → old Pod terminated
ReplicaSet-v1 (replicas: 2):
Pod 1 (v1) terminating... Pod 2 (v1) Pod 3 (v1)

ReplicaSet-v2 (replicas: 1):
Pod 4 (v2) ✓ READY
Pod 4 (v2) passes its readiness probe → it's now in the Service's endpoints. RS-v1 scales down from 3→2 — Pod 1 receives SIGTERM and begins graceful shutdown. The Service routes traffic to Pod 2, Pod 3, and Pod 4. At no point is there zero healthy Pods.
⑤ Process continues — replace remaining Pods
ReplicaSet-v1 (replicas: 1):
Pod 3 (v1)

ReplicaSet-v2 (replicas: 2):
Pod 4 (v2) ✓ Pod 5 (v2) ✓
The process repeats: RS-v2 scales to 2, RS-v1 scales to 1. Each new Pod must pass readiness before the next old Pod is killed. Traffic is always served by at least 3 Pods (mix of v1 and v2).
$ kubectl rollout status deploy/my-app
Waiting for deployment rollout: 2 out of 3 new replicas have been updated...
⑥ Rollout complete — all Pods on v2 ✓
ReplicaSet-v1 (replicas: 0): ← kept for rollback history

ReplicaSet-v2 (replicas: 3):
Pod 4 (v2) ✓ Pod 5 (v2) ✓ Pod 6 (v2) ✓
All 3 Pods are now v2. RS-v1 is scaled to 0 but not deleted — it's kept as a rollback target. Running kubectl rollout undo would scale RS-v1 back up and RS-v2 down, instantly reverting to v1.
$ kubectl rollout status deploy/my-app
deployment "my-app" successfully rolled out

07 Graceful Shutdown — Step by Step

Definition: When a Pod is deleted, Kubernetes follows a 6-step shutdown sequence designed to give your application time to finish work, close connections, and clean up without losing data.

① Delete
② Endpoints
③ preStop
④ SIGTERM
⑤ Grace Period
⑥ SIGKILL
① You delete the Pod
Users → Service → Pod: my-app (serving traffic) → Database
kubectl delete pod my-app — the API server marks the Pod as Terminating. The Pod still exists but is now scheduled for deletion. The terminationGracePeriodSeconds countdown begins (default: 30s).
② Pod removed from Service endpoints (IN PARALLEL with step ③)
Users → Service ✗ Pod: my-app (Terminating) → Database

⚠ Endpoint removal takes 1-5 seconds to propagate to all kube-proxies on all nodes
The Endpoints controller removes the Pod's IP from the Service's endpoint list. kube-proxy on every node updates iptables/IPVS rules. But this propagation is not instant — during the 1-5 second window, some nodes may still route traffic to this Pod.
This is why preStop: sleep 5 exists — to delay the actual shutdown until endpoints are fully propagated, preventing "connection reset" errors.
③ preStop hook runs (if configured)
preStop: sleep 5 → waits for endpoint removal to propagate → then: nginx -s quit
The kubelet calls the preStop handler — either an exec command or an httpGet request. This runs synchronously — SIGTERM is NOT sent until preStop finishes. The preStop execution time counts toward the grace period. Common use: sleep 5 to let endpoints propagate, then trigger app's own graceful drain.
lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 5 && /app/drain.sh"]
④ SIGTERM sent to PID 1 — App must handle this!
SIGTERM → PID 1 → App catches signal → Finishes in-flight requests → Closes DB connection → Flushes metrics buffer → exit 0
SIGTERM is sent to PID 1 in each container. Your app must catch this signal and: (1) stop accepting new requests, (2) finish in-flight requests, (3) close database/Redis connections (commit pending transactions), (4) flush write buffers and metrics, (5) exit with code 0.
⚠ PID 1 trap: If your Dockerfile uses shell form CMD app, PID 1 is bash, which does NOT forward SIGTERM to your app! Use exec form CMD ["app"] or use tini as init process.
⑤ Grace period countdown (default: 30 seconds)
preStop time + SIGTERM shutdown time must fit inside terminationGracePeriodSeconds: 60

Example: preStop takes 5s + app drains in 10s = 15s total. Well within 60s grace period. ✓
Kubernetes waits up to terminationGracePeriodSeconds for the container to exit. The total time includes preStop + shutdown time. If your app needs 60s to drain, set the grace period to 75s (60 + buffer). If the container exits before the deadline, Kubernetes proceeds immediately to step ⑥.
spec:
  terminationGracePeriodSeconds: 60 # default is 30
⑥ SIGKILL — If container is still alive after grace period
SIGKILL ☠ → Process force-killed by Linux kernel

In-flight requests get "connection reset". DB transactions rolled back. Buffered data lost. Metrics gap.
SIGKILL cannot be caught or handled. The Linux kernel force-terminates the process. This is the last resort. If your containers are regularly getting SIGKILLed, it means they're not shutting down fast enough — increase the grace period or fix the app's shutdown logic. After SIGKILL, the Pod object is removed from the API server and etcd.
Step 1 of 6
SRE Principle — Test Graceful Shutdown Under Load

Run a load test, then kubectl delete pod. Check for zero 5xx errors. If you see "connection reset" or 502s, add preStop: sleep 5 and increase terminationGracePeriodSeconds. This is the #1 cause of errors during deployments.

08 Shutdown Scenarios

Scenario A — App handles SIGTERM ✓

SIGTERM → app finishes requests (3s) → closes DB conn (1s) → exit 0. Result: zero data loss, zero failed requests.

Scenario B — App ignores SIGTERM ✗

SIGTERM → app ignores it → 60s pass → SIGKILL ☠. Result: in-flight requests get "connection reset". DB transactions rolled back. Data potentially lost.

Scenario C — No preStop hook ⚠

SIGTERM sent immediately, but Service endpoints take 1-5s to propagate. During this window, kube-proxy still routes traffic to the terminating Pod → users get 502 errors. Fix: add preStop: sleep 5.

12 Failure Diagnosis — Step by Step

Definition: Failures happen in a predictable order during the Pod lifecycle. Walk through each category to systematically diagnose any Pod issue.

① Schedule
② Image
③ Config
④ Crash
⑤ OOM
⑥ Probe
⑦ Dependency
① Scheduling Failure — No suitable node found
Pod stuck in Pending → No node has enough CPU/memory
Definition: The scheduler cannot find any node that satisfies the Pod's requirements (resources, affinity, tolerations). The Pod stays in Pending indefinitely.
$ kubectl describe pod stuck-pod | tail -3
Warning FailedScheduling default-scheduler
0/3 nodes are available: 1 Insufficient cpu, 2 had taint {gpu: true}.
Detect: kubectl describe pod → Events → FailedScheduling
Fix: Add nodes, reduce resource requests, fix nodeSelector/affinity, add tolerations, delete unused Pods
② Image Pull Failure — Can't download container image
ImagePullBackOff → Registry: image not found / auth failed
Definition: The kubelet instructs the container runtime to pull the image, but it fails. Causes: wrong name/tag, registry requires authentication (missing imagePullSecrets), network issue, Docker Hub rate limit.
Failed to pull image "myapp:v99": rpc error: manifest unknown
Error: ImagePullBackOff
Detect: kubectl describe pod → Events → ErrImagePull/ImagePullBackOff
Fix: Verify image:tag exists (docker pull myapp:v99), create imagePullSecrets, check network/DNS
③ Config Failure — Missing ConfigMap, Secret, or Volume
CreateContainerConfigError → ConfigMap "app-config" not found
Definition: The container references a ConfigMap, Secret, or PVC that doesn't exist in the namespace. The container can't be created because its configuration is incomplete.
Error: configmap "app-config" not found
Fix: Create the missing resource: kubectl create configmap app-config --from-file=config.yaml
Or mark it optional: optional: true in the env/volume reference
④ Application Crash — Container starts then dies
CrashLoopBackOff → Container exits with code 1 → kubelet restarts with backoff
Definition: The container starts, runs briefly, then exits with a non-zero code. This is a bug in your application code — unhandled exception, missing dependency, wrong command.
$ kubectl logs crash-pod --previous
Traceback (most recent call last):
  File "app.py", line 42: conn = psycopg2.connect(DB_URL)
psycopg2.OperationalError: could not connect to server
Key command: kubectl logs pod --previous shows logs from the last crashed container — this is where the error lives!
⑤ OOM Kill — Container exceeded memory limit
OOMKilled · exit 137 → Container used 256Mi but limit is 256Mi → Linux kernel kills it
Definition: The container's memory usage exceeds its resources.limits.memory. The Linux kernel's OOM killer force-terminates the process (SIGKILL, exit 137). Unlike CPU (which is throttled), memory overuse = immediate death.
$ kubectl describe pod oom | grep -A2 "Last State"
  Last State: Terminated
    Reason: OOMKilled
    Exit Code: 137
Fix: Increase memory limit, fix memory leak (check with kubectl top pod), use profiling tools
⑥ Probe Failure — App running but health check fails
Liveness fail → KILL + restart    Readiness fail → remove from traffic (no kill)
Definition: The kubelet's periodic health check gets a failure response. For liveness: the container is killed and restarted. For readiness: the Pod is removed from Service endpoints but NOT killed — giving it time to recover.
Warning Unhealthy kubelet Liveness probe failed: HTTP 503
Normal Killing kubelet Container web failed liveness probe, will be restarted
⑦ Dependency Failure — External service is down
Pod running fine → Database is DOWN → Readiness probe fails → Pod removed from traffic
Definition: Your app is running but can't reach a database, cache, or external API. The app process is alive (liveness passes) but can't serve requests (readiness fails). The correct response is to stop traffic, NOT restart.
⚠ CRITICAL: Never put dependency checks in liveness probes! If DB goes down and liveness checks DB → all Pods restart simultaneously → thundering herd → cascading total outage. Use readiness probes for dependency checks.

19 PDB — Node Drain Workflow

Definition: A PodDisruptionBudget limits how many Pods can be simultaneously unavailable during voluntary disruptions (node drain, cluster upgrade). It does NOT protect against involuntary failures (node crash).

① Before
② Drain starts
③ PDB check
④ Evict + reschedule
⑤ Continue drain
① Normal state — 3 replicas across 2 nodes
PDB: minAvailable: 2

node-a: Pod1 Pod2
node-b: Pod3
3 healthy replicas. PDB requires at least 2 to always be running. allowedDisruptions: 1 (only 1 can be down at a time).
② Admin starts draining node-a
kubectl drain node-a → API server begins evicting Pods from node-a
kubectl drain node-a --ignore-daemonsets — the drain controller asks the API server to evict Pod1 from node-a. Before allowing it, the API server checks the PDB.
③ API server checks PDB before each eviction
Evict Pod1? Running: 3, minAvailable: 2 → after eviction: 2 ≥ 2 → ALLOWED ✓

Evict Pod2? Running: 2, minAvailable: 2 → after eviction: 1 < 2 → BLOCKED ✗
The API server allows Pod1 eviction (leaves 2 running). But it blocks Pod2 eviction because that would drop below minAvailable: 2. The drain is paused until Pod1 is rescheduled and Running on another node.
④ Pod1 rescheduled on node-c — PDB satisfied again
node-a: Pod1 evicted Pod2 (still here)
node-b: Pod3
node-c: Pod1 rescheduled ✓
Pod1 is rescheduled to node-c and passes readiness probe. Running count is back to 3. The drain controller can now proceed to evict Pod2.
⑤ Pod2 evicted — drain complete
node-a: empty (drained) ✓
node-b: Pod3
node-c: Pod1 Pod2 rescheduled ✓
Pod2 is evicted and rescheduled. node-a is now empty and safe for maintenance. At no point did the running count drop below 2. Users experienced zero downtime.

Final SRE Wisdom

The goal isn't zero failures — it's fast, automated, observable recovery. Design Pods to crash safely (exit codes, graceful shutdown), detect failures quickly (probes, metrics), recover automatically (controllers, replicas), and provide full visibility (logs, traces, events).
