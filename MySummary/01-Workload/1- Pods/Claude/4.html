01 What is a Pod?

Definition: A Pod is the smallest deployable unit in Kubernetes. It's a logical host for one or more containers that share network, storage, and lifecycle. Every container in Kubernetes runs inside a Pod — even a single container is wrapped in a Pod.

Analogy

A Pod is a shared apartment. Containers are roommates — they share the same address (IP), living space (volumes), and lease (lifecycle). Kubernetes manages apartments, not individual people.

What Containers Share Inside a Pod
Shared ResourceDefinitionWhat This Means in Practice
Network NamespaceAll containers get the same IP address and port space via a shared Linux network namespaceContainer A on :8080 and Container B on :9090 are reachable via localhost. External traffic reaches them at the same Pod IP.
Storage VolumesVolumes declared in the Pod spec can be mounted by any container in the PodThe web container writes logs to /var/log/app.log; the sidecar reads the same file and ships it to Elasticsearch. Both mount the same emptyDir volume.
IPC NamespaceShared inter-process communication — System V IPC and POSIX message queuesLegacy apps that use shared memory for fast data exchange between processes can work across containers in the same Pod.
PID NamespaceWhen shareProcessNamespace: true, containers see each other's process treesA debug sidecar can run kill -USR1 <app-pid> to trigger a heap dump, or strace -p <pid> to trace the app.
UTS NamespaceSame hostname for all containers (= Pod name)hostname command returns the Pod name in every container.
LifecycleAll containers are co-scheduled on the same node and start/stop togetherIf the Pod is deleted, ALL containers receive SIGTERM. If the node fails, ALL containers fail. There is no way to move one container to another node.
SRE Principle — Cattle, Not Pets

Pods are disposable. They get new names and IPs when replaced. Never store important data inside a Pod without a PersistentVolume. Never depend on a specific Pod's IP. Design your application to survive any Pod being killed at any time. This is the foundation of reliable Kubernetes operations.

02 Pod Internal Architecture

Definition: When Kubernetes creates a Pod, it first creates a hidden pause container (also called the infrastructure container). This tiny container does nothing except hold the network namespace alive. When your app container crashes and restarts, the Pod's IP address is preserved because the pause container keeps running.

Pod Internal Architecture — The Pause Container

Why the Pause Container Matters

When your app container crashes (exit code 1, OOMKilled, etc.), the kubelet restarts it inside the same Pod. Because the pause container is still running, the Pod keeps its IP address. Without the pause container, every container restart would mean a new network namespace and a new IP — breaking all connections.

04 Init Containers — In Detail

Definition: Init containers are specialized containers that run before any app containers start. They execute one at a time in the order they're listed. Each must exit with code 0 before the next one begins. If any fails, the Pod keeps retrying that init container.

Init Container Execution Flow
Init:1/3 status. Kubelet retries Init 2 with exponential backoff. Init 3 and App containers never start. Pod is stuck until Init 2 succeeds or you fix the issue.

Full YAML Example

apiVersion: v1
kind: Pod
metadata:
  name: my-app
spec:
  initContainers:

  # Init 1: Wait until the database is reachable
  - name: wait-for-db
    image: busybox:1.36
    command:
    - 'sh'
    - '-c'
    - 'until nslookup postgres.default.svc.cluster.local; do echo "Waiting for DB..."; sleep 2; done'

  # Init 2: Run database migrations
  - name: run-migrations
    image: myapp/migrate:v3.2
    command: ["./migrate", "--source", "file:///migrations", "up"]
    env:
    - name: DATABASE_URL
      valueFrom:
        secretKeyRef:
          name: db-credentials
          key: url

  # Init 3: Download TLS certificates from Vault
  - name: download-certs
    image: vault:1.15
    command: ["vault", "read", "-field=certificate", "pki/issue/my-app"]
    volumeMounts:
    - name: certs
      mountPath: /certs

  containers:
  - name: web
    image: myapp/web:v2.1
    ports:
    - containerPort: 8080
    volumeMounts:
    - name: certs
      mountPath: /etc/tls
      readOnly: true

  volumes:
  - name: certs
    emptyDir: {}
$ kubectl get pod my-app -w NAME READY STATUS RESTARTS AGE my-app 0/1 Init:0/3 0 2s # Init 1 running my-app 0/1 Init:1/3 0 8s # Init 1 done, Init 2 running my-app 0/1 Init:2/3 0 14s # Init 2 done, Init 3 running my-app 0/1 PodInitializing 0 19s # All init done, app starting my-app 1/1 Running 0 21s # App container ready!

05 Sidecar Containers (Native, v1.29+)

Definition: A native sidecar is an init container with restartPolicy: Always. It starts during the init phase (guaranteed to start before app containers) and runs for the entire Pod lifetime (guaranteed to stop after app containers). This solves the old problem of sidecars defined as regular containers having unpredictable startup/shutdown ordering.

apiVersion: v1
kind: Pod
metadata:
  name: app-with-sidecar
spec:
  initContainers:
  # This is a SIDECAR — note restartPolicy: Always
  - name: log-shipper
    image: fluent/fluent-bit:2.1
    restartPolicy: Always       # ← This makes it a sidecar
    volumeMounts:
    - name: app-logs
      mountPath: /var/log/app
    resources:
      requests:
        cpu: "50m"
        memory: "64Mi"
      limits:
        memory: "128Mi"

  containers:
  - name: web
    image: myapp/web:v2.1
    ports:
    - containerPort: 8080
    volumeMounts:
    - name: app-logs
      mountPath: /var/log/app

  volumes:
  - name: app-logs
    emptyDir: {}

06 Ephemeral Containers

Definition: Temporary debug containers injected into a running Pod via kubectl debug. Not defined in the Pod spec. Share the Pod's namespaces so you can inspect files, network, and processes of the target container.

# Attach a debug shell to a running pod
kubectl debug -it my-app --image=busybox:1.36 --target=web

# Copy the pod and attach debug container with shared processes
kubectl debug my-app -it --image=nicolaka/netshoot --copy-to=debug-pod --share-processes
$ kubectl debug -it my-app --image=busybox --target=web Targeting container "web". If you don't see a command prompt, try pressing enter. / # wget -qO- localhost:8080/healthz {"status":"healthy","db":"connected","cache":"warm"} / # ls /proc/1/root/app/ main config.yaml templates/ / # cat /proc/1/root/app/config.yaml database_url: postgres://db:5432/myapp
SRE Principle — Debug Without Disrupting

Ephemeral containers let you troubleshoot production Pods without restarting them. This preserves the exact state causing the issue. Use minimal production images (distroless) for security, then inject full debug tools (netshoot, busybox) only when investigating.

08 Creating Pods — YAML (Declarative)

Definition: Declarative means you define the desired state in a YAML file, and Kubernetes figures out how to achieve it. This is the production-recommended approach because YAML files can be version-controlled in Git.

          name: app-config

    - name: DB_PASSWORD
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
    - name: LOG_LEVEL
      value: "info"
    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"
      limits:
        cpu: "500m"
        memory: "256Mi"

        path: /healthz

10 Creating Pods — Via Controllers (Production)

Definition: In production, you never create Pods directly. You create a controller (Deployment, StatefulSet, etc.) that creates and manages Pods for you. If a Pod dies, the controller recreates it. This is self-healing.

What Happens When a Node Crashes — Naked Pod vs Controller Pod
# Create a Deployment (most common)
kubectl create deployment my-app --image=myapp:v2.1 --replicas=3

# Generate Deployment YAML
kubectl create deployment my-app --image=myapp:v2.1 --replicas=3 --dry-run=client -o yaml > deploy.yaml
SRE Principle — Never Run Naked Pods

Every production Pod must be managed by a controller. Naked Pods are for testing only. The difference between a naked Pod and a controller-managed Pod is the difference between "service restored in seconds" and "pager goes off at 3 AM."

11 Updating Manual (Naked) Pods

Most Pod fields are immutable after creation. For naked Pods, updating means delete + recreate:

# Export → Edit → Delete → Recreate
kubectl get pod my-app -o yaml > pod.yaml
# Edit pod.yaml (change image, env, etc.)
kubectl delete pod my-app          # ⚠ DOWNTIME STARTS HERE
kubectl apply -f pod.yaml          # ⚠ DOWNTIME ENDS HERE
This Causes Downtime

Between delete and create, your service is completely unavailable. No traffic handling, no recovery. This is why naked Pods should never be used in production.

12 Updating Controller-Managed Pods

When Pods are managed by a Deployment, you update the Deployment and it performs a rolling update — zero downtime.

4 Ways to Update

# Method 1: Edit YAML file and apply
kubectl apply -f deployment.yaml

# Method 2: Change image directly
kubectl set image deployment/my-app web=myapp:v2.2

# Method 3: Edit live object in editor
kubectl edit deployment my-app

# Method 4: JSON patch
kubectl patch deployment my-app -p '{"spec":{"template":{"spec":{"containers":[{"name":"web","image":"myapp:v2.2"}]}}}}'
Rolling Update — What Happens Internally

    type: RollingUpdate

14 Graceful Shutdown — Complete Workflow

Definition: When a Pod is deleted, Kubernetes follows a precise 6-step shutdown sequence designed to give your application time to finish work, close connections, and clean up. Understanding each step prevents data loss and failed requests.

Graceful Shutdown — Full Architecture Diagram

Full YAML — Graceful Shutdown Configuration

spec:
  terminationGracePeriodSeconds: 60   # Total window: 60 seconds
  containers:
  - name: web
    image: myapp:v2.1
    lifecycle:
      preStop:
        exec:
          command:
          - "/bin/sh"
          - "-c"
          - "sleep 5 && kill -SIGTERM 1"
          # sleep 5: wait for endpoint removal to propagate
          # kill -SIGTERM 1: tell app to start shutting down
$ kubectl get pod my-app -w NAME READY STATUS RESTARTS AGE my-app 1/1 Running 0 4h12m my-app 1/1 Terminating 0 4h12m # SIGTERM sent my-app 0/1 Terminating 0 4h12m # Container exited # Pod removed

Scenario 1: App Handles SIGTERM Correctly ✓

SRE Principle — Test Graceful Shutdown Under Load

Run a load test, then kubectl delete pod during the test. Check for zero 5xx errors. If you see connection resets or 502s, add a preStop: sleep 5 hook and increase your terminationGracePeriodSeconds. This is the #1 cause of errors during deployments.

27 ⑦ Dependency Failures

Definition: Your app is running but can't reach a database, cache, or external API.

Detect: Readiness probe fails, app logs show connection errors.

Handle: Use readiness probes (not liveness!) so the Pod is removed from traffic but NOT restarted. Restarting won't fix a down database.

SRE Principle — Liveness ≠ Readiness

Liveness checks if the process is alive (never check external deps). Readiness checks if it can serve traffic (should check deps). If you put a DB check in liveness, and the DB goes down, ALL Pods restart → thundering herd → cascading failure → total outage.

28 Crash Loop Lifecycle

Backoff formula: min(10s × 2^(n-1), 300s) → 10s, 20s, 40s, 80s, 160s, 300s cap. Resets after 10 min of healthy running.

30 Probes Explained

Definition: A probe is a periodic diagnostic check run by the kubelet against a container. Four mechanisms: httpGet (HTTP 200-399), tcpSocket (connection opens), exec (exit code 0), grpc (SERVING).

Probe Timeline — How They Interact

32 Probe Configuration YAML

startupProbe:                       # Protect slow-starting apps
  httpGet:
    path: /healthz
    port: 8080
  failureThreshold: 30              # 30 × 10s = 300s = 5min max startup
  periodSeconds: 10

livenessProbe:                      # Detect deadlocks (NEVER check external deps!)
  httpGet:
    path: /healthz                 # Lightweight, internal-only endpoint
    port: 8080
  periodSeconds: 15
  timeoutSeconds: 3
  failureThreshold: 3

readinessProbe:                     # Control traffic (CAN check external deps)
  httpGet:
    path: /ready                  # Checks DB, cache, dependencies
    port: 8080
  periodSeconds: 5
  failureThreshold: 2
  successThreshold: 1

33 Probe Best Practices

Common Mistakes That Cause Outages

❌ DB check in liveness → DB down → all Pods restart → thundering herd → total outage

❌ Probe too aggressive (period:1, threshold:1) → brief CPU spike → Pod killed

❌ No startup probe → JVM takes 90s → liveness kills it at 30s → CrashLoop

❌ Probe does heavy computation → causes the overload it's trying to detect

34 Requests vs Limits

resources:
  requests:           # GUARANTEED minimum — scheduler uses this to place Pod
    cpu: "250m"      # 250 millicores = 0.25 CPU core
    memory: "128Mi"  # 128 Mebibytes
  limits:             # HARD CEILING — enforced by kernel
    cpu: "500m"      # Exceed → throttled (slowed, NOT killed)
    memory: "256Mi"  # Exceed → OOM KILLED (exit 137)
$ kubectl top pods NAME CPU(cores) MEMORY(bytes) web-abc 45m 98Mi # Healthy web-def 490m 241Mi # Near limits! web-ghi 500m 256Mi # At limit — CPU throttled, OOM risk

35 Resource Calculation for Multi-Container Pods

# Pod with: Init(500m, 512Mi), Init(200m, 256Mi), Sidecar(100m, 128Mi), App(300m, 256Mi)
#
# MAX(init containers)   = 500m CPU, 512Mi mem  (inits run one-at-a-time)

# Pod effective          = MAX(500m, 400m) = 500m CPU

SRE Principle — Four Golden Signals

Latency (p50/p95/p99) · Traffic (req/sec) · Errors (5xx rate) · Saturation (CPU/mem vs limits). Monitor these for every Pod, alert on deviations from baseline.

Final SRE Wisdom

The goal isn't zero failures — it's fast, automated, observable recovery. Design Pods to: crash safely (meaningful exit codes, graceful shutdown handling), detect failures quickly (probes, metrics, alerting), recover automatically (controllers, restart policies, replicas across zones), and provide full visibility (structured logs, distributed traces, Kubernetes events). A well-instrumented Pod that restarts cleanly in 5 seconds is worth infinitely more than a fragile Pod that silently corrupts data when it eventually fails.
