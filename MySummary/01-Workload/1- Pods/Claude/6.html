01 What is a Pod?

Definition — PodThe smallest deployable unit in Kubernetes. A logical host for one or more containers that share network (same IP address), storage (shared volumes), and lifecycle (co-scheduled on the same node, start and stop together). Every container in Kubernetes runs inside a Pod.
Definition — Pause ContainerA hidden infrastructure container automatically created for every Pod. Its only job is to hold the Linux network namespace alive. When your app container crashes and restarts, the Pod's IP address is preserved because the pause container keeps the namespace running.
Definition — Namespace (Linux)A Linux kernel feature that isolates system resources. Containers in the same Pod share network, IPC, and (optionally) PID namespaces, but have separate mount and user namespaces. This is how containers in a Pod share an IP but have isolated filesystems.
Shared ResourceDefinitionWhat It MeansExample
NetworkShared Linux network namespace → same IP + port spaceContainers talk via localhostApp on :8080, sidecar scrapes localhost:8080/metrics
StorageVolumes declared in Pod spec, mountable by any containerContainers read/write same filesApp writes /var/log/app.log, Fluent Bit reads it
IPCShared IPC namespace → System V IPC + POSIX message queuesShared memory between processesLegacy apps using shm for inter-process data exchange
PIDshareProcessNamespace: true → containers see each other's PIDsDebug container can signal appkill -USR1 <app-pid> to trigger heap dump
LifecycleAll containers co-scheduled on same nodePod deleted → all containers dieNode crash → entire Pod lost, controller recreates
SRE Principle — Cattle, Not Pets

Pods are disposable. New name, new IP on replacement. Never store data without PersistentVolumes. Never depend on a specific Pod IP. If a Pod is sick, replace it — don't repair it. This is the foundation of reliable Kubernetes operations.

Full Pod YAML — Every Important Field Annotated

apiVersion: v1                    # API version for Pod resources
kind: Pod                         # Resource type
metadata:
  name: my-app                    # Unique name within namespace
  namespace: production           # Logical grouping (default: "default")
  labels:                          # Key-value pairs for selection/grouping
    app: web                      # Used by Services to route traffic
    version: v2.1                # Used by Deployments for rollouts
    component: frontend
  annotations:                     # Non-identifying metadata
    prometheus.io/scrape: "true"  # Prometheus auto-discovery
    prometheus.io/port: "9090"
spec:
  terminationGracePeriodSeconds: 60 # Time for graceful shutdown (default 30)
  restartPolicy: Always           # Always | OnFailure | Never
  serviceAccountName: my-app-sa   # Identity for API access (RBAC)
  securityContext:                 # Pod-level security settings
    runAsNonRoot: true            # Prevent running as root
    runAsUser: 1000              # UID for all containers
    fsGroup: 1000                # GID for volume mounts

  initContainers:                  # Run BEFORE app containers, sequentially
  - name: wait-for-db
    image: busybox:1.36
    command: ['sh','-c','until nslookup postgres; do sleep 2; done']

  - name: log-shipper             # SIDECAR — note restartPolicy: Always
    image: fluent-bit:2.1
    restartPolicy: Always         # ← This makes it a native sidecar (v1.29+)
    volumeMounts:
    - name: logs
      mountPath: /var/log/app

  containers:                      # App containers — run in parallel after init
  - name: web
    image: myapp/web:v2.1
    ports:
    - containerPort: 8080
      name: http
    env:
    - name: DB_HOST               # From ConfigMap
      valueFrom:
        configMapKeyRef:
          name: app-config
          key: db-host
    - name: DB_PASSWORD           # From Secret (base64 encoded)
      valueFrom:
        secretKeyRef:
          name: db-secret
          key: password
    resources:                     # CPU and memory allocation
      requests:                    # Guaranteed minimum (scheduler uses this)
        cpu: "250m"              # 0.25 CPU cores
        memory: "128Mi"          # 128 Mebibytes
      limits:                      # Hard ceiling (kernel enforced)
        cpu: "500m"              # Exceed → throttled (NOT killed)
        memory: "256Mi"          # Exceed → OOM KILLED (exit 137)
    startupProbe:                  # Protects slow-starting apps
      httpGet:
        path: /healthz
        port: 8080
      failureThreshold: 30        # 30 × 10s = 5min startup window
      periodSeconds: 10
    livenessProbe:                 # Detects deadlocks/hangs
      httpGet:
        path: /healthz            # NEVER check external deps here!
        port: 8080
      periodSeconds: 15
      timeoutSeconds: 3
      failureThreshold: 3
    readinessProbe:                # Controls traffic routing
      httpGet:
        path: /ready              # CAN check DB, cache, dependencies
        port: 8080
      periodSeconds: 5
      failureThreshold: 2
    lifecycle:
      preStop:                      # Runs before SIGTERM
        exec:
          command: ["/bin/sh","-c","sleep 5"]  # Wait for endpoint removal
    volumeMounts:
    - name: logs
      mountPath: /var/log/app
    - name: data
      mountPath: /data
    securityContext:
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false

  volumes:
  - name: logs
    emptyDir: {}                   # Ephemeral — deleted when Pod dies
  - name: data
    persistentVolumeClaim:         # Persistent — survives Pod deletion
      claimName: app-data-pvc

02 Pod Creation Flow ▶

Definition — Pod LifecycleThe sequence of events from kubectl apply to the Pod serving traffic. Involves 5 Kubernetes components: API server, etcd, scheduler, kubelet, and container runtime.

① You submit the Pod YAML to the API Server
kubectl → API Server → validates → authenticates → admits
What happens: Your kubectl apply -f pod.yaml sends the Pod spec over HTTPS to the API server. The API server performs 3 checks: (1) Validation — is the YAML schema correct? (2) Authentication — who are you? (via kubeconfig certificate/token). (3) Authorization — are you allowed? (RBAC check). (4) Admission — mutating webhooks add defaults (e.g., service account), validating webhooks enforce policies (e.g., "no privileged containers").
Pod status: Pending with no node assigned. Condition: PodScheduled: False.
$ kubectl apply -f pod.yaml
pod/my-app created
② API Server persists Pod to etcd
API Server → etcd (distributed key-value store)
What happens: The API server writes the Pod object to etcd — the cluster's single source of truth. The Pod now exists durably in the system, but spec.nodeName is still empty — no node is assigned yet.
Definition — etcdA strongly consistent, distributed key-value store. It stores ALL Kubernetes state: every Pod, Service, Secret, ConfigMap, etc. If etcd loses data, the entire cluster state is lost. That's why etcd backup is critical for disaster recovery.
③ Scheduler picks the best node
kube-scheduler watches for unscheduled Pods → scores nodes → picks winner

node-01: 92% CPU ✗   node-02: 35% CPU ✓ SELECTED   node-03: tainted ✗
What happens: The kube-scheduler watches for Pods with empty spec.nodeName. It runs a 2-phase algorithm: (1) Filtering — eliminates nodes that can't run the Pod (insufficient resources, wrong taints, affinity mismatch). (2) Scoring — ranks remaining nodes by criteria like resource balance, topology spread, and anti-affinity. It writes spec.nodeName: node-02 back to the API server.
Definition — kube-schedulerA control plane component that watches for newly created Pods with no assigned node, and selects a node for them to run on. Factors include: resource requirements, hardware/software/policy constraints, affinity/anti-affinity, data locality, and workload spreading.
If no node fits: Pod stays in Pending with event: FailedScheduling: 0/3 nodes available.
④ Kubelet pulls the container image
kubelet (node-02) → containerd (CRI) → Registry → downloads layers
What happens: The kubelet on node-02 sees the new Pod assigned to it. It instructs the container runtime (containerd or CRI-O) to pull the image. The runtime downloads each image layer from the registry, unpacks them into a container filesystem, and reports ready. If the image is already cached locally, this is instant.
Definition — kubeletAn agent that runs on every node. It watches for Pods assigned to its node and ensures their containers are running and healthy. It talks to the container runtime via CRI (Container Runtime Interface), runs probes, reports status back to the API server, and manages pod lifecycle.
Definition — Container RuntimeThe software that actually runs containers. Kubernetes uses CRI (Container Runtime Interface) to communicate with it. Common runtimes: containerd (default), CRI-O. Docker was removed as a direct runtime in v1.24, but Docker-built images still work.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 ContainerCreating 3s
⑤ Init containers run sequentially
Init 1: wait-for-db ⏳ → then → Init 2: migrate → then → Init 3: download-certs

Each must exit 0 before next starts. Sidecars (restartPolicy: Always) start and keep running.
What happens: Init containers execute one at a time, in order. Init 1 runs; when it exits 0, Init 2 starts. If any init fails, kubelet retries it with exponential backoff. App containers cannot start until ALL init containers succeed. Native sidecars (init containers with restartPolicy: Always) start during this phase but continue running.
Definition — Init ContainerA specialized container that runs BEFORE app containers. Used for setup tasks: waiting for dependencies, running database migrations, downloading config files. They run sequentially and must complete successfully. They do NOT support probes.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 Init:1/3 8s # Init 1 done, Init 2 running
⑥ App containers start in parallel
pause container (holds network)
web (PID 1: app server)   metrics (PID 1: exporter)
All start simultaneously. postStart hooks run if defined.
What happens: Kubelet creates the pause container first (holds network namespace, gets the Pod IP), then starts all app containers in parallel. Each gets its own PID namespace but shares the Pod's network. If a postStart lifecycle hook is defined, it runs immediately (parallel with the container's entrypoint — not guaranteed to run before it).
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 PodInitializing 15s
⑦ Probes begin — startup → liveness → readiness
Startup probe: /healthz ⏳ → passes ✓ → Liveness + Readiness activate
What happens: If a startup probe is configured, it runs first. During this time, liveness and readiness probes are completely disabled. Once startup passes, both activate. The readiness probe determines when the Pod is added to Service endpoints. Until readiness passes, the Pod gets zero traffic.
Definition — ProbeA periodic diagnostic check performed by the kubelet against a container. Uses one of 4 mechanisms: httpGet (HTTP 200-399), tcpSocket (connection opens), exec (exit code 0), or gRPC (SERVING status). Each probe has configurable period, timeout, and failure thresholds.
⑧ Pod is Ready — added to Service endpoints — receives traffic! ✓
Users → Service (LB) → Pod: my-app READY 1/1 ✓ ⟷ Database
What happens: Once readiness passes, the Endpoints controller adds this Pod's IP to the Service's endpoint list. kube-proxy on every node updates iptables/IPVS rules. Traffic begins flowing. The Pod is fully operational.
Definition — EndpointsA Kubernetes object that lists all Pod IPs that belong to a Service. When a Pod passes its readiness probe, its IP is added. When it fails or is deleted, it's removed. kube-proxy watches Endpoints to know where to route traffic.
$ kubectl get pod my-app
NAME READY STATUS RESTARTS AGE
my-app 1/1 Running 0 22s

Init Container
DefinitionA container that runs BEFORE app containers start, executing setup tasks. Init containers run one at a time in order. Each must exit successfully (code 0) before the next begins. If one fails, the Pod stays stuck until it succeeds.
Init 1: wait-for-db ✓ → then → Init 2: migrate ✓ → then → App starts
Runs when: Before any app container, sequentially. Restarts: On failure (blocks entire Pod). Probes: Not supported. Use cases: Wait for DB to be ready, run migrations, download config/certs, fix volume permissions.
initContainers:
- name: wait-for-db
  image: busybox:1.36
  command: ['sh','-c','until nslookup postgres; do echo waiting; sleep 2; done']
- name: run-migrations
  image: myapp/migrate:v3
  command: ["./migrate", "up"]
  env:
  - name: DATABASE_URL
    valueFrom:
      secretKeyRef: { name: db-creds, key: url }
Sidecar Container (Native, v1.29+)
DefinitionAn init container with restartPolicy: Always. It starts during the init phase (guaranteed before app containers) and runs for the entire Pod lifetime (guaranteed to stop AFTER app containers). Solves the old problem of sidecars having unpredictable startup/shutdown ordering.
Sidecar starts FIRST → App starts SECOND → ... → App stops FIRST → Sidecar stops LAST
Runs when: Starts in init phase, runs forever. Restarts: Always (independent of Pod restartPolicy). Probes: All 3 supported. Use cases: Log shipping (Fluent Bit), service mesh proxy (Envoy/Istio), monitoring agent, secret injection (Vault Agent).
initContainers:
- name: log-shipper
  image: fluent-bit:2.1
  restartPolicy: Always     # ← Makes it a sidecar
  resources:
    requests: { cpu: "50m", memory: "64Mi" }
  volumeMounts:
  - { name: logs, mountPath: /var/log/app }
App Container
DefinitionThe main container(s) defined in spec.containers[]. This is where your application code runs. All app containers start simultaneously (in parallel) after all init containers complete.
Runs when: After all init done, in parallel with other app containers. Restarts: Per Pod restartPolicy (Always/OnFailure/Never). Probes: All 3 supported and strongly recommended. This is the core of your Pod — web servers, APIs, workers, batch processors.
Ephemeral Container
DefinitionA temporary debug container injected into a running Pod via kubectl debug. NOT defined in the Pod spec — added on-the-fly for troubleshooting. Shares the Pod's namespaces so you can inspect files, network, and processes of the target container without restarting the Pod.
Runs when: On-demand, for debugging only. Restarts: Never. Probes: None. Key benefit: Debug production Pods without disrupting them — preserves the exact state causing the issue.
# Attach debug shell to running pod
kubectl debug -it my-app --image=busybox --target=web

# Copy pod with shared processes for deep debugging
kubectl debug my-app -it --image=nicolaka/netshoot --copy-to=dbg --share-processes

① Pod scheduled — kubelet begins init phase
kubelet sees Pod assigned to this node → creates pause container → begins init containers in order
The kubelet creates the pause container first (establishes network namespace + IP), then starts the first init container. No app containers run yet. Pod status: Init:0/3.
② Init 1: wait-for-db — polls until database is reachable
wait-for-db: nslookup postgres... waiting... waiting... → DNS resolves! exit 0 ✓
The first init container runs a loop: until nslookup postgres; do sleep 2; done. It keeps polling DNS until the postgres Service is discoverable. When it succeeds, it exits with code 0. Kubelet moves to Init 2. Status: Init:1/3.
$ kubectl logs my-app -c wait-for-db
waiting for postgres...
waiting for postgres...
postgres.default.svc.cluster.local resolved! Done.
③ Init 2: migrate — applies database schema changes
migrate: applying migration 001_create_users... 002_add_email... done! → exit 0 ✓
The migration tool connects to the database (now available thanks to Init 1) and applies schema changes. When complete, exits 0. Status: Init:2/3.
④ Sidecar: log-shipper — starts and keeps running
log-shipper (restartPolicy: Always) — starts and runs continuously alongside app
Because this init container has restartPolicy: Always, it's a native sidecar. It starts during init phase but does NOT block the next container — it runs in the background for the entire Pod lifetime. It's guaranteed to be running before app containers start.
⑤ All init done — app containers start!
web (app) log-shipper (sidecar, already running) — serving traffic after readiness passes
All init containers complete. App containers start in parallel. The sidecar is already running. Status changes: PodInitializing → Running. Once readiness probes pass, the Pod receives traffic.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 1/1 Running 22s
⑥ What if an init container FAILS?
Init 2: migrate — exit 1 ✗ (DB connection refused)

kubelet retries Init 2 with exponential backoff: 10s → 20s → 40s → ...
The entire Pod is stuck. Init 3 never runs. App containers never start. Pod stays in Init:1/3 indefinitely. Kubelet retries the failed init container. To debug: kubectl logs my-app -c run-migrations. Common causes: DB not ready, wrong credentials, network issue.
$ kubectl get pod my-app
NAME READY STATUS AGE
my-app 0/1 Init:CrashLoopBackOff 5m

06 Rolling Update ▶

Definition — Rolling UpdateA deployment strategy that gradually replaces old Pods with new ones, ensuring zero downtime. The Deployment creates a new ReplicaSet, scales it up while scaling the old one down. Each new Pod must pass its readiness probe before an old Pod is terminated.
① All v1
② New RS
③ Scale up
④ Replace
⑤ Complete
① All 3 Pods on v1
RS-v1 (3): Pod1 v1 Pod2 v1 Pod3 v1
Stable state. All traffic balanced across 3 v1 Pods via Service.
② You update — new ReplicaSet created
RS-v1 (3): Pod1 v1 Pod2 v1 Pod3 v1
RS-v2 (0): empty — just created
kubectl set image deploy/my-app web=myapp:v2 → Deployment creates RS-v2 with 0 replicas.
③ RS-v2 scales to 1 — new Pod must pass readiness
RS-v1 (3): v1 v1 v1
RS-v2 (1): Pod4 v2 ⏳ starting
RS-v2 creates Pod4 (v2). It goes through: image pull → init → startup probe. It must pass readiness before any v1 Pod can be killed. maxSurge: 1 allows 4 total Pods temporarily.
④ Pod4 ready → Pod1 terminated → process repeats
RS-v1 (2): Pod1 terminating v1 v1
RS-v2 (1): Pod4 v2 ✓ READY
Pod4 passes readiness → RS-v1 scales 3→2 → Pod1 receives SIGTERM. Traffic now goes to Pod2, Pod3, Pod4. Zero Pods down at any time.
⑤ All Pods now v2 — rollout complete
RS-v1 (0): kept for rollback
RS-v2 (3): v2 ✓ v2 ✓ v2 ✓
All 3 Pods on v2. RS-v1 is kept at 0 replicas (not deleted) — running kubectl rollout undo scales RS-v1 back up.
$ kubectl rollout status deploy/my-app
deployment "my-app" successfully rolled out

07 Graceful Shutdown ▶

Definition — Graceful ShutdownThe orderly 6-step sequence Kubernetes follows when deleting a Pod. Designed to give your application time to finish in-flight requests, close database connections, flush buffers, and clean up — preventing data loss and failed requests.
① Delete
② Endpoints
③ preStop
④ SIGTERM
⑤ Grace
⑥ SIGKILL
① kubectl delete pod my-app
Users → Service → Pod (serving) ⟷ DB
API server marks Pod as Terminating. Grace period countdown starts (default 30s). Pod still exists and may still receive traffic briefly.
② Pod removed from Service endpoints (PARALLEL with ③)
Users → Service ✗ Pod (Terminating)
Endpoints controller removes Pod IP from Service. But propagation to all kube-proxies on all nodes takes 1-5 seconds. During this window, some nodes may still route traffic here. This is why preStop: sleep 5 exists — it delays SIGTERM until endpoints fully propagate.
Definition — EndpointsA K8s object listing Pod IPs for a Service. Updated by the Endpoints controller. kube-proxy watches changes and updates iptables/IPVS on each node. Propagation is NOT instant — takes 1-5s across large clusters.
③ preStop hook executes
preStop: sleep 5 → waits for endpoints to propagate → safe to shut down
Kubelet runs the preStop handler synchronously. SIGTERM is NOT sent until preStop finishes. Time counts toward grace period. Common pattern: sleep 5 to let endpoints propagate, then trigger app drain.
④ SIGTERM sent to PID 1 in each container
SIGTERM → PID 1 → App catches signal → finish requests → close DB → flush buffers → exit 0
Your app must handle SIGTERM: stop accepting new work, finish in-flight requests, close DB connections (commit pending transactions), flush metric buffers, exit cleanly.
⚠ PID 1 TrapIf your Dockerfile uses CMD app (shell form), PID 1 is bash — which does NOT forward SIGTERM to your app! Use CMD ["app"] (exec form) so your app IS PID 1 and receives SIGTERM directly. Or use tini as an init process.
⑤ Grace period countdown
preStop time + SIGTERM shutdown time must fit inside terminationGracePeriodSeconds: 60
Kubernetes waits up to terminationGracePeriodSeconds for the container to exit. If your app drains in 10s and preStop takes 5s, that's 15s — well within 60s. If the container exits before the deadline, Kubernetes proceeds immediately.
⑥ SIGKILL — if container still alive (last resort)
SIGKILL ☠ → Force-killed by Linux kernel → Cannot be caught
SIGKILL cannot be caught, blocked, or handled. The kernel force-terminates the process. Consequences: in-flight requests get "connection reset", DB transactions rolled back, buffered data lost, metrics gap. If this happens regularly, increase grace period or fix shutdown logic.

08 Shutdown Scenarios ▶

✓ Clean
✗ Ignored
⚠ No preStop
Scenario A — App handles SIGTERM correctly ✓
SIGTERM → Finish requests (3s) → Close DB conn (1s) → Flush metrics → exit 0 ✓
Result: Zero data loss. Zero failed requests. Clean exit. Total time: ~5s (well within 60s grace). This is the gold standard. Every production app should behave this way.
Scenario B — App ignores SIGTERM → SIGKILL ✗
SIGTERM → App ignores it... 60s pass... → SIGKILL ☠
Result: In-flight HTTP requests get "connection reset". DB transactions rolled back — partial writes lost. Buffered metrics never flushed — monitoring gap. File handles not closed — possible corruption. Fix: Handle SIGTERM in your app. Use exec form in Dockerfile (CMD ["app"]).
Scenario C — No preStop hook → endpoint race condition ⚠
SIGTERM sent immediately → but endpoints take 1-5s to propagate → some traffic still arrives!
Result: During the 1-5s propagation window, kube-proxy on some nodes still routes traffic to this Pod — but the app is shutting down → users get 502/connection reset errors. Fix: Add preStop: sleep 5 to delay shutdown until endpoints fully propagate. This is the #1 cause of errors during deployments.

Pending
DefinitionPod accepted by the API server but containers are not yet running. The Pod is waiting for scheduling, image pulling, volume attachment, or init containers to complete.
Common causes: Insufficient CPU/memory on nodes, taint not tolerated, image pulling (large image), PVC not bound, init container still running.
NAME READY STATUS AGE
my-app 0/1 Pending 5m
Debug: kubectl describe pod my-app → scroll to Events section → look for FailedScheduling.
Running
DefinitionPod bound to a node. At least one container is running, or is in the process of starting or restarting. Note: Running does NOT mean healthy — the container could be in CrashLoopBackOff (repeatedly crashing and restarting).
Important: A Pod with Running status and READY 0/1 means the container is running but failing readiness probes — it's NOT receiving Service traffic.
Succeeded
DefinitionAll containers in the Pod have exited with code 0 (success) and will not be restarted. This is a terminal state. Common for Jobs and batch workloads.
Failed
DefinitionAll containers have terminated and at least one exited with a non-zero code or was killed by the system. This is a terminal state for Pods with restartPolicy: Never.
Debug: kubectl logs pod --previous to see last crash logs. Check kubectl get pod -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'.
Unknown
DefinitionThe Pod status cannot be determined. Usually means the kubelet on the Pod's node has stopped reporting to the API server — caused by node crash, network partition, or kubelet failure.
Debug: kubectl get nodes → check if the node is NotReady. Check kubelet logs on the node.

11 Lifecycle Hooks

Definition — postStartA hook that runs AFTER a container is created, in parallel with the entrypoint. NOT guaranteed to run before the entrypoint. If it fails, the container is killed.

① Scheduling Failure
DefinitionThe kube-scheduler cannot find any node that satisfies the Pod's resource requests, affinity rules, or toleration requirements. Pod stays in Pending indefinitely.
Warning FailedScheduling 0/3 nodes available: 1 Insufficient cpu, 2 had taint {gpu: true}
Detect: kubectl describe pod → Events → FailedScheduling
Fix: Add nodes, reduce requests, fix affinity, add tolerations, clean up unused Pods
② Image Pull Failure
DefinitionThe container runtime cannot download the specified image from the registry. Causes: wrong image name/tag, registry authentication required, network issues, Docker Hub rate limiting.
Failed to pull image "myapp:v99": manifest unknown
Error: ImagePullBackOff
Fix: Verify image exists (docker pull myapp:v99), create imagePullSecrets, check DNS/network
③ Configuration Failure
DefinitionThe container references a ConfigMap, Secret, or PVC that doesn't exist in the namespace. The container can't be created because its environment or volume configuration is incomplete.
Error: configmap "app-config" not found
Fix: Create the missing resource or mark it optional: true
④ Application Crash
DefinitionThe container starts, runs briefly, then exits with a non-zero code. The application itself has a bug — unhandled exception, missing dependency, wrong startup command.
$ kubectl logs crash-pod --previous
Traceback: File "app.py", line 42
psycopg2.OperationalError: could not connect to server
Key command: kubectl logs pod --previous — shows logs from the LAST crashed container.
⑤ OOM Kill
DefinitionOut Of Memory Kill. The container's memory usage exceeds its resources.limits.memory. The Linux kernel's OOM killer force-terminates the process with SIGKILL (exit 137). Unlike CPU (throttled), memory overuse = immediate death.
$ kubectl describe pod oom | grep Reason
  Reason: OOMKilled
  Exit Code: 137
Fix: Increase memory limit, fix memory leak, profile with kubectl top pod
⑥ Probe Failure
DefinitionThe kubelet's periodic health check receives a failure response. Liveness failure → container killed and restarted. Readiness failure → Pod removed from Service endpoints (no traffic) but NOT killed.
Warning Unhealthy kubelet Liveness probe failed: HTTP 503
Normal Killing kubelet Container failed liveness probe, will be restarted
⑦ Dependency Failure
DefinitionYour app is running but an external service it depends on (database, cache, API) is unavailable. The app process is alive (liveness passes) but cannot serve requests properly (readiness should fail).
CRITICAL RULE: NEVER put dependency checks in liveness probes! If DB goes down → liveness fails → ALL Pods restart → thundering herd → cascading total outage. Use readiness probes for dependency checks — they remove traffic without killing the Pod.

DefinitionRuns for the entire lifetime of the container (after startup passes). Answers: "Is this process still alive and functioning?" On failure: container is KILLED and RESTARTED. CRITICAL: NEVER check external dependencies in liveness — if DB is down, restarting your app won't fix it and will cause a thundering herd.

17 Resource Scheduling ▶

Definition — RequestsThe guaranteed minimum resources for a container. The scheduler uses requests to decide node placement. The container is guaranteed to get at least this much CPU/memory.
Definition — LimitsThe hard ceiling enforced by Linux cgroups. CPU over limit → throttled (slowed). Memory over limit → OOM killed (exit 137).
① Request
② Filter
③ Score
④ Place
⑤ Enforce
① Pod requests CPU: 250m, memory: 128Mi
Pod: web (requests: cpu 250m, mem 128Mi)
Your Pod spec says it needs at least 250 millicores of CPU and 128 MiB of memory. The scheduler must find a node with this much allocatable capacity remaining.
② Scheduler filters out unfit nodes
node-01: 50m CPU free ✗ (not enough)
node-02: 2000m free ✓
node-03: tainted {gpu} ✗ (no toleration)
Filtering phase: Scheduler eliminates nodes that can't run this Pod. Checks: sufficient resources, matching taints/tolerations, node affinity, PVC availability.
③ Scheduler scores remaining nodes
node-02: score 85 ✓ (balanced resources)
node-04: score 72 (slightly more loaded)
Scoring phase: Ranks surviving nodes by: resource balance (LeastRequestedPriority), pod spreading (topology), inter-pod affinity, and custom priorities. Highest score wins.
④ Pod placed on winning node
node-02 selected → Pod: web scheduled here
Scheduler writes spec.nodeName: node-02 to the API server. The kubelet on node-02 picks it up and starts creating containers. The requested resources are now "reserved" on node-02 — they won't be double-booked by another Pod.
⑤ Limits enforced at runtime by Linux kernel
CPU: using 480m of 500m limit → near throttle
Memory: using 260Mi of 256Mi limit → OOM KILLED!
CPU over limit → throttled: The kernel slows the process via CPU bandwidth limiting (CFS). Your app gets slower but keeps running.
Memory over limit → OOM killed: The kernel's OOM killer immediately terminates the process (SIGKILL, exit 137). No grace period.

19 QoS & Eviction ▶

Guaranteed
Burstable
BestEffort
Eviction Order
Guaranteed — Highest Priority
DefinitionEvery container in the Pod has equal requests and limits for both CPU and memory (requests == limits). These Pods are the LAST to be evicted when nodes run out of resources. Use for mission-critical workloads.
resources:
  requests: { cpu: "500m", memory: "256Mi" }
  limits:   { cpu: "500m", memory: "256Mi" }  # requests == limits
Burstable — Middle Priority
DefinitionAt least one container has resource requests or limits, but they are NOT equal. The Pod can "burst" above its requests (up to limits) when extra capacity is available. Most production workloads use this class.
resources:
  requests: { cpu: "250m", memory: "128Mi" }
  limits:   { cpu: "1", memory: "512Mi" }     # limits > requests
BestEffort — Lowest Priority (DANGER)
DefinitionNo requests or limits set on any container. Gets whatever resources are leftover. FIRST to be evicted under memory pressure. Never use in production.
containers:
- name: app
  image: myapp:v1
  # No resources defined → BestEffort
Eviction Order Under Memory Pressure
Node memory pressure → kubelet starts evicting:

① BestEffort Pods — killed FIRST (no guarantees)
② Burstable Pods using > requests — killed next (exceeding their promise)
③ Guaranteed Pods — killed LAST (only if absolutely necessary)
The kubelet monitors node memory. When it drops below threshold, it evicts Pods in QoS order: BestEffort first, then Burstable (sorted by usage vs requests), then Guaranteed last. Within each class, the Pod using the most memory relative to its request is evicted first.

20 PDB Node Drain ▶

Definition — PodDisruptionBudget (PDB)A Kubernetes API object that limits how many Pods of a workload can be simultaneously unavailable during voluntary disruptions (node drain, cluster upgrade). It ensures high availability by enforcing a minAvailable or maxUnavailable threshold. PDBs do NOT protect against involuntary disruptions (hardware crash).
① Before
② Drain
③ PDB Check
④ Reschedule
⑤ Complete
① 3 replicas across 2 nodes. PDB: minAvailable: 2
node-a: Pod1 Pod2    node-b: Pod3

PDB allows at most 1 disruption (3 - 2 = 1).
② Admin drains node-a for maintenance
kubectl drain node-a --ignore-daemonsets
API server begins processing eviction requests for Pods on node-a.
③ API checks PDB before each eviction
Evict Pod1? Running=3, min=2, after=2 ≥ 2 → ALLOWED ✓
Evict Pod2? Running=2, min=2, after=1 < 2 → BLOCKED ✗

Drain pauses. Waiting for Pod1 to be rescheduled and READY elsewhere.
The eviction API checks the PDB before each eviction. It allows Pod1 (leaves 2 running). But blocks Pod2 because that would drop below minAvailable: 2. The drain is paused until Pod1 is Running + Ready on another node.
④ Pod1 rescheduled on node-c — PDB satisfied
node-a: Pod1 gone Pod2    node-b: Pod3    node-c: Pod1 ✓ Ready

Running count: 3 again. Drain can now evict Pod2.
⑤ Drain complete — node-a is empty
node-a: empty ✓ (safe for maintenance)
node-b: Pod3    node-c: Pod1 Pod2 ✓

At no point did running count drop below 2. Zero downtime.

Final SRE Wisdom

The goal isn't zero failures — it's fast, automated, observable recovery. Design Pods to crash safely, detect failures quickly, recover automatically, and provide full visibility. A well-instrumented Pod that restarts cleanly in 5 seconds is worth infinitely more than a fragile Pod that silently corrupts data when it finally fails.
