Fundamentals

Q1 What is a Pod and why is it the smallest deployable unit?
Easy▼
AnswerA Pod is a group of one or more containers that share network (same IP), storage (shared volumes), and lifecycle (co-scheduled, start/stop together). It's the smallest unit because Kubernetes never schedules a bare container — every container must run inside a Pod. Even a single-container app is wrapped in a Pod.
Pod: my-app (IP: 10.244.1.5)
├── Container A: nginx (port 80) ← shares IP with B
├── Container B: log-agent (port 9090) ← talks to A via localhost:80
└── Volume: /var/log (shared emptyDir)
Why It Matters for CKADYou must understand that containers in a Pod communicate via localhost, not Service DNS. They share the same port space — two containers can't both use port 80.
Q2 What is the pause container and why does it exist?
Medium▼
AnswerThe pause container is a hidden infrastructure container created automatically for every Pod. It holds the Linux network namespace alive. When your app container crashes and kubelet restarts it, the Pod's IP address is preserved because the pause container keeps the namespace running. Without it, every container restart would mean a new IP — breaking all connections.
pause (holds network: eth0 → 10.244.1.5)
├── web container ← uses pause's network
└── web crashes → restarts ← IP stays same because pause is alive
Q3 What resources do containers share inside a Pod?
Easy▼
AnswerShared: Network namespace (same IP + ports + localhost), Storage volumes (any volume mountable by all containers), IPC namespace (shared memory), UTS namespace (same hostname), Lifecycle (co-scheduled, co-terminated).

NOT shared: Filesystem (each container has its own unless they mount the same volume), PID namespace (separate by default — opt-in via shareProcessNamespace: true), CPU/memory (each container has its own cgroup limits).
Q4 What is the difference between a Pod and a Deployment?
Easy▼
AnswerA Pod is a single instance of your application. A Deployment is a controller that manages multiple Pod replicas, provides rolling updates, rollback capability, and auto-healing. If a Pod dies, nobody recreates it. If a Deployment's Pod dies, the Deployment creates a new one automatically.
Pod (naked)Deployment
Self-healingNo — dies foreverYes — auto-recreates
Rolling updateNoYes — zero downtime
RollbackNoYes — kubectl rollout undo
ScalingNoYes — kubectl scale
Production useNeverAlways
Exam TrapCKAD may ask you to create a "naked Pod" — that's fine for the exam. But real-world questions may test whether you know to use Deployments in production.

Q8 What is the difference between containerPort and exposing a port?
Medium▼
AnswercontainerPort is purely informational — it tells humans and tools which port the container listens on. It does NOT actually open or restrict any port. A container can listen on any port regardless of what containerPort says. To make a Pod accessible from outside the cluster, you need a Service (ClusterIP, NodePort, or LoadBalancer).

Q13 Delete a Pod with a 60-second grace period. Then force-delete one instantly.
Easy▼

Q16 Create a Pod with a volume that two containers share
Medium▼
apiVersion: v1
kind: Pod
metadata:
  name: shared-vol
spec:
  containers:
  - name: writer
    image: busybox
    command: ["sh","-c","while true; do date >> /data/log.txt; sleep 5; done"]
    volumeMounts:
    - name: shared
      mountPath: /data
  - name: reader
    image: busybox

Q18 How do you check the logs of a container that already crashed?
Easy▼
kubectl logs my-app --previous
Answer--previous (or -p) shows logs from the last terminated container instance. This is critical for debugging CrashLoopBackOff — the current container may have no logs yet because it just started. The crash evidence is in the previous container's logs.

Q21 What happens if an init container fails?
Medium▼
AnswerThe Pod stays stuck. The failed init container is retried with exponential backoff (10s → 300s cap) forever — ignoring the Pod's restartPolicy. All subsequent init containers and app containers never start. Pod status shows Init:CrashLoopBackOff.
Q22 What is a native sidecar container? How is it different from a regular init container?
Hard▼
AnswerA native sidecar (v1.29+) is an init container with restartPolicy: Always. It starts during the init phase but runs for the entire Pod lifetime. Unlike regular init containers (which run and exit), sidecars keep running alongside app containers. They're guaranteed to start BEFORE and stop AFTER app containers.
initContainers:
- name: log-shipper
  image: fluent-bit:2.1
  restartPolicy: Always   # ← THIS makes it a sidecar

Q24 How do you add an ephemeral debug container to a running Pod?
Medium▼

Q38 When do liveness and readiness probes start if a startup probe is configured?
Hard▼
AnswerWhile the startup probe is running, liveness and readiness are completely disabled. They don't start until the startup probe passes for the first time. After that, startup probe stops, and liveness + readiness begin their normal cycles.
Startup probe running (liveness + readiness DISABLED)
→ passes ✓ →
Liveness active (every 15s) + Readiness active (every 5s)

Resources & QoS

Q43 What is the difference between requests and limits?
Medium▼
RequestsLimits
DefinitionGuaranteed minimum — scheduler uses for placementHard ceiling — enforced by kernel cgroups
CPU overCan burst above requestsThrottled (slowed, NOT killed)
Memory overCan burst above requestsOOM Killed (exit 137)
resources:
  requests:
    cpu: "250m"       # 0.25 CPU cores
    memory: "128Mi"   # 128 Mebibytes
  limits:
    cpu: "500m"       # Exceed → throttled
    memory: "256Mi"   # Exceed → OOM KILLED

Q52 Pod shows ImagePullBackOff. What's happening and does it retry?
Medium▼
AnswerThe kubelet can't download the container image. It retries with exponential backoff: 10s → 20s → 40s → 80s → 160s → 300s cap. After reaching 300s, it retries every 5 minutes forever. It never stops. restartPolicy has no effect on image pulls.
# Check the exact error
kubectl describe pod X | grep -A5 "Events"

# Common fixes
# Wrong tag: kubectl set image pod/X web=nginx:correct-tag
# Auth needed: kubectl create secret docker-registry ...
Q53 Pod shows CrashLoopBackOff. What is the backoff sequence?
Hard▼
AnswerThe container keeps crashing. Kubelet retries with exponential backoff:
10s → 20s → 40s → 80s → 160s → 300s (cap)
After 300s cap, retries every 5 minutes forever. No max retry count. Backoff resets to 10s after 10 minutes of successful running.
# Debug steps
kubectl logs crash-pod --previous   # Logs from LAST crash
kubectl describe pod crash-pod      # Exit code + reason
Q54 Pod shows OOMKilled with exit code 137. What happened?
Medium▼
AnswerThe container exceeded its memory limits. The Linux kernel's OOM killer sent SIGKILL (signal 9). Exit code = 128 + 9 = 137. Unlike CPU (throttled), memory overuse = immediate death. No graceful shutdown.
kubectl describe pod X | grep -i "oom\|reason\|exit"
kubectl top pod X   # Check current usage vs limit
Q55 What do these exit codes mean: 0, 1, 126, 127, 137, 139, 143?
Hard▼

Q56 Pod shows CreateContainerConfigError. Does it retry?
Medium▼
AnswerYes, retries forever. The kubelet checks every ~60 seconds (sync frequency). The moment you create the missing ConfigMap/Secret, the container starts automatically on the next sync. restartPolicy has no effect — the container never started.

Security Context

Q61 Write a Pod that runs as non-root user with read-only filesystem
Medium▼
apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:           # Pod-level (applies to all containers)
    runAsNonRoot: true
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
  - name: app
    image: nginx
    securityContext:         # Container-level (overrides Pod-level)
      readOnlyRootFilesystem: true
      allowPrivilegeEscalation: false
      capabilities:
        drop: ["ALL"]
Q62 What is the difference between Pod-level and container-level securityContext?
Medium▼
AnswerPod-level (spec.securityContext): applies to ALL containers + volumes. Fields: runAsUser, runAsGroup, fsGroup, runAsNonRoot.

Container-level (spec.containers[].securityContext): overrides Pod-level for that specific container. Additional fields: readOnlyRootFilesystem, allowPrivilegeEscalation, capabilities, privileged.

Q68 Schedule a Pod on a specific node using nodeName (direct assignment)
Easy▼
spec:
  nodeName: worker-01   # Bypasses scheduler entirely
Exam TrapnodeName bypasses the scheduler. If the node doesn't exist or has no capacity, the Pod stays Pending. Prefer nodeSelector or nodeAffinity for production.
Q69 Write a Pod that tolerates a taint
Medium▼
# Node has taint: kubectl taint nodes node1 dedicated=gpu:NoSchedule

spec:
  tolerations:
  - key: "dedicated"
    operator: "Equal"
    value: "gpu"
    effect: "NoSchedule"
Key ConceptTaints on nodes repel Pods. Tolerations on Pods allow them to be scheduled on tainted nodes. A toleration doesn't guarantee scheduling on that node — it just removes the restriction.

Q71 Write a Pod with node affinity — prefer SSD but don't require it
Hard▼
spec:
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
      - weight: 80
        preference:
          matchExpressions:
          - key: disktype
            operator: In
            values: ["ssd"]
Key Conceptpreferred = soft rule (scheduler tries but doesn't fail if no match). required = hard rule (Pod stays Pending if no match). Weight (1-100) lets you prioritize multiple preferences.

Q76 A Pod keeps restarting. Walk through the complete debugging process.
Hard▼
# Step 1: Check the status and restart count
kubectl get pod X

# Step 2: Check events for WHY
kubectl describe pod X | tail -20

# Step 3: Check PREVIOUS container's logs (the crash evidence)
kubectl logs X --previous

# Step 4: Check exit code and reason
kubectl get pod X -o jsonpath='{.status.containerStatuses[0].lastState.terminated}'

# Step 5: Based on exit code:
#   137 → OOMKilled → increase memory limits
#   1   → App error → fix code (check --previous logs)
#   127 → CMD not found → fix Dockerfile/command
#   143 → SIGTERM → Pod was deleted (normal)

# Step 6: Check resource usage
kubectl top pod X

# Step 7: Live debug if needed
kubectl debug -it X --image=busybox --target=web
Q77 What happens during graceful shutdown? Explain each step.
Hard▼
kubectl delete pod X
→ ① Pod marked Terminating — removed from Service endpoints (no new traffic)
→ ② preStop hook runs (e.g., sleep 5 — waits for endpoint propagation)
→ ③ SIGTERM sent to PID 1 — app should finish requests, close DB connections, exit
→ ④ Grace period countdown (default 30s, configurable)
→ ⑤ SIGKILL if still alive — force-killed, cannot be caught
→ ⑥ Pod removed from API server
