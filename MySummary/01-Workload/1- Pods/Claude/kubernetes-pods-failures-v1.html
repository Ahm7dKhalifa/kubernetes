Key Insight

Pre-run failures (scheduling, image pull, config) always retry forever — Kubernetes never gives up trying to start your Pod. Runtime failures (crash, OOM, probes) depend on restartPolicy. Infrastructure failures (eviction, node death) never retry the same Pod — a controller must create a new one.

02 The Retry Rule

Definition — The Two Retry SystemsKubernetes has two completely different retry mechanisms. Understanding which one handles your failure is the key to understanding retry behavior:

1. Kubelet Retry (container level) — the kubelet on the node keeps trying to start/restart the container. This handles: image pull, config errors, container crashes, OOM kills. Controlled by restartPolicy.

2. Controller Retry (pod level) — a Deployment/ReplicaSet/Job watches for missing Pods and creates new ones. This handles: eviction, node death, pod deletion. Naked Pods have NO controller, so they're gone forever.

Critical Distinction

Kubelet retries = same Pod, same node, same IP. The container restarts inside the existing Pod.
Controller retries = brand new Pod, possibly different node, new IP. The old Pod is gone — a completely new Pod is created.

04 Image Pull Failure ▶

What happens
Retry behavior
Backoff timeline
How to fix
Kubelet can't download the container image from the registry
kubelet → Registry: "image not found" / "401 unauthorized" / timeout
What fails: The container runtime (containerd) tries to pull the image and gets an error. Common causes: wrong image name/tag, private registry without credentials, Docker Hub rate limiting, network/DNS issue.
Failed to pull image "myapp:v99": rpc error: manifest unknown
RETRIES FOREVER with exponential backoff
ErrImagePull → ImagePullBackOff (retry with backoff) → ErrImagePull → ImagePullBackOff → ∞
Retry mechanism: Kubelet retries pulling the image with exponential backoff. It alternates between ErrImagePull (actively trying) and ImagePullBackOff (waiting before retry).

Backoff: Starts at ~10 seconds, doubles each time, caps at 5 minutes. After reaching the cap, it retries every 5 minutes forever.

Stops when: Never. Kubelet retries forever until the image becomes available OR you delete/update the Pod. There is no maximum retry count.

restartPolicy has NO effect here — the container hasn't started yet, so there's nothing to "restart." The kubelet simply keeps trying to pull the image.
Exact timeline of what you see
$ kubectl get pod bad-image -w

bad-image 0/1 ImagePullBackOff 14s # Waiting ~10s
bad-image 0/1 ErrImagePull 26s # Retry #2 fails
bad-image 0/1 ImagePullBackOff 48s # Waiting ~20s
bad-image 0/1 ErrImagePull 1m10s # Retry #3 fails
bad-image 0/1 ImagePullBackOff 2m # Waiting ~40s
bad-image 0/1 ImagePullBackOff 10m # Waiting ~5min (max)
bad-image 0/1 ImagePullBackOff 3h # Still retrying every 5min...

kubectl describe pod bad-image | grep -A5 "Events"

# Fix 2: Private registry — create image pull secret

  --docker-username=user \
  --docker-password=pass

# Then add to Pod spec:
# spec:
#   imagePullSecrets:
#   - name: my-reg

# Fix 3: Docker Hub rate limit — authenticate
kubectl create secret docker-registry dockerhub \
  --docker-server=docker.io \

What happens
Retry behavior
How to fix
Missing ConfigMap, Secret, or volume mount
CreateContainerConfigError → Pod references ConfigMap "app-config" that doesn't exist
Error: configmap "app-config" not found
RETRIES FOREVER — kubelet keeps checking
Retry mechanism: Kubelet periodically re-checks whether the missing ConfigMap/Secret has been created. The container stays in CreateContainerConfigError and never starts. As soon as you create the missing resource, kubelet detects it and the container starts automatically.

restartPolicy has NO effect — the container never started, so there's nothing to restart.

Stops when: Never — waits forever until the resource exists or Pod is deleted.
How to fix
# Create the missing ConfigMap
kubectl create configmap app-config --from-literal=db-host=postgres

# Create the missing Secret
kubectl create secret generic db-secret --from-literal=password=mypass

# OR mark it optional in the Pod spec:
env:
- name: OPTIONAL_VAR
  valueFrom:
    configMapKeyRef:
      name: maybe-exists
      key: value
      optional: true   # ← Container starts even if ConfigMap missing

06 Application Crash ▶

What happens
restartPolicy: Always
restartPolicy: OnFailure
restartPolicy: Never
Backoff timeline
Container starts then exits with non-zero code
Container starts → Crash! exit 1 (exception/bug) → what happens next depends on restartPolicy
The container process dies. This is different from pre-run failures — the container DID start and DID run, but the application had a bug, missing dependency, or configuration issue.
restartPolicy: Always → RETRIES FOREVER
exit 1 → wait 10s → exit 1 → wait 20s → exit 1 → wait 40s → ∞ forever
Used by: Deployments, StatefulSets, DaemonSets (the default).
Behavior: Kubelet restarts the container regardless of exit code (even exit 0). Uses exponential backoff: 10s, 20s, 40s, 80s, 160s, 300s cap. After 10 minutes of successful running, backoff resets to 10s.
Never gives up. The container will keep crashing and restarting forever until you fix the code or delete the Pod.
restartPolicy: OnFailure → RETRIES ON ERROR
exit 1 (error) → restart with backoff ∞

exit 0 (success) → STAYS STOPPED ✓ (job done)
Used by: Jobs, batch workloads.
Behavior: Kubelet restarts the container only if it exits with a non-zero code (failure). If it exits 0 (success), it stays stopped — the job is complete. Retries forever on failure with the same exponential backoff.
This is perfect for Jobs — retry on failure, stop on success.
restartPolicy: Never → NEVER RETRIES — STAYS DEAD
exit 1 (error) → Container stays dead. Pod status: Failed.

exit 0 (success) → Container stays stopped. Pod status: Succeeded.
Used by: Jobs (when the Job controller handles retry at the Pod level, not container level).
Behavior: The container is NEVER restarted regardless of exit code. The Pod goes to Failed or Succeeded status and stays there forever. For Jobs, the Job controller creates a brand new Pod instead (up to backoffLimit).
This is the ONLY policy where a container stays permanently dead.

07 OOM Kill ▶

What happens
Retry behavior
How to detect & fix
Container exceeds memory limit → kernel kills it
Container: using 250Mi → 254Mi... → 257Mi > limit 256Mi → SIGKILL! exit 137
What happens: The Linux kernel's OOM killer detects the container's memory cgroup exceeding its limit. It sends SIGKILL (cannot be caught) → process dies instantly with exit code 137. No graceful shutdown. No time to clean up.
DEPENDS ON restartPolicy — same as app crash
OOM kills are treated exactly like app crashes. The container exited with non-zero (137), so:

Always: Restarts forever with backoff. Container will keep OOM-ing if you don't fix the memory leak.
OnFailure: Restarts forever (137 ≠ 0, so it's a failure).
Never: Container stays dead. Pod status: Failed.
How to detect & fix
$ kubectl describe pod oom-app | grep -A3 "Last State"
  Last State: Terminated
    Reason: OOMKilled
    Exit Code: 137

$ kubectl top pod oom-app
NAME CPU MEMORY
oom-app 50m 248Mi # limit is 256Mi → OOM imminent!
Fix: Increase resources.limits.memory, fix the memory leak in your app, profile heap usage.

08 Probe Failures ▶

Startup fail
Liveness fail
Readiness fail
Startup Probe Failure
Startup: checking /healthz... fail... fail... → 30 failures × 10s = 5min → KILL container → restartPolicy applies
Retry behavior: The startup probe itself retries up to failureThreshold times (e.g., 30). If it never passes → container is killed. Then restartPolicy determines if the container restarts:

Always/OnFailure: Container restarts, startup probe begins again from scratch. This loops forever (CrashLoopBackOff).
Never: Container stays dead.
Liveness Probe Failure
Running OK... → Liveness: 3 consecutive failures → KILL container → restartPolicy applies
Retry behavior: Liveness probe checks every periodSeconds. After failureThreshold consecutive failures → container is killed and restarted (per restartPolicy). Kubelet keeps running liveness checks forever. If the underlying problem persists, this becomes a CrashLoopBackOff cycle.

Key point: Liveness kills the container. This is destructive. That's why you should NEVER check external dependencies in liveness — if the DB is down, killing your app won't fix the DB!
Readiness Probe Failure
Running OK, serving traffic → Readiness fails → Removed from Service (no traffic) → Container keeps running!
Retry behavior: Readiness probe NEVER kills the container. It only controls whether the Pod receives traffic from the Service. Kubelet keeps checking every periodSeconds forever. When the probe starts passing again, the Pod is automatically added back to the Service endpoints.

This is the safe probe for dependency checks. DB goes down → readiness fails → Pod removed from traffic → DB comes back → readiness passes → Pod gets traffic again. No restarts. No data loss. No disruption.

09 Dependency Failure ▶

DB goes down
With readiness (correct)
With liveness (WRONG!)
External service becomes unavailable
Pod running fine ⟷ Database DOWN ✗
Your app process is alive and healthy. But the database it depends on is unreachable. The app can't serve meaningful requests. What should Kubernetes do?
Correct: Readiness probe checks DB → Pod removed from traffic
Pod alive → Readiness fails (DB down) → Removed from Service → Pod keeps running, waiting for DB

DB comes back → Readiness passes → Added back to Service ✓
Result: Pod stays alive. No restart. No data loss. Traffic goes to other healthy Pods. When DB recovers, this Pod automatically starts receiving traffic again. Self-healing without destruction.
WRONG: Liveness probe checks DB → CATASTROPHIC CASCADE
DB DOWN → Liveness fails on ALL Pods → ALL Pods killed + restarted simultaneously

All Pods restarting → All hit DB at once (thundering herd) → DB still down → ALL fail again → TOTAL OUTAGE
Result: Every single Pod restarts at the same time. When they all come back, they ALL try to reconnect to the DB simultaneously (thundering herd). DB is still down → they all fail liveness again → all restart again. Infinite loop of destruction. Complete service outage.

This is why the rule is absolute: NEVER put external dependency checks in liveness probes.

10 Init Container Failure ▶

What happens
Retry behavior
Timeline
An init container exits with non-zero code
Init 1: ✓ → Init 2: exit 1 ✗ → Init 3: never runs → App: never starts
The failed init container blocks the entire Pod. Everything after it (subsequent inits, sidecars, app containers) never starts.
RETRIES FOREVER — ignores restartPolicy!
Critical difference: Init containers always retry regardless of the Pod's restartPolicy. Even if the Pod has restartPolicy: Never, a failed init container will be retried with exponential backoff. This is because the Pod hasn't "run" yet — it never got past initialization.

Backoff: Same formula: 10s → 20s → 40s → 80s → 160s → 300s cap.
Stops when: Never — retries forever until init exits 0, or you delete the Pod.
Exception: If the Pod's restartPolicy is Never AND the init container fails, the entire Pod is marked Failed. But the controller (Job) may create a new Pod to retry.
What you see
$ kubectl get pod my-app -w
NAME READY STATUS AGE
my-app 0/1 Init:1/3 8s # Init 2 running
my-app 0/1 Init:Error 10s # Init 2 failed!
my-app 0/1 Init:CrashLoopBackOff 22s # Waiting 10s
my-app 0/1 Init:CrashLoopBackOff 45s # Waiting 20s
my-app 0/1 Init:CrashLoopBackOff 5m # Keeps retrying forever

11 Eviction ▶

What happens
Retry behavior
Naked vs Controller
Kubelet evicts Pod due to node resource pressure
Node memory: 95% used! → kubelet evicts BestEffort Pods first → Pod: Evicted
When a node runs low on memory, disk, or PIDs, the kubelet evicts Pods in QoS priority order (BestEffort → Burstable → Guaranteed). The evicted Pod is terminated and not restarted on the same node.
NO RETRY on same Pod — Controller must create a new one
The kubelet does NOT restart evicted Pods. An evicted Pod is dead. Its status is Failed with reason Evicted. It stays in this state forever (until garbage collected).

Who recreates it? Only a controller (Deployment, ReplicaSet, StatefulSet). The controller detects that the actual replica count is below desired, and creates a brand new Pod — possibly on a different node. This is a NEW Pod with a new name and new IP.
Naked Pod = gone forever. Controller Pod = recreated.
Naked Pod: Evicted → gone forever. Nobody recreates it. ✗

Deployment Pod: Evicted → ReplicaSet creates NEW Pod on healthy node ✓

12 Node Death ▶

What happens
Timeline
Naked vs Controller
The node running your Pod crashes
Node: worker-02 ☠ (hardware/kernel/power failure) → All Pods on this node go Unknown
The node stops reporting heartbeats to the API server. After node-monitor-grace-period (default 40s), the node is marked NotReady. After pod-eviction-timeout (default 5 min), all Pods on the dead node are marked for deletion.
What you see over time
$ kubectl get nodes -w
worker-02 Ready <none> 5d
worker-02 NotReady <none> 5d # After 40s of no heartbeat

$ kubectl get pods -w
my-app 1/1 Running 0 2h
my-app 1/1 Unknown 0 2h # Node went NotReady
my-app 1/1 Terminating 0 2h # After 5 min, Pod marked for deletion
# If Deployment-managed: new Pod created on healthy node
my-app-new 0/1 ContainerCreating 0 1s
NO RETRY for the same Pod
Naked Pod: Node dies → Pod gone FOREVER. No controller = no recreation. ✗

Deployment Pod: Node dies → wait 5 min → NEW Pod created on healthy node ✓
The original Pod is never "restarted." It's dead on a dead node. A controller creates a completely new Pod (new name, new IP, possibly different node). This is why controllers are essential for production.

13 restartPolicy — Complete Reference

Definition — restartPolicyA Pod-level field that tells the kubelet what to do when a container exits. Set once for the entire Pod — all containers follow the same policy. Only applies to containers that have actually started (not pre-run failures like image pull or config errors).

# Deployments (services that should always run)
restartPolicy: Always      # DEFAULT — Kubernetes adds this if you don't specify

# Jobs (batch tasks that should retry on failure)
restartPolicy: OnFailure   # Retry failures, stop on success

# Jobs (when Job controller handles retry at Pod level)
restartPolicy: Never       # Let the container die, Job creates a new Pod

14 Backoff Formula

Definition — Exponential BackoffWhen a container keeps failing, Kubernetes waits longer between each restart to avoid wasting resources. The formula: min(10s × 2^(n-1), 300s) where n = restart count. After 10 minutes of healthy running, the backoff timer resets to 10s.
Restart #Wait Before RetryCumulative Time
110 seconds~10s
220 seconds~30s
340 seconds~1m 10s
480 seconds~2m 30s
5160 seconds~5m 10s
6+300 seconds (cap)+5 min per retry
Backoff Reset

If a container runs successfully for 10 consecutive minutes, the backoff timer resets to 10 seconds. This means: fix the bug → container starts → runs for 10 min → if it crashes again, wait is only 10s instead of 300s.
