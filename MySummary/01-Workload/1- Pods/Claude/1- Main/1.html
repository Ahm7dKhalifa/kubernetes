Kubernetes Pods

The ultimate deep-dive into Pods — from lifecycle and failure handling to health probes, disruption budgets, and SRE operational principles.

SRE-Focused  ·  Operations  ·  Best Practices

01 What is a Pod?

A Pod is the smallest deployable unit in Kubernetes. It is a wrapper around one or more containers that share the same network namespace (same IP address), storage volumes, and lifecycle. Kubernetes never runs a bare container — it always runs a Pod.

Think of it this way

A Pod is like an apartment — the containers inside are roommates. They share the same address (IP), the same living space (volumes), and move in/out together (lifecycle). Kubernetes manages apartments, not individual people.

Pod Anatomy — Shared Resources

Key Characteristics

PropertyDescription
Shared NetworkAll containers in a Pod share the same IP and port space. They communicate via localhost.
Shared StorageContainers can mount the same volumes — useful for sidecar patterns (e.g., log shipping).
Co-schedulingAll containers land on the same node. They start and stop together.
Ephemeral by DesignPods are disposable. They can be killed, rescheduled, or replaced at any time. Never treat a Pod as permanent.
Unique IdentityEach Pod gets a unique name and UID. Replacement Pods get new names and IPs.
SRE Principle — Cattle, Not Pets

Pods are cattle, not pets. You don't name them, nurse them, or repair them individually. If a Pod is sick, you replace it. Design your applications to be stateless and resilient to Pod replacement. This is the foundation of reliable operations in Kubernetes.

02 Pod Types (by Container Count)

Single-Container Pod

The most common pattern. One Pod = one container = one process. This is the default and recommended approach.

Example: A single web server, a single API, a single worker.

Multi-Container Pod

Multiple tightly-coupled containers that must share resources and coordinate. Used for sidecars, adapters, and ambassadors.

Example: App + log shipper, App + proxy, App + config reloader.

03 Creating Pods

Method 1 — Individual Pod (Direct)

Creating a standalone Pod directly. This is only for testing/debugging — in production, always use controllers.

apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: web
spec:
  containers:
  - name: web
    image: nginx:1.25
    ports:
    - containerPort: 80

Method 2 — Via Controllers (Production)

In production, Pods are created indirectly through higher-level controllers that manage their lifecycle:

ControllerCreates Pods ForKey Feature
DeploymentStateless servicesRolling updates, rollbacks, replica scaling
StatefulSetStateful servicesStable identity, ordered startup, persistent storage
DaemonSetOne per nodeNode-level agents (monitoring, logging)
JobBatch tasksRun to completion, retries
CronJobScheduled tasksTime-based triggers
ReplicaSetReplica managementEnsures N replicas (used internally by Deployment)
SRE Principle — Never Run Naked Pods

A "naked Pod" (created directly, not by a controller) will not be rescheduled if a node fails. In production, always create Pods through a Deployment, StatefulSet, or other controller. This ensures self-healing — the controller detects the missing Pod and recreates it.

04 Updating Pods

Pods themselves are mostly immutable after creation. You cannot change the image, commands, or most spec fields of a running Pod. Instead, you use controllers to manage updates.

Update Strategies

StrategyHow It WorksDowntime?
Rolling Update
Default		 Gradually replaces old Pods with new ones. At every step, some old and some new Pods are running. Zero downtime ✓
Recreate Kills all old Pods first, then creates new ones. Simple but causes a gap. Brief downtime ✗
Blue/Green Deploy new version alongside old. Switch traffic at once via Service selector change. Zero downtime ✓
Canary Send a small % of traffic to new Pods. Gradually increase if healthy. Zero downtime ✓

SRE Principle — Graceful Shutdown

Your application must handle SIGTERM — finish in-flight requests, close database connections, flush buffers. If your app needs more than 30 seconds, increase terminationGracePeriodSeconds. A preStop hook is ideal for draining load balancer connections before the process exits.

06 Pod Lifecycle & Phases

Every Pod goes through a series of phases from creation to termination. The status.phase field tells you where the Pod is in its lifecycle.

Pod Phase State Machine
PhaseMeaningSRE Action
PendingPod accepted but containers not yet running. Could be scheduling, image pull, or waiting for volumes.Check Events, node resources, image availability
RunningAt least one container is running or starting/restarting.Monitor probes, resource usage, logs
SucceededAll containers exited with code 0. Terminal state (for Jobs).Verify output, clean up if needed
FailedAll containers terminated, at least one exited non-zero.Check logs, exit codes, OOM events
UnknownCannot get Pod status — usually node connectivity issue.Check node health, network, kubelet status

07 Container Lifecycle & States

Inside a Pod, each container has its own state, tracked in status.containerStatuses[].state.

Waiting

Container is not running yet. Could be pulling image, waiting for init containers, or in CrashLoopBackOff.

Field: state.waiting.reason

Running

Container is executing. The postStart hook (if any) has completed. Process is alive.

Field: state.running.startedAt

Terminated

Container finished execution — either successfully (exit 0) or with an error. Check exit code and reason.

Field: state.terminated.exitCode

Lifecycle Hooks

HookWhen It RunsUse Case
postStartImmediately after container starts (parallel with entrypoint)Warm caches, register with service discovery
preStopImmediately before container receives SIGTERMDrain connections, deregister, flush data

08 Failure Reasons & Root Causes

Understanding why containers fail is the first step to building resilient systems. Here are the most common failure categories:

CategoryCommon ReasonsHow to Detect
Application Crash Unhandled exception, segfault, panic, null pointer kubectl logs, exit code ≠ 0
OOM Killed Container exceeded memory limit → kernel kills it Exit code 137, OOMKilled reason in status
Liveness Probe Failure App is hung/deadlocked, probe times out Events show "Liveness probe failed", container restarts
Image Pull Error Wrong image name, tag, registry auth, network issue ImagePullBackOff or ErrImagePull status
Configuration Error Missing ConfigMap/Secret, wrong env vars, bad mount CreateContainerConfigError, Pod stuck in Pending
Resource Starvation Insufficient CPU/memory on the node, unschedulable Pending state, events show FailedScheduling
Dependency Failure Database down, external API unreachable, DNS failure App logs show connection errors, readiness probe fails
SRE Principle — Exit Codes are Your Telemetry

Always design applications to return meaningful exit codes: 0 = success, 1 = general error, 137 = OOMKilled (128 + signal 9), 143 = SIGTERM (128 + signal 15). These codes are the first data point when diagnosing failures at scale. Monitor exit code distribution as a key SLI.

09 Crash Loop Lifecycle

When a container keeps failing and restarting, it enters the dreaded CrashLoopBackOff. Kubernetes uses exponential backoff to avoid hammering a broken container.

CrashLoopBackOff — Exponential Backoff Timeline

The backoff delay doubles each time: 10s, 20s, 40s, 80s, 160s, up to a maximum of 5 minutes. It resets to 10s after the container runs successfully for 10 minutes.

10 Restart Policy

The restartPolicy field in the Pod spec tells the kubelet what to do when a container exits. It applies to all containers in the Pod.

Always
Default

Always restart, regardless of exit code. Used for long-running services (Deployments).

OnFailure
Retry on error

Only restart if container exits non-zero. Used for Jobs (retry failures, stop on success).

Never
One-shot

Never restart. Pod stays in Failed/Succeeded state. Used for Jobs where you want a new Pod per retry.

Workload TypeRestart PolicyWhy
Deployment / DaemonSetAlwaysServices must stay running forever
Job (in-pod retry)OnFailureRetry inside same Pod, stop on success
Job (new pod per retry)NeverJob Controller creates replacement Pods
SRE Principle — Restart ≠ Resolution

A restart policy only masks symptoms — it doesn't fix the underlying bug. Always pair restart policies with alerting on restart count. If a container restarts > 3 times in 10 minutes, that's an incident — not "self-healing." Set up kube_pod_container_status_restarts_total alerts in Prometheus.

11 Debugging Failures

The SRE Debugging Ladder

When a Pod is failing, follow this systematic approach from broad to specific:

# Step 1: Get high-level status
kubectl get pods -o wide

# Step 2: Read events for scheduling/pull/probe issues
kubectl describe pod/my-app

# Step 3: Check current and previous container logs
kubectl logs pod/my-app
kubectl logs pod/my-app --previous   # logs from the LAST crashed container

# Step 4: Check exit code and OOM status
kubectl get pod/my-app -o jsonpath='{.status.containerStatuses[0].lastState}'

# Step 5: Exec into a running container for live debugging
kubectl exec -it pod/my-app -- /bin/sh

# Step 6: For crashed pods, attach an ephemeral debug container
kubectl debug -it pod/my-app --image=busybox --target=web

# Step 7: Check node-level issues
kubectl describe node <node-name>
Pro Tip

The --previous flag is your best friend for CrashLoopBackOff. It shows logs from the last terminated container — which is where the error happened. Without it, you only see the newly starting (and immediately crashing) container.

12 Container Probes — Health Monitoring

Probes are periodic diagnostic checks that Kubernetes performs on containers to determine if they are healthy and ready. The kubelet on each node runs the probes.

SRE Principle — Don't Trust, Verify

A container being "Running" doesn't mean your app is healthy. It could be deadlocked, have a broken DB connection, or be stuck in an infinite loop. Probes are your automated health verification — the equivalent of a human checking "are you actually working?" every few seconds. Never deploy to production without probes.

Check Mechanisms

Each probe uses one of four mechanisms to check the container:

MechanismHow It WorksBest For
httpGet Sends an HTTP GET to a path/port. Success = status code 200-399. Web apps, APIs, any HTTP service
tcpSocket Opens a TCP connection to a port. Success = connection established. Databases, message queues, non-HTTP services
exec Runs a command inside the container. Success = exit code 0. Custom checks, file existence, process checks
gRPC Calls a gRPC health check endpoint. Success = SERVING status. gRPC microservices

Probe Outcomes

Success

Container passed the check

Failure

Container failed the check

Unknown

Check itself failed (don't act)

13 Probe Types — The Three Probes

Three Probe Types — What Each Controls

Complete Probe Example

containers:
- name: web
  image: myapp:v3

  # ── Startup: Give slow app up to 5min to start ──
  startupProbe:
    httpGet:
      path: /healthz
      port: 8080
    failureThreshold: 30        # 30 × 10s = 300s = 5min max
    periodSeconds: 10

  # ── Liveness: Detect deadlocks ──
  livenessProbe:
    httpGet:
      path: /healthz
      port: 8080
    periodSeconds: 15           # Check every 15 seconds
    timeoutSeconds: 3          # Timeout per check
    failureThreshold: 3        # 3 failures → restart

  # ── Readiness: Control traffic ──
  readinessProbe:
    httpGet:
      path: /ready
      port: 8080
    periodSeconds: 5            # Check frequently
    failureThreshold: 2        # 2 fails → stop traffic
    successThreshold: 1        # 1 success → resume traffic
SRE Principle — Probe Design Rules

Liveness ≠ Readiness. Liveness should check if the process is alive. Readiness should check if it can serve traffic (DB connected, caches warm). Never make liveness depend on external services — if the DB is down, restarting your app won't fix it.

Don't make probes too aggressive. A liveness probe with periodSeconds: 1 and failureThreshold: 1 will kill containers that are briefly busy. Use reasonable values: 10-15s period, 3 failure threshold.

Use startup probes for slow starters. Without them, the liveness probe can kill containers that are still initializing (JVM warmup, large dataset loading).

14 Init Containers

Init containers run before the app containers start. They run sequentially (one at a time), and each must succeed before the next begins. Only after all init containers complete do the app containers start.

Init Container Execution Order

Common Use Cases

Use CaseWhat the Init Container Does
Wait for dependencyPolls until database or service is reachable
Run migrationsApplies DB schema changes before app starts
Clone configDownloads config files from git or S3
Generate certsCreates TLS certificates before the app needs them
Set permissionsFixes volume ownership/permissions as root

15 Sidecar Containers

Since Kubernetes v1.29 (stable v1.31), native sidecar containers are init containers with restartPolicy: Always. They start before app containers and run for the entire Pod lifetime alongside them.

initContainers:
- name: log-agent
  image: fluentbit:latest
  restartPolicy: Always     # ← This makes it a sidecar
  volumeMounts:
  - name: logs
    mountPath: /var/log/app
Key Difference from Regular Init Containers

Regular init containers run to completion and stop. Sidecars start during init phase but keep running alongside app containers. They are guaranteed to start before app containers and shut down after them — perfect for service meshes, log shippers, and monitoring agents.

16 Ephemeral Containers

Ephemeral containers are temporary debugging containers injected into a running Pod. They are not defined in the Pod spec — you add them on-the-fly for troubleshooting.

# Attach a debug container to a running pod
kubectl debug -it my-app --image=busybox --target=web

# Or copy the pod with a debug container
kubectl debug my-app -it --image=ubuntu --copy-to=debug-pod
SRE Principle — Debug Without Disrupting

Ephemeral containers let you debug production Pods without restarting them. This is critical for investigating issues that only reproduce in production. The debug container shares the Pod's namespace, so you can inspect the filesystem, network, and processes of the target container.

17 Pod Resource Calculation

When a Pod has multiple container types (init, sidecar, app), Kubernetes calculates the Pod's effective resource request/limit using specific rules:

Resource Calculation Formula

Example Calculation

ContainerTypeCPU RequestMemory Request
init-migrateInit500m512Mi
init-downloadInit200m256Mi
log-agentSidecar100m128Mi
webApp300m256Mi

Calculation: MAX init = 500m CPU, 512Mi mem. SUM(app+sidecar) = 400m CPU, 384Mi mem. Pod effective = MAX(500m, 400m) = 500m CPU and MAX(512Mi, 384Mi) = 512Mi mem.

18 Quality of Service (QoS) Classes

Kubernetes assigns a QoS class to each Pod based on its resource requests and limits. This determines the eviction priority when the node runs out of resources.

Guaranteed
Last to be evicted

Every container has equal requests and limits for CPU and memory. Highest priority.

requests:
  cpu: "500m"
  memory: "256Mi"
limits:
  cpu: "500m"
  memory: "256Mi"
Burstable
Middle priority

At least one container has requests or limits, but they are not equal. Can burst above requests.

requests:
  cpu: "250m"
  memory: "128Mi"
limits:
  cpu: "1"
  memory: "512Mi"
BestEffort
First to be evicted

No requests or limits set. Lowest priority — evicted first under pressure.

# No resources defined
containers:
- name: app
  image: myapp
SRE Principle — Always Set Resources

In production, every container must have resource requests (at minimum). Without them, the scheduler makes blind decisions, overcommits nodes, and your Pods get evicted first. For critical workloads, use Guaranteed QoS. For most services, Burstable with reasonable limits is the sweet spot.

19 Disruption & Pod Disruption Budgets

Disruptions are events that cause Pods to be removed from a node. They come in two flavors:

Voluntary Disruptions

Controlled — initiated by a human or automation:

Node drain for maintenance • Cluster upgrade • Scaling down replicas • Deleting a Deployment • Pod eviction by autoscaler

Involuntary Disruptions

Uncontrolled — unexpected failures:

Hardware failure • Kernel panic • Cloud VM termination • OOM kill by kernel • Network partition

Pod Disruption Budgets (PDBs)

A PDB is a Kubernetes API object that limits how many Pods can be disrupted at once during voluntary disruptions. It protects application availability during maintenance.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  minAvailable: 2              # Always keep at least 2 Pods running
  # OR
  # maxUnavailable: 1           # Allow at most 1 Pod down at a time
  selector:
    matchLabels:
      app: web
PDB in Action — Node Drain with minAvailable: 2
Limitation

PDBs only protect against voluntary disruptions (node drain, scale-down). They cannot prevent involuntary disruptions like hardware crashes. For those, you need replicas across multiple nodes and failure zones.

Reliable operations require comprehensive observability. Here are the key metrics, logs, and practices every SRE should implement for Pod health.

The Four Golden Signals for Pods

Latency

How long requests take (p50, p95, p99)

Traffic

Requests per second to the Pod

Errors

Error rate (5xx, timeouts, failures)

Saturation

CPU/memory utilization vs limits

SRE Principle — Observability Layers

Layer 1 — Metrics: Prometheus + Grafana for real-time dashboards. Alert on golden signals and Pod-level metrics above.

Layer 2 — Logs: Structured JSON logging shipped via sidecar (Fluent Bit) to a central store. Always include request ID, trace ID, Pod name, and node.

Layer 3 — Traces: Distributed tracing (Jaeger/Tempo) to follow requests across Pods and services.

Layer 4 — Events: Kubernetes Events are gold for debugging. Use tools like kube-event-exporter to ship them to your logging system.

21 Production Readiness Checklist

Before deploying any Pod to production, walk through this SRE checklist:

Health & Probes

✅ Liveness probe configured (detects deadlocks)

✅ Readiness probe configured (controls traffic routing)

✅ Startup probe if app takes > 10s to initialize

✅ Probes hit a lightweight, dependency-free endpoint

Resources & Limits

✅ CPU and memory requests set for every container

✅ Memory limits set (prevents OOM on the node)

✅ QoS class is Guaranteed or Burstable (never BestEffort)

✅ Resource values based on load testing, not guesses

Resilience & Availability

✅ Pods managed by a controller (Deployment, StatefulSet — never naked)

✅ At least 2-3 replicas for critical services

✅ Pod anti-affinity to spread replicas across nodes/zones

✅ PodDisruptionBudget set (minAvailable or maxUnavailable)

✅ Graceful shutdown handles SIGTERM properly

Observability

✅ Structured logging (JSON) to stdout/stderr

✅ Metrics endpoint exposed (/metrics for Prometheus)

✅ Alerts on restart count, OOM, error rate, latency

✅ Distributed tracing headers propagated

Security & Safety

✅ Non-root container (runAsNonRoot: true)

✅ Read-only root filesystem where possible

✅ No privileged containers unless absolutely necessary

✅ Secrets mounted from Kubernetes Secrets (never hardcoded)

✅ Network policies restricting traffic to necessary services only

Final SRE Wisdom

The goal isn't zero failures — it's fast, automated recovery. Design Pods to crash safely (exit codes, graceful shutdown), detect failures quickly (probes, metrics), recover automatically (controllers, restart policies), and provide full visibility (logs, traces, events). A well-instrumented Pod that restarts cleanly is worth more than a fragile Pod that never crashes.
