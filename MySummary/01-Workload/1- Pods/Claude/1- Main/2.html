01 What is a Pod?

A Pod is the smallest and most basic deployable unit in Kubernetes. It's a thin wrapper around one or more containers that tells Kubernetes: "treat these containers as a single, atomic unit."

Kubernetes does not run containers directly. Every container in Kubernetes lives inside a Pod. Even a single container runs inside a Pod — it's just a Pod with one container.

Simple Analogy

Think of a Pod as a shared apartment. The containers are the roommates. They share the same address (IP), the same living space (volumes), and they move in and out together (lifecycle). Kubernetes manages apartments, not individual people.

What Makes a Pod Special?

A Pod provides a shared execution environment for its containers. This means all containers inside a Pod share:

Shared ResourceWhat This MeansPractical Impact
Network NamespaceAll containers share the same IP address and port spaceContainer A can reach Container B via localhost:PORT. No need for service discovery between containers in the same Pod.
Storage VolumesVolumes defined in the Pod spec can be mounted by any containerA log-shipper sidecar can read log files written by the app container. Both mount the same emptyDir volume.
IPC NamespaceContainers can communicate using System V IPC or POSIX message queuesUseful for legacy apps that use shared memory for inter-process communication.
PID Namespace (optional)When shareProcessNamespace: true, containers can see each other's processesA debug sidecar can inspect or signal the app process. Used for process monitoring.
LifecycleAll containers are scheduled to the same node and start/stop togetherIf the Pod is deleted, all containers are terminated. If the node fails, all containers fail.
HostnameAll containers see the same hostname (= Pod name)hostname command returns the Pod's name in every container.

What a Pod is NOT

A Pod is not a virtual machine. It does not have its own OS, kernel, or full networking stack. It's a Kubernetes abstraction that groups containers sharing Linux namespaces and cgroups. Each container is still an isolated process — they just share some namespace boundaries.

Key Characteristics

PropertyDetail
EphemeralPods are designed to be disposable. They can be killed, evicted, or rescheduled at any time. You should never treat a Pod as permanent storage or as a long-lived identity.
Unique IdentityEach Pod gets a unique name (e.g., web-7d4b9c6f5-x2k9m) and a cluster-internal IP address. When a Pod is replaced, the new Pod gets a new name and new IP.
Single NodeAll containers in a Pod are always co-located on the same node. They cannot span multiple nodes.
OwnerReferencePods created by controllers (Deployment, Job, etc.) have an ownerReferences field pointing to the controller. This is how Kubernetes knows which controller manages which Pods.
SRE Principle — Cattle, Not Pets

Pods are cattle, not pets. You don't give them unique names, you don't SSH into them to fix issues, and you don't care which specific Pod is serving a request. If a Pod is unhealthy, you replace it — not repair it. This mindset is the foundation of reliable, scalable operations in Kubernetes.

02 Pod Internals — Under the Hood

When Kubernetes creates a Pod, it actually creates a hidden infrastructure container first, then starts your containers inside its namespace. Understanding this helps debug networking and lifecycle issues.

Pod Internal Architecture

The Pause Container

Every Pod has a hidden pause container (also called the "infrastructure container"). It's the first thing created and the last to be destroyed. Its job is to hold the network namespace alive. If your app container crashes and restarts, the network namespace (and therefore the IP address) persists because the pause container is still running. This is why Pods keep their IP even when containers restart.

How Containers Communicate Inside a Pod

03 Pod Types (by Container Count)

Single-Container Pod

The most common and recommended pattern. One Pod = one container = one process. This keeps things simple — the Pod lifecycle equals the container lifecycle.

When to use: Almost always. Each microservice, API, worker, or web server should be its own single-container Pod.

Rule of thumb: If you'd run it as a separate process on a VM, it should be a separate Pod in Kubernetes.

Multi-Container Pod

Multiple containers that are tightly coupled and must share resources. Use only when containers genuinely need to be co-located — they share data, communicate via localhost, or have dependent lifecycles.

When to use: Only when containers must share network, storage, or lifecycle. If they can work independently, use separate Pods.

Warning: Adding containers to a Pod increases blast radius — if the Pod is evicted, ALL containers die.

05 Creating Pods

Method 1 — Individual Pod (Direct / Naked)

Creating a standalone Pod directly — only for testing and debugging.

# Declarative (YAML file)
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: web
    env: dev
spec:
  containers:
  - name: web
    image: nginx:1.25
    ports:
    - containerPort: 80
    resources:
      requests:
        cpu: "250m"
        memory: "128Mi"
# Imperative (one-liner)
kubectl run my-app --image=nginx:1.25 --port=80

# Generate YAML without creating (dry-run)
kubectl run my-app --image=nginx:1.25 --dry-run=client -o yaml > pod.yaml
SRE Principle — Never Run Naked Pods in Production

A naked Pod (one created directly, not by a controller) will not be rescheduled if a node fails, crashes, or is drained. It simply disappears. In production, always create Pods through a controller (Deployment, StatefulSet, DaemonSet, Job). The controller watches for missing Pods and recreates them — this is how Kubernetes self-heals.

06 Updating Pods

Pods are mostly immutable. Once created, you cannot change most fields. The way to "update" a Pod is to replace it with a new one.

Update Strategy 1 — Rolling Update (Default for Deployments)

Gradually replaces old Pods with new ones. At every step, some old and some new Pods are running. Zero downtime.

Rolling Update — Visual Timeline

Update Strategy 2 — Recreate

Kills all old Pods first, then creates all new Pods. Causes a gap where zero Pods are running. Use only when your app cannot have two versions running simultaneously (e.g., incompatible DB schema).

Update Strategy 3 — Rollback

# Check rollout history
kubectl rollout history deployment/my-app

# Rollback to the previous version
kubectl rollout undo deployment/my-app

# Rollback to a specific revision
kubectl rollout undo deployment/my-app --to-revision=3

08 Deleting Pods

# Graceful delete (default 30s grace period)
kubectl delete pod my-app

# Custom grace period
kubectl delete pod my-app --grace-period=60

# Force delete (skip graceful shutdown — DANGEROUS)
kubectl delete pod my-app --grace-period=0 --force

# Delete all pods in a namespace
kubectl delete pods --all -n my-namespace
Never Force-Delete Unless Absolutely Necessary

Force-deleting a Pod (--grace-period=0 --force) removes the Pod from the API server immediately without waiting for the kubelet to confirm the containers have stopped. The containers may still be running on the node. This can cause data corruption, split-brain issues, or duplicate processing. Only use it when the node is confirmed unreachable.

09 Graceful Shutdown — Deep Dive

When a Pod is deleted, Kubernetes follows a precise, ordered shutdown sequence. Understanding every step is critical for SREs to prevent data loss and request failures.

The Complete Graceful Shutdown Sequence

Key Details

StepDetailSRE Impact
Endpoint removalThe Pod is removed from Service endpoints in parallel with the SIGTERM. There's a brief window where traffic may still arrive after SIGTERM.Add a preStop: sleep 5 to give the endpoints time to propagate before the app starts shutting down.
preStop hookRuns synchronously before SIGTERM. Can be an exec command or httpGet. Its execution time counts toward the grace period.Use to drain connections, deregister from service discovery, or complete in-flight work.
SIGTERMSent to PID 1 in each container. If PID 1 is a shell (bash), it does NOT forward signals to child processes — your app never receives SIGTERM!Use exec form in Dockerfile (CMD ["app"]) not shell form (CMD app). Or use tini as PID 1.
Grace periodDefault: 30 seconds. Configurable via terminationGracePeriodSeconds. The preStop hook + SIGTERM wait time both count toward this.If your app needs 60s to drain, set terminationGracePeriodSeconds: 75 (60s drain + 15s buffer).
SIGKILLSent only if the container is still alive after the grace period. Cannot be caught or handled.If containers are regularly being SIGKILLed, increase the grace period or fix the app's shutdown logic.
SRE Principle — Test Your Graceful Shutdown

Most production incidents involving "connection reset" or "502 errors during deploy" are caused by poor graceful shutdown handling. Always test: (1) Your app catches SIGTERM, (2) it finishes in-flight requests, (3) it closes database connections, (4) it exits within the grace period. Run kubectl delete pod during load testing and verify zero errors.

12 Container States

Each container inside a Pod has its own state, independent of the Pod phase. Check via status.containerStatuses[].state.

Waiting

Container is not yet running. Kubernetes is performing prerequisite operations.

Common reasons:

ContainerCreating — Setting up volumes, network

ImagePullBackOff — Can't pull image

CrashLoopBackOff — Waiting before restart

CreateContainerConfigError — Missing Secret/ConfigMap

Running

Container is executing. The postStart hook has completed (if defined).

Key fields:

Note: Running doesn't mean healthy. The container could be deadlocked.

Terminated

Container finished execution — either succeeded (exit 0) or failed.

13 Lifecycle Hooks

Kubernetes provides two lifecycle hooks that run code at specific moments in a container's life:

postStart

When: Immediately after the container is created — runs in parallel with the container's entrypoint (not guaranteed to run before it).

Behavior: If the hook fails, the container is killed and restarted (subject to restart policy).

Use cases: Register with service discovery, warm caches, send "started" notification.

lifecycle:
  postStart:
    exec:
      command: ["/bin/sh", "-c", "curl -X POST http://registry/register"]

preStop

When: Immediately before the container receives SIGTERM. Runs synchronously — SIGTERM waits for it to complete.

Behavior: Execution time counts toward terminationGracePeriodSeconds. If the hook hangs, SIGKILL still fires after grace period.

Use cases: Drain connections, deregister, flush data, sleep to allow endpoint propagation.

lifecycle:
  preStop:
    exec:
      command: ["/bin/sh", "-c", "sleep 10 && nginx -s quit"]

15 Debugging Failures — The SRE Ladder

When a Pod is failing, follow this systematic top-down approach:

# ── STEP 1: What's the overall status? ──
kubectl get pods -o wide
# Look at STATUS, RESTARTS, AGE, NODE columns

# ── STEP 2: What do the events say? ──
kubectl describe pod my-app
# Scroll to "Events:" section — gold mine for scheduling, pull, probe issues

# ── STEP 3: What do the logs say? ──
kubectl logs pod/my-app                     # Current container logs
kubectl logs pod/my-app --previous          # Last crashed container logs ← CRITICAL
kubectl logs pod/my-app -c sidecar          # Specific container in multi-container Pod
kubectl logs pod/my-app --all-containers    # All containers at once

# ── STEP 4: What's the exit code? ──
kubectl get pod my-app -o jsonpath='{.status.containerStatuses[0].lastState.terminated.exitCode}'
# 137 = OOMKilled, 143 = SIGTERM, 1 = app error

# ── STEP 5: Is it a resource issue? ──
kubectl top pods                            # Current CPU/memory usage
kubectl describe node <node-name>           # Node resource pressure

# ── STEP 6: Shell into a running container ──
kubectl exec -it pod/my-app -- /bin/sh
# Check filesystem, network, env vars, processes

# ── STEP 7: Attach ephemeral debug container ──
kubectl debug -it pod/my-app --image=busybox --target=web
# For crashed pods — shares namespace for inspection

# ── STEP 8: Copy Pod with debug tools ──
kubectl debug pod/my-app -it --image=ubuntu --copy-to=debug-pod --share-processes
# Creates a copy of the pod with a debug container attached

16 Crash Loop Lifecycle — In Depth

When a container keeps failing and restarting, it enters CrashLoopBackOff. The kubelet uses exponential backoff to delay each successive restart attempt.

CrashLoopBackOff — Complete Backoff Timeline

Backoff Reset Rule

The backoff timer resets to 10s after the container runs successfully for 10 consecutive minutes. If it crashes again after that, the backoff starts over from 10s.

CrashLoopBackOff is Not a Phase

Important distinction: CrashLoopBackOff is a container waiting reason, not a Pod phase. The Pod is still in Running phase — it's the container inside that's in Waiting state with reason CrashLoopBackOff.

17 Restart Policy

The restartPolicy field tells the kubelet what to do when a container exits. It is set at the Pod level and applies to all containers in the Pod.

Always
Default policy

Always restart the container, regardless of exit code (0 or non-zero). Even if the container succeeds, it gets restarted.

Used by: Deployments, DaemonSets, StatefulSets

Reason: Services must run forever

OnFailure
Retry on error only

Restart only if the container exits with a non-zero exit code. If it exits with 0 (success), the container stays stopped.

Used by: Jobs (in-pod retry)

Reason: Retry failures, stop on success

Never
One-shot execution

Never restart the container, regardless of exit code. The Pod stays in Succeeded or Failed status forever.

Used by: Jobs (new Pod per retry)

Reason: Let Job Controller create replacement Pods

Container Exits WithrestartPolicy: AlwaysrestartPolicy: OnFailurerestartPolicy: Never
Exit code 0 (success)Restart ✓Stay stopped ✗Stay stopped ✗
Exit code 1 (error)Restart ✓Restart ✓Stay stopped ✗
Exit code 137 (OOMKilled)Restart ✓Restart ✓Stay stopped ✗

18 Restart Mechanics — Deep Details

Restart Scope — Pod Level, Not Container Level

restartPolicy is set at the Pod level, not per-container. You cannot have one container with Always and another with Never in the same Pod. All containers follow the same policy.

Exception: Native sidecar containers (init containers with restartPolicy: Always) can have their own restart behavior independent of the Pod-level policy. This is the only case where individual container restart behavior differs.

In-Place Restart (Same Pod)

When a container is restarted (due to crash or liveness probe failure), it's restarted in the same Pod on the same node. The Pod keeps its name, IP, and volumes. Only the container process is killed and re-created. This is called in-place restart.

Restart Delay (Exponential Backoff)

PropertyValue
Initial delay10 seconds
Multiplier×2 each failure (10s → 20s → 40s → 80s → 160s → 300s)
Maximum delay5 minutes (300 seconds)
Reset conditionContainer runs successfully for 10 minutes → backoff resets to 10s
Configurable?No — these values are hardcoded in the kubelet. You cannot customize them.

Restart Count

The restart count is tracked in status.containerStatuses[].restartCount. There is no maximum retry count for restart policies — Kubernetes will keep restarting the container forever (with backoff). The only limits are backoffLimit (for Jobs) and activeDeadlineSeconds.

SRE Principle — Restart ≠ Resolution

A restart only masks the symptom. If a container restarts 50 times, that's 50 opportunities you missed to fix the root cause. Alert on restart count. Set up a Prometheus alert: increase(kube_pod_container_status_restarts_total[10m]) > 3. Treat frequent restarts as incidents, not "self-healing."

19 What Are Probes?

A probe is a periodic diagnostic check performed by the kubelet against a container. The kubelet calls a handler on the container at a configurable interval, and based on the result, takes action (restart the container, remove from Service, etc.).

Probes answer the question: "Is this container actually working, or is it just 'running' but broken inside?"

SRE Principle — Don't Trust, Verify

A container being in "Running" state only means the process hasn't exited. It could be deadlocked, have a broken database connection, be stuck in an infinite loop, or have a full disk. Probes are your automated verification — the equivalent of a human checking "are you actually working?" every few seconds. Never deploy to production without all three probe types configured.

24 Probe Best Practices

SRE Principle — Liveness ≠ Readiness

Liveness checks should be SIMPLE: "Is the process alive and not deadlocked?" Check an internal endpoint that doesn't touch external dependencies. If the DB is down, restarting your app won't fix it — but a bad liveness probe will keep restarting it uselessly.

Readiness checks should be COMPLETE: "Can this Pod serve traffic right now?" Check database connectivity, cache availability, dependent services. A failing readiness probe removes the Pod from traffic without killing it — giving it time to recover.

Use separate endpoints: /healthz for liveness (lightweight, no dependencies), /ready for readiness (checks dependencies).

Common Probe Mistakes

❌ Liveness probe checks external dependency — DB goes down → liveness fails → all Pods restart → thundering herd → cascading failure

❌ Probe too aggressive — periodSeconds: 1, failureThreshold: 1 kills containers that are briefly busy

❌ No startup probe for slow apps — JVM takes 90s to start, liveness kills it at 30s, CrashLoopBackOff

❌ Readiness probe never fails — always returns 200, so broken Pods keep receiving traffic

❌ Probe endpoint does heavy computation — health check causes the very overload it's trying to detect

25 Init Containers

Init containers are specialized containers that run before app containers start. They run one at a time, in order, and each must complete successfully before the next begins.

Init Container Execution Flow

Key Rules

RuleDetail
Sequential executionInit containers run one-by-one. Init 2 doesn't start until Init 1 succeeds.
Must succeedIf any init container fails, Kubernetes retries it (subject to Pod restart policy). The Pod cannot proceed.
Run to completionEach init container must exit successfully (code 0). They are not long-running.
No probesInit containers do not support liveness, readiness, or startup probes.
Resource calculationInit container resources are calculated separately (MAX of all inits, not SUM).

26 Sidecar Containers (Native)

Since Kubernetes v1.29 (stable v1.31), native sidecar containers are init containers with restartPolicy: Always. They start during the init phase but run for the entire Pod lifetime.

initContainers:
- name: log-agent
  image: fluent-bit:latest
  restartPolicy: Always       # ← This single field makes it a sidecar

27 App Containers

App containers are the "normal" containers defined in spec.containers[]. They run your application code. All app containers in a Pod start simultaneously (in parallel), not sequentially. They are the core of what your Pod does.

28 Ephemeral Containers

Ephemeral containers are temporary debug containers you inject into a running Pod on-the-fly. They are NOT defined in the Pod spec — you add them using kubectl debug.

# Attach a debug container to a running pod
kubectl debug -it my-app --image=busybox --target=web

# Copy the pod and add a debug container
kubectl debug my-app -it --image=ubuntu --copy-to=debug-pod --share-processes

SRE Principle — Debug Without Disrupting

Ephemeral containers let you debug production Pods without restarting them. This preserves the exact state that caused the issue — memory, file handles, network connections. Use distroless or minimal images in production, then attach a full debug image (with curl, netcat, strace) only when needed.

29 Requests vs Limits

Requests

Guaranteed minimum. The scheduler uses requests to decide which node has enough room. The container is guaranteed to get at least this much.

If a node has 4 CPU and existing Pods request 3.5 CPU total, only Pods requesting ≤ 0.5 CPU can be scheduled there.

Limits

Hard ceiling. The container cannot use more than this. If it tries to exceed the memory limit, it gets OOM-killed. CPU is throttled (not killed).

Memory limit exceeded → container killed (exit 137). CPU limit exceeded → container throttled (slowed down, not killed).

31 Quality of Service (QoS) Classes

Kubernetes assigns a QoS class to each Pod based on resource configuration. This determines eviction priority when the node is under memory pressure.

Guaranteed
Last evicted · Highest priority

Every container has equal requests and limits for both CPU and memory. requests == limits.

Burstable
Middle priority

At least one container has requests or limits set, but they're not equal. Can use more than requested (burst).

BestEffort
First evicted · Lowest priority

No requests or limits set on any container. Gets whatever is leftover. Evicted first.

SRE Principle — Always Set Resource Requests

In production, every container must have at least resource requests. Without them, the scheduler guesses, nodes get overcommitted, and your critical Pods get evicted first (BestEffort). For mission-critical workloads, use Guaranteed QoS (requests = limits). For most services, Burstable is the sweet spot — set requests based on typical usage and limits based on peak.

32 Disruption Types

Voluntary Disruptions

Controlled — initiated by human or automation:

kubectl drain node for maintenance · Cluster upgrade · Deployment rolling update · Manual Pod deletion · Autoscaler scale-down · Cloud provider maintenance window

Protection: PodDisruptionBudgets (PDBs)

Involuntary Disruptions

Uncontrolled — unexpected failures:

Hardware failure · Kernel panic · Cloud VM termination · Network partition · OOM kill by node kernel · Power outage · Disk failure

Protection: Replicas + spread across nodes/zones + QoS classes

33 Pod Disruption Budgets (PDBs)

A PDB limits how many Pods in a workload can be simultaneously unavailable during voluntary disruptions.

apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: web-pdb
spec:
  # Option 1: Minimum Pods that must stay running
  minAvailable: 2
  # OR Option 2: Maximum Pods that can be down at once
  # maxUnavailable: 1
  # Can also use percentages: minAvailable: "50%"
  selector:
    matchLabels:
      app: web
FieldMeaningExample with 5 replicas
minAvailable: 3At least 3 Pods must be running at all timesAt most 2 can be disrupted at once
maxUnavailable: 1At most 1 Pod can be down at a time4 must always be running
minAvailable: "80%"At least 80% of Pods must be runningAt least 4 of 5 must be up

SRE Principle — Observability Layers

Layer 1 — Metrics: Prometheus + Grafana for real-time dashboards. Alert on golden signals and Pod-level metrics.

Layer 2 — Logs: Structured JSON logging to stdout/stderr, shipped via sidecar (Fluent Bit/Fluentd) to central store. Always include request ID, trace ID, Pod name.

Layer 3 — Traces: Distributed tracing (Jaeger/Tempo/Zipkin) to follow requests across Pods and services.

Layer 4 — Events: Kubernetes Events (scheduling, pulling, probing, killing) — export with kube-event-exporter to your logging backend.

Final SRE Wisdom

The goal of Pod operations isn't zero failures — it's fast, automated, observable recovery. Design Pods to crash safely (meaningful exit codes, graceful shutdown), detect failures quickly (probes, metrics, alerts), recover automatically (controllers, restart policies, replicas), and provide full visibility (structured logs, distributed traces, Kubernetes events). A well-instrumented Pod that restarts cleanly in 5 seconds is worth more than a fragile Pod that never crashes but silently corrupts data when it does.
