01 · Foundations

What a Deployment really is

A Deployment is a declarative controller for stateless Pods. You describe the desired end state — image, replica count, update rules — and the controller continuously reconciles reality toward it.

A Deployment never touches Pods directly. It owns ReplicaSets, and each ReplicaSet owns Pods. When you change the Pod template (most often the image tag), the Deployment creates a new ReplicaSet and shifts replicas from old to new according to the strategy you chose. The old ReplicaSet is kept (scaled to 0) so you can roll back instantly.

Deployment (desired state)
Active ReplicaSet + Pods
Old ReplicaSet (rollback target)
◆ Mental model

You change the template; the Deployment changes the ReplicaSets; the ReplicaSets change the Pods. The strategy field only controls how fast and how safely that hand-off from old RS to new RS happens.

▲ The arithmetic that matters

During a RollingUpdate the controller keeps Pods inside a window: at most replicas + maxSurge total, and at least replicas − maxUnavailable available. With replicas: 4, maxSurge: 1, maxUnavailable: 0 you never serve fewer than 4 ready Pods and never run more than 5 — the safest, slowest setting.

A new image triggers the loop: create surge Pods on the new ReplicaSet, wait for them to pass their readiness probe, then scale down an equal number of old Pods, and repeat until the new ReplicaSet holds all replicas.

04 · Native

Recreate

Terminate every old Pod first, then start the new ones. Simple, deterministic, and it guarantees only one version runs at a time — at the cost of a downtime gap.

Standard definition

A deployment strategy in which all running instances of the current version are terminated before any instances of the new version are created. Because the two versions never overlap, exactly one version exists at any time — at the cost of a window of full unavailability between them.

Definition & principle

The controller scales the old ReplicaSet to 0, waits for those Pods to fully terminate, and only then scales the new ReplicaSet up to replicas. There is a window where zero Pods serve traffic.

When it's the right call

  • Schema migrations that aren't backward-compatible. If v2 changes the DB shape so v1 can no longer run against it, you must not have both live at once.
  • Singletons. A workload that grabs an exclusive lock or writes to a single file can't tolerate two replicas overlapping.
  • Dev / batch jobs where a few seconds of downtime is irrelevant.
✕ Best practice

Never use Recreate on a customer-facing path like the Jahez menu or checkout API — every in-flight request fails during the gap. Reserve it for internal workers and migrations behind a maintenance flag.

Recreate rollout — menu-migrator v1 → v21/4
1

Steady state on v1

Two v1 Pods serve traffic. The Service endpoint list points at both.

2

Scale old ReplicaSet to 0

The controller deletes both v1 Pods at once. Endpoints empty out — this is the downtime gap. Requests now get connection-refused or a 503 from the Service.

3

Create new ReplicaSet Pods

Only after the old Pods are gone does the v2 ReplicaSet scale up. The Pods start, pull the image, and begin their readiness probe.

4

v2 Ready — gap closes

When both v2 Pods pass readiness they're added to Endpoints and traffic resumes. The whole window from step 2 to here is your outage.

▲ Note

Recreate has no rollingUpdate block — maxSurge/maxUnavailable are meaningless here. Adding them is a validation error.

Does it create all 20 pods in parallel?

A common assumption with replicas: 20 is that step 3 fires off 20 pod creations in one flat burst. It doesn't — the behaviour splits into two phases, and the create phase is deliberately throttled.

Phase 1 — terminate (parallel)

  • Old ReplicaSet scales to 0; all 20 old pods get SIGTERM at once.
  • Controller waits until every one has fully terminated.
  • This whole window is the downtime gap.

Phase 2 — create (slow-start batched)

  • New ReplicaSet scales to 20 in one scale op.
  • But the RS controller creates pods in exponential batches, not one flat burst.
  • Readiness does not gate creation (that's RollingUpdate, not this).

The ReplicaSet controller uses a slow-start safeguard (SlowStartInitialBatchSize = 1): it creates pods in concurrent batches that double on each success — and only proceeds to the next batch if the previous one's API creates succeeded.

slow-start batching · 20 replicascontroller internals
# the RS controller scales 0 → 20 in these concurrent batches:
batch 1 → 1  pod    # if it fails (bad image / webhook reject) → stop here, fail fast
batch 2 → 2  pods   # 3 created so far
batch 3 → 4  pods   # 7
batch 4 → 8  pods   # 15
batch 5 → 5  pods   # 20 (capped at the remainder)
# within a batch the creates are concurrent; batches run in quick succession
# — roughly one reconcile cycle, so it *looks* effectively parallel
◆ Why batch instead of one burst?

Defensive throttling. If the pod template is broken — unpullable image, an admission webhook that rejects it — the controller fails after batch 1 instead of spamming the API server with 20 doomed creates. It also keeps controller QPS within the client rate limits.

▲ "Created" ≠ "Running"

Even once all 20 Pod objects exist, they still have to be scheduled and have images pulled by each node's kubelet. On a small cluster you'll see them come up in waves because the nodes can't pull and start 20 containers at once — so actual startup parallelism is bounded by node capacity and image-pull throughput, not by the Deployment controller.

Memory footprint — requests vs limits vs usage

Two pods, each requesting 1 GB and capped at 3 GB. Because Recreate tears everything down before rebuilding, the reserved-memory and limit lines fall all the way to zero during the gap — the resource view makes the downtime literally visible as a cliff.

Limits — 3 GB/pod (cap)
Requests — 1 GB/pod (reserved on nodes)
Usage — 0.5–1.5 GB/pod (actual)

Reading it: No surge overhead, but a total drop to 0 GB reserved while the gap is open: the nodes momentarily reclaim all 2 GB of requests and 6 GB of limit headroom, then the new pods re-reserve it as they start cold (≈0.5 GB) and ramp up.

05 · Native

RollingUpdate

The default, and the right choice for almost every stateless service. New Pods come up before old ones go down, so capacity never dips below your floor and there is no downtime.

Standard definition

A deployment strategy that incrementally replaces instances of the old version with the new one, a controlled few at a time, keeping enough instances available throughout so the service stays up. The pace is bounded by maxSurge and maxUnavailable.

Definition & principle

The controller advances in small windows bounded by maxSurge (how far above replicas it may go) and maxUnavailable (how far below). Each window: bring up new Pods, wait for readiness, retire an equal number of old Pods. Repeat until the new ReplicaSet owns every replica.

maxSurge ↑

Extra Pods allowed above desired count. Higher = faster rollout, more peak resource use. Set as a count (1) or percent (25%).

maxUnavailable ↓

Pods allowed below desired count during the roll. 0 = never lose capacity (needs surge ≥ 1). Higher = faster but thinner.

The new Pod passes readiness and joins Endpoints. Now there are 5 Ready, so the controller retires one v1 to return to the window. Both versions briefly serve traffic together.

4

The loop repeats: another v2 comes up, more v1 drain. The mix shifts toward v2 one window at a time.

5

Last v1 draining

Four v2 are Ready and serving; the final v1 Pod terminates gracefully (drains its in-flight requests over terminationGracePeriodSeconds).

6

The new ReplicaSet owns all 4 replicas; the old one is scaled to 0 but kept for rollback. kubectl rollout status returns success.

▲ Why readiness is non-negotiable

The controller only advances when a new Pod reports Ready. Without a real readiness probe, K8s treats "container started" as "ready" and will drain old Pods while the new ones are still warming up — re-introducing the very downtime RollingUpdate exists to prevent.

"Ready" means ready to serve — not just running

When the rollout "waits for Ready", that's a specific Pod condition driven by the readinessProbe — the same signal that adds the Pod's IP to the Service. It is not "the container process started". Three states sit on top of each other, and the rollout paces off the strictest one:

StateWhat it meansDriven byEffect on rollout
RunningPID 1 is up (state: running). May still be connecting to Postgres / warming caches.kubelet started the containernone — controller ignores it
ReadyPod can serve traffic now; IP is added to the Service EndpointSlice.readinessProbe passingnecessary, not sufficient
AvailableHas been Ready continuously for minReadySeconds.Ready + minReadySecondsthis is what gates the next window

The maxSurge/maxUnavailable arithmetic is computed against availableReplicas, not raw Ready count — so an old Pod is only drained once a new one has been Ready and stayed Ready for minReadySeconds.

▲ Two gotchas

No readinessProbe → the container is considered ready the instant it's Running, so "Ready" collapses into "started" and the controller advances too early. minReadySeconds: 0 (the default) → no soak buffer, so a Pod that's Ready for one millisecond and then crashes still briefly counted as available. For a service like checkout, set minReadySeconds: 10–15 so a flapping new version can't race through the rollout.

06 · Advanced

Blue / Green

Run two complete environments side by side — blue (current) and green (next). All traffic stays on blue until green is fully deployed and verified, then you flip a single Service selector to cut over instantly. Rollback is the same flip in reverse.

Standard definition

A deployment strategy that maintains two production environments — one live (blue), one idle (green) — deploys the new version to the idle one, and switches all traffic over in a single atomic cut-over once it is verified. Rollback is the reverse switch.

Principle

  • Two Deployments with distinct version labels, both fully scaled.
  • One Service whose selector currently matches only blue.
  • Cutover = patch the selector to version: green. The endpoint list swaps atomically.

Strengths

  • Instant, atomic switch — no half-rolled state.
  • Instant rollback (flip back).
  • Green can be smoke-tested via a separate preview Service before cutover.

Costs

  • Needs 2× capacity during the overlap.
  • Long-lived connections / in-flight requests on blue are cut at the flip.
  • Stateful concerns (DB migrations) still need care.
Blue/Green cutover — menu-service v1 → v21/4
1

Blue (v1) live

Service selector = version: blue. Only v1 Pods are in Endpoints.

2

The green Deployment scales up fully. It's Ready but the production Service still selects blue, so green receives zero live traffic. Verify it through a private preview Service.

3

One kubectl patch changes the Service selector to version: green. Endpoints swap atomically — the next request lands on v2. This is the cutover.

4

After a soak period (kept around for instant rollback), scale blue to 0 or delete it. Green is now the new blue.

▲ The one-line model

Blue/Green is Recreate without the gap. It removes the downtime by running both environments at once, and the price is 2× capacity during the overlap plus instant rollback as a bonus.

✗ But you can't always substitute it

The reason to pick Recreate is often that two versions must never run together — an incompatible DB schema, an exclusive lock, a singleton. Blue/Green's overlap reintroduces exactly that: green and blue (or the new schema and the old pods) are live at the same time. If strict single-version is why you chose Recreate, Blue/Green will break it — so the "no gap" upgrade isn't free, it changes the safety guarantee.

Canary

Release the new version to a small slice of traffic first, watch its metrics, and only widen the slice once it proves healthy. The plain-K8s way controls the percentage through the ratio of replicas behind a shared Service.

Standard definition

A deployment strategy in which the new version is released to a small subset of traffic first and widened progressively only after it is observed to be healthy, limiting the blast radius of a bad release. Percentage is controlled by replica ratio or by weighted routing.

Principle (replica-ratio canary)

Both the stable and canary Deployments share a common label (app: menu) that the Service selects. Traffic splits roughly by Pod count: 8 stable + 2 canary ≈ 80/20. To shift weight you scale the Deployments; to promote you scale canary up and stable down.

◆ Precise % needs a mesh

Replica-ratio canary is coarse (you can't do 1% with 4 replicas). For exact weights, header stickiness, or automated metric-based promotion, use Argo Rollouts, Flagger, or Istio VirtualService weights — shown at the end of this section.

3

Stable 2 / canary 2. Half the fleet is v2. If the metrics held through the bake window, advance; if any breached threshold, scale canary back to 0 — that is the rollback.

4

Stable 1 / canary 3. Most traffic is on v2; this is the last checkpoint before full promotion. The shrinking stable set is your remaining safety margin.

5

Step 4 — 100%

Stable 0 / canary 4. Fully promoted — v2 is now the stable version (relabel it and the next release starts from here). A bad metric at any step would have scaled canary to 0 for an instant rollback.

Canary progression patterns

The slider near the top uses one shape — equal 25% steps. But the canary weight curve is itself a design choice. Below are the four common shapes, each as a full pattern: definition, principles, best practices, when to use, a cluster walkthrough, and one memory footprint. Stepped / staged

Definition

A canary progression that advances through a fixed set of equal traffic weights (25 → 50 → 75 → 100), pausing at each for a bake window and a metric gate before the next jump.

Principles

  • Equal weight increments, one checkpoint per step.
  • Bake + automated metric analysis at every stage.
  • Advance only on healthy signals; otherwise hold or roll back.
  • Rollback = shift weight back / scale canary to 0.

Best practices

  • Keep the steps few and even so each is easy to reason about.
  • Gate every step on the same metric set (error rate, p99, checkout success).
  • Make the bake long enough to cover at least one real traffic cycle.
  • Automate the steps with Argo Rollouts or Flagger, not a human clicking.
◆ When to use

The sensible default for most releases — when you want simple, auditable, predictable stages and moderate risk.

A/B testing

Route specific users — not a random percentage — to a variant based on a request attribute: an HTTP header, cookie, geo, or device. Used to test a product hypothesis (does the new menu layout lift basket size in Riyadh?), not just to de-risk a deploy.

Standard definition

A release strategy that serves two or more versions simultaneously to different user segments — chosen by request attributes such as headers, cookies, geography, or device — to compare their behaviour or business outcomes under controlled conditions. The split is deterministic per user, not random.

Principle

Canary asks "is v2 stable?" — A/B asks "is v2 better for this segment?" The split is deterministic per user (sticky), so the same customer always sees the same variant and you can measure conversion cleanly. This needs L7 routing — an Ingress controller (NGINX) or a mesh (Istio) — because Services route at L4 and can't read headers.

Routing cookbook — how the Ingress actually splits traffic

⚠ First, the NGINX vs Istio question

NGINX Ingress and Istio are two different L7 routers — you run one or the other, never both. NGINX Ingress is a controller you install in front of your Services; Istio is a service mesh. They express the same routing rule in different syntax. So in every case below, Option 1 and Option 2 are two ways to write the same split — pick the one that matches what your cluster already runs and apply only that one.

◆ The one idea behind all of them

Whichever router you use, it does the same thing: for each request it checks your match rules top to bottom, the first rule whose condition is true picks the backend, and anything unmatched falls to the default. Only the part of the request the condition looks at changes. The slider in each case below walks one request through that decision.

Aside · What the NGINX canary annotation actually is

A normal Ingress rule maps one host + path to exactly one backend — there is no built-in "if this header send to B, else A" inside a single Ingress. So NGINX splits traffic a different way: you keep your normal main Ingress (serving 100% to menu-a), then add a second Ingress for the same host and path carrying nginx.ingress.kubernetes.io/canary: "true". That flag tells the controller “this is not a competing route — it is an overlay that siphons off a slice.” The main keeps everything by default; the canary captures the matching slice and sends it to menu-b.

That is why every NGINX example here ships two Ingresses. Istio needs only one: a single VirtualService holds the match route and the default together, so one resource does the whole split.

A companion annotation decides which slice the canary captures — that condition is the whole game:

canary-by-header + -valueRequests whose header equals the valueA/B (segment)
canary-by-header-patternRequests whose header matches a regexA/B
canary-by-cookieRequests whose cookie value is alwaysA/B (sticky)
canary-weightA random percentage of all requestscanary release
◆ So why is it used for A/B testing?

The family is named after canary releases, but it is really a general traffic-splitting primitive. Set canary-weight and it sends a random % — that is a canary release. Set canary-by-header or canary-by-cookie and it targets a specific segment — that is A/B testing. Same machinery, different condition: weight de-risks a deploy; header/cookie compares variants for a chosen audience. Constraints: one canary Ingress per main Ingress (same host/path), and if several conditions are set NGINX honours them header → cookie → weight — first match wins.

Aside · How Istio does it in one VirtualService

Istio attaches routing to a host through a single VirtualService. Its http field is an ordered list of rules; each rule has an optional match (the condition) and a route (where matched traffic goes). The mesh walks the list top to bottom and the first rule whose match is true wins. A rule with no match is the catch-all default — so you put the experiment rule first and the default (→ menu-a) last. That is the entire split, in one object: no overlay, no second resource.

The same shape covers every case in the cookbook — only the match block changes (a headers match, a queryParams match, a uri.prefix, or a cookie regex). For a random split you drop match entirely and give one rule two destinations with weights.

◆ Why one resource is enough (vs NGINX’s two Ingresses)

An NGINX Ingress rule maps a host/path to a single backend, so a split needs the canary overlay on a second Ingress. A VirtualService rule already carries both the condition and the destination(s), and the list is ordered — so match, default, and weights all live in one place. You also get explicit precedence from the rule order, instead of NGINX’s fixed header → cookie → weight. The trade-off: this only works if you actually run a service mesh.

Shadow / mirror

Send a copy of real production traffic to the new version while users keep getting responses only from the old one. The shadow's responses are discarded. You test v2 against true production load and request shapes with zero user risk.

Standard definition

A deployment strategy in which a copy of live production traffic is mirrored to the new version in parallel with the current one, while only the current version's responses are returned to users. It validates the new version under real load and request shapes with zero user-facing risk.

Principle

  • The mesh duplicates each request: the primary goes to stable and its response returns to the user; the mirror goes to v2 and its response is thrown away.
  • Perfect for validating performance, memory, and error behaviour under genuine load before any user sees v2.
✕ The side-effect trap

Mirrored requests hit real code. If v2 writes to the production DB, charges Mada, or sends notifications, shadowing will double-execute those side effects. Shadow only against isolated dependencies — a shadow DB, a sandbox Mada key, and mocked notification sinks.

Memory footprint — requests vs limits vs usage

The shadow copy is sized like production to absorb 100% mirrored traffic, so reserved memory doubles to 8 GB during the test — and its usage is real, since it processes every live request.

Limits — 3 GB/pod (cap)
Requests — 1 GB/pod (reserved on nodes)
Usage — 0.5–1.5 GB/pod (actual)

Reading it: Same 2× reserved cost as Blue/Green (8 GB / 24 GB) for the mirror window. Shadow usage tracks production closely because it sees identical traffic — which is the whole point, and also why uncontrolled side-effects are dangerous.

Probes & rollout safety

Probes are what make a rollout safe rather than merely automated. They tell the controller when a Pod can take traffic and when it must be restarted.

ProbeAnswersOn failureRole in rollouts
readinessProbe"Can I serve now?"Removed from Endpoints (no restart)Gates rollout progress — controller waits for Ready.
livenessProbe"Am I deadlocked?"Container restartedRecovers stuck Pods; unrelated to rollout pacing.
startupProbe"Have I finished booting?"Killed if boot too slowProtects slow-start apps so liveness doesn't kill them early.
✕ The classic outage

No readiness probe → K8s marks a Pod "Ready" the instant the process starts → the controller drains old Pods while new ones are still connecting to Postgres → 503s for 10–20 seconds. A correct readinessProbe on a real dependency check prevents this entirely.

▲ Graceful shutdown

Pair readiness with a preStop hook (sleep 5) and a sane terminationGracePeriodSeconds. On SIGTERM the Pod is pulled from Endpoints first; the sleep gives in-flight requests and the kube-proxy/LB time to stop sending new ones before the process exits.

Rollback & revision history

Every template change creates a new revision (a retained ReplicaSet). Rollback re-points the Deployment at a previous revision — itself a rolling operation.

rollback.shoperate
# see the revision history
kubectl -n jahez-prod rollout history deploy/menu-service
# inspect what changed in revision 7
kubectl -n jahez-prod rollout history deploy/menu-service --revision=7
# roll back to the immediately previous revision
kubectl -n jahez-prod rollout undo deploy/menu-service
# roll back to a specific revision
kubectl -n jahez-prod rollout undo deploy/menu-service --to-revision=6
# abort a bad rollout in flight
kubectl -n jahez-prod rollout undo deploy/menu-service   # undo reverses the in-progress roll
◆ Keep history bounded

revisionHistoryLimit: 10 is sensible. Setting it to 0 deletes old ReplicaSets and removes your ability to rollout undo — don't.

13 · Operations

Best-practice checklist

✓ Always

  • Define a real readiness probe that checks dependencies.
  • Set resources.requests so the scheduler can place surge Pods.
  • Use maxUnavailable: 0 + maxSurge: 1 for customer-facing services.
  • Add a preStop hook + terminationGracePeriodSeconds.
  • Spread across zones with topologySpreadConstraints.
  • Set progressDeadlineSeconds so stuck rollouts fail loudly.

✗ Avoid

  • Recreate on anything users touch.
  • Rolling out with no readiness probe.
  • Shadowing traffic into shared stateful dependencies.
  • Blue/Green without budgeting 2× capacity.
  • Using :latest tags — pin immutable versions.
  • revisionHistoryLimit: 0 (kills rollback).
▲ Choosing a strategy — quick rule

Stateless service, normal release → RollingUpdate. Need instant cutover/rollback and can afford 2× → Blue/Green. De-risk by exposing a small % first → Canary. Testing a product hypothesis on a segment → A/B. Validating under real load with no user risk → Shadow. Incompatible schema / singleton → Recreate (behind a maintenance window).
