Volume 04 · Resource Management

The economics of your cluster.

A Kubernetes cluster is not unlimited compute — it is a finite pool of CPU cycles, memory pages, ephemeral storage, and devices that must be rationed, scheduled, throttled, evicted, and autoscaled. This is the SRE reference for how Kubernetes accounts for resources, how requests and limits drive every scheduling and runtime decision, how QoS classes determine who lives and who dies under pressure, and how HPA, VPA, the cluster autoscaler, and the node-level resource managers coordinate to keep your platform efficient, predictable, and cheap.

Chapter 01 · Foundations

Why resource management is non-negotiable

A Kubernetes cluster is a multi-tenant, time-sharing OS spread across many machines. Every Pod you schedule competes for the same finite pools: CPU time, RAM, ephemeral disk, PIDs, network bandwidth, and increasingly, GPUs, hugepages, and NUMA-aware resources. Without an explicit, declarative resource contract, the scheduler is guessing, the kubelet is reactive, and your platform is one noisy-neighbor away from a cascading outage.

💸 Cost

Unscoped Pods cause overprovisioning. Studies (Datadog, Sysdig, Densify) consistently report cluster utilization between 10%–30% across the industry. The cost gap between what you provision and what you use is the single largest line item on most Kubernetes cloud bills.

📉 Reliability

Pods without requests get scheduled onto already-saturated nodes. Pods without limits starve their neighbors. The kubelet evicts both in unpredictable orders. Resource contracts are how you make reliability deterministic instead of statistical.

🔭 Capacity planning

Requests are the unit of currency the scheduler uses. They define how much of a node is "spoken for", and therefore how many nodes you need. The cluster autoscaler, the bin-packer, your finance team — they all read requests, not actual usage.

💡 The SRE lens

Treat resources: as part of your service's SLO contract. The number of CPU shares and memory pages a Pod gets at p99 is a property of the platform, not luck. Right-sizing is not a one-time exercise — it's a continuous loop of measuring, recommending (VPA), and applying (rollouts) that closes the gap between request and reality.

Chapter 02 · Mental Model

The Kubernetes resource model, end-to-end

Resources in Kubernetes flow through five layers. Understanding where each decision happens is the difference between guessing and debugging.

The two questions every layer asks

Across all five layers, every decision boils down to two questions about every Pod:

1. What did you ask for? requests

Requests are a reservation. The scheduler subtracts your requests from node allocatable capacity to decide if you fit. The kubelet uses them to set cpu.weight (CPU share) and to compute the OOM score. They are the only signal autoscalers and capacity planners consult.

2. What's the ceiling? limits

Limits are a cap. CPU above the limit is throttled by the Linux CFS scheduler — your process keeps running, just slower. Memory above the limit is not throttled — the kernel's OOM killer terminates the container and the kubelet records OOMKilled.

⚠️ The asymmetry that bites everyone

CPU limits cause throttling. Memory limits cause death. This single sentence explains 80% of "why is my Pod restarting?" tickets. CPU throttling is recoverable and observable through container_cpu_cfs_throttled_seconds_total. Memory OOM is terminal — by the time you see it in kubectl describe pod, the process is already gone.

Chapter 03 · Units

CPU and memory units, exactly

Kubernetes resource units are precise. Misreading them is the source of subtle 1000× bugs. Memorize this table or learn it the hard way.

CPU

One Kubernetes CPU = one vCPU on a cloud VM = one hyperthread on bare metal. It is measured in cores (whole numbers) or millicores (m suffix, where 1000m = 1 CPU). CPU is compressible: when a Pod tries to exceed its limit, the kernel throttles it rather than killing it.

ValueMeaningSI equivalent
11 full CPU core1000m
0.5 or 500mHalf a CPU core500 millicores
100m10% of one CPU0.1 CPU
2.5 or 2500m2.5 CPU cores2500 millicores
0.0011 millicore (minimum)1m
🧠 How the kubelet translates CPU

requests.cpu becomes cpu.weight in cgroup v2 (relative share when contended). limits.cpu becomes cpu.max as a quota / period pair: a limit of 500m means the container can use 50ms of CPU every 100ms period, then it is throttled until the next period.

Memory

Memory is measured in bytes, with SI (powers of 10) or binary (powers of 2) suffixes. Always use binary suffixes (Mi, Gi) — decimal ones (M, G) silently undercount and break dashboards. Memory is incompressible: there is no "throttling" — exceed the limit and the kernel OOM-kills your process.

ValueBytesNotes
128Mi134,217,728128 × 2²⁰ — use this
128M128,000,000128 × 10⁶ — 4.7% smaller, avoid
1Gi1,073,741,8241 × 2³⁰
1G1,000,000,0001 × 10⁹
1Ti≈ 1.1 × 10¹²For storage / hugepages
500Ki512,000Rarely useful but valid

Other resources

Beyond CPU and memory, you can request and limit:

ephemeral-storage

Sum of writable container layer + emptyDir + logs. Measured in bytes. Exceeding the limit causes Pod eviction by the kubelet, not the kernel. Critical to set for log-heavy services.

hugepages-2Mi / hugepages-1Gi

Pre-allocated huge memory pages for low-latency workloads (databases, DPDK, JVM with -XX:+UseLargePages). Requests must equal limits — they cannot burst.

Extended resources

Anything advertised by a device plugin: nvidia.com/gpu, amd.com/gpu, intel.com/sgx. Always integer quantities, requests must equal limits.

Native devices (DRA)

Dynamic Resource Allocation (v1.32 GA) — replaces device plugins for complex devices. Pods reference ResourceClaims; the scheduler binds them at schedule time.

Chapter 04 · Pod Resources

Requests vs limits, fully decoded

Requests and limits look like a single concept with two numbers. They are not. They live in different decision loops, on different timescales, and produce wildly different failure modes.

Requests · the reservation

  • Used by the scheduler to filter feasible nodes
  • Set the cgroup cpu.weight (CPU share)
  • Set the QoS class together with limits
  • Determine OOM score adjustment
  • Counted against ResourceQuota
  • Drive cluster autoscaler decisions

Limits · the ceiling

  • Never used by the scheduler (it can't see them for placement)
  • Set cpu.max (CFS quota) — triggers throttling
  • Set memory.max — triggers OOM kill on excess
  • Sum of limits on a node may exceed node capacity (overcommit)
  • Counted against ResourceQuota when specified

Four valid configurations and what they mean

ConfigQoSBehaviorWhen to use
requests = limits Guaranteed Fixed slice. No bursting. Last to be evicted under pressure. Latency-critical services, databases, payment gateways
requests < limits Burstable Reserved minimum, can use spare capacity up to the limit. Most stateless services with bursty traffic (the 90% case)
only requests Burstable Reserved minimum, no CPU/mem ceiling. Risky for memory. JVM apps tuned with -Xmx, dev/test only
nothing specified BestEffort No reservation. First evicted. Scheduler treats requests as zero. Nothing in production. Period.

YAML: a complete, production-shaped Pod spec

deployment-jahez-checkout.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: jahez-checkout
  namespace: jahez-prod
  labels:
    app.kubernetes.io/name: checkout
    app.kubernetes.io/component: api
spec:
  replicas: 3
  selector:
    matchLabels: {app: checkout}
  template:
    metadata:
      labels: {app: checkout}
    spec:
      priorityClassName: jahez-critical
      terminationGracePeriodSeconds: 45
      containers:
      - name: app
        image: registry.jahez.local/checkout:1.42.0
        ports:
        - containerPort: 8080
        # --- Resource contract ---
        resources:
          requests:
            cpu: 500m            # reserve half a core
            memory: 512Mi         # reserve 512 MiB
            ephemeral-storage: 1Gi
          limits:
            cpu: "2"              # can burst to 2 cores
            memory: 1Gi           # hard cap → OOMKill if exceeded
            ephemeral-storage: 4Gi
        readinessProbe:
          httpGet: {path: /healthz/ready, port: 8080}
          periodSeconds: 5
          failureThreshold: 3
        livenessProbe:
          httpGet: {path: /healthz/live, port: 8080}
          periodSeconds: 10
          failureThreshold: 6
          initialDelaySeconds: 30
        env:
        - name: GOMEMLIMIT          # or JVM -XX:MaxRAMPercentage
          valueFrom:
            resourceFieldRef:
              resource: limits.memory
              divisor: 1
        - name: GOMAXPROCS
          valueFrom:
            resourceFieldRef:
              resource: limits.cpu
FieldWhat it does
priorityClassNameAssigns a PriorityClass. Higher-priority Pods can preempt lower ones when the cluster is full. jahez-critical means kube-scheduler may evict lower-priority Pods to make room for this one.
terminationGracePeriodSecondsTime the kubelet waits between SIGTERM and SIGKILL during eviction. Must exceed your slowest in-flight request — for a checkout API, 45s lets active payments complete.
requests.cpu: 500mThe scheduler subtracts 500m from a candidate node's allocatable.cpu. The kubelet writes cpu.weight ≈ 51 to the cgroup (the value scales 1m → 1024 weight units, normalized).
requests.memory: 512MiScheduler reservation. Kubelet does not set a min memory on the cgroup; it sets a soft "memory low" hint and adjusts the container's OOM score.
requests.ephemeral-storage: 1GiScheduler considers node's ephemeral storage capacity (writable layer + emptyDir + logs). Eviction kicks in if usage exceeds limits.ephemeral-storage.
limits.cpu: "2"CFS quota set to 200ms per 100ms period. Container is throttled — not killed — once it exceeds. Quoted as a string to avoid YAML parsing it as a number with different semantics.
limits.memory: 1GiHard cap. The Linux OOM killer terminates the container if its RSS+page cache exceeds 1 GiB. Pod restart counted; exit code 137.
limits.ephemeral-storage: 4GiKubelet evicts the Pod (not OOM) when total writable + emptyDir + logs exceed this. Watch kubelet_volume_stats_used_bytes.
GOMEMLIMIT via Downward APITells the Go runtime its memory ceiling so the garbage collector can act before the OOM killer does. Same idea as JVM -XX:MaxRAMPercentage=75 — make the runtime aware of its container limit.
GOMAXPROCS via Downward APICaps Go's P count to the CPU limit. Without this, Go reads /proc/cpuinfo and spawns one P per host core — wasteful in a containerized world.
✅ Idiom: make the runtime container-aware

The most common cause of OOM kills isn't a memory leak — it's a JVM or Go runtime that sized itself against the host's 64 GiB instead of the container's 1 GiB. Always wire GOMEMLIMIT, GOMAXPROCS, -XX:MaxRAMPercentage, or Node's --max-old-space-size from the Downward API. The runtime then makes its own decisions (GC, thread pool sizing) inside the right envelope.

Chapter 05 · Quality of Service

QoS classes: who lives, who dies, who waits

Kubernetes derives a Quality-of-Service class from your requests/limits settings. You don't set it directly — it's computed. This class drives every eviction decision the kubelet makes under node pressure and changes how the OOM killer prioritizes containers.

Guaranteed

Top tier

Every container in the Pod has both CPU and memory requests equal to limits. Pod gets a dedicated CPU pinning eligibility (with CPU Manager static policy) and is last in the OOM eviction order.

oom_score_adj = -997
Eviction rank: last
Burstable

Middle tier

At least one container has a request, but requests ≠ limits (or one is missing). This is where the bulk of production workloads land. Kubelet evicts these in order of how much their actual usage exceeds their request.

oom_score_adj = 2..999
Eviction rank: middle
BestEffort

Bottom tier

No requests or limits set anywhere in the Pod. Scheduler treats requests as zero, meaning it will happily pack the Pod onto a full node. First to be killed when the node feels pressure.

oom_score_adj = 1000
Eviction rank: first

Eviction order under memory pressure

Determining your Pod's QoS class

bash 
# Quick: just ask Kubernetes
$ kubectl get pod jahez-checkout-xyz -o jsonpath='{.status.qosClass}'
Guaranteed

# All Pods in a namespace with their class
$ kubectl get pods -n jahez-prod -o custom-columns=\
    NAME:.metadata.name,QOS:.status.qosClass

# Find every BestEffort pod cluster-wide — these are landmines
$ kubectl get pods -A -o jsonpath='{range .items[?(@.status.qosClass=="BestEffort")]}\
{.metadata.namespace}/{.metadata.name}{"\n"}{end}'
💡 When to choose Guaranteed

Use Guaranteed for: databases, payment processors, anything with strict tail-latency SLOs, anything you don't want the kubelet to second-guess. Use Burstable for: most stateless APIs — you want the option of cheap bursts. Never run anything important as BestEffort. A LimitRange (Chapter 8) eliminates BestEffort by default in your namespace.

Chapter 06 · The Hard Parts

OOM kills and CPU throttling, in mechanical detail

These are the two most common production incidents tied to resources. Both are observable, both are preventable, both are routinely misdiagnosed.

How an OOM kill actually happens

1
Allocation request

Container's process calls malloc / page fault

2
Cgroup check

Kernel compares cgroup memory usage vs memory.max

3
OOM trigger

Over limit → cgroup-level OOM killer invoked

4
Victim selection

Highest oom_score process in the cgroup gets SIGKILL

5
Kubelet observes

Reports exit code 137 → status OOMKilled

⚠️ "Working set" vs "RSS" — what the kubelet measures

The kubelet's eviction logic uses working set memory (container_memory_working_set_bytes) which is RSS plus active anonymous pages minus page cache. Your dashboards must use the same metric. RSS alone undercounts; memory_usage_bytes overcounts page cache. Working set is what the OOM killer sees.

How CPU throttling actually happens

The Linux CFS (Completely Fair Scheduler) enforces CPU limits using two cgroup parameters: cpu.cfs_period_us (default 100,000 = 100 ms) and cpu.cfs_quota_us (computed from your limit). A container with limits.cpu: 500m gets quota = 50,000: it can run for at most 50 ms in every 100 ms window. After that, every thread in the container is descheduled until the next period starts.

🧠 Why throttling at p99 is worse than it looks

A service with average CPU usage of 30% can still throttle badly at p99 if its work arrives in bursts. CFS doesn't average — it enforces per-period. A 200ms request that needs 1 full CPU for 100ms straight will throttle even though your dashboard says "we have plenty of headroom". Watch container_cpu_cfs_throttled_seconds_total / container_cpu_cfs_periods_total; anything above ~25% is a real latency problem.

The "remove CPU limits" debate

A common modern position (Tim Hockin, Buoyant, multiple SRE teams) is: set CPU requests, but no CPU limits. The reasoning: CPU is compressible, so the kernel will already share fairly via cpu.weight. Throttling on a node that has spare cycles is pure waste. Without limits, a Burstable Pod uses idle capacity for free.

Arguments for no CPU limits

  • Eliminates throttling at p99/p999 entirely
  • Uses cluster headroom that you've already paid for
  • cpu.weight still enforces fairness under contention
  • Aligns with how Linux schedulers were designed

Arguments for keeping CPU limits

  • Multi-tenant clusters where one team's bug shouldn't starve another
  • Predictable load tests — same wall-clock latency every run
  • Cost attribution: limits map cleanly to chargeback
  • Defense against runaway loops or thread leaks
⚖️ Pragmatic middle ground

For single-team production namespaces with priority classes already in place, drop CPU limits and trust cpu.weight. For multi-tenant platforms, batch jobs, or anything where one bad actor can ruin shared infrastructure, keep CPU limits but set them generously (4–8× the request). Memory limits should always be set — there's no analog of "throttling" for memory.

Chapter 07 · Modern API

Pod-level resources and in-place resize

Historically, every container in a Pod owned its own request/limit. With sidecars, Istio proxies, and Datadog agents now common, summing every container's request became awkward — you'd either over-reserve or have to coordinate among teams.

Two newer APIs change this:

Pod-level resources (alpha → beta)

You can now declare resources at the spec level, and the kubelet treats them as the Pod's total budget — any container in the Pod can use them.

pod-level-resources.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: jahez-payment-with-sidecar
spec:
  # Pod-level budget shared across all containers
  resources:
    requests:
      cpu: "2"
      memory: 2Gi
    limits:
      cpu: "4"
      memory: 4Gi

  containers:
  - name: app             # no per-container resources needed
    image: registry.jahez.local/payment:2.0
  - name: datadog-agent
    image: gcr.io/datadoghq/agent:7
    # Optionally still cap the sidecar specifically
    resources:
      limits:
        memory: 256Mi
FieldPurpose
spec.resources.requestsPod-wide reservation. The scheduler reserves this much on the node regardless of how it's split between containers at runtime.
spec.resources.limitsPod-wide cap. The kubelet creates a parent cgroup at this size and child cgroups for each container under it.
Per-container resourcesBecome sub-limits inside the Pod budget. Optional and additive — if not set, the container can use any of the Pod's headroom.
⚠️ Feature gate

Pod-level resources are still under the PodLevelResources feature gate (beta in v1.32, GA target later). Check your control plane and kubelet versions support it before relying on it in production. Container-level resources remain the universally supported pattern.

In-place resize without restart

Until v1.27, changing a Pod's resources required deleting and recreating the Pod (or the whole Deployment rollout). The new resize subresource (beta in v1.32, GA targeted in v1.33) lets you patch CPU and memory live, while the Pod keeps running. The kubelet updates cgroups; the container never restarts.

bash 
# Bump the checkout pod from 500m → 1500m CPU while it's serving traffic
$ kubectl patch pod jahez-checkout-7d4f --subresource resize --patch '
spec:
  containers:
  - name: app
    resources:
      requests:
        cpu: "1500m"
        memory: "1Gi"
      limits:
        cpu: "3"
        memory: "2Gi"
'

# Watch the resize succeed or fail
$ kubectl get pod jahez-checkout-7d4f -o jsonpath='{.status.resize}'
Proposed
$ kubectl get pod jahez-checkout-7d4f -o jsonpath='{.status.resize}'
InProgress

Each container declares a resizePolicy per resource saying whether the resize requires a restart:

resize-policy.yaml 
spec:
  containers:
  - name: app
    resources:
      requests: {cpu: 500m, memory: 512Mi}
      limits:   {cpu: "2",  memory: 1Gi}
    # Per-resource resize semantics
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired      # cgroup-only change, no restart
    - resourceName: memory
      restartPolicy: RestartContainer  # JVM heap won't grow — restart needed
✅ Why this is huge

In-place resize is the missing piece that makes VPA usable in production. Previously VPA had to evict your Pods to apply recommendations — a rolling restart for a sizing change. Now VPA can adjust live, which means continuous right-sizing without the blast-radius cost.

Chapter 08 · Namespace Governance

LimitRange — defaults and bounds per namespace

LimitRange is the cheapest reliability investment in any Kubernetes platform. It does three jobs at admission time:

  1. Default requests and limits when none are specified — kills BestEffort by accident.
  2. Bound requests and limits between a min and max — prevents both starvation and runaway requests.
  3. Constrain ratio of limit / request — caps how much overcommit you allow.
jahez-prod-limitrange.yaml 
apiVersion: v1
kind: LimitRange
metadata:
  name: jahez-prod-defaults
  namespace: jahez-prod
spec:
  limits:
  # --- Per-container rules ---
  - type: Container
    default:                  # applied if container has no limits
      cpu: "1"
      memory: 512Mi
    defaultRequest:           # applied if container has no requests
      cpu: 100m
      memory: 128Mi
    min:                      # requests below this are rejected
      cpu: 10m
      memory: 32Mi
    max:                      # limits above this are rejected
      cpu: "4"
      memory: 8Gi
    maxLimitRequestRatio:     # prevents 100x burstable cheating
      cpu: "10"             # limit can be at most 10× request
      memory: "4"           # memory cap stricter — 4×

  # --- Per-pod rules (sum of all containers) ---
  - type: Pod
    max:
      cpu: "8"
      memory: 16Gi

  # --- PVC bounds ---
  - type: PersistentVolumeClaim
    min: {storage: 1Gi}
    max: {storage: 500Gi}
FieldEffect
type: ContainerThe rules apply per container. Most LimitRanges target this.
type: PodThe rules apply to the sum across all containers in the Pod. Use max to prevent a single Pod from monopolizing a node.
type: PersistentVolumeClaimBounds PVC sizes. Stops developers from accidentally requesting 10 TiB.
defaultThe limit assigned if the container's spec omits it. Turns BestEffort into Burstable automatically.
defaultRequestThe request assigned if the spec omits it. Without this, scheduler treats request as 0 — same as BestEffort.
minHard floor. The API rejects Pods whose request falls below this. Useful to enforce "every workload reserves at least something."
maxHard ceiling on limits. Prevents accidentally requesting 200 CPUs on a 16-CPU cluster.
maxLimitRequestRatioCaps how aggressive your overcommit can be. cpu: 10 means a Pod with request 100m can have a limit at most of 1 core.
💡 SRE recipe: zero-BestEffort policy

Apply a LimitRange with both default and defaultRequest set to every production namespace. From that moment, the cluster is incapable of producing a BestEffort Pod by mistake — even Pods authored without a resources: block come out as Burstable with sensible numbers.

Chapter 09 · Namespace Governance

ResourceQuota — hard caps per namespace

Where LimitRange shapes individual Pods, ResourceQuota caps the aggregate of a whole namespace. It's the multi-tenant fairness primitive: a single team can't accidentally — or deliberately — consume more than its share. Once any quota dimension is full, new Pods in that namespace are rejected at admission.

jahez-team-quota.yaml 
apiVersion: v1
kind: ResourceQuota
metadata:
  name: jahez-prod-quota
  namespace: jahez-prod
spec:
  hard:
    # --- Compute aggregate ---
    requests.cpu: "100"            # namespace can reserve 100 CPUs total
    requests.memory: 200Gi
    limits.cpu: "200"              # overcommit allowed up to 2x
    limits.memory: 300Gi

    # --- Storage ---
    requests.storage: 5Ti
    persistentvolumeclaims: "50"

    # --- Object counts ---
    pods: "500"
    services: "50"
    services.loadbalancers: "5"   # each LB costs $$
    configmaps: "200"
    secrets: "200"

    # --- Extended resources ---
    requests.nvidia.com/gpu: "4"   # this team gets 4 GPUs max

  # --- Scoped quotas: apply only to matching Pods ---
  scopeSelector:
    matchExpressions:
    - scopeName: PriorityClass
      operator: In
      values: [jahez-batch]
FieldMeaning
requests.cpu / requests.memorySum of CPU/memory requests across all Pods in the namespace. The scheduler-relevant number — controls how many nodes the namespace effectively reserves.
limits.cpu / limits.memorySum of limits. Set higher than requests to allow overcommit; equal to enforce strict accounting.
requests.storageSum of spec.resources.requests.storage across all PVCs. Drives chargeback.
persistentvolumeclaimsMaximum PVC count. Useful when PVCs translate to cloud disks that cost money.
podsMaximum Pods. A safety valve against runaway controllers, e.g. a misconfigured Job that creates 10,000 Pods.
services.loadbalancersCaps cloud LoadBalancer Services. Each one is a paid cloud resource. Common to set to a single digit.
requests.nvidia.com/gpuExtended-resource quota. Same pattern works for any device-plugin-advertised resource.
scopeSelectorFilters which Pods are counted. Common scopes: BestEffort, NotBestEffort, Terminating, NotTerminating, PriorityClass, CrossNamespacePodAffinity.

The LimitRange ↔ ResourceQuota dance

ResourceQuota requires every Pod to have requests and limits set for any resource the quota tracks. If a quota constrains requests.cpu, every container's requests.cpu must be specified — otherwise the Pod is rejected. LimitRange fills the gaps by providing defaults. So in practice you deploy them as a pair:

  • ResourceQuota: "this namespace consumes at most N CPUs"
  • LimitRange: "every container has a default, so a missing field doesn't break admission"
bash 
# Inspect quota usage
$ kubectl describe resourcequota jahez-prod-quota -n jahez-prod
Resources         Used   Hard
requests.cpu      67     100
requests.memory   142Gi  200Gi
limits.cpu        145    200
pods              312    500

# Why was my pod rejected?
$ kubectl create -f bigpod.yaml
Error from server (Forbidden): pods "bigpod" is forbidden:
  exceeded quota: jahez-prod-quota, requested: requests.cpu=20,
  used: requests.cpu=85, limited: requests.cpu=100
Chapter 10 · Priority

PriorityClass, preemption, and disruption budgets

QoS classes decide who gets evicted under node pressure. PriorityClass decides who gets scheduled when the cluster is full — and who gets booted to make room. They are independent and complementary: a Burstable Pod with high priority can preempt a Guaranteed Pod with low priority.

priority-classes.yaml 
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: jahez-critical
value: 1000000
globalDefault: false
preemptionPolicy: PreemptLowerPriority
description: "Tier-0 workloads: payments, ordering, gateway"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: jahez-standard
value: 10000
globalDefault: true
preemptionPolicy: PreemptLowerPriority
description: "Default for all production workloads"
---
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: jahez-batch
value: 100
preemptionPolicy: Never          # waits patiently instead of evicting
description: "Nightly reports, log aggregation, ML training"
FieldEffect
valueInteger priority. Higher wins. Reserve the top range (≥ 2⁹) for system-critical classes (system-cluster-critical, system-node-critical). Pick wide gaps between tiers so future tiers fit in between.
globalDefault: trueIf set on a PriorityClass, any Pod that doesn't reference a class gets this one. Use exactly one default per cluster.
preemptionPolicy: PreemptLowerPriorityWhen this Pod can't schedule, the scheduler may evict lower-priority Pods. This is the default.
preemptionPolicy: NeverPod still gets its priority for scheduling order but won't trigger preemption. Right for batch workloads that can wait.

PodDisruptionBudget — the brake

Priority + preemption can kill your Pods. A PodDisruptionBudget is the contract you sign with the cluster saying "you may evict, but never below this floor." Critical for stateful workloads.

pdb.yaml 
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: jahez-checkout-pdb
  namespace: jahez-prod
spec:
  minAvailable: "75%"      # or absolute: minAvailable: 2
  # Alternative: maxUnavailable: 1
  selector:
    matchLabels:
      app: checkout
  # Optional: only protect Pods that pass the readiness gate
  unhealthyPodEvictionPolicy: AlwaysAllow
⚠️ PDBs only protect against voluntary disruption

A PDB blocks kubectl drain, cluster autoscaler scale-down, and node upgrades from breaching the floor. It does not protect against node crashes, kubelet OOM eviction, or hardware failure — those are involuntary. For full coverage, pair PDBs with anti-affinity (spread replicas across nodes) and topology spread constraints (across zones).

Chapter 11 · Autoscaling

The three axes of autoscaling

Kubernetes scales resources in three independent dimensions. They solve different problems and operate on different timescales. Mixing them up is the #1 source of "why didn't my cluster scale?" tickets.

↔ Horizontal (HPA)

Adds or removes Pod replicas based on observed metrics (CPU, memory, custom).

Timescale: seconds to minutes · Best for: stateless services under variable load

↕ Vertical (VPA)

Recommends — or sets — better request/limit values for each container based on history.

Timescale: hours to days · Best for: right-sizing, batch jobs, anything that can't scale horizontally

▦ Cluster (CA / Karpenter)

Adds or removes nodes when Pods can't be scheduled or nodes are underutilized.

Timescale: minutes · Best for: matching node capacity to demand from HPA

How they compose

🧠 The metric chain

Every autoscaler reads from a metrics pipeline: kubelet exposes cAdvisor metrics → metrics-server aggregates them → HPA / VPA read via the Metrics API. For custom or external metrics, you add prometheus-adapter (or KEDA, which gives you 60+ event sources). Without metrics-server installed, no autoscaler moves — yet this is the most-forgotten bootstrap step.

Chapter 12 · HPA

Horizontal Pod Autoscaler in depth

HPA is a controller that periodically queries metrics, computes a desired replica count, and patches a target workload's spec.replicas. It's the most-used autoscaler by a wide margin.

The formula

desiredReplicas = ceil( currentReplicas × ( currentMetric / desiredMetric ) )

Subject to minReplicas ≤ desired ≤ maxReplicas and the configured behavior (rate limits, stabilization windows).

If current CPU utilization is 80% and target is 50%, with 4 replicas: ceil(4 × 80 / 50) = 7 replicas. HPA scales up immediately; scale-down waits for the stabilization window (default 5 min) to avoid thrash.

A modern HPA spec (v2 API)

hpa-checkout.yaml 
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: jahez-checkout-hpa
  namespace: jahez-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: jahez-checkout
  minReplicas: 3
  maxReplicas: 50

  metrics:
  # --- Resource metric: CPU utilization vs request ---
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60

  # --- Resource metric: memory absolute value ---
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 700Mi

  # --- Custom metric from prometheus-adapter ---
  - type: Pods
    pods:
      metric:
        name: http_requests_per_second
      target:
        type: AverageValue
        averageValue: "500"

  # --- External metric: SQS queue depth, Kafka lag, etc. ---
  - type: External
    external:
      metric:
        name: kafka_consumergroup_lag
        selector:
          matchLabels: {topic: orders}
      target:
        type: AverageValue
        averageValue: "1000"

  # --- Scale behavior: tune speed and stability ---
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 30      # react fast to bursts
      policies:
      - type: Percent
        value: 100                          # can double replicas
        periodSeconds: 15
      - type: Pods
        value: 4                            # or add 4 pods, whichever bigger
        periodSeconds: 15
      selectPolicy: Max
    scaleDown:
      stabilizationWindowSeconds: 300     # wait 5 min before shrinking
      policies:
      - type: Percent
        value: 10                           # at most 10% per minute
        periodSeconds: 60
FieldWhat it does
scaleTargetRefThe workload to scale. Must implement the scale subresource — Deployment, ReplicaSet, StatefulSet, or any custom controller that does. Not DaemonSet (one Pod per node by design).
minReplicasThe floor — even at zero load, you keep this many Pods. Set to 2+ for any service with an SLO.
maxReplicasThe ceiling. Vital — without it, a metrics spike can stampede your cluster into OOM. Pair with a quota.
Resource · UtilizationPercentage of requests. averageUtilization: 60 means "scale up if avg CPU usage across Pods is over 60% of request." Requires the container to have CPU request set — without it, HPA can't compute a utilization ratio.
Resource · AverageValueAbsolute value per Pod. Use when you care about absolute memory headroom, not percentage.
Pods metricCustom metric reported by your application via the custom metrics API. The value is averaged across Pods.
External metricMetric not attached to a Pod — queue depth, RPS at the LB, business KPIs. KEDA is the canonical way to wire these.
behavior.scaleUp.stabilizationWindowTime the HPA waits before scaling up. Short for spiky workloads, longer for noisy metrics.
behavior.scaleUp.policiesRate limits. Each policy caps either by % or absolute number per period. selectPolicy: Max picks the fastest scaling rule (default), Min picks the slowest, Disabled blocks scaling in that direction.
behavior.scaleDown.stabilizationWindowLong is safer — avoids flapping when traffic dips. 5 min is a reasonable default; longer for traffic-spike-prone services.

💡 HPA gotchas to internalize
  • Requests are required. HPA computes utilization vs requests. A container without a CPU request gives HPA no denominator.
  • HPA cannot see startup spikes. New Pods report 0 CPU until past their initial readiness window — the rolling average smooths past those, but a sudden 10× burst can outrun the scale-up rate.
  • Don't combine CPU + memory as scale signals carelessly. HPA picks whichever metric demands more replicas. If memory grows monotonically (GC delay, leak, cache), the HPA will scale up forever — set a sane maxReplicas.
  • HPA + VPA on the same resource = oscillation. Don't let both manage CPU. Either VPA in Off recommendation-only mode, or VPA on memory while HPA owns CPU.
  • Predictive scaling. For workloads with known traffic curves (Jahez at lunch and dinner), KEDA + cron triggers or KEDA + Prometheus historical metrics beat reactive HPA.
Chapter 13 · VPA

Vertical Pod Autoscaler in depth

The VPA observes historical CPU and memory usage and recommends — or directly applies — better request/limit values. Where HPA changes the count, VPA changes the shape. It's most useful for workloads that don't scale horizontally well (singleton services, leader-elected pods, stateful stores) or for closing the gap between request and reality over time.

Three update modes

Off

Compute recommendations and expose them on the VPA object, but never apply. Use this as a perpetual right-sizing dashboard.

Initial

Set recommended values when the Pod is first created. Existing Pods are not touched. Safe for stateful workloads.

Auto / Recreate

Evict + recreate Pods (or, soon, in-place resize) to apply current recommendations. Powerful but disruptive — pair with a PDB.

vpa-checkout.yaml 
apiVersion: autoscaling.k8s.io/v1
kind: VerticalPodAutoscaler
metadata:
  name: jahez-checkout-vpa
  namespace: jahez-prod
spec:
  targetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: jahez-checkout

  updatePolicy:
    updateMode: Auto          # Off | Initial | Recreate | Auto
    minReplicas: 2            # won't evict if it would drop below 2

  resourcePolicy:
    containerPolicies:
    - containerName: app
      mode: Auto
      minAllowed:            # floor — recommendation will never go below
        cpu: 100m
        memory: 128Mi
      maxAllowed:            # ceiling — recommendation capped here
        cpu: "4"
        memory: 4Gi
      controlledResources: [cpu, memory]
      controlledValues: RequestsAndLimits   # also adjusts limits

    # Don't touch the sidecar's resources
    - containerName: istio-proxy
      mode: Off
FieldPurpose
targetRefThe workload to right-size. Same shape as HPA — must support the scale subresource.
updateModeDecides whether VPA only reports (Off), sets at creation (Initial), evicts and resizes (Recreate), or fully manages with in-place when possible (Auto).
minReplicas (under updatePolicy)Eviction-safety floor. VPA won't evict if fewer Pods would remain. Critical when combined with rolling updates.
containerPoliciesPer-container rules. You can opt individual containers out (set mode: Off) — common for proxy sidecars whose owners want stable sizes.
minAllowedRecommendation floor. Without this, VPA can recommend dangerously low values (e.g. for an idle service it never saw under load).
maxAllowedRecommendation ceiling. Caps blast radius if your usage history is contaminated by a single bad day.
controlledResourcesWhich resources VPA manages. You can have VPA own memory only and HPA own CPU — the most common safe combination.
controlledValuesRequestsAndLimits (proportional) or RequestsOnly. Be careful with RequestsAndLimits when you don't want limits to grow.

Reading recommendations

bash 
$ kubectl describe vpa jahez-checkout-vpa -n jahez-prod
...

    Container Name:  app
    Lower Bound:                  # can probably get away with this
      Cpu:     250m
      Memory:  340Mi
    Target:                       # the recommended value
      Cpu:     480m
      Memory:  612Mi
    Uncapped Target:              # ignoring maxAllowed
      Cpu:     480m
      Memory:  612Mi

⚠️ VPA + HPA on the same resource: don't

If both manage CPU on the same workload, they fight: HPA scales out because per-Pod CPU is high, which lowers the average → VPA observes low per-Pod usage → VPA shrinks requests → per-Pod CPU is high again → HPA scales out again. Pick a strategy: (a) HPA on CPU, VPA on memory only, (b) HPA on a custom metric (RPS, queue depth) and VPA on CPU+memory, or (c) VPA in Off mode purely as a sizing advisor.

Chapter 14 · Cluster Autoscaling

Cluster Autoscaler and Karpenter

Pod-level autoscalers are useless if there's nowhere to put the new Pods. Cluster autoscaling closes the loop by adding nodes when scheduling fails and removing nodes when they're underutilized. Two implementations dominate today.

Cluster Autoscaler (CA)

The original. Watches for unschedulable Pods, then scales up a configured node group (ASG, MIG, scale set). Conservative, battle-tested, and supported on every cloud. Node group choice is static — you decide shapes up-front.

Karpenter

Newer (AWS-born, now multi-cloud). Doesn't use node groups — instead picks instance types just-in-time from a NodePool of allowed shapes. Tighter bin-packing, faster provisioning, and significant cost wins. Increasingly the default for new AWS clusters.

How CA decides to scale up

1
Pending Pod

kube-scheduler can't place a Pod due to insufficient resources

2
CA notices

Loops every 10s checking for unschedulable Pods

3
Simulate node groups

For each group: would adding 1 node make the Pod fit?

4
Pick best

Expander chooses (random, most-pods, least-waste, price)

5
Provision

Calls cloud API to grow the ASG/MIG; new node joins cluster

How CA decides to scale down

  • A node has been underutilized for --scale-down-unneeded-time (default 10 min)
  • All Pods on it can be rescheduled elsewhere
  • No PDBs would be violated
  • No Pods carry the cluster-autoscaler.kubernetes.io/safe-to-evict: "false" annotation
  • The node isn't local-storage-only (no PVCs with local volumes)

Karpenter — provisioner-driven sizing

karpenter-nodepool.yaml 
apiVersion: karpenter.sh/v1
kind: NodePool
metadata:
  name: jahez-default
spec:
  template:
    spec:
      nodeClassRef:
        group: karpenter.k8s.aws
        kind: EC2NodeClass
        name: jahez-default
      requirements:
      - key: kubernetes.io/arch
        operator: In
        values: [amd64, arm64]
      - key: karpenter.k8s.aws/instance-category
        operator: In
        values: [m, c, r]
      - key: karpenter.k8s.aws/instance-generation
        operator: Gt
        values: ["5"]               # gen 6+ only
      - key: karpenter.sh/capacity-type
        operator: In
        values: [spot, on-demand]  # prefer spot
      expireAfter: 720h             # refresh nodes monthly
  limits:
    cpu: "1000"                   # hard cap across the NodePool
    memory: 4000Gi
  disruption:
    consolidationPolicy: WhenEmptyOrUnderutilized
    consolidateAfter: 30s
FieldEffect
requirementsConstraints Karpenter applies when picking an instance type. Wider sets = better bin-packing because Karpenter can choose from many shapes.
karpenter.sh/capacity-typespot can save 60–90% but is preemptible. Karpenter handles spot interruption gracefully (drains and replaces) — safer than Cluster Autoscaler with ASGs.
expireAfterForces nodes to roll periodically. Useful for security patches, kubelet upgrades, and to prevent slow memory leaks.
limitsTotal resources Karpenter is allowed to provision under this NodePool — your bill's hard ceiling.
consolidationPolicy: WhenEmptyOrUnderutilizedKarpenter continuously tries to repack Pods onto fewer/cheaper nodes. The biggest cost-saving feature.
consolidateAfter: 30sWait time before consolidating, so transient bursts don't trigger churn.
✅ Real-world cost impact

Teams that move from fixed ASGs + CA to Karpenter routinely report 30–50% compute cost reduction, mostly from consolidation (continuous bin-packing) and shape flexibility (picking a smaller, cheaper instance when traffic permits). The operational complexity is non-trivial — node lifecycles get more dynamic, so observability has to keep up.

Chapter 15 · Node-Level

Resource managers: pinning, NUMA, and topology

For most workloads, the kubelet's default behavior — share CPUs fairly, let the kernel decide where pages live — is correct. For latency-critical or NUMA-sensitive workloads (databases, AI inference, DPDK), Kubernetes exposes finer-grained managers that take CPU and memory placement decisions off the kernel scheduler and into deterministic policy.

Three node-level managers coordinate through the Topology Manager:

CPU Manager

Decides whether containers get shared CPU time (CFS-scheduled) or get exclusive pinned cores. static policy assigns whole CPUs to Guaranteed Pods that request integer CPU counts.

Memory Manager

Decides which NUMA node a Pod's memory is allocated from. Static policy aligns memory to the same NUMA node as the Pod's pinned CPUs, avoiding cross-NUMA traffic.

Device Manager

Discovers GPUs, FPGAs, SR-IOV NICs via device plugins. Assigns them to Pods with a device-aware affinity hint that Topology Manager uses to keep everything on the same socket.

Topology Manager — the coordinator

Topology Manager doesn't allocate anything itself. It collects hints from CPU, Memory, and Device managers, intersects them, and either approves placement or rejects the Pod. The result: a Pod whose CPU, RAM, and GPU all live on the same NUMA node — or no Pod at all.

Topology Manager policies

PolicyBehaviorUse for
noneDefault. No coordination. Each manager acts independently.General workloads
best-effortTry to align hints, but admit Pod even if alignment fails.NUMA-aware workloads that can tolerate misalignment
restrictedTry to align. If hints don't intersect, reject Pod (it goes Pending).Workloads that must be aligned or shouldn't run
single-numa-nodeAll hints must converge on exactly one NUMA node. Strictest.HPC, in-memory databases, ultra-low-latency apps

Configuring on the kubelet

These managers are kubelet-level settings, not Pod-level. You enable them via the KubeletConfiguration file (the canonical way) or via flags during the kubeadm bootstrap.

/var/lib/kubelet/config.yaml 
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration

# --- CPU Manager ---
cpuManagerPolicy: static            # or "none" (default)
cpuManagerReconcilePeriod: 10s
cpuManagerPolicyOptions:
  full-pcpus-only: "true"             # avoid SMT siblings to a non-pinned pod
  align-by-socket: "true"

# --- Memory Manager ---
memoryManagerPolicy: Static
reservedMemory:
- numaNode: 0
  limits:
    memory: 2Gi

# --- Topology Manager ---
topologyManagerPolicy: restricted
topologyManagerScope: container      # or "pod" — pod-scope is stricter

Pod requirements to get pinned CPUs

The static CPU Manager only pins CPUs for Pods that meet all of:

  • QoS class is Guaranteed (requests == limits for both CPU and memory)
  • CPU request is an integer number of CPUs (not 500m, not 1500m)
pinned-workload.yaml 
apiVersion: v1
kind: Pod
metadata:
  name: jahez-search-engine
spec:
  containers:
  - name: elasticsearch
    image: docker.elastic.co/elasticsearch/elasticsearch:8.13
    resources:
      requests:
        cpu: "4"           # integer CPU → pinning eligible
        memory: 16Gi
      limits:
        cpu: "4"           # equal to request → Guaranteed QoS
        memory: 16Gi
⚠️ Reservation cost

Pinned CPUs are taken out of the shared pool. If you pin too aggressively, other Burstable Pods on the node can starve. Use pinning surgically — for the 5% of workloads that genuinely benefit from it (databases, inference), not for every API.

Chapter 16 · Eviction

Node-pressure eviction

The kubelet runs a background eviction loop. When a node is running out of memory, disk, PIDs, or inodes, the kubelet kills Pods before the kernel does — gracefully, with SIGTERM, respecting termination grace, and reporting the reason. This is your last line of defense against the OOM killer reaping arbitrary processes.

Soft vs hard thresholds

Soft eviction

Triggered when a signal exceeds threshold for at least eviction-soft-grace-period. Sends SIGTERM, waits for terminationGracePeriodSeconds, then SIGKILL.

Use for: routine pressure handling, gives Pods time to drain.

Hard eviction

Triggered immediately when a signal exceeds threshold. Skips grace period — SIGKILL right away.

Use for: protecting node availability when pressure is acute.

Signals the kubelet watches

SignalWhat it measuresDefault hard threshold
memory.availableFree memory on the node (not counting page cache)< 100Mi
nodefs.availableFree space on kubelet's root filesystem< 10%
nodefs.inodesFreeFree inodes on root fs< 5%
imagefs.availableFree space where container images live (often same as nodefs)< 15%
imagefs.inodesFreeFree inodes for image filesystem< 5%
pid.availableFree PIDs on the nodevaries

Eviction ranking — who gets killed first

When the kubelet decides to evict, it ranks Pods using two keys, in order:

  1. QoS / Priority: BestEffort > Burstable > Guaranteed. Within Burstable, lower PriorityClass wins.
  2. Usage over request: The Pod whose actual usage most exceeds its request is killed first within a class.

This is why setting honest requests matters even for Guaranteed Pods: if every Guaranteed Pod has identical requests, kubelet falls back to actual usage to decide.

Configuring eviction

kubelet eviction config 
apiVersion: kubelet.config.k8s.io/v1beta1
kind: KubeletConfiguration

evictionHard:
  memory.available: "200Mi"
  nodefs.available: "5%"
  imagefs.available: "10%"

evictionSoft:
  memory.available: "500Mi"
  nodefs.available: "15%"

evictionSoftGracePeriod:
  memory.available: "1m30s"
  nodefs.available: "2m"

evictionMaxPodGracePeriod: 60   # caps a Pod's terminationGracePeriodSeconds
evictionMinimumReclaim:            # keep reclaiming until we're past threshold + this
  memory.available: "100Mi"
  nodefs.available: "500Mi"
🧠 Soft eviction is what you want

Hard eviction with default thresholds means a sudden spike kills Pods instantly with no graceful shutdown — your readiness gate doesn't unhook from the LB in time, and clients see 5xx. Configure a generous soft threshold with a 60–120s grace period. Hard thresholds remain as a backstop, but soft should fire first in normal operation.

Chapter 17 · Node-Level

System-reserved and node allocatable

Not every byte of a node's RAM is available for Pods. The kubelet itself, the container runtime, system daemons (sshd, journald, your DaemonSets), and the kernel all need resources. If you don't reserve for them, your "user" Pods will steal from them under pressure — and that's how nodes go NotReady.

💡 Cloud defaults are often wrong

EKS, GKE, and AKS each reserve different amounts by default. EKS's formula reserves memory based on node size; GKE has a stepped function; AKS reserves a flat amount. Check your managed cluster's docs and compare against the workloads you're running. Underestimating system-reserved on small (4 GiB) nodes means the kubelet itself can get OOM'd by a runaway Pod — and a node going NotReady is far worse than a Pod crash-looping.

18 SRE Playbook · Right-sizing

Right-sizing as a closed loop

Right-sizing isn't a one-shot decision you make at deployment time. It's a continuous loop: measure → recommend → apply → re-measure. Workloads change. Traffic patterns shift with Ramadan, Black Friday, salary day. Code changes alter allocation patterns. A service that needed 2 GiB last quarter might need 800 MiB today after a JVM upgrade — or 4 GiB after a new feature shipped.

1
Measure
Collect container_cpu_usage_seconds_total, container_memory_working_set_bytes, and container_cpu_cfs_throttled_seconds_total over a representative window (7–14 days minimum, covering weekly cycles).
→
2
Recommend
Compute percentile-based recommendations. VPA in Off mode does this for free. Rule of thumb: requests = p50–p75 of historical usage; limits = p99 × 1.2–1.5 safety margin.
→
3
Apply
Roll out via your normal deploy pipeline. Use in-place resize for long-running stateful services where a restart is expensive. Watch the rollout — a too-aggressive shrink causes immediate OOMs.
→
4
Verify
Check error rate, p99 latency, throttle rate, and OOM count for 48h. If clean, lock it in. If not, roll back and widen the window.

The four metrics that actually matter

MetricWhat it tells youAction
container_memory_working_set_bytes Live memory the kernel won't reclaim. This is what gets compared against the limit for OOM decisions. Set requests.memory at p75 of this; limits.memory at p99 × 1.3.
rate(container_cpu_usage_seconds_total[5m]) Actual CPU consumption in cores. A pod requesting 500m but averaging 80m is overprovisioned by 6×. Set requests.cpu at p75 of usage. Limits — see chapter 6.
rate(container_cpu_cfs_throttled_seconds_total[5m]) ÷ rate(container_cpu_cfs_periods_total[5m]) Throttle ratio. If >5%, the workload is being squeezed during bursts even though average usage looks fine. Raise the CPU limit, or remove it entirely if the pod is Guaranteed-class and you trust the node sizing.
kube_pod_container_status_terminated_reason{reason="OOMKilled"} The blunt signal. If this counter increments, the memory limit was wrong — full stop. Bump the limit immediately, then investigate whether it's a leak or a legitimate working-set growth.

Slack: how much headroom to leave

Stateless HTTP service
req = p75 · lim = p99 × 1.3

HPA absorbs traffic spikes. Keep limits tight; the autoscaler is your overflow valve.

JVM / GC'd runtime
req = heap × 1.4 · lim = req × 1.2

Account for metaspace, off-heap buffers, thread stacks. Wire -XX:MaxRAMPercentage=75 against the limit.

Batch / cron job
req = p95 · lim = p99 × 1.5

One-shot work has no HPA safety net. Over-provision slightly — a failed batch costs more than wasted RAM for 10 minutes.

Stateful (DB, cache)
req = peak · lim = req (Guaranteed)

Pin to Guaranteed QoS. These pods are the last thing you want evicted under pressure.

✅ The Jahez sizing review cadence

Run VPA in Off (advisor) mode against every production workload. Surface the recommendations weekly in a dashboard. Quarterly, review services whose recommendation diverges from the actual request by more than 30% — those are the ones leaking money (over-provisioned) or risking SEV1s (under-provisioned).

19 SRE Playbook · Patterns

Idiomatic patterns & anti-patterns

Most resource incidents trace back to one of a small set of recurring mistakes. Here are the patterns that work — and the anti-patterns that look reasonable until they take you down at 03:00.

Patterns that work

✅ LimitRange + ResourceQuota as a pair

Always set them together at the namespace level. LimitRange ensures every pod gets some request even if the author forgot. ResourceQuota caps the blast radius of any single team or namespace. Without LimitRange, a forgotten request lets a BestEffort pod through; without ResourceQuota, a single namespace can starve the cluster.

✅ Runtime-aware env vars via Downward API

For any GC'd or pooled runtime (JVM, Go, Node, .NET), wire the limit into the runtime: GOMEMLIMIT, -XX:MaxRAMPercentage, --max-old-space-size, DOTNET_GCHeapHardLimit. Skipping this is why your "1 GiB pod" suddenly OOMs at 950 MiB — the GC didn't know there was a ceiling and never aggressively collected.

✅ CPU requests yes, CPU limits maybe

For latency-sensitive services on dedicated node pools where you trust your sizing, omitting CPU limits lets pods burst into spare capacity and is generally safe. For multi-tenant clusters, noisy-neighbor workloads, or shared node pools where one runaway pod can starve others, keep CPU limits. The right answer depends on who else lives on the node.

✅ HPA + PDB + PriorityClass as a trio

Every production Deployment needs all three. HPA scales for load. PDB protects from drain-induced outages. PriorityClass ensures you don't get preempted by a non-critical batch job. Missing any one of these creates a class of incident that's "obviously avoidable" in the postmortem.

Anti-patterns that bite

🚨 BestEffort pods in production

If a pod has no resource requests, it's BestEffort — first to be evicted, last to be scheduled fairly. The "I don't know what to set" excuse leads to outages. If you genuinely don't know, set conservative requests (100m CPU, 128Mi RAM) and let VPA recommend better values. Never ship a production workload with empty resources:.

🚨 limits.memory == requests.memory with no headroom

This sounds disciplined — "exact sizing!" — but it leaves zero room for GC overhead, cache warmup, or transient allocations. The pod becomes Guaranteed QoS (good) but OOMs on the first usage spike (bad). For most runtimes, allow at least 20% headroom between request and limit unless you've measured the working set extensively and know it's flat.

🚨 HPA with minReplicas: 1

A single replica means zero redundancy during rollouts, node drains, or AZ failures. The HPA will eventually scale up, but "eventually" can be 60s of total outage. Set minReplicas: 2 minimum for any user-facing service, and pair with a PodDisruptionBudget of minAvailable: 1.

🚨 HPA on memory for GC'd languages

JVM and Go services hold onto memory after GC. Memory usage looks flat or monotonically increasing — it doesn't drop when load decreases. An HPA targeting memory will scale up under load but never scale back down. Use CPU or a custom metric (RPS, queue depth, p95 latency) instead.

🚨 HPA + VPA on the same resource axis

If HPA scales replicas on CPU, VPA must not also be in Auto mode on CPU — they fight. VPA shrinks the per-pod request → HPA thinks usage ratio went up → adds replicas → VPA shrinks again. Use VPA Off mode for recommendations only, or VPA on memory while HPA handles CPU.

⚠️ Quota without LimitRange

ResourceQuota requires every pod to declare requests and limits — but it doesn't provide defaults. Without LimitRange, every developer must remember to set resources on every pod, every time. They won't. CI passes; kubectl apply fails with "must specify requests.cpu" two minutes before the demo.

20 SRE Playbook · Troubleshooting

Resource-related failure modes & how to diagnose them

Five symptoms cover ~90% of resource-related incidents. Each has a distinct signature in kubectl describe, metrics, and pod events. Knowing which one you're looking at saves the first 15 minutes of an incident.

1. OOMKilled

$ kubectl describe pod jahez-checkout-7d4f-abc12 
Last State:    Terminated
  Reason:      OOMKilled
  Exit Code:   137
  Started:     Wed, 20 May 2026 14:22:11 +0300
  Finished:    Wed, 20 May 2026 14:47:33 +0300

Exit code 137 = SIGKILL by OOM killer. The container exceeded its memory limit. Three possibilities, in order of likelihood: (a) limit is too low for legitimate working set — bump it 30% and re-measure; (b) a memory leak — check container_memory_working_set_bytes over the previous 24h; a steadily climbing line is a leak; (c) a one-shot allocation spike (large file upload, batch query result) — cap the spike at the application layer.

2. CPU throttling without high CPU

Symptom: p99 latency spikes, but kubectl top pod shows CPU well under the limit. The trap: top shows averaged usage; throttling happens at the 100ms CFS period boundary.

PromQL — throttle ratio 
# Throttle ratio per pod over 5m. Anything >0.05 (5%) is worth fixing.
sum by (pod) (rate(container_cpu_cfs_throttled_seconds_total[5m]))
  /
sum by (pod) (rate(container_cpu_cfs_periods_total[5m]))

Fix: raise the CPU limit, or remove it. See chapter 6 for the full debate.

3. Pending pod — "0/X nodes available"

$ kubectl describe pod <pending-pod> 
Events:
  Type     Reason            Age   From                Message
  ----     ------            ----  ----                -------
  Warning  FailedScheduling  2m    default-scheduler   0/12 nodes are available:
    8 Insufficient cpu, 4 Insufficient memory.

The request is larger than any single node's free allocatable. Options: (a) reduce the request if it's over-sized; (b) let Cluster Autoscaler / Karpenter add a bigger node — check its logs to see why it didn't; (c) if the pod legitimately needs more than fits, split the workload or move to a node pool with larger instances.

4. Evicted pod

$ kubectl get pod <evicted-pod> -o yaml 
status:
  phase: Failed
  reason: Evicted
  message: The node was low on resource: memory.
           Container app was using 1843200Ki, which exceeds its request of 1Gi.

Kubelet evicted this pod under node-pressure (chapter 16). The fix depends on the QoS class: if it was Burstable and exceeded its request, raise the request. If it was BestEffort, give it requests. If it was Guaranteed and still got evicted, your system-reserved is too low and the kubelet itself was at risk — bump system-reserved and kube-reserved.

5. Quota rejection at apply time

$ kubectl apply -f deployment.yaml 
Error from server (Forbidden): error when creating "deployment.yaml":
  pods "jahez-search-engine-abc" is forbidden: exceeded quota: jahez-prod-quota,
  requested: requests.memory=4Gi, used: requests.memory=28Gi, limited: requests.memory=30Gi

Check current usage with kubectl describe resourcequota -n jahez-prod. Either reduce the new workload's request, free space by right-sizing something else, or raise the quota with platform-team approval. Don't just bump the quota reflexively — it exists for a reason.

21 SRE Playbook · Production checklist

The pre-flight checklist

Before any workload is considered production-ready at Jahez (or anywhere serious), every item below should be a green checkbox. Treat this as a code-review checklist for Deployment YAML.

Namespace level

✓
LimitRange exists — defaults and max/min for CPU and memory per container, plus a maxLimitRequestRatio to prevent oversubscription.
✓
ResourceQuota exists — caps total requests/limits, PVCs, and object counts. Includes a scope for non-terminating pods so batch jobs don't consume the production budget.
✓
NetworkPolicy default-deny — unrelated to resources, but shipped at the same time as the LimitRange/Quota pair when bootstrapping a namespace.

Per workload

✓
Every container has explicit requests and limits for CPU and memory. No reliance on LimitRange defaults — they're a safety net, not a strategy.
✓
QoS class is intentional — Guaranteed for stateful and latency-critical paths; Burstable for stateless services with HPA; BestEffort only for genuinely throwaway work.
✓
Runtime memory flag wired to the limit — GOMEMLIMIT, -XX:MaxRAMPercentage, --max-old-space-size, DOTNET_GCHeapHardLimit — sourced from the Downward API, not hardcoded.
✓
Liveness, readiness, and startup probes — with timeouts that account for cold-start and GC pauses. A 1-second timeout on a JVM service that does a 4-second startup GC is an outage waiting to happen.
✓
PriorityClass assigned — jahez-critical for payments/checkout, jahez-standard for most services, jahez-batch for nightly jobs.
✓
PodDisruptionBudget — minAvailable set to at least 1, ideally maxUnavailable: 25% for larger Deployments.
✓
HPA configured — minReplicas ≥ 2 for user-facing services; maxReplicas sized against quota and node capacity; scale-down stabilization window ≥ 5 minutes.
✓
Topology spread constraints — pods spread across zones and nodes so a single-AZ failure doesn't take the service down.
✓
VPA in Off mode — collecting recommendations for the weekly right-sizing review.

Cluster level

✓
system-reserved and kube-reserved set explicitly on every node — not relying on the cloud provider's default formula. Sized against observed kubelet + daemonset usage.
✓
Eviction thresholds tuned — soft thresholds with grace periods give workloads a chance to exit cleanly before hard thresholds bite.
✓
Cluster Autoscaler / Karpenter configured with sensible node-pool limits. Without an upper bound, a runaway HPA + a permissive autoscaler can burn six figures in an afternoon.
✓
Topology Manager policy: restricted on nodes running NUMA-sensitive workloads (databases, ML inference).
✓
Cost / efficiency dashboard — requested vs allocated vs actual usage per namespace and per workload. Without this, you have no signal that anything needs right-sizing.
💡 Make it a policy, not a vibe

Encode the checklist in Kyverno or OPA Gatekeeper policies. A pod without resources.requests shouldn't be a code-review catch — it should be rejected by admission. The checklist exists so the policy doesn't have to enumerate every rule; the policy exists so the checklist doesn't have to be remembered.
