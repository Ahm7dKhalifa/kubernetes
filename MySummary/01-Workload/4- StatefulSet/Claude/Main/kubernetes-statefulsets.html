Kubernetes StatefulSets

The complete guide — stable identity, ordered operations, persistent storage, headless services, and update strategies. Interactive step-by-step workflows.

01 What Is a StatefulSet & Why?

Definition — StatefulSetA StatefulSet manages stateful applications by providing stable, unique Pod identities (name + hostname + DNS), persistent storage (each Pod gets its own PVC that survives restarts), and ordered operations (Pods are created, deleted, and updated in a predictable sequence). It's the workload controller for databases, message queues, and any app that needs to remember who it is.
Definition — Stateful vs StatelessStateless: any Pod can handle any request, Pods are interchangeable (web servers, APIs). Use Deployments.
Stateful: each Pod has a unique role or data. Losing a Pod's identity or storage would break the app (databases, Kafka, ZooKeeper, Elasticsearch). Use StatefulSets.
Use CaseWhy StatefulSet?
MySQL/PostgreSQL replicasPrimary needs stable identity. Each replica has its own data volume.
MongoDB replica setMembers discover each other by stable DNS name.
Kafka brokersEach broker has a unique ID and persistent log storage.
ZooKeeper ensembleOrdered startup required. Stable hostnames for leader election.
Elasticsearch clusterEach node has persistent data, unique node name.
Redis clusterSlot assignment tied to node identity.
Consul/etcdCluster membership requires stable network addresses.
Analogy

A Deployment manages cattle — identical, replaceable, numbered by random hash. A StatefulSet manages pets — each has a name (mysql-0, mysql-1, mysql-2), its own bedroom (PVC), and a fixed address (DNS). If a pet dies, it's replaced with the same name and same room — not a random new one.

Pod Naming — The Critical Difference
Deployment Pods (random, disposable):
web-6d4f5b-abc12 web-6d4f5b-def34 web-6d4f5b-ghi56
If Pod dies → replacement gets NEW random name. App can't rely on names.

StatefulSet Pods (ordered, persistent identity):
mysql-0 mysql-1 mysql-2
If mysql-1 dies → replacement is ALSO named mysql-1. Same name, same DNS, same PVC.
Storage — Shared vs Dedicated
Deployment: All Pods share 1 PVC (or use ephemeral emptyDir)
Pod A Pod B Pod C → all mount → PVC-shared

StatefulSet: Each Pod gets its own dedicated PVC
mysql-0 → data-mysql-0
mysql-1 → data-mysql-1
mysql-2 → data-mysql-2
If mysql-1 dies and restarts → it re-mounts data-mysql-1. Data preserved!
Ordering — Sequential vs Parallel
Deployment scale up (parallel):
Pod A Pod B Pod C ← all created simultaneously

StatefulSet scale up (ordered):
mysql-0 created → must be Ready ✓
then → mysql-1 created → must be Ready ✓
then → mysql-2 created → must be Ready ✓

Why? Databases need the primary (index 0) up first. Replicas join only after primary is ready.

03 The 3 Guarantees ▶

① Stable Identity
② Stable Storage
③ Ordered Operations
Guarantee 1 — Stable, Unique Network Identity
DefinitionEach Pod gets a predictable name ({statefulset}-{ordinal}), a stable hostname (same after restart), and a unique DNS record ({pod}.{service}.{namespace}.svc.cluster.local). These never change for the lifetime of the StatefulSet.
StatefulSet: mysql (replicas: 3)

mysql-0 → hostname: mysql-0 → DNS: mysql-0.mysql-svc.default.svc.cluster.local
mysql-1 → hostname: mysql-1 → DNS: mysql-1.mysql-svc.default.svc.cluster.local
mysql-2 → hostname: mysql-2 → DNS: mysql-2.mysql-svc.default.svc.cluster.local

If mysql-1 crashes → new mysql-1 gets SAME name, SAME hostname, SAME DNS.
Guarantee 2 — Stable, Persistent Storage
DefinitionEach Pod gets its own PersistentVolumeClaim auto-created from volumeClaimTemplates. The PVC name is {volumeClaimTemplate}-{pod}. When a Pod is deleted and recreated, it re-mounts the same PVC — data is preserved.
mysql-0 → data-mysql-0 (10Gi) ← created automatically
mysql-1 → data-mysql-1 (10Gi)
mysql-2 → data-mysql-2 (10Gi)

mysql-1 dies → new mysql-1 created → re-mounts data-mysql-1
All data intact. No data loss. PVCs are NOT deleted when Pods are deleted.
Guarantee 3 — Ordered, Graceful Operations
DefinitionCreation: Pods are created in order: 0, 1, 2. Each must be Running+Ready before the next starts.
Deletion: Pods are deleted in reverse: 2, 1, 0.
Update: Pods are updated in reverse: 2, 1, 0 (newest first).
Scale 0→3: 0 → ready → 1 → ready → 2

Scale 3→1: 2 deleted → gone → 1 deleted

Update: 2 updated → ready → 1 updated → ready → 0 updated

Why reverse for update/delete? Index 0 is usually the primary/leader. It should be the last to go down.

05 Headless Service ▶

Definition — Headless ServiceA Service with clusterIP: None. Instead of load-balancing to a single VIP, DNS returns the individual Pod IPs. Each Pod gets its own DNS A record. This is required for StatefulSets — it's how Pods get their stable DNS names.
Normal vs Headless
Headless DNS
YAML
Normal Service vs Headless Service
Normal Service (clusterIP: auto):
web-svc (10.96.0.15) → load balance → Pod A / Pod B / Pod C
DNS: web-svc.default.svc → 10.96.0.15 (single VIP)

Headless Service (clusterIP: None):
mysql-svc (no ClusterIP!)
DNS: mysql-svc.default.svc → 10.244.1.5, 10.244.2.8, 10.244.3.2 (all Pod IPs!)
DNS: mysql-0.mysql-svc.default.svc → 10.244.1.5 (specific Pod!)
DNS: mysql-1.mysql-svc.default.svc → 10.244.2.8 (specific Pod!)
Per-Pod DNS Records
Full DNS format:
{pod-name}.{service-name}.{namespace}.svc.cluster.local

mysql-0 → mysql-0.mysql-svc.default.svc.cluster.local
mysql-1 → mysql-1.mysql-svc.default.svc.cluster.local
mysql-2 → mysql-2.mysql-svc.default.svc.cluster.local

Apps use these DNS names to connect to SPECIFIC Pods (e.g., always connect to mysql-0 for writes).
Headless Service YAML
apiVersion: v1
kind: Service
metadata:
  name: mysql-svc                 # Must match StatefulSet's serviceName
spec:
  clusterIP: None                 # ← THIS makes it headless
  selector:
    app: mysql
  ports:
  - port: 3306
    name: mysql
CriticalThe headless Service MUST be created BEFORE the StatefulSet. The Service name must match spec.serviceName in the StatefulSet. Without it, Pods won't get DNS names.

# Short form (within same namespace):

mongodb://mongo-0.mongo-svc:27017,mongo-1.mongo-svc:27017,mongo-2.mongo-svc:27017/mydb?replicaSet=rs0

bootstrap.servers=kafka-0.kafka-svc:9092,kafka-1.kafka-svc:9092,kafka-2.kafka-svc:9092
SRE Principle

Always use DNS names, never Pod IPs. Pod IPs change on restart. DNS names are stable and automatically point to the new IP. This is the entire point of StatefulSets + Headless Services.

07 VolumeClaimTemplates ▶

Definition — volumeClaimTemplatesA template for creating PVCs automatically. For each Pod, the StatefulSet controller creates a PVC named {volumeClaimTemplate.name}-{pod-name}. The PVC is bound to a PersistentVolume and mounted into the Pod. PVCs are NOT deleted when Pods are deleted — data survives.
How it works
Naming
YAML
Auto-PVC creation for each Pod
StatefulSet: mysql (replicas: 3)
volumeClaimTemplates: name=data, 10Gi

Creates automatically:
PVC: data-mysql-0 (10Gi) → mounted in mysql-0 at /var/lib/mysql
PVC: data-mysql-1 (10Gi) → mounted in mysql-1 at /var/lib/mysql
PVC: data-mysql-2 (10Gi) → mounted in mysql-2 at /var/lib/mysql
PVC naming formula
Format: {volumeClaimTemplate.name}-{statefulset}-{ordinal}

Template name: data, StatefulSet: mysql
→ data-mysql-0, data-mysql-1, data-mysql-2

Template name: logs, StatefulSet: kafka
→ logs-kafka-0, logs-kafka-1, logs-kafka-2
volumeClaimTemplates:
- metadata:
    name: data                  # PVC name prefix
  spec:
    accessModes: ["ReadWriteOnce"]
    storageClassName: standard  # Or your StorageClass
    resources:
      requests:
        storage: 10Gi

08 PVC Lifecycle ▶

Pod deleted
Pod recreated
Scale down + up
Pod deleted → PVC stays!
mysql-1 deleted

data-mysql-1 (10Gi) — STILL EXISTS
PVC is NOT deleted when Pod is deleted. Data is preserved.
This is by design — you never want to lose database data just because a Pod restarted.
Pod recreated → re-mounts same PVC
mysql-1 recreated (new Pod, same name)
→ data-mysql-1 re-mounted

New Pod → same name → finds existing PVC → mounts it → all data intact.
The app starts up and sees all its previous data. As if nothing happened.
Scale down 3→1 then back 1→3
Scale 3→1:
mysql-2 deleted → data-mysql-2 kept
mysql-1 deleted → data-mysql-1 kept
mysql-0 running → data-mysql-0 in use

Scale 1→3:
mysql-1 created → data-mysql-1 re-mounted (old data!)
mysql-2 created → data-mysql-2 re-mounted (old data!)

Scale down + up = data preserved. PVCs survive the entire lifecycle.
Cleanup warning

PVCs are NEVER auto-deleted by default. After deleting a StatefulSet, you must manually delete PVCs: kubectl delete pvc data-mysql-0 data-mysql-1 data-mysql-2. Abandoned PVCs keep consuming storage.

09 Full StatefulSet YAML

# Step 1: Headless Service (MUST create first)
apiVersion: v1
kind: Service
metadata:
  name: mysql-svc
spec:
  clusterIP: None                   # ← Headless
  selector:
    app: mysql
  ports:
  - port: 3306
    name: mysql
---
# Step 2: StatefulSet
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
spec:
  serviceName: mysql-svc            # Must match Headless Service name
  replicas: 3
  podManagementPolicy: OrderedReady  # OrderedReady (default) or Parallel

  updateStrategy:
    type: RollingUpdate             # RollingUpdate (default) or OnDelete
    rollingUpdate:
      partition: 0                  # Update all Pods (see section 13)

  selector:
    matchLabels:
      app: mysql

  template:
    metadata:
      labels:
        app: mysql
    spec:
      terminationGracePeriodSeconds: 30
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - containerPort: 3306
          name: mysql
        env:
        - name: MYSQL_ROOT_PASSWORD
          value: "rootpass"
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
        resources:
          requests: { cpu: "500m", memory: "512Mi" }
          limits: { cpu: "1", memory: "1Gi" }
        readinessProbe:
          exec:
            command: ["mysqladmin", "ping"]
          periodSeconds: 10

  volumeClaimTemplates:              # Auto-creates PVC per Pod
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 10Gi

Steps
What happens
Verify

11 Ordered Scaling ▶

Scale Up
Scale Down
Parallel mode
Scale Up 3→5 (ordered: 3, then 4)
mysql-0 ✓ mysql-1 ✓ mysql-2 ✓ (existing)

mysql-3 creating + data-mysql-3 created → wait for Ready ✓
then → mysql-4 creating + data-mysql-4 created → Ready ✓
kubectl scale statefulset mysql --replicas=5
Scale Down 5→2 (reverse order: 4, 3, 2)
mysql-4 terminating → gone
then → mysql-3 terminating → gone
then → mysql-2 terminating → gone

mysql-0 ✓ mysql-1 ✓ (remaining)
data-mysql-2 data-mysql-3 data-mysql-4 ← PVCs still exist!
PVCs not deleted

Scaling down does NOT delete PVCs. If you scale back up, Pods remount their old PVCs with all data intact. To free storage, delete PVCs manually.

Parallel mode — skip ordering
spec:
  podManagementPolicy: Parallel   # All Pods created/deleted at once
With OrderedReady (default): 0 → ready → 1 → ready → 2
With Parallel: 0, 1, 2 all created simultaneously

Use Parallel only when startup order doesn't matter (e.g., Cassandra where all nodes are peers).

12 Update Strategies ▶

RollingUpdate
OnDelete
Comparison
RollingUpdate (default) — Reverse order
DefinitionUpdates Pods one at a time in reverse ordinal order (highest index first). Each Pod must become Ready before the next is updated. Index 0 (primary) is updated last.
updateStrategy:
  type: RollingUpdate
Update image mysql:8.0 → mysql:8.1:

mysql-2 terminated → mysql-2 (8.1) created → Ready ✓
then → mysql-1 terminated → mysql-1 (8.1) → Ready ✓
then → mysql-0 terminated → mysql-0 (8.1) → Ready ✓

Primary (index 0) updated LAST. Replicas updated first to minimize downtime risk.
OnDelete — Manual control
DefinitionTemplate is updated but Pods are NOT automatically replaced. You must manually delete each Pod. When deleted, the controller recreates it with the new template. Gives you full control over update timing.
updateStrategy:
  type: OnDelete
Update template (image mysql:8.0 → 8.1):
mysql-0 (8.0) mysql-1 (8.0) mysql-2 (8.0) ← nothing happens!

You manually delete mysql-2:
kubectl delete pod mysql-2 → mysql-2 (8.1) recreated

You delete mysql-1 when ready:
kubectl delete pod mysql-1 → mysql-1 (8.1) recreated
SRE Use Case

Use OnDelete for critical databases where you want to verify each node after update before proceeding to the next. You control exactly when each Pod is replaced.

RollingUpdateOnDelete
Automatic?Yes — reverse orderNo — must delete Pods manually
ControlLess (automatic)Full manual control

13 Partitioned Rolling Update ▶

Definition — partitionOnly Pods with ordinal ≥ partition value are updated. Pods below the partition keep the old template. This lets you do a canary update — update one Pod first, verify, then update the rest.
Canary (partition=2)
Promote (partition=0)
YAML
Canary — Update only mysql-2 first
kubectl patch statefulset mysql -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":2}}}}'
kubectl set image statefulset/mysql mysql=mysql:8.1
mysql-0 (8.0) mysql-1 (8.0) mysql-2 (8.1) ← UPDATED (ordinal ≥ 2)

Only mysql-2 updated. mysql-0 and mysql-1 untouched. Verify mysql-2 works correctly.
Promote — Update the rest
# Set partition to 0 → update ALL remaining Pods
kubectl patch statefulset mysql -p '{"spec":{"updateStrategy":{"rollingUpdate":{"partition":0}}}}'
mysql-1 (8.0) → mysql-1 (8.1) ← updated (ordinal ≥ 0)
mysql-0 (8.0) → mysql-0 (8.1) ← updated last

All 3 now running 8.1 ✓
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    partition: 2       # Only Pods with ordinal ≥ 2 are updated

14 Delete Behavior ▶

Delete STS
Non-cascading
Delete Pod
Delete StatefulSet (cascading — default)
kubectl delete statefulset mysql
mysql-2 terminating → mysql-1 terminating → mysql-0 terminating
(reverse order)

data-mysql-0 data-mysql-1 data-mysql-2 ← PVCs STILL EXIST!
mysql-svc ← Service STILL EXISTS!

You must manually delete PVCs and Service if you want full cleanup.
Non-cascading delete — keep Pods
kubectl delete statefulset mysql --cascade=orphan
StatefulSet deleted. Pods become orphans (still running).
Recreate StatefulSet with same name + selector → adopts orphan Pods.
Delete individual Pod — replaced with same name
kubectl delete pod mysql-1
mysql-1 deleted → mysql-1 recreated (same name, same PVC)

StatefulSet controller recreates the Pod with the same ordinal and re-mounts the same PVC.

15 PVC Retention Policy ▶

Definition — persistentVolumeClaimRetentionPolicy (v1.27+)Controls whether PVCs are automatically deleted when the StatefulSet is deleted or scaled down. Default: Retain (keep PVCs). Can be set to Delete for automatic cleanup.
Retain (default)
Delete
YAML
Retain (default) — PVCs kept forever
Delete STS → PVCs stay. Scale down → PVCs stay.
Pro: Data safety. Con: Must clean up manually.
Delete — PVCs auto-deleted
Delete STS → PVCs deleted. Scale down → PVCs deleted.
Pro: No manual cleanup. Con: DATA LOSS if accidental!
spec:
  persistentVolumeClaimRetentionPolicy:
    whenDeleted: Retain     # When STS deleted: Retain or Delete
    whenScaled: Retain      # When scaled down: Retain or Delete

16 Monitoring & Best Practices

Always create Headless Service first

Without it, Pods don't get DNS records. Create Service before StatefulSet.

Use DNS names, never Pod IPs

Pod IPs change on restart. DNS names (mysql-0.mysql-svc) are stable and auto-update.

Set readiness probes

Ordered creation waits for Ready. Without probes, Pods are "Ready" immediately — the next Pod starts before the app is actually serving. Can break cluster formation.

Plan PVC cleanup

PVCs are never auto-deleted (by default). After decommissioning, manually delete PVCs or use persistentVolumeClaimRetentionPolicy.

Use partition for canary updates

Update one replica first (partition=N-1), verify, then promote (partition=0). Critical for database version upgrades.

SRE Wisdom

StatefulSets are for pets — treat them carefully. Every operation (scale, update, delete) should be planned and verified. Unlike Deployments where you can "move fast and break things," a StatefulSet mistake can mean data loss. Use OnDelete for production databases, partition for canary updates, and always backup before upgrades.
