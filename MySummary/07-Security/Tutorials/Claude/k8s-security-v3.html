1. Why Security Matters

Kubernetes runs your production workloads, holds your secrets, talks to your databases, and exposes services to the internet. A misconfigured RBAC binding or a leaked ServiceAccount token can hand an attacker the entire cluster.

The Real-World Risk

A single Kubernetes cluster typically hosts:

  • Dozens of applications from multiple teams (multi-tenancy)
  • Database credentials, API keys, TLS certificates (Secrets)
  • Service-to-service communication that crosses trust boundaries
  • CI/CD pipelines that need to deploy without humans
  • Developer access from laptops, dashboards, and IDEs
⚠️

What Attackers Want

Cluster-admin access, mining cryptocurrency on your nodes, stealing customer data, lateral movement to cloud accounts via instance metadata.

🎯

Common Attack Surface

Exposed kubelet APIs, overly broad ServiceAccount permissions, public dashboards, default namespace permissions, weak admission controls.

🛡️

Defense in Depth

Multiple layers: AuthN, AuthZ, Admission, NetworkPolicy, PodSecurity, runtime monitoring. No single control is enough.

The Principle of Least Privilege (PoLP) Every identity (human or machine) should have the minimum permissions needed to do its job — nothing more. This is the foundation of every decision you'll make in this guide.

2. The 3A Security Model

Every request to the Kubernetes API passes through three sequential gates. If a request fails any one of them, it's rejected. This is the mental model you must internalize.

Every request flows: Client → AuthN → AuthZ → Admission → etcd
1

Authentication (AuthN) — "Who are you?"

The API server verifies the caller's identity using TLS certificates, bearer tokens, OIDC, or webhooks. If it can't establish identity, the request gets 401 Unauthorized.

2

Authorization (AuthZ) — "What can you do?"

Given the verified identity, can this user perform this verb (get/list/create/delete) on this resource (pods/secrets/nodes) in this namespace? RBAC is the standard mechanism. Fails → 403 Forbidden.

3

Admission Control — "Is it valid and safe?"

Mutating admission controllers can modify the request (inject sidecars, add defaults). Validating controllers can reject it (enforce policies like "no privileged pods"). Only after this does the object reach etcd.

3. API Request Lifecycle (Deep)

Let's trace what happens when you run kubectl apply -f pod.yaml — from your terminal all the way to etcd.

STEP 1 OF 7

kubectl reads kubeconfig

kubectl loads ~/.kube/config, finds the current context, extracts the cluster URL, your client certificate or token, and the default namespace.

~/.kube/config (excerpt)yaml
current-context: prod-admin
contexts:
- name: prod-admin
  context:
    cluster: prod
    user: ahmed-prod
    namespace: payments
STEP 2 OF 7

HTTPS request to API server

kubectl marshals your YAML into JSON, opens a TLS connection to the API server (validating its server cert), and sends an HTTP POST with your credentials in the request.

requesthttp
POST /api/v1/namespaces/payments/pods HTTP/2
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"apiVersion":"v1","kind":"Pod",...}
STEP 3 OF 7

TLS termination & AuthN

The API server presents its server certificate, validates your client certificate (or token), and determines the User/Group identity. If multiple authenticators are configured, it tries them in order until one succeeds.

Output of AuthN A canonical identity: username + groups[]. For example: ahmed@jahez.com in groups [engineering, oncall].
STEP 4 OF 7

Authorization decision

The API server asks each configured authorizer (RBAC, Node, Webhook): "Can this identity do create pods in namespace payments?" The first authorizer to return Allow wins; if all return NoOpinion or Deny, request is denied.

authz checktrace
# SubjectAccessReview
user:      ahmed@jahez.com
verb:      create
resource:  pods
namespace: payments
decision:  ALLOW # via RoleBinding
STEP 5 OF 7

Mutating admission

Each configured mutating webhook gets to modify the object. Examples: Istio injects an envoy sidecar, defaults like imagePullPolicy are added, ServiceAccount token is mounted automatically.

Order matters Mutating webhooks run first (in priority order), then validating webhooks. A validating webhook seeing a "no-sidecar" rule will see the already-injected sidecar.
STEP 6 OF 7

Validating admission

Schema validation (kind/apiVersion correct), then Pod Security Admission (no privileged in restricted namespaces), then custom validating webhooks (OPA Gatekeeper, Kyverno). Any rejection here → request fails.

STEP 7 OF 7

Persist to etcd & respond

The final object is written to etcd. The API server returns 201 Created with the persisted object. Watchers (scheduler, kubelet, controllers) get notified via the watch protocol and the pod starts being scheduled.

4. Authentication — Who Are You?

Authentication answers a single question: "Is this request from who it claims to be?" Kubernetes itself does not store user records — it delegates identity to certificates, external providers, and token systems.

The Two Identity Types

👤

Users (Human)

External identities — developers, operators, CI bots. Kubernetes has no User object. Identity comes from certificates, OIDC, or bearer tokens issued outside the cluster.

Used by: kubectl, dashboards, CI/CD.

🤖

ServiceAccounts (In-Cluster)

Kubernetes-native identities. Stored as objects (kind: ServiceAccount) in a namespace. Pods automatically authenticate as a SA via a mounted token.

Used by: pods, controllers, in-cluster apps.

Critical concept Kubernetes has no API for managing users. You cannot kubectl create user. Users only exist as a side effect of valid credentials. This is intentional — Kubernetes leaves identity management to your existing IdP (Okta, Google, AD).

5. Users vs ServiceAccounts (Side-by-Side)

Kubernetes recognizes two fundamentally different kinds of account. The visual below captures the core split — humans on one side, machines on the other.

User accounts (Admin, Developer) vs Service accounts (Prometheus, Jenkins) · source: KodeKloud
Reading the diagram The left side is for humans — an admin doing cluster operations, a developer deploying apps. The right side is for machines — Prometheus polling the API for metrics, Jenkins deploying workloads from a pipeline. One key asymmetry the diagram simplifies: Kubernetes stores ServiceAccounts as real objects, but has no User object — user identity always comes from an external credential (a certificate or OIDC token).

Can an External App or Tool Be a User Account?

This is one of the most confusing parts — so let's clear it up directly. Yes — an external app or tool absolutely can authenticate as a User account. It is not a humans-only thing.

The confusion comes from the names. "User account" and "ServiceAccount" sound like they describe who is calling. They don't, really. They describe where the identity is defined and how the credential is issued — not whether a human or a machine is on the other end.

The Actual Distinction

🤖

ServiceAccount

An identity that lives inside the cluster as an object. Kubernetes itself creates it and signs its tokens. Namespace-scoped. You can kubectl get serviceaccount.

👤

User

An identity Kubernetes does not store at all. It comes entirely from an external credential — an X.509 cert, an OIDC token. Kubernetes just reads the username from whatever you present. There is no User object.

So the real question isn't "is the caller human or machine?" It's "where does the credential come from?"

That Means Jenkins Has Two Valid Options

Option A Jenkins as a ServiceAccount

Create a ServiceAccount in the cluster, bind RBAC to it, and hand Jenkins a token for it. Identity string: system:serviceaccount:ci:jenkins. The common, recommended path for in-cluster CI — and what the slide above depicts.

Option B Jenkins as a User

Issue Jenkins an X.509 client certificate with CN=jenkins-ci, or set it up as an OIDC client. Now Jenkins authenticates as the User jenkins-ci. Kubernetes has no record of it — the cert is the whole identity. Perfectly valid, often preferred when Jenkins runs outside the cluster.

The machine/human label is a usage convention, not a technical rule A ServiceAccount token could be used by a human — you can kubectl create token and use it yourself (just not recommended). And a User identity is routinely used by machines — cloud IAM, CI certs, external operators all authenticate as Users.

So Why the "Humans = User, Machines = SA" Guideline At All?

Because of practicality. A ServiceAccount token is trivial to obtain if your code already runs in a pod — it's auto-mounted at a known path, auto-rotated, and scoped to the namespace. Zero credential management. That's a perfect fit for in-cluster apps like Prometheus.

But if your tool runs outside the cluster (Jenkins on its own VM, a laptop, a GitHub Actions runner), there's no pod — so no auto-mounted token. You now have to deliver a credential somehow. At that point a client cert or OIDC client (the User path) is often the cleaner choice — and that's why external tools frequently end up as Users.

A Simple Decision Rule

Where does the caller run?Best identity type
Inside the cluster, as a pod ServiceAccount — token auto-mounted
Outside the cluster (CI server, laptop, external operator) User — via OIDC, or X.509 cert
Outside, but you want simple setup Either — a ServiceAccount token exported into a kubeconfig also works

That last row is the real source of confusion: you can take a ServiceAccount token and put it in a kubeconfig on an external machine. So even "runs outside = User" isn't absolute. Both work — it's a tradeoff of credential management and rotation.

The crisp mental model ServiceAccount = cluster-managed identity. User = externally-managed identity. Either can be driven by a human or a machine. The slide's "machines use service accounts" is a common pattern, not a constraint.
Aspect User ServiceAccount
Stored in cluster No Yes (namespaced)
Managed by External IdP / X.509 kubectl create sa
Scope Cluster-wide identity Namespace-scoped
Typical credential Client cert, OIDC token JWT projected token
Identity string format ahmed@jahez.com system:serviceaccount:ns:name
Used by Humans, CI Pods, controllers

What a ServiceAccount Is Actually Responsible For

This is the part that trips everyone up — so let's be precise. A ServiceAccount is an identity, not an actor. It does nothing by itself.

The badge analogy Think of a ServiceAccount like an ID badge. The badge doesn't open doors — a person holding the badge opens doors, and only the doors the badge is authorized for. The ServiceAccount is the badge. The pod is the person. RBAC is the list of doors the badge unlocks.

So "what does the ServiceAccount do?" is slightly the wrong question. The right question is: "when a pod uses this ServiceAccount, what is it allowed to do?" And the answer is always: whatever RBAC says — nothing more, nothing less.

The One Thing It Is For

A ServiceAccount answers exactly one question: when something inside a pod sends a request to the Kubernetes API server, who is making that request? That's it. It is purely about talking to the Kubernetes control plane — it is the pod's login credential for https://kubernetes.default.svc.

Three Kinds of Traffic — Only One Uses the ServiceAccount

The confusion comes from mixing up three completely different things a pod does. Here they are, side by side:

Only ① Pod → API server uses the ServiceAccount · ② and ③ are network/app concerns

Case ① — Pod → Kubernetes API Server (SA IS used)

This is the only traffic the ServiceAccount touches. Example: Prometheus inside a pod wants to ask the API server "list all pods so I can scrape their metrics." That request carries the SA's token. The API server reads the token, establishes the identity system:serviceaccount:monitoring:prometheus, then asks RBAC: "is this identity allowed to list pods?"

Identity vs permission The SA is the identity. RBAC is the permission. Whether the pod can "create pods" depends entirely on what RBAC Role you bound to that SA — not on the SA itself. A brand-new SA with no RoleBinding can do essentially nothing.

Case ② — Pod → Another Pod (SA is NOT used)

When your orders-api pod calls your payments-api pod over HTTP on port 8080, that is ordinary network traffic. Kubernetes does not authenticate it with the SA token. The SA token sitting in the pod's filesystem is irrelevant here — unless your application code deliberately chooses to read it and send it. What actually governs this traffic:

  • NetworkPolicy — decides whether the packet is even allowed to reach the destination pod.
  • Your app's own auth — a JWT, an API key, or mTLS (often via a service mesh like Istio). This is application-level, not Kubernetes-level.

Case ③ — Pod ← Receiving From Others (SA is NOT used)

A pod does not "use its SA" to receive traffic. Receiving is governed by NetworkPolicy ingress rules (is this source allowed to connect?) and your application's own login logic (does this caller present a valid token/key?). The ServiceAccount plays no part in inbound traffic at all.

Direct Answers to the Common Questions

QuestionAnswer
"Does a ServiceAccount create pods?" Only if you gave it an RBAC Role with create pods. By default a SA can do almost nothing. Most app pods never create pods — only controllers and operators do.
"Is the SA used when pods talk to each other?" No. That is NetworkPolicy + app-level auth. The SA token is not involved.
"Is the SA used when a pod receives traffic?" No. That is NetworkPolicy ingress + your app's login logic.
"What is the SA used for, then?" Exactly one thing: identifying the pod when it calls the Kubernetes API server.

The Honest Practical Truth

Most application pods never talk to the API server at all. A typical web app or an orders-api talks to a database and to other services — none of which involves the SA. They still get a SA assigned (the namespace default one) because Kubernetes assigns one automatically, but they never use the token.

Most app pods never use their SA · only API-server-facing workloads truly need a scoped SA + RBAC

That asymmetry is exactly why hardening guides tell you to set automountServiceAccountToken: false — if a pod never calls the API server, don't even mount the credential. ServiceAccounts genuinely matter for a smaller set of workloads: monitoring tools, CI deployers, controllers, operators, and ingress controllers. Those are the pods that do talk to the API server, and those are the ones where you carefully scope an SA plus a least-privilege RBAC Role.

The one mental model to keep A ServiceAccount only matters for pod → Kubernetes API server traffic. It is the pod's identity for that one conversation. It grants zero permissions on its own — RBAC decides what that identity is allowed to do. Pod-to-pod application traffic does not use it at all.

6. Authentication Methods (Deep Dive)

The API server supports many authenticators simultaneously. Each request is tried against each authenticator in order; the first one to return a success result wins.

X.509 Client Certificates

The most common way to authenticate kubeadm-bootstrapped clusters. The client presents a certificate signed by the cluster's CA. The Common Name (CN) becomes the username; Organization (O) fields become groups.

create-user-cert.shbash
# 1. Generate key + CSR
openssl genrsa -out ahmed.key 2048
openssl req -new -key ahmed.key -out ahmed.csr \
  -subj "/CN=ahmed@jahez.com/O=engineering/O=oncall"

# 2. Submit CSR to Kubernetes
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: ahmed-csr
spec:
  request: $(cat ahmed.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  usages: ["client auth"]
EOF

# 3. Approve & extract
kubectl certificate approve ahmed-csr
kubectl get csr ahmed-csr -o jsonpath='{.status.certificate}' | base64 -d > ahmed.crt
Use sparingly Client certs can't be revoked individually before expiry. Prefer OIDC for human users. Use certs for break-glass admin access only.

Static Bearer Tokens

The API server can be started with a --token-auth-file=tokens.csv flag. Each line: token,user,uid,"group1,group2". The client sends Authorization: Bearer <token>.

tokens.csvcsv
32a5f7...d1,ahmed,uid-1001,"engineering,oncall"
b8e2c9...4f,ci-deploy-bot,uid-2002,"automation"
Not recommended for production No expiration, no revocation without API server restart. Tokens leak via shell history, env vars, logs. Use OIDC or SA tokens instead.

ServiceAccount Tokens (JWT)

Tokens signed by the API server itself. Modern clusters use Projected Bound Tokens — short-lived JWTs scoped to a specific pod and audience.

projected-token.yamlyaml
apiVersion: v1
kind: Pod
spec:
  serviceAccountName: orders-api
  containers:
  - name: app
    image: jahez/orders
    volumeMounts:
    - name: vault-token
      mountPath: /var/run/secrets/vault
  volumes:
  - name: vault-token
    projected:
      sources:
      - serviceAccountToken:
          path: token
          audience: vault.jahez.internal  # scoped!
          expirationSeconds: 3600             # 1 hour
Property Reference
PropertyExplanation
volumes[].projectedA projected volume combines multiple sources (tokens, configmaps, secrets) into one directory.
projected.sources[].serviceAccountTokenRequests a freshly minted, bound JWT for the pod's ServiceAccount — not the legacy static secret.
serviceAccountToken.pathThe filename the token is written as inside the mounted volume directory.
serviceAccountToken.audienceScopes the token to one recipient (e.g. Vault). The token is rejected if presented anywhere else — limits blast radius if leaked.
serviceAccountToken.expirationSecondsToken lifetime. kubelet auto-refreshes it before expiry. Short values (1h) reduce the window of misuse.
volumeMounts[].mountPathFilesystem path inside the container where the projected volume appears.

OpenID Connect (OIDC) — Recommended for Humans

Delegate authentication to an identity provider (Google, Okta, Azure AD, Keycloak, Dex). The user gets an ID token, sends it as a bearer token. The API server validates it against the IdP's JWKS endpoint.

kube-apiserver flagsflags
--oidc-issuer-url=https://accounts.google.com
--oidc-client-id=jahez-k8s.apps.googleusercontent.com
--oidc-username-claim=email
--oidc-groups-claim=groups
--oidc-username-prefix=oidc:
--oidc-groups-prefix=oidc:
kubeconfig with oidcyaml
users:
- name: ahmed-oidc
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: kubectl-oidc_login
      args:
      - get-token
      - --oidc-issuer-url=https://accounts.google.com
      - --oidc-client-id=jahez-k8s.apps.googleusercontent.com
Why OIDC wins for humans Centralized user management, SSO, group sync, MFA, instant deactivation when an employee leaves your IdP.

Webhook Token Authentication

The API server POSTs the token to an external webhook, which returns whether it's valid and the username/groups. Used by managed clouds (EKS uses this for IAM authentication).

webhook tokenreviewjson
// API server → webhook
{
  "apiVersion": "authentication.k8s.io/v1",
  "kind": "TokenReview",
  "spec": { "token": "AQICAHj..." }
}

// webhook → API server
{
  "status": {
    "authenticated": true,
    "user": {
      "username": "arn:aws:iam::123:user/ahmed",
      "groups": ["system:masters"]
    }
  }
}

Authenticating Proxy

An upstream proxy (oauth2-proxy, nginx) terminates auth and forwards requests with X-Remote-User, X-Remote-Group headers. The API server trusts these headers when the proxy presents a valid client cert.

Common for self-hosted dashboards, browser-based kubectl alternatives. Less common in modern setups (OIDC is simpler).

7. ServiceAccount Tokens — Lifecycle

Understanding how SA tokens are issued, projected into pods, and validated is essential for secure pod-to-service authentication.

Pod → kubelet → API server → JWT → external service (validated via JWKS)

Manually request a token

terminalbash
# Get a 1-hour token for an SA (modern way - bound tokens)
kubectl create token jahez-orders-api \
  --namespace production \
  --audience vault.jahez.internal \
  --duration 1h

# Decode and inspect
kubectl create token jahez-orders-api -n production | \
  cut -d. -f2 | base64 -d | jq
Legacy vs Bound Tokens Before v1.24, every SA had a permanent Secret token that never expired. Since v1.24, tokens are short-lived (1h default) and bound to a specific pod. Auto-rotated by kubelet. Never create long-lived SA secrets in modern clusters.

8. Authorization — What Can You Do?

After AuthN succeeds, the API server knows who the request is from. Authorization decides whether that identity is allowed to perform the requested action on the requested resource.

How Multiple Authorizers Combine

The API server runs all configured authorizers in order. Each returns one of three verdicts:

✓

Allow

Request proceeds to admission. No other authorizers consulted.

✗

Deny

Hard reject — request fails immediately with 403, regardless of other authorizers.

?

NoOpinion

Pass to next authorizer. If all say NoOpinion, request is denied.

Default for missing rules Kubernetes is deny-by-default: if no Allow rule matches, the request is denied. You only need to write Allow rules; you never write Deny rules in RBAC.

Available Authorization Modes

ModeUse CaseHow It Works
RBAC Default for human & SA permissions Roles + Bindings stored as cluster objects
Node kubelet → API server Auto-authorizes kubelets to read pods on their own node
ABAC Legacy, rarely used Policy file loaded at startup; no runtime updates
Webhook Custom external authorizer API server POSTs SubjectAccessReview to your service
AlwaysAllow Dev only — never production Every request authorized (no AuthZ)

9. RBAC Deep Dive

RBAC (Role-Based Access Control) is the standard authorization mechanism in Kubernetes. It composes four resource types into permission grants.

A Binding glues Subjects (who) to a Role (what they can do)

The Four RBAC Objects

Role

Namespaced. Defines permissions within one namespace — like "can read pods in payments".

ClusterRole

Cluster-wide. Defines permissions on cluster-scoped resources (nodes, PVs, CRDs) or namespace-scoped resources across all namespaces.

RoleBinding

Namespaced. Grants a Role (or ClusterRole) to subjects, scoped to one namespace.

ClusterRoleBinding

Cluster-wide. Grants a ClusterRole to subjects across the entire cluster.

Mixing & Matching

CombinationEffect
RoleBinding → RolePermissions scoped to the binding's namespace.
RoleBinding → ClusterRoleClusterRole's permissions applied only within the binding's namespace. Useful for reusing common permission sets.
ClusterRoleBinding → ClusterRoleCluster-wide permissions everywhere.
ClusterRoleBinding → RoleInvalid — Kubernetes will reject this.

10. Full RBAC YAML Examples

Real-world RBAC patterns ranging from a read-only developer to a CI deployer to a controller's ServiceAccount.

Example 1 — Namespaced Read-Only Developer

Goal: give the engineering group read access (get/list/watch) to pods, services, and deployments in the payments namespace.

01-dev-readonly.yamlyaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: payments
  name: developer-readonly
rules:
- apiGroups: [""]                       # core API
  resources: ["pods", "services", "configmaps"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments", "replicasets"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/log"]                  # subresource
  verbs: ["get"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: engineering-readonly-payments
  namespace: payments
subjects:
- kind: Group
  name: engineering                       # from OIDC group claim
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: developer-readonly
  apiGroup: rbac.authorization.k8s.io
Property Reference
PropertyExplanation
kind: RoleNamespaced permission set — only valid inside metadata.namespace.
rules[].apiGroupsWhich API group the resource belongs to. "" is the core group (pods, services); "apps" covers deployments/replicasets.
rules[].resourcesThe resource types being granted. pods/log is a subresource — needed separately to read logs.
rules[].verbsThe actions allowed. get/list/watch = read-only. No create/update/delete means this role cannot modify anything.
kind: RoleBindingConnects subjects to a Role, scoped to one namespace.
subjects[].kindType of identity: Group, User, or ServiceAccount.
subjects[].nameThe identity value. Here a group name that comes from the OIDC groups claim.
subjects[].apiGroupFor User/Group it is rbac.authorization.k8s.io; for ServiceAccount it is omitted.
roleRefThe Role (or ClusterRole) being granted. Immutable — to change it you must delete and recreate the binding.

  kind: Role
  name: deployer
  apiGroup: rbac.authorization.k8s.io

PropertyExplanation

Example 3 — Restricted Resource Names (extreme PoLP)

Sometimes you want an app to only manage specific named objects, not all of a kind. Use resourceNames.

03-named-resources.yamlyaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: payments
  name: leader-election
rules:
- apiGroups: ["coordination.k8s.io"]
  resources: ["leases"]
  resourceNames: ["orders-leader"]    # ONLY this lease
  verbs: ["get", "update", "patch"]
- apiGroups: ["coordination.k8s.io"]
  resources: ["leases"]
  verbs: ["create"]                       # create can't be restricted by name
Property Reference
PropertyExplanation
apiGroups: [coordination.k8s.io]The API group that owns Lease objects, used for leader election.
resources: [leases]Lease objects coordinate which replica is the active leader.
resourceNames: [orders-leader]Narrows the rule to a single named object — the app can touch only the orders-leader lease, no other lease in the namespace.
Second rule with verbs: [create]Separate rule because create cannot be limited by resourceNames — the object name doesn't exist until creation, so K8s ignores the field for that verb.

11. Node Authorizer & ABAC

Node Authorizer (always enabled)

A specialized authorizer that automatically grants kubelets exactly the permissions they need — and nothing more.

  • kubelet on node-A can only read pods scheduled to node-A
  • It can read Secrets, ConfigMaps, PVCs that are referenced by pods on its node
  • It can update only its own Node object status, not other nodes
  • Identifies kubelets by username prefix system:node: and group system:nodes
Why it's important Without this, a compromised kubelet could read every Secret in the cluster. Node authorizer is the boundary that contains node breaches.

ABAC (legacy)

Attribute-Based Access Control via a static policy file. Each line is a JSON object describing one allow rule. Loaded at API server startup — to change, you must restart the API server.

abac-policy.jsonljsonl
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy","spec":{"user":"alice","namespace":"*","resource":"*","apiGroup":"*"}}
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy","spec":{"group":"system:authenticated","namespace":"*","resource":"events","readonly":true}}
Avoid ABAC for new clusters Inflexible (no hot reload), no fine-grained verbs, hard to audit. RBAC supersedes it.

12. Admission Controllers — The Third Gate

After AuthN and AuthZ pass, the request is still in-flight, not yet persisted. Admission controllers can mutate or reject it based on cluster-wide policy.

Two Phases

🔧

Mutating Admission

Modifies the object. Examples: inject Istio sidecar, add default labels, set imagePullSecrets, mount ServiceAccount tokens.

✓

Validating Admission

Accept or reject — cannot modify. Examples: enforce "no privileged pods", "image must be from approved registry", "all pods must have resource limits".

13. Pod Security Admission (PSA)

Modern replacement for the deprecated PodSecurityPolicy. Built-in validating controller that enforces three security profiles at the namespace level.

The Three Profiles

privileged

Unrestricted — anything allowed. Use only for system namespaces.

baseline

Minimally restrictive. Prevents known privilege escalation. Easy migration path.

restricted

Heavily restricted. Industry-standard hardening. Run-as-non-root, drop capabilities, seccomp, etc.

Three Modes per Profile

For each profile, you choose what happens when a pod violates it:

ModeBehaviorWhen to use
enforceReject pod creationProduction lockdown
auditAllow, log violation to audit logVisibility
warnAllow, return warning to userMigration / education

Applying PSA to a Namespace

restricted-namespace.yamlyaml
apiVersion: v1
kind: Namespace
metadata:
  name: payments
  labels:
    # Enforce restricted — reject violating pods
    pod-security.kubernetes.io/enforce: restricted
    pod-security.kubernetes.io/enforce-version: v1.28
    # Warn for baseline (additional visibility)
    pod-security.kubernetes.io/warn: restricted
    pod-security.kubernetes.io/warn-version: v1.28
    # Audit log all violations
    pod-security.kubernetes.io/audit: restricted
    pod-security.kubernetes.io/audit-version: v1.28
Property Reference
PropertyExplanation
pod-security.kubernetes.io/enforceThe profile to hard-enforce. A pod violating restricted is rejected at admission.
pod-security.kubernetes.io/enforce-versionPins the profile to a specific K8s version so rule changes in newer releases don't silently alter behavior.
pod-security.kubernetes.io/warnProfile checked in warn mode — the pod is still created but the user gets a console warning.
pod-security.kubernetes.io/auditProfile checked in audit mode — violations are written to the audit log only, no user feedback.
All three modes togetherYou can run enforce/warn/audit at different profile levels simultaneously — a common migration pattern.

A Pod That Passes "restricted"

compliant-pod.yamlyaml
apiVersion: v1
kind: Pod
metadata:
  name: orders-api
  namespace: payments
spec:
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: app
    image: jahez/orders-api:v2.1
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
    resources:
      limits:
        memory: "512Mi"
        cpu: "500m"
Property Reference
PropertyExplanation
spec.securityContext.runAsNonRootRequired by restricted — the container is rejected if its image would run as UID 0.
spec.securityContext.runAsUser: 10001Explicit non-zero UID for the process. A high, fixed UID avoids collisions with host users.
spec.securityContext.fsGroupGID applied to mounted volumes so the non-root process can read/write them.
seccompProfile.type: RuntimeDefaultEnables the container runtime's default syscall filter — mandatory under restricted.
containers[].securityContext.allowPrivilegeEscalation: falseBlocks the process from gaining more privileges via setuid binaries. Required by restricted.
readOnlyRootFilesystem: trueMakes the container root filesystem immutable — limits what malware can persist.
capabilities.drop: ["ALL"]Strips every Linux capability. restricted permits only re-adding NET_BIND_SERVICE.
resources.limitsCPU/memory ceilings — not a PSA requirement but standard hardening to prevent noisy-neighbor and DoS.

14. Validating & Mutating Webhooks

When built-in admission isn't enough, you can register external HTTPS endpoints to receive admission reviews. This is how OPA Gatekeeper, Kyverno, Istio, and Linkerd plug in.

Registering a Validating Webhook

- name: images.jahez.io

    service:
      namespace: security
      name: image-policy
      path: /validate

  - apiGroups: [""]
    apiVersions: ["v1"]
    resources: ["pods"]

PropertyExplanation

16. Pod & Container SecurityContext

SecurityContext defines privilege and access control settings for a Pod or Container — UID, capabilities, filesystem mode, SELinux, seccomp. Distinct from RBAC: this controls what happens inside the container at the OS level.

Pod-level vs Container-level

Settings can be at spec.securityContext (applies to all containers) or spec.containers[].securityContext (overrides per container).

FieldScopeEffect
runAsUserPod / ContainerUID to run process as (numeric)
runAsGroupPod / ContainerPrimary GID
runAsNonRootPod / ContainerBlock container if image runs as UID 0
fsGroupPod onlyGID applied to mounted volumes
seLinuxOptionsPod / ContainerSELinux context label
seccompProfilePod / ContainerLinux syscall filter
privilegedContainer onlyFull host access — never set true
allowPrivilegeEscalationContainer onlyBlock setuid binaries
readOnlyRootFilesystemContainer onlyMake / read-only
capabilitiesContainer onlyAdd/drop Linux capabilities

Production-Grade Hardened Pod

hardened-pod.yamlyaml
apiVersion: v1
kind: Pod
metadata:
  name: orders-api
spec:
  securityContext:                  # pod-wide defaults
    runAsNonRoot: true
    runAsUser: 10001
    runAsGroup: 10001
    fsGroup: 10001
    seccompProfile:
      type: RuntimeDefault          # enable default seccomp
    supplementalGroups: [2000]

  containers:
  - name: app
    image: registry.jahez.com/orders-api:v2.1
    securityContext:                # container override
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      privileged: false
      capabilities:
        drop: ["ALL"]              # strip all caps
        add:  ["NET_BIND_SERVICE"]  # only what we need (port < 1024)
    volumeMounts:
    - name: tmp                    # app needs writable /tmp
      mountPath: /tmp
    resources:
      limits:   { cpu: 500m, memory: 512Mi }
      requests: { cpu: 100m, memory: 128Mi }

  volumes:
  - name: tmp
    emptyDir: {}
Property Reference
PropertyExplanation
spec.securityContextPod-level block — settings here apply to every container unless overridden.
runAsNonRoot / runAsUser / runAsGroupForce the process to run as a specific non-root UID/GID instead of whatever the image defaults to.
fsGroupSupplementary GID that owns mounted volumes — only valid at pod level.
supplementalGroupsExtra GIDs added to the process, e.g. to access group-owned shared storage.
containers[].securityContextContainer-level block — overrides the pod-level settings for this one container.
allowPrivilegeEscalation: falsePrevents the process from acquiring more privileges than its parent.
readOnlyRootFilesystem: trueMounts / read-only; the app must use an explicit writable volume for scratch space.
privileged: falseExplicitly denies full host access. A privileged container is effectively root on the node.
capabilities.drop / addDrop every Linux capability, then re-add only the minimum (here NET_BIND_SERVICE to bind low ports).
volumes[].emptyDirAn ephemeral writable volume — paired with readOnlyRootFilesystem to give the app a safe /tmp.
Capabilities cheat sheet NET_BIND_SERVICE (bind <1024), CHOWN (change file ownership), SETUID/SETGID (change UID), SYS_TIME (set clock). Drop ALL, add only what the app demands.

17. Network Policies — L3/L4 Firewall

By default, all pods in a cluster can talk to each other freely. NetworkPolicies turn this off and let you define explicit allow rules — pod-level firewalls.

Default-Deny — The Critical Starting Point

default-deny.yamlyaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec:
  podSelector: {}                # all pods in namespace
  policyTypes:
  - Ingress
  - Egress
  # No ingress: rules → all incoming blocked
  # No egress: rules → all outgoing blocked
Property Reference
PropertyExplanation
kind: NetworkPolicyAn L3/L4 firewall rule applied to pods. Requires a CNI that enforces NetworkPolicy.
spec.podSelector: {}An empty selector matches every pod in the namespace — this policy applies cluster-namespace-wide.
policyTypes: [Ingress, Egress]Declares which traffic directions this policy governs.
No ingress rules listedWith Ingress in policyTypes but zero rules, all inbound traffic is denied.
No egress rules listedSame logic — all outbound traffic is denied. This is the deny-by-default baseline.

Targeted Allow — Frontend → Backend Only

allow-frontend-to-orders.yamlyaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-allow-frontend
  namespace: payments
spec:
  podSelector:
    matchLabels:
      app: orders-api          # protect these pods
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:             # from same namespace
        matchLabels: { app: frontend }
    - namespaceSelector:       # or from observability ns
        matchLabels: { name: monitoring }
    ports:
    - protocol: TCP
      port: 8080
  egress:
  - to:
    - podSelector: { matchLabels: { app: postgres } }
    ports: [{ protocol: TCP, port: 5432 }]
  - to:                       # DNS
    - namespaceSelector: {}
      podSelector: { matchLabels: { k8s-app: kube-dns } }
    ports: [{ protocol: UDP, port: 53 }]
Property Reference
PropertyExplanation
spec.podSelector.matchLabelsTargets only pods labeled app: orders-api — this policy protects the backend, not the whole namespace.
ingress[].from[].podSelectorAllows traffic from pods (in the same namespace) carrying the matching label — here frontend.
ingress[].from[].namespaceSelectorAllows traffic from any pod in namespaces with the matching label — here the monitoring namespace.
ingress[].portsRestricts allowed inbound traffic to a specific protocol and port (TCP 8080).
egress[].to[].podSelectorAllows outbound traffic only to matching pods — here the postgres database.
egress DNS ruleExplicitly permits UDP 53 to kube-dns — without it, name resolution breaks under a default-deny policy.
Multiple list items under fromItems are OR'd — traffic matching any source entry is allowed.
CNI required NetworkPolicy is only enforced if your CNI plugin supports it. Calico, Cilium, Antrea, Weave do. Flannel (default) does NOT. Check before relying on it.

18. Secrets Management

Kubernetes Secrets store sensitive data, but they're not encrypted by default — they're base64 encoded. Treat them as plaintext unless you've enabled encryption at rest.

The Five Layers of Secret Hardening

1

Encryption at Rest (etcd)

Configure --encryption-provider-config on kube-apiserver to encrypt Secrets in etcd with AES-CBC or KMS. Without this, anyone with etcd access reads them.

2

RBAC on Secrets

Never grant list or get on secrets to humans broadly. Limit Secret access to specific ServiceAccounts with resourceNames.

3

External Secret Stores

Vault, AWS Secrets Manager, GCP Secret Manager. Pull at runtime via External Secrets Operator or CSI Secret Store driver. Master secret never lives in etcd.

4

GitOps with SealedSecrets / SOPS

Need secrets in Git? Use Bitnami SealedSecrets (encrypts with a cluster-side controller key) or Mozilla SOPS (encrypts per-field). Plaintext never reaches Git.

5

Audit & Rotation

Enable Kubernetes audit logging for Secret operations. Rotate secrets on a schedule (90 days) and on personnel changes.

Encryption at Rest Config

encryption-config.yamlyaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
- resources:
  - secrets
  - configmaps
  providers:
  - kms:                            # preferred: cloud KMS
      name: aws-kms
      endpoint: unix:///var/run/kmsplugin/socket.sock
      cachesize: 1000
  - aescbc:                          # fallback
      keys:
      - name: key1
        secret: <base64 32-byte key>
  - identity: {}                     # last = readable (for migration)
Property Reference
PropertyExplanation
kind: EncryptionConfigurationPassed to kube-apiserver via --encryption-provider-config to encrypt objects before they hit etcd.
resources[].resourcesWhich object types to encrypt — typically secrets and configmaps.
providersAn ordered list. For writes, the first provider is used; for reads, each is tried in order until one decrypts.
providers[].kmsEnvelope encryption via an external KMS plugin (AWS/GCP/Azure). Preferred — the key never leaves the KMS.
kms.cachesizeHow many decrypted data-encryption keys to cache in memory to reduce KMS calls.
providers[].aescbcLocal AES-CBC encryption with a key stored in the config file itself — weaker, used as fallback.
providers[].identity: {}No-op "encryption" = plaintext. Placed last so existing unencrypted data is still readable during migration.

  name: payments-defaults
  namespace: payments
spec:
  limits:
  - type: Container
    default:          { cpu: 500m, memory: 512Mi }
    defaultRequest:   { cpu: 100m, memory: 128Mi }
    max:              { cpu: "4",  memory: 8Gi }
    min:              { cpu: 10m, memory: 32Mi }
Property Reference
PropertyExplanation
kind: ResourceQuotaCaps the total resources a namespace can consume — prevents one team from starving the cluster.
spec.hard.requests.cpu / requests.memorySum of all container requests in the namespace cannot exceed these values.
spec.hard.limits.cpu / limits.memorySum of all container limits ceiling for the namespace.
spec.hard.pods / secretsCaps the count of objects — limiting secrets reduces blast radius and curbs sprawl.
spec.hard.services.loadbalancersLimits how many cloud load balancers the namespace can provision (each costs money).
kind: LimitRangeSets per-container defaults and bounds — works alongside ResourceQuota.
limits[].defaultThe limit automatically applied to containers that don't specify one.
limits[].defaultRequestThe request auto-applied when a container omits it — also satisfies PSA/quota requirements.
limits[].max / minHard bounds — a container requesting outside this range is rejected at admission.

Step 5 — NetworkPolicies (default-deny + frontend allow)

project/05-netpol.yamlyaml
# Default deny all ingress/egress in payments
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: payments
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]
---
# Allow DNS for everyone
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: payments
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
  - to:
    - namespaceSelector:
        matchLabels: { kubernetes.io/metadata.name: kube-system }
      podSelector:
        matchLabels: { k8s-app: kube-dns }
    ports:
    - { protocol: UDP, port: 53 }
    - { protocol: TCP, port: 53 }
---
# Allow ingress to orders-api from frontend
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-api-allow-frontend
  namespace: payments
spec:
  podSelector:
    matchLabels: { app: orders-api }
  policyTypes: [Ingress, Egress]
  ingress:
  - from:
    - podSelector:
        matchLabels: { app: frontend }
    ports:
    - { protocol: TCP, port: 8080 }
  egress:
  - to:
    - podSelector:
        matchLabels: { app: postgres }
    ports:
    - { protocol: TCP, port: 5432 }
Property Reference
PropertyExplanation
default-deny-all policyEmpty podSelector + both policyTypes with no rules — blocks every direction for every pod first.
allow-dns policyA separate egress-only policy re-permitting DNS. Without it, default-deny breaks all name resolution.
namespaceSelector with kubernetes.io/metadata.nameA built-in label every namespace carries automatically — the reliable way to target kube-system.
Combined namespaceSelector + podSelector under one to entryBoth must match (AND) — traffic is allowed only to kube-dns pods inside kube-system.
orders-api-allow-frontend policyThe targeted exception — opens just the paths the app actually needs on top of default-deny.
ingress from app: frontend on 8080Only the frontend may reach the API, and only on its HTTP port.
egress to app: postgres on 5432The API may only reach the database — it cannot make arbitrary outbound connections.
Layered policies are additiveNetworkPolicies combine as a union of allows — multiple small policies build the final allowed set.

Step 6 — Deploy the App with Full Security

project/06-orders-api.yamlyaml
apiVersion: v1
kind: Secret
metadata:
  name: orders-db-credentials
  namespace: payments
type: Opaque
data:
  password: c3VwZXJzZWNyZXQxMjM=     # prefer External Secrets in real life
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: orders-api-config
  namespace: payments
data:
  log_level: "info"
  feature_flag_new_checkout: "true"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders-api
  namespace: payments
  labels: { app: orders-api }
spec:
  replicas: 3
  selector:
    matchLabels: { app: orders-api }
  template:
    metadata:
      labels: { app: orders-api }
    spec:
      serviceAccountName: orders-api        # scoped identity
      automountServiceAccountToken: true
      securityContext:                       # pod-level
        runAsNonRoot: true
        runAsUser: 10001
        fsGroup: 10001
        seccompProfile:
          type: RuntimeDefault
      containers:
      - name: api
        image: registry.jahez.com/orders-api:v2.1
        securityContext:                     # container-level
          allowPrivilegeEscalation: false
          readOnlyRootFilesystem: true
          capabilities:
            drop: ["ALL"]
        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef:
              name: orders-db-credentials
              key: password
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: orders-api-config
              key: log_level
        ports:
        - { containerPort: 8080, name: http }
        resources:
          requests: { cpu: 100m, memory: 128Mi }
          limits:   { cpu: 500m, memory: 512Mi }
        volumeMounts:
        - { name: tmp, mountPath: /tmp }
        livenessProbe:
          httpGet: { path: /healthz, port: http }
          initialDelaySeconds: 15
        readinessProbe:
          httpGet: { path: /ready, port: http }
      volumes:
      - name: tmp
        emptyDir: {}
Property Reference
PropertyExplanation
Secret (type Opaque)Holds the DB password. data values are base64-encoded — encryption at rest or External Secrets is the real protection.
ConfigMapNon-sensitive runtime config (log level, feature flags) consumed by the same Deployment.
spec.template.spec.serviceAccountNameRuns the pods as the scoped orders-api SA — ties the deployment to the least-privilege Role from Step 4.
template.spec.securityContextPod-level hardening — non-root UID, fsGroup, RuntimeDefault seccomp. Required to pass the namespace's restricted PSA.
containers[].securityContextContainer hardening — no privilege escalation, read-only root FS, all capabilities dropped.
env[].valueFrom.secretKeyRefInjects the DB password from the Secret as an env var — the app never embeds the credential.
env[].valueFrom.configMapKeyRefInjects a single key from the ConfigMap as an env var.
resources.requests / limitsScheduling guarantees and ceilings — also satisfy the namespace LimitRange and ResourceQuota.
livenessProbe / readinessProbeLiveness restarts a hung container; readiness gates traffic until the app is ready.
volumes[].emptyDir mounted at /tmpProvides writable scratch space since the root filesystem is read-only.

kubectl create token <sa> -n <ns> --duration=1h
kubectl get serviceaccount <sa> -n <ns> -o yaml

# ─── CSRs ────────────────────────────────────────────
kubectl get csr
kubectl certificate approve <csr-name>
kubectl certificate deny <csr-name>

# ─── PSA & SECURITY ─────────────────────────────────
kubectl label namespace <ns> \
  pod-security.kubernetes.io/enforce=restricted \
  --overwrite

# ─── NETWORK POLICIES ───────────────────────────────
kubectl get netpol -A
kubectl describe netpol <name> -n <ns>

# ─── SECRETS ────────────────────────────────────────
kubectl create secret generic db --from-literal=password=s3cr3t -n payments
kubectl get secret db -n payments -o jsonpath='{.data.password}' | base64 -d

# ─── AUDIT ──────────────────────────────────────────
# Find pods running as root
kubectl get pods -A -o json | \
  jq -r '.items[] | select(.spec.securityContext.runAsNonRoot != true) | "\(.metadata.namespace)/\(.metadata.name)"'

# Find privileged containers
kubectl get pods -A -o json | \
  jq -r '.items[] | select(.spec.containers[].securityContext.privileged == true) | .metadata.name'

# Find ClusterRoleBindings to default SA (likely too permissive)
kubectl get clusterrolebindings -o json | \
  jq '.items[] | select(.subjects[]?.name=="default")'

Final Mental Model

①

AuthN — Who?

Certs, OIDC, SA tokens. Don't store users in K8s.

②

AuthZ — What?

RBAC: Role + Binding. Deny by default. Always least privilege.

③

Admission — Valid?

PSA enforces pod security. Webhooks enforce custom policy.

④

Runtime — Safe?

SecurityContext locks down the container. NetPol limits traffic.
