1Foundations

1.1 Why Security Matters

Kubernetes runs your production workloads, holds your secrets, talks to your databases, and exposes services to the internet. A misconfigured RBAC binding or a leaked ServiceAccount token can hand an attacker the entire cluster.

The Real-World Risk

A single Kubernetes cluster typically hosts:

  • Dozens of applications from multiple teams (multi-tenancy)
  • Database credentials, API keys, TLS certificates (Secrets)
  • Service-to-service communication that crosses trust boundaries
  • CI/CD pipelines that need to deploy without humans
  • Developer access from laptops, dashboards, and IDEs
⚠️

What Attackers Want

Cluster-admin access, mining cryptocurrency on your nodes, stealing customer data, lateral movement to cloud accounts via instance metadata.

🎯

Common Attack Surface

Exposed kubelet APIs, overly broad ServiceAccount permissions, public dashboards, default namespace permissions, weak admission controls.

🛡️

Defense in Depth

Multiple layers: AuthN, AuthZ, Admission, NetworkPolicy, PodSecurity, runtime monitoring. No single control is enough.

The Principle of Least Privilege (PoLP) Every identity (human or machine) should have the minimum permissions needed to do its job — nothing more. This is the foundation of every decision you'll make in this guide.

1.2 The 3A Security Model

Every request to the Kubernetes API passes through three sequential gates. If a request fails any one of them, it's rejected. This is the mental model you must internalize.

Every request flows: Client → AuthN → AuthZ → Admission → etcd
1

Authentication (AuthN) — "Who are you?"

The API server verifies the caller's identity using TLS certificates, bearer tokens, OIDC, or webhooks. If it can't establish identity, the request gets 401 Unauthorized.

2

Authorization (AuthZ) — "What can you do?"

Given the verified identity, can this user perform this verb (get/list/create/delete) on this resource (pods/secrets/nodes) in this namespace? RBAC is the standard mechanism. Fails → 403 Forbidden.

3

Admission Control — "Is it valid and safe?"

Mutating admission controllers can modify the request (inject sidecars, add defaults). Validating controllers can reject it (enforce policies like "no privileged pods"). Only after this does the object reach etcd.

1.3 API Request Lifecycle (Deep)

Let's trace what happens when you run kubectl apply -f pod.yaml — from your terminal all the way to etcd.

STEP 1 OF 7

kubectl reads kubeconfig

kubectl loads ~/.kube/config, finds the current context, extracts the cluster URL, your client certificate or token, and the default namespace.

~/.kube/config (excerpt)yaml

    cluster: prod
    user: ahmed-prod
    namespace: payments
STEP 2 OF 7

HTTPS request to API server

kubectl marshals your YAML into JSON, opens a TLS connection to the API server (validating its server cert), and sends an HTTP POST with your credentials in the request.

requesthttp
POST /api/v1/namespaces/payments/pods HTTP/2
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{"apiVersion":"v1","kind":"Pod",...}
STEP 3 OF 7

TLS termination & AuthN

The API server presents its server certificate, validates your client certificate (or token), and determines the User/Group identity. If multiple authenticators are configured, it tries them in order until one succeeds.

Output of AuthN A canonical identity: username + groups[]. For example: ahmed@jahez.com in groups [engineering, oncall].
STEP 4 OF 7

Authorization decision

The API server asks each configured authorizer (RBAC, Node, Webhook): "Can this identity do create pods in namespace payments?" The first authorizer to return Allow wins; if all return NoOpinion or Deny, request is denied.

authz checktrace
# SubjectAccessReview
user:      ahmed@jahez.com
verb:      create
resource:  pods
namespace: payments
decision:  ALLOW # via RoleBinding
STEP 5 OF 7

Mutating admission

Each configured mutating webhook gets to modify the object. Examples: Istio injects an envoy sidecar, defaults like imagePullPolicy are added, ServiceAccount token is mounted automatically.

Order matters Mutating webhooks run first (in priority order), then validating webhooks. A validating webhook seeing a "no-sidecar" rule will see the already-injected sidecar.
STEP 6 OF 7

Validating admission

Schema validation (kind/apiVersion correct), then Pod Security Admission (no privileged in restricted namespaces), then custom validating webhooks (OPA Gatekeeper, Kyverno). Any rejection here → request fails.

STEP 7 OF 7

Persist to etcd & respond

The final object is written to etcd. The API server returns 201 Created with the persisted object. Watchers (scheduler, kubelet, controllers) get notified via the watch protocol and the pod starts being scheduled.

2Authentication

2.1 Authentication — Who Are You?

Authentication answers a single question: "Is this request from who it claims to be?" Kubernetes itself does not store user records — it delegates identity to certificates, external providers, and token systems.

The Two Identity Types

👤

Users (Human)

External identities — developers, operators, CI bots. Kubernetes has no User object. Identity comes from certificates, OIDC, or bearer tokens issued outside the cluster.

Used by: kubectl, dashboards, CI/CD.

🤖

ServiceAccounts (In-Cluster)

Kubernetes-native identities. Stored as objects (kind: ServiceAccount) in a namespace. Pods automatically authenticate as a SA via a mounted token.

Used by: pods, controllers, in-cluster apps.

Critical concept Kubernetes has no API for managing users. You cannot kubectl create user. Users only exist as a side effect of valid credentials. This is intentional — Kubernetes leaves identity management to your existing IdP (Okta, Google, AD).

Can an External App or Tool Be a User Account?

This is one of the most confusing parts — so let's clear it up directly. Yes — an external app or tool absolutely can authenticate as a User account. It is not a humans-only thing.

The confusion comes from the names. "User account" and "ServiceAccount" sound like they describe who is calling. They don't, really. They describe where the identity is defined and how the credential is issued — not whether a human or a machine is on the other end.

The Actual Distinction

🤖

ServiceAccount

An identity that lives inside the cluster as an object. Kubernetes itself creates it and signs its tokens. Namespace-scoped. You can kubectl get serviceaccount.

👤

User

An identity Kubernetes does not store at all. It comes entirely from an external credential — an X.509 cert, an OIDC token. Kubernetes just reads the username from whatever you present. There is no User object.

So the real question isn't "is the caller human or machine?" It's "where does the credential come from?"

That Means Jenkins Has Two Valid Options

Option A Jenkins as a ServiceAccount

Create a ServiceAccount in the cluster, bind RBAC to it, and hand Jenkins a token for it. Identity string: system:serviceaccount:ci:jenkins-service-account. The common, recommended path for in-cluster CI — and what the slide above depicts.

Option B Jenkins as a User

Issue Jenkins an X.509 client certificate with CN=jenkins-ci, or set it up as an OIDC client. Now Jenkins authenticates as the User jenkins-ci. Kubernetes has no record of it — the cert is the whole identity. Perfectly valid, often preferred when Jenkins runs outside the cluster.

The machine/human label is a usage convention, not a technical rule A ServiceAccount token could be used by a human — you can kubectl create token and use it yourself (just not recommended). And a User identity is routinely used by machines — cloud IAM, CI certs, external operators all authenticate as Users.

So Why the "Humans = User, Machines = SA" Guideline At All?

Because of practicality. A ServiceAccount token is trivial to obtain if your code already runs in a pod — it's auto-mounted at a known path, auto-rotated, and scoped to the namespace. Zero credential management. That's a perfect fit for in-cluster apps like Prometheus.

But if your tool runs outside the cluster (Jenkins on its own VM, a laptop, a GitHub Actions runner), there's no pod — so no auto-mounted token. You now have to deliver a credential somehow. At that point a client cert or OIDC client (the User path) is often the cleaner choice — and that's why external tools frequently end up as Users.

A Simple Decision Rule

Where does the caller run?Best identity type
Inside the cluster, as a pod ServiceAccount — token auto-mounted
Outside the cluster (CI server, laptop, external operator) User — via OIDC, or X.509 cert
Outside, but you want simple setup Either — a ServiceAccount token exported into a kubeconfig also works

That last row is the real source of confusion: you can take a ServiceAccount token and put it in a kubeconfig on an external machine. So even "runs outside = User" isn't absolute. Both work — it's a tradeoff of credential management and rotation.

What a ServiceAccount Is Actually Responsible For

This is the part that trips everyone up — so let's be precise. A ServiceAccount is an identity, not an actor. It does nothing by itself.

The badge analogy Think of a ServiceAccount like an ID badge. The badge doesn't open doors — a person holding the badge opens doors, and only the doors the badge is authorized for. The ServiceAccount is the badge. The pod is the person. RBAC is the list of doors the badge unlocks.

So "what does the ServiceAccount do?" is slightly the wrong question. The right question is: "when a pod uses this ServiceAccount, what is it allowed to do?" And the answer is always: whatever RBAC says — nothing more, nothing less.

The One Thing It Is For

A ServiceAccount answers exactly one question: when something inside a pod sends a request to the Kubernetes API server, who is making that request? That's it. It is purely about talking to the Kubernetes control plane — it is the pod's login credential for https://kubernetes.default.svc.

Three Kinds of Traffic — Only One Uses the ServiceAccount

The confusion comes from mixing up three completely different things a pod does. Here they are, side by side:

Only ① Pod → API server uses the ServiceAccount · ② and ③ are network/app concerns

Case ① — Pod → Kubernetes API Server (SA IS used)

This is the only traffic the ServiceAccount touches. Example: Prometheus inside a pod wants to ask the API server "list all pods so I can scrape their metrics." That request carries the SA's token. The API server reads the token, establishes the identity system:serviceaccount:monitoring:prometheus, then asks RBAC: "is this identity allowed to list pods?"

Identity vs permission The SA is the identity. RBAC is the permission. Whether the pod can "create pods" depends entirely on what RBAC Role you bound to that SA — not on the SA itself. A brand-new SA with no RoleBinding can do essentially nothing.

Case ② — Pod → Another Pod (SA is NOT used)

When your orders-api-pod pod calls your payments-api pod over HTTP on port 8080, that is ordinary network traffic. Kubernetes does not authenticate it with the SA token. The SA token sitting in the pod's filesystem is irrelevant here — unless your application code deliberately chooses to read it and send it. What actually governs this traffic:

  • NetworkPolicy — decides whether the packet is even allowed to reach the destination pod.
  • Your app's own auth — a JWT, an API key, or mTLS (often via a service mesh like Istio). This is application-level, not Kubernetes-level.

Case ③ — Pod ← Receiving From Others (SA is NOT used)

A pod does not "use its SA" to receive traffic. Receiving is governed by NetworkPolicy ingress rules (is this source allowed to connect?) and your application's own login logic (does this caller present a valid token/key?). The ServiceAccount plays no part in inbound traffic at all.

Direct Answers to the Common Questions

QuestionAnswer
"Does a ServiceAccount create pods?" Only if you gave it an RBAC Role with create pods. By default a SA can do almost nothing. Most app pods never create pods — only controllers and operators do.
"Is the SA used when pods talk to each other?" No. That is NetworkPolicy + app-level auth. The SA token is not involved.
"Is the SA used when a pod receives traffic?" No. That is NetworkPolicy ingress + your app's login logic.
"What is the SA used for, then?" Exactly one thing: identifying the pod when it calls the Kubernetes API server.

The Honest Practical Truth

Most application pods never talk to the API server at all. A typical web app or an orders-api-pod talks to a database and to other services — none of which involves the SA. They still get a SA assigned (the namespace default one) because Kubernetes assigns one automatically, but they never use the token.

Most app pods never use their SA · only API-server-facing workloads truly need a scoped SA + RBAC

That asymmetry is exactly why hardening guides tell you to set automountServiceAccountToken: false — if a pod never calls the API server, don't even mount the credential. ServiceAccounts genuinely matter for a smaller set of workloads: monitoring tools, CI deployers, controllers, operators, and ingress controllers. Those are the pods that do talk to the API server, and those are the ones where you carefully scope an SA plus a least-privilege RBAC Role.

The one mental model to keep A ServiceAccount only matters for pod → Kubernetes API server traffic. It is the pod's identity for that one conversation. It grants zero permissions on its own — RBAC decides what that identity is allowed to do. Pod-to-pod application traffic does not use it at all.

Defaults: No ServiceAccount, No Roles

A natural question: what does Kubernetes do before you configure anything? What if a pod has no ServiceAccount, or a resource has no Role? Let's break it into the two halves.

Case 1 — A Pod With No ServiceAccount Specified

You actually can't have a pod with no ServiceAccount. If you don't set serviceAccountName, the ServiceAccount admission controller automatically assigns the namespace's default ServiceAccount. Every namespace gets a default SA created the moment the namespace itself is created.

Omitting serviceAccountName doesn't mean "no identity" — admission injects the default SA

Here's the important part: the default ServiceAccount has almost no permissions. It has no RoleBinding out of the box. A pod using it can authenticate to the API server ("I am system:serviceaccount:payments:default") but RBAC will deny nearly every request — it can't list pods, read secrets, or create anything.

It can still do a few harmless things every authenticated identity can do — like discovery endpoints (/api, /version), granted via the built-in system:discovery ClusterRole. But for real work, it is effectively powerless.

Case 2 — No Role or RoleBinding for a Resource

This is where Kubernetes' core security principle kicks in: deny by default. RBAC is purely additive — there are no "deny" rules, you only ever write "allow" rules. So if no Role grants access to a resource, access is denied. The absence of a rule is the denial.

No matching allow rule → 403 Forbidden. The absence of a rule is itself the denial.

Putting Both Together

The combined default A pod with no SA configured → uses the default SA. The default SA has no RoleBinding → RBAC denies almost everything. Result: the pod authenticates fine, but is authorized for essentially nothing. This is intentional — a fresh pod is locked out of the API server by default, and you must explicitly grant permissions. That is least-privilege working as designed.

Important Caveat — This Assumes RBAC Is Enabled

Everything above is true when the API server runs with --authorization-mode=RBAC (or Node,RBAC) — the standard for any real cluster. kubeadm, EKS, GKE, and AKS all do this.

The dangerous exception If a cluster is started with --authorization-mode=AlwaysAllow, there is no authorization step — every authenticated request is allowed regardless of Roles. Some bare local setups historically did this. If a pod is doing things it was never granted, check the authorization mode first.

Practical Consequences Worth Knowing

🟢

Your app still works

The default SA being powerless only affects the cluster API. The pod can still talk to databases and other pods — that traffic doesn't use the SA. A pod on default with no Roles runs your app perfectly fine; it just can't manage Kubernetes itself.

⚠️

Never bind to the default SA

A RoleBinding → default SA silently grants those permissions to every pod in the namespace that didn't pick its own SA. Always create a named SA for any workload needing API access and bind to that.

🔒

Disable the token if unused

If a pod never calls the API server (most app pods), set automountServiceAccountToken: false. The default SA is still assigned, but no token sits in the container for an attacker to steal.

2.3 Authentication Methods (Deep Dive)

The API server supports many authenticators simultaneously. Each request is tried against each authenticator in order; the first one to return a success result wins.

X.509 Client Certificates

The most common way to authenticate kubeadm-bootstrapped clusters. The client presents a certificate signed by the cluster's CA. The Common Name (CN) becomes the username; Organization (O) fields become groups.

create-user-cert.shbash
# 1. Generate key + CSR
openssl genrsa -out ahmed.key 2048
openssl req -new -key ahmed.key -out ahmed.csr \
  -subj "/CN=ahmed@jahez.com/O=engineering/O=oncall"

# 2. Submit CSR to Kubernetes
cat <<EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: ahmed-csr
spec:
  request: $(cat ahmed.csr | base64 | tr -d '\n')

Tokens signed by the API server itself. Modern clusters use Projected Bound Tokens — short-lived JWTs scoped to a specific pod and audience.

Authenticating Proxy

An upstream proxy (oauth2-proxy, nginx) terminates auth and forwards requests with X-Remote-User, X-Remote-Group headers. The API server trusts these headers when the proxy presents a valid client cert.

Common for self-hosted dashboards, browser-based kubectl alternatives. Less common in modern setups (OIDC is simpler).

2.4 ServiceAccount lifecycle

A ServiceAccount is not a password stored somewhere. It is a name in etcd plus short-lived tokens that are minted, mounted, refreshed and killed automatically. Follow one workload — order-dispatcher in jahez-prod — from kubectl apply to deletion. Tap a step number or use the buttons; the diagram highlights who is doing the work.

Step 1 of 11 · You → API server → etcd

Create the ServiceAccount

  • The request goes through authentication, RBAC and admission like any object, then is stored in etcd with a new uid.
  • Since Kubernetes 1.24 no token Secret is created. The ServiceAccount is only a name, a uid and a few settings.
  • It can do nothing yet: a new ServiceAccount has zero permissions.
Step 2 of 11 · You → API server → etcd

Grant permissions with RBAC

  • A Role lists exactly what the app needs: read its own ConfigMap, and manage its leader-election Lease.
  • A RoleBinding hands that Role to the ServiceAccount. Subjects are matched by name, not uid.
  • Order does not matter: the binding can exist before the ServiceAccount or the Role.
Step 3 of 11 · You → Deployment → ReplicaSet controller

Assign it to the Pods

  • Set serviceAccountName in the Pod template of the Deployment.
  • The Deployment controller creates a ReplicaSet; the ReplicaSet controller then sends one Pod CREATE per replica, acting as system:serviceaccount:kube-system:replicaset-controller.
  • On a running Pod the field is immutable. On a Deployment, changing it rolls out new Pods.
Step 4 of 11 · ServiceAccount admission plugin

Admission mutates the Pod

  • Empty serviceAccountName? It is set to default.
  • It checks the ServiceAccount exists. If not, the Pod is rejected and the ReplicaSet shows FailedCreate: error looking up service account jahez-prod/order-dispatcher-service-account: serviceaccount "order-dispatcher-service-account" not found.
  • It copies the ServiceAccount's imagePullSecrets if the Pod has none.
  • Unless automount is false, it adds a projected volume kube-api-access-<random> and mounts it read-only in every container (init containers too) at /var/run/secrets/kubernetes.io/serviceaccount.
Step 5 of 11 · Scheduler · kubelet · TokenRequest API

Scheduled → kubelet requests a token

  • The scheduler binds the Pod to ip-10-20-1-15; that node's kubelet picks it up.
  • The kubelet calls the TokenRequest API for the Pod's ServiceAccount, asking for ~1 hour (3607 s) and binding the token to this Pod's name and uid.
  • The Node authorizer only lets a kubelet request tokens for Pods scheduled on its own node.
  • The API server signs a JWT with the cluster's ServiceAccount signing key. The token is not stored anywhere in the cluster.
Step 6 of 11 · kubelet

kubelet writes the files and starts the container

  • The projected volume is a tmpfs (RAM), never written to the node's disk.
  • Three files appear: token (from TokenRequest), ca.crt (ConfigMap kube-root-ca.crt), namespace (downward API).
  • Files are swapped atomically through a ..data symlink, so the app never reads a half-written token.
  • Only now does the container start.
Step 7 of 11 · Your code → API server

The app calls the API

  • "In-cluster config" = env vars KUBERNETES_SERVICE_HOST/PORT + token + ca.crt → https://kubernetes.default.svc.
  • Authentication: the API server checks the signature, expiry and audience, then checks that the bound Pod still exists with the same uid and the ServiceAccount uid matches.
  • Result: user system:serviceaccount:jahez-prod:order-dispatcher-service-account, groups system:serviceaccounts, system:serviceaccounts:jahez-prod, system:authenticated.
  • Authorization: RBAC allows the ConfigMap read (200) and denies anything else (403).
Step 8 of 11 · kubelet → TokenRequest API

Rotation

  • The kubelet refreshes the token when it is older than 80% of its lifetime (or 24 h) — about every 48 minutes here.
  • The new token is swapped in through ..data; the old one keeps working until its own expiry.
  • Your app must re-read the file. client-go and the C# KubernetesClient reload it automatically. Code that reads the token once at startup keeps working only because of the 1-year extension, and shows up as stale-token use in audit logs.
Step 9 of 11 · Pod → Vault / AWS STS

Use the identity outside the cluster (optional)

  • Add a second projected token with its own audience (here vault.jahez.internal). It is useless against the Kubernetes API.
  • The external service validates the JWT with the cluster's public keys: OIDC discovery at /.well-known/openid-configuration → /openid/v1/jwks (EKS publishes this issuer URL).
  • AWS IRSA works the same way, with audience sts.amazonaws.com and the eks.amazonaws.com/role-arn annotation on the ServiceAccount.
Step 10 of 11 · You / controller → API server

Pod deleted → its token dies

  • The token is bound to the Pod uid, so the API server rejects it as soon as the Pod is gone — even before exp.
  • The tmpfs volume is wiped with the Pod: the token never touched the disk.
  • The ReplicaSet creates a replacement Pod, which goes back to step 4 and gets a brand-new token.
Step 11 of 11 · You → API server

ServiceAccount deleted → end of life

  • Every token of that ServiceAccount fails the uid check → running Pods get 401 on their next API call.
  • Running Pods are not killed; they just lose API access.
  • New Pods are rejected at admission → the ReplicaSet reports FailedCreate.
  • Trap: the RoleBinding stays. Recreate a ServiceAccount with the same name and it gets a new uid but inherits the old permissions, because bindings match by name. Delete the RBAC objects too.

3Authorization

3.1 Authorization — What Can You Do?

After AuthN succeeds, the API server knows who the request is from. Authorization decides whether that identity is allowed to perform the requested action on the requested resource.

How Multiple Authorizers Combine

The API server runs all configured authorizers in order. Each returns one of three verdicts:

✓

Allow

Request proceeds to admission. No other authorizers consulted.

✗

Deny

Hard reject — request fails immediately with 403, regardless of other authorizers.

?

NoOpinion

Pass to next authorizer. If all say NoOpinion, request is denied.

Default for missing rules Kubernetes is deny-by-default: if no Allow rule matches, the request is denied. You only need to write Allow rules; you never write Deny rules in RBAC.

Available Authorization Modes

ModeUse CaseHow It Works
RBAC Default for human & SA permissions Roles + Bindings stored as cluster objects
Node kubelet → API server Auto-authorizes kubelets to read pods on their own node
ABAC Legacy, rarely used Policy file loaded at startup; no runtime updates
Webhook Custom external authorizer API server POSTs SubjectAccessReview to your service
AlwaysAllow Dev only — never production Every request authorized (no AuthZ)

3.2 RBAC Deep Dive

RBAC (Role-Based Access Control) is the standard authorization mechanism in Kubernetes. It composes four resource types into permission grants.

A Binding glues Subjects (who) to a Role (what they can do)

The Four RBAC Objects

Role

Namespaced. Defines permissions within one namespace — like "can read pods in payments".

ClusterRole

Cluster-wide. Defines permissions on cluster-scoped resources (nodes, PVs, CRDs) or namespace-scoped resources across all namespaces.

RoleBinding

Namespaced. Grants a Role (or ClusterRole) to subjects, scoped to one namespace.

ClusterRoleBinding

Cluster-wide. Grants a ClusterRole to subjects across the entire cluster.

Mixing & Matching

CombinationEffect
RoleBinding → RolePermissions scoped to the binding's namespace.
RoleBinding → ClusterRoleClusterRole's permissions applied only within the binding's namespace. Useful for reusing common permission sets.
ClusterRoleBinding → ClusterRoleCluster-wide permissions everywhere.
ClusterRoleBinding → RoleInvalid — Kubernetes will reject this.

3.4 Advanced RBAC Patterns

Real clusters rarely have one-subject-one-role bindings. This section covers multi-subject bindings, aggregated ClusterRoles, role composition, and the relationship architecture that ties it all together.

The Full RBAC Relationship Model

Before the patterns, internalize how the four objects relate. RBAC is a many-to-many graph: many subjects can share one binding, many bindings can point at one role, and a role's rules are an additive set.

RBAC is a many-to-many graph · a subject's effective permission is the UNION of all its bindings

Pattern 1 — One Binding, Many Subjects of Mixed Types

A single subjects array can hold any mix of Users, Groups, and ServiceAccounts. They all receive the same role. This is the cleanest way to grant identical access to a heterogeneous set of identities.

adv-01-multi-subject.yamlyaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: payments
  name: incident-responder-role
rules:
- apiGroups: ["", "apps"]
  resources: ["pods", "pods/log", "deployments", "events"]
  verbs: ["get", "list", "watch"]
- apiGroups: [""]
  resources: ["pods/exec"]
  verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1

metadata:
  name: incident-responders-role-binding
  namespace: payments

# 1) An individual human user
- kind: User
  name: ahmed@jahez.com
  apiGroup: rbac.authorization.k8s.io
# 2) Another individual user
- kind: User
  name: sara@jahez.com
  apiGroup: rbac.authorization.k8s.io
# 3) An entire group from the OIDC provider
- kind: Group
  name: oidc:sre-oncall
  apiGroup: rbac.authorization.k8s.io
# 4) A ServiceAccount used by an automated triage bot
- kind: ServiceAccount
  name: triage-bot-service-account

# 5) A ServiceAccount from a DIFFERENT namespace
- kind: ServiceAccount

Property Reference
PropertyExplanation
subjects (array)Holds any number of entries of any mixed kind. All entries receive the exact same roleRef.
kind: User + apiGroupFor User and Group, apiGroup is rbac.authorization.k8s.io and no namespace is set (users are not namespaced).
kind: GroupGrants the role to every identity carrying that group claim — the most scalable subject type.

Key rule A binding has many subjects but exactly one roleRef. If you need a subject to have two roles, you create two bindings. roleRef is also immutable — to change which role a binding points at, you must delete and recreate it.

Pattern 2 — One Subject Across Many Bindings (Permission Stacking)

The inverse pattern. A single subject can appear in many bindings; its effective permission is the union of all of them. This is how you compose access from small, reusable roles.

Three small single-purpose roles compose into one effective permission set via the union rule

Pattern 3 — Aggregated ClusterRoles

An aggregated ClusterRole has an empty rules list and an aggregationRule with label selectors. Kubernetes automatically fills its rules by merging every ClusterRole whose labels match. Add a new matching ClusterRole and the aggregate updates itself — no edit to the parent.

adv-02-aggregated-clusterrole.yamlyaml
# Parent: rules are auto-filled by the controller
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-cluster-role
aggregationRule:
  clusterRoleSelectors:
  - matchLabels:
      rbac.jahez.io/aggregate-to-monitoring: "true"
rules: []   # ← left empty; controller populates it
---
# Child A — matches the selector, so it is merged in
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-pods-cluster-role
  labels:
    rbac.jahez.io/aggregate-to-monitoring: "true"
rules:
- apiGroups: [""]
  resources: ["pods", "nodes", "services"]
  verbs: ["get", "list", "watch"]
---
# Child B — also matches; merged in too
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: monitoring-metrics-cluster-role
  labels:
    rbac.jahez.io/aggregate-to-monitoring: "true"
rules:
- apiGroups: ["metrics.k8s.io"]
  resources: ["pods", "nodes"]
  verbs: ["get", "list"]
Property Reference
PropertyExplanation
aggregationRuleMarks this ClusterRole as an aggregate. Its presence tells the RBAC controller to manage rules automatically.
clusterRoleSelectors[].matchLabelsLabel query — any ClusterRole carrying these labels is merged into the parent.
rules: [] on the parentIntentionally empty. The controller overwrites it with the union of all matched children. Editing it manually is pointless — it gets reverted.

Anti-patternWhy it's badDo instead
Binding to the default SA Silently grants the permission to every pod that didn't pick its own SA. Create a named SA per workload; bind to that.
verbs: ["*"] + resources: ["*"] Effectively cluster-admin; impossible to audit; breaks least privilege. Enumerate the exact verbs and resources needed.

3.5 Node Authorizer & ABAC

Node Authorizer (always enabled)

A specialized authorizer that automatically grants kubelets exactly the permissions they need — and nothing more.

  • kubelet on node-A can only read pods scheduled to node-A
  • It can read Secrets, ConfigMaps, PVCs that are referenced by pods on its node
  • It can update only its own Node object status, not other nodes
  • Identifies kubelets by username prefix system:node: and group system:nodes
Why it's important Without this, a compromised kubelet could read every Secret in the cluster. Node authorizer is the boundary that contains node breaches.

ABAC (legacy)

Attribute-Based Access Control via a static policy file. Each line is a JSON object describing one allow rule. Loaded at API server startup — to change, you must restart the API server.

abac-policy.jsonljsonl
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy","spec":{"user":"alice","namespace":"*","resource":"*","apiGroup":"*"}}
{"apiVersion":"abac.authorization.kubernetes.io/v1beta1","kind":"Policy","spec":{"group":"system:authenticated","namespace":"*","resource":"events","readonly":true}}
Avoid ABAC for new clusters Inflexible (no hot reload), no fine-grained verbs, hard to audit. RBAC supersedes it.

4.2 Pod Security Admission (PSA)

Modern replacement for the deprecated PodSecurityPolicy. Built-in validating controller that enforces three security profiles at the namespace level.

The Three Profiles

privileged

Unrestricted — anything allowed. Use only for system namespaces.

baseline

Minimally restrictive. Prevents known privilege escalation. Easy migration path.

restricted

Heavily restricted. Industry-standard hardening. Run-as-non-root, drop capabilities, seccomp, etc.

Three Modes per Profile

For each profile, you choose what happens when a pod violates it:

5.1 kubectl Context & kubeconfig

A kubeconfig is your client's address book, not part of any cluster. It lives on the engineer's laptop and tells kubectl where to send each command. One file can list many clusters, but that does not connect them: every command goes to exactly one cluster, and each cluster has its own API server, CA, credentials and RBAC. Step through where the file lives, how a command picks a cluster, how that goes wrong, and how to prevent it.

Step 1 of 4 · Ahmed's laptop

Where the file lives

  • The kubeconfig is a client file on the laptop: ~/.kube/config, or whatever $KUBECONFIG points to.
  • kubectl reads it on every command to learn where to send the request and which credential to show.
  • The clusters never read it. Listing two clusters in one file does not connect them — like two numbers in a phone's contacts.
  • Each cluster is fully separate: its own API server, its own CA, its own RBAC, its own ServiceAccount tokens.
Step 2 of 4 · kubectl → staging API server

One command → one cluster

  • current-context is jahez-staging, so kubectl picks cluster jahez-staging-eks and user ahmed-staging.
  • It runs aws eks get-token for a short-lived token, sends the request to the staging API server URL, and verifies that server with the staging CA.
  • Staging authenticates Ahmed and checks its own RBAC: jahez-engineers = edit → 200.
  • Prod is not contacted at all. --context=jahez-prod would send one command to prod without changing the default.
Step 3 of 4 · Ahmed → prod API server (by accident)

The problem: the wrong context

  • Yesterday Ahmed ran kubectl config use-context jahez-prod to check a log. The file still says current-context: jahez-prod.
  • Today he cleans up staging: kubectl delete deploy order-dispatcher-deployment. Nothing on screen says which cluster he is in.
  • kubectl sends it to prod. Prod authenticates him correctly, and prod RBAC allows it because engineers have edit there too.
  • Result: the prod order-dispatcher is gone — orders stop being dispatched. Kubernetes did exactly what it was told.
Step 4 of 4 · Laptop habits + prod RBAC

The solution: make the context visible, prod hard to change

  • See it: show the active context in the shell prompt (⎈ jahez-prod in red).
  • Separate it: keep prod in its own file and load it only on purpose (KUBECONFIG=~/.kube/prod), so the default file cannot reach prod.
  • Limit it: in the prod cluster, humans get view; changes arrive only through GitOps (Argo CD). The same delete now returns 403.
  • No stored secrets: use exec plugins (aws eks get-token) that mint short-lived tokens instead of embedding certificates.

Does the context protect prod? Two cases

No. A context only decides which cluster gets the command. If you are logged in to both clusters and the command lands in prod, what happens next is decided inside prod: authentication, then RBAC, then admission. Two traps make the wrong-cluster mistake easy: use-context rewrites the shared file, so it switches every terminal; and nothing on screen forces you to look. The two cases below run the same accident with different prod permissions.

Case A — edit in staging, view in prod

Step 1 of 5 · Case A · edit in staging, view in prod

The setup

  • Ahmed is logged in to both clusters, and both contexts live in one ~/.kube/config.
  • Staging RBAC gives the group jahez-engineers edit. Prod RBAC gives the same group only view.
  • Changes to prod come from Argo CD, whose ServiceAccount has edit in prod.
Step 2 of 5 · Terminal A → the shared file

Terminal A switches to prod

  • In terminal A Ahmed runs kubectl config use-context jahez-prod to read a log.
  • use-context edits the file itself: current-context is now jahez-prod.
  • Terminal B reads the same file, so terminal B is now on prod too — its prompt may still look like staging if it was not refreshed.
Step 3 of 5 · Terminal B → prod API server

Terminal B sends the delete to prod

  • Ahmed returns to terminal B to clean staging and runs kubectl delete deploy order-dispatcher-deployment.
  • kubectl reads current-context: jahez-prod and sends the request to the prod API server.
  • Authentication succeeds: the AWS token is valid, so prod knows this is ahmed@jahez.com in group jahez-engineers.
Step 4 of 5 · Prod RBAC

Prod RBAC stops it

  • Prod RBAC looks for a rule that lets jahez-engineers delete deployments in jahez-prod. There is none — only view.
  • The API server returns 403 Forbidden. Nothing reaches admission or etcd; the Deployment is untouched.
  • The mistake still happened, but it could not do damage. This is the real protection — the kubeconfig did nothing to stop it.
Step 5 of 5 · Laptop

Habits that stop the mix-up

  • Never use-context prod. Pass --context on each command, so no terminal has prod as its default.
  • Or use kubie: each kubie ctx opens a shell with its own copy of the file, so switching in one terminal cannot change another.
  • With an explicit context the same delete goes to staging, where Ahmed has edit — exactly what he meant.

5.2 Pod & Container SecurityContext

SecurityContext defines privilege and access control settings for a Pod or Container — UID, capabilities, filesystem mode, SELinux, seccomp. Distinct from RBAC: this controls what happens inside the container at the OS level.

The walkthrough below starts from a Pod with no securityContext and an attacker who already has a shell in it, then adds one property per step. Each step shows the problem, the fix, the full Pod YAML and what the attacker sees.

Step 1 of 10 · The problem

Default: no securityContext

  • The .NET image was built without a USER line, so the app runs as uid 0 = root.
  • A bug in the app (say an unsafe file upload) gives an attacker a shell. They are root inside the container.
  • A container is not a VM: it is an ordinary process on the node's kernel. Root inside is uid 0 on the node too, held back only by a few walls.
  • With root they can rewrite the app, install tools, send raw packets to neighbours, and if any wall breaks, take over the node.
Step 2 of 10 · Fix ① · Pod securityContext

runAsUser / runAsGroup: pick a non-root number

  • Linux does not care about names. Every process carries a UID (user number) and GID (group number); names like root or app are just labels from the image's /etc/passwd.
  • runAsUser: 10001 makes the process uid 10001 — a plain user with no special rights. 10001 does not even need a name.
  • Now it can only write files whose owner or group lets it. /app, /usr and /etc belong to uid 0 → Permission denied.
  • New problem: the PVC at /data is owned by uid 0 too, so the app can no longer save its files. Step 4 fixes that.
Step 3 of 10 · Fix ② · kubelet check at start

runAsNonRoot: refuse images that would run as root

  • runAsUser is a setting. runAsNonRoot: true is a check: the kubelet refuses to start a container whose final UID would be 0.
  • It protects you when someone later removes runAsUser, or a new image tag switches back to root.
  • Here a team adds a report tool from the stock nginx image. Its Dockerfile has no USER, so it would run as root → CreateContainerConfigError.
  • Trap: if the image says USER app (a name, not a number), the kubelet cannot prove it is non-root and also refuses. Use a numeric USER or set runAsUser.
Step 4 of 10 · Fix ③ · Pod securityContext

fsGroup: let the non-root user write its volume

  • A fresh EBS volume is owned by uid 0, so uid 10001 cannot write /data.
  • fsGroup: 10001 tells the kubelet: give this volume to group 10001, make it group-writable, and add 10001 to the process's groups.
  • New files inherit the group (setgid bit s), so every container in the Pod can share them.
  • fsGroupChangePolicy: OnRootMismatch skips the slow recursive change when the volume is already correct.
Step 5 of 10 · Fix ④ · container securityContext

allowPrivilegeEscalation: no way back to root

  • Images often contain setuid programs (su, sudo, passwd, old ping). Running one switches the process to the file owner's UID — root.
  • So uid 10001 alone is not enough: the attacker runs a setuid binary, or exploits one, and is root again.
  • allowPrivilegeEscalation: false sets the kernel flag no_new_privs: setuid bits and file capabilities are ignored for this process and all its children.
Step 6 of 10 · Fix ⑤ · container securityContext

capabilities: drop ALL, add back only what you need

  • Linux splits root's power into about 40 capabilities. A process with a capability can do that one privileged thing, even as non-root (via file capabilities).
  • The container runtime gives 14 by default — e.g. NET_RAW lets a process craft raw packets: ARP-spoof or sniff neighbours on the Pod network.
  • drop: ["ALL"] removes every one. The app keeps working because a normal API on port 8080 needs none.
  • Dangerous ones never to add to apps: SYS_ADMIN (mount, almost root), SYS_TIME (change the clock of the whole node), NET_ADMIN (firewall rules), SYS_PTRACE (read other processes' memory).
Step 7 of 10 · Fix ⑥ · container securityContext

readOnlyRootFilesystem: nothing can be dropped into the image

  • Even as uid 10001, the attacker could write anywhere the image allows — some images have world-writable paths.
  • readOnlyRootFilesystem: true mounts the whole image read-only, even for root. No miners, no web shells, no edited config.
  • The app still needs scratch space: .NET writes to /tmp, so mount an emptyDir there. Volumes like /data stay writable.
Step 8 of 10 · Fix ⑦ · Pod securityContext

seccompProfile: block dangerous kernel calls

  • Everything a program does goes through system calls to the shared kernel: open, connect, mount, unshare, ptrace, bpf…
  • Many container-escape exploits rely on rarely used calls (for example unshare to build a new user namespace, then a kernel bug).
  • seccompProfile: RuntimeDefault applies the runtime's filter: normal app calls pass, the risky ones return Operation not permitted.
Step 9 of 10 · What never to do in an app

privileged: true removes every wall

  • privileged: true = root + all 41 capabilities + every host device (/dev/nvme0n1…) + no seccomp. With hostPID it also sees every process on the node.
  • From such a Pod an attacker enters the node's namespaces and is root on the node — able to read every other Pod's Secrets and tokens from /var/lib/kubelet.
  • Only node agents need it (CNI, CSI node plugins). Pod Security Admission baseline and restricted reject it.
Step 10 of 10 · The hardened Pod

All together

  • Each property closes one door: who you are (①②), what you can share (③), whether you can climb back (④), which root powers exist (⑤), what you can change (⑥), which kernel calls you can make (⑦).
  • The same attacker now has a shell as uid 10001 with no capabilities, a read-only image, no setuid escape and a filtered kernel — and the app works normally.
  • This exact set is what Pod Security Admission restricted requires (see 4.2).

5.4 Secrets Management

Kubernetes Secrets store sensitive data, but they're not encrypted by default — they're base64 encoded. Treat them as plaintext unless you've enabled encryption at rest.

The Five Layers of Secret Hardening

1

Encryption at Rest (etcd)

Configure --encryption-provider-config on kube-apiserver to encrypt Secrets in etcd with AES-CBC or KMS. Without this, anyone with etcd access reads them.

2

RBAC on Secrets

Never grant list or get on secrets to humans broadly. Limit Secret access to specific ServiceAccounts with resourceNames.

3

External Secret Stores

Vault, AWS Secrets Manager, GCP Secret Manager. Pull at runtime via External Secrets Operator or CSI Secret Store driver. Master secret never lives in etcd.

4

GitOps with SealedSecrets / SOPS

Need secrets in Git? Use Bitnami SealedSecrets (encrypts with a cluster-side controller key) or Mozilla SOPS (encrypts per-field). Plaintext never reaches Git.

5

Audit & Rotation

Enable Kubernetes audit logging for Secret operations. Rotate secrets on a schedule (90 days) and on personnel changes.

7.1 Designing an RBAC Database Model

Step out of Kubernetes for a moment. Suppose you're a software engineer building your own RBAC system — for a SaaS app, an internal tool, anything. How do you model it in a relational database? Should subjects share a table or each get their own? This section is a deep dive into that design decision.

The Core Entities

Every RBAC system, Kubernetes included, reduces to the same conceptual pieces. Name them clearly first:

🎭

Subject

The "who" — a user, a group, a service account, an API key. The thing that holds permissions.

📋

Role

A named bundle of permissions. The "what can be done", reusable across many subjects.

🔑

Permission

A single atomic grant — a (verb, resource) pair like (read, invoices).

🔗

Binding / Assignment

The join that connects a Subject to a Role. The "who has what".

The Easy Part — Role, Permission, and the Join

Three of the four entities are uncontroversial. A Role has many Permissions, a Permission can belong to many Roles — a classic many-to-many resolved with a junction table:

schema — roles & permissionssql
CREATE TABLE roles (
  id          BIGSERIAL PRIMARY KEY,
  name        TEXT NOT NULL UNIQUE,
  description TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE permissions (
  id        BIGSERIAL PRIMARY KEY,
  action    TEXT NOT NULL,   -- 'read', 'write', 'delete'
  resource  TEXT NOT NULL,   -- 'invoices', 'reports'
  UNIQUE(action, resource)
);

-- junction: many roles <-> many permissions
CREATE TABLE role_permissions (
  role_id       BIGINT REFERENCES roles(id) ON DELETE CASCADE,
  permission_id BIGINT REFERENCES permissions(id) ON DELETE CASCADE,
  PRIMARY KEY (role_id, permission_id)
);

Nothing tricky here. The real design question is the fourth entity — the binding — because a binding must point at a Subject, and subjects come in different types: users, groups, service accounts, API keys. How do you store a foreign key to "any of several different tables"?

The name of the problem This is called the polymorphic association problem (sometimes "polymorphic relationship" or "generic relationship"). It is not aggregation or composition — those are UML object-relationship terms. The precise term for "a foreign key that can reference one of several tables" is polymorphic association. Knowing the name lets you find the established solutions.

Aggregation vs Composition — Clearing Up the Terms

You asked whether this is aggregation or composition. Those terms describe lifecycle ownership between objects, which is a different axis from the polymorphic-FK problem. Worth pinning down so you use them correctly:

TermMeaningIn RBAC terms
Composition Strong "part-of" — the child cannot exist without the parent; deleting the parent deletes the child. A RoleBinding is composed into nothing — but a role_permissions row is composition-like: it dies with its role (ON DELETE CASCADE).
Aggregation Weak "has-a" — the child can exist independently; deleting the parent leaves the child alive. A Role aggregates Permissions — delete the role and the permissions still exist for other roles to use.
Polymorphic association A reference that can point to one of several entity types. The actual problem here — a binding referencing User or Group or ServiceAccount.

So the honest answer: a Role aggregates permissions (weak ownership), and the subject-reference question is a polymorphic association. Those are two different concepts and your design touches both.

The Central Question, Visualized

A single FK column can't natively point at three different tables — this is the polymorphic association problem

The Four Solutions

There are four established ways to model the subject reference. We'll go through each with schema, an ER diagram, and trade-offs.

Solution A — A Separate Binding Table per Subject Type

Each subject type gets its own dedicated binding table, each with a real, enforced foreign key. This is essentially what Kubernetes' API does conceptually (different subject kinds, strongly typed).

solution-a.sqlsql
CREATE TABLE user_role_bindings (
  id      BIGSERIAL PRIMARY KEY,
  user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role_id BIGINT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  UNIQUE(user_id, role_id)
);

CREATE TABLE group_role_bindings (
  id       BIGSERIAL PRIMARY KEY,
  group_id BIGINT NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
  role_id  BIGINT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  UNIQUE(group_id, role_id)
);

CREATE TABLE sa_role_bindings (
  id    BIGSERIAL PRIMARY KEY,
  sa_id BIGINT NOT NULL REFERENCES service_accounts(id) ON DELETE CASCADE,
  role_id BIGINT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  UNIQUE(sa_id, role_id)
);
Solution A — every subject type gets its own binding table with a real FK

Benefits: Every foreign key is real and database-enforced — referential integrity is guaranteed. Type-specific columns are natural (a user binding could have an expires_at, a SA binding might not). Query plans are simple and well-indexed.

Costs: "List all bindings for any subject" requires a UNION across N tables. Adding a new subject type means a new table plus touching every query. Application code has N near-identical paths.

Choose A when Subject types are few and stable (2–4, rarely changing), referential integrity is non-negotiable, and the subject types genuinely differ in their columns/behavior. This is the safest default for most systems.

Solution B — A Shared subjects Supertype Table

Introduce one parent subjects table that every concrete type extends. Each user/group/SA row also has a row in subjects sharing the same id. The binding's FK points at subjects — a single, real, enforced FK. This is the Class Table Inheritance pattern.

solution-b.sqlsql
-- the supertype: one row per subject of ANY kind
CREATE TABLE subjects (
  id           BIGSERIAL PRIMARY KEY,
  subject_type TEXT NOT NULL      -- 'user' | 'group' | 'service_account'
                 CHECK (subject_type IN ('user','group','service_account')),
  display_name TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- subtypes: PK is also a FK back to the supertype
CREATE TABLE users (
  id     BIGINT PRIMARY KEY REFERENCES subjects(id) ON DELETE CASCADE,
  email  TEXT NOT NULL UNIQUE,
  password_hash TEXT NOT NULL
);
CREATE TABLE groups (
  id   BIGINT PRIMARY KEY REFERENCES subjects(id) ON DELETE CASCADE,
  name TEXT NOT NULL UNIQUE
);
CREATE TABLE service_accounts (
  id    BIGINT PRIMARY KEY REFERENCES subjects(id) ON DELETE CASCADE,
  token_hash TEXT NOT NULL
);

-- ONE binding table, ONE real FK
CREATE TABLE role_bindings (
  id         BIGSERIAL PRIMARY KEY,
  subject_id BIGINT NOT NULL REFERENCES subjects(id) ON DELETE CASCADE,
  role_id    BIGINT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  UNIQUE(subject_id, role_id)
);
Solution B — a shared supertype; subtype PKs double as FKs into it

Benefits: One binding table, one real enforced FK — full referential integrity and no UNIONs. "List all bindings" is a trivial join. Adding a new subject type = one new subtype table; role_bindings never changes. Common columns (display_name, created_at) live in one place.

Costs: Creating a user is now a two-row insert (subjects + users) — wrap it in a transaction. Fetching a fully-typed subject needs a join to the right subtype. Slightly more schema upfront.

Choose B when You expect subject types to grow over time, you want one uniform binding path in code, and you still refuse to give up FK integrity. This is the best general-purpose answer for a serious RBAC system — it's how mature platforms model it.

Solution C — Polymorphic Columns (subject_type + subject_id)

One binding table with two columns: a subject_type string and a subject_id number. The application interprets them together. Popular in ORMs (Rails calls it a polymorphic association; Laravel calls it morphs).

solution-c.sqlsql
CREATE TABLE role_bindings (
  id           BIGSERIAL PRIMARY KEY,
  subject_type TEXT NOT NULL      -- 'user' | 'group' | 'service_account'
                 CHECK (subject_type IN ('user','group','service_account')),
  subject_id   BIGINT NOT NULL,    -- NO foreign key possible!
  role_id      BIGINT NOT NULL REFERENCES roles(id),
  UNIQUE(subject_type, subject_id, role_id)
);
-- subject_id cannot be a real FK — it points at different
-- tables depending on subject_type. Integrity is the app's job.
Solution C — one table, but the FK is dashed: the database cannot enforce it

Benefits: Dead simple — one table, trivial to add subject types (just a new allowed string). Zero schema migrations for new types. ORMs support it natively, so it's fast to ship.

Costs: No referential integrity — the database cannot guarantee subject_id points at a real row. Delete a user and orphaned bindings linger. No ON DELETE CASCADE. Joins need a CASE/conditional and indexes are weaker. All correctness moves into application code (and triggers, if you bolt them on).

Choose C only when You're prototyping, the team strongly relies on an ORM that favors it, or subject types are wildly dynamic. For a security-critical system like RBAC, the loss of FK integrity is a real liability — orphaned permission grants are a genuine vulnerability. Prefer B.

Solution D — Exclusive Arc (Multiple Nullable FKs)

One binding table with one nullable FK column per subject type, plus a constraint enforcing that exactly one is non-null. Each FK is real and enforced — you keep integrity without a supertype table.

solution-d.sqlsql
CREATE TABLE role_bindings (
  id      BIGSERIAL PRIMARY KEY,
  role_id BIGINT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
  -- one real FK per subject type, all nullable
  user_id BIGINT REFERENCES users(id) ON DELETE CASCADE,
  group_id BIGINT REFERENCES groups(id) ON DELETE CASCADE,
  sa_id    BIGINT REFERENCES service_accounts(id) ON DELETE CASCADE,
  -- the "arc": exactly ONE subject column may be set
  CONSTRAINT one_subject CHECK (
    (CASE WHEN user_id  IS NOT NULL THEN 1 ELSE 0 END)
  + (CASE WHEN group_id IS NOT NULL THEN 1 ELSE 0 END)
  + (CASE WHEN sa_id    IS NOT NULL THEN 1 ELSE 0 END) = 1
  )
);
Solution D — every FK is real; a CHECK constraint enforces exactly one is used

Benefits: Full referential integrity on every subject type, in one table, with no supertype. ON DELETE CASCADE works per type. The CHECK constraint makes "exactly one subject" a database guarantee.

Costs: The table widens with every new subject type — add a column and update the CHECK. Queries are slightly awkward (COALESCE or per-column filters). Doesn't scale gracefully past a handful of types.

Choose D when You have a small fixed set of subject types (2–4), you want one binding table, and you want the database — not the app — to guarantee integrity, but you don't want the extra subjects supertype table of Solution B.

When Separate vs When Shared — The Principle

Strip it down to the underlying decision rule, which generalizes far beyond RBAC:

1

Do the types share behavior and get treated uniformly?

If the rest of the system constantly says "for any subject, do X" — list them together, bind them together — that uniformity is a signal to share a table (Solution B or D). If each type is handled by genuinely separate code paths, separate tables (A) reflect reality.

2

How different are the columns?

If users, groups, and SAs share most fields, a shared/supertype table avoids duplication. If they diverge heavily (few common columns), forcing them together creates a sparse table full of nulls — separate tables are cleaner.

3

How often will new types appear?

A fixed set that will never change → separate tables are fine. An open-ended set → a shared model (B) means new types don't ripple through every query and migration.

4

Can you afford to lose FK integrity?

For an RBAC system — almost never. That single rule eliminates Solution C for production. Among the integrity-preserving options, pick by type count: few & fixed → A or D; many & growing → B.

The formal vocabulary The problem is a polymorphic association. Solution B is Class Table Inheritance (a supertype/subtype pattern, also called Table-Per-Type). Solution D is the exclusive arc (or exclusive-belongs-to). The Role↔Permission relationship is aggregation. Solution C is what ORMs market as a "polymorphic association" — accurate name, but it trades away the database's strongest guarantee.

The Recommended Model

For a real, security-critical RBAC system that should age well, Solution B (shared supertype) is the strongest default: one uniform binding table, full referential integrity, and graceful growth as subject types multiply. Here's the complete picture tied together:

"Who Can Do X?" — The Resolution Query

Whatever model you pick, the payoff is answering the authorization question. With Solution B it's one clean join chain:

authorize.sqlsql
-- Does subject 42 have permission (read, invoices)?
SELECT EXISTS (
  SELECT 1
  FROM role_bindings      rb
  JOIN role_permissions  rp ON rp.role_id = rb.role_id
  JOIN permissions       p  ON p.id = rp.permission_id
  WHERE rb.subject_id = 42
    AND p.action   = 'read'
    AND p.resource = 'invoices'
) AS allowed;

That single query is your authorizer — the relational equivalent of what the Kubernetes API server does when it evaluates RBAC. Note the structural echo: subjects ≈ K8s subjects, role_bindings ≈ RoleBinding, roles ≈ Role, permissions ≈ a Role's rules. You've effectively rebuilt Kubernetes RBAC in SQL.

The takeaway The problem is a polymorphic association. For production RBAC, never sacrifice referential integrity — that rules out the bare polymorphic-column approach. Pick the shared supertype model when subject types will grow, separate tables (or an exclusive arc) when they're few and fixed. The Role-to-Permission link is aggregation. Name the patterns correctly and the right schema follows from the constraints.

      object.spec.template.spec.containers.all(c, has(c.resources.limits) && has(c.resources.limits.memory))
