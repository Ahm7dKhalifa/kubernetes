Volume · Reliability Engineering · jahez-prod

System Reliability Engineering

Also called dependability engineering. Five words get used interchangeably in incident reviews: availability, reliability, resilience, fault tolerance, self-healing. They answer different questions, sit at different layers, and run on different clocks. This guide separates them, then puts them back together on a real Jahez request path.

Definition
Reliability is the ability of a system to consistently perform its intended function correctly over time, even when failures occur.

In plain terms: can customers keep ordering when things go wrong?

01 · Vocabulary

The four properties, one question each

Each term is a question you ask about the system. If you can name the question, you can name the property.

AvailabilityIs the system reachable right now?The Jahez app opens and the API gateway answers. Measured as uptime: 99.99%.
ReliabilityDoes it keep working correctly over time?Of 1,000 checkout attempts, 998 become real orders. Measured as success rate.
ResilienceCan it recover from failures?The orders primary in PostgreSQL fails → failover → recovery → service restored.
Fault toleranceCan it keep operating during a failure with no interruption?Node in me-central-1a dies, replicas in 1b and 1c keep serving. Customers notice nothing.
DependabilityAvailability + Reliability + Resilience + Fault ToleranceThe umbrella property. When leadership asks "can we trust the platform during Ramadan iftar peak?", they are asking about dependability.
02 · The classic trap

A service can be available but unreliable

Uptime only says the front door opens. It says nothing about whether checkout succeeds behind it. A pod that returns 200 OK on /health while every POST /orders fails with a payment timeout is 100% available and badly unreliable.

Try it · example numbers, not production data

Why the error budget matters

An SLO of 99.9% on checkout allows 1 failure per 1,000 attempts. Two failures means the budget is spent twice over, even though uptime looks perfect. SRE practice is to freeze risky releases when the budget is gone. That is a reliability decision, not an availability one.

03 · The pair people confuse most

Reliability vs fault tolerance

Reliability is about how often things go wrong. Fault tolerance is about what happens when they go wrong.

AspectReliabilityFault tolerance
FocusCorrect operation over timeSurviving component failures
Question"How often does it fail?""What happens when it fails?"
Measured byError rate, success rate, MTBFContinuity during failure, zero user impact
GoalMinimize failuresHide failures
Payment service9,990 of 10,000 succeed (99.9%)Node A fails, Node B takes over, nobody notices
In KubernetesPods rarely crash, readiness keeps traffic off unready podsReplicas across zones, Service shifts traffic away from dead endpoints

The two are independent axes

Not fault tolerant
Fault tolerant
Reliable
Reliable but fragileWorks correctly almost all the time. A single node loss takes it down. Example: one-replica promo-engine with perfect code.
DependableLow error rate and survives node or zone loss. Target for order-service.
Unreliable
NeitherBuggy and single-point. Fails often, fails hard.
Survives, still flakyThree replicas across zones, but a race condition fails 1% of requests. Redundancy cannot fix bad logic.
Key relationship

Fault tolerance is one of the main ways to achieve reliability. Reliability is the broader outcome: faults happen, fault tolerance absorbs them, the system keeps running, and over time fewer failures become visible.

04 · Putting it together

Two paths after a fault

When a fault occurs, either fault tolerance hides it completely, or it leaks into service impact and resilience brings you back. Both paths feed reliability over time.

05 · Kubernetes mechanism

Self-healing

Self-healing is the platform's ability to detect failures and restore the desired state without a human. Kubernetes constantly checks your workloads and fixes them when something breaks.

FailureWho detectsActionTypical time
Container process exitskubeletRestart container per restartPolicy, with CrashLoop backoff (10s → 5m cap)Seconds
App deadlocked, process alivekubelet via liveness probeKill and restart container after failureThresholdperiodSeconds × failureThreshold
App up but not readykubelet via readiness probeRemove pod IP from EndpointSlice. No restart.Seconds
Pod deleted or evictedReplicaSet / StatefulSet / DaemonSet controllerCreate a replacement pod; scheduler places itSeconds
Node unreachablenode-lifecycle controllerTaint node, evict pods after toleration expires, controllers create replacements elsewhere~40s detect + 300s default toleration
Node resource pressurekubelet eviction managerEvict pods by QoS class and prioritySeconds
Precision note on "rescheduling"

Kubernetes never moves a pod. A pod is bound to its node for life. On node failure the pod is evicted, and its controller creates a new pod with a new name and IP that the scheduler places elsewhere. A bare pod with no controller is simply gone. Also, eviction waits for the default tolerationSeconds: 300 on node.kubernetes.io/unreachable. For latency-sensitive services you can shorten it (see section 11).

Liveness probe pitfall

Never check PostgreSQL, Redis or Elasticsearch from a liveness probe. If Redis blips, every menu-service pod restarts at once and turns a dependency hiccup into a full outage. Dependencies belong in readiness at most, and often not even there.

07 · Different levels of concept

Self-healing vs resilience

Self-healing is a mechanism inside the platform. Resilience is a property of the whole system, apps plus infrastructure. Self-healing is one building block of resilience, and resilience is much bigger.

AspectSelf-healingResilience
LevelMechanism: how the system fixes itselfProperty: how the system behaves under failure
ScopeKubernetes / infrastructureEntire system (apps + infra)
FocusRecovery actionsEnd-to-end behavior
Question"Can it fix itself?""Can it survive and keep working?"
ClockSystem time: seconds to minutesRequest time: milliseconds
Owner at JahezPlatform team (manifests, probes, PDBs)Service team (timeouts, fallbacks) + platform
Self-healing without resilience fails when…
  • Recovery is slower than customer patience (pod takes 90s to warm up)
  • The service collapses under load before a replacement is ready
  • A dependency fails and nothing restarts it, because it is outside the cluster
Resilience patterns
  • Timeouts per dependency
  • Bounded retries with jittered backoff
  • Circuit breakers
  • Fallback and graceful degradation (cache, empty section)
  • Failover to replica
08 · Jahez case study

Search aggregator: one failure, two responses

search-aggregator in jahez-prod fans out to three services, merges the results and returns the restaurant search page: personalization-service, recommendation-service and ads-service (sponsored restaurant slots). Walk through what happens when ads fails.

09 · Validate the model

Mental-model correction

Incorrect statement

"Self-healing only means the user will receive a totally crashed response because one service failed."

Corrected

Self-healing says nothing about what the user receives during the failure. It is about how the platform restores broken components to a healthy state afterwards. What the user receives is decided by resilience in the calling service. With no timeouts or fallbacks, the user gets an error and Kubernetes still self-heals the ads pod. With them, the user gets a page without ads and Kubernetes self-heals the ads pod. Self-healing happens in both cases.

Aggregator designUser sees during failureSelf-healing happens?Resilient?
No timeout, await allSpinner, then 504 after gateway timeoutYesNo
Timeout, no fallbackFast 500 errorYesPartly (fails fast)
Timeout + fallback per callRestaurants without sponsored slotsYesYes, degrades gracefully
10 · Application layer

Resilience in ASP.NET Core

The platform cannot add fallbacks for you. This is the full Program.cs for search-aggregator using Microsoft.Extensions.Http.Resilience. It wires timeouts, retries and circuit breakers per dependency, splits liveness from readiness, and returns a partial response when a non-critical dependency fails.

search-aggregator/SearchAggregator.csproj
<Project Sdk="Microsoft.NET.Sdk.Web">

    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

  </ItemGroup>

search-aggregator/Program.cs
using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using Microsoft.Extensions.Diagnostics.HealthChecks;
using Microsoft.Extensions.Http.Resilience;

var builder = WebApplication.CreateBuilder(args);

// Graceful shutdown: finish in-flight searches after SIGTERM.
// Must be lower than terminationGracePeriodSeconds minus the preStop sleep.
builder.Services.Configure<HostOptions>(o => o.ShutdownTimeout = TimeSpan.FromSeconds(20));

// One resilience profile per dependency. Critical deps get more patience.
static void Critical(HttpStandardResilienceOptions o)
{
    o.AttemptTimeout.Timeout = TimeSpan.FromMilliseconds(600);
    o.TotalRequestTimeout.Timeout = TimeSpan.FromMilliseconds(1500);
    o.Retry.MaxRetryAttempts = 2;
    o.Retry.UseJitter = true;
    o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(15);
    o.CircuitBreaker.FailureRatio = 0.5;
    o.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(10);
}

static void Optional(HttpStandardResilienceOptions o)
{
    o.AttemptTimeout.Timeout = TimeSpan.FromMilliseconds(300);
    o.TotalRequestTimeout.Timeout = TimeSpan.FromMilliseconds(400);
    o.Retry.MaxRetryAttempts = 1;
    o.Retry.UseJitter = true;
    o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(10);
    o.CircuitBreaker.FailureRatio = 0.3;
    o.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(30);
}

builder.Services.AddHttpClient("personalization", c =>
        c.BaseAddress = new("http://personalization-service.jahez-prod.svc.cluster.local"))
    .AddStandardResilienceHandler(Critical);

builder.Services.AddHttpClient("recommendation", c =>
        c.BaseAddress = new("http://recommendation-service.jahez-prod.svc.cluster.local"))
    .AddStandardResilienceHandler(Optional);

builder.Services.AddHttpClient("ads", c =>
        c.BaseAddress = new("http://ads-service.jahez-prod.svc.cluster.local"))
    .AddStandardResilienceHandler(Optional);

// Liveness checks only the process itself. Readiness can include warm-up state.
builder.Services.AddSingleton<WarmupState>();
builder.Services.AddHealthChecks()
    .AddCheck("self", () => HealthCheckResult.Healthy(), tags: ["live"])
    .AddCheck<WarmupCheck>("warmup", tags: ["ready"]);

var app = builder.Build();

app.Lifetime.ApplicationStarted.Register(() =>
    app.Services.GetRequiredService<WarmupState>().Ready = true);

app.MapHealthChecks("/health/live",  new HealthCheckOptions { Predicate = r => r.Tags.Contains("live") });
app.MapHealthChecks("/health/ready", new HealthCheckOptions { Predicate = r => r.Tags.Contains("ready") });

app.MapGet("/v1/search", async (string q, string city, IHttpClientFactory http, ILogger<Program> log, CancellationToken ct) =>
{
    var personalization = http.CreateClient("personalization");
    var recommendation  = http.CreateClient("recommendation");
    var ads             = http.CreateClient("ads");
    var qs = $"?q={Uri.EscapeDataString(q)}&city={Uri.EscapeDataString(city)}";

    // Fan out in parallel. Each optional call has its own fallback.
    var resultsTask = personalization.GetFromJsonAsync<List<Restaurant>>("/v1/rank" + qs, ct);
    var recsTask    = SafeAsync(() => recommendation.GetFromJsonAsync<List<Restaurant>>("/v1/recs" + qs, ct), "recommendation", log);
    var adsTask     = SafeAsync(() => ads.GetFromJsonAsync<List<SponsoredSlot>>("/v1/slots" + qs, ct), "ads", log);

    List<Restaurant>? results;
    try { results = await resultsTask; }
    catch (Exception ex) when (ex is HttpRequestException or TimeoutException or Polly.CircuitBreaker.BrokenCircuitException)
    {
        // Search results are the core function. Without them, fail fast and honestly.
        log.LogError(ex, "personalization unavailable");
        return Results.Problem("Search is temporarily unavailable", statusCode: 503);
    }

    var recs = await recsTask;
    var slots = await adsTask;

    return Results.Ok(new SearchResponse(
        SearchResults: results ?? [],
        Recommendations: recs ?? [],
        Ads: slots ?? [],
        Degraded: recs is null || slots is null));
});

app.Run();

// Returns null instead of throwing, so one optional dependency never sinks the page.
static async Task<T?> SafeAsync<T>(Func<Task<T?>> call, string dep, ILogger log) where T : class
{
    try { return await call(); }
    catch (Exception ex) when (ex is not OperationCanceledException { CancellationToken.IsCancellationRequested: true })
    {
        log.LogWarning(ex, "{Dependency} failed, serving degraded response", dep);
        return null;
    }
}

public record Restaurant(string Id, string Name, double Rating, int EtaMinutes);
public record SponsoredSlot(string RestaurantId, int Position, string CampaignId);
public record SearchResponse(List<Restaurant> SearchResults, List<Restaurant> Recommendations, List<SponsoredSlot> Ads, bool Degraded);

public class WarmupState { public volatile bool Ready; }

public class WarmupCheck(WarmupState state) : IHealthCheck
{
    public Task<HealthCheckResult> CheckHealthAsync(HealthCheckContext context, CancellationToken ct = default) =>
        Task.FromResult(state.Ready ? HealthCheckResult.Healthy() : HealthCheckResult.Unhealthy("warming up"));
}
Design decisions in this code

Personalization is critical, so it gets two retries and a longer budget, and its failure returns 503. Recommendation and ads are optional, so they get one retry, a 400ms ceiling and a null fallback. The Degraded flag lets the mobile app hide empty sections and lets you count degraded responses as a separate SLI. The circuit breaker sampling window must be at least twice the attempt timeout, which both profiles satisfy.

11 · Platform layer

Apply-ready manifests

Every branch of the Reliability Engineering tree as real YAML for search-aggregator. Apply with kubectl apply -f search-aggregator-reliability.yaml.

search-aggregator-reliability.yaml
# ── Deployment: health checks, availability, fault tolerance, graceful shutdown ──
apiVersion: apps/v1
kind: Deployment
metadata:
  name: search-aggregator
  namespace: jahez-prod
  labels:
    app.kubernetes.io/name: search-aggregator
    app.kubernetes.io/part-of: search
spec:
  replicas: 6                          # availability: 2 per zone
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 25%
      maxUnavailable: 0                 # never drop below desired during rollout
  selector:
    matchLabels:
      app.kubernetes.io/name: search-aggregator
  template:
    metadata:
      labels:
        app.kubernetes.io/name: search-aggregator
        app.kubernetes.io/part-of: search
    spec:
      priorityClassName: jahez-customer-critical
      terminationGracePeriodSeconds: 35  # preStop 10s + ShutdownTimeout 20s + 5s slack
      restartPolicy: Always              # reliability: kubelet restarts crashed containers

      # Fault tolerance: spread evenly across me-central-1a/b/c
      topologySpreadConstraints:
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: DoNotSchedule
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: search-aggregator
        - maxSkew: 1
          topologyKey: kubernetes.io/hostname
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app.kubernetes.io/name: search-aggregator

      # Fault tolerance: avoid two replicas on one node
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                topologyKey: kubernetes.io/hostname
                labelSelector:
                  matchLabels:
                    app.kubernetes.io/name: search-aggregator

      # Self-healing speed: evict from a dead node after 60s instead of the default 300s
      tolerations:
        - key: node.kubernetes.io/unreachable
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 60
        - key: node.kubernetes.io/not-ready
          operator: Exists
          effect: NoExecute
          tolerationSeconds: 60

      containers:
        - name: search-aggregator
          image: ghcr.io/jahez/search-aggregator:1.14.2
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
          env:
            - name: ASPNETCORE_URLS
              value: "http://+:8080"
            - name: DOTNET_gcServer
              value: "1"
          resources:
            requests:
              cpu: "500m"
              memory: "512Mi"
            limits:
              memory: "768Mi"

          # Health checks: startup guards slow JIT/warm-up, then hands off
          startupProbe:
            httpGet: { path: /health/live, port: http }
            periodSeconds: 3
            failureThreshold: 20            # up to 60s to start
          livenessProbe:                   # process only, never dependencies
            httpGet: { path: /health/live, port: http }
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3
          readinessProbe:                  # controls EndpointSlice membership
            httpGet: { path: /health/ready, port: http }
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 2
            successThreshold: 1

          # Graceful shutdown: let kube-proxy/ingress drop this endpoint before SIGTERM
          lifecycle:
            preStop:
              sleep:
                seconds: 10                 # native sleep action, K8s 1.30+
---
# ── Service: load balancing across ready endpoints only ──
apiVersion: v1
kind: Service
metadata:
  name: search-aggregator
  namespace: jahez-prod
  labels:
    app.kubernetes.io/name: search-aggregator
spec:
  type: ClusterIP
  selector:
    app.kubernetes.io/name: search-aggregator
  ports:
    - name: http
      port: 80
      targetPort: http
  trafficDistribution: PreferClose      # keep traffic in-zone when healthy (K8s 1.31+)
---
# ── PodDisruptionBudget: survive voluntary disruptions (node drains, upgrades) ──
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata:
  name: search-aggregator
  namespace: jahez-prod
spec:
  minAvailable: 4                      # one full zone (2 pods) can be drained at a time
  unhealthyPodEvictionPolicy: AlwaysAllow
  selector:
    matchLabels:
      app.kubernetes.io/name: search-aggregator
---
# ── HPA: keep headroom so a zone loss doesn't overload the survivors ──
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: search-aggregator
  namespace: jahez-prod
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: search-aggregator
  minReplicas: 6
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 60     # ~66% capacity left after losing 1 of 3 zones
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - { type: Percent, value: 100, periodSeconds: 30 }
    scaleDown:
      stabilizationWindowSeconds: 300

12 · Roadmap change

Rename "Reliability & Health" to Reliability Engineering

Organizing question: How do workloads remain healthy and operational despite failures? Each branch maps to a manifest field you just saw.

7. Reliability Engineering │ ├── Health Checks # startupProbe, livenessProbe, readinessProbe │ ├── Liveness Probe │ ├── Readiness Probe │ └── Startup Probe │ ├── Availability # replicas, Service, trafficDistribution │ ├── Replicas │ ├── Multi-Zone Deployment │ └── Load Balancing │ ├── Reliability # restartPolicy, controllers │ ├── Self-Healing │ ├── Restart Policies │ └── Controller Reconciliation │ ├── Resilience # app code + mesh (Istio retries/outlier detection) │ ├── Retries │ ├── Timeouts │ ├── Failover │ └── Circuit Breakers │ ├── Fault Tolerance # topologySpreadConstraints, podAntiAffinity │ ├── Redundancy │ ├── Active-Active │ ├── Multi-AZ │ └── Anti-Affinity │ └── Graceful Shutdown # preStop, terminationGracePeriodSeconds, HostOptions
Two small refinements

"Multi-Zone Deployment" under Availability and "Multi-AZ" under Fault Tolerance are the same mechanism. Keep it in one place, or label the first as "replica count" and the second as "zone spreading". Also, Resilience patterns mostly live in application code or a service mesh, not in core Kubernetes objects. It helps to mark that branch "app + mesh" so the roadmap stays honest about what kubectl apply can give you.

13 · The complete picture

Full workload management map

The only major category missing from the earlier roadmap was Observability: how do I know the workload is healthy and performing correctly? Without it you cannot measure any of the properties above.

1. Workload Types # Deployment, StatefulSet, DaemonSet, Job, CronJob 2. Deployment & Release # rolling, blue/green, canary, A/B 3. Resource Management # requests/limits, HPA, VPA, QoS 4. Placement # nodeSelector, affinity, taints, spread 5. Prioritization # PriorityClass, preemption 6. Disruptions # PDB, drains, eviction 7. Reliability Engineering # this guide 8. Configuration & Secrets # ConfigMap, Secret, env 9. Storage # PV, PVC, StorageClass 10. Networking # Service, Ingress, NetworkPolicy 11. Observability ├── Logging # structured logs, Degraded=true events ├── Metrics # success rate SLI, restarts, p99 latency ├── Tracing # fan-out spans: aggregator → ads ├── Alerting # error-budget burn rate └── Monitoring # dashboards per service
How observability measures each property

Availability: probe success from outside the cluster. Reliability: ratio of successful to total checkout requests. Resilience: time to recover (MTTR) and the share of responses with Degraded=true. Fault tolerance: user-facing error rate during a zone-loss game day, which should stay flat.
