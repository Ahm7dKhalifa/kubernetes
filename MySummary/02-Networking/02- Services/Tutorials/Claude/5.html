Pod → External World

What happens when a Pod inside the cluster makes a request to an external website, API, or database outside the cluster? Full packet path with request AND response arrows.

01 The Problem — Why Can't the Pod IP Go to the Internet? ▶

The problem
The solution: SNAT
Analogy
Pod IPs are internal — the internet doesn't know them
Solution: SNAT — replace Pod IP with Node IP before leaving
Definition — SNAT (Source NAT)Before the packet leaves the node, the kernel rewrites the source IP from the Pod's internal IP (10.244.1.5) to the Node's external IP (192.168.1.10). The external server sees the Node's IP as the sender and can respond to it. When the response arrives at the node, conntrack reverses the SNAT and delivers it back to the Pod.
Analogy: Sending mail from an office building
Without SNATEmployee in Room 203 (Pod 10.244.1.5) sends a letter with return address "Room 203, Internal Floor 2." The post office has no idea where that is — letter comes back undeliverable.

With SNATThe mailroom (iptables) crosses out "Room 203" and writes "123 Main Street" (Node's IP) as the return address. The reply arrives at 123 Main Street. The mailroom (conntrack) remembers "this was for Room 203" and delivers it internally.

03 Full Response Path: External → Pod ▶

Diagram
Packet at each step
# ❶ api.stripe.com sends response:
src: 142.250.80.46:443 → dst: 73.45.12.99:44320  ← to public IP

# ❷ ISP/router reverse NAT:
src: 142.250.80.46:443 → dst: 192.168.1.10:44320  ← to Node's IP

# ❸ Node NIC receives on eth0

# ❹ conntrack reverse SNAT (PREROUTING):
# Lookup: "192.168.1.10:44320 was originally 10.244.1.5:44320"
src: 142.250.80.46:443 → dst: 10.244.1.5:44320  ← Pod IP restored!

# ❺ Kernel routes to local Pod subnet → veth pair

# ❻ App Pod receives:
src: 142.250.80.46:443 → dst: 10.244.1.5:44320
# App sees the response from Stripe, addressed to its own Pod IP
# The SNAT was completely transparent — App never knew it happened

Full trace
# From inside any Pod:
curl http://google.com

# ══ REQUEST PATH ══
# 1. CoreDNS resolves google.com → 142.250.80.46
# 2. Pod sends: src=10.244.1.5:55210 dst=142.250.80.46:80
# 3. iptables MASQUERADE: src rewritten → 192.168.1.10:55210
# 4. Routing: 142.250.80.46 → default gateway → internet
# 5. Google receives from 192.168.1.10 (or public NAT IP)

# ══ RESPONSE PATH ══
# 6. Google responds: src=142.250.80.46 dst=192.168.1.10:55210
# 7. Packet arrives at Node NIC
# 8. conntrack reverses: dst → 10.244.1.5:55210
# 9. Pod receives Google's HTML response ✓

IP whitelisting

If the external API requires IP whitelisting (e.g., Stripe, payment providers), you need a stable egress IP. Use a Cloud NAT Gateway (AWS NAT GW, GCP Cloud NAT) so all cluster traffic exits through one predictable IP.

06 Example: Pod connects to External Database ▶

Diagram
ExternalName Service
Use ExternalName Service for clean DNS alias
# Instead of hardcoding db.example.com in your app:
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: db.example.com

# Now your app can use:
# psql -h external-db -U postgres
# CoreDNS resolves "external-db" → CNAME → db.example.com → real IP
# If DB moves to a new host, just update the ExternalName Service
# No app code changes needed!

07 Controlling Egress with NetworkPolicy ▶

Default: allow all
Block all egress
Allow only DNS + HTTPS
DefaultWithout any NetworkPolicy, ALL Pods can reach ANY external address on ANY port. Your Pod can call google.com, Stripe API, or any random website. No restrictions.
Block ALL outgoing traffic
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-egress
spec:
  podSelector:
    matchLabels:
      app: restricted
  policyTypes:
  - Egress
  # No egress rules = deny ALL outgoing traffic
  # Pod can't even do DNS lookups!
Allow DNS (port 53) + HTTPS (port 443) only
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns-https
spec:
  podSelector:
    matchLabels:
      app: api-client
  policyTypes:
  - Egress
  egress:
  # Allow DNS
  - ports:
    - { port: 53, protocol: UDP }
    - { port: 53, protocol: TCP }
  # Allow HTTPS to any external IP
  - ports:
    - { port: 443, protocol: TCP }
Always allow DNS!

If you block egress, you MUST explicitly allow port 53 (DNS). Without DNS, the Pod can't resolve any hostname — not even internal Service names. This is the #1 egress policy mistake.

4. RoutingKernel routes to default gateway (not a Pod subnet)Node kernel

7. InternetPacket reaches the external serverInternet
8. ResponseExternal server responds to the public/node IPExternal

10. conntrackKernel reverses SNAT: dst rewritten from Node IP back to Pod IPNode kernel

Key Takeaways

1. Pods CAN reach the internet by default — no special config needed.
2. The kernel does SNAT (MASQUERADE) to replace Pod IP with Node IP before the packet leaves.
3. conntrack automatically reverses the NAT on the response path.
4. The external server sees the Node's IP (or NAT gateway IP), NOT the Pod's IP.
5. For IP whitelisting, use a Cloud NAT Gateway for a stable egress IP.
6. Use NetworkPolicy (Egress rules) to restrict which external addresses Pods can reach.
7. If you block egress, ALWAYS allow port 53 (DNS) or nothing works.
8. Use ExternalName Service to alias external hostnames without hardcoding them in your app.
