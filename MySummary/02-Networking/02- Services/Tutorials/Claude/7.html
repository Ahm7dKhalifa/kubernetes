Part I · High Level

What a Service is, the problems it removes, and how its parts work together.

1

Foundations

Definition, the needs, the solution and how the types compare.

1.1Introduction

In one sentence

A Service gives a changing group of Pods one stable name and one stable virtual IP, and spreads each new connection over the Pods that are Ready.

A Service is a namespaced object in the core Kubernetes API (v1/Service). You write a label selector and a list of ports. Kubernetes then keeps four things true on its own: the API server gives the Service a ClusterIP from the Service CIDR; the EndpointSlice controller (inside kube-controller-manager) keeps the list of Ready Pod IPs that match the selector; kube-proxy on every node turns that list into kernel rules (iptables, IPVS or nftables) that rewrite packets sent to the ClusterIP; and CoreDNS answers menu-api-service.jahez-prod.svc.cluster.local with that IP. On Jahez EKS (me-central-1) kube-proxy, CoreDNS and the VPC CNI are EKS add-ons, and the AWS Load Balancer Controller turns type: LoadBalancer into an NLB.

✓ It is
  • a stable name and IP for whatever Pods match a selector, today and after every rollout
  • layer-4 load balancing (TCP, UDP, SCTP) — one Pod is picked per new connection
  • a DNS record per Service (and per Pod, for headless Services)
  • the way to open Pods to the outside — NodePort on every node, or a cloud load balancer
✕ It is not
  • a process or Pod — nothing runs “the Service”; it is rules on every node plus a DNS record
  • an HTTP router — no paths, hosts or TLS routing; that is Ingress or Gateway API
  • a health checker — it trusts each Pod's readiness probe
  • a firewall — who may connect is NetworkPolicy
  • how Pods reach the internet — that is SNAT on the node (group 4)

Definitions

1

Service

A Service is an object that names a group of Pods by label and gives them one stable address.
🎯 Why it exists

Pods are cattle: they restart with new IPs and there are several of them. Callers need one address that never changes.

📄 What it looks like
📄 service.yamlyaml
kind: Service
metadata:
  name: order-api-service
spec:
  selector:
    app: order-api
⚙ What Kubernetes does with it

The API server stores it and allocates an IP; controllers and every node react within a second.

Before
order-api config:
  10.244.1.6:8080  (one Pod)
→
After
order-api config:
  http://order-api-service
📍 Where it lives

Namespace jahez-prod, stored in etcd; file in apps/<app>/service.yaml.

⚠ Watch out

Its name is a DNS label: lowercase, ≤ 63 chars. The selector must match the Pod template labels, not the Deployment's own labels.

2

Selector & labels

The selector is the label query (app: menu-api) that decides which Pods are behind the Service.
🎯 Why it exists

It decouples the Service from any one Deployment: a canary Deployment with the same label joins automatically.

📄 What it looks like
📄 selectoryaml
selector:
  app: menu-api
⚙ What Kubernetes does with it

The EndpointSlice controller re-evaluates the selector every time a Pod is created, changes labels or becomes Ready.

Before
Pods with app=menu-api: 3
Endpoints: 3
→
After
kubectl label pod … app-
Endpoints: 2  (Pod left)
📍 Where it lives

spec.selector of the Service; labels on spec.template.metadata.labels of the Deployment.

⚠ Watch out

Only equality (key: value) — no matchExpressions. A typo means zero endpoints and every call fails with “connection refused”.

3

ClusterIP (virtual IP)

The ClusterIP is a virtual IP from the Service CIDR (10.96.0.0/12) that no network card owns.
🎯 Why it exists

Callers need an IP that survives every Pod change; kernel rules translate it to a real Pod IP.

📄 What it looks like
📄 liveyaml
spec:
  clusterIP: 10.96.0.15   # written by the API server
⚙ What Kubernetes does with it

The API server allocates it once at create; it never changes until the Service is deleted.

Before
spec:
  type: ClusterIP
→
After
spec:
  clusterIP: 10.96.0.15
📍 Where it lives

In spec.clusterIP; real only as iptables rules on every node.

⚠ Watch out

You cannot ping it (no rule for ICMP) — test with curl or nc. It is immutable: changing it means delete and recreate.

4

port · targetPort · nodePort

Three port numbers on one path: port the Service listens on, targetPort the container listens on, nodePort on every node.
🎯 Why it exists

Callers keep a simple port (80) while each app picks its own (8080), and outside traffic needs a port on the node.

📄 What it looks like
📄 portsyaml
ports:
  - name: http
    port: 80
    targetPort: http   # → 8080
    nodePort: 30080
⚙ What Kubernetes does with it

kube-proxy writes a DNAT rule from ClusterIP:port (and NodeIP:nodePort) to PodIP:targetPort.

Before
curl menu-api-service:80
→
After
packet dst → 10.244.2.8:8080
📍 Where it lives

spec.ports[] of the Service; containerPort names in the Pod.

⚠ Watch out

targetPort defaults to port. A wrong targetPort gives endpoints that look fine but every call is refused.

5

EndpointSlice

An EndpointSlice is the list of Ready Pod IPs and ports behind one Service (up to 100 per slice).
🎯 Why it exists

Something must turn “Pods with this label” into concrete addresses that nodes can program.

📄 What it looks like
📄 endpointsliceyaml
endpoints:
  - addresses: ["10.244.2.8"]
    conditions: {ready: true}
⚙ What Kubernetes does with it

The controller adds a Pod when its readiness probe passes and removes it when it fails or terminates.

Before
new Pod: 0/1 Running
→
After
1/1 Ready → added to slice
📍 Where it lives

Namespace jahez-prod, label kubernetes.io/service-name.

⚠ Watch out

Written by Kubernetes for selector Services — editing it by hand is undone. See the Endpoints/EndpointSlices guide.

6

kube-proxy

kube-proxy is a DaemonSet Pod on every node that turns Services and EndpointSlices into kernel NAT rules.
🎯 Why it exists

Each node's kernel must know where 10.96.0.15 really goes, without a proxy process in the packet path.

📄 What it looks like
📄 ruleyaml
-A KUBE-SEP-BBB2 -j DNAT --to-destination 10.244.2.8:8080
⚙ What Kubernetes does with it

It watches the API and rewrites the node's iptables (or IPVS / nftables) when anything changes.

Before
node 1 NAT table:
  (no menu-api rules)
→
After
KUBE-SVC-MENUAPI… → 3 × KUBE-SEP
📍 Where it lives

kube-system/kube-proxy DaemonSet (EKS add-on).

⚠ Watch out

It is not in the packet path; if it dies, existing rules keep working but new Pods are not added.

7

CoreDNS & Service names

CoreDNS is the cluster DNS server that answers <service>.<namespace>.svc.cluster.local.
🎯 Why it exists

Apps should call a name, not an IP, and the same name should work in every environment.

📄 What it looks like
🖨 namesout
menu-api-service                       # same namespace
menu-api-service.jahez-prod            # other namespace
menu-api-service.jahez-prod.svc.cluster.local
⚙ What Kubernetes does with it

It watches Services and serves an A record with the ClusterIP (or every Pod IP for headless).

Before
nslookup menu-api-service
→
After
Address: 10.96.0.15
📍 Where it lives

kube-system/coredns, Service IP 10.96.0.10 in every Pod's /etc/resolv.conf.

⚠ Watch out

Short names only work in the same namespace. ndots:5 means external names try 5 cluster suffixes first — end them with a dot in hot paths.

8

DNAT · SNAT · conntrack

DNAT rewrites a packet's destination, SNAT rewrites its source, and conntrack remembers both so the reply is rewritten back.
🎯 Why it exists

This is how a virtual IP works without a proxy: the kernel edits headers in place.

📄 What it looks like
🖨 traceout
dst 10.96.0.15:80  → DNAT → 10.244.2.8:8080
reply src 10.244.2.8 → un-DNAT → 10.96.0.15
⚙ What Kubernetes does with it

kube-proxy only writes the rules; the kernel applies them to each packet and stores the flow in conntrack.

Before
src 10.244.1.5
dst 10.96.0.15:80
→
After
src 10.244.1.5
dst 10.244.2.8:8080
📍 Where it lives

The Linux kernel of every node (netfilter).

⚠ Watch out

conntrack entries outlive rule changes: an existing connection stays on its old Pod until it closes.

9

NodePort

A NodePort Service also opens one port (30000–32767) on every node's IP and forwards it to the Pods.
🎯 Why it exists

Something outside the cluster needs a reachable address; node IPs are routable, Pod IPs are not.

📄 What it looks like
📄 portsyaml
type: NodePort
ports:
  - port: 80
    nodePort: 30080
⚙ What Kubernetes does with it

kube-proxy adds a rule on every node for :30080; with the default policy it also SNATs to the node.

Before
curl 192.168.1.10:30080
(no rule)
→
After
→ DNAT → any menu-api Pod
📍 Where it lives

spec.ports[].nodePort; open on all nodes.

⚠ Watch out

Default externalTrafficPolicy: Cluster hides the client IP. Node security groups must allow the range.

10

LoadBalancer

A LoadBalancer Service asks the cloud for a real load balancer (on Jahez EKS an AWS NLB) in front of the Pods.
🎯 Why it exists

The internet needs one public, highly available address with health checks.

📄 What it looks like
📄 lbyaml
type: LoadBalancer
loadBalancerClass: service.k8s.aws/nlb
⚙ What Kubernetes does with it

The AWS LB Controller creates the NLB and target group, then writes its DNS name into status.loadBalancer.

Before
EXTERNAL-IP  <pending>
→
After
EXTERNAL-IP  k8s-jahezpro-….elb.me-central-1.amazonaws.com
📍 Where it lives

In AWS (the NLB) plus the Service in jahez-prod.

⚠ Watch out

Each one is a billed NLB. Without a controller (bare metal, kind) it stays <pending> forever.

11

Headless Service

A headless Service has clusterIP: None: no virtual IP, DNS returns every Pod IP.
🎯 Why it exists

Databases and StatefulSets need to reach one particular Pod (the primary), not a random one.

📄 What it looks like
📄 headlessyaml
clusterIP: None
selector:
  app: orders-db
⚙ What Kubernetes does with it

No kube-proxy rules; CoreDNS serves one A record per Ready Pod plus a name per StatefulSet Pod.

Before
nslookup orders-db-service
→
After
10.244.1.6
10.244.2.3
10.244.3.7
📍 Where it lives

apps/orders-db/headless-service.yaml; named in the StatefulSet's serviceName.

⚠ Watch out

The client picks the Pod — the Npgsql driver, not Kubernetes, chooses the primary.

12

ExternalName

An ExternalName Service is a DNS alias (CNAME) from a cluster name to an outside name.
🎯 Why it exists

Apps keep calling pay-gw-service while the real host changes per environment.

📄 What it looks like
📄 extnameyaml
type: ExternalName
externalName: api.pay-gw.example
⚙ What Kubernetes does with it

CoreDNS answers with a CNAME; no IP, no ports, no kube-proxy rules.

Before
nslookup pay-gw-service
→
After
CNAME api.pay-gw.example
📍 Where it lives

apps/external/pay-gw-service.yaml.

⚠ Watch out

TLS and HTTP Host still say pay-gw-service unless the client overrides them — certificates often fail.

1.2Problems or needs

In one sentence

Without Services, every caller must track changing Pod IPs by hand, spread its own load, avoid Pods that are not ready, and find a way in from outside — and it breaks on every rollout.

Step 1 of 5 · Pod IPs change on every restart
Wherejahez-prodWhoyou · order-apiBlocksPod IP
  • order-api must call menu-api. The only address a Pod has is its IP, e.g. 10.244.1.6.
  • You paste it into order-api's config. It works — until the next rollout, eviction or node drain.
  • The new Pod gets a new IP from the node's range; the old one is gone.
⌘ manual commandsbash
kubectl get pods -n jahez-prod -l app=menu-api -o wide        # note the IPs
kubectl rollout restart deployment/menu-api-deployment -n jahez-prod
kubectl get pods -n jahez-prod -l app=menu-api -o wide        # every IP is new
kubectl exec -n jahez-prod deploy/order-api-deployment -- curl -s -m 2 http://10.244.1.6:8080/healthz

command terminated with exit code 7

How Services remove each of these problems → 1.3 Solution

1.3Solution

In one sentence

You declare one Service per app; Kubernetes keeps a stable IP and name for it, tracks the Ready Pods behind it, and programs every node to forward to them.

  1. Label the Pods. The Deployment's Pod template carries app: menu-api.
  2. Write a Service with selector: {app: menu-api} and port: 80 → targetPort: http.
  3. Apply it. The API server stores it and allocates ClusterIP 10.96.0.15.
  4. The EndpointSlice controller finds the 3 Ready Pods and writes their IPs into a slice.
  5. kube-proxy on every node writes NAT rules: 10.96.0.15:80 → one of the 3 Pods :8080.
  6. CoreDNS answers menu-api-service.jahez-prod.svc.cluster.local → 10.96.0.15.
  7. order-api calls http://menu-api-service — forever, through every rollout and scale.

2.1Architecture — where each part runs

A Service lives in four places: the control plane stores it, a controller lists its Pods, every node turns it into NAT rules, and CoreDNS gives it a name.

Cross node — request, response, how a Pod is picked
It is random, not local-first

iptables uses probability chains: with 3 Pods 1/3, then 1/2, then the rest. kube-proxy does not prefer local Pods by default. After DNAT, the kernel routing table decides local (veth) or remote (tunnel / VPC).

To keep traffic on the node: internalTrafficPolicy: Local keeps only the Pods on the caller's node. The real risk is not uneven load: if that node has no Ready Pod, the traffic is dropped. Prefer trafficDistribution: PreferClose (same zone first, falls back) — see 4.2.

3.0How a Service works

In one sentence

apiVersion: v1

    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ip
    service.beta.kubernetes.io/aws-load-balancer-scheme: internet-facing
    service.beta.kubernetes.io/aws-load-balancer-ssl-cert: arn:aws:acm:me-central-1:111122223333:certificate/3f1c-example
    service.beta.kubernetes.io/aws-load-balancer-ssl-ports: https
    service.beta.kubernetes.io/aws-load-balancer-healthcheck-path: /healthz/ready

    app: menu-api

4.1Egress — Pod → outside

In one sentence

Pods reach the internet through SNAT: the node rewrites the private Pod IP to its own, and conntrack rewrites the reply back.

On Jahez EKS

The VPC CNI SNATs Pod traffic to the node's primary IP only for destinations outside the VPC (AWS_VPC_K8S_CNI_EXTERNALSNAT=false); private subnets then leave through the NAT gateway in each AZ. Partners that allow-list Jahez see the NAT gateway Elastic IPs.

Example IP 203.0.113.25 is a documentation address.

🖨 egress responsetrace
# ❼ The gateway responds:
src: 203.0.113.25:443 → dst: 73.45.12.99:44320 (public IP)

# Router/ISP reverse NAT:
src: 203.0.113.25:443 → dst: 192.168.1.10:44320 (Node IP)

# Node NIC receives → conntrack reverse SNAT:
src: 203.0.113.25:443 → dst: 10.244.1.5:44320 (Pod IP restored!)

# Kernel routes to local Pod subnet → veth → order-api Pod receives ✓
# App sees: response from 203.0.113.25 addressed to its Pod IP
# SNAT was completely transparent — App never knew it happened
