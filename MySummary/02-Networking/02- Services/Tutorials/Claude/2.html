02 What Is a Service? ▶

Definition + Diagram
How it finds Pods
Full lifecycle
Service = Stable front door for a group of Pods
Definition — ServiceA Kubernetes object that provides a stable IP address (ClusterIP), DNS name, and load balancing for a set of Pods. The Service uses a label selector to find its target Pods. When Pods are added or removed, the Service's endpoint list auto-updates. Clients talk to the Service — they never need to know individual Pod IPs.
The Service web-svc (blue) selects all Pods with label app=web (green). It ignores the app=api Pod (teal). Each node runs kube-proxy (orange) which programs iptables/IPVS rules to route Service traffic to the correct Pods.
Label selector matching — how Service finds Pods
Service full lifecycle — from create to handle traffic

Pod IPUnique IP assigned to each Pod by the CNI plugin. Changes on restart. Internal to cluster.10.244.1.5

Can two Pods on different nodes have the same IP?NO. Every Pod in the cluster gets a globally unique IP from the Pod CIDR range. The CNI plugin ensures uniqueness across all nodes. Example: Node 1 uses 10.244.1.0/24 (Pods get 10.244.1.x), Node 2 uses 10.244.2.0/24 (Pods get 10.244.2.x). Different subnets per node → no collisions possible.

04 ClusterIP Service (Default) ▶

DefinitionCreates a virtual IP (ClusterIP) reachable ONLY from inside the cluster. Provides DNS name + load balancing. The default and most common Service type.
Full Cluster Diagram
YAML
Create
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP              # Default — can omit
  selector:
    app: web                  # Finds Pods with this label
  ports:
  - port: 80                  # Service listens on
    targetPort: 80            # Forwards to Pod's port
kubectl expose deployment web --port=80 --target-port=80 --name=web-svc

05 Case: Traffic Routed — Same Node ▶

Diagram
How kube-proxy decides
How kube-proxy picks which Pod to route to
Random selection (iptables mode)kube-proxy programs iptables rules with probability-based chains. Each Pod has an equal chance. With 3 Pods, each gets ~33% of traffic. kube-proxy does NOT prefer local Pods by default — it's random across all endpoints.

To prefer local Pods: set service.spec.internalTrafficPolicy: Local — only routes to Pods on the same node as the source. Reduces latency but risks uneven load.

06 Case: Traffic Routed — Cross Node ▶

Diagram
Traffic from App-1 on Node 1 is intercepted by kube-proxy's iptables. The iptables DNAT rewrites the destination from 10.96.0.15 (Service IP) to 10.244.3.7 (Pod IP on Node 3). The CNI overlay network (Calico/Cilium/Flannel) handles cross-node delivery. The response packet follows the reverse path.

07 Service Full Lifecycle ▶

Create
Pod added
Pod deleted
Pod fails readiness
Service created — endpoints discovered
New Pod with matching label created

Endpoint controller detects new Pod → adds its IP to Endpoints → kube-proxy updates iptables → new Pod starts receiving traffic. Automatic.

Pod deleted or crashes

Pod removed → Endpoint controller removes its IP from Endpoints → kube-proxy removes it from iptables → traffic no longer sent to dead Pod. Automatic, ~1-2s delay.

Pod fails readiness probe

Pod still exists but fails readiness → Endpoint controller removes it from Endpoints → no traffic. Pod passes readiness again → IP re-added. This is why readiness probes are critical — they prevent sending traffic to unhealthy Pods.

08 NodePort Service ▶

DefinitionOpens a port (30000-32767) on EVERY node's IP. External users connect via NodeIP:NodePort. Creates a ClusterIP automatically. Traffic: External → Node:30080 → kube-proxy → Pod.
Full Diagram
Multiple Services
YAML
Multiple Services on the same nodes — different NodePorts
spec:
  type: NodePort
  selector: { app: web }
  ports:
  - port: 80           # ClusterIP port
    targetPort: 80     # Pod port
    nodePort: 30080    # External port on all nodes

09 LoadBalancer Service ▶

DefinitionCloud provider provisions a public Load Balancer with an external IP. Traffic: Internet → LB (35.192.0.1) → NodePort → kube-proxy → Pod. Superset of NodePort + ClusterIP.
Diagram
YAML
spec:
  type: LoadBalancer
  selector: { app: web }
  ports:
  - port: 80
    targetPort: 80
Superset chain

LoadBalancer creates: ① ClusterIP ② NodePort ③ Cloud LB. You get all 3 layers. On bare-metal: LB stays Pending forever (use MetalLB).

10 Headless Service — PostgreSQL Example ▶

DefinitionclusterIP: None. No VIP. DNS returns ALL Pod IPs. Client decides which Pod to connect to. Required for StatefulSets. Used when you need to target specific Pods (primary for writes, replica for reads).

11 Multi-Container Pod + Service ▶

Diagram
Port mapping
The Service sends traffic to PodIP:targetPort. Whichever container inside the Pod is listening on that port receives the traffic. In a multi-container Pod, the Service doesn't know or care which container it is — it just sends to the port. If you need to reach the sidecar's metrics, create a second Service with targetPort: 9090.

12 Can Two Pods Have the Same IP?

Answer: NO. Every Pod in the entire cluster gets a globally unique IP address. The CNI plugin assigns IP ranges per node from the Pod CIDR. No two nodes share the same subnet.
Each node gets a different /24 subnet from the Pod CIDR. Node 1 = 10.244.1.x, Node 2 = 10.244.2.x, Node 3 = 10.244.3.x. Different subnets → impossible for two Pods to get the same IP, even across different nodes.

SRE Checklist When Service Doesn't Work

① kubectl get endpoints svc-name — empty? → selector doesn't match Pod labels.
② kubectl get pods --show-labels — do labels match?
③ kubectl describe pod — is Pod passing readiness?
④ Is targetPort correct (matches containerPort)?
⑤ Is there a NetworkPolicy blocking traffic?
