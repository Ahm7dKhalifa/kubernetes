The complete guide — networking model, all Service types, Ingress, NetworkPolicy, DNS discovery, and SRE operations. Interactive step-by-step workflows.

01 Kubernetes Networking Model ▶

3 Rules
IP-per-Pod
CNI Plugins
The 3 Fundamental Rules
Rule 1 — Every Pod gets its own IPEach Pod has a unique IP address in the cluster. Containers WITHIN a Pod share the same IP and communicate via localhost.
Rule 2 — Pods can talk to any Pod directlyAny Pod can reach any other Pod by its IP — no NAT required. Even across nodes. The network is flat.
Rule 3 — Pods can talk to any Service by nameServices provide stable DNS names and virtual IPs. Pods use DNS to discover Services. The cluster DNS (CoreDNS) resolves Service names to ClusterIPs.
IP-per-Pod Model
Node 1 (192.168.1.10)
├── Pod A (10.244.1.5) ← unique Pod IP
├── Pod B (10.244.1.6)

Node 2 (192.168.1.11)
├── Pod C (10.244.2.3)
├── Pod D (10.244.2.4)

Pod A → Pod D: curl 10.244.2.4:80 ← works directly, no NAT!
Same-Pod containers: Container 1 → Container 2: curl localhost:8080
CNI — Who Implements This?
Definition — CNI (Container Network Interface)A plugin that implements the Pod-to-Pod networking. Kubernetes defines the rules (flat network, no NAT). The CNI plugin makes it happen. Without a CNI, Pods can't communicate across nodes.
CNI PluginHowNetworkPolicy?
CalicoBGP routing or VXLAN overlayYes
CiliumeBPF (high performance)Yes (advanced)
FlannelVXLAN overlay (simple)No
WeaveEncrypted mesh overlayYes
Key

Flannel does NOT support NetworkPolicy. If you need NetworkPolicy (you do in production), use Calico or Cilium.

02 Pod Communication ▶

Same Pod
Pod to Pod
Pod to Service
External to Pod
Container-to-Container (same Pod)
Pod (10.244.1.5)
├── Container A (port 80)
└── Container B (port 8080)

Container A → B: curl localhost:8080 ← share network namespace
Container B → A: curl localhost:80
Containers in the same Pod share the same network namespace (same IP, same loopback). They communicate via localhost. Port conflicts ARE possible — two containers can't use the same port.
Pod-to-Pod (any node)
Pod A (10.244.1.5, Node 1) → Pod B (10.244.2.3, Node 2)

curl 10.244.2.3:80 ← works directly, flat network

Problem: Pod IPs change on restart! Don't hardcode them.
Solution: Use Services (stable VIP + DNS name).
Pod-to-Service (the normal way)
App Pod → web-svc (10.96.0.15:80) → load balance → web-0 / web-1 / web-2

curl web-svc:80 ← DNS name (stable)
curl 10.96.0.15:80 ← ClusterIP (stable)

Service IP never changes. DNS auto-resolves. Load balanced across all matching Pods.
External-to-Pod (from internet/users)
Internet → Ingress / LB (public IP) → Service → Pod

3 ways to expose:
① NodePort — Service on every node's IP:port (30000-32767)
② LoadBalancer — Cloud LB with public IP
③ Ingress — HTTP/HTTPS routing (host/path based)

03 Port Types — The 4 Ports ▶

The most confusing topic in K8s networkingThere are 4 different "port" fields. Each refers to a different layer. Getting them wrong means traffic doesn't flow.
All 4 Ports
Traffic Flow
YAML Example
FieldWhereMeaningExample
containerPortPod specPort the container listens on (informational)80 (nginx)
targetPortService specPort on the Pod the Service forwards TO80 (must match containerPort)
portService specPort the Service listens on (the ClusterIP port)80 or any
nodePortService specPort on every node's IP (NodePort Service only)30000-32767
Traffic Flow — Which Port at Each Step
ClusterIP:
App → web-svc:port (80) → Pod:targetPort (80)

NodePort:
External → Node-IP:nodePort (30080) → web-svc:port (80) → Pod:targetPort (80)

LoadBalancer:
Internet → LB-IP:port (80) → Node:nodePort → Pod:targetPort (80)
# Pod
containers:
- ports:
  - containerPort: 80     # Container listens here

# Service
spec:
  type: NodePort
  ports:
  - port: 80              # Service ClusterIP port
    targetPort: 80        # Forward to Pod's containerPort
    nodePort: 30080       # Port on every node (external access)
Shortcut

If targetPort is omitted, it defaults to the same value as port. If nodePort is omitted (NodePort type), K8s auto-assigns one from 30000-32767.

04 What Is a Service?

Definition — ServiceA stable abstraction that provides a fixed IP address (ClusterIP) and DNS name for a set of Pods. The Service load-balances traffic across all matching Pods. It solves the problem: "Pod IPs change on restart — how do I reliably connect to my app?"
Definition — How It Finds PodsA Service uses a selector to find Pods with matching labels. The selector is continuously evaluated — when Pods are added or removed, the Service's endpoint list updates automatically. No manual registration.
Analogy

A Service is a phone number for a team. You call the team number (Service IP), and it routes to whoever is available (healthy Pod). Team members (Pods) can come and go, but the team number never changes.

05 ClusterIP Service (Default) ▶

DefinitionThe default Service type. Creates a virtual IP (ClusterIP) that is only reachable from INSIDE the cluster. Provides stable internal DNS name. Pods use this to talk to other Pods. Not accessible from outside.
How it works
YAML
Create
App Pod → web-svc (ClusterIP: 10.96.0.15:80) → round-robin →
├── web-pod-1 (10.244.1.5:80)
├── web-pod-2 (10.244.2.3:80)
└── web-pod-3 (10.244.3.7:80)

Internal only. Not reachable from outside the cluster.
DNS: web-svc.default.svc.cluster.local → 10.96.0.15
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: ClusterIP              # Default — can omit
  selector:
    app: web                  # Matches Pods with label app=web
  ports:
  - port: 80                  # Service listens on 80
    targetPort: 80            # Forwards to Pod's port 80
    protocol: TCP
# Imperative
kubectl expose deployment web --port=80 --target-port=80 --name=web-svc

# Or with create
kubectl create service clusterip web-svc --tcp=80:80

06 NodePort Service ▶

DefinitionExposes the Service on each node's IP at a static port (30000-32767). Accessible from OUTSIDE the cluster via NodeIP:NodePort. Creates a ClusterIP automatically (NodePort is a superset of ClusterIP).
How it works
YAML
Create
Access
User (browser)
↓ http://192.168.1.10:30080 (any node's IP)
Node 1 (192.168.1.10) or Node 2 (192.168.1.11) or Node 3 (192.168.1.12)
↓ kube-proxy routes to Service
web-svc (ClusterIP: 10.96.0.15:80)
↓ round-robin
Pod 1 / Pod 2 / Pod 3

Works on ANY node's IP — even if the Pod isn't on that node. kube-proxy handles routing.
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: NodePort
  selector:
    app: web
  ports:
  - port: 80                  # ClusterIP port
    targetPort: 80            # Pod port
    nodePort: 30080           # External port (30000-32767)
kubectl expose deployment web --type=NodePort --port=80 --target-port=80 --name=web-svc
# Access from outside (any node IP works)
curl http://<any-node-ip>:30080

# Find nodePort
kubectl get svc web-svc
# PORT(S): 80:30080/TCP   ← port:nodePort

07 LoadBalancer Service ▶

DefinitionProvisions an external load balancer (cloud provider: AWS ELB, GCP LB, Azure LB) with a public IP. Traffic flows: Internet → LB → NodePort → Pod. Superset of NodePort (which is a superset of ClusterIP). Only works in cloud environments.
How it works
YAML
Flow
Internet users
↓ http://35.192.0.1:80 (public LB IP)
Cloud Load Balancer (35.192.0.1)
↓
Node 1:30080 or Node 2:30080 (NodePort)
↓
Pod (targetPort 80)
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  type: LoadBalancer
  selector:
    app: web
  ports:
  - port: 80
    targetPort: 80
What K8s creates:
① ClusterIP (internal VIP) ← always
② NodePort (on every node) ← always
③ Cloud LB (public IP) ← only in cloud

In bare-metal/minikube: stays Pending forever (no cloud LB). Use MetalLB or minikube tunnel.

08 ExternalName Service

DefinitionMaps a Service name to an external DNS name (CNAME record). No proxy, no ClusterIP. Just DNS aliasing. Pods use the Service name and get redirected to the external hostname.
apiVersion: v1
kind: Service
metadata:
  name: external-db
spec:
  type: ExternalName
  externalName: db.example.com     # External DNS name
App Pod → curl external-db:3306 → DNS resolves to db.example.com → connects to external DB

No selector. No ClusterIP. No endpoints. Just a DNS CNAME alias. Useful for external databases, APIs, or services outside K8s.

09 Headless Service (clusterIP: None) ▶

DefinitionA Service with clusterIP: None. No virtual IP. DNS returns all Pod IPs instead of one VIP. Each Pod gets its own DNS A record. Required for StatefulSets. Used when you need to connect to a SPECIFIC Pod.
Normal vs Headless
YAML
Normal ClusterIP:
nslookup web-svc → 10.96.0.15 (1 VIP, load balanced)

Headless:
nslookup web-svc → 10.244.1.5, 10.244.2.3, 10.244.3.7 (all Pod IPs!)
nslookup web-0.web-svc → 10.244.1.5 (specific Pod — StatefulSet)
spec:
  clusterIP: None    # ← This makes it headless
  selector:
    app: web

11 Service Discovery — DNS ▶

DefinitionCoreDNS automatically creates DNS records for every Service. Pods use DNS names (not IPs) to discover Services. This is the primary discovery mechanism in Kubernetes.
DNS Format
Examples
Env Vars
DNS naming convention
Service: {service}.{namespace}.svc.cluster.local
web-svc.default.svc.cluster.local → ClusterIP

Short forms (same namespace):
web-svc ← works within same namespace
web-svc.default ← explicit namespace

Pod (headless/StatefulSet):
{pod}.{service}.{namespace}.svc.cluster.local
mysql-0.mysql-svc.default.svc.cluster.local
# From inside any Pod:

# Same namespace — short name works
curl http://web-svc:80
curl http://db-svc:5432

# Cross-namespace — must include namespace
curl http://web-svc.production:80
curl http://db-svc.database.svc.cluster.local:5432

# DNS lookup
nslookup web-svc.default.svc.cluster.local
Environment Variables (legacy method)
# Kubernetes auto-injects env vars for every Service in the same namespace:
WEB_SVC_SERVICE_HOST=10.96.0.15
WEB_SVC_SERVICE_PORT=80

# But DNS is preferred because:
# - Env vars are only set at Pod creation (not updated if Service changes)
# - Service must exist BEFORE the Pod is created
# - DNS works cross-namespace

12 Endpoints ▶

DefinitionAn Endpoints object lists all Pod IPs that match a Service's selector. Created and updated automatically. When a Pod becomes Ready, its IP is added. When it's deleted or fails readiness, it's removed. The Service reads Endpoints to know where to send traffic.
How it works
Inspect
No endpoints?
Service: web-svc (selector: app=web)
↓ automatically finds Pods with app=web
Endpoints: 10.244.1.5:80, 10.244.2.3:80, 10.244.3.7:80

Pod fails readiness → 10.244.2.3 removed from endpoints
New Pod created → 10.244.2.9 added to endpoints
kubectl get endpoints web-svc
# NAME      ENDPOINTS
# web-svc   10.244.1.5:80,10.244.2.3:80,10.244.3.7:80

kubectl describe endpoints web-svc
Service with NO endpoints — common bug
Symptom: kubectl get endpoints web-svc shows <none>

Causes:
① Selector mismatch — Service selector doesn't match any Pod labels
② No Pods exist with matching labels
③ All matching Pods fail readiness probes

If endpoints are empty, the Service has nowhere to send traffic → connection refused.
# Debug: compare Service selector vs Pod labels
kubectl get svc web-svc -o jsonpath='{.spec.selector}'
# {app: web}

kubectl get pods --show-labels | grep app=web
# If no Pods match → that's the problem!

13 Ingress ▶

Definition — IngressAn API object that manages external HTTP/HTTPS access to Services. Provides host-based routing (example.com → service A), path-based routing (/api → service B), and TLS termination. Much more powerful than NodePort — one entry point routes to many services. Requires an Ingress Controller (nginx, traefik, etc.).
Architecture
Why Ingress?
YAML
Internet (users)
↓ https://app.example.com/api
Ingress Controller (nginx Pod) ← reads Ingress rules
↓ route by host/path
├── app.example.com/ → frontend-svc:80 → Frontend Pods
├── app.example.com/api → api-svc:80 → API Pods
└── admin.example.com → admin-svc:80 → Admin Pods
Why not just use NodePort/LoadBalancer?
Without IngressWith Ingress
3 services = 3 LoadBalancers = 3 public IPs ($$$)1 Ingress = 1 LB = 1 IP → routes to all 3 services
No path-based routing/api → svc A, /web → svc B
No host-based routingapp.com → svc A, admin.com → svc B
No TLS terminationHTTPS with cert managed by Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  ingressClassName: nginx
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-svc
            port:
              number: 80
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-svc
            port:
              number: 80

14 Ingress Rules ▶

Path-based
Host-based
TLS
Default backend
Path-based routing — one host, multiple paths
rules:
- host: app.example.com
  http:
    paths:
    - path: /
      pathType: Prefix
      backend:
        service: { name: frontend-svc, port: { number: 80 } }
    - path: /api
      pathType: Prefix
      backend:
        service: { name: api-svc, port: { number: 80 } }
pathType: Prefix = /api matches /api, /api/v1, /api/users. pathType: Exact = only exact match.
Host-based routing — multiple domains
rules:
- host: app.example.com
  http:
    paths:
    - path: /
      pathType: Prefix
      backend:
        service: { name: app-svc, port: { number: 80 } }
- host: admin.example.com
  http:
    paths:
    - path: /
      pathType: Prefix
      backend:
        service: { name: admin-svc, port: { number: 80 } }
TLS — HTTPS termination
spec:
  tls:
  - hosts:
    - app.example.com
    secretName: app-tls-secret    # Secret with tls.crt and tls.key
  rules:
  - host: app.example.com
    ...
# Create TLS secret
kubectl create secret tls app-tls-secret --cert=tls.crt --key=tls.key
Default backend — catch-all
spec:
  defaultBackend:
    service:
      name: default-svc
      port:
        number: 80
  rules:
  - ...
Handles requests that don't match any rule. Usually serves a 404 page or redirects.

15 NetworkPolicy ▶

Definition — NetworkPolicyA firewall rule for Pods. By default, all Pods can talk to all other Pods (flat network, no restrictions). NetworkPolicy lets you restrict: which Pods can receive traffic (ingress) and which Pods can send traffic (egress). Requires a CNI that supports it (Calico, Cilium — NOT Flannel).
Default behavior
How it works
Key concepts
Default — NO NetworkPolicy = allow ALL
Pod A → Pod B ← allowed
Pod A → Pod C ← allowed
Any Pod → Any Pod ← everything allowed!

No NetworkPolicy = completely open network. Any Pod can reach any other Pod on any port.
With NetworkPolicy — deny by default, allow explicitly
Step 1: Create a "deny all" policy on target Pods
→ ALL traffic to target Pods is BLOCKED

Step 2: Create allow rules for specific sources
→ Only allowed Pods can reach target Pods

Think of it as: "deny everything, then poke holes for what you need."
Key concepts
ConceptMeaning
podSelectorWhich Pods this policy applies TO (target)
policyTypes: [Ingress]Controls incoming traffic to target Pods
policyTypes: [Egress]Controls outgoing traffic from target Pods
ingress.fromWho is allowed to send traffic IN
egress.toWhere target Pods are allowed to send traffic OUT
namespaceSelectorAllow traffic from Pods in specific namespaces

16 NetworkPolicy Examples ▶

Deny all ingress
Allow specific
Allow namespace
Egress DNS only
Deny all ingress to Pods with app=db
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-all-db
spec:
  podSelector:
    matchLabels:
      app: db           # Applies to Pods with app=db
  policyTypes:
  - Ingress               # Controls incoming traffic
  # No ingress rules = deny ALL incoming traffic
Any Pod → db Pod ✗ BLOCKED
All incoming traffic to db Pods is denied. No exceptions (yet).
Allow ONLY app=api Pods to reach app=db on port 5432
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api-to-db
spec:
  podSelector:
    matchLabels:
      app: db
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api       # Only from Pods with app=api
    ports:
    - port: 5432
      protocol: TCP
api Pod (app=api) → port 5432 → db Pod ✓ ALLOWED
web Pod (app=web) → db Pod ✗ BLOCKED
Allow from specific namespace
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          env: production    # Only from Pods in namespaces labeled env=production
      podSelector:
        matchLabels:
          app: api          # AND only from Pods with app=api
AND vs OR

When namespaceSelector and podSelector are in the SAME from entry → AND (both must match). In SEPARATE from entries → OR (either can match).

Egress — Allow only DNS (port 53)
spec:
  podSelector:
    matchLabels:
      app: restricted
  policyTypes:
  - Egress
  egress:
  - ports:
    - port: 53
      protocol: UDP
    - port: 53
      protocol: TCP
Pods with app=restricted can ONLY make DNS queries (port 53). All other outgoing traffic is blocked. Useful for Pods that should only talk to Services (via DNS) and nothing else.

17 Monitoring & Best Practices

Always use DNS names, not Pod IPs

Pod IPs change on restart. Service DNS names and ClusterIPs are stable.

Check endpoints when Service doesn't work

kubectl get endpoints svc-name — if empty, selector doesn't match any Pods.

Use Ingress for HTTP, NodePort only for dev

NodePort wastes ports (30000-32767) and requires knowing node IPs. Ingress provides clean URLs and TLS.

Start with deny-all NetworkPolicy

Apply a deny-all policy first, then add allow rules. This is zero-trust networking. Without NetworkPolicy, all Pods can talk to all Pods.

Flannel doesn't support NetworkPolicy

If you need NetworkPolicy (you do), use Calico or Cilium as your CNI plugin.

SRE Wisdom

Networking issues are the #1 cause of "it works in dev but not in prod." Check: ① Are endpoints populated? ② Is the selector correct? ③ Is there a NetworkPolicy blocking traffic? ④ Is the Pod passing readiness probes? ⑤ Is the targetPort correct?
