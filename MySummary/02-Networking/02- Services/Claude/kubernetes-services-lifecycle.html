Service Lifecycle & Request Workflows

How every K8s component participates — from Service creation to handling traffic. Step-by-step diagrams showing the exact path of every packet through the system.

01 Creation Step ① — kubectl → API Server ▶

What happens
Diagram
What API Server does
You run the command
kubectl expose deployment web --port=80 --target-port=80 --name=web-svc
kubectl sends a POST /api/v1/namespaces/default/services request to the API Server with the Service spec: name=web-svc, type=ClusterIP, selector={app:web}, port=80, targetPort=80.
1 ⌨️ kubectlsends Service spec →→→ 🗄️ API Servervalidates + stores in etcd
POST /api/v1/namespaces/default/services

2 🗄️ API Server →→→ 🔵 Service: web-svcClusterIP: 10.96.0.15 ← assigned
API Server picks unused IP from --service-cluster-ip-range (10.96.0.0/12)
What the API Server does internally
A Validates: selector exists, ports valid, name unique
B Allocates ClusterIP from range 10.96.0.0/12 (stored in etcd bitmap)
C Stores Service object in etcd
D Notifies all watchers: Endpoint Controller + kube-proxy + CoreDNS
KeyThe ClusterIP is just a number stored in etcd. No network interface has this IP. It becomes "real" only when kube-proxy programs iptables rules to intercept packets destined for it.

02 Creation Step ② — Endpoint Controller Builds Endpoints ▶

What happens
Diagram
Readiness gate
The Endpoint Controller (runs inside kube-controller-manager on the control plane) watches for new Services. When it sees web-svc with selector app=web, it scans ALL Pods in the namespace. For each Pod that has label app=web AND is Ready (passing readiness probe), it adds the Pod's IP:port to an Endpoints object.
🗄️ API Servernotifies: "new Service created"
↓
1 👁️ Endpoint Controllerwatches Services + Pods
↓
Scans: "find all Pods with label app=web that are Ready"

Pods found with app=web + Ready ✓
web-abc1210.244.1.5:80 ✓ Ready web-def3410.244.2.3:80 ✓ Ready web-ghi5610.244.3.7:80 ✓ Ready
↓
2 📋 Endpoints: web-svc10.244.1.5:80, 10.244.2.3:80, 10.244.3.7:80
Endpoint Controller creates/updates Endpoints object in API Server
Only Ready Pods get endpoints
web-abc1210.244.1.5 ✓ Ready → IN endpoints
web-xyz9910.244.1.8 ✗ Not Ready → NOT in endpoints
web-def3410.244.2.3 ✓ Ready → IN endpoints
Why readiness matters

A Pod that's Running but NOT Ready (e.g., app is still loading config, warming cache) is excluded from endpoints. Traffic is NEVER sent to unready Pods. This is why readiness probes are critical for zero-downtime deployments.

03 Creation Step ③ — kube-proxy Programs iptables on Every Node ▶

What happens
Diagram — All nodes
iptables rules
kube-proxy runs as a DaemonSet on EVERY node. It watches the API Server for Service and Endpoint changes. When it sees web-svc (ClusterIP 10.96.0.15) with Endpoints [10.244.1.5, 10.244.2.3, 10.244.3.7], it programs iptables NAT rules on its node so that any packet destined for 10.96.0.15:80 is intercepted and rewritten (DNAT) to one of the real Pod IPs.
🗄️ API ServerService + Endpoints changed
↓ watch event to all kube-proxy instances ↓

Node 1 (192.168.1.10)
⚙️ kube-proxy → 🔥 iptables rules updated10.96.0.15:80 → DNAT → 3 backends
Node 2 (192.168.1.11)
⚙️ kube-proxy → 🔥 iptables rules updated10.96.0.15:80 → DNAT → 3 backends
Node 3 (192.168.1.12)
⚙️ kube-proxy → 🔥 iptables rules updated10.96.0.15:80 → DNAT → 3 backends
Every node now knows: "if I see packet to 10.96.0.15:80, rewrite destination to a real Pod IP"
What the iptables rules actually look like
Simplified iptables NAT chain on EVERY node:

KUBE-SERVICES chainif dst=10.96.0.15:80 → jump to KUBE-SVC-WEB
↓
KUBE-SVC-WEB chainprobability 0.33 → KUBE-SEP-1probability 0.33 → KUBE-SEP-2probability 0.33 → KUBE-SEP-3
↓
KUBE-SEP-1DNAT to 10.244.1.5:80 KUBE-SEP-2DNAT to 10.244.2.3:80 KUBE-SEP-3DNAT to 10.244.3.7:80
Key insight

The ClusterIP 10.96.0.15 is never assigned to a NIC. It only exists in iptables rules. When a packet with dst=10.96.0.15 enters the kernel's network stack, the PREROUTING/OUTPUT chain catches it and rewrites the destination to a real Pod IP. The packet then travels to the actual Pod as if the Service never existed.

04 Creation Step ④ — CoreDNS Registers DNS Record ▶

What happens
Diagram
CoreDNS (Deployment in kube-system) also watches the API Server. When it sees the new Service, it creates a DNS A record: web-svc.default.svc.cluster.local → 10.96.0.15. Every Pod's /etc/resolv.conf points to CoreDNS as the nameserver, so Pods can now resolve web-svc to the ClusterIP.
🗄️ API Server →→→ 🌐 CoreDNSwatches Service objects
↓
DNS A record created:web-svc.default.svc.cluster.local → 10.96.0.15

Inside every Pod:
Any Pod/etc/resolv.conf: nameserver 10.96.0.10 (CoreDNS)
search default.svc.cluster.local svc.cluster.local cluster.local
↑ This search domain is why "curl web-svc" works — it appends ".default.svc.cluster.local"
1 / 2
Creation Summary

① kubectl → API Server stores Service + assigns ClusterIP. ② Endpoint Controller finds matching Ready Pods → builds Endpoints list. ③ kube-proxy (on every node) → programs iptables DNAT rules. ④ CoreDNS → creates DNS A record. Now the Service is fully operational — any Pod can curl web-svc:80.

05 ClusterIP Request — Packet Journey Step by Step ▶

① App calls DNS
② DNS resolves
③ Packet created
④ iptables intercepts
⑤ DNAT rewrites
⑥ CNI routes
⑦ Pod receives
⑧ Response
① Application code makes HTTP request
📱 App Pod (Node 1)code: curl http://web-svc:80/api
↓
App uses the SERVICE NAME, not an IP. The OS resolver is triggered.
The app calls web-svc:80. The HTTP library triggers a DNS lookup via the OS resolver. The Pod's /etc/resolv.conf points to CoreDNS (10.96.0.10).
② CoreDNS resolves the name to ClusterIP
📱 App Pod → DNS query: "web-svc.default.svc.cluster.local?" → 🌐 CoreDNS10.96.0.10:53
↓
Response: A recordweb-svc → 10.96.0.15 → 📱 App Podnow knows: web-svc = 10.96.0.15
③ App Pod creates a TCP packet
📦 TCP Packet createdsrc: 10.244.1.2:45678 (App Pod)dst: 10.96.0.15:80 (ClusterIP)
↓ enters kernel network stack on Node 1
Packet has destination = ClusterIP. But this IP doesn't exist on any NIC!
④ iptables intercepts the packet (OUTPUT chain)
🔥 iptables OUTPUT chain (Node 1 kernel)rule: if dst = 10.96.0.15:80 → jump to KUBE-SVC-WEB
↓ match!
iptables catches the packet BEFORE it reaches the wire. The packet is "trapped" in the kernel.
Since the packet originates FROM a Pod on this node, it hits the OUTPUT iptables chain. kube-proxy's rules match on destination=10.96.0.15 and redirect to the Service's chain.
⑤ iptables DNAT — rewrites destination to a real Pod IP
🎲 KUBE-SVC-WEB chainrandom probability:33% → 10.244.1.5 | 33% → 10.244.2.3 | 33% → 10.244.3.7
↓ random selects 10.244.2.3 (Pod on Node 2)
✏️ DNAT (Destination NAT)BEFORE: dst = 10.96.0.15:80AFTER: dst = 10.244.2.3:80
The packet's destination IP is rewritten from the virtual ClusterIP to a real Pod IP. The packet now looks like it was always going to the Pod directly. conntrack remembers this mapping for the response.
⑥ CNI routes the packet to the destination node
📦 Packetsrc: 10.244.1.2 | dst: 10.244.2.3
↓
🖥️ Node 1 routing table10.244.2.0/24 → via VXLAN tunnel → Node 2
↓ VXLAN encapsulate (or BGP route)
Physical network: Node 1 (192.168.1.10) → Node 2 (192.168.1.11)
↓ decapsulate on Node 2
🖥️ Node 2delivers to Pod at 10.244.2.3
The CNI plugin (Calico/Flannel/Cilium) handles cross-node routing. With VXLAN, the packet is encapsulated in a UDP packet between nodes. With BGP (Calico), nodes have direct routes. Either way, the packet reaches the destination Pod.
⑦ Target Pod receives and processes the request
🎯 web-def34 (10.244.2.3:80, Node 2)nginx receives HTTP GET /apiprocesses request, generates response
⑧ Response travels back — conntrack reverses the NAT
📦 Response packetsrc: 10.244.2.3:80 | dst: 10.244.1.2:45678
↓ CNI routes Node 2 → Node 1
🔄 conntrack on Node 1remembers: this connection was DNAT'd from 10.96.0.15reverse: src 10.244.2.3 → rewrite to 10.96.0.15
↓
📱 App Pod sees response from 10.96.0.15:80App thinks it talked to ClusterIP directly. It never knew about 10.244.2.3.
Key

The App Pod only ever sees the ClusterIP (10.96.0.15). It has no idea the request was routed to 10.244.2.3 on a different node. The DNAT + conntrack makes the Service completely transparent. This is the beauty of Kubernetes Services.

Full flow

↓
4 🎲 KUBE-SVC-WEBsame probability chain as ClusterIPselects: 10.244.3.7:80 (Pod on Node 3)

↓ response: Node 3 → Node 1 → User

Why ANY node's IP works — even without the Pod
Node 2 (no web Pods here!)
kube-proxy → iptables: port 30080 → DNAT to Pod on Node 1 or Node 3
kube-proxy programs iptables on ALL nodes, even nodes without the target Pod. The request enters on Node 2, gets DNAT'd to a Pod on a different node, and CNI routes it there.
externalTrafficPolicy: Local — avoid extra hops
spec:
  externalTrafficPolicy: Local   # Only route to Pods on THIS node
User → Node 1:30080 → Only Pods on Node 1. If none → connection refused!
Cluster (default): Any backend Pod, may cross nodes. Even load. Extra hops.
Local: Only Pods on the same node. No extra hops. Preserves client IP. But uneven load — nodes without Pods return nothing.

08 Case: Pods on Same Node — Local Path ▶

Diagram
Packet path
Node 1 — everything here
⚙️ kube-proxy + iptables
📱 App Pod (10.244.1.2) → curl web-svc → 🔥 iptablesDNAT → 10.244.1.5 → 🎯 Web Pod (10.244.1.5)
🚀 Fastest path — packet never leaves the node. No VXLAN. No physical network. Just kernel routing.
Path: App Pod → kernel OUTPUT chain → iptables DNAT (10.96.0.15 → 10.244.1.5) → kernel routes locally (same subnet 10.244.1.x) → Web Pod receives. Response: Web Pod → kernel → conntrack reverses SNAT → App Pod.
Performance

Local routing = microseconds. No network serialization, no encapsulation. This is why co-locating communicating Pods on the same node (via pod affinity) can improve latency-sensitive apps.

Cross-node overhead
VXLAN (Flannel, Calico VXLAN mode): ~50 bytes overhead per packet (UDP encapsulation). Adds ~0.1ms latency.

BGP (Calico native mode): No encapsulation. Direct L3 routing. Near-zero overhead. But requires network infrastructure support.

eBPF (Cilium): Bypasses iptables entirely. Processes packets in kernel BPF programs. Fastest option but more complex.

New Pod now receives traffic! The Service "discovered" it automatically via label selector.
Critical: Pod ONLY gets traffic AFTER readiness passes
Pod Running but NOT Readyreadiness probe failing → NOT in endpoints → NO traffic
Pod Running AND Readyreadiness probe passing ✓ → IN endpoints → receives traffic ✓
Without readiness probes

Pod is "Ready" the moment the container starts. But the app may need 30 seconds to load config, warm cache, connect to DB. During those 30s, the Pod is in endpoints and receives traffic but returns errors. Always set readiness probes!

13 Troubleshoot: No Endpoints — Component Breakdown ▶

Where it breaks
Diagnose
Fix
Service: web-svc (selector: app=web)
↓
❌ Endpoints: <none>No Pod IPs! Service has nowhere to send traffic.
↓
iptables: no backends → connection refused
3 reasons Endpoints are empty:
① Service selector app=web doesn't match any Pod labels (typo: Pods have app=nginx).
② No Pods exist with the matching label at all.
③ Pods exist but ALL are failing readiness probes (Ready: 0/1).
# Step 1: Check endpoints
kubectl get endpoints web-svc
# <none> — problem confirmed

# Step 2: Check Service selector
kubectl get svc web-svc -o jsonpath='{.spec.selector}'
# {"app":"web"}

# Step 3: Check Pods with that label
kubectl get pods -l app=web
# No resources found ← selector mismatch or no Pods!

# Step 4: Check actual Pod labels
kubectl get pods --show-labels
# web-xxx   app=nginx  ← wrong label!
# Fix A: Change Pod labels to match Service selector
kubectl label pod web-xxx app=web --overwrite

# Fix B: Change Service selector to match Pod labels
kubectl patch svc web-svc -p '{"spec":{"selector":{"app":"nginx"}}}'

# Fix C: If Pods failing readiness → fix the probe or the app
kubectl describe pod web-xxx | grep -A5 Readiness
