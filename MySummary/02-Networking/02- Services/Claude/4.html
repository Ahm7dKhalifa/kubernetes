01 After iptables — Who Actually Sends the Packet? ▶

The answer
Diagram
Analogy
Nobody "sends" it — the kernel just modifies the packet in-flight
The Critical InsightWhen App-1 sends a packet to 10.96.0.15:80 (ClusterIP), the packet enters the Linux kernel's network stack. Before the packet leaves the node, it passes through the kernel's netfilter hooks. At the PREROUTING hook, an iptables DNAT rule changes the destination header from 10.96.0.15 to 10.244.2.3 (a real Pod IP). The packet then continues through the kernel normally with the new destination. The kernel's routing table decides: is 10.244.2.3 local (same node) or remote (different node)? Then it delivers accordingly.

iptables does NOT "forward" or "resend" the packet. It just changes the header. The kernel's normal routing does the rest. Think of it as a post office worker crossing out the wrong address on an envelope and writing the correct one — the mail carrier (kernel routing) delivers it normally.
The packet's real journey through the kernel
Analogy: The postal system
How to think about it App-1 = you writing a letter addressed to "Customer Service Dept" (ClusterIP 10.96.0.15)
iptables DNAT = the mailroom clerk who crosses out "Customer Service Dept" and writes "John Smith, Room 203" (Pod IP 10.244.2.3) on the envelope
Kernel routing = the mail carrier who sees the address and delivers it
conntrack = the clerk remembers "replies from Room 203 should show 'Customer Service Dept' as return address"

The clerk doesn't carry the letter. The carrier doesn't know the address was changed. Everyone does their one job. The letter flows through the system without anyone "resending" it.

03 Same Node — Request Path ▶

Diagram
Packet at each step
Exact packet headers at each step
# ❶ App-1 creates packet (after DNS resolves web-svc → 10.96.0.15):
src: 10.244.1.5:44320 → dst: 10.96.0.15:80  ← virtual Service IP

# ❸ After iptables DNAT (same packet, header modified in-flight):
src: 10.244.1.5:44320 → dst: 10.244.1.6:80  ← real Pod IP (header rewritten!)

# ❹ Kernel routing: 10.244.1.6 is on local subnet → local delivery

src: 10.244.1.5:44320 → dst: 10.244.1.6:80  ← same packet, delivered locally

# Web Pod has NO IDEA the original destination was 10.96.0.15
# It just sees a packet from 10.244.1.5 addressed to its own IP

04 Same Node — Response Path ▶

Diagram
Packet headers
# ❶ Web Pod creates response:
src: 10.244.1.6:80 → dst: 10.244.1.5:44320

# ❷ conntrack reverses the DNAT (automatic SNAT on POSTROUTING):
src: 10.96.0.15:80 → dst: 10.244.1.5:44320   ← src changed to ClusterIP!

# ❹ App-1 receives:
src: 10.96.0.15:80 → dst: 10.244.1.5:44320
# App thinks the response came from 10.96.0.15 (the Service)
# It has NO IDEA it actually came from 10.244.1.6 (specific Pod)
# This transparency is the whole point of Services!

05 Cross Node — Request Path ▶

Diagram
Packet headers
# ❶ App sends:
src: 10.244.1.5:44320 → dst: 10.96.0.15:80  ← ClusterIP

# ❷ iptables DNAT (Node 1 kernel):
src: 10.244.1.5:44320 → dst: 10.244.2.3:80  ← real Pod IP on Node 2

# ❹ CNI wraps in VXLAN (outer addresses are NODE IPs):
outer: src=192.168.1.10 dst=192.168.1.11  ← node-to-node
inner: src=10.244.1.5    dst=10.244.2.3     ← pod-to-pod (unchanged)

# ❺ Travels over physical network (ethernet/switch) to Node 2

# ❼ CNI unwraps on Node 2:
src: 10.244.1.5:44320 → dst: 10.244.2.3:80  ← original inner packet

# ❾ Web Pod receives: same src/dst as step ❷

08 Headless — Direct Path (No iptables!) ▶

Completely different flowWith a Headless Service, there is NO ClusterIP, NO iptables DNAT, NO kube-proxy involvement. DNS returns raw Pod IPs. The client connects directly to the Pod — same as plain Pod-to-Pod networking. The only "Service" part is the DNS lookup.
Request + Response
Packet trace
# ① DNS resolves pg-0.pg-svc → 10.244.2.3 (raw Pod IP, no ClusterIP)

# ③ App sends directly to Pod IP (iptables has NO DNAT rule for this):
src: 10.244.1.5:44320 → dst: 10.244.2.3:5432

# ④ pg-0 Pod on Node 2 receives and responds:
src: 10.244.2.3:5432 → dst: 10.244.1.5:44320

# ⑤ App receives response (NO conntrack rewrite — real Pod IP visible!):
src: 10.244.2.3:5432 → dst: 10.244.1.5:44320

# KEY DIFFERENCES from ClusterIP:
# ✗ No iptables DNAT (no virtual IP to rewrite)
# ✗ No conntrack (no rewrite to reverse)
# ✗ No kube-proxy involvement at all
# ✓ Just plain Pod-to-Pod networking via CNI
# ✓ App sees the REAL Pod IP (not hidden behind a VIP)
