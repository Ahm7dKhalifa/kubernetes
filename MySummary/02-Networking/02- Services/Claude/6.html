03 ClusterIP — Cross Node Route ▶

Request →
Response ←
How kube-proxy decides
Response ← (green arrows going LEFT and UP)
How does kube-proxy / iptables decide LOCAL vs REMOTE?
It doesn't "decide" — it's randomiptables has probability-based DNAT chains. With 3 Pods it's 33% each. kube-proxy does NOT prefer local Pods by default. The choice is random — sometimes local, sometimes cross-node.

To force local routing: set internalTrafficPolicy: Local on the Service → iptables only includes Pods on the SAME node. Reduces latency but risks uneven load.

After iptables picks a Pod IP: the kernel's routing table determines if it's local (same subnet) or remote (different subnet). This is pure IP routing — not a "decision" by kube-proxy.
# iptables chain (simplified) — probability-based:
-A KUBE-SVC-xxx -m statistic --mode random --probability 0.333 -j KUBE-SEP-aaa  # → 10.244.1.6
-A KUBE-SVC-xxx -m statistic --mode random --probability 0.500 -j KUBE-SEP-bbb  # → 10.244.2.8
-A KUBE-SVC-xxx                                                -j KUBE-SEP-ccc  # → 10.244.3.4

# After DNAT, kernel routing decides local vs remote:
# ip route show:
10.244.1.0/24 dev cni0     # ← LOCAL (same node) → veth delivery
10.244.2.0/24 via 192.168.1.11  # ← REMOTE → CNI tunnel to Node 2
10.244.3.0/24 via 192.168.1.12  # ← REMOTE → CNI tunnel to Node 3

05 LoadBalancer — Internet → Pod ▶

Full flow
ClusterIP (10.96.0.15) — iptables DNAT rules on every node Layer 2: NodePort (30080) — port opened on every node's real IP Layer 3: Cloud LB (35.192.0.1) — public IP → health checks nodes → forwards to NodePort Same internal path as NodePort: LB → Node:30080 → iptables DNAT → Pod (local or cross-node via CNI) Response: Pod → conntrack reverses → Node:30080 → LB → Internet ⚠ On bare-metal / minikube: EXTERNAL-IP stays <pending> forever (no cloud LB). Use MetalLB or minikube tunnel.

06 Headless — PostgreSQL Primary/Replica ▶

Full flow
Response
Response: direct from Pod — no conntrack rewrite!
# Client connects directly to pg-0 (no iptables involved):
src: 10.244.1.5:44320 → dst: 10.244.1.6:5432  ← real Pod IP, not VIP

# pg-0 responds directly:
src: 10.244.1.6:5432 → dst: 10.244.1.5:44320

# Client receives → sees REAL Pod IP as source
# (In ClusterIP, conntrack would rewrite to 10.96.0.15)
# (In Headless, no rewrite — full transparency!)

# This is how PostgreSQL drivers know which node is primary:
# host=pg-0.pg-svc,pg-1.pg-svc target_session_attrs=read-write

07 Egress — Pod → External Website ▶

Request ↓
Response ↑
Response: External → Node → conntrack reverse → Pod
# ❼ Stripe responds:
src: 142.250.80.46:443 → dst: 73.45.12.99:44320 (public IP)

# Router/ISP reverse NAT:
src: 142.250.80.46:443 → dst: 192.168.1.10:44320 (Node IP)

# Node NIC receives → conntrack reverse SNAT:
src: 142.250.80.46:443 → dst: 10.244.1.5:44320 (Pod IP restored!)

# Kernel routes to local Pod subnet → veth → App Pod receives ✓
# App sees: response from 142.250.80.46 addressed to its Pod IP
# SNAT was completely transparent — App never knew it happened
