v3 — Request & response packet flow between every component. Where the Service object actually exists and how traffic really routes through the cluster.

01 A Service Is Virtual — It Lives EVERYWHERE ▶

The truth
Where it lives
Full diagram
A Service is NOT a Pod, NOT a process, NOT on any node
Key InsightA Service has NO running process. There is NO "Service Pod" on any node. The ClusterIP (10.96.0.15) is a virtual IP — it exists only as iptables/IPVS rules programmed by kube-proxy on EVERY node. When a packet is sent to the ClusterIP, the Linux kernel's netfilter (iptables) intercepts it before it even leaves the node and rewrites the destination to a real Pod IP.
Common misconception

"The Service lives on the control plane" → WRONG. The Service OBJECT is stored in etcd (on the control plane), but the traffic routing happens via iptables rules on EVERY worker node. The control plane never handles Service traffic.

Where each part of a Service exists
ComponentWhereWhat it does
Service Object (YAML definition)etcd (control plane)Stores the spec: selector, ports, ClusterIP. Just data — no traffic handling.
Endpoints Objectetcd (control plane)List of Pod IPs matching the selector. Updated by the Endpoint Controller.
DNS RecordCoreDNS Pods (usually on worker nodes)Resolves web-svc → 10.96.0.15. Watches Service objects.
iptables / IPVS RulesEVERY node (kernel level)The actual traffic routing. Rewrites ClusterIP → Pod IP. This is where the "magic" happens.
kube-proxyEVERY node (DaemonSet)Watches Service/Endpoints changes → programs iptables/IPVS rules. Does NOT handle traffic itself.
Key

kube-proxy is NOT a proxy in the traditional sense. It doesn't forward traffic. It just programs rules. The Linux kernel (iptables) does the actual packet rewriting. kube-proxy is a "rule programmer."

03 kube-proxy Role — Rule Programmer, Not a Proxy ▶

Definitionkube-proxy is a DaemonSet Pod that runs on EVERY node. It watches the API server for Service/Endpoint changes and programs iptables (or IPVS) rules in the node's Linux kernel. It does NOT sit in the data path — actual packets never flow through kube-proxy. The kernel handles packet rewriting directly.

09 Does App Connect to iptables or kube-proxy?

AnswerThe App Pod connects to neither directly. The App sends a normal TCP packet to the ClusterIP (e.g., 10.96.0.15:80). The Linux kernel's netfilter (iptables) intercepts the packet transparently at the network stack level — before the packet even leaves the Pod's network namespace. The App has no idea iptables is rewriting the destination. kube-proxy is never in the packet path — it only programmed the rules earlier.
ComponentIn the data path?Role
App PodYes — sourceSends packet to ClusterIP
iptables (kernel)Yes — transparentRewrites destination IP (DNAT) at kernel speed
CNI (Calico/Cilium)Yes — if cross-nodeDelivers packet to target node via overlay/BGP
Target PodYes — destinationReceives the request, sends response
kube-proxyNOOnly programs iptables rules. Not in packet path.
API ServerNOOnly stores Service/Endpoints objects. Not in packet path.
etcdNOOnly stores data. Not in packet path.

10 Response Path — conntrack Remembers ▶

Definition — conntrackThe Linux connection tracking system. When iptables DNATs a packet (rewrites ClusterIP → Pod IP), conntrack remembers the original destination. When the response comes back from the Pod, conntrack automatically reverses the rewrite — so the App sees the response coming from the ClusterIP (not the Pod IP). The App never knows it was talking to a specific Pod.

11 Summary — Where Everything Lives

QuestionAnswer
Where does the Service object live?In etcd (control plane). Just data — name, selector, ClusterIP, ports.
Where does the Service route traffic?Nowhere specific — iptables rules on EVERY node do the routing.
Does traffic go through the control plane?NEVER. The control plane only stores/notifies. Zero traffic passes through it.
Does traffic go through kube-proxy?NEVER. kube-proxy only programs iptables rules. It's not in the data path.
What actually routes packets?iptables (Linux kernel) on the source Pod's node. Kernel-speed DNAT.
What about cross-node?CNI plugin (Calico/Cilium/Flannel) delivers packets between nodes after iptables rewrites the destination.
What about Headless Services?No iptables involved at all. DNS returns Pod IPs directly. Client connects to Pods without any intermediate routing.
The Big Picture

A Service is an abstraction distributed across all nodes. The definition lives in etcd. The DNS record lives in CoreDNS. The routing rules live in iptables on every node. There is no single "Service machine" — it's a cluster-wide concept implemented by cooperation between the API server, endpoint controller, kube-proxy, iptables, and CoreDNS.
