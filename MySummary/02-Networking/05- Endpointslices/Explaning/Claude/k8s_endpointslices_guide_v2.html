Kubernetes EndpointSlices

The live backend list behind every Service — how the controller builds it, how kube-proxy, CoreDNS and the AWS Load Balancer Controller read it, and how to write your own. Jahez context: EKS in me-central-1, namespace jahez-prod.

Jahez reference · v1 · Kubernetes v1.34+ · companion to Services v3
Part I · High Level

1. Foundations

1.1Introduction

In one sentenceAn EndpointSlice is the live, chunked list of backend addresses behind a Service — which Pod IPs, on which ports, in what state and in which zone.

An EndpointSlice is a namespaced Kubernetes API object in the discovery.k8s.io/v1 group (stable since v1.21, maintained by SIG Network). Each slice holds up to 100 endpoints by default. The EndpointSlice controller inside kube-controller-manager creates and updates slices for every Service that has a selector. Everything that needs to know "where are the Pods of this Service right now" reads them: kube-proxy on every node, CoreDNS for headless names, the AWS Load Balancer Controller for IP targets, Gateway API and mesh controllers. It replaces the single-object v1 Endpoints API, which is deprecated since v1.33.

✓ It is

  • A data object: a list of addresses + ports + conditions + topology
  • Written by a controller (or by you for selectorless Services)
  • Chunked: one Service can own many slices
  • The source of truth kube-proxy uses to program iptables / IPVS / nftables rules
  • Per address family: an IPv4 slice and an IPv6 slice are separate objects

✕ It is not

  • Not a load balancer — it moves no packets
  • Not the Service: the Service is the stable name + virtual IP; the slice is the changing backend list
  • Not a health checker — it copies Pod readiness, it does not probe
  • Not something you edit for selector Services: the controller overwrites your changes
  • Not the legacy Endpoints object (one per Service, no zones, no terminating state)

1.2Problems or needs

In one sentenceA Service is only a name and a virtual IP; something must keep a live list of the Pods behind it — and before EndpointSlices that list was one giant object per Service.

1.3Solution

In one sentenceCut the big list into small slices of ≤100 endpoints, give each endpoint its own state and zone, and let only the changed slice travel.

The solution in steps

  1. Slice it. The controller writes many small EndpointSlices per Service, each with at most 100 endpoints.
  2. One family, one port set per slice. IPv4 and IPv6 live in different slices; Pods whose named port resolves differently go to different slices.
  3. Update only what changed. A Pod change rewrites the one slice that holds it. Other slices are not touched.
  4. State per endpoint. ready, serving and terminating let readers drain Pods gracefully.
  5. Place per endpoint. nodeName, zone and hints make zone-local routing possible.
  6. Labels, not names. kubernetes.io/service-name links slices to a Service; managed-by lets several writers coexist.

In one sentenceRuns 3 Pods labelled app: order-api, with port http and a readiness probe — the three things the slice depends on.
YAMLorder-api-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-api-deployment
  namespace: jahez-prod
  labels:
    app: order-api
spec:
  replicas: 3
  selector:
    matchLabels:
      app: order-api
  template:
    metadata:
      labels:
        app: order-api               # ← the Service selector matches this
    spec:
      terminationGracePeriodSeconds: 45
      topologySpreadConstraints:     # one Pod per zone → one endpoint per zone
        - maxSkew: 1
          topologyKey: topology.kubernetes.io/zone
          whenUnsatisfiable: ScheduleAnyway
          labelSelector:
            matchLabels:
              app: order-api
      containers:
        - name: order-api
          image: 123456789012.dkr.ecr.me-central-1.amazonaws.com/jahez/order-api:2026.11.3
          ports:
            - name: http             # ← targetPort "http" resolves to 8080
              containerPort: 8080
            - name: metrics
              containerPort: 9090
          readinessProbe:            # ← drives conditions.ready / serving
            httpGet:
              path: /health/ready
              port: http
            periodSeconds: 5
            failureThreshold: 2
          lifecycle:
            preStop:                 # keep serving while readers drop the endpoint
              sleep:
                seconds: 15
What each block does
  • template.metadata.labels — what the Service selector matches.
  • ports[].name: http — the name the Service targetPort resolves.
  • readinessProbe — flips conditions.ready.
  • preStop.sleep + terminationGracePeriodSeconds — keep serving while readers remove the endpoint.
  • topologySpreadConstraints — one Pod per zone, so zone hints have something in every zone.

YAMLorder-api-service.yaml

kind: Service
metadata:
  name: order-api-service
  namespace: jahez-prod

    app: order-api

  type: ClusterIP
