PART I · 01—04

Foundations

What endpoints actually are, why slices exist, and what's inside one.

§1 The Problem — Why Endpoints Exist At All

You probably already know what a Service does: it gives a stable virtual IP and DNS name to a set of Pods. kubectl get svc shows you products-svc → 10.96.42.7 and you call it from anywhere in the cluster. That part is the friendly face.

But that friendly face is a lie of omission. A Service doesn't actually know anything about its Pods. A Service is just a label selector and a virtual IP. Something else has to do the messy real work — keep a live, dynamic list of "which Pod IPs are alive right now, on which nodes, are they ready, are they terminating, what zone are they in?" — and feed that list to every kube-proxy on every node so packets get DNAT'd to a real backend.

That "something else" is the Endpoint object. And later, the EndpointSlice.

The chain of trust

The four problems Endpoints solves

Problem 1 — Pods are mortal

A Pod is killed, rescheduled, gets a brand-new IP from the CNI. If clients held the old IP, they break. Endpoints decouples identity (a name) from address (a churn-prone IP).

Problem 2 — Pods don't know about each other

Pod A talking to Pod B by IP would need to discover Pod B somehow. Endpoints centralizes that discovery into a single watched API object so every component (kube-proxy, DNS, ingress, mesh) sees the same truth.

Problem 3 — Health changes the routable set

A Pod can be running but not ready (failing its readiness probe). It can be terminating but still serving in-flight requests. The endpoint object encodes ready, serving, and terminating per address so routers can react in milliseconds.

Problem 4 — kube-proxy needs a watch source

Every node runs kube-proxy which programs the kernel (iptables/ipvs/nftables) so that packets to the Service VIP get DNAT'd to a real Pod IP. kube-proxy doesn't watch Pods directly — that would be too noisy. It watches Endpoints / EndpointSlices, which already filter for "ready, in this service".

Why "Slice" and not "Endpoint"

The old Endpoints API stored every backend IP for a Service inside one big object. That worked at 10 Pods. It melted at 5,000 Pods: every Pod change rewrote the whole object, every kube-proxy on every node received the full new copy, control-plane traffic exploded.

EndpointSlices break that single document into many small ones (default cap: 100 endpoints per slice). A Pod change now rewrites one slice, not the whole list. §13 has the side-by-side comparison.

One sentence to remember: a Service publishes a name and a VIP; an EndpointSlice publishes the live list of Pod IPs behind it; kube-proxy reads the slice and writes kernel rules so packets land correctly.

§2 What Is an Endpoint?

An Endpoint (singular) is the most primitive concept here: a { IP, port, protocol } tuple plus enough metadata to say "this address belongs to this Pod, on this node, in this zone, and right now its conditions are X."

An Endpoint is not a Kubernetes object on its own. It's a row inside a larger object. There are two larger objects that hold rows of endpoints:

① Endpoints (the API)

The legacy v1 object. kind: Endpoints. Holds all rows for a Service in one document under subsets[].

Deprecated in v1.33. Still present for backward compatibility.

② EndpointSlice (the API)

The modern object. kind: EndpointSlice. Holds up to ~100 endpoint rows per slice; many slices per Service.

GA in v1.21. Source of truth for kube-proxy today.

The five fields that define an endpoint row

Whether you look at the old Endpoints or the new EndpointSlice, an endpoint row carries the same essential information:

FieldWhat it isExample
addressesOne or more IPs (always exactly 1 for controller-managed slices)10.244.1.7
conditionsready / serving / terminating booleansready: true
targetRefWhich Pod this address belongs tokind: Pod, name: products-7f8d
nodeNameWhich node the Pod is on (drives topology routing)worker-2
zoneFailure / availability zone of the nodeme-central-1a

An Endpoint is not the same as a Pod

This is the most common confusion. Watch this carefully:

Pod = a workload object. Has containers, status, owner ReplicaSet, restart policy. Exists whether or not any Service points at it.

Endpoint = a routing record. Exists because a Service exists and its selector matched this Pod. It's a derivative of the Pod, not the Pod itself.

If you delete a Service, the Pods stay alive — but every endpoint row for them disappears. If a Pod fails its readiness probe, the Pod stays alive — but its endpoint row flips ready: false and kube-proxy stops routing to it within milliseconds.

§3 What Is an EndpointSlice?

An EndpointSlice is a Kubernetes API object that groups together a subset of network endpoints that all share the same protocol, port, address family, and Service.

Three keywords matter here:

  • Subset — it does not contain all backends for the Service. There can be many slices per Service. Default cap is 100 endpoints per slice; tunable up to 1000 via --max-endpoints-per-slice on the controller-manager.
  • Grouped by — every endpoint inside one slice must share the same addressType (IPv4 vs IPv6 vs FQDN) and the same port set. If a Service exposes both IPv4 and IPv6, there are at minimum two slices.
  • Owned by — slices have an ownerReference back to the Service and a kubernetes.io/service-name label, so a watcher can find all slices for a Service with one label-selector query.

Naming convention

When the controller creates a slice for a Service called products-svc, it generates the slice name as products-svc-<5-char-random>. Example: products-svc-x7k2p.

If you list slices for a Service:

$ kubectl get endpointslices -l kubernetes.io/service-name=products-svc

NAME                  ADDRESSTYPE   PORTS   ENDPOINTS                       AGE
products-svc-x7k2p    IPv4          80      10.244.1.7,10.244.2.3,...       4d
products-svc-bn83l    IPv6          80      fd00::1:7,fd00::2:3,...         4d

Two slices — one per address family. Both belong to the same Service.

Why "100 per slice" specifically

Mostly an arbitrary chosen ceiling that balances two pressures:

  • Too small → too many slices → too many watch events on the API server.
  • Too large → defeats the purpose: a one-Pod change still triggers a full slice rewrite + broadcast.

At 100, a single Pod-add/remove rewrites ~100 endpoints worth of data, not 10,000. The controller doesn't actively rebalance — it fills slices and leaves them alone unless a slice is fully drained.

Subtle but important: the port in an EndpointSlice is the targetPort on the Pod, not the port the Service publishes. A Service can publish port 80 → target 8080; the slice shows 8080. That's because kube-proxy already knows it needs to DNAT 80→8080, and it only cares about where to send the packet after DNAT.

How They Work

The controller, the lifecycle, the dataplane, and the conditions that gate every packet.

§5 The EndpointSlice Controller

EndpointSlices don't appear by magic. There's a specific control-plane component that creates and updates them: the EndpointSlice controller, one of dozens of controllers running inside kube-controller-manager.

What it watches and what it writes

The reconcile algorithm (simplified)

When a Pod, Service, or Node changes, the controller's loop fires. Its job is to make slices match reality with the fewest possible API writes. From the upstream code:

# On change for Service S:
1. Find all Pods matching S.selector (label-selector via local informer cache)
2. Group them by (addressType, port set) → buckets
3. For each bucket:
   a. List existing EndpointSlices labelled kubernetes.io/service-name=S
   b. Compute desired endpoints (only ready or terminating pods that exist)
   c. # Pass 1: keep slices that are still useful
      For each existing slice:
        - Remove endpoints no longer desired
        - Update endpoints that changed (e.g. ready: true → false)
   d. # Pass 2: pack remaining new endpoints into modified slices first
      Add new endpoints to slices we already touched
   e. # Pass 3: only create new slices if no room left
      If endpoints remain, create new slice(s)
4. Send minimal create/update/delete API calls

Key design choice: the controller prioritizes fewer updates over perfect packing. If there are 10 new endpoints and 2 slices each with room for 5, it will create a new slice rather than touch both existing slices. Touching fewer slices = fewer watch events broadcast to every kube-proxy in the cluster.

§7 kube-proxy — The Consumer

An EndpointSlice is just data. The thing that turns that data into actual packet routing on every node is kube-proxy. Every node runs one (it's a DaemonSet).

What kube-proxy does, end-to-end

  1. Watches the Kubernetes API for Services, EndpointSlices, and (optionally) Nodes.
  2. Computes the desired set of dataplane rules: for each Service, the list of ready endpoint IPs and how to load-balance among them.
  3. Writes those rules to the Linux kernel using one of three backends:
    • iptables — default historically. Long chains of NAT rules. Simple, but O(n) rule evaluation per packet.
    • ipvs — uses the kernel's L4 load balancer. O(1) lookup. Best for clusters with thousands of Services.
    • nftables — newer, faster, replacing iptables on modern kernels. Default-eligible since v1.31.

What kube-proxy ignores

This is where conditions earn their keep. kube-proxy reads every slice but does not blindly route to every address. Its filtering logic is roughly:

# For each endpoint in the slice:
if conditions.ready == true:
    include in regular pool
elif conditions.serving == true and all_regular_endpoints_terminating:
    include in fallback pool  # PreferTerminating mode
else:
    skip entirely

# With externalTrafficPolicy: Local —
# only include endpoints where nodeName == this_node

# With topology hints —
# only include endpoints whose hints.forZones contains this_zone

Why kube-proxy filters again on top of the slice: the slice tells you everything that could serve the Service. kube-proxy decides what actually should, based on policies that depend on the current node (topology, externalTrafficPolicy, internalTrafficPolicy). The same slice produces different ruleset on different nodes.

Service mesh: bypassing kube-proxy

Service meshes (Istio, Linkerd, Cilium service mesh) read the same EndpointSlices but skip kube-proxy entirely. They program their own L7 proxies (Envoy sidecars, eBPF dataplane). That's why slices are the source of truth — they decouple discovery (controller writes slices) from dataplane (kube-proxy or mesh consumes them).

§8 Endpoint Conditions — ready vs serving vs terminating

The three boolean conditions are the most important fields on an endpoint row. They control whether a packet ever reaches a Pod. Understanding the subtle difference between them is essential for graceful shutdowns and zero-downtime deploys.

ConditionTrue when…Who reads it
readyPod's Ready condition is True AND Pod is not terminatingkube-proxy — primary routing decision
servingPod's Ready condition is True (regardless of terminating state)kube-proxy — fallback drain pool; service meshes for retries
terminatingPod has a deletionTimestamp setkube-proxy + meshes to drain in-flight requests

The matrix that catches everyone out

Here's what makes serving a separate field from ready:

Pod is…readyservingterminatingWhy
Just started, probe pending falsefalsefalse App not booted yet
Healthy and serving normally truetruefalse The happy path
Readiness probe started failing falsefalsefalse App unhealthy — pull from rotation
kubectl delete just hit falsetruetrue Drain mode: new conns blocked, in-flight allowed
Terminating + readiness now failing too falsefalsetrue Fully out — not even draining

Why serving exists: historically ready was reused for both "is the app healthy" and "should we route new traffic." When the platform added the concept of routing existing traffic to terminating pods for graceful drains, they needed a third state. So ready got narrowed to "yes new traffic", serving covers "the app can still handle a packet right now even if I shouldn't send it new connections."

§9 Auto-Generated Slice — From Service to Slice

The common case: you write a Deployment and a Service, the controller writes slices for you. Below is the full chain, every YAML, no shortcuts.

Step 1 — Deployment with readiness probe

apiVersion: apps/v1
kind: Deployment
metadata:
  name: products
  namespace: shop
spec:
  replicas: 3
  selector:
    matchLabels:
      app: products
  template:
    metadata:
      labels:
        app: products                  # ★ slice controller matches on this
    spec:
      containers:
      - name: app
        image: ghcr.io/jahez/products:1.4.2
        ports:
        - name: http                    # ★ named ports help readability
          containerPort: 8080
        - name: metrics
          containerPort: 9090

        readinessProbe:                   # ★ this controls ready=true/false
          httpGet:
            path: /health/ready
            port: http
          initialDelaySeconds: 5
          periodSeconds: 5
          failureThreshold: 3

  name: products-svc

§10 Manual EndpointSlice — Pointing at External Services

You're allowed to write EndpointSlices by hand. The classic use case: a Service that points at backends that aren't Kubernetes Pods — a legacy on-prem database, a managed RDS instance, a third-party API. You create a Service without a selector, then write the slice yourself.

Pattern 1 — Static external database

Scenario: your microservice wants to talk to analytics-db.internal:5432 at a stable Kubernetes DNS name (analytics-svc.shop.svc.cluster.local) so you can swap the backend later without changing app code.

kind: Service

  name: analytics-svc
  namespace: shop
spec:
  ports:

    protocol: TCP
    port: 5432
    targetPort: 5432

  conditions:
    ready: true

Now any pod can do psql -h analytics-svc.shop.svc.cluster.local -p 5432 and kube-proxy will load-balance between the two external IPs. If the DB IP changes, you edit the slice — no app deploys needed.

Three rules for manually-managed slices

  1. Set endpointslice.kubernetes.io/managed-by to anything except endpointslice-controller.k8s.io. That reserved value tells the built-in controller "this one is mine, I'll overwrite it". Pick something descriptive like ops-team or my-mesh.example.com/controller.
  2. Pick the addressType carefully. It's immutable — you cannot change a slice from IPv4 to IPv6 later. Delete and recreate.
  3. Each manual slice can hold up to 100 addresses. For more, write multiple slices with the same Service label.

Pattern 2 — ExternalName instead

If the external thing has a DNS name (not just an IP), don't write a manual slice. Use a Service of type ExternalName — it's a pure DNS CNAME and doesn't even involve kube-proxy:

apiVersion: v1
kind: Service
metadata:
  name: stripe-api
  namespace: payments
spec:
  type: ExternalName
  externalName: api.stripe.com                       # DNS CNAME

No slice is created. Pods doing curl stripe-api.payments get a CNAME to api.stripe.com via CoreDNS. Used when the upstream's IPs change frequently or are TLS-bound to a hostname.

Debugging "why is my Service returning 503"

A surprisingly common failure mode: the Service exists, Pods are running, but curl svc times out. The fix is almost always in the slices.

  1. Check that any slice exists for your Service. 
    kubectl get endpointslices -l kubernetes.io/service-name=YOUR_SVC -n YOUR_NS
    Empty result → the Service's selector matches zero Pods (typo in labels, or Pods are in another namespace).
  2. Check that endpoints are ready. 
    kubectl get endpointslices -l kubernetes.io/service-name=YOUR_SVC -n YOUR_NS -o yaml | grep ready:
    All false → readiness probes are failing. kubectl describe pod shows the probe failure reason.
  3. Check that the port resolves. The slice's ports[].port must match a real containerPort. If you used a named port that doesn't exist on the container, the slice will have port: 0 or no port — and kube-proxy will refuse to route.

Subtle gotcha: a Service whose selector matches Pods in a different namespace will produce an empty slice. Services and the Pods they select must be in the same namespace.

§12 Topology Aware Routing

By default kube-proxy load-balances randomly across all ready endpoints, regardless of which zone they're in. In a multi-zone cluster (say me-central-1a/b/c), this means traffic regularly crosses zones. Two problems:

  • Cost — cloud providers charge for cross-zone bandwidth.
  • Latency — same-zone is typically <1ms, cross-zone is several ms.

Topology aware routing solves this by letting the EndpointSlice controller annotate each endpoint with a hint — "this endpoint should preferentially serve clients from zone X." kube-proxy reads the hint and filters out endpoints whose hints don't include the current node's zone.

Enabling it — the modern way (Kubernetes 1.27+)

Set spec.trafficDistribution on the Service:

apiVersion: v1
kind: Service
metadata:
  name: products-svc
  namespace: shop
spec:
  trafficDistribution: PreferClose          # ★ enable topology routing
  selector:
    app: products
  ports:
  - port: 80
    targetPort: 8080

The legacy way (still works, pre-1.27)

metadata:
  annotations:
    service.kubernetes.io/topology-mode: Auto          # newer annotation
    # or the older:
    # service.kubernetes.io/topology-aware-hints: auto

What the slice looks like once hints are populated

The controller examines the zone of every node hosting a ready Pod, calculates how to balance traffic proportionally to each zone's capacity, and writes per-endpoint hints:

endpoints:
- addresses: ["10.244.1.7"]
  conditions: { ready: true, serving: true }
  nodeName: worker-1
  zone: me-central-1a
  hints:
    forZones:
    - name: me-central-1a                                # ★ serve only 1a clients

- addresses: ["10.244.2.3"]
  conditions: { ready: true, serving: true }
  nodeName: worker-2
  zone: me-central-1b
  hints:
    forZones:
    - name: me-central-1b                                # ★ serve only 1b clients

- addresses: ["10.244.0.9"]
  conditions: { ready: true, serving: true }
  nodeName: worker-3
  zone: me-central-1c
  hints:
    forZones:
    - name: me-central-1c

How traffic flows (3-zone, 6-pod example)

Safety fallback

What if your single in-zone Pod dies? kube-proxy falls back to using endpoints from all zones — the hints are preferences, not hard constraints. From the upstream docs:

If kube-proxy is unable to find at least one endpoint with a hint targeting the zone it is running in, it falls to using endpoints from all zones. This is the "PreferClose" semantic — same-zone if possible, cluster-wide otherwise.

When topology routing does NOT activate

  • Too few endpoints to safely balance. The controller has heuristics — if any zone has zero Pods or too few to handle its share, it skips hints to avoid overloading one zone.
  • Service has externalTrafficPolicy: Local or internalTrafficPolicy: Local. Those policies already constrain routing to the local node; mixing with topology hints would be confusing.
  • Nodes don't have topology.kubernetes.io/zone labels. Common on single-zone clusters or bare-metal.

§13 Dual-Stack & Address Types

An addressType is a slice's address family — IPv4 or IPv6. The field is immutable. One slice cannot mix IPv4 and IPv6 endpoints. This is by design: kube-proxy programs separate iptables/ipv6tables rule sets, so each ruleset wants its own slice to watch.

The third value FQDN was intended for endpoints that are domain names, but it's now deprecated and unused by the controller and kube-proxy.

The dual-stack case

apiVersion: v1
kind: Service
metadata:
  name: products-svc
spec:
  ipFamilyPolicy: RequireDualStack                  # ★ key field
  ipFamilies: [IPv4, IPv6]
  selector: { app: products }
  ports:
  - port: 80
    targetPort: 8080

Apply this and the controller writes two slices:

$ kubectl get endpointslices -l kubernetes.io/service-name=products-svc

The same three Pods, two slices, two address types. kube-proxy on each node consumes both — it programs iptables for IPv4 traffic and ip6tables for IPv6 traffic.

§18 Gateway Service — LoadBalancer + externalTrafficPolicy: Local

The gateway is the only externally-exposed service. We use type: LoadBalancer so the cloud provider provisions a public NLB, and externalTrafficPolicy: Local so that traffic landing on a node is only forwarded to gateway pods on that same node. This preserves the client source IP and avoids an extra cluster hop — but it makes the nodeName field on each EndpointSlice endpoint functionally critical.

Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: gateway
  namespace: shop
  labels: { app: gateway, tier: edge }
spec:
  replicas: 3
  selector:
    matchLabels: { app: gateway }
  template:
    metadata:
      labels: { app: gateway, tier: edge }
    spec:
      # Topology spread: try to put one gateway pod per zone.
      # Combined with externalTrafficPolicy:Local, this ensures every
      # node that receives external traffic has a local gateway pod.
      topologySpreadConstraints:
      - maxSkew: 1
        topologyKey: topology.kubernetes.io/zone
        whenUnsatisfiable: DoNotSchedule
        labelSelector:
          matchLabels: { app: gateway }
      containers:
      - name: gateway
        image: ghcr.io/jahez/gateway:1.14.2
        ports:
        - name: http
          containerPort: 8080
        readinessProbe:
          httpGet: { path: /actuator/health/readiness, port: http }
          periodSeconds: 3
          failureThreshold: 2
        livenessProbe:
          httpGet: { path: /actuator/health/liveness, port: http }
          periodSeconds: 10
        lifecycle:
          preStop:
            exec: { command: ["sh", "-c", "sleep 10"] }   # let slice update propagate
      terminationGracePeriodSeconds: 40

Service (LoadBalancer)

apiVersion: v1
kind: Service
metadata:
  name: gateway-svc
  namespace: shop
  annotations:
    service.beta.kubernetes.io/aws-load-balancer-type: "nlb"
    service.beta.kubernetes.io/aws-load-balancer-scheme: "internet-facing"
spec:
  type: LoadBalancer
  selector:
    app: gateway
  ports:
  - name: http
    port: 80
    targetPort: http        # named port — slice will store the resolved 8080
  externalTrafficPolicy: Local   # THE KEY FLAG
  # Default would be Cluster — kube-proxy would forward to ANY ready pod cluster-wide,
  # SNAT'ing the source IP. With Local, kube-proxy on a node only forwards to pods
  # with nodeName == that node. If no local pod exists, the LB health check fails
  # for that node and stops routing to it — preserving the client IP.
  internalTrafficPolicy: Cluster

What externalTrafficPolicy: Local changes in iptables

kube-proxy on each node filters the EndpointSlice locally before generating rules — it only emits KUBE-SEP entries for endpoints where nodeName == hostname.

# On worker-1, the gateway-svc chain has ONLY worker-1's pod:
$ iptables -t nat -L KUBE-XLB-GATEWAY -n
target              prot  opt  source       destination
KUBE-SEP-W1-GW      tcp   --   anywhere     anywhere     probability 1.000  -> 10.244.1.10:8080

# On worker-2:
KUBE-SEP-W2-GW      tcp   --   anywhere     anywhere     probability 1.000  -> 10.244.2.10:8080

# If worker-3's gateway pod dies and no replacement lands there before
# the slice updates, worker-3 has NO local endpoint. The NLB's TCP
# health check to port 80 on worker-3 fails (kube-proxy returns RST),
# and the NLB stops sending traffic to that node. Client traffic
# keeps flowing via worker-1 and worker-2.
Watch out: If you accidentally set replicas: 2 on a 3-node cluster with externalTrafficPolicy: Local, one node will permanently fail the NLB health check. Cluster-LB target utilization will look fine, but 1/3 of LB capacity is unused. Always pair Local with topology spread + replicas ≥ node count, or use a DaemonSet.

#         Patroni sidecar PATCHes pod labels:
#         pg-0 → role=demoted (or pod just disappears)
#         pg-1 → role=primary

#         postgres-rw slice now points to 10.244.2.20 (pg-1)

from pymongo import MongoClient

# mongodb+srv:// tells the driver to do a DNS SRV lookup,
# pull all replica set members, and connect to each one.
# The driver maintains its own monitor that periodically
# re-queries DNS — picking up changes from the EndpointSlice.
client = MongoClient(
  "mongodb+srv://mongo-headless.shop.svc.cluster.local/users?replicaSet=rs0&readPreference=secondaryPreferred"
)
db = client.users
profiles = db.profiles

The flow at runtime:

  1. PyMongo resolves _mongodb._tcp.mongo-headless.shop.svc.cluster.local → CoreDNS returns 3 SRV records (one per pod in the slice).
  2. Driver opens a socket to each pod, runs isMaster, learns who's primary, who's secondary.
  3. If a pod dies, its slice endpoint flips ready=false → CoreDNS no longer returns it → driver's next SRV re-query (every 60s by default) drops it.
  4. Driver's internal heartbeat also notices the closed socket within ~10s and re-routes operations.
The pattern: for any clustered database (Postgres/Patroni, MySQL Group Replication, MongoDB RS, Cassandra, Elasticsearch, Kafka), the recipe is the same: StatefulSet + headless Service + readinessProbe. §22 External Payments — Manual EndpointSlice for the Mada Gateway

Mada is the Saudi national payment processor. Like Visa or Stripe, it lives outside the cluster — its gateway runs at two static IPs on a private peered network. We want our payments microservice to call mada-payment-gateway.shop.svc.cluster.local like any other in-cluster service, with:

  • kube-proxy load balancing across the two Mada IPs
  • Network policies that work as if Mada were a Pod (deny-by-default with explicit egress allow to the Service)
  • Observability via standard service metrics

Pattern: a Service without a selector + a manually-managed EndpointSlice. No Pod is involved — we are writing the slice ourselves.

  # No nodeName — this address isn't on any cluster node.
  # No zone — we could set it to a fake zone if we want topology routing,

RuleWhy it matters
Label kubernetes.io/service-name MUST exist and match the Service nameThis is the only way kube-proxy joins your slice to the Service. Forget it and the slice is orphaned (the ClusterIP works but routes to nothing).

Keeping the slice in sync if Mada's IPs change

You have three options, in increasing order of robustness:

  1. Just GitOps it. Mada IPs rarely change. Commit the slice YAML, deploy via Argo CD. Done.
  2. External DNS controller. If Mada exposes api.mada.com.sa, use a tool like external-dns or kube-external-sync that periodically resolves the hostname and patches the slice.
  3. Custom operator. Watch the partner's API/notification webhook and patch the slice. Overkill for Mada specifically, but worth it for partners that change IPs weekly (some Cloudflare workers, ngrok endpoints, etc).

§24 Best Practices — Hard-Earned Defaults

1. Always have a real readinessProbe

Without one, kubelet defaults to "ready as soon as the container starts" — long before your app can actually serve traffic. EndpointSlices will then list every booting pod as ready: true, and kube-proxy will hammer them with traffic that the app drops. Symptom: occasional 502s during rollouts.

# Bad — defaults; ready as soon as the process exists
containers:
- name: app
  image: ...

# Good — readiness is what controls slice membership
containers:
- name: app
  image: ...
  readinessProbe:
    httpGet: { path: /actuator/health/readiness, port: http }
    periodSeconds: 3
    failureThreshold: 2
    successThreshold: 1

2. Use preStop + grace period to drain slices cleanly

When a pod is deleted, the slice is updated almost immediately (within ~500ms typically), but kube-proxy on every node may take another second or two to actually stop sending new connections. If your app exits the moment it gets SIGTERM, in-flight connections from kube-proxy still see an open socket and get RST. Solution: preStop sleep before SIGTERM, plus a generous terminationGracePeriodSeconds.

containers:
- name: app
  lifecycle:
    preStop:
      exec:
        # Slice update propagates in ~1-3s; sleep 10 is safe.
        # Combined with serving=true while terminating, in-flight requests drain.
        command: ["sh", "-c", "sleep 10"]
terminationGracePeriodSeconds: 40

3. Never re-use the reserved managed-by value for manual slices

The string endpointslice-controller.k8s.io is reserved for the built-in controller. If you tag a manually-managed slice with it, the controller may take ownership and overwrite your endpoints. Use any other identifier — your tool name, your team, the operator that writes it.

4. Set publishNotReadyAddresses: true for clustered databases' headless services

Patroni, MySQL Group Replication, MongoDB RS, and Cassandra all need to discover their peers before they're ready (so they can form a quorum). The default behavior of leaving not-ready endpoints out of the slice would cause a chicken-and-egg startup failure. publishNotReadyAddresses: true tells the slice controller to include endpoints with ready: false as long as the pod has an IP.

5. Don't write slices in kube-system

The slice controller treats some namespaces with elevated trust — and your slice could collide with one that another controller manages. Keep manual slices in your application namespaces (here, shop).

6. Pin replicas ≥ node count when using externalTrafficPolicy: Local

If any node lacks a local pod, the LB health check fails for that node. With replicas < nodes, you waste LB capacity. Either (a) ensure replicas ≥ node count and add topologySpreadConstraints, or (b) use a DaemonSet, or (c) use externalTrafficPolicy: Cluster and accept the source-IP loss.

7. Prefer trafficDistribution: PreferClose over old topology annotations

The service.kubernetes.io/topology-mode annotation still works for backwards compatibility, but spec.trafficDistribution: PreferClose (v1.27+) is the supported, GA way to ask for same-zone routing. It populates hints.forZones on slice endpoints; kube-proxy uses those hints automatically.

8. Watch slice churn during big rollouts

Every readiness flip causes a slice PATCH, which fans out to every kube-proxy. In a 500-node cluster with 5,000 pods rolling, slice churn can saturate the API server's watch budget. Mitigations: spread rollouts (maxSurge/maxUnavailable lower), bump --max-endpoints-per-slice to reduce slice count, use NodeLocal DNS to cut DNS-driven churn.

9. Treat slice count as a capacity signal

If you see slice counts climbing (multiple slices per Service), it means either you have >100 endpoints (split is expected) or your topology hints are fragmenting traffic. Both are worth investigating; the latter often indicates over-zealous topology configuration.

10. Stop reading the old Endpoints object — it's deprecated

If you have legacy controllers, operators, or scripts that read v1/Endpoints, plan to migrate them to discovery.k8s.io/v1/EndpointSlice. The Endpoints API was deprecated in v1.33 (April 2025). The compatibility mirror will be removed in a future release.

  curl -sv -m 3 http://$SVC.$NS.svc.cluster.local/health

# 8. Does the slice show the right port?
kubectl get endpointslice -n $NS -l kubernetes.io/service-name=$SVC \
  -o jsonpath='{.items[*].ports[*]}{"\n"}'

# 9. Topology hints active?
kubectl get endpointslice -n $NS -l kubernetes.io/service-name=$SVC \
  -o jsonpath='{.items[*].endpoints[*].hints}{"\n"}'

The most common 5-second fix

~70% of "my Service isn't working" bugs are: the Service selector doesn't match any Pod labels. Always start with step 4 above. If kubectl get pod -l "$SELECTOR" returns zero pods, you've found it.

  name: <auto or manual>

  labels:
    kubernetes.io/service-name: <svc>           # REQUIRED — joins slice → svc
    endpointslice.kubernetes.io/managed-by: ...  # identifies the controller/operator
  ownerReferences: [...Service...]            # on controller-managed slices
addressType: IPv4 | IPv6                       # one per slice
ports:                                        # named ports resolved to numeric here
- name: <port name from service>
  port: <resolved containerPort>
  protocol: TCP|UDP|SCTP
  appProtocol: http|http2|grpc|tls|...        # optional hint for mesh sidecars
endpoints:                                    # up to 100 entries (configurable to 1000)
- addresses: [<1 IP for controller-managed>]
  conditions:
    ready: true|false                          # take new connections
    serving: true|false                        # can handle requests (still during graceful term)
    terminating: true|false                    # pod has deletionTimestamp set
  nodeName: <node hosting the pod>             # used by externalTrafficPolicy: Local
  zone: <failure domain>                       # used by topology routing
  hostname: <pod hostname>                     # StatefulSet pods get this
  targetRef: { kind: Pod, name: ..., namespace: ... }
  hints:
    forZones: [{ name: me-central-1a }]         # topology-aware routing
