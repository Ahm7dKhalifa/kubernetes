01 // CORE CONCEPTS

Ingress vs Egress

Every Pod has a cluster-internal IP — ephemeral, invisible to the outside world. Ingress is the controlled gate for traffic coming in. Egress is the controlled gate for traffic going out. Without them: chaos, cost overruns, and zero security posture.

📥

Ingress — Inbound

The Ingress resource is a K8s API object defining HTTP/HTTPS routing rules. The Ingress Controller is the actual running Pod (nginx, traefik, AWS ALB) that enforces them.

  • → Routes external traffic → internal ClusterIP Services
  • → SSL/TLS termination at the edge (cert-manager)
  • → Host-based and path-based routing
  • → Rate limiting, WAF, auth via annotations
  • → One cloud LB for ALL services
  • → Canary / blue-green traffic splitting
📤

Egress — Outbound

K8s default: all Pod-to-Pod and Pod-to-Internet traffic is allowed. Egress NetworkPolicies flip this to default-deny. An Egress Gateway (Istio/Cilium) centralises outbound through one audited exit node.

  • → Controls Pod → external destinations
  • → Default-deny = zero-trust outbound
  • → Whitelist only DB, cache, 3rd-party APIs
  • → Limits blast radius on compromise
  • → PCI-DSS, HIPAA, SOC2 compliance
  • → Static egress IP via NAT gateway

02 // MOTIVATION

Why Do You Need Them?

01

Single LoadBalancer

One Ingress Controller = one cloud LB shared by all services. Without it: one LB per service. 10 services = 10× cost ≈ $750/mo vs $75/mo.

02

Automated TLS

cert-manager + Let's Encrypt auto-issues & renews certs. Backends use plain HTTP internally — simpler, faster, zero manual cert rotation.

03

Path Routing

/api → backend, /web → frontend, /metrics → prometheus — all on one hostname, one IP, zero extra infra.

04

Zero-Trust Egress

Default-deny outbound. Pods reach only whitelisted IPs/ports. Lateral movement eliminated if a pod is compromised.

05

Rate Limiting

Per-IP and per-route limits via annotations. One runaway client can't exhaust your error budget for every other user.

06

Canary Releases

Route 5% of traffic to v2. Monitor. If healthy: raise to 20%, 50%, 100%. Rollback in <30 seconds via one annotation change.

07

Compliance

PCI-DSS, HIPAA, SOC2 require strict network controls. Egress policies prove data never leaves to unauthorised destinations.

08

Observability

Nginx exports Prometheus metrics per route: RPS, P99 latency, 4xx/5xx rates. Feeds directly into Grafana SLO dashboards.

03 // BEFORE — NAIVE CLUSTER — FULL ARCHITECTURE

Before: The Unsecured Cluster

Three worker nodes. App A (API) runs 3 replicas, App B (Frontend) runs 3 replicas. Redis sits on Node 3 unsecured. Every app has its own dedicated cloud LoadBalancer. No TLS. No NetworkPolicy. Any pod can reach any other pod, Redis, or Postgres. This is the starting state most teams inherit.

🔥
Problem state: 3 separate cloud LoadBalancers ($225/mo), NodePort exposed on every node, plain HTTP only, app-b and any other pod can freely connect to Redis and Postgres, no rate limiting, no audit trail, no metrics. A single compromised pod = full database access.
FULL CLUSTER — BEFORE — 3 NODES · app-a ×3 · app-b ×3 · redis · postgres · ALL PROBLEMS VISIBLE
Exposed/Unsecured pods & services
Cost problem (3 cloud LBs)
Unrestricted pod-to-pod traffic

💸 3× LoadBalancer Cost

Three dedicated cloud LBs × $75/month = $225/month just for ingress. Scale to 10 services = $750/month. One Ingress Controller sharing a single LB costs $75/month total.

🔓 Zero TLS

All traffic between users and services is plain HTTP. Passwords, tokens, and PII transmitted in cleartext. MITM attacks are trivial on any public network.

🦠 Unrestricted Lateral Movement

app-b can directly connect to Redis (FLUSHALL) and Postgres (DROP TABLE). One compromised frontend pod = full database access. No audit trail. No block.

📡 NodePort on Every Node

NodePort 31001/31002 are open on the public IP of every node. Even nodes meant for internal workloads become part of the attack surface.

📉 No Metrics

No central RPS, latency, or error rate per service. Incidents are discovered by users, not alerts. MTTR measured in hours, not minutes.

🔑 Secrets in Plain Env Vars

DB_PASSWORD hardcoded in Deployment YAML and stored unencrypted in etcd. Readable by anyone with kubectl access. No rotation possible without redeploying.

04 // AFTER — PRODUCTION CLUSTER — FULL ARCHITECTURE

After: The Secured Cluster

Same three nodes, same apps, same replica counts — but now with an HA Ingress Controller (2 replicas across nodes 1 & 2), TLS via cert-manager, path-based routing, NetworkPolicy default-deny across all namespaces, Calico CNI enforcing eBPF policies, Prometheus scraping every workload, and Postgres/Redis isolated in their own namespace.

✅
Secured state: ONE shared cloud LoadBalancer → 2× nginx-controller (HA). TLS terminates at edge. app-a and app-b are ClusterIP-only (not reachable from internet directly). app-b CANNOT reach Redis or Postgres — NetworkPolicy blocks it. All secrets from K8s Secret resources. All pods have resource limits, readiness probes, and security contexts. Prometheus scrapes /metrics on every pod.
FULL CLUSTER — AFTER — 3 NODES · nginx-controller ×2 · app-a ×3 · app-b ×3 · postgres · redis · NetworkPolicy

app-b (Frontend) — secured pods

✅ One Shared LoadBalancer

Single cloud LB for the entire cluster. $75/month regardless of how many services run behind it. 10x cheaper at 10 services.

✅ Automated TLS

cert-manager provisions and auto-renews Let's Encrypt certs. Alert at 14 days before expiry. Zero manual rotation ever.

✅ Zero-Trust Network

app-b is incapable of reaching Redis or Postgres — NetworkPolicy blocks it at the kernel via Calico eBPF. Compromise contained.

✅ Full Observability

Every pod exposes Prometheus metrics. Nginx exports per-route RPS, P99 latency, error rates. Grafana SLO dashboards populated automatically.

✅ HA Ingress Controller

Two nginx controller pods across two nodes via podAntiAffinity. If Node 1 fails, Node 2's controller handles all traffic — zero intervention.

✅ Production Hygiene

Pinned image tags, resource limits, readiness/liveness probes, security contexts, Secrets references, PodDisruptionBudgets — all set correctly.

8-Step Request Journey (After State)

1

DNS Resolution

Browser resolves api.myapp.com → DNS CNAME → cloud LoadBalancer IP (203.0.113.10). The single shared IP fronting all apps.

2

Cloud LB → Ingress Controller

TCP packet hits cloud LB → health checks route only to healthy nginx-controller pods. Controller-1 (leader) handles normally. If it fails, Controller-2 (standby) takes over — zero intervention required.

3

TLS Termination

Nginx terminates TLS using the cert in Secret myapp-tls-secret (filled automatically by cert-manager). Backend pods receive plain HTTP internally — faster. HSTS header added on response to enforce future HTTPS-only.

4

Annotation Middleware

Rate limit check (100 rps/IP) → connection limit (20 concurrent) → CORS headers → proxy body size guard → security header injection. Any violation returns 429/400 before touching backend pods.

5

Host + Path Rule Matching

Host: api.myapp.com, Path: /api/users → matches rule 1 → forwards to app-a-service ClusterIP (10.96.0.10:80). Path: /api/health → also matches app-a. web.myapp.com/* → app-b-service.

6

kube-proxy IPVS Service LB

IPVS rules select one of 3 healthy app-a pod endpoints (round-robin). Only pods that pass readinessProbe are in the endpoint list. A pod being restarted never receives traffic.

7

Pod Processes — Egress Begins

app-a-pod-2 handles request. It queries Postgres and Redis. Each outbound connection goes through Calico eBPF rules in the kernel — checked against NetworkPolicy before the packet even leaves the pod's network namespace.

8

Response + Prometheus

Response: Pod → kube-proxy → Ingress Controller → Cloud LB → User. Nginx adds X-Content-Type-Options, X-Frame-Options, Referrer-Policy. nginx_ingress_requests_total counter incremented. Latency histogram updated for this route.

08 // SRE PRINCIPLES

SRE Around Ingress & Egress

SREs treat the Ingress Controller as the cluster's primary observability boundary and NetworkPolicies as the primary blast-radius limiter. Both are prerequisites for reliable service ownership.

📊 Golden Signals at Ingress

Ingress Controller exports per-route Prometheus metrics: Latency (P50/P95/P99), Traffic (RPS), Errors (4xx/5xx rate), Saturation (connection queue depth). These feed SLO dashboards without any app-side instrumentation.

OBSERVABILITY

🎯 SLO Enforcement via Rate Limits

"99.9% of requests in <200ms." Rate limiting prevents one client from burning your entire error budget for all users. Set burst = RPS × P99 latency. Return 429 (not 503) — signal to client, not blast to backend.

ERROR BUDGET

🔥 Blast Radius Reduction

If app-b is compromised, NetworkPolicy prevents it from reaching Postgres or Redis. Incident is contained to one service's data. Without egress policies, one compromised frontend pod = full database access.

INCIDENT SCOPE

🔄 Canary + Error Budget

Canary Ingress: 5% traffic to v2. SRE monitors error rate differential. If v2 burns error budget 2× faster than v1, auto-rollback by setting canary weight back to 0. No runbook needed — one annotation edit.

TOIL REDUCTION

🔒 TLS as an SLI

Expired cert = 100% request failure = instant P0. SLI: "cert must not expire." Alert at 30d, 14d, 7d remaining. cert-manager automates renewal but you MUST alert on renewal failures — automation fails silently.

RELIABILITY

⏱️ Structured Logs → MTTR

JSON logs from Nginx: ts, method, host, path, status, latency_ms, upstream, bytes. During incident: query "which upstream caused 502 spike in last 5m?" Cuts MTTR from hours to minutes.

MTTR

⚠️ Silent NetworkPolicy Failures

Misconfigured NetworkPolicy blocks traffic silently — no error, no crash, just timeout. Write CI tests: "can app-a reach 5432? can app-b NOT reach 5432?" Run with netcat/curl in a test pod pre-merge.

TESTING

📈 Capacity Planning

Ingress RPS histograms reveal daily/weekly traffic patterns. HPA scales pods before saturation using CPU threshold. Egress metrics show DB connection pool usage — alert before exhaustion, not after the outage.

CAPACITY

📋 Runbook: Ingress Down

(1) Check controller pod logs. (2) Verify cloud LB health targets. (3) Check TLS secret exists + not expired. (4) kubectl port-forward to bypass Ingress for testing. (5) Check controller CPU/memory limits. (6) Roll back Ingress annotations if recently changed.
