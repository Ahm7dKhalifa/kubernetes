Chapter 00 · Foundations · Deep Dive

What is Ingress?
What is Egress?

The complete mental model. Every Pod in Kubernetes gets a cluster-internal IP that is invisible to the outside world. Ingress controls the gate for traffic coming in. Egress controls the gate for traffic going out. Without them: cost overruns, zero security, and chaos.

📥 Ingress — inbound HTTP/S 📤 Egress — outbound control 🔒 TLS termination 💰 Cost: 1 LB vs N LBs 🛡 Zero-trust networking
KUBERNETES NETWORK FLOW — OVERVIEW
Section A

📥 What is Ingress?

Ingress is how external traffic finds its way into your Kubernetes cluster. Without it, the only option is to give every Service its own cloud LoadBalancer — a separate IP, a separate bill, for each one. Ingress solves this with a single entry point that routes to many backends.

📋

Ingress Resource

A Kubernetes API object (kind: Ingress) that defines routing rules. It is purely declarative — it does nothing by itself. Think of it as a configuration file that the Ingress Controller reads.

rules: - host: www.my-store.com http: paths: - path: /image → image-service - path: /video → video-service
💡The Ingress Resource is just YAML. It only becomes active when an Ingress Controller is running to enforce it.
⚙️

Ingress Controller

The actual running Pod (nginx, Traefik, AWS ALB, GCP GLB) that reads Ingress Resources and enforces the rules. It handles the real network work: TLS termination, request routing, header injection, and metrics collection.

nginx
Most popular · annotations-heavy · battle-tested
Traefik
Auto-config · CRD-based · built-in dashboard
AWS ALB
Native AWS · WAF integration · managed
GCP GLB
Global · CDN-backed · Cloud Armor WAF

What Ingress Gives You

💸

One LoadBalancer

All services share a single cloud LB. 10 services = $75/mo instead of $750/mo. The Ingress Controller multiplexes all traffic from one IP.

🔒

Automated TLS

cert-manager + Let's Encrypt = free SSL certs auto-provisioned and renewed. Backends use plain HTTP internally. Zero manual cert rotation, ever.

🛣️

Path & Host Routing

/image → image-service. /video → video-service. api.domain.com → api-service. One hostname, clean URLs, zero port numbers for users to remember.

⚡

Rate Limiting

Annotation-based: 100 rps/IP, 20 concurrent connections. One runaway client gets 429 — all other users are unaffected. No code change in any backend.

🔄

Canary Releases

Route 5% of traffic to v2. Monitor error rates. Increase to 20%, 50%, 100%. Instant rollback: set canary-weight to 0. One annotation change, zero redeploys.

📊

Observability

nginx exports Prometheus metrics per route: RPS, P99 latency, 4xx/5xx rates. Powers Grafana SLO dashboards automatically — no instrumentation in backends.

Section B

📤 What is Egress?

Kubernetes default: all Pod-to-Pod and Pod-to-Internet traffic is completely unrestricted. Any pod can call any other pod, any database, any external IP. Egress control flips this to default-deny and only allows explicitly whitelisted destinations.

⚠️ Without Egress Control

🔴 image-pod can directly call video's database — no restriction
🔴 Compromised pod can exfiltrate data to any external IP
🔴 Lateral movement: one breach = all services at risk
🔴 No audit trail of what called what — impossible forensics
🔴 Fails PCI-DSS, HIPAA, SOC2 compliance requirements

✅ With Egress Control

🟢 image-pod can ONLY reach image-mysql:3306 + DNS:53
🟢 Compromised pod is contained — blast radius = one service
🟢 Kernel-level enforcement via Calico eBPF — cannot be bypassed
🟢 Dropped packets logged — full audit trail for forensics
🟢 Satisfies PCI-DSS 1.2, HIPAA §164.312, SOC2 CC6.6

The Two Layers of Egress Control

🛡️

Layer 1 — NetworkPolicy

L4 · TCP/UDP ports · pod selectors

A Kubernetes native API object. Defines which pods can talk to which other pods and on which ports. Enforced at the kernel level by the CNI plugin (Calico, Cilium, Weave). Default: allow-all. With a NetworkPolicy applied: default-deny for selected pods.

kind: NetworkPolicy spec: podSelector: matchLabels: { app: image } policyTypes: [Egress] egress: - to: [image-mysql] # ONLY this # all else DROPPED at kernel
✓ Works with Calico, Cilium, Weave — any NetworkPolicy-capable CNI
🌐

Layer 2 — Egress Gateway

L4/L7 · DNS filtering · static IP · audit logs

For outbound-to-internet traffic. A centralized exit node (Istio Egress Gateway, Cilium Egress Gateway, or a NAT proxy) that all pods must route through. Provides a static outbound IP for whitelisting by external services, and a single audit point for all external calls.

→ Pods route outbound via dedicated gateway node
→ Single static IP for all cluster egress (S3, Stripe, etc.)
→ DNS-based filtering — block calls to unapproved hostnames
→ Full request audit log: pod, destination, timestamp, bytes
⚡ Used with Istio, Cilium Enterprise, or dedicated NAT gateway
Section C

🔩 All Components — In Depth

☁️

Cloud LoadBalancer

GCP / AWS / Azure

The single external entry point. It has a public IP and listens on :80 and :443. It forwards all TCP traffic to the nginx-controller pods. There should only ever be ONE — created by the Ingress Controller's Service of type LoadBalancer. This is what DNS points to.

Type: LoadBalancer :80 → :443 redirect Health checks nginx pods $75/month (shared by all)
⎈

Ingress Controller (nginx)

ns: ingress-nginx · 2 replicas HA

The workhorse Pod. Runs nginx inside. Watches the Kubernetes API for Ingress Resource objects. When you kubectl apply an Ingress, the controller auto-generates the nginx.conf and reloads nginx — without downtime. Two replicas with podAntiAffinity ensures they land on different nodes.

What it actually does per request: terminates TLS → checks rate limit → validates CORS → matches host/path rules → rewrites URL → proxies to backend Service → injects security headers → records Prometheus metrics → returns response.

TLS terminate :443 2 replicas · podAntiAffinity Leader election Prometheus :10254/metrics 0-downtime config reload
📋

Ingress Resource

kind: Ingress · networking.k8s.io/v1

The YAML you write. Defines rules: host + path → Service + port. Also holds annotations that configure the Ingress Controller behavior: rate limits, CORS, auth, canary weights. The controller watches for changes and reconfigures in real-time.

spec.rules
host/path → Service routing table
spec.tls
Which Secret holds the TLS cert
metadata.annotations
Rate limit, CORS, canary, auth
IngressClass
Which controller enforces this
🔐

cert-manager

ClusterIssuer · Certificate CRDs

Manages the entire TLS certificate lifecycle. Talks to Let's Encrypt (ACME protocol) to issue free 90-day certs. Automatically renews 15 days before expiry. Stores certs in Kubernetes Secrets. The Ingress Controller reads those Secrets for TLS termination. Zero human intervention after initial setup.

Flow: cert-manager sees Ingress with cert-manager annotation → creates Order → ACME http-01 challenge via nginx → Let's Encrypt validates → issues cert → stores in Secret → nginx reads Secret → TLS active.
🛡️

NetworkPolicy (Calico / Cilium)

L4 · eBPF kernel enforcement

The egress control mechanism. A Kubernetes API object that Calico or Cilium translates into eBPF programs in the Linux kernel. Every packet leaving a pod is checked against these rules before it even leaves the pod's network namespace — at nanosecond speed, completely transparent to the application.

Important: The default Kubernetes CNI (flannel) does NOT enforce NetworkPolicy. You must use Calico, Cilium, Weave Net, or another NetworkPolicy-capable CNI. Flannel ignores NetworkPolicy objects entirely.

Kernel-level enforcement Flannel: does NOT work Calico/Cilium: required default-deny + explicit allow
🔗

ClusterIP Services

type: ClusterIP · NOT LoadBalancer

After Ingress, backend services use type: ClusterIP instead of type: LoadBalancer. A ClusterIP is an internal-only virtual IP — it exists only inside the cluster. External traffic cannot reach it directly. The Ingress Controller is the only path in. This is the key architectural shift: services are not exposed; the Ingress is the single exposed surface.

❌ BEFORE
type: LoadBalancer = $75/mo per service + NodePort on every node
✅ AFTER
type: ClusterIP = $0 + only accessible via Ingress Controller
Section D

⚖️ Ingress vs Egress — Side by Side

Dimension 📥 INGRESS 📤 EGRESS
Direction External → Cluster (inbound) Pod → Outside cluster (outbound)
K8s Resource kind: Ingress (networking.k8s.io/v1) kind: NetworkPolicy (policyTypes: Egress)
Enforced by Ingress Controller Pod (nginx/traefik) CNI Plugin (Calico/Cilium) at kernel level
Protocol support HTTP/HTTPS only (L7) Any TCP/UDP port (L4)
Default behavior All external traffic blocked (no LB exists) All outbound allowed (no policy = open)
TLS Terminates at Ingress Controller Not applicable (not a proxy)
Rate limiting Yes — per-IP, per-route annotations No — binary allow/deny only
Bypass possible? Yes — if NodePort also exists No — kernel enforcement cannot be bypassed
Observability Full Prometheus metrics per route Calico: dropped packet counters only
Compliance TLS = PCI-DSS 4.2, SOC2 CC6.7 Isolation = PCI-DSS 1.2, HIPAA §164.312

kind: Ingress

  name: store-ingress
  namespace: production
  annotations:

Canary Deploy — Safe Rollout

# ── Start canary: 5% traffic to video v2.0.0 ────────────────────
kubectl apply -f - <<EOF
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: video-canary
  namespace: production
  annotations:
    kubernetes.io/ingress.class: "nginx"
    nginx.ingress.kubernetes.io/canary: "true"
    nginx.ingress.kubernetes.io/canary-weight: "5"
spec:
  rules:
  - host: www.my-online-store.com
    http:
      paths:
      - path: /video(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: video-service-v2
            port: { number: 80 }
EOF

# Verify canary Ingress created
kubectl get ingress -n production
# Should see: video-stable + video-canary
# ── Monitor canary error rate (watch for 5-10 min) ───────────────
# Using kubectl + metrics-server:
kubectl top pods -n production -l version=v2.0.0

# ── Increase weight gradually ────────────────────────────────────
# 5% → 20%
kubectl annotate ingress video-canary -n production --overwrite \
  nginx.ingress.kubernetes.io/canary-weight="20"

# 20% → 50%
kubectl annotate ingress video-canary -n production --overwrite \
  nginx.ingress.kubernetes.io/canary-weight="50"

# 50% → 100% (full release)
kubectl annotate ingress video-canary -n production --overwrite \
  nginx.ingress.kubernetes.io/canary-weight="100"

# ── Full promotion: update stable + remove canary ────────────────
kubectl set image deployment/video-deployment video=myapp/video:v2.0.0 -n production
kubectl rollout status deployment/video-deployment -n production
kubectl delete ingress video-canary -n production
# ── Instant rollback: set canary weight to 0 ────────────────────
kubectl annotate ingress video-canary -n production --overwrite \
  nginx.ingress.kubernetes.io/canary-weight="0"
# 100% traffic now goes to stable v1.5.0 — zero downtime

# ── Or delete canary entirely ────────────────────────────────────
kubectl delete ingress video-canary -n production

# ── Everyday kubectl commands ────────────────────────────────────

kubectl get events -n production --sort-by='.lastTimestamp'

kubectl describe pod -n production -l app=image

# Stream logs from all image pods
kubectl logs -n production -l app=image --all-containers -f --tail=100

# Force delete a stuck pod

kubectl uncordon worker-node-1  # re-enable after maintenance
