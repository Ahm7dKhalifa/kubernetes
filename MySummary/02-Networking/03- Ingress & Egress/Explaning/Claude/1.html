01 // DEFINITIONS

What Are They, Exactly?

In Kubernetes, every Pod gets an IP address — but those IPs are ephemeral, cluster-internal, and not directly routable from the outside world. Ingress and Egress are the two gatekeeping concepts that control how traffic flows in and out of your cluster, services, and pods.

📥

Ingress

Ingress manages inbound traffic from outside the cluster to Services inside it. It provides HTTP/HTTPS routing, SSL termination, virtual hosting, and path-based routing — all via a single LoadBalancer IP. Think of it as the smart front door of your cluster.

Kubernetes defines two objects:

  • Ingress Resource — a declarative YAML config defining routing rules (host, path → service)
  • Ingress Controller — an actual running Pod (nginx, traefik, HAProxy, etc.) that reads the Ingress Resource and enforces the rules
  • SSL/TLS termination at the cluster edge
  • Name-based and path-based virtual hosting
  • Rate limiting, auth, IP whitelisting via annotations
  • WebSocket and gRPC support
  • Load balancing algorithms (round-robin, sticky sessions)
📤

Egress

Egress controls outbound traffic from Pods in the cluster to external destinations — databases, third-party APIs, the internet, or other clusters. Without egress controls, any Pod can phone home anywhere. Egress policies enforce zero-trust outbound behavior.

Kubernetes controls egress via:

  • NetworkPolicy — L4 rules (IP/port) that permit or deny egress flows per Pod selector
  • Egress Gateway (Istio/Cilium) — routes all outbound through a single audited exit node
  • DNS-based egress filtering (by hostname, not just IP)
  • Force all outbound through a NAT gateway for static IPs
  • Block internet access for compliance-sensitive workloads
  • Mutual TLS (mTLS) for outbound service-to-service calls

02 // WHY & BENEFITS

Why Do You Need Them?

Before Ingress existed, exposing services required one LoadBalancer per service — that's expensive (each cloud LB costs money) and operationally painful. NetworkPolicies came later to fix the naive "allow all" default networking model.

01

Cost Efficiency

One Ingress Controller = one cloud LoadBalancer for all services. Without it, you'd pay for an LB per service — 10 services = 10 LBs = 10× the cost.

02

SSL Termination

Handle TLS certificates once at the Ingress layer via cert-manager + Let's Encrypt. Your backend services communicate over plain HTTP internally — simpler, faster.

03

Path-Based Routing

Route /api/* → backend service, /web/* → frontend service, /metrics/* → monitoring — all on the same IP and hostname.

04

Security Layer

Ingress annotations enable rate limiting, IP whitelisting, OAuth2 proxy, WAF integration, and basic auth without touching application code.

05

Zero-Trust Egress

NetworkPolicies default-deny all outbound. Pods can only talk to explicitly whitelisted destinations — databases, queues, APIs. Lateral movement is eliminated.

06

Compliance Ready

PCI-DSS, HIPAA, SOC2 require strict network controls. Egress policies enforce data residency and prevent exfiltration to unauthorized IPs.

07

Observability

Ingress Controllers expose Prometheus metrics: request rate, latency P50/P99, error rate, upstream response time — per route, per service.

08

Canary & A/B Testing

Nginx Ingress supports canary annotations: route 10% of traffic to the new service version, 90% to stable — zero infrastructure changes needed.

03 // YAML CONFIGURATIONS

Production YAML Configs

Full, annotated YAML for every object you'll need in a production cluster.

# ────────────────────────────────────────────
# INGRESS RESOURCE — routes external HTTP/S traffic
# to internal Services based on host + path rules
# ────────────────────────────────────────────
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: production-ingress
  namespace: production
  annotations:
    # Use nginx ingress controller
    kubernetes.io/ingress.class: "nginx"
    # Force HTTPS redirect
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    # Rate limit: 100 req/min per IP
    nginx.ingress.kubernetes.io/limit-rps: "100"
    # Enable CORS
    nginx.ingress.kubernetes.io/enable-cors: "true"
    # Enable proxy buffering for performance
    nginx.ingress.kubernetes.io/proxy-buffering: "on"
    # Increase body size for file uploads
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    # Timeout configuration
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"

spec:
  # TLS configuration — terminates SSL here
  tls:
  - hosts:
    - api.myapp.com
    - web.myapp.com
    secretName: myapp-tls-secret   # cert stored here

  rules:
  # Rule 1: API service on subdomain
  - host: api.myapp.com
    http:
      paths:
      - path: /v1
        pathType: Prefix
        backend:
          service:
            name: api-service-v1
            port:
              number: 80
      - path: /v2
        pathType: Prefix
        backend:
          service:
            name: api-service-v2
            port:
              number: 80

  # Rule 2: Frontend service on main domain
  - host: web.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 3000
# ────────────────────────────────────────────
# NGINX INGRESS CONTROLLER DEPLOYMENT
# This is what actually processes the Ingress rules
# Runs as a Deployment in the cluster
# ────────────────────────────────────────────
apiVersion: v1
kind: Namespace
metadata:
  name: ingress-nginx

---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-ingress-controller
  namespace: ingress-nginx
spec:
  replicas: 2       # HA — 2 controller replicas
  selector:
    matchLabels:
      app: ingress-nginx
  template:
    metadata:
      labels:
        app: ingress-nginx
    spec:
      serviceAccountName: nginx-ingress-serviceaccount
      containers:
      - name: nginx-ingress-controller
        image: registry.k8s.io/ingress-nginx/controller:v1.9.4
        args:
        - /nginx-ingress-controller
        - --publish-service=ingress-nginx/ingress-nginx-svc
        - --election-id=ingress-controller-leader
        - --ingress-class=nginx
        - --configmap=ingress-nginx/nginx-configuration
        ports:
        - name: http
          containerPort: 80
        - name: https
          containerPort: 443
        resources:
          requests:
            cpu: "100m"
            memory: "90Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
        livenessProbe:
          httpGet:
            path: /healthz
            port: 10254
          initialDelaySeconds: 10
          periodSeconds: 10
        readinessProbe:
          httpGet:
            path: /healthz

# LoadBalancer Service — this gets the external IP
apiVersion: v1
kind: Service
metadata:
  name: ingress-nginx-svc
  namespace: ingress-nginx
spec:
  type: LoadBalancer
  selector:
    app: ingress-nginx
  ports:
  - name: http
    port: 80
    targetPort: 80
  - name: https
    port: 443
    targetPort: 443
# ────────────────────────────────────────────
# EGRESS NetworkPolicy — controls outbound traffic
# Strategy: default-deny all, then allow explicitly
# ────────────────────────────────────────────

# Step 1: Default DENY ALL egress for the namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: production
spec:
  podSelector: {}    # applies to ALL pods in namespace
  policyTypes:
  - Egress
  # No egress rules = deny everything by default

---
# Step 2: Allow specific egress for the API pods
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: api-egress-policy
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api-service    # only applies to api pods
  policyTypes:
  - Egress
  egress:
  # Allow DNS (required for name resolution)
  - ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53

  # Allow talk to the database (in db namespace)
  - to:
    - namespaceSelector:
        matchLabels:
          name: database
      podSelector:
        matchLabels:
          app: postgres
    ports:
    - protocol: TCP
      port: 5432

  # Allow talk to Redis cache (same namespace)
  - to:
    - podSelector:
        matchLabels:
          app: redis
    ports:
    - protocol: TCP
      port: 6379

  # Allow external HTTPS to payment gateway only
  - to:
    - ipBlock:
        cidr: 203.0.113.0/24    # payment gateway IP range
    ports:
    - protocol: TCP
      port: 443
# ────────────────────────────────────────────
# INGRESS NetworkPolicy — controls who can REACH
# your pods from inside the cluster
# ────────────────────────────────────────────

# Default deny all ingress to production namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
  namespace: production
spec:
  podSelector: {}
  policyTypes:
  - Ingress

---
# Allow ingress only from nginx controller to api-service
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-ingress-controller
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api-service
  policyTypes:
  - Ingress
  ingress:
  # Only nginx ingress controller pods can reach this service
  - from:
    - namespaceSelector:
        matchLabels:
          name: ingress-nginx
      podSelector:
        matchLabels:
          app: ingress-nginx
    ports:
    - protocol: TCP
      port: 8080

---
# Allow prometheus to scrape metrics from all pods
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-prometheus-scrape
  namespace: production
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          name: monitoring
    ports:
    - protocol: TCP
      port: 9090
# ────────────────────────────────────────────
# AUTOMATED TLS WITH CERT-MANAGER
# Auto-renewing Let's Encrypt certificates
# ────────────────────────────────────────────

# 1. ClusterIssuer — defines how to get certs
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: letsencrypt-prod
spec:
  acme:
    server: https://acme-v02.api.letsencrypt.org/directory
    email: ops@myapp.com
    privateKeySecretRef:
      name: letsencrypt-prod-key
    solvers:
    - http01:
        ingress:
          class: nginx

---
# 2. Certificate — requests the actual cert
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: myapp-tls
  namespace: production
spec:
  secretName: myapp-tls-secret    # matches Ingress tls.secretName
  duration: 2160h                  # 90 days
  renewBefore: 360h                # renew 15 days before expiry
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  dnsNames:
  - api.myapp.com
  - web.myapp.com
  - *.myapp.com                   # wildcard cert

---
# 3. Ingress now just references the secret
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: secure-ingress
  namespace: production
  annotations:
    cert-manager.io/cluster-issuer: "letsencrypt-prod"
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  tls:
  - hosts: [api.myapp.com, web.myapp.com]
    secretName: myapp-tls-secret   # cert-manager fills this
  rules:
  - host: api.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-service
            port: { number: 80 }

# CANARY INGRESS — Route % of traffic to new version
# Useful for A/B testing and gradual rollouts
# ────────────────────────────────────────────

# Main (stable) Ingress
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress-stable
  namespace: production
spec:
  rules:
  - host: api.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-v1-service    # stable version
            port: { number: 80 }

---
# Canary Ingress — 20% of traffic to v2
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: api-ingress-canary
  namespace: production
  annotations:
    # Mark this as a canary ingress
    nginx.ingress.kubernetes.io/canary: "true"
    # Send 20% of requests here
    nginx.ingress.kubernetes.io/canary-weight: "20"
    # OR: route users with header "X-Canary: true"
    nginx.ingress.kubernetes.io/canary-by-header: "X-Canary"
    nginx.ingress.kubernetes.io/canary-by-header-value: "true"
    # OR: route users based on cookie
    nginx.ingress.kubernetes.io/canary-by-cookie: "canary"
spec:
  rules:
  - host: api.myapp.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: api-v2-service    # new version — gets 20%
            port: { number: 80 }

Ingress Request Journey (Step-by-Step)

1

DNS Resolution

User's browser resolves api.myapp.com → DNS CNAME points to the cloud LoadBalancer's external IP (the one assigned to the Ingress Controller Service).

2

Cloud LoadBalancer → Ingress Controller Pod

TCP packet arrives at cloud LB → forwarded to one of the Ingress Controller pods on port 80/443. The LB performs health checks and only routes to healthy controller pods.

3

TLS Termination

Nginx terminates the TLS connection using the cert stored in the Secret (from cert-manager). The connection to backend pods is plain HTTP — simpler and faster internally.

4

Rule Matching (Host + Path)

Nginx evaluates the Host header and URL path against Ingress rules. api.myapp.com/v1/* matches rule 1 → routes to api-service-v1. Most-specific path wins.

5

Middleware Execution

Annotations are applied in order: rate limit check → IP allowlist → auth header validation → request body size check → add X-Real-IP header. Any failure returns 4xx immediately.

6

kube-proxy + Service Load Balancing

Nginx proxies to the ClusterIP of api-service-v1. kube-proxy (iptables/IPVS rules) then selects one of the 3 healthy Endpoints (pod IPs) using round-robin or least-connections.

7

Pod Processes Request + Egress

The selected Pod receives the request, processes it, and may need to make egress calls (DB, cache, external APIs). These are checked against NetworkPolicy egress rules before leaving the pod.

8

Response Flows Back

Response travels: Pod → kube-proxy → Ingress Controller → Cloud LB → User. Nginx adds response headers (CORS, HSTS, X-Content-Type-Options) on the way out.

06 // SRE PRINCIPLES

SRE Principles Around Ingress & Egress

Site Reliability Engineering views Ingress and Egress not just as networking primitives — they are key reliability, observability, and security control planes. Here's how an SRE thinks about them.

📊 Golden Signals at the Ingress

The Ingress Controller is the perfect place to measure all four SRE Golden Signals: Latency (P50/P95/P99 per route), Traffic (RPS per upstream), Errors (4xx/5xx rate per service), Saturation (connection queue depth). These feed directly into SLO dashboards.

OBSERVABILITY

🎯 SLO Enforcement via Rate Limiting

Define an SLO: "99.9% of requests complete in <200ms." Ingress rate limiting prevents runaway clients from consuming all capacity and degrading SLOs for others. Set burst limits = (RPS × P99_latency). Excess requests get 429 Too Many Requests — graceful degradation, not outage.

SLO / ERROR BUDGET

🔥 Blast Radius Reduction

NetworkPolicy egress rules limit the blast radius of a compromised Pod. If App B is pwned, it cannot reach PostgreSQL (egress blocked). This contains the incident to one service. Without egress policies, a single compromised Pod could exfiltrate your entire database.

INCIDENT RESPONSE

🔄 Canary Deployments & Toil Reduction

Using Ingress canary annotations, deployments shift from "big-bang" to gradual: 1% → 5% → 20% → 100%. SREs monitor error rate and latency at each stage. If the canary degrades, rollback is instant — change one annotation. This eliminates deployment toil and reduces MTTR.

TOIL REDUCTION

🛡️ Defense in Depth

Layered security: Cloud firewall → Ingress IP allowlist → NetworkPolicy ingress → mTLS (Istio) → application auth. No single layer is the whole defense. Egress NetworkPolicies are the last line against data exfiltration even if the app layer is compromised. Zero-trust by default.

SECURITY

⏱️ MTTR via Structured Logging

Configure Ingress to emit structured JSON logs: {"ts","method","host","path","status","latency_ms","upstream","bytes"}. These flow into ELK/Loki. During incidents, you can instantly correlate "which upstream service caused this 502 spike?" — cutting Mean Time To Resolve significantly.

MTTR REDUCTION

🚨 Circuit Breaking at Egress

When App A calls PostgreSQL, an Egress Gateway (Istio) can detect that DB latency spiked above 1s and circuit-break further calls — returning cached data or errors immediately instead of piling up threads. This prevents cascading failures from propagating upstream to users.

RESILIENCE

📈 Capacity Planning

Ingress metrics reveal true traffic patterns: daily peaks, weekly cycles, burst patterns. SREs use this to right-size the cluster (HPA triggers, node autoscaling). Egress metrics reveal database connection counts — if connections near the pool max, scale before the outage, not after.

CAPACITY

🔒 Certificate Expiry as an SLI

An expired TLS cert causes 100% of user requests to fail — it's a P0 incident. SREs create an SLI: "TLS certificate must never expire." Alert at 30 days, 14 days, 7 days remaining. cert-manager automates renewal but the alert catches failures in the renewal process itself.

RELIABILITY

🌍 Multi-Region Egress Consistency

In multi-region clusters, egress policies must be consistent across regions. A policy that allows DB access in us-east but not eu-west causes asymmetric failures hard to debug. Use GitOps (ArgoCD/Flux) to ensure NetworkPolicy YAMLs are identical across regions — policy drift is an SRE failure mode.

CONSISTENCY

⚠️ NetworkPolicy Testing in CI

NetworkPolicies are silent — a misconfiguration doesn't crash a pod, it just blocks traffic. SREs write integration tests: "After deploy, can App A reach port 5432? Can App B NOT reach port 5432?" Run with tools like netcat, curl, or network-policy-conformance in CI pipelines.

TESTING

📋 Runbook: Ingress Down

SREs pre-write runbooks: (1) Check controller pod logs. (2) Check cloud LB health. (3) Verify TLS secret exists. (4) Check Ingress resource for syntax errors. (5) Test with kubectl port-forward to bypass Ingress. (6) Check resource limits on controller pods. Runbooks = faster MTTR.

💡
SRE Golden Rule: Every Ingress route should have a corresponding SLO. Every NetworkPolicy egress rule should have a corresponding test in CI. If you can't measure it and test it, you don't own it — you're just hoping it works.
⚠️
Common SRE Trap: NetworkPolicies silently drop packets — there's no error, no crash, just a timeout. Always validate policies with kubectl exec pod -- nc -zv target-ip 5432 and alert on unexpected packet drops from your CNI (Cilium/Calico metrics).
ℹ️
Gateway API (future of Ingress): The Kubernetes community is moving from the Ingress resource to the Gateway API (GatewayClass, Gateway, HTTPRoute, TCPRoute). It's more expressive, multi-tenancy-safe, and supports all protocols. Start evaluating it for greenfield clusters today.
