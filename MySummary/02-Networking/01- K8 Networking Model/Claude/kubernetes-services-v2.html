01 The Problem — Why Do We Need Services? ▶

The Problem
3 Reasons
What Service Solves
Pods are ephemeral — IPs change constantly
T=0 — Everything works:
web-pod-1 → 10.244.1.5:80 ← App connects here

T=1 — Pod crashes, new Pod created:
web-pod-1 → 10.244.1.5 DEAD ✗
web-pod-2 → 10.244.2.9:80 ← NEW IP!

T=2 — App breaks:
App still tries 10.244.1.5 → Connection refused!

The app hardcoded the Pod IP. Pod died. New Pod got a different IP. App is broken.
3 Problems Pods Have Without Services
Problem 1 — Unstable IPsPod IPs are assigned by the CNI when the Pod is created. When a Pod dies and is recreated (even with the same name in a StatefulSet), it MAY get a different IP. You cannot rely on Pod IPs.
Problem 2 — No Load BalancingIf you have 3 replicas of your web app, how does a client know about all 3 IPs? And how does it balance traffic across them? Pods don't provide this — you'd have to implement it yourself.
Problem 3 — No Stable DNSPods don't get DNS names by default (only StatefulSet Pods with headless Services do). Without DNS, you're stuck hardcoding IPs — which change.
What a Service Provides
Service: web-svcClusterIP: 10.96.0.15 (NEVER changes)DNS: web-svc.default.svc.cluster.local
↓ load-balance (round-robin) ↓
Pod-1 (10.244.1.5) Pod-2 (10.244.2.9) Pod-3 (10.244.3.2)
① Stable IP — ClusterIP 10.96.0.15 never changes, even if all Pods behind it die and are replaced.
② Stable DNS — web-svc always resolves to the ClusterIP. Apps use DNS, not IPs.
③ Load Balancing — Traffic is distributed across all healthy Pods automatically.
④ Auto-Discovery — When Pods are added/removed, the Service's endpoint list updates automatically. No manual registration.

Pod IP (Internal, Ephemeral)
DefinitionA unique IP address assigned to each Pod by the CNI plugin when the Pod is created. It comes from the Pod CIDR range (e.g., 10.244.0.0/16). This IP is internal to the cluster — not reachable from outside. It is ephemeral — changes when the Pod is recreated.
Node 1 (Pod CIDR: 10.244.1.0/24)
├── Pod A → 10.244.1.5
├── Pod B → 10.244.1.6

Node 2 (Pod CIDR: 10.244.2.0/24)
├── Pod C → 10.244.2.3
├── Pod D → 10.244.2.4
Each node gets its own Pod CIDR subnet. Pods on Node 1 get 10.244.1.x, Pods on Node 2 get 10.244.2.x. This is why two Pods on different nodes will NEVER have the same IP — they're on different subnets.
Node IP (Internal or External)
DefinitionThe IP address of the actual machine (VM/bare-metal) that the node runs on. Nodes have TWO IPs:
InternalIP: Private network IP (e.g., 192.168.1.10). Used for node-to-node communication within the cluster.
ExternalIP: Public IP (e.g., 35.192.0.5). Only in cloud environments. Used by NodePort and LoadBalancer Services to receive external traffic.
kubectl get nodes -o wide
# NAME    INTERNAL-IP     EXTERNAL-IP    OS-IMAGE
# node1   192.168.1.10    35.192.0.5     Ubuntu 22.04
# node2   192.168.1.11    35.192.0.6     Ubuntu 22.04
ClusterIP (Virtual, Stable)
DefinitionA virtual IP assigned to a Service by Kubernetes (from the Service CIDR, e.g., 10.96.0.0/12). It is NOT tied to any network interface — it exists only in iptables/IPVS rules managed by kube-proxy. It is stable (never changes for the lifetime of the Service) and internal-only (not reachable from outside the cluster).
Service: web-svcClusterIP: 10.96.0.15 ← virtual, stable, internal

This IP doesn't exist on any NIC. It's programmed into iptables rules on every node. When a Pod sends a packet to 10.96.0.15, kube-proxy's iptables rules intercept it and redirect to a real Pod IP.
External IP (Public, Routable)
DefinitionA public IP address reachable from the internet. There are 3 ways to get one:
① NodePort: Uses the node's ExternalIP + a high port (30000-32767). Not a dedicated IP.
② LoadBalancer: Cloud provider creates a dedicated public IP (e.g., AWS ELB gives you 35.192.0.1).
③ Ingress: The Ingress Controller's LoadBalancer gets a public IP. All Ingress rules share it.
DNS (Domain Name System in K8s)
DefinitionCoreDNS runs as a Deployment inside the cluster (in kube-system namespace). It automatically creates DNS records for every Service. Pods are configured to use CoreDNS as their DNS server (via /etc/resolv.conf).
CoreDNS (kube-system)

Creates DNS records automatically:
web-svc.default.svc.cluster.local → 10.96.0.15 (ClusterIP)
db-svc.production.svc.cluster.local → 10.96.1.42

Short forms within same namespace:
web-svc → 10.96.0.15
web-svc.default → 10.96.0.15

03 Can Two Pods on Different Nodes Have the Same IP? ▶

Answer: NO
Why — Pod CIDR
How it's enforced
Answer: NO — Pod IPs are globally unique in the cluster
Node 1 → Pod CIDR: 10.244.1.0/24 (256 IPs)
├── Pod A: 10.244.1.5
├── Pod B: 10.244.1.6

Node 2 → Pod CIDR: 10.244.2.0/24 (256 IPs)
├── Pod C: 10.244.2.3 ← different subnet!
├── Pod D: 10.244.2.4

10.244.1.x ≠ 10.244.2.x → no overlap possible
Why — Each Node Gets a Unique Pod CIDR Subnet
When a node joins the cluster, the controller-manager assigns it a unique Pod CIDR range from the cluster's Pod network (e.g., --cluster-cidr=10.244.0.0/16). Each node gets a /24 subnet (256 IPs):

Node 1 → 10.244.1.0/24
Node 2 → 10.244.2.0/24
Node 3 → 10.244.3.0/24

Since subnets don't overlap, Pod IPs can never collide — even across nodes.
How it's enforced
① kube-controller-manager allocates a unique /24 per node via --cluster-cidr and --node-cidr-mask-size.
② CNI plugin (Calico, Flannel, Cilium) assigns Pod IPs from the node's allocated subnet. It tracks used IPs to avoid duplicates within the node.
③ CNI plugin also sets up routes so that packets destined for 10.244.2.x are routed to Node 2 (via VXLAN tunnel or BGP route).

This is the "flat network" model: any Pod IP is routable from any node, and no two Pods ever share an IP.

04 Service Internals — How a Service Actually Works ▶

Components
Selector → Endpoints
iptables rules
3 Components That Make Services Work
① API ServerStores the Service object (name, ClusterIP, selector, ports). Assigns the ClusterIP from the Service CIDR range.
② Endpoint ControllerWatches Pods matching the Service's selector. Maintains an Endpoints object listing all healthy Pod IPs. Updates automatically when Pods are added/removed/fail readiness.
③ kube-proxyRuns on EVERY node as a DaemonSet. Watches Services and Endpoints. Programs iptables rules (or IPVS rules) on each node to intercept traffic to the ClusterIP and redirect it to a real Pod IP.
Selector → Endpoints — How the Service finds Pods
Service: web-svcselector: app=web
↓ endpoint controller watches Pods with app=web ↓
Endpoints: web-svc10.244.1.5:80, 10.244.2.3:80, 10.244.3.7:80

Pod added (app=web) → IP added to Endpoints
Pod deleted → IP removed from Endpoints
Pod fails readiness → IP removed from Endpoints
iptables — How kube-proxy redirects traffic
On every node, kube-proxy creates iptables rules:

If destination = 10.96.0.15:80 (ClusterIP)
→ DNAT to one of:
  33% → 10.244.1.5:80 (Pod 1)
  33% → 10.244.2.3:80 (Pod 2)
  33% → 10.244.3.7:80 (Pod 3)

This is random probability-based load balancing. The ClusterIP is virtual — no network interface has this IP. iptables intercepts the packet before it goes to the wire and rewrites the destination to a real Pod IP.

05 kube-proxy Modes ▶

iptables (default)
IPVS
Comparison
iptables mode (default)
Howkube-proxy programs iptables NAT rules on every node. Packets to ClusterIP are intercepted by iptables and DNAT'd to a random backend Pod IP. Probability-based load balancing (random selection).
Pros: Simple, reliable, default. Cons: O(n) rule evaluation — slow with thousands of Services. Random selection, no least-connection or round-robin.
IPVS mode (advanced)
Howkube-proxy programs IPVS (IP Virtual Server) rules instead of iptables. IPVS is a kernel-level L4 load balancer. Uses hash tables — O(1) lookup. Supports real algorithms: round-robin, least-connection, source-hash.
Pros: Much faster with 1000s of Services. Real LB algorithms. Cons: Requires IPVS kernel modules. Slightly more complex.
iptables (default)IPVS
PerformanceO(n) — degrades with many ServicesO(1) — scales well
LB algorithmRandom probabilityRound-robin, least-conn, source-hash
SetupDefault, no extra configNeeds kernel modules
Use when< 1000 Services> 1000 Services

06 Full Service Lifecycle — Create to Handle Traffic ▶

① Create
② ClusterIP assigned
③ Endpoints built
④ kube-proxy programs
⑤ DNS registered
⑥ Traffic flows
⑦ Pod changes
① You create the Service
kubectl expose deployment web --port=80 --target-port=80 --name=web-svc
The kubectl command sends a Service object to the API server. Fields: name=web-svc, type=ClusterIP, selector={app: web}, port=80, targetPort=80.
② API Server assigns a ClusterIP
Service: web-svcClusterIP: 10.96.0.15 ← assigned from --service-cluster-ip-rangeselector: app=webport: 80 → targetPort: 80
The API server picks an unused IP from the Service CIDR range (e.g., 10.96.0.0/12) and assigns it. This IP is now reserved and will never change for the lifetime of this Service.
③ Endpoint controller builds Endpoints
Service: web-svc (selector: app=web)
↓ endpoint controller scans Pods ↓
Pods with app=web AND passing readiness:
web-abc (10.244.1.5) ✓ web-def (10.244.2.3) ✓ web-ghi (10.244.3.7) ✓

Endpoints: web-svc → [10.244.1.5:80, 10.244.2.3:80, 10.244.3.7:80]
④ kube-proxy programs iptables on EVERY node
kube-proxy (on every node) watches the API server for Service + Endpoint changes.

Node 1: iptables rules updated
Node 2: iptables rules updated
Node 3: iptables rules updated

Rule: 10.96.0.15:80 → DNAT → 10.244.1.5:80 | 10.244.2.3:80 | 10.244.3.7:80

Now ANY Pod on ANY node can reach 10.96.0.15:80 and traffic will be routed to one of the backend Pods.
⑤ CoreDNS registers DNS record
CoreDNS adds A record:
web-svc.default.svc.cluster.local → 10.96.0.15

Pods can now use: curl web-svc:80 ← DNS resolves to ClusterIP
⑥ Traffic flows — end to end
App Pod (any node)
↓ curl web-svc:80
CoreDNS: web-svc → 10.96.0.15
↓ packet to 10.96.0.15:80
kube-proxy iptables: DNAT → 10.244.2.3:80
↓ packet redirected to real Pod IP
web-def (10.244.2.3:80) receives request
↓ response sent back via same path
App Pod receives response ✓
⑦ When Pods change — auto-update
Pod crashes:
web-def (10.244.2.3) dies
→ Endpoint controller removes 10.244.2.3 from Endpoints
→ kube-proxy updates iptables: now only 2 backends

New Pod created:
web-xyz (10.244.2.9) passes readiness
→ Endpoint controller adds 10.244.2.9 to Endpoints
→ kube-proxy updates iptables: 3 backends again

All automatic. ClusterIP and DNS never change. Only the backend Pod IPs update.

07 Case: Service with Pods on the SAME Node ▶

Diagram
Traffic path
Node 1 (192.168.1.10)
├── kube-proxy (iptables rules)
├── App Pod (10.244.1.2) ← sends request
├── Web Pod A (10.244.1.5) ← backend
├── Web Pod B (10.244.1.6) ← backend
└── Web Pod C (10.244.1.7) ← backend

Service: web-svc (ClusterIP: 10.96.0.15)
Endpoints: 10.244.1.5, 10.244.1.6, 10.244.1.7
Traffic never leaves the node
App Pod → curl web-svc:80
↓ DNS → 10.96.0.15
↓ iptables on THIS node → DNAT to 10.244.1.6
↓ packet goes to Web Pod B on the SAME node
↓ No network hop. Stays local. Fastest path.
When all Pods are on the same node, traffic stays within the node's network stack. iptables intercepts and redirects — the packet never crosses the physical network. This is the fastest scenario.

Diagram
Local Pod selected
Remote Pod selected
Node 1 (192.168.1.10)
├── kube-proxy (iptables)
├── App Pod (10.244.1.2) ← sends request
└── Web Pod A (10.244.1.5) ← backend on Node 1

Node 2 (192.168.1.11)
├── kube-proxy (iptables)
└── Web Pod B (10.244.2.3) ← backend on Node 2

Node 3 (192.168.1.12)
├── kube-proxy (iptables)
└── Web Pod C (10.244.3.7) ← backend on Node 3

Service: web-svc (ClusterIP: 10.96.0.15)
Endpoints: 10.244.1.5, 10.244.2.3, 10.244.3.7
iptables selects a LOCAL Pod (lucky case)
App Pod (Node 1) → curl web-svc:80
↓ iptables randomly picks 10.244.1.5 (Pod A on Node 1)
↓ Traffic stays on Node 1. No network hop.
iptables selects a REMOTE Pod (cross-node)
App Pod (Node 1) → curl web-svc:80
↓ iptables randomly picks 10.244.2.3 (Pod B on Node 2)
↓ DNAT: dst = 10.244.2.3
↓ CNI routes packet Node 1 → Node 2 (via VXLAN/BGP)
↓ Web Pod B (Node 2) receives request
↓ Response: Node 2 → Node 1 → App Pod

Cross-node. Extra network hop. Slightly slower but still fast (microseconds).
externalTrafficPolicy: Local

For NodePort/LoadBalancer Services, you can set externalTrafficPolicy: Local to force traffic to only go to Pods on the same node the request arrived on. Avoids extra hops but may cause uneven load distribution.

12 Headless Service (clusterIP: None) ▶

vs Normal
YAML
Use case
Normal ClusterIP Service:
nslookup web-svc → 10.96.0.15 (one virtual IP, load balanced by kube-proxy)

Headless Service (clusterIP: None):
nslookup web-svc → 10.244.1.5, 10.244.2.3, 10.244.3.7 (ALL Pod IPs returned!)
nslookup web-0.web-svc → 10.244.1.5 (specific Pod by name!)
No virtual IP. No kube-proxy rules. DNS returns Pod IPs directly. The CLIENT decides which Pod to connect to. Used for StatefulSets where apps need to target specific Pods.
spec:
  clusterIP: None     # ← headless
  selector:
    app: web
Use for: StatefulSets (MySQL, Kafka, MongoDB), peer-to-peer discovery (Pods need to know ALL other Pod IPs), applications that do their own load balancing (gRPC clients with client-side LB).

13 ExternalName Service

DefinitionMaps a Service name to an external DNS name (CNAME record). No proxy, no ClusterIP, no selector. Just a DNS alias. Pods call the Service name and get redirected to the external hostname.
spec:
  type: ExternalName
  externalName: db.example.com
App Pod → curl external-db:3306 → DNS CNAME → db.example.com

Use when your database or API is outside Kubernetes. App code uses the K8s Service name. If you later migrate the DB into K8s, just change the Service type — app code doesn't change.

Definition

Full YAML
Port FieldWhereWhat It Means
containerPortPod specPort the app LISTENS on inside the container. Informational (doesn't enforce). Example: nginx listens on 80.
targetPortService specPort on the Pod the Service FORWARDS traffic TO. Must match what the container actually listens on. Usually = containerPort.
portService specPort the Service EXPOSES on the ClusterIP. Can be different from targetPort. Example: Service:8080 → Pod:80.
nodePortService specPort opened on EVERY node's IP. Range 30000-32767. Only for NodePort/LoadBalancer. External access point.
ClusterIP traffic:
App Pod → web-svc:port(80) → kube-proxy → Pod:targetPort(80)
NodePort traffic:
User → NodeIP:nodePort(30080) → ClusterIP:port(80) → Pod:targetPort(80) 
# Pod
containers:
- ports:
  - containerPort: 80     # App listens here

# Service (NodePort)
ports:
- port: 80              # ClusterIP port
  targetPort: 80        # → Pod port (must match containerPort)
  nodePort: 30080       # External port on every node
Defaults

targetPort defaults to same as port if omitted. nodePort auto-assigned from 30000-32767 if omitted (NodePort type).

15 Endpoints — The Bridge Between Service and Pods ▶

What are they
Lifecycle
Debug empty
DefinitionAn Endpoints object is auto-created for each Service. It lists the IP:port of every Pod matching the Service's selector that is currently Ready. kube-proxy reads Endpoints to build iptables rules. No endpoints = no traffic routing.
kubectl get endpoints web-svc
# NAME      ENDPOINTS
# web-svc   10.244.1.5:80,10.244.2.3:80,10.244.3.7:80
Pod passes readiness: IP added to Endpoints ✓
Pod fails readiness: IP removed from Endpoints ✗
Pod deleted: IP removed from Endpoints ✗
New Pod created + ready: IP added to Endpoints ✓

Automatic. No manual management. Endpoint controller constantly reconciles.
Debug: Service has NO endpoints
kubectl get endpoints web-svc
# ENDPOINTS: <none>  ← PROBLEM! No Pods to route to.

# Cause 1: Selector doesn't match any Pod labels
kubectl get svc web-svc -o jsonpath='{.spec.selector}'
kubectl get pods --show-labels

# Cause 2: No Pods exist
kubectl get pods -l app=web

# Cause 3: Pods exist but all failing readiness
kubectl get pods -l app=web
# READY: 0/1 ← readiness probe failing

Superset chain:
ClusterIP ⊂ NodePort ⊂ LoadBalancer

LoadBalancer creates a NodePort, which creates a ClusterIP. Each type INCLUDES all features of the type before it.

Headless: StatefulSets, peer discovery, client-side LB (gRPC).
ExternalName: External databases/APIs outside K8s.
Ingress (not a Service type): HTTP/HTTPS routing. Multiple Services behind one IP.

Checklist

Can't reach
