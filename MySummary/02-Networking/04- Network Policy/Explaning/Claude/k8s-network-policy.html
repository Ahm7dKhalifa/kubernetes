01 · Foundations

What a NetworkPolicy actually is

A NetworkPolicy is a Kubernetes API object that declares which network connections are allowed in and out of a set of pods. It is not a process, not a sidecar, and not a piece of code that runs inside your pod — it is a specification that the CNI plugin compiles into kernel-level packet filters (iptables, eBPF, or nftables) on every node.

The single sentence definition

📘 Formal definition

A NetworkPolicy is a namespaced Kubernetes resource (networking.k8s.io/v1) that selects a group of pods via a podSelector and declares an allow-list of ingress (incoming) and/or egress (outgoing) traffic at L3/L4 — using sources/destinations identified by pod labels, namespace labels, or IP CIDR blocks, restricted to specific TCP/UDP/SCTP ports.

The four words that matter

🎯 Selects

A policy applies only to pods that match its podSelector. Pods not selected by any policy keep their default behavior (allow-all).

📜 Declares

Policies are declarative — you describe the desired state. The CNI continuously reconciles kernel rules to match.

✅ Allow-list

NetworkPolicy is purely additive: each rule adds what is allowed. There is no deny verb in v1 — denial happens by omission.

🧱 L3/L4

Operates at IP + port level. It cannot inspect HTTP paths, headers, or methods — that is the job of a service mesh or L7 policy (Cilium, Istio AuthorizationPolicy).

The mental model: a per-pod firewall

The clearest way to think about it: every pod in a Kubernetes cluster has an invisible firewall sitting in front of it. By default, that firewall has a single rule — ALLOW ANY. The moment you create a NetworkPolicy that selects that pod, the firewall flips its default to DENY ANY and then layers on top of that whatever you explicitly allowed.

Fig 1.1 — The firewall flips to default-deny only for pods selected by a policy

Where it lives

The object lives in etcd at the path /registry/networkpolicies/<namespace>/<name>. It is namespaced — a policy in jahez-prod only selects pods in jahez-prod. The kube-controller-manager does not act on it directly; instead, every node's CNI agent (e.g., Calico's calico-node, Cilium's cilium-agent) watches the API for NetworkPolicy events and translates them into local kernel rules.

Key insight. NetworkPolicy is enforced per-node, on the source side and the destination side. A rule allowing pod A → pod B requires both nodes (where A runs and where B runs) to agree. The CNI is responsible for keeping rules in sync as pods are scheduled and rescheduled.
02 · Foundations

Why NetworkPolicy exists

Kubernetes is built on a flat networking model: every pod can reach every other pod by IP, across nodes, across namespaces, with no NAT. This is wonderful for development and lateral movement for an attacker who just compromised one container.

The flat-network problem

The Kubernetes networking model has three rules:

  1. Every pod gets its own routable IP address.
  2. Every pod can communicate with every other pod, on every node, without NAT.
  3. An agent on the node (kubelet, system daemons) can reach all pods on that node.

This is by design — it makes the cluster feel like a single flat network and removes all the port-mapping complexity of Docker's bridge networking. But it has a security implication that hits hard the first time it bites you.

⚠️ The blast radius

If an attacker gets RCE in any pod — say, your image-processing worker via a libpng exploit — that pod can immediately open a TCP connection to:

  • Your Postgres pod's port 5432 in the databases namespace.
  • Your Redis pod's port 6379 with no auth (the default).
  • Your internal admin dashboard on :8080.
  • The cluster's metadata service at 169.254.169.254 (cloud IAM credentials).
  • Every other workload in every other namespace.

None of this requires DNS, certificates, or service accounts. Just a TCP connect() call.

What NetworkPolicy gives you

NetworkPolicy is the Kubernetes-native answer to microsegmentation — the idea that traffic should be allowed only between components that have a documented reason to talk. It is one of the foundational pillars of zero-trust networking inside the cluster.

🎯 Blast-radius reduction

A compromised pod can only reach what its policy allows. Lateral movement stops at the first deny.

🧾 Compliance

PCI-DSS 1.2/1.3, HIPAA, SOC 2 all require documented network segmentation. NetworkPolicy is the Kubernetes way to satisfy auditors.

🪪 Identity-based

Rules use pod labels — not IPs. Pods can move between nodes, scale up and down, get new IPs, and the policy keeps working.

🧪 Multi-tenancy

Namespace-scoped policies let you isolate teams, environments (prod vs. staging), or customer tenants on the same cluster.

📤 Egress control

Restrict which external endpoints pods can reach — block exfiltration to attacker-controlled domains, or limit cloud SDK access to specific buckets.

🔁 Declarative drift-free

Policies are GitOps-friendly. Apply via Argo/Flux; the CNI continuously reconciles kernel rules.

03 · Foundations

The default-allow problem & the additive model

NetworkPolicy has two behaviors that surprise everyone the first time. Internalizing them is the difference between policies that work and policies that silently break production.

Rule 1 — A pod with no policy is fully open

If no NetworkPolicy selects a given pod, that pod accepts all ingress traffic and can send all egress traffic. Kubernetes ships with default-allow.

Rule 2 — A pod with any policy flips to default-deny for that direction

The moment a pod is selected by at least one policy whose policyTypes includes Ingress, that pod's ingress flips to default-deny — only what is explicitly allowed by the union of all matching policies' ingress rules will work. Same independently for Egress.

The asymmetry trap. If you write a policy that only specifies policyTypes: [Ingress], the pod's egress stays default-allow. Many teams ship "secure" policies that lock down ingress while egress remains wide open — DNS exfil, anyone?

Rule 3 — Policies are purely additive (OR)

If three policies select the same pod, the effective allow-list is the union of all three. There is no concept of priority, ordering, or override. If any policy allows a flow, it's allowed.

Fig 3.1 — Multiple policies on the same pod: their allow-lists are unioned

Once you internalize this, the design pattern becomes obvious: start every namespace with a default-deny policy that selects everything, then layer narrow allow-rules on top. We use exactly this pattern in the Jahez project below.

04 · Foundations

The CNI & the enforcement layer

A NetworkPolicy stored in etcd is just YAML. It does nothing until a CNI plugin that supports NetworkPolicy translates it into kernel-level filters on every node. If your CNI does not support NetworkPolicy — your policies are silently inert.

The flow from kubectl apply to packet drop

From YAML to dropped packet
1 / 5

Step 1 — Apply & validate

You run kubectl apply -f policy.yaml. The kube-apiserver validates the schema (admission), authorizes the request (RBAC), and writes the object to etcd at /registry/networkpolicies/<ns>/<name>. The API server returns 201 Created.

At this moment nothing in your data plane has changed yet. The policy exists only in etcd.

Step 2 — CNI agent observes

On every node, the CNI's per-node agent (e.g. calico-node, cilium-agent, kube-router) holds a watch on networkpolicies and pods via the API server. The watch fires with the new object.

The agent computes which local pods are affected by intersecting the policy's podSelector with the labels of pods scheduled to this node.

Step 3 — Compile to data-plane primitives

The agent compiles the high-level allow-rules into the data-plane primitive used by that CNI:

  • Calico (iptables mode) — programs Linux iptables chains and ipset sets per pod interface.
  • Calico (eBPF mode) / Cilium — loads eBPF programs attached to the pod's veth at tc ingress/egress, with a policy-map lookup per packet.
  • kube-router — uses ipsets + iptables.
  • Antrea — programs Open vSwitch flow rules.

Step 4 — Pod identity → IP mapping

Because rules are written against labels but the kernel filters on IP addresses, the agent maintains a real-time mapping from "selector → set of pod IPs" and updates the kernel rules whenever pods come and go. In Cilium this is the identity; in Calico it's the ipset.

Step 5 — Packet hits the rule

A pod attempts connect(orders-pod-ip:8080). The packet leaves the pod's veth, hits the source node's egress chain — if denied, dropped here. If allowed, it crosses the overlay (VXLAN/IP-in-IP/native routing) to the destination node, where it hits the destination ingress chain — if denied, dropped here.

Both endpoints enforce. A flow must be allowed by the source pod's egress policy and the destination pod's ingress policy. Either side dropping = silent connection timeout to the application.

05 · Anatomy

The NetworkPolicy object — full anatomy

Every NetworkPolicy you will ever write is a permutation of the same six fields. Master them and you can express any L3/L4 policy.

networkpolicy-anatomy.yamlYAML
apiVersion: networking.k8s.io/v1          # 1. The stable v1 API group
kind: NetworkPolicy                        # 2. Always NetworkPolicy
metadata:
  name: orders-allow-from-gateway           # 3. Name (DNS subdomain)
  namespace: jahez-prod                     #    Namespaced object
spec:
  podSelector:                              # 4. WHICH pods this policy governs
    matchLabels:
      app: orders-svc
  policyTypes:                              # 5. Direction(s) this policy controls
    - Ingress                                  #    -- flips ingress to default-deny
    - Egress                                   #    -- flips egress to default-deny
  ingress:                                  # 6a. Allow-list of incoming flows
    - from:
        - podSelector:
            matchLabels: { app: api-gateway }
      ports:
        - { protocol: TCP, port: 8080 }
  egress:                                   # 6b. Allow-list of outgoing flows
    - to:
        - podSelector:
            matchLabels: { app: postgres }
      ports:
        - { protocol: TCP, port: 5432 }
    - to:                                    # DNS — almost always required
        - namespaceSelector: { matchLabels: { kubernetes.io/metadata.name: kube-system } }
          podSelector: { matchLabels: { k8s-app: kube-dns } }
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }

Field-by-field reference

FieldRequiredTypePurpose
spec.podSelector✅LabelSelectorSelects pods to which this policy applies. {} selects all pods in the namespace.
spec.policyTypesrecommended[Ingress, Egress]Declares which directions the policy is authoritative for. Inferred if omitted, but always set explicitly.
spec.ingress[]conditionalNetworkPolicyIngressRule[]List of allow-rules for incoming traffic. Empty list / absent = no ingress allowed (when policyTypes contains Ingress).
spec.egress[]conditionalNetworkPolicyEgressRule[]List of allow-rules for outgoing traffic. Same semantics for Egress direction.

ingress[].ports[]—NetworkPolicyPort[]Ports allowed by this rule. Omitted = all ports for this rule.
egress[].to[]—NetworkPolicyPeer[]Destinations allowed by this rule.
egress[].ports[]—NetworkPolicyPort[]Ports allowed by this rule.

The "rule" structure — AND vs OR

This is where most people get tripped up. Within a single rule, the from peers are OR'd, the ports are OR'd, and the rule allows the cartesian product (from × ports). Multiple rules in the same ingress[] array are also OR'd.

⚡ AND inside a peer

The exception that bites: when you put both podSelector AND namespaceSelector as keys of the same from/to entry (no dash before the second key), they are AND'd. Two separate dashed entries = OR; same entry, two keys = AND.

OR — pods in either namespace OR with labelYAML
from:
  - namespaceSelector:
      matchLabels: { env: prod }
  - podSelector:
      matchLabels: { app: monitoring }
# allows: any pod in env=prod NS  OR
#         any pod with app=monitoring (in same NS)
AND — only specific pods in specific NSYAML
from:
  - namespaceSelector:
      matchLabels: { env: prod }
    podSelector:
      matchLabels: { app: monitoring }
# allows: only pods with app=monitoring
#         that ALSO live in env=prod NS
06 · Anatomy

The podSelector — who does this policy govern?

Every NetworkPolicy starts by answering one question: which pods am I about to apply rules to? That is the job of spec.podSelector. Get this wrong and your policy applies to the wrong pods (or none at all).

Three forms you will use daily

1️⃣ Empty selector

podSelector: {} — selects all pods in the namespace. Used for namespace-wide default-deny.

2️⃣ matchLabels

Equality match: pods that have all these labels. The 90% case.

3️⃣ matchExpressions

Set-based: In, NotIn, Exists, DoesNotExist. Use when you need OR over label values or "has any version".

podselector-examples.yamlYAML
# A — Select all pods in the namespace
spec:
  podSelector: {}

# B — Equality: pods labelled app=orders-svc AND tier=backend
spec:
  podSelector:
    matchLabels:
      app: orders-svc
      tier: backend

# C — Set: pods labelled app IN (orders-svc, payments-svc)
spec:
  podSelector:
    matchExpressions:
      - { key: app, operator: In, values: [orders-svc, payments-svc] }

# D — Exists: any pod with a `version` label
spec:
  podSelector:
    matchExpressions:
      - { key: version, operator: Exists }

# E — Combined: equality AND set
spec:
  podSelector:
    matchLabels:
      tier: backend
    matchExpressions:
      - { key: env, operator: NotIn, values: [staging, test] }
Always namespaced. spec.podSelector only selects pods in the policy's own namespace. There is no way for a NetworkPolicy in jahez-prod to select pods in monitoring. To restrict cross-namespace targeting use namespaceSelector in the peer side (covered in §10).

Label hygiene matters

NetworkPolicy is only as good as your label discipline. Adopt a consistent set of labels across every workload:

📐 Recommended label schema
  • app.kubernetes.io/name — the application identifier (e.g. orders-svc)
  • app.kubernetes.io/component — role within the app (api, worker, db)
  • app.kubernetes.io/part-of — higher-level grouping (jahez-checkout)
  • tier — frontend / backend / data
  • env — prod / staging / dev
07 · Anatomy

policyTypes — the most misunderstood field

If you remember one thing from this guide: always set policyTypes explicitly. Inferred behavior is the #1 source of "my policy isn't doing what I thought".

What it does

The policyTypes field tells Kubernetes which directions this policy is authoritative for. The presence of Ingress in the list means: "for the pods I select, this policy is locking down ingress; from now on only what I list under spec.ingress is allowed." Same for Egress.

The three valid combinations

A · [Ingress]

Locks down ingress only. Egress remains default-allow (unless another policy locks egress).

B · [Egress]

Locks down egress only. Ingress remains default-allow.

C · [Ingress, Egress]

Locks down both directions in one policy.

The inference rules (when policyTypes is omitted)

If you do not set policyTypes, Kubernetes infers it from which of spec.ingress / spec.egress are present:
  • Has spec.ingress only → inferred as [Ingress]
  • Has spec.egress only → inferred as [Ingress, Egress] (yes, Ingress too — surprising!)
  • Has both → [Ingress, Egress]
  • Has neither → [Ingress]
Never rely on inference. Always set policyTypes explicitly.

The "block all egress" trick

This is the canonical default-deny-egress policy. Note how the egress field is absent — that's not a typo:

default-deny-egress.yamlYAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-egress
  namespace: jahez-prod
spec:
  podSelector: {}              # every pod in the namespace
  policyTypes: [Egress]      # lock down egress
  # NOTE: no `egress:` key at all
  # → empty allow-list → ALL egress denied

Compare this to a policy with egress: [] — same effect — versus one with egress: [{}] which means "one rule with no peers and no ports = allow all".

08 · Anatomy

Ingress rules — controlling who reaches in

Ingress rules describe the allowed sources of traffic arriving at the selected pods. Each rule is a tuple of from peers and ports; if a packet's source matches at least one rule's from AND its destination port matches that same rule's ports, it is allowed.

The shape of one rule

ingress-rule-shape.yamlYAML
ingress:
  - from:                        # list of NetworkPolicyPeer (OR'd)
      - podSelector: {...}
      - namespaceSelector: {...}
      - ipBlock: {...}
    ports:                       # list of NetworkPolicyPort (OR'd)
      - { protocol: TCP, port: 8080 }
      - { protocol: TCP, port: 8443 }
  - from:                        # a SECOND rule, also OR'd with the first
      - podSelector: { matchLabels: { app: monitoring } }
    ports:
      - { protocol: TCP, port: 9090 }

Rule semantics — the four edge cases

ShapeMeaning
ingress: []Empty list — deny all ingress
ingress: [{}]One rule with no from and no ports — allow all ingress
ingress: [{ from: [...] }]From listed peers, on any port
ingress: [{ ports: [...] }]From any source, but only on listed ports

Worked example — orders-svc accepts only the gateway and the metrics scraper

orders-ingress.yamlYAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: orders-ingress
  namespace: jahez-prod
spec:
  podSelector:
    matchLabels: { app: orders-svc }
  policyTypes: [Ingress]
  ingress:
    # Rule 1 — API gateway can hit business endpoints
    - from:
        - podSelector:
            matchLabels: { app: api-gateway }
      ports:
        - { protocol: TCP, port: 8080 }
    # Rule 2 — Prometheus from monitoring NS scrapes metrics
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: monitoring }
          podSelector:
            matchLabels: { app.kubernetes.io/name: prometheus }
      ports:
        - { protocol: TCP, port: 9090 }

Named ports

You can reference a port by its name rather than number — useful when the same policy targets pods that may use different numeric ports but standard names like http or metrics.

named-port.yamlYAML
ports:
  - protocol: TCP
    port: http           # resolved per-pod from containerPort name
09 · Anatomy

Egress rules — controlling who the pods reach out to

Egress rules are the symmetric counterpart of ingress: a list of allowed destinations. The mechanics are identical, but two real-world subtleties bite hard: DNS and stateful return traffic.

DNS — the hidden dependency in every egress policy

The classic break. You apply a default-deny-egress policy, then explicitly allow your app to reach Postgres on TCP/5432 — and the app still can't connect. Why? Because before any TCP connection, the app does getaddrinfo("postgres.databases.svc.cluster.local"), which is a UDP/53 query to kube-dns in kube-system. You blocked DNS. You always need to allow DNS in any egress-restricted pod.
allow-dns.yaml — the snippet you will copy into every egress policyYAML
egress:
  - to:
      - namespaceSelector:
          matchLabels: { kubernetes.io/metadata.name: kube-system }
        podSelector:
          matchLabels: { k8s-app: kube-dns }
    ports:
      - { protocol: UDP, port: 53 }
      - { protocol: TCP, port: 53 }    # for >512-byte responses / DoT

Note we use kubernetes.io/metadata.name — a label automatically added to every namespace by the API server since v1.22, so we don't need to label kube-system ourselves.

Stateful return — you do not need to allow it

Common confusion: "I allowed egress to Postgres, do I need to allow ingress for the response?" — No. NetworkPolicy is conntrack-aware: the CNI tracks established connections, and reply packets in an allowed flow are automatically permitted. You only write rules for the connection initiation.

Egress to external destinations

Egress rules can target IP CIDR blocks for non-cluster destinations (a payment gateway, a SaaS API, the internet). See §10 for ipBlock mechanics, including the except field for fine-grained denies.

egress-payment-gateway.yamlYAML
egress:
  - to:
      - ipBlock:
          cidr: 52.84.0.0/15     # Mada / payment provider range
    ports:
      - { protocol: TCP, port: 443 }
9.5 · Anatomy · Deep Dive

Ingress & Egress in depth — the 3-tier worked example

The clearest way to internalize ingress and egress is to walk through a tiny but realistic three-tier app: a frontend, a backend API, and a database. We will start with zero policies (everything is open and the database is exposed), then progressively add policies until the frontend cannot reach the database — only the backend can — while every legitimate flow keeps working.

9.5.1 Direction is always relative to the pod

Before diagrams, the one fact that confuses everyone the first time: ingress and egress are always written from the perspective of the pod that the policy selects. If the pod is the database, "ingress" is traffic arriving at the database from someone else. If the pod is the backend, "egress" is traffic leaving the backend toward someone else. The same wire — backend → database — is the backend's egress and simultaneously the database's ingress.

Fig 9.5.1 — A single connection is described from both ends. Both ends must permit it.
Key consequence. When you debug a "blocked connection", you must check policies on both the source pod (egress) and the destination pod (ingress). Either side dropping = packet dies.

9.5.2 The 3-tier app we'll secure

A simple e-commerce frontend that calls a backend API, which reads/writes a Postgres database. All three live in the shop namespace.

Fig 9.5.2 — The intended traffic: user → frontend → backend → database. The dangerous flow we want to prevent: frontend → database (skipping the backend).

9.5.4 BEFORE — no NetworkPolicy applied

With zero NetworkPolicies, every pod can reach every other pod on every port. The frontend can connect directly to the database, completely bypassing the backend's authorization, validation, and audit logging.

Fig 9.5.3 — BEFORE: an attacker who pops the frontend (XSS, SSRF, RCE in image upload) gets a direct line to Postgres. They can dump customers, modify orders, exfiltrate cards.

Reproduce it from a frontend pod:

verify-before.shbash

9.5.5 AFTER — with NetworkPolicies applied

We are going to apply three NetworkPolicies. Together they enforce: frontend can talk to backend only; backend can talk to database only; database accepts only from backend; and nothing in the namespace can reach anything else.

Fig 9.5.4 — AFTER: the same packet that worked in BEFORE now hits an iptables/eBPF DROP rule on the database pod's veth — silent timeout for the attacker.

9.5.6 The three policies — with arrows annotated

We'll write each policy and pair it with a small per-pod arrow diagram showing exactly what that policy lets in and out. Read these from the perspective of the selected pod.

① frontend-policy — selected pod is the frontend

Fig 9.5.5 — frontend-policy: ingress from ingress-nginx; egress to backend only. Database egress is implicitly denied.
01-frontend-policy.yamlYAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: frontend-policy
  namespace: shop
spec:
  podSelector:                                  # selects: the frontend
    matchLabels:
      tier: frontend
      app: web
  policyTypes: [Ingress, Egress]            # lock down BOTH directions
  #  ┌─ INGRESS ──────────────────────────────────┐
  #  │ Allow public traffic from ingress-nginx    │
  #  │ on port 80 (the Service forwards to here). │
  #  └────────────────────────────────────────────┘
  ingress:
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: ingress-nginx }
      ports:
        - { protocol: TCP, port: 80 }
  #  ┌─ EGRESS ───────────────────────────────────┐
  #  │ Allow ONLY two outbound flows:             │
  #  │  1. to the backend on port 8080            │
  #  │  2. to kube-dns for name resolution        │
  #  │ Everything else (incl. the database!)      │
  #  │ is implicitly denied.                       │
  #  └────────────────────────────────────────────┘
  egress:
    - to:
        - podSelector:
            matchLabels: { tier: backend, app: api }
      ports:
        - { protocol: TCP, port: 8080 }

10 · Anatomy

Peers — pod, namespace, and ipBlock selectors

A "peer" is the entity on the other side of an allowed flow. Three kinds: podSelector, namespaceSelector, ipBlock. Every peer entry uses exactly one combination of these three keys.

The three peer types

🟦 podSelector

Pods in the policy's own namespace matching the given labels.

Cross-namespace? Combine with namespaceSelector.

🟪 namespaceSelector

All pods in namespaces matching the given labels (including the policy's own NS, if labelled).

🟧 ipBlock

External CIDR. Used for traffic from/to outside the cluster (or to clamp pod-to-pod by IP).

Five peer patterns you will write

peer-patterns.yamlYAML
# 1. Pods in the same namespace
- podSelector:
    matchLabels: { app: api-gateway }

# 2. All pods in another namespace (use NS auto-label)
- namespaceSelector:
    matchLabels: { kubernetes.io/metadata.name: monitoring }

# 3. Specific pods in another namespace (AND — same dash entry!)
- namespaceSelector:
    matchLabels: { kubernetes.io/metadata.name: monitoring }
  podSelector:
    matchLabels: { app.kubernetes.io/name: prometheus }

# 4. External CIDR (the internet, a VPC subnet, a third-party API)
- ipBlock:
    cidr: 0.0.0.0/0
    except:
      - 10.0.0.0/8           # carve out internal RFC1918
      - 169.254.169.254/32  # cloud metadata service!

# 5. Allow from any pod in any namespace (use sparingly)
- namespaceSelector: {}    # {} = all namespaces
The metadata-service trap. On AWS / GCP / Azure, pods can hit 169.254.169.254 to grab the node's IAM credentials. Always add this IP to except in any wide-open egress allow list, or use IRSA / Workload Identity / Pod Identity which bypasses IMDS entirely.

11 · Patterns

Pattern: default-deny baseline

The single most important pattern in this entire guide. Every namespace that holds workloads should ship with a default-deny policy applied first, before any allow-specific rules. This flips the namespace from "allow by default" to "deny by default", and is the cornerstone of zero-trust microsegmentation.

Three flavors

A · deny ingress only

Pods can still call out (DNS works, calls to APIs work). Nothing can reach in unless a later policy allows it.

B · deny egress only

Pods accept traffic, but cannot reach anything — not even DNS. Use only with a paired allow-DNS policy.

C · deny both

Total isolation. The strongest baseline. Combine with explicit allow-DNS + allow-business policies.

The canonical default-deny-all

00-default-deny-all.yaml — apply first to every namespaceYAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: jahez-prod
spec:
  podSelector: {}                # every pod in this namespace
  policyTypes:
    - Ingress
    - Egress
  # no `ingress:` and no `egress:` keys
  # → empty allow-list in both directions
  # → every pod here flips to default-deny in BOTH directions

This single 11-line YAML is the most powerful security control in the cluster. From the moment it's applied, no pod in jahez-prod can talk to anything — not the API server, not DNS, not Postgres, not the internet. Your apps will start failing immediately. That is the point.

The companion: allow-DNS

Always pair the default-deny with an allow-DNS policy. Without DNS, almost nothing works (image pulls happen at the kubelet level so they're unaffected, but every http.Get("https://api.example.com") in your app fails).

01-allow-dns.yaml — companion to default-denyYAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: jahez-prod
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: kube-system }
          podSelector:
            matchLabels: { k8s-app: kube-dns }
      ports:
        - { protocol: UDP, port: 53 }
        - { protocol: TCP, port: 53 }
Order doesn't matter. Because policies are unioned, you can apply allow-dns before default-deny-all or after — the resulting allow-list is identical. Apply both together via Kustomize/Helm to keep them in lockstep.
12 · Patterns

Pattern: allow-specific (the workhorse)

After default-deny, every meaningful flow needs an explicit allow. The allow-specific pattern is one policy per service that lists the exact upstream and downstream pods it talks to.

The three-rule template

For any backend service, you typically need three rule blocks:

  1. Ingress from upstream callers — the gateway, other internal services that depend on you.
  2. Egress to downstream dependencies — your database, the cache, the next microservice.
  3. Egress to platform services — DNS (always), metrics push (if used), logging sidecar.
orders-svc-allow.yaml — the workhorse templateYAML
apiVersion: networking.k8s.io/v1

metadata:

    matchLabels: { app.kubernetes.io/name: orders-svc }

        - podSelector:
            matchLabels: { app.kubernetes.io/name: api-gateway }
      ports:
        - { protocol: TCP, port: 8080 }
    # [2] from monitoring NS — Prometheus scrape
    - from:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: monitoring }
          podSelector:
            matchLabels: { app.kubernetes.io/name: prometheus }
      ports:
        - { protocol: TCP, port: 9090 }
  egress:
    # [3] to orders-db (Postgres) in the data NS
    - to:
        - namespaceSelector:
            matchLabels: { kubernetes.io/metadata.name: jahez-data }
          podSelector:
            matchLabels: { app.kubernetes.io/name: orders-db }

        - { protocol: TCP, port: 5432 }

        - podSelector:
            matchLabels: { app.kubernetes.io/name: catalog-svc }

        - { protocol: TCP, port: 8080 }

            matchLabels: { k8s-app: kube-dns }

15 · Patterns

Pattern: external CIDR egress

When a pod must reach something outside the cluster — a SaaS API, a payment processor, an on-prem database, the public internet — you allow the destination via ipBlock. Two patterns dominate: precise allow-list and wide-open with carve-outs.

Pattern A — precise allow-list (preferred)

payments-egress-precise.yamlYAML
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: payments-egress-external
  namespace: jahez-prod
spec:
  podSelector:
    matchLabels: { app.kubernetes.io/name: payments-svc }
  policyTypes: [Egress]
  egress:
    # Mada / payment processor — get the CIDR from the provider
    - to:
        - ipBlock: { cidr: 52.84.0.0/15 }
        - ipBlock: { cidr: 198.51.100.0/24 }
      ports:
        - { protocol: TCP, port: 443 }

Pattern B — open internet with carve-outs

For a service that legitimately needs broad internet egress (image-processing pulling random URLs, analytics fan-out), use 0.0.0.0/0 with except to still block the cluster-internal RFC1918 ranges and the dangerous metadata service IP.

internet-egress-with-carveouts.yamlYAML
spec:
  egress:
    - to:
        - ipBlock:
            cidr: 0.0.0.0/0
            except:
              - 10.0.0.0/8            # internal cluster overlay
              - 172.16.0.0/12         # internal RFC1918
              - 192.168.0.0/16        # internal RFC1918
              - 169.254.169.254/32    # cloud metadata service !!
      ports:
        - { protocol: TCP, port: 443 }
Always except 169.254.169.254/32. This is the IMDS — Instance Metadata Service — on EC2, GCE, Azure. From inside a pod it returns the node's IAM credentials. SSRF + open egress = full cloud account compromise. Use IRSA (EKS), Workload Identity (GKE), or AAD Pod Identity (AKS) to give pods their own scoped identity, and block IMDS unconditionally.

The except field — gotchas

⚠️ except CIDRs must be subsets of cidr

If your cidr is 10.0.0.0/16 you cannot except: 192.168.0.0/24 — the API server rejects it. The exceptions must fall within the parent block.

⚠️ except is per-ipBlock, not global

If you have two ipBlock entries, each has its own except. They do not interact.

Project · P7 · Payments

P7 — Payments service: PCI scope & external egress

A NetworkPolicy that you wrote but didn't test is a security control that exists in your manifest repo and not in the kernel. The first time you find out it doesn't work is during the incident.

The four testing techniques

1️⃣ Manual probe with netshoot

Spin a debug pod with the labels of the source you want to simulate, then curl -m 3 the target. Failure = drop.

2️⃣ cyclonus & kubectl-np-viewer

Open-source tools that enumerate your policies and tell you the effective allow-matrix.

3️⃣ CNI-native flow logs

Cilium's hubble observe, Calico's calicoctl flow logs — show every accepted/denied flow in real time.

4️⃣ Synthetic test pods

Permanent canary pods with known labels in CI that probe their expected paths every minute. Alert when expected flows fail or unexpected ones succeed.

Step 1 — Reproduce in a probe pod

Forget the application. Spin a netshoot pod with the same labels as the failing source pod, then curl -v the target. If this works but your app fails, it's an app bug; if this fails, it's a policy issue.

Step 2 — List policies that select source & target

kubectl get netpol -n jahez-prod -o json | \
  jq '.items[] | select(.spec.podSelector.matchLabels."app.kubernetes.io/name" == "orders-svc")'

Both source's egress policies AND target's ingress policies must permit the flow.

Step 3 — Check policyTypes & rules carefully

Common bugs: policyTypes: [Ingress] when you meant both. A peer that's a namespaceSelector alone (matches all pods in matching NS — usually fine) versus combined with podSelector (AND, much narrower).

Step 4 — Verify the labels

kubectl get pod -n jahez-prod orders-svc-xxxx --show-labels

If the pod is missing app.kubernetes.io/name=orders-svc, the policy doesn't match it — which means default-allow if no other policy selects it, or default-deny if some other catch-all selects it.

Step 5 — Tap the CNI

Cilium: hubble observe --from-pod jahez-prod/orders-svc-xxxx --verdict DROPPED.

Calico: calicoctl get globalnetworkset + flow logs.

If the CNI says "no policy match — implicit deny", the source/target labels don't match what your policy expects. If it says "denied by policy X", you know which manifest to fix.

The ten common pitfalls

Every team that has rolled out NetworkPolicies in production has hit at least five of these. Here they are, ranked roughly by how often they bite.

① Forgetting to allow DNS

You apply default-deny-egress, the app starts timing out on every named lookup. The single most common break. Always pair default-deny with allow-DNS to kube-system/k8s-app=kube-dns.

② Your CNI doesn't enforce policies

Flannel-only clusters, AKS without --network-policy, EKS without VPC CNI policy support — the YAMLs apply cleanly but nothing happens. Test with a known-deny rule and verify it actually blocks.

③ AND vs OR confusion in peers

Putting podSelector and namespaceSelector as keys of the same dashed entry = AND (specific pods in specific NS). As separate dashed entries = OR. People write OR when they mean AND, accidentally allowing all pods in the source NS.

④ Inferred policyTypes surprises

If you only set spec.egress, Kubernetes infers policyTypes: [Ingress, Egress] — which means ingress also gets locked down to nothing. Always set policyTypes explicitly.

⑤ policyTypes: [Ingress] + leaving egress wide open

You secure ingress meticulously, then forget that egress is still default-allow. A compromised pod still has full egress to the internet, the metadata service, and every other pod's metrics port.

⑥ Missing 169.254.169.254 carve-out

Open-internet egress policies that don't except: 169.254.169.254/32 let SSRF in any pod steal IAM credentials from IMDS. Always except the metadata service.

⑦ Cluster mesh / multi-cluster blind spots

If you use Cilium ClusterMesh / Submariner / Istio multi-cluster, traffic from another cluster appears with foreign IPs that no podSelector can match. Use cluster-aware peers (Cilium fromGroups) or ipBlock by remote pod CIDR.

⑧ Hostnetwork pods bypass policies

Pods with spec.hostNetwork: true use the node's network namespace and are not subject to NetworkPolicy on most CNIs. Audit for this — it's how some agents (node-exporter) and some sneaky workloads escape.

⑨ Service IPs vs Pod IPs in ipBlock

NetworkPolicy ipBlock filters pod IPs, not Service ClusterIPs. After kube-proxy rewrites destination, the policy sees the pod IP. Don't try to ipBlock the Service VIP — it won't match.

⑩ "Just for now" wide-open rules that never get tightened

Someone debugs an issue by adding {} # allow all as a temporary measure. The TODO never gets done. Audit policies in CI for empty selectors and `0.0.0.0/0` without exceptions; fail builds.

The 4-step rollout playbook

  1. Audit the matrix. Document every flow before writing a single policy. (See §P1 for the format.)
  2. Apply default-deny in audit/observe mode first. Cilium and Calico both support audit mode that logs without enforcing — run for a week, find missing flows.
  3. Roll out namespace-by-namespace. Start with the lowest-risk NS (e.g., a dev environment), then platform NS (monitoring), then your core production NS.
  4. Add CI gates. Every PR adding a Deployment must add a corresponding NetworkPolicy or fail the build. Kyverno / OPA Gatekeeper enforces this.
