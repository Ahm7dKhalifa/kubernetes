§ 01 — What are Volumes?
Definition

What are Kubernetes Volumes?

Simple Explanation

Every container gets its own ephemeral writable layer on top of its image. The moment Kubernetes kills or restarts that container — crash, OOM, probe failure — the layer is destroyed and every write inside it is gone.

A Volume solves this: it is a directory attached to the Pod, not the container. It persists across individual container restarts — and when using a PVC, it persists even when the whole Pod is deleted.

Official / Technical Definition

On-disk files in a container are ephemeral, which presents problems for non-trivial applications when running in containers. One problem occurs when a container crashes or is stopped. The container state is not saved so all of the files that were created or modified during the lifetime of the container are lost. During a crash, the kubelet restarts the container with a clean state.

A second problem occurs when multiple containers are running in a Pod and need to share files. It can be challenging to set up and access a shared filesystem across all of the containers.

The Kubernetes volume abstraction solves both of these problems. A Volume is a directory, possibly with some data in it, which is accessible to the containers in a Pod. How that directory comes to be, the medium that backs it, and the contents of it are determined by the particular volume type used.

To use a volume, specify the volumes to provide for the Pod in .spec.volumes and declare where to mount those volumes into containers in .spec.containers[*].volumeMounts. A volume cannot be mounted within another volume. Also, a volume cannot contain a hard link to anything in a different volume.

ℹ
Mental Model Think of a Volume as a USB drive attached to the Pod. Any container in the Pod can plug into it at any path it chooses. The drive stays intact if one container crashes. Only removing the entire Pod ejects the drive (for emptyDir) — or the drive stays permanently in the cloud (for PVCs).
Interactive — Volume Anatomy: How It Actually Works
1 / 5
Step 1 — The Problem: Container Writes Are Ephemeral

Database writes go into the container's own writable layer. When Kubernetes kills and restarts the container — OOM kill, crash, probe failure — a brand new container starts from the base image. All data is permanently wiped.

Step 2 — Fix: Declare a Volume on the Pod Spec

You add volumes: to the Pod spec — not inside the container definition. The container declares volumeMounts to say where to mount it. Now all database writes go to the PVC-backed volume on a real cloud disk, not the ephemeral container layer.

Step 3 — Sharing: Multiple Containers, Same Volume, Different Paths

The same volume is mounted into Container A at /var/log/app and into Container B at /logs. Both paths resolve to the identical directory on disk. When A writes app.log, B reads it at /logs/app.log immediately — no network, no API calls, pure filesystem I/O. This is the sidecar pattern.

Step 4 — Container Crashes: Volume Survives, Container Does Not

Container A is OOM-killed. Kubernetes restarts just the container — the Pod keeps running. The emptyDir directory is untouched. When Container A restarts, it remounts the volume and finds every file exactly as it left them. Container restarts do NOT delete volumes. Only Pod deletion does.

Step 5 — Two Volume Types: Temporary (emptyDir) vs Permanent (PVC)

The most important decision in Kubernetes storage: emptyDir for temporary shared scratch (data that can be recreated), PVC for anything permanent (databases, user uploads, application state). The API looks the same — only the volume type differs.

📦

Declared at Pod Level

Volumes live in .spec.volumes[] on the Pod spec — not inside any container. All containers in the Pod can see and mount them. Think: "Pod comes with a drive; containers plug in."

🔗

Each Container Mounts Explicitly

A container must declare volumeMounts to access a volume. Two containers can mount the same volume at different paths — both see identical files with zero data copies.

⏳

Pod Lifetime, Not Container Lifetime

Volumes survive container crashes and restarts. emptyDir is deleted only when the Pod is removed. PVC-backed volumes persist beyond even Pod deletion.

🔌

Same API, Many Backends

Identical volumeMounts syntax works for RAM (emptyDir), cloud disks (PVC), config files (ConfigMap), credentials (Secret), and NFS. Your container code never changes.

§ 02 — Why Volumes?
Motivation

Why Are Volumes Critical?

Simple Explanation

Kubernetes treats containers as cattle, not pets — disposable, replaceable, constantly killed and rescheduled. For stateless apps, this is a feature. For stateful workloads (databases, queues, file stores), this behavior is catastrophic without volumes.

Official / Technical Context

Docker also has a concept of volumes, though it is somewhat looser and less managed. A Docker volume is a directory on disk or in another container. Docker provides volume drivers, but the functionality is somewhat limited.

Kubernetes supports many types of volumes. A Pod can use any number of volume types simultaneously. Ephemeral volume types have a lifetime of a Pod, but persistent volumes exist beyond the lifetime of a Pod. When a Pod ceases to exist, Kubernetes destroys ephemeral volumes; however, Kubernetes does not destroy persistent volumes. For any kind of volume in a given Pod, data is preserved across container restarts.

At its core, a volume is a directory, possibly with some data in it, which is accessible to the containers in a Pod. How that directory comes to be, the medium that backs it, and the contents of it are determined by the particular volume type used. This directly addresses the need for workloads that require durable state beyond the ephemeral container filesystem.

⚠
The Core Problem MySQL container OOM-killed at 14:32 → Kubernetes restarts in 3s → new container from clean base image → every table, row, and index permanently destroyed. You cannot run any stateful workload in Kubernetes without volumes.
Interactive — Real Scenarios: Without vs With Volumes
1 / 4
Scenario 1 — Database Without a Volume: Crash = Permanent Data Loss

Without a volume, Postgres stores data entirely in the container's writable layer. Kubernetes creates a brand-new container from the base image when it restarts — which has no data. The database is silently wiped every time the container crashes.

Scenario 1 Fixed — Database WITH a PVC: Crash-Safe

With a PVC at /var/lib/postgresql/data, all writes go to an EBS cloud disk. Container crashes 100 times — the disk is unchanged. New container starts, remounts the same disk, finds all 250,000 rows intact. This is what makes databases possible on Kubernetes.

Scenario 2 — Sidecar Log Shipping: emptyDir as Shared Bus

The App writes structured logs to /var/log/app/app.log. Fluentd reads from /logs/app.log (same file, different mount path) and ships to Elasticsearch. Zero network calls between containers — just filesystem reads/writes. This is the foundation of Kubernetes observability.

Scenario 3 — ConfigMap Volume: Live Config Without Redeployment

Update a ConfigMap with kubectl apply and Kubernetes automatically refreshes the mounted files inside running containers within ~60 seconds — no pod restart, no redeployment, no downtime. The app just reads the file on next access and gets the new value. Exception: subPath mounts freeze at container start time.

💾

Stateful Data Persistence

Databases, message queues, file uploads, ML models — all need data to survive crashes, restarts, and rescheduling to new nodes. PVCs back every serious stateful Kubernetes workload.

🤝

Zero-Network Sidecar Sharing

Two containers in the same Pod share data via filesystem I/O — no REST, no gRPC. App writes, sidecar reads. Simpler, faster, and more reliable than inter-container networking.

🔐

Config & Secret Injection

Mount ConfigMaps as files for live hot-reload. Mount Secrets as tmpfs (RAM) files — never written to disk. Update config without redeploying. Rotate secrets without restarting pods.

⚡

RAM-Backed High-Speed I/O

emptyDir {medium: Memory} gives you a tmpfs — RAM as a filesystem. Sub-millisecond latency, perfect for AI inference scratch, sort buffers, and shared Unix sockets.

☁️

Cloud-Portable Storage

Identical PVC YAML on AWS (EBS), GCP (PD), Azure (Disk), or on-prem (NFS/Ceph). Only the StorageClass differs per cluster. Your app YAML is truly cloud-portable.

📁

Node Filesystem Access

DaemonSets use hostPath to read /var/log (logs), /proc (metrics), and /var/run/docker.sock (runtime). Impossible to access node-level resources without volumes.

§ 03 — How Volumes Work
Internals

How Volumes Work Internally

Simple Explanation

Behind every mounted volume is a precise 7-step lifecycle managed by the API server, controller-manager, and kubelet. Understanding these steps helps you debug "PVC stuck in Pending", slow Pod starts, and mount failures — problems every Kubernetes engineer hits in production.

Official / Technical — Volume Mount Internals

Volumes are mounted on the host before being bind-mounted into the container. The kubelet is responsible for managing volume attachment, mounting, and cleanup. It calls volume plugins (or CSI drivers) via gRPC calls defined in the Container Storage Interface specification.

The kubelet uses a VolumeManager goroutine that continuously reconciles the desired volume state (volumes that should be attached and mounted for running Pods) with the actual state on the node. This reconciliation loop calls the appropriate volume plugin operations: Attach(), MountDevice(), SetUp() for provisioning, and their counterparts for teardown.

For CSI volumes specifically, the kubelet communicates with the node-side CSI driver via a Unix Domain Socket. The driver must implement the NodeServer gRPC service, which exposes NodeStageVolume, NodePublishVolume, NodeUnpublishVolume, and NodeUnstageVolume RPCs. The staging step performs a global mount on the node (for shared access across multiple Pods), while the publish step performs a Pod-specific bind-mount into the container's namespace.

01

Declare — Add volumes: to Pod Spec

You write volumes: in the Pod spec with a name and type (e.g. emptyDir: {} or persistentVolumeClaim: {claimName: my-pvc}). No storage is created yet — this is pure YAML configuration. Containers reference the volume by name in their volumeMounts.

02

Schedule — Topology-Aware Node Placement

The scheduler must place the Pod on a node that can physically access the storage. Cloud block disks (EBS, Azure Disk) are zone-specific — an EBS volume in us-east-1a cannot attach to a node in us-east-1b. With WaitForFirstConsumer binding mode, the provisioner creates the disk in the same zone as the node the Pod lands on — preventing the classic "volume not accessible in zone" error.

03

Provision — Create the Physical Storage

For dynamic provisioning, the CSI driver's external-provisioner sidecar watches for unbound PVCs and calls CreateVolume on the driver. This creates the actual cloud disk (AWS API, GCP API, Azure API). For static provisioning, an admin pre-created the PV — this step is skipped entirely.

04

Attach — Connect Disk to the Node

The external-attacher calls ControllerPublishVolume on the CSI driver — this attaches the block device to the node at the hypervisor level (e.g. tells AWS to attach EBS vol-0abc to EC2 instance i-0xyz). The disk now appears as /dev/nvme1n1 on the node but is not yet mounted. This step alone takes 10–45 seconds — it calls the cloud provider API.

05

Stage & Mount — Format and Make it a Filesystem

Kubelet calls NodeStageVolume: formats the device if new (e.g. mkfs.ext4), then mounts to a global staging path. Then NodePublishVolume: bind-mounts into the Pod's specific volume directory at /var/lib/kubelet/pods/<uid>/volumes/.

06

Bind-Mount Into Container Namespace

The container runtime (containerd) uses Linux mount --bind to project the Pod's volume directory into the container's mount namespace at your mountPath. The container sees it as a completely ordinary directory — it cannot tell it is a bind mount from outside its namespace.

07

Teardown — Full Reverse Chain on Pod Deletion

Pod deleted: ① containers stop → ② bind mounts removed from container namespaces → ③ NodeUnpublishVolume → ④ NodeUnstageVolume → ⑤ ControllerUnpublishVolume detaches disk from node. If reclaim policy is Delete, the cloud disk is destroyed. If Retain, disk and all data survive for manual recovery.

⚡
Why Pods With PVCs Start Slowly Steps 3 (provision) and 4 (attach) call cloud provider APIs. Provisioning a new EBS volume: ~10s. Attaching it to a node: ~20–40s. Total first-start penalty: 30–90 seconds before your app even begins. Set initialDelaySeconds on probes accordingly. Use pre-provisioned static PVs for latency-sensitive workloads.
§ 04 — Volume Types
Volume Types

Every Volume Type — Architecture & Deep Dive

Simple Explanation

Kubernetes provides over 20 volume types grouped into three families: Ephemeral (live and die with the Pod), Persistent (outlive the Pod via PVCs), and Config/Special (inject data from the Kubernetes control plane). Each solves a specific problem.

Official / Technical — Volume Type Classification

Kubernetes supports several types of volumes. The type of a volume determines where the data comes from, how the data persists, and how it is made accessible to a Pod. Volume types can be broadly categorized as follows:

Ephemeral volumes — backed by the local node; exist only for the lifetime of the Pod. Types include emptyDir, configMap, secret, downwardAPI, projected, and generic ephemeral volumes. Ephemeral volumes are specified inline in the Pod spec and are tightly coupled to the Pod's lifecycle.

Persistent volumes — backed by external storage systems that outlive Pod and node boundaries. These are consumed via PersistentVolumeClaim objects which abstract the underlying storage infrastructure. CSI-based storage is the standard for persistent volumes in modern Kubernetes clusters.

Host-local volumes — hostPath and local volumes reference paths on the node's filesystem directly. These have significant security and portability implications and should be used only for specific use cases such as system-level DaemonSets. Use of hostPath is strongly discouraged for general workloads due to security risks and node coupling.

emptyDir — Ephemeral Pod-Scoped Scratch Space

An empty directory created when a Pod is assigned to a node. Accessible to all containers in the Pod simultaneously. Survives container restarts (container crashes do not delete it). Permanently deleted when the Pod is removed from the node for any reason — node drain, pod deletion, eviction, or rescheduling.

Setting medium: Memory switches backing storage from the node's disk to RAM (tmpfs). Sub-millisecond I/O. Data counts against the container's memory limit and vanishes if the node restarts.

EphemeralPod-scopedAll containers share itOptional RAM backing
Official / Technical — emptyDir Specification

An emptyDir volume is first created when a Pod is assigned to a Node, and exists as long as that Pod is running on that node. All containers in the Pod can read and write the same files in the emptyDir volume, though that volume can be mounted at the same or different paths in each container. When a Pod is removed from a node for any reason, the data in the emptyDir is deleted permanently.

A container crashing does not remove a Pod from a node. The data in an emptyDir volume is safe across container crashes.

By default, emptyDir volumes are stored on whatever medium that backs the node such as disk, SSD, or network storage, depending on your environment. However, you can set the emptyDir.medium field to "Memory" to tell Kubernetes to mount a tmpfs (RAM-backed filesystem) for you instead. While tmpfs is very fast, be aware that unlike disks, tmpfs is cleared on node reboot and any files you write count against your container's memory limit.

A size limit can be specified for the default medium, which limits the total capacity of all files in the emptyDir. This storage is allocated from node ephemeral storage. If that quota is exceeded, the pod will be evicted.

emptyDir Architecture — Step by Step
1 / 4
Step 1 — Pod scheduled: kubelet creates empty directory on node disk

The moment the Pod is assigned to a node, the kubelet creates an empty directory on the node's disk (or in RAM). This happens before any containers start. The directory is already there when the first container begins.

Step 2 — Containers start: each gets a bind-mount at their mountPath

Both containers are bind-mounted to the same directory at different paths. Container A writes to /data/output.txt. Container B reads it immediately at /shared/output.txt. They are the exact same file — zero copying, zero latency.

Step 3 — Container A crashes: emptyDir data survives the restart

When Container A crashes and is restarted by Kubernetes, the emptyDir is completely untouched. The restarted container remounts /data and finds every file exactly as before. Container restart ≠ data loss for emptyDir.

Step 4 — Pod deleted: emptyDir permanently gone — use PVC to avoid this

When the Pod is deleted (or rescheduled to a new node), the kubelet deletes the emptyDir directory immediately. All files are permanently gone — no recovery possible. emptyDir is for temporary data only. Use PVC for anything you must keep.

emptydir-demo.yaml
# Two containers sharing an emptyDir — writer writes, reader reads
apiVersion: v1
kind: Pod
metadata:
  name: emptydir-demo
spec:
  containers:
  - name: writer
    image: busybox
    command: ["sh","-c","while true; do date >> /data/log.txt; sleep 5; done"]
    volumeMounts:
    - name: shared
      mountPath: /data
  - name: reader
    image: busybox
    command: ["sh","-c","tail -f /data/log.txt"]
    volumeMounts:
    - name: shared
      mountPath: /data    # same volume name = same directory
  volumes:
  - name: shared
    emptyDir:
      medium: ""        # ""=disk | "Memory"=RAM (tmpfs, faster, uses mem limit)
      sizeLimit: 500Mi # ALWAYS set — prevents node disk exhaustion & eviction
💡
When to use emptyDirSidecar log shipping (app writes, fluentd reads) · Init container handoff (init downloads files, main reads them) · Sort/merge scratch for batch jobs · Shared Unix sockets (app + Envoy proxy in same Pod)

hostPath — Direct Node Filesystem Access

Mounts a file or directory from the host node's filesystem directly into the Pod. Data persists across Pod restarts as long as the Pod stays on the same node. But it is completely node-local — if Kubernetes reschedules the Pod to a different node, it sees a completely different (possibly empty) directory.

The type field adds validation: Directory requires the path to exist, DirectoryOrCreate creates it if missing, Socket requires an existing Unix socket (used for container runtime access).

Survives container restartNode-local onlyMajor security risk
Official / Technical — hostPath Specification

A hostPath volume mounts a file or directory from the host node's filesystem into your Pod. This is not something that most Pods will need, but it offers a powerful escape hatch for some applications.

For example, some uses for hostPath are: running a container that needs access to Docker internals; use /var/lib/docker as a hostPath. Running cAdvisor in a container; use a hostPath of /sys. Allowing a Pod to specify whether a given hostPath should exist prior to the Pod running, whether it should be created, and what it should exist as.

In addition to the required path property, you can optionally specify a type for a hostPath volume. The supported values for the type field are: "" (empty string, default), DirectoryOrCreate, Directory, FileOrCreate, File, Socket, CharDevice, BlockDevice.

Warning: HostPath volumes present many security risks, and it is a best practice to avoid the use of HostPaths when possible. When a HostPath volume must be used, it should be scoped to only the required file or directory, and mounted as ReadOnly. If restricting HostPath access to specific directories through AdmissionPolicy, volumeMounts MUST be required to use readOnly mounts for the policy to be effective.

hostPath Architecture — Step by Step
1 / 3
Step 1 — Node directory bind-mounted directly into the container

The node's /var/log directory is bind-mounted into the container at /host-logs. The container reads the real node logs — the exact same files as the node's OS sees. No copy, no sync — the literal same directory via a Linux bind mount.

Step 2 — DaemonSet: 1 Pod per node, each reads its own node's logs

A DaemonSet runs exactly one Pod per node. Each Pod mounts its own node's /var/log via hostPath. Each Pod sees only the logs from its specific node — never another node's logs. This is the canonical, correct use of hostPath.

Step 3 — Why hostPath is dangerous & what to use instead

hostPath breaks container isolation. A container with hostPath: / can read /etc/shadow. A container with Docker socket access can spawn privileged containers and escape. Only use hostPath in DaemonSets that genuinely need node-level access, always with readOnly: true.

hostpath-daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
spec:
  template:
    spec:
      containers:
      - name: log-collector
        image: fluent/fluent-bit
        volumeMounts:
        - name: varlog
          mountPath: /host-logs
          readOnly: true  # always readOnly unless you must write
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
          type: Directory
          # types: File|Directory|Socket|CharDevice|BlockDevice
          #        FileOrCreate|DirectoryOrCreate
⚠
Never Use hostPath for Application DataIf the Pod is rescheduled to a new node, it gets a completely different (possibly empty) directory. Data on the old node becomes inaccessible. Use PVC for all application data. hostPath is for DaemonSets only.

configMap — Live Configuration Files with Auto Hot-Reload

A ConfigMap stores configuration data as key-value pairs. Mounted as a volume, each key becomes a filename and its value becomes the file content. Files are read-only. When you update the ConfigMap with kubectl apply, Kubernetes automatically refreshes the mounted files inside running containers within ~60 seconds — no Pod restart needed.

Important exception: subPath mounts do NOT auto-update. They are frozen at the time the container started. Use full directory mounts for hot-reload.

Read-onlyHot-reload ~60sKey = filenamesubPath = no hot-reload
Official / Technical — configMap Volume Specification

The configMap resource provides a way to inject configuration data into Pods. The data stored in a ConfigMap can be referenced in a volume of type configMap and then consumed by containerized applications running in a Pod.

When referencing a ConfigMap, you provide the name of the ConfigMap in the volume. You can customize the path to use for a specific entry in the ConfigMap using the items field. If you omit items, every key in the ConfigMap is placed into a file with the same name as the key. Note that the mounted ConfigMap data is updated automatically in the running Pod; the kubelet checks whether the mounted ConfigMap is fresh on every periodic sync. However, the kubelet uses its local cache for getting the current value of the ConfigMap.

A ConfigMap mounted using a subPath volume mount will not receive ConfigMap updates. subPath mounts bypass the symlink mechanism used for atomic updates, which means the file is frozen at container start time.

The total size of a ConfigMap's data and binaryData fields must be less than 1 MiB. If you need to store data that is larger than this limit, consider mounting a volume or using a separate database or file service.

configmap-volume.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  app.properties: |
    server.port=8080
    db.host=postgres-svc
  nginx.conf: |
    server { listen 80; root /usr/share/nginx/html; }
---
spec:
  containers:
  - name: app
    volumeMounts:
    # Full mount → /etc/app/app.properties + /etc/app/nginx.conf (hot-reloads ✓)
    - name: config-vol
      mountPath: /etc/app
    # subPath: mounts single key as specific file path (does NOT hot-reload ✗)
    - name: nginx-conf
      mountPath: /etc/nginx/nginx.conf
      subPath: nginx.conf
  volumes:
  - name: config-vol
    configMap:
      name: app-config
      defaultMode: 0644
      items:                        # optional: filter + rename specific keys
      - key: app.properties
        path: application.properties # rename key to different filename
  - name: nginx-conf
    configMap:
      name: app-config

secret — Sensitive Data, Mounted from RAM, Never on Disk

Secret volumes work identically to configMap volumes — each key becomes a file — but with critical security differences: Secret files are backed by tmpfs (RAM) on the node, so they are never written to disk. Secrets are only delivered to nodes that are running Pods which request them, minimizing exposure. Data disappears when the Pod is deleted.

Base64 is NOT encryption — it is just encoding. Enable etcd encryption at rest. Better yet, use the Secrets Store CSI Driver (Vault, AWS Secrets Manager) so secrets never enter etcd at all.

Sensitivetmpfs = RAM onlyRBAC requiredEncrypt etcd at rest
Official / Technical — Secret Volume Specification

A secret volume is used to pass sensitive information, such as passwords, to Pods. You can store secrets in the Kubernetes API and mount them as files for use by Pods without coupling them to Kubernetes directly. Secret volumes are backed by tmpfs (a RAM-backed filesystem) so they are never written to non-volatile storage.

Secrets are only sent to a node if a Pod on that node requires it. The kubelet stores the secret into a tmpfs so that the secret is not written to disk storage. Once the Pod that depends on the secret is deleted, the kubelet deletes its local copy of the secret data as well.

Note: A container using a Secret as a subPath volume mount does not receive automated Secret updates. Individual secrets are limited to 1MiB in size.

Kubernetes Secrets are, by default, stored unencrypted in the API server's underlying data store (etcd). Anyone with API access can retrieve or modify a Secret, and so can anyone with access to etcd. For production clusters: enable Encryption at Rest for Secrets; enable or configure RBAC rules that restrict reading and writing the Secret; restrict Secret access to specific containers; consider using external Secret management solutions (HashiCorp Vault, AWS Secrets Manager) via the Secrets Store CSI Driver.

secret-volume.yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  username: YWRtaW4=              # base64("admin") — NOT encrypted!
  password: U3VwZXJTZWNyZXQxMjM= # base64("SuperSecret123")
---
spec:
  containers:
  - name: app
    volumeMounts:
    - name: db-creds
      mountPath: /var/secrets/db
      readOnly: true     # ALWAYS readOnly for secrets
    # App reads: fs.readFileSync('/var/secrets/db/password', 'utf8').trim()
    # Creates: /var/secrets/db/username and /var/secrets/db/password
  volumes:
  - name: db-creds
    secret:
      secretName: db-credentials
      defaultMode: 0400   # r-------- owner read-only. NEVER 0644 for secrets!

persistentVolumeClaim — The Standard for All Durable Storage

The Pod references a PVC by name, and Kubernetes mounts whatever cloud disk, NFS share, or Ceph pool the PVC is bound to. Data persists independently of the Pod — delete the Pod, recreate it on any node, and it reattaches to the same data. Even node failure cannot destroy the data (it lives in a cloud disk).

This is the recommended approach for all stateful applications. Your Pod YAML never mentions cloud-specific details — just the PVC name. The PVC abstracts away whether storage is AWS EBS, GCP PD, Azure Disk, or NFS. Identical YAML, any cloud.

Survives Pod deletionDynamic provisioningCloud-portableResizable online
Official / Technical — PersistentVolumeClaim Volume

A persistentVolumeClaim volume is used to mount a PersistentVolume into a Pod. PersistentVolumeClaims are a way for users to "claim" durable storage (such as a GCE PersistentDisk or an iSCSI volume) without knowing the details of the particular cloud environment.

A PersistentVolume (PV) is a piece of storage in the cluster that has been provisioned by an administrator or dynamically provisioned using Storage Classes. It is a resource in the cluster just like a node is a cluster resource. PVs have a lifecycle independent of any individual Pod that uses the PV.

A PersistentVolumeClaim (PVC) is a request for storage by a user. It is similar to a Pod. Pods consume node resources and PVCs consume PV resources. Pods can request specific levels of resources (CPU and Memory). Claims can request specific size and access modes (e.g., they can be mounted ReadWriteOnce, ReadOnlyMany, ReadWriteMany, or ReadWriteOncePod).

The interaction between PVs and PVCs follows this lifecycle: Provisioning (static or dynamic) → Binding (a control loop in the control plane watches for new PVCs and finds a matching PV to bind to it) → Using (Pods use claims as volumes) → Releasing (when a user is done with their volume, they can delete the PVC object) → Reclaiming (the reclaim policy tells the cluster what to do with the volume after it has been released from its claim).

pvc-volume.yaml
# Step 1: Developer requests storage — no cloud-specific details needed
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: postgres-data
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-ssd  # gp3 on AWS, pd-ssd on GCP, Premium_LRS on Azure
  resources:
    requests:
      storage: 50Gi
---
# Step 2: Pod references PVC by name only — no cloud details anywhere
spec:
  containers:
  - name: postgres
    image: postgres:15
    env:
    - { name: PGDATA, value: /var/lib/postgresql/data/pgdata }
    volumeMounts:
    - name: pg-storage
      mountPath: /var/lib/postgresql/data
  volumes:
  - name: pg-storage
    persistentVolumeClaim:
      claimName: postgres-data  # just the name — all cloud details abstracted away

nfs — Network File System: Shared Multi-Node Read-Write

NFS mounts an NFS server export into Pods via the network. The critical advantage: NFS supports ReadWriteMany (RWX) — multiple Pods running on different nodes can all read and write the same directory simultaneously. Cloud block storage (EBS, Azure Disk) can only attach to one node at a time (RWO).

In production, use the NFS Subdir External Provisioner or AWS EFS CSI Driver for dynamic NFS provisioning. Direct NFS volumes require the NFS server to be pre-provisioned and reachable from all cluster nodes.

ReadWriteManyMulti-node concurrentPre-provision required
Official / Technical — NFS Volume Specification

An nfs volume allows an existing NFS (Network File System) share to be mounted into a Pod. Unlike emptyDir that is erased when a Pod is removed, the contents of an nfs volume are preserved and the volume is merely unmounted. This means that an NFS volume can be pre-populated with data, and that data can be shared between Pods. NFS can be mounted by multiple writers simultaneously.

NFS volumes support the ReadWriteMany access mode, making them suitable for workloads that require concurrent read/write access from multiple Pods across multiple nodes — a capability not supported by block storage types such as awsElasticBlockStore, gcePersistentDisk, or azureDisk.

You must have your own NFS server running with the share exported before you can use it in Kubernetes. For production use, the NFS Subdir External Provisioner or cloud-managed equivalents such as AWS EFS CSI Driver are recommended for dynamic provisioning of NFS-based PersistentVolumes.

nfs-pv-pvc.yaml
apiVersion: v1

  name: nfs-pv

projected — Merge Multiple Sources Into One Mount Path

Projects multiple volume sources — Secret, ConfigMap, ServiceAccountToken, DownwardAPI — into a single mounted directory. Without projected, you need separate volumeMounts entries for each source. With projected, everything appears under one path like /var/run/pod-info/.

The serviceAccountToken source generates short-lived, audience-scoped JWTs — automatically rotated before expiry. Much more secure than the legacy auto-mounted token (which never expires). Required for OIDC-based auth with Vault, AWS IAM, etc.

Multi-sourceSingle mountPathAuto-rotating tokensDownwardAPI
Official / Technical — Projected Volume Specification

A projected volume maps several existing volume sources into the same directory. The following volume types can be projected: secret, configMap, serviceAccountToken, downwardAPI, and clusterTrustBundle.

All sources are required to be in the same namespace as the Pod. The serviceAccountToken source is particularly important for security: it uses the TokenRequest API to obtain a bound service account token, scoped to an audience, with a configurable expiration time. This supersedes the deprecated auto-mounted token and is required for workloads that authenticate to external services (e.g. Vault, AWS IAM via IRSA) using OIDC-based identity federation.

The downwardAPI source within a projected volume exposes Pod and container metadata (such as Pod name, namespace, labels, annotations, resource limits) as files. This allows processes within containers to discover information about themselves without relying on Kubernetes API access.

projected-volume.yaml
# All 4 sources merged into /var/run/secrets/combined/
volumes:
- name: pod-credentials

    - secret:
        name: db-credentials  # creates: /combined/username, /combined/password
    - configMap:
        name: app-config     # creates: /combined/app.properties
    - serviceAccountToken:
        path: sa-token      # creates: /combined/sa-token (auto-rotated JWT)

        items:

            fieldPath: metadata.name

csi — Container Storage Interface: The Modern Driver Standard

CSI is the official Kubernetes storage extension API. Before CSI, adding a new storage provider required patching Kubernetes source code. Now any vendor ships a standalone driver (installed as a DaemonSet + Deployment) implementing the gRPC CSI spec. All major cloud providers now ship CSI drivers. All in-tree plugins are being removed in Kubernetes 1.29+.

CSI drivers enable features impossible with in-tree plugins: volume snapshots, online resize, volume cloning, topology-aware provisioning, and storage capacity tracking. Use CSI for all new storage integrations.

Industry standardOut-of-tree driversSnapshots + ResizeVolume cloning
Official / Technical — CSI Volume Specification

The Container Storage Interface (CSI) defines a standard interface for container orchestration systems (like Kubernetes) to expose arbitrary storage systems to their container workloads. CSI drivers allow storage vendors to develop a plugin once and have it work across multiple container orchestration systems.

CSI volumes can be used as an ephemeral inline volume (defined directly in the Pod spec, without a PersistentVolumeClaim) or as a persistent volume provisioned via a StorageClass. Inline CSI volumes allow storage drivers to manage ephemeral, Pod-scoped volumes — this is the mechanism used by the Secrets Store CSI Driver to inject secrets from external providers.

CSI drivers consist of two components: the Controller Plugin (runs on the control plane or any node, handles volume provisioning, deletion, attaching, detaching, and snapshotting via the ControllerServer gRPC service) and the Node Plugin (runs as a DaemonSet on every node, handles the node-specific operations via the NodeServer gRPC service: staging, mounting, and unmounting volumes into Pod directories).

The Kubernetes SIG Storage community maintains a set of CSI sidecar containers (external-provisioner, external-attacher, external-resizer, external-snapshotter) that act as adapters between the Kubernetes API and CSI driver RPCs, eliminating the need for driver authors to write Kubernetes-specific controller code.

§ 06 — Persistent Volumes
Persistent Storage

PersistentVolume & PersistentVolumeClaim

What is a PersistentVolume (PV)?

A PersistentVolume is a real piece of storage that exists in your cluster — independent of any Pod or application. Think of it as a disk registered with Kubernetes. It could be an AWS EBS volume, a GCP Persistent Disk, an NFS share, or a local disk. Kubernetes manages it as an object, just like it manages Pods and Services.

The key property of a PV: it outlives any Pod that uses it. When your Postgres pod dies, restarts, or moves to another node — the PV and its data remain completely intact.

Official Definition — PersistentVolume

A PersistentVolume (PV) is a piece of storage in the cluster provisioned by an administrator or dynamically by a StorageClass. It is a cluster-level resource with a lifecycle independent of any individual Pod. A PV captures the implementation details of the storage — the NFS server address, the EBS volume ID, the Ceph pool — abstracting these away from the workload that consumes it.

PVs are non-namespaced objects. They can be created statically by an admin pointing to existing infrastructure, or dynamically by a provisioner when a PVC requests storage that matches a StorageClass. The PV object includes capacity, access modes, reclaim policy, volume mode, and the volume plugin-specific configuration.

What is a PersistentVolumeClaim (PVC)?

A PVC is a request for storage. A developer writes "I need 50Gi of fast storage, read-write from one node" — without knowing anything about the underlying disks. Kubernetes matches this request to an available PV and binds them together. The Pod then uses the PVC like a normal volume — it never sees the PV directly.

PVCs are namespace-scoped (unlike PVs which are cluster-scoped). Each application team can manage their own PVCs without seeing or touching the underlying infrastructure.

Official Definition — PersistentVolumeClaim

A PersistentVolumeClaim (PVC) is a namespaced API object that expresses a user's request for storage. Claims can request specific size, access modes (RWO, ROX, RWX, RWOP), volume mode (Filesystem or Block), and StorageClass. The PVC abstracts the underlying storage technology from the workload author.

The PV controller in the control plane continuously reconciles unbound PVCs against available PVs. When a suitable PV is found — or dynamically provisioned — the controller sets status.phase on both objects to Bound and records the cross-reference: the PV's spec.claimRef points to the PVC, and the PVC's spec.volumeName points to the PV.

Why Use PVs? — Benefits & When to Use

💾

Data Survives Pod Deletion

Pods are ephemeral — Kubernetes kills them constantly. PVs decouple data from the container lifecycle. Delete the Pod, redeploy, scale to zero — the data is always on the disk, untouched.

🔒

Developer / Admin Separation

Admins provision real storage (PVs). Developers claim storage (PVCs) without needing to know the cloud provider, disk type, or credentials. Clean separation of concerns.

☁️

Cloud Portability

PVC YAML is identical across AWS, GCP, and Azure. Only the StorageClass changes per cluster. Your application manifests are truly cloud-portable.

✅

When to Use PVs

Use PVs for: databases (Postgres, MySQL, MongoDB), message queues (Kafka, RabbitMQ), user uploads, ML model storage, CI/CD artifact caches, and any data that must outlive a Pod restart.

🔄

When NOT to Use PVs

Do NOT use PVs for: temporary scratch space (use emptyDir), config files (use ConfigMap), secrets (use Secret), or stateless apps that store nothing. PVs have cost and latency overhead.

📈

Resize, Snapshot, Clone

PVs support online resize (no downtime), point-in-time snapshots for backup/DR, and volume cloning for creating staging environments from production data.

Cluster Architecture — Multi PV & Multi PVC

Interactive — Complete Cluster: Nodes, Pods, PVCs, PVs, Storage
1 / 6
Step 1 — Full Cluster: 2 Nodes, 4 Pods, 3 PVCs, 3 PVs, 3 Disks

A real cluster with 2 nodes, 4 pods, 3 PVCs, and 3 cloud disks. Each stateful pod references its own PVC. The stateless nginx pod uses no PVC. PVCs are namespace-scoped; PVs and their backing disks are cluster-scoped. Notice RWX (app-uploads via EFS) allows multiple pods to share it, while RWO (pg-data, redis-data) are exclusive.

Step 2 — How Binding Works: PVC Matches a PV

The PV controller checks 4 criteria: matching storageClassName, matching accessModes, sufficient capacity (PV capacity ≥ PVC request), and matching label selector. The first PV that satisfies all four criteria gets bound. If none match, the PVC stays Pending until a suitable PV appears or is dynamically provisioned.

Step 3 — Multiple Matching PVs: Which One Gets Chosen?

When multiple PVs all match the criteria, Kubernetes always picks the smallest PV that satisfies the request — to minimize wasted capacity. A 30Gi PVC will bind to a 40Gi PV before a 100Gi PV. To guarantee a specific PV is used, use spec.volumeName in the PVC or label selectors on both PV and PVC.

Step 4 — After Every Rollout: App Always Binds to Same Volume

The secret: the PVC persists across Pod lifecycles. The PVC is not deleted when the Pod is deleted — it stays Bound to the same PV. The next Pod (v2) references the same PVC by name, so it automatically gets the same EBS volume and all its data. StatefulSets make this explicit with volumeClaimTemplates — each replica gets a stable, named PVC that never changes across rollouts.

Step 5 — Can Two PVCs Share the Same PV?

RWO (block storage): A PV can only be bound to one PVC at a time. It is exclusive. Once PVC-A binds to a PV, PVC-B cannot bind to the same PV — it stays Pending until a separate PV is found. RWX (NFS/EFS): Multiple PVCs can bind to the same NFS PV simultaneously — all Pods on all nodes read and write the same shared directory.

Step 6 — Guaranteeing Same Volume After Every Rollout

Three strategies to ensure an app always binds to the same volume: volumeName (hardcode the PV name — for static provisioning), StatefulSet with volumeClaimTemplates (recommended — PVC name is stable across rollouts so it always remounts the same PV), or label selectors (flexible matching for complex environments). StatefulSet is the gold standard.

How to Bind a PVC to a PV — All Methods

The standard approach. PVC declares a storageClassName and the provisioner automatically creates a matching PV. No admin work needed. The PVC will always rebind to the same PV after pod restarts because the PVC object persists.

  name: fast-ssd

  name: postgres-data

Can Different Claims Share the Same Volume?

The Rules on PV Sharing

RWO PVs (block storage) — One PVC at a time. Exclusive binding. Once PVC-A binds, no other PVC can bind to that PV until PVC-A is deleted and the PV is reclaimed.

RWX PVs (NFS/EFS) — Multiple PVCs can bind to the same PV simultaneously. All Pods across all nodes read and write the same directory. True concurrent shared storage.

ROX PVs — Multiple PVCs can bind for read-only access. Used for distributing ML models or static assets to many Pods.

Official — Access Mode and Binding Exclusivity

A PersistentVolume can be mounted on a host in any way supported by the resource provider. Each PV gets its own set of access modes that describe the specific capabilities of that particular volume. A volume can only be mounted using one access mode at a time, even if it supports many.

PVs that use the ReadWriteOnce access mode can only be bound to a single PVC. The binding is exclusive: once a PV is bound to a PVC, that PV is unavailable to other claims. The ReadWriteMany access mode allows the volume to be mounted as read-write by many nodes simultaneously, which also means many PVCs in different namespaces can reference the same RWX PV.

Note that ReadWriteOncePod (RWOP, available since Kubernetes 1.22) is even stricter than RWO: it ensures only a single Pod across the entire cluster can mount the volume with read-write access — not just a single node. This prevents split-brain scenarios in critical single-writer workloads.

§ 08 — StorageClass
Dynamic Provisioning

StorageClass

Simple Explanation

A StorageClass enables dynamic provisioning — Kubernetes automatically creates a PV (and the underlying cloud disk) when a PVC is created. Zero manual PV management.

Official / Technical — StorageClass API

A StorageClass provides a way for administrators to describe the classes of storage they offer. Each StorageClass contains the fields provisioner, parameters, and reclaimPolicy, which are used when a PersistentVolume belonging to the class needs to be dynamically provisioned. The name of a StorageClass cannot be changed after creation.

The volumeBindingMode: WaitForFirstConsumer field delays volume binding and dynamic provisioning until a Pod consuming the PVC is created. This ensures PersistentVolumes are provisioned in the same topology zone as the scheduled Pod — critical for zone-restricted storage like AWS EBS, GCE Persistent Disk, and Azure Disk.

When allowVolumeExpansion: true is set, users can resize PVCs by editing the claim object. The control plane orchestrates the resize through the CSI driver's ControllerExpandVolume and NodeExpandVolume RPCs, enabling online filesystem expansion without Pod restart in most cases.

✓
Dynamic Provisioning Flow
PVC created → Kubernetes sees StorageClass → calls provisioner → creates cloud disk → creates PV → binds PV to PVC → Pod mounts volume. No admin action needed.

Project 2 — Multi-Container Log Pipeline (Sidecar Pattern)

log-pipeline.yaml
apiVersion: v1
kind: Pod
metadata:
  name: log-pipeline
spec:
  containers:
  # Container 1: App — writes logs to shared emptyDir
  - name: app
    image: myapp:latest
    volumeMounts:
    - { name: shared-logs, mountPath: /var/log/app }
    - { name: app-config,  mountPath: /etc/app }
    - { name: tmp-cache,   mountPath: /tmp }

  # Container 2: Fluentd sidecar — ships logs to Elasticsearch
  - name: fluentd
    image: fluent/fluentd-kubernetes-daemonset:v1
    env:
    - { name: FLUENT_ELASTICSEARCH_HOST, value: elasticsearch-master }
    volumeMounts:
    - { name: shared-logs,   mountPath: /var/log/app, readOnly: true }
    - { name: fluentd-config, mountPath: /fluentd/etc }

  # Container 3: Prometheus node exporter
  - name: exporter
    image: prom/node-exporter
    volumeMounts:
    - { name: host-proc, mountPath: /host/proc, readOnly: true }

  volumes:
  # Shared between app + fluentd
  - name: shared-logs
    emptyDir:
      sizeLimit: 2Gi

  # RAM-backed temp space
  - name: tmp-cache
    emptyDir:
      medium: Memory
      sizeLimit: 256Mi

  # ConfigMaps
  - { name: app-config,    configMap: { name: app-config } }
  - { name: fluentd-config, configMap: { name: fluentd-config } }

  # Node /proc for metrics
  - name: host-proc
    hostPath: { path: /proc, type: Directory }
§ 14 — Best Practices
Best Practices

Storage Best Practices

Official / Technical — Production Guidance from kubernetes.io

Dynamic provisioning is the recommended approach. Use StorageClasses with WaitForFirstConsumer to ensure volumes are created in the same availability zone as the consuming Pod. Set a default StorageClass with the annotation storageclass.kubernetes.io/is-default-class: "true".

Resource quota: Use ResourceQuota objects to limit PVC consumption per namespace. This prevents a single team from exhausting cluster-wide storage capacity and supports chargeback models.

PodSecurityAdmission: The Restricted PSA policy prohibits hostPath volumes and restricts volume types to those considered safe. The Baseline policy disallows the most dangerous hostPath configurations. Enforce these policies in production namespaces to prevent privilege escalation through volume mounts.

VolumeSnapshot: The VolumeSnapshot API (GA in Kubernetes 1.20) provides a standardized mechanism for point-in-time snapshots of PVCs. Snapshots are stored as VolumeSnapshot objects and backed by VolumeSnapshotContent objects, analogous to the PVC/PV relationship. They can be used to provision new PVCs from a snapshot (restore) or to clone volumes (dataSource referencing an existing PVC).

Storage Capacity Tracking: When storageCapacity: true is set on a StorageClass, the CSI driver reports available storage capacity per topology segment. The scheduler uses this information to avoid scheduling Pods to nodes where PVC provisioning would fail due to insufficient capacity.

⚡

Use StorageClass Always

Prefer dynamic provisioning. Set a default StorageClass. Use WaitForFirstConsumer for zone-aware storage.

📊

Always Set sizeLimit

Without a sizeLimit on emptyDir, a runaway process can fill the node disk and cause all Pods to be evicted.

🔐

Encrypt Secrets at Rest

Enable etcd encryption for Secrets. In production, use external secret managers (Vault, AWS Secrets Manager) via CSI.

🛡️

Retain Policy in Production

Use reclaimPolicy: Retain on production StorageClasses. Delete causes irreversible data loss on accidental PVC deletion.

📸

Snapshot Before Changes

Always take a VolumeSnapshot before DB migrations, upgrades, or destructive operations. CSI snapshots are fast and cheap.

🚫

Avoid hostPath in Prod

Use hostPath only for DaemonSets that genuinely need node-level access. It breaks Pod portability and is a security risk.
